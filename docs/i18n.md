# Internationalization (i18n)

The English lessons are canonical. Translated **lesson** markdown is **never committed to `main`** — it lives on a separate configured branch (`translations` by default), and the site fetches it at runtime the same free way it fetches English (`raw.githubusercontent.com`). Most enabled locales are machine-generated; Simplified Chinese (`zh`) is human-maintained and the workflow refuses to overwrite it. No Vercel functions, no KV, no per-view cost. Per-language **README** files are also hand-authored for quality and committed to `main` (see below).

This pipeline covers lessons under `phases/` only. Certification curricula remain English-only and are intentionally excluded from both machine translation and book generation.

The default engine for machine-managed locales is **NLLB-200** ([No Language Left Behind, Meta AI, 2022](https://arxiv.org/abs/2207.04672)), an open translation model covering 200 languages, which runs **inside the GitHub Actions runner with no API key and no bill**. Compute is the free CI runner; there is no translation-API cost at all. Paid LLM providers (Anthropic/OpenAI) and DeepL remain available as optional higher-quality upgrades via `--provider`. Human-maintained locales cannot be passed to the translation script.

## Pieces

The `languages.json` registry drives lesson translation and the site switcher. The per-language **README is separate**: its language set and translated blocks live in `scripts/readme_translations.py`, hand-authored for quality and independent of the registry.

| Piece | Where | Committed to main? |
|-------|-------|--------------------|
| Language registry | `languages.json` | Yes (one small file) |
| Lesson translation script | `scripts/translate_lessons.py` (prose-only walker; refuses `manual` locales) | Yes |
| README generator + translations | `scripts/build_readme_i18n.py` + `scripts/readme_translations.py` (hand-authored) | Yes |
| CI workflow | `.github/workflows/translate.yml` (sharded per language × phase) | Yes |
| Translated lesson markdown | configured translation ref (`translations` by default), `i18n/<lang>/…/<lang>.md` | No (separate branch) |
| Translated README | `i18n/<lang>/README.md`, linked from the header of `README.md` | **Yes** |
| Translated books | `scripts/build_book.py --lang <code>` builds from a locally restored, complete `i18n/<lang>/` tree and fails closed if any lesson is missing, stale, structurally invalid, or would fall back to English; the release workflow currently publishes English only | No |
| Switcher options | `site/langs.js` (generated by `build.js` from published `source`/`ci`/`manual` entries) | No (gitignored, like `data.js`) |
| Site switcher | `site/lesson.html` | Yes (the UI + fetch logic) |

## Add a language

Add one entry to `languages.json`, the single source of truth. Fields:

- `code` — the tag used in filenames, URLs, and the switcher value.
- `name` — English name, used in the LLM-provider prompt.
- `native` — label shown in the switcher.
- `nllb` — the FLORES-200 code (e.g. `zho_Hans`, `tur_Latn`); **required** for the default NLLB provider — `translate_lessons.py` exits if a requested language has none.
- `ci` — `true` opts a non-source, non-manual language into the automatic push-triggered build matrix. `workflow_dispatch` may request any registered machine-managed language.
- `manual` — `true` means lesson translations are maintained by people. The locale appears in the site switcher, but both automatic and manually dispatched machine-translation jobs reject it.

The translation matrix selects `ci: true` entries that are not `manual`. The site switcher emits `source`, `ci`, and `manual` entries, so a published human-maintained locale remains selectable without entering the machine-translation queue. The README bar is independent: it can list any language `readme_translations.py` covers.

## How it runs

1. A push to `main` that changes `phases/**/docs/en.md`, `languages.json`, or the translation workflow itself triggers `.github/workflows/translate.yml`. Certification lesson changes do not trigger it. Human-maintained locales are excluded even when requested through `workflow_dispatch`. The prepare job validates `AIFS_TRANSLATION_REF`; it enables publishing only when `AIFS_TRANSLATION_REPOSITORY` is the current repository and otherwise records that the configured external source is read-only and skips the translation matrix.
2. For machine-managed locales with publishing enabled, the matrix is **one job per (language, phase)**. A full 523-lesson language run is ~27h on a CPU runner, far past the 6-hour job limit, so a per-language job always timed out before publishing. Splitting by phase keeps the largest job (phase 19, 85 lessons) near ~4.5h, well under the limit. Each job restores its language's prior output from the configured repository/ref, runs `translate_lessons.py --phase <phase>`, audits the completed phase, and pushes only its own `i18n/<lang>/phases/<phase>/` slice back to that same ref with a fetch-and-retry loop, so disjoint slices merge without collisions.
3. The site's language switcher sets `?lang=<code>`; `fetchLesson` pulls `i18n/<lang>/…/<lang>.md` from the configured translation repository and ref and **falls back to canonical English** if that translation isn't published yet. English (`lang=en`) remains tied to the active deployment repository and ref, so fork previews render their own English edits.

## Published translation source

The site build, curriculum audit, and translation publisher share two configuration names: `AIFS_TRANSLATION_REPOSITORY` (`owner/repository`) and `AIFS_TRANSLATION_REF` (a branch name). Their defaults are the repository being built or checked and `translations`, respectively. Set both names to the same values as GitHub Actions repository variables and as deployment environment variables (for example, in Vercel). The publisher restores, rebases, and pushes through one dedicated remote at that exact ref; the generated site metadata keeps this translation source separate from `ACTIVE_REPOSITORY` and the active preview ref used for English.

The built-in publisher deliberately uses `github.token`, whose write permission is scoped to the workflow's current repository. It runs when `AIFS_TRANSLATION_REPOSITORY` is the current `github.repository`, including when `AIFS_TRANSLATION_REF` selects a non-default branch. If `AIFS_TRANSLATION_REPOSITORY` points elsewhere, that source is **read-only** for this workflow: the prepare job emits an explicit notice and skips the translation matrix instead of generating unpublishable work or silently pushing to the current repository. Publishing to an external repository therefore requires a separate explicitly credentialed workflow; the site and curriculum audit may continue to consume that external source.

Before a fork publishes its configured translation branch, the curriculum job records that the branch is absent and skips the lesson audit. It does not hide network, authentication, or other remote failures. The language remains selectable on the site, but a missing translated file falls back to English from the active repository/ref. Once the configured branch exists, CI fetches that exact repository/ref and the translation audit becomes blocking.

## GitHub Pages mirror

`.github/workflows/deploy-pages.yml` builds `site/` and publishes it with the official GitHub Pages artifact workflow on every push to `main`, plus manual dispatches. The build reads GitHub Actions' repository and branch metadata, so a fork serves its own English source and defaults to the same repository's `translations` branch. Publish that branch before `main`; otherwise translated lesson requests fall back to English until the branch becomes available.

The Pages deployment is a static mirror. The canonical site remains `https://aiengineeringfromscratch.com`, and its canonical, Open Graph, sitemap, and `llms.txt` URLs intentionally keep that origin. GitHub Pages does not implement the Vercel rewrites, response headers, or `/api/markdown` content negotiation declared in `vercel.json`; use the explicit `.html` routes on the mirror. Enable **Settings → Pages → Source: GitHub Actions** before the first deployment.

## Never wastes a run

For machine-managed locales, every lesson is keyed by the `sha256` of its English source and the provider that generated it in a per-(language, phase) cache (`i18n/<lang>/.cache/<phase>.json`), written per lesson in the runner and **published to the configured translation ref when the job finishes**. Legacy bare-hash entries are treated as NLLB output by the translator and upgrade to provider-aware records when regenerated, but the auditor and translated-book preflight require current structured records. Human-maintained locales use a separate strict record with the three required fields needed to bind reviewed prose to its inputs: `source_sha256`, `output_sha256`, and `provider: "manual"`. The source hash uses the canonical English text after universal-newline normalization; the output hash covers the translated file's actual bytes. Bare hashes, missing fields, another provider marker, stale English, or modified translated bytes all fail the audit. `manual` is deliberately not a machine translator provider and cannot be selected through `translate_lessons.py`. So:

- For a machine-managed locale, the first run translates everything once. Later runs skip a lesson only when its English hash and provider match the cache, its output exists, and integrity checks pass. Changing the source or provider, deleting the output, or failing integrity checks regenerates that lesson.
- A cancelled or interrupted machine-translation phase job does not publish, so it loses that job's runner-local progress and the next run resumes that phase from the **last published** cache. Because each shard is a single phase, it comfortably finishes and publishes within the job limit.
- For a human-maintained locale, changing either the English source or translated file makes the audit fail until a person reviews the translation and refreshes both hashes in its structured provenance record.

## Per-language README

The README is the landing page, so its translations are **hand-authored** (highest quality) rather than machine-generated, and they live in `main` at `i18n/<lang>/README.md`. `scripts/readme_translations.py` holds prose and heading translations keyed by the exact English block. Simplified Chinese additionally uses `i18n/zh/catalog/*.json` for all 20 phase descriptions and 523 lesson titles, plus `i18n/zh/readme-structural.json` for visible list, table, badge, and HTML copy that is outside ordinary prose blocks. `scripts/build_readme_i18n.py` rebuilds each file from the canonical English README. Code fences, commands, identifiers, language names, and link/image targets stay unchanged; repo-root-relative targets receive the required `../../` prefix. Other languages may fall back to English, but Simplified Chinese is complete by contract: every current prose span, lesson row, phase, and other visible structural line must be translated or explicitly allowlisted, and stale keys are rejected.

`python3 scripts/build_readme_i18n.py --check` runs in CI (`curriculum.yml`) and fails if any committed README is stale. It also fails when Simplified Chinese would fall back to English, misses any of the 523 lesson titles or 20 phase entries, leaves a visible structural line unclassified, or contains stale inventory keys. The README-counts bot regenerates translated READMEs whenever it syncs the English stats block.

Use `python3 scripts/audit_translations.py --lang zh` to audit the human-maintained lesson tree directly from a normal clone's local `origin/translations` remote-tracking ref, without checking it out. CI continues to fetch the source selected by `AIFS_TRANSLATION_REPOSITORY` and `AIFS_TRANSLATION_REF` and passes that exact ref to the auditor. The audit requires a one-to-one lesson path set, complete structured provenance keys, current English and translated-output SHA-256 values, valid non-empty UTF-8 Chinese content, no unresolved protection sentinels, no substantive verbatim English prose, and preserved heading, fence, table, raw-HTML, code, math, link, and URL structure. Pass `--translation-ref <ref>` to match a different published source, `--phase <phase-directory>` to check one CI shard, or `--translation-root <directory>` to audit a locally restored `i18n/` tree instead.

## What is protected during translation

NLLB is a sentence translator, not an instruction-following model, so the walker never lets it see anything but prose. It processes the lesson line by line: fenced code blocks, raw HTML, display math, and metadata lines (`**Type:** … **Time:**`) pass through verbatim. Markdown table structure and separator rows stay fixed while visible cell text is translated. In prose and table cells, inline code, inline math, image/link destinations, technical tokens, and URLs are protected; visible emphasis and link/image labels remain translatable. Human-maintained translations must preserve every English metadata key used by the canonical lesson (`Type`, `Language` or `Languages`, `Prerequisites`, `Phases exercised`, `Time`, and optional `Related`) but may localize their values. Fence parsing respects the marker character and opening length, and one-line `$$ … $$` math does not hide the prose that follows.

This is verified mechanically: running the walker with an identity "translation" reproduces all **523 lessons byte-for-byte**, so a real run can only ever change prose. If a placeholder fails to round-trip, that lesson keeps its English (fail-safe).

## Cost

Default provider `nllb`: **free** for machine-managed locales. NLLB-200 runs in the GitHub Actions runner — no API key, no secret, no per-token bill. The only resource is free CI compute; the model is cached between runs, and unchanged lessons are reused only when their source hash, provider, output, and integrity checks still match. Vercel cost does not change.

Optional upgrades (`--provider anthropic|openai|deepl`) give higher fluency at low-tens-of-dollars per full pass per language, if you later want to polish a high-traffic language. Those providers read the key from the `LLM_API_KEY` environment variable (DeepL uses the same variable for its auth key). NLLB stays the zero-cost default.

## Quality sample

Below are excerpts from `05 · 03 Word Embeddings`, showing that prose reads naturally while code, math, `king - man + woman`, technical terms, and the metadata header survive untouched. The Simplified Chinese (`zh`) excerpt is a **human-maintained example**, not output generated by NLLB or Anthropic. The Turkish excerpt illustrates the fluency available from an optional LLM provider; the free NLLB-200 default is typically plainer.

### 简体中文 (zh)

> # 词嵌入 —— 从零实现 Word2Vec
>
> > 词以其所处的语境为意。用一个浅层网络训练这个想法,几何结构便会自然浮现。
>
> **Type:** Build · **Languages:** Python · **Prerequisites:** 阶段 5 · 02(BoW + TF-IDF)、阶段 3 · 03(从零实现反向传播) · **Time:** 约 75 分钟
>
> **问题** —— TF-IDF 知道 `dog` 和 `puppy` 是不同的词,但不知道二者含义几乎相同。在 `dog` 上训练的分类器无法泛化到讨论 `puppy` 的评论。你可以靠列举同义词勉强弥补,但这在罕见词、领域术语,以及所有你未曾预料的语言上都会失效。
>
> 你想要的是这样一种表示:`dog` 和 `puppy` 在空间中彼此靠近;`king - man + woman` 落在 `queen` 附近;在 `dog` 上训练的模型能免费地把部分信号迁移到 `puppy`。
>
> **核心概念** —— **分布假说**(Firth,1957):"要了解一个词,就看它与哪些词为伴。" Word2Vec 有两种形式:**Skip-gram** 给定中心词预测周围词(窗口为 2 时 `cat -> (the, sat, on)`);**CBOW(连续词袋)** 给定周围词预测中心词。网络只有一个隐藏层且无非线性:输入是词表上的 one-hot 向量,输出是 softmax,训练后丢弃输出层,隐藏层权重即为嵌入。诀窍是用**负采样(negative sampling)**把对 10 万词的 softmax 转成二分类。

### Türkçe (tr)

> # Kelime Gömmeleri —— Word2Vec'i Sıfırdan
>
> > Bir kelime, birlikte bulunduğu kelimelerden ibarettir. Bu fikri sığ bir ağ ile eğitin, geometri kendiliğinden ortaya çıkar.
>
> **Type:** Build · **Languages:** Python · **Prerequisites:** Aşama 5 · 02 (BoW + TF-IDF), Aşama 3 · 03 (Sıfırdan Geri Yayılım) · **Time:** ~75 dakika
>
> **Problem** —— TF-IDF, `dog` ve `puppy`'nin farklı kelimeler olduğunu bilir ama neredeyse aynı anlama geldiklerini bilmez. `dog` üzerinde eğitilen bir sınıflandırıcı, `puppy` hakkındaki bir yoruma genelleme yapamaz. Eş anlamlıları listeleyerek geçiştirebilirsiniz, ama bu; nadir terimlerde, alana özgü jargonda ve öngöremediğiniz her dilde başarısız olur.
>
> `dog` ve `puppy`'nin uzayda birbirine yakın düştüğü, `king - man + woman`'ın `queen`'e yakın indiği bir temsil istiyorsunuz. Word2Vec bunu verdi: iki katmanlı bir ağ, trilyon token'lık eğitim, 2013'te yayımlandı.
>
> **Kavram** —— **Dağılımsal hipotez** (Firth, 1957): "Bir kelimeyi birlikte bulunduğu kelimelerden tanırsın." İki tür: **Skip-gram** merkez kelimeden çevredekileri tahmin eder (pencere 2 ile `cat -> (the, sat, on)`); **CBOW** çevredekilerden merkezi tahmin eder. Ağın doğrusal olmayan aktivasyonu olmayan tek bir gizli katmanı vardır: girdi one-hot vektör, çıktı softmax'tır; eğitimden sonra çıktı katmanı atılır, gizli katman ağırlıkları gömmelerdir. Püf nokta, 100 bin kelimelik softmax'ı **negatif örnekleme (negative sampling)** ile ikili sınıflandırmaya çevirmektir.

Note how `dog`, `puppy`, `king - man + woman`, `softmax`, `one-hot`, `Skip-gram`, `CBOW`, `TF-IDF`, `Word2Vec`, and the `**Type:** / **Time:**` labels stay verbatim in both languages while the surrounding prose is fully localized. Machine-managed output is constrained by protection/restore checks, and the human-maintained `zh` tree is held to the same structural invariants by the translation audit.
