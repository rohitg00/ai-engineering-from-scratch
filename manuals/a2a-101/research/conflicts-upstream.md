Commit [`cfc9d34`](https://github.com/a2aproject/A2A/commit/cfc9d34bc41e368827eb6446d31f912e44f795c5), PR [#1997](https://github.com/a2aproject/A2A/pull/1997), merged 2026-07-21. What an implementer does differently: a card that advertises a `GRPC` interface may now put a bare `host:port` in `url`; a client must not reject a gRPC interface whose `url` has no scheme. This resolves D34 and is the only change queued for 1.0.2.

### 2.2 New §7.6.4 In-Task Authorization Scope

Commit [`6550d34`](https://github.com/a2aproject/A2A/commit/6550d344b39c11f3ba64131f4841c8f6fd8e2754), PR [#2081](https://github.com/a2aproject/A2A/pull/2081), merged 2026-07-30 (gitvote). New text:

> The `TASK_STATE_AUTH_REQUIRED` state signals that additional authorization is required to continue processing a Task. The A2A protocol does not define the scope, representation, validity, or revocation semantics of the authorization decision or credential obtained in response to this state.
>
> Agents MUST NOT treat the `TASK_STATE_AUTH_REQUIRED` state transition, by itself, as authorization for any particular operation. ...
>
> A credential or authorization decision obtained while a Task is in `TASK_STATE_AUTH_REQUIRED` MUST NOT be assumed to authorize subsequent messages on the Task unless that behavior is explicitly defined by the implementation, credential issuer, or extension.

What an implementer does differently: a server that leaves `AUTH_REQUIRED` must re-check authorization on every later message rather than treating the state exit as a grant. The manual's §4.3 and §6.1 describe `AUTH_REQUIRED` without these two MUST NOTs.
