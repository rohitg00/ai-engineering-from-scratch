## a2a-tck: the Technology Compatibility Kit

### What it is

"A compatibility test suite that validates A2A (Agent-to-Agent) Protocol implementations across three transports: gRPC, JSON-RPC, and HTTP+JSON" ([README.md:3](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L3-L3)). It is a pytest project: `tck/` holds requirement specs, transport clients, validators and reporting; `tests/compatibility/` holds the conformance tests that need a running System Under Test (SUT); `tests/unit/` needs none ([AGENTS.md:7-35](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/AGENTS.md#L7-L35)). Package version `1.0.0`, license metadata `MIT` at the tag ([pyproject.toml:5-14](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/pyproject.toml#L5-L14)); `main` later aligned the license metadata (`cd34e1f`, "fix: align package license metadata (#199)").

### Protocol version

The bundled specification is a snapshot of the A2A repository's `v1.0.0` branch at commit `173695755607e884aa9acf8ce4feed90e32727a1`, downloaded 2026-03-13 ([specification/version.json:1-12](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/specification/version.json#L1-L12)); `main` carries the same pin. The TCK therefore targets v1.0.0, not the v1.0.1 patch the manual uses. JSON Schema (`a2a.json`) and generated proto stubs are derived from that snapshot (`specification/` directory; `make spec` and `make proto` regenerate them, [README.md:131-137](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L131-L137)).

### How to run it against a server

Clone and check out the tag, install, run:

```bash
git clone --filter=blob:none https://github.com/a2aproject/a2a-tck.git
cd a2a-tck
git checkout 1.0.0.alpha2
uv venv && source .venv/bin/activate
uv pip install -e .
./run_tck.py --sut-host http://localhost:9999
```

The install and quick-start lines are [README.md:12-34](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L12-L34); the bundled `run-tck` skill says to prefix the runner with `uv run` and to run from the TCK root ([.agents/skills/run-tck/SKILL.md:61-80](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/.agents/skills/run-tck/SKILL.md#L61-L80)). Python 3.11+ and `uv` are required ([README.md:7-8](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L7-L8)).

`run_tck.py` is a thin wrapper that builds one pytest command ([run_tck.py:34-72](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/run_tck.py#L34-L72)):

```
python -m pytest tests/compatibility/ --sut-host=<url> --tb=short
       [--transport=grpc,jsonrpc,http_json] [-m must|should|may] [-q|-v|-v -s --log-cli-level=INFO]
       --compatibility-report=reports/compatibility
       --html=reports/tck_report.html --self-contained-html
       --junitxml=reports/junitreport.xml [extra pytest args after --]
```

Flags ([README.md:40-51](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L40-L51)): `--sut-host URL` (required), `--transport LIST`, `--level must|should|may`, `-v`, `--verbose-log`, and `-- <pytest args>` (for example `-- -x --pdb`). One more pytest option is not in the README: `--webhook-host` names the host the SUT uses to reach the TCK's own webhook receiver for the push-delivery tests (default `localhost`) ([tests/compatibility/conftest.py:70-78](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tests/compatibility/conftest.py#L70-L78)); the receiver is a small `http.server` started once per session ([tck/webhook/server.py:1-5](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/webhook/server.py#L1-L5), [conftest.py:187-190](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tests/compatibility/conftest.py#L187-L190)).

Transport discovery: the TCK fetches `{sut-host}/.well-known/agent-card.json` and builds one client per `supportedInterfaces[]` entry, keyed by `protocolBinding` (`JSONRPC`, `GRPC`, `HTTP+JSON`) at that interface's `url`; with no interfaces it fails outright ([conftest.py:85-140](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tests/compatibility/conftest.py#L85-L140), [README.md:84-94](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L84-L94)). All three bindings are covered: gRPC, JSON-RPC and HTTP+JSON, each with its own test package ([tests/compatibility/grpc](https://github.com/a2aproject/a2a-tck/tree/1.0.0.alpha2/tests/compatibility/grpc), [jsonrpc](https://github.com/a2aproject/a2a-tck/tree/1.0.0.alpha2/tests/compatibility/jsonrpc), [http_json](https://github.com/a2aproject/a2a-tck/tree/1.0.0.alpha2/tests/compatibility/http_json)) and the cross-transport tests parametrized over `ALL_TRANSPORTS`.

SUT generation: Gherkin scenarios in `scenarios/` (`core_operations.feature`, `streaming.feature`) feed a code generator that emits a Java/Quarkus SUT into the a2a-java repository's `tck` module (`A2A_JAVA_DIR=... make codegen-a2a-java-sut`, [README.md:107-127](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L107-L127)); the tag also ships generated `sut/a2a-python` and `sut/a2a-jakarta` trees, and `main` documents both as targets (`make codegen-a2a-python-sut`, `uv run python sut_agent.py` on `:9999` and gRPC `:10000`; `make codegen-a2a-jakarta-sut`, `mvn wildfly:run`) ([main README.md:129-161](https://github.com/a2aproject/a2a-tck/blob/263b9cfaf16a554bdfb166a7ba5b67716e946349/README.md#L129-L161)).

### Compliance levels and categories

Levels follow RFC 2119 ([README.md:66-82](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L66-L82)):

| Level | Meaning | Test behavior |
|---|---|---|
| MUST | absolute requirement | hard failure |
| SHOULD | expected unless there is a reason to differ | `xfail`, does not block compatibility |
| MAY | optional | skipped when the agent card does not declare the capability |

Markers: `core`, `must`, `should`, `may`, `grpc`, `jsonrpc`, `http_json`, `streaming`, `integration` ([pyproject.toml:52-62](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/pyproject.toml#L52-L62), [tests/compatibility/markers.py:17-25](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tests/compatibility/markers.py#L17-L25)). Requirement families are identified by prefix ([AGENTS.md:46-52](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/AGENTS.md#L46-L52)); the registry at the tag defines: `CORE-SEND/STREAM/GET/LIST/CANCEL/EXECUTION-MODE/ERR/CAP/MULTI/HIST-*` ([tck/requirements/core_operations.py](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/requirements/core_operations.py)), `STREAM-*` (streaming.py), `PUSH-CREATE/GET/LIST/DEL/DELIVER-*` ([push_notifications.py](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/requirements/push_notifications.py)), `CARD-DISC/PROTO/STRUCT/EXT/SIGN/CACHE-*` ([agent_card.py](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/requirements/agent_card.py)), `AUTH-TLS/SERVER/INTASK/SCOPE-*` ([auth.py](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/requirements/auth.py)), `VER-CLIENT/SERVER-*` ([versioning.py](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/requirements/versioning.py)), `DM-*` (data_model.py), `BIND-*` (interop.py), `JSONRPC-FMT/SVC/ERR/SSE-*`, `HTTP_JSON-URL/SVC/QP/ERR/STATUS/SSE-*`, `GRPC-SVC/META/ERR-*`. Having a requirement ID does not mean having a test: requirements with an `operation` and no `multi-operation` tag are run generically (send the `sample_input`, validate the response against the JSON schema or proto type, run any custom validators) ([tests/compatibility/core_operations/test_requirements.py:68-83](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tests/compatibility/core_operations/test_requirements.py#L68-L83), [89-121](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tests/compatibility/core_operations/test_requirements.py#L89-L121), [149-195](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tests/compatibility/core_operations/test_requirements.py#L149-L195)); multi-operation ones need a dedicated test, and families such as `AUTH-SCOPE-*` and `CARD-SIGN-*` have no test at the tag (a grep of `tests/compatibility` finds no reference to them). The tag has 129 test functions; `main` has 135.

### What the report looks like

Four files land in `reports/` after every run ([README.md:96-105](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/README.md#L96-L105)): `compatibility.json`, `compatibility.html` (self-contained, with an executive summary, agent-card details and per-test results), `tck_report.html` (pytest-html) and `junitreport.xml`. The JSON has three parts ([tck/reporting/json_formatter.py:37-68](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/reporting/json_formatter.py#L37-L68)):

```json
{
  "summary": {"timestamp": ..., "sut_url": ..., "spec_version": ...,
              "overall_compatibility": "97.3%", "must_compatibility": ..., "should_compatibility": ..., "may_compatibility": ...},
  "per_requirement": {"CORE-SEND-002": {"level": "MUST", "status": "PASS", "transports": {"jsonrpc": "PASS", "grpc": "FAIL"}, "errors": [...], "test_ids": [...]}},
  "per_transport": {"jsonrpc": {"total": n, "passed": n, "failed": n, "skipped": n}},
  "agent_card": {...}
}
```

Per-requirement status is `PASS`, `FAIL` or `SKIPPED`, computed per transport and then combined (any failure fails the requirement) ([tck/reporting/aggregator.py:105-125](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/reporting/aggregator.py#L105-L125)); requirements in the registry that no test touched are listed as `NOT TESTED` ([aggregator.py:164](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/reporting/aggregator.py#L164-L164)). The percentages exclude `SKIPPED` and `NOT TESTED` rows ([aggregator.py:200-203](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/reporting/aggregator.py#L200-L203)); `main` fixed a bug where `NOT TESTED` counted as compatible (`cf4985b`, "#218"). The console prints a header, SUT and spec version, the overall percentage (green at 100%, yellow at 80% and above), a level table, a per-transport summary and the failed requirements ([tck/reporting/console_formatter.py:45-55](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/reporting/console_formatter.py#L45-L55), [71-80](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/reporting/console_formatter.py#L71-L80)). The HTML report links each requirement to the pinned specification source ([tck/reporting/html_formatter.py:22-32](https://github.com/a2aproject/a2a-tck/blob/1.0.0.alpha2/tck/reporting/html_formatter.py#L22-L32)).

## a2a-inspector: the browser debugger

### What it is

"A web-based tool designed to help developers inspect, debug, and validate servers that implement the A2A (Agent2Agent) protocol": connect to an agent by base URL, view its card, run "basic validation on the agent card", chat with the agent, and watch the raw messages in a debug console ([main README.md:3-13](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/README.md#L3-L13)). FastAPI backend plus a TypeScript frontend, joined by socket.io ([main README.md:5](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/README.md#L5-L5), [backend/app.py:15](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/app.py#L15-L15)).

### Which protocol version

The only release, `v0.1.0` (2025-06-18), predates v1.0: it depends on `a2a-sdk>=0.2.6` ([pyproject.toml:7](https://github.com/a2aproject/a2a-inspector/blob/v0.1.0/pyproject.toml#L7-L7)), requires a top-level `url` on the card ([backend/validators.py:9-20](https://github.com/a2aproject/a2a-inspector/blob/v0.1.0/backend/validators.py#L9-L20)), expects a `kind` discriminator and lowercase `role: "agent"` on every event ([validators.py:97-120](https://github.com/a2aproject/a2a-inspector/blob/v0.1.0/backend/validators.py#L97-L120)), and talks JSON-RPC only through `A2AClient` ([backend/app.py:221-223](https://github.com/a2aproject/a2a-inspector/blob/v0.1.0/backend/app.py#L221-L223)). It cannot inspect a v1.0 agent.

`main` (66 commits later, 2026-08-08) is the usable version: it depends on `a2a-sdk[all]>=1.1.2` ([pyproject.toml:7](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/pyproject.toml#L7-L7)), its validators accept "both v0.3 (Pydantic-based, camelCase JSON) and v1.0 (protobuf-based ...)" and list the differences they tolerate (no `final`, `TASK_STATE_*` names, flat parts, `supportedInterfaces`) ([backend/validators.py:1-15](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/validators.py#L1-L15)), and it builds the client with `ClientFactory` over JSON-RPC, HTTP+JSON and gRPC, falling back to the v0.3 constructor signature when the installed SDK is old ([backend/app.py:340-366](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/app.py#L340-L366), [586-592](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/app.py#L586-L592)). The transport actually used is the card's first interface ([app.py:131-148](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/app.py#L131-L148)). It reports the version it is speaking only indirectly, through the SDK it imports.

### What it checks

Agent card ([main validators.py:61-135](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/validators.py#L61-L135)): `name`, `description`, `version`, `skills` present; either `url` (absolute `http(s)`) or a non-empty `supportedInterfaces` whose entries have `url` and `protocolBinding` (or legacy `transport`); `capabilities` is an object; `defaultInputModes`/`defaultOutputModes` are arrays of strings; `skills` non-empty. Results arrive as `validation_errors` next to the card ([app.py:517-521](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/app.py#L517-L521)).

Each streamed event ([validators.py:138-214](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/validators.py#L138-L214)): a task has `id` and a recognised `status.state`; a status update has a recognised state; an artifact update has a non-empty `parts` array; a message has non-empty parts and role `agent`, `ROLE_AGENT` or `2`. The backend adds a `kind` (`task`, `message`, `status-update`, `artifact-update`) from the SDK type name and lowercases v1.0 state names before validation and display ([app.py:228-300](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/app.py#L228-L300)). It does not check the `A2A-Version` header, error codes, content types, pagination or any of the fourteen behaviors above; "spec compliance" here means the structural checks listed.

### How to run it

From `main` ([README.md:34-131](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/README.md#L34-L131)); prerequisites Python 3.10+, `uv`, Node.js and npm ([README.md:15-19](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/README.md#L15-L19)):

```bash
git clone https://github.com/a2aproject/a2a-inspector.git && cd a2a-inspector
uv sync
(cd frontend && npm install)
bash scripts/run.sh                       # frontend watch build + backend together
# or, in two terminals:
(cd frontend && npm run build -- --watch)
(cd backend && uv run -- uvicorn app:app --host 127.0.0.1 --port 5001 --reload)
# or Docker:
docker build -t a2a-inspector . && docker run -d -p 8080:8080 a2a-inspector
```

Then open `http://127.0.0.1:5001` (or `:8080` for Docker) and enter the agent's base URL. Custom request headers typed into the UI are forwarded to the agent, which is how a bearer token reaches an authenticated agent ([app.py:490-495](https://github.com/a2aproject/a2a-inspector/blob/8aa064639af106ff771d60428ef6d460f5454743/backend/app.py#L490-L495)).

## a2a-itk: the Integration Test Kit

It exists: https://github.com/a2aproject/a2a-itk, "Integration Testing Kit for A2A SDKs" (GitHub description), Apache-2.0, no tags or releases, `main` at `b57c5332` (2026-09-30). It is not a conformance checker for one server; it is a cross-SDK interoperability harness: "a technical toolkit designed to verify compatibility across different A2A SDK implementations and versions. It uses a multi-hop traversal model to ensure that messages can be routed across a cluster of agents using varied transport protocols (JSON-RPC, gRPC, and HTTP-JSON/REST), including support for streaming" ([README.md:7](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/README.md#L7-L7)).

How it works ([README.md:11-41](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/README.md#L11-L41)): a test runner sends one nested traversal instruction to Agent 1 over JSON-RPC; each agent resolves the next peer's card and forwards the rest over the scenario's transport; the trace comes back in the response (or, for push scenarios, is collected by a mock notification server at `GET /notifications`). Topologies are generated as Eulerian circuits (Hierholzer's algorithm) so every directed edge is exercised once ([README.md:42-49](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/README.md#L42-L49)). Behaviors: `send_message`, streaming, `push_notification`, and `resubscribe` (stream, disconnect, `SubscribeToTask`, then `CancelTask`) ([README.md:73-84](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/README.md#L73-L84)).

Peers are defined in `matrix.yaml`: Python, Go and TypeScript in both `v10` (repo `main`) and `v03` (`+itk` overlay tags) lines, Java, Rust and .NET in `v10` only, with per-line transport ceilings (`go_v03` has no `http_json`; `dotnet` has no `grpc`) ([matrix.yaml:25-52](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/matrix.yaml#L25-L52), [README.md:62-71](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/README.md#L62-L71)). Each SDK repository carries its own agent under `itk/` built from `protos/instruction.proto` ([README.md:277-281](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/README.md#L277-L281)). Broken pairs are listed in `known_failures.yaml`; two of them document SDK splits from this manual's matrix: a2a-rs has no v0.3 client at all, and a2a-rs's REST client sends `SubscribeToTask` as `GET`, which POST-only servers (the .NET SUT) reject ([known_failures.yaml:24-40](https://github.com/a2aproject/a2a-itk/blob/b57c5332aa883b27c1e5c915fe61cac76d2a1de9/known_failures.yaml#L24-L40)).

## Reading the four together

- The TCK is the only tool that grades a single server, and only against v1.0.0; of the fourteen split behaviors it pins down B6 and B10 (error present, code unchecked), B2 and B3 in part, and tests nothing about B1, B4-unset, B5 token rules, B9's inferred value, B11, B12 and B14; its content-type and gRPC-status expectations disagree with the specification in ways that penalise the SDKs that follow §11.1 and §5.4.
- The inspector shows traffic and catches malformed cards and events; it decides nothing about protocol conformance.
- The CLI is the fastest way to reproduce a split by hand (`-o jsonl --stream`, `--svc-param A2A-Version=...`, `task subscribe`, `server --exec`), but it is a client, with a2a-go's behaviors on the wire.
- The ITK answers the question the TCK cannot: whether two SDKs talk to each other, and its known-failures file is where the B1 verb split first shows up as a recorded incompatibility.
