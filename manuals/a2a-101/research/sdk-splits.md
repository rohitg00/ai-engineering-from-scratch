# A2A SDK splits: 14 behaviors across the official SDKs

Specification pinned to A2A v1.0.1 (2026-05-28); prose quotes are from `research/sources/specification.md` at that tag and proto quotes from `a2a.proto` at the same tag. The reference SDK is a2a-sdk (Python) 1.2.2. Compiled 2026-10-06 from the five per-SDK notes under `research/v2/notes/`, the wire captures in `research/sdk-wire/FINDINGS.md`, the Python clone at `research/a2a-python` (v1.2.2) and the capture kit at `/tmp/aiefs-manuals/manuals/a2a-101/capture/`. Every link is a permalink at the release tag; kit references are local file paths because the kit is not published.

Reading the tables: "Server" is what the SDK's request handler does on its 1.0 path; "Client" is what the SDK's own client sends. JSON-RPC errors always travel inside an HTTP 200 envelope in every implementation; only the REST status and the gRPC status vary. ".NET tag" means v1.0.0-preview2; where main (unreleased) differs the cell says so.

## 2. The fourteen behaviors

### B1. Which HTTP method the REST `SubscribeToTask` route accepts

**Specification.** The prose routes it as POST: §5.3 lists "Subscribe to task | `SubscribeToTask` | `SubscribeToTask` | `POST /tasks/{id}:subscribe`" and §11.3.2 says "`POST /tasks/{id}:subscribe` - Subscribe to task updates (SSE response, returns error for terminal tasks)". The normative proto routes it as GET: `a2a.proto` lines 76-82, `option (google.api.http) = { get: "/tasks/{id=*}:subscribe" additional_bindings: { get: "/{tenant}/tasks/{id=*}:subscribe" } }`.

### B2. When the server closes a stream

**Specification.** §3.1.2: "The stream MUST close when the task reaches a terminal state (`TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, `TASK_STATE_CANCELED`, `TASK_STATE_REJECTED`)." §3.1.6: "The stream MUST terminate when the task reaches a terminal state". §11.7: "then zero or more status or artifact update events until the task reaches a terminal or interrupted state, at which point the stream closes." §7.6.1: "the agent SHOULD maintain any active response streams with the client after setting the TaskState to `TASK_STATE_AUTH_REQUIRED`." The three statements do not agree on interrupted states.

## 4. Agreements: where every SDK agrees with each other and not with the specification

1. **Extended card authentication (B13).** §13.3 says the operation "MUST require authentication". Python, JS (callback form), Java, Go, .NET and Rust all hand the card to whoever asks unless the integrator adds a check outside the SDK core. Only the kit's deployer gates it, with a bearer check that runs before any A2A method.
2. **The `?A2A-Version=` request parameter (B7).** §3.6.1 allows clients to send the version "as a request parameter instead of a header". No single-version SDK server reads it: Python ([routes/common.py:113-122](https://github.com/a2aproject/a2a-python/blob/v1.2.2/src/a2a/server/routes/common.py#L113-L122) copies only headers), JS, Go, .NET and Rust read the header only; Java reads it only in the optional multi-version router. The kit reads both.
3. **The §6.4 version-error body.** §6.4 ("Version Negotiation Error") shows a version failure answered with HTTP 400 and a problem-details body that lists `supportedVersions`. Every SDK that rejects a version uses its ordinary A2A error envelope instead (`-32009` in a JSON-RPC error, or a `google.rpc.Status` body on REST) and none lists the supported versions in a structured field (Python's and Java's messages mention them in prose only).
4. **The push token header (B3).** §4.3.1 defines `PushNotificationConfig.token` but gives it no transport. Every SDK that pushes puts it in a custom header, under two spellings: `X-A2A-Notification-Token` (Python, JS, Java, kit) and `A2A-Notification-Token` (Go, Rust).
5. **Authorization scoping needs the integrator (B12).** §13.1 says servers "MUST implement authorization checks on every A2A Protocol Operations request". No SDK ships authentication, so the default deployment of every SDK (and the kit) serves every task to every caller; Java's fail-closed default denies everything rather than scoping, and Python, JS and Go scope only once something sets a user name.
6. **No `messageId` idempotency (B14).** Allowed by §3.3.1's MAY, but worth stating as an agreement: no implementation, kit included, detects a resent message, so a client retry without `taskId` always creates a second task.
7. **JSON-RPC errors travel in HTTP 200.** Every SDK and the kit answer JSON-RPC errors (including `VersionNotSupportedError`) with HTTP 200 and an `error` member; §9 does not say otherwise, but §6.4's 400 example does, and only JSON-RPC's own rules are followed.
