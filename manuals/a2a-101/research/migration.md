## D.1 What the pinned sources frame the change as

- docs whats-new-v1: "This document provides a comprehensive overview of changes from A2A Protocol v0.3.0 to v1.0. The v1.0 release represents a significant maturation of the protocol with enhanced clarity, stronger specifications, and important structural improvements."
- docs announcing-1.0: "The v1.0 release tightens specification behavior, which includes breaking changes in the interaction protocol. AgentCard, however, has evolved in a backward-compatible way and now allows agents to advertise support for both existing v0.3 protocol behavior and v1.0 simultaneously. This enables clients to migrate progressively rather than through a single cutover." and "The official SDKs ensure v1.0 A2A agents work seamlessly with older versions."
- spec §1.4, change control: "- Documentation: Migration guidance MUST be provided via an ancillary document when introducing major breaking changes." and "- SDK/Schema Aliases: SDKs and JSON Schemas SHOULD provide deprecated alias types/definitions to maintain backward compatibility."
- spec Appendix A: "This appendix catalogs renamed protocol messages and objects, their legacy identifiers, and the planned deprecation/removal schedule. All legacy names and anchors MUST remain resolvable until the stated earliest removal version."
- spec §3.6.2: "Agents CAN expose multiple interfaces for the same transport with different versions under the same or different URLs." (the mechanism the announcement calls "advertise support for both")

## D.3 What a server does when the version header is missing

Rule: spec §3.6.1 "(except for 0.3 Clients - 0.3 will be assumed for empty header)" and §3.6.2 "Agents MUST interpret empty value as 0.3 version." together with "If the version is not supported by the interface, agents MUST return a [`VersionNotSupportedError`](#332-error-handling)." So a 1.0-only interface MUST answer a header-less request with `VersionNotSupportedError`: JSON-RPC `-32009`, gRPC `FAILED_PRECONDITION`, HTTP `400 Bad Request` (§5.4), `ErrorInfo.reason` `VERSION_NOT_SUPPORTED`. The §6.4 sample ("Version Negotiation Error") shows the HTTP 400 body for an unsupported `0.5` (still in RFC 9457 shape: D13). The pinned sources say nothing about where in the pipeline the check runs (before or after authentication), nor about how a server that serves both 0.3 and 1.0 on one URL should separate the two beyond "CAN expose multiple interfaces".

What the SDKs do (server side; from `research/v2/notes/*.md` B7 cells plus a2a-python code):

| SDK | Missing or empty header | Unsupported value | Comparison | Where checked |
|---|---|---|---|---|
| a2a-python 1.2.2 | treated as `'0.3'`, then rejected by a 1.0 handler: `VersionNotSupportedError` (-32009; REST 400) | same error | exact match, else same major (`actual_v.major == expected_v.major`); patch ignored | `@validate_version(PROTOCOL_VERSION_1_0)` on every JSON-RPC and REST dispatcher method; **not** on the gRPC servicer |
| a2a-js 1.3.0 | `'0.3'`; rejected unless the card declares `0.3` for that binding | rejected | exact string against the card's `protocolVersion` | all three bindings (`-32009` with HTTP 200; REST 400; gRPC `FAILED_PRECONDITION`) |
| a2a-go 2.6.0 | accepted (header never read) | accepted | none | nowhere; `VersionNotSupported` is mapped but never emitted |
| a2a-java 1.4.0.Final | `0.3`, rejected: `-32009`, REST 400, gRPC `UNIMPLEMENTED` | rejected | major compared; needs `major.minor` form | per-binding handlers; the optional multiversion modules route `0.3` or absent to the 0.3 handler instead |
| a2a-dotnet 1.0.0-preview2 | JSON-RPC accepts missing, `1.0`, `0.3`; REST ignores the header | JSON-RPC `-32009` (HTTP 200) | exact strings | JSON-RPC only; main gRPC: absent accepted, only `"1.0"` accepted, `0.3` rejected |
| a2a-rs (server 0.5.1) | JSON-RPC: missing or empty becomes `"0.3"` and is rejected with `-32009` (HTTP 200) | `-32009` | major only | JSON-RPC only; REST and gRPC ignore it |
