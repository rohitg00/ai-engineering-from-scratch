# How this manual was made

> This page records the pin, the two machines, the lab method, each experiment with its machine and its count, and what the lab folder holds.

## The pin

The manual pins `langchain` 1.5.0, released on 2026-11-11 at commit `c2f4036e`. The same pin holds `langchain-core` 1.8.0, `langgraph` 1.2.22, `deepagents` 0.7.38, and `langsmith` 0.14.17. [Sources and conflicts](#s-ref-sources-and-conflicts) gives the commit of each package. We read the code and the docs and checked every fact on 2026-11-14.

The packages of the stack move fast, and their version numbers are not aligned. A statement in this manual is about the pin only. [Section 8.5](#s-migration-from-0-x-and-stale-advice) lists what differs in older code and older pages.

## Four kinds of evidence

Each fact carries one of four labels, and [the sources page](#s-ref-sources-and-conflicts) ranks them.

**The code:** a class, a default, or an error text read in the source at the tag. A paragraph says when we also ran it.

**A capture:** a listing from the capture kit, which drives the real stack. Where a capture needs a model, the model is Qwen3 4B Instruct on Ollama on the x86 server guest. The file names the model, its settings, the machine, and the date.

**We measured:** a number from one of our lab runs. The paragraph names the machine and the number of runs.

**The documentation:** a statement from the docs at commit `04d4d4a`. We use it for paths that this edition did not run, and the text says so.

## The lab method

- **Real models of the lab.** The local models were Qwen3 0.6B, 1.7B, 4B, 8B, 14B, and 30B-A3B, and gpt-oss 20B, on Ollama, with `nomic-embed-text` for embeddings. Qwen3 4B on the x86 server guest ran the failure drill, the runtime traces, and the T02 agent matrix. It also ran T05, T07, T08, T11, T17, T18, and T19, and the reruns of T10, T15, and T16. The other model runs of the lab ran on the Mac. The capture kit is apart from the lab, and it recorded on the x86 server guest.
- **The context on the guest.** The reruns of T10, T15, and T16 set a context of 8192 tokens. The other runs on the guest set none, so Ollama used its default context. During T02, `ollama ps` showed 4096. The prompts of those runs were short.
- **Hosted models on a budget.** Claude Haiku 5.5 (`claude-haiku-5-5`) and Claude Sonnet 5.5 (`claude-sonnet-5-5`) ran in the bench, through the Anthropic API from the Mac. A shared ledger recorded every call and its cost, and stopped the runs at a fixed cap. The bench spent $0.93 in 2,589 calls. Haiku ran the full suite, and Sonnet ran the 30-task subset. [The bench method](#s-ref-the-bench-method) gives the settings. Haiku also ran the 20 evals of [section 9.6](#s-evals-that-check-state) once, in 64 calls for $0.011353, with a ledger of their own. It ran the 60 file-rule attacks of T22 in 134 calls for $0.02136, and the ledger rows are in `T22-sec-fs-permissions-mac/`.
- **Stand-ins for the stack alone.** T03, T10, T15, and T16 on the guest used a model stand-in with a fixed delay, or no delay. Those times hold the cost of the stack and the database only. T10, T15, and T16 then ran again with Qwen3 4B, and sections 5.2, 5.5, and 8.1 show only those rows. T03 keeps its stand-in, because it measures checkpoint writes with no model.
- **Local recorders, proxies, and relays.** A recorder on `127.0.0.1` stood in for a LangSmith endpoint. For the streaming runs, a proxy in front of Ollama stamped each line it passed on. So the lab could time each token on one clock. For the retry runs, a relay in front of Ollama dropped or held each connection.
- **A new process for each step.** The crash, approval, and assistant runs started each step in a new Python process, so each resume was a restart.
- **Warm-up runs left out.** A file marks its warm-up rows, and the summary leaves them out. The raw files keep them.
- **One LangSmith account and no license.** T21 used a new LangSmith account on the free plan, from the Mac, against the hosted API. The kept files replace its ids with labels. We used no Agent Server license. [Section 8.8](#s-limits-at-the-pin-and-what-comes-in-the-next-edition) lists what that left out.
- **Small samples.** Many cases ran once or three times. Each paragraph gives its count, and a result from one run is an example, not a rate.

## What is in the lab folder

[The lab folder](manuals/langchain-101/capture/lab) holds one folder for each row of the table above, and the folder `summary`. 13 rows also keep an older Mac folder: T01, T02, T04, T05, T06, T07, T08, T11, T17, T18, T19, TRC, and the failure drill. The lab README marks which of its rows the x86 runs replaced. The rows of T10, T15, and T16 keep their older stand-in folder beside a second-pass folder that ends in `-real`.

- **Raw recordings.** Each experiment folder keeps the files of its run, unchanged, as JSON lines, logs, and text. A long log is kept as an excerpt whose lines are exact.
- **Scripts.** Many folders keep the lab scripts that made them, and the lab README names them. The demo folders hold the output of `run.sh` in `capture/demos/`.
- **Summaries.** `capture/run.py` computes one summary for each data set into `summary/`. Each chart reads one or two of the 48 summary files, or the summary of the bench, and each measured number comes from one. The production service keeps ten more summaries in its own folder, and `capture/labsum.py` rebuilds them from its raw runs.
- **A list of changes.** The README of the lab folder names every file that we cut, left out, or changed, with the reason.

No file holds a key, a token, or the name of a person. The only host names are `127.0.0.1` and the public hosts that recorded requests and error texts name, such as `api.smith.langchain.com`. The addresses and names in the test inputs are made up.

## The capture kit

[The capture kit](manuals/langchain-101/capture) drives the stack in one Python process, with no keys. It writes 56 files to `capture/out/`, and every listing in the manual is cut from one of them.

- **19 model-free files.** They call no model. They cover the versions, the messages, the tool schemas, the graph structure, and the Mermaid text of every graph the manual draws. They also cover durability, interrupts, reducers, the functional API, subgraphs, error handlers, and the recursion limit. They give the same bytes on every run.
- **36 recorded files and one sidecar.** 34 of them call `ChatOllama` on `qwen3:4b-instruct-2507-q4_K_M`, with temperature 0, seed 42, `num_ctx` 16384, and `num_predict` 512. The store, retrieval, and retrieval agent files call `OllamaEmbeddings` on `nomic-embed-text`, and two of them call no chat model. We recorded them on the x86 server guest, on CPU, on 2026-11-14. The first line under each title names the models, the settings, the machine, and the date.

No scenario uses a fake chat model. A failure comes from a tool that raises, from a port where nothing listens, or from a relay that drops connections. The decision middleware asks Qwen3 4B through a small adapter of the kit. No scenario uses a fake embedding. The store and retrieval scenarios embed with `nomic-embed-text` on the Ollama server of the guest.

```bash
cd manuals/langchain-101
python3 capture/run.py --model-free
python3 capture/run.py --check
python3 capture/run.py --check --live
```

The first command writes the model-free files and the lab summaries, offline. A plain `python3 capture/run.py` writes every file and needs Ollama.

The check runs the model-free scenarios again and compares each file byte for byte. For each recorded file, it checks the model line and the strings that the manual relies on. These are message types, tool names, and error texts. It then computes the summaries again and compares them. It prints one `skipped` line for the recorded scenarios and one for the lab runs. With `--live`, it records the model scenarios again into a temporary folder and checks the same structure.

## Record it again on your machine

1. Create the virtual environment of the kit from `capture/requirements.txt` with Python 3.13.
2. Install Ollama, pull the Qwen3 models, and start PostgreSQL for the experiments that use them.
3. Run the script of one experiment, from a folder that keeps one. Each script writes the files of its own folder.
4. Run `python3 capture/run.py` from the manual directory to compute the summaries again.

Your times will differ from ours, and so can the words of the model. The message types, the error texts, the checkpoints, and the order of events must not. If one of them differs at the pin, a claim of this manual depends on our machines.
