# 文件切塊策略橫向評析（Chunking Strategies, Compared）

> 文件切塊（Chunking）的邊界決定了檢索器在物理上所能觸及的最高上限。若切塊邊界出現了偏差，下游無論換上多麼強大的 embedding 模型、重排序器或大語言模型，皆無法挽回該處造成的資訊硬性損毀。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 11 lessons 04 (embeddings), 06 (RAG), 07 (advanced RAG); Phase 19 Track B foundations (lessons 20-29)
**Time:** ~90 minutes

## Learning Objectives｜學習目標
- 從零手寫實作五大經典切塊策略：固定字元視窗切塊、句子邊界切塊、遞迴階層切塊、語義分群切塊，以及 Markdown 結構標題切塊。
- 在包含黃金標準答案跨度（Gold-labeled Answer Spans）的測試語料庫上客觀度量 Recall@K，並解釋為何某些策略在一般散文中勝出，而另一些策略在技術文件上表現較佳。
- 解讀分塊長度分布，精確識別各策略所注入的經典失效模式：孤兒殘句、符號腰斬、空標題切塊、語義漂移。
- 在無需跑全套評測基準的前提下，透過審視文件類型、平均段落長度與顯式結構三大特徵，為全新語料庫選擇預設切塊策略。

## The Problem｜問題

每一個 RAG 檢索增強生成管線，皆始於將原始長文件切割為適當大小的文字碎片——既要足夠小以便塞入 embedding 模型的上下文視窗，又要足夠大以完整保留獨立自洽的語意脈絡。切塊邊界的選取絕非一個無足輕重的超參數；它直接為檢索器在物理上所能召回的知識設定了絕對的理論上限。

當使用者提問「預算熔斷的具體閾值設定是多少？」時，檢索器唯有在包含該熔斷閾值的切塊被成功召回時方能作答。若固定視窗切塊器將閾值數值與周圍上下文切開，該片段的 embedding 向量會移至不同的語義分群中，BM25 得分會下降，重排序器看到的只是雜訊，最終大模型生成的回答會是錯的。2024 年發布的重磅論文《LongRAG: Enhancing Retrieval-Augmented Generation with Long-context LLMs》實測證實：單純更動切塊邊界策略，便能在檢索召回率上引發高達 35% 的絕對波動差距！2025 年關於「上下文感知切塊標頭」的後續研究進一步縮小了差距，但並未消除差距。

本課將並列實作這五大核心策略，在標註有精確答案字符區間的測試語料上端到端執行，讓你親眼閱讀各策略在召回率維度上的真實客觀指標。

### 固定視窗切塊（Fixed-window）

最純粹的暴力對照基準。每隔 N 個字元機械式硬切一刀。可選擇設定重疊長度（Overlap），使得在位置 N 被腰斬的句子能在從 N - overlap 開始的下一個切塊中完整出現。其特點是執行極速、絕對確定性，但邊界極度糟糕。在工程實踐中適合作為對照，不宜作為預設策略。

### 句子邊界切塊（Sentence）

透過正規表示式或確定性狀態機在句子結束標點符號處實施切割。將一個或多個完整句子打包進單一分塊，直到觸及目標字元預算。徹底避免了在單詞中途被腰斬的尷尬，但依然無法避免在段落或章節中途中斷。許多早期 RAG 系統將其作為預設，適合處理缺乏顯式層次結構的一般散文。

### 遞迴階層切塊（Recursive split）

2023 年代各大開源庫廣泛推崇的層次化策略。優先嘗試在最高階的語意分隔符號處切分（如連續雙換行、段落分隔符）；若碎片依然過大，退回至次級分隔符號（單換行）；接著退回至句子邊界；最後才退化至字元。一旦分塊尺寸收斂至預算之內，遞迴立即終止。該策略在面對排版格式混亂複雜的文件時展現出極強的韌性，因為它能針對不同區域自適應收斂。

### 語義分群切塊（Semantic clustering）

為文件中的每一句話各自計算 embedding。沿著時序將圍繞在同一主題質心（Centroid）周圍的相鄰句子動態分群成塊。一旦後續句子與當前質心的餘弦相似度跌破設定閾值，立即執行切割。分塊邊界直接反映語義本質而非字元計數。缺點是建置較慢且強依賴於 embedding 模型，但在段落內部頻繁轉移話題的複雜文件中具備卓越的抗噪能力。

### Markdown 結構標題切塊（Structural markdown headers）

針對自帶顯式層次結構的規範文件（Markdown、reStructuredText、RFC 風格的編號章節），嚴格在標題邊界處切分。每個分塊包含該級標題及其下的所有內容，直到遇到同級或更高層級的新標題為止。它能產出主題最為純淨的微型切塊，但前提是原始語料庫具備標準清晰的結構排版。

### 如何以 Recall@K 精確度量切塊品質

在標註有黃金答案的查詢集中，每道提問皆精確記錄了標準答案在原始長文件中的具體字元起止偏移量（Offsets）。在切塊建立索引後，我們向檢索器提問：**被檢索召回的 Top-K 個切塊中，是否存在任意一個切塊與黃金答案區間發生了實體重疊？** 若存在，該查詢的 Recall@K 記為 1；若完全未覆蓋，記為 0。在整個查詢測試集上求平均。對五大策略重複運作完全相同的評估，輸出清晰的召回率排行榜，直接揭示哪一種切塊策略能征服你當前所擁有的特定語料庫。

## Build It｜動手實作

`code/main.py` 實作了以下核心模組：

- `fixed_window(text, size, overlap)`：固定字元視窗切塊對照基準。
- `sentence_chunks(text, target)`：句子邊界自適應打包器。
- `recursive_split(text, separators, target)`：階層化遞迴降級切塊演算法。
- `semantic_chunks(text, similarity_threshold)`：基於模擬 embedding 的語義質心動態分群器。
- `structural_markdown(text)`：感知 H1/H2/H3 標題的結構化切塊器。
- `mock_embed(text, dim)`：基於字串雜湊的確定性 embedding 函式，確保全流程離線自閉環。
- `DenseIndex`：輕量級向量索引庫，採用與第 19 階段 Track B 混合檢索課程相同的結構。
- `eval_recall(strategy, corpus, queries, k)`：端到端召回率評估迴圈。
- `main()` 函式：在內建的測試夾具語料庫上執行所有策略，印出標準的 Recall@K 評測對比表。

執行測試：

```bash
python3 code/main.py
```

輸出結果：展示一張矩陣表格，每行代表一種策略，每列代表不同的 K 值。句子切塊在結構化文件上表現較差；Markdown 結構切塊在 Markdown 夾具上表現最佳；遞迴切塊在混合語料上也能應付，因為遞迴會依區域調整；而語義分群切塊則在缺乏標題的一般散文語料中穩居榜首。

## 圖表無法掩蓋的五大經典失效模式

**孤兒殘句（Orphan sentences）**：句子打包器產出的切塊往往恰好遺漏了最關鍵的段落中心句。embedding 向量隨後直接指向完全錯誤的語義分群。

**符號腰斬（Mid-symbol cuts）**：固定視窗在程式碼或 YAML 中間硬生生切上一刀，將一個長變數名稱劈成兩半。這兩半碎片在向量化後皆退化為純粹的雜訊。

**純標題空切塊（Header-only chunks）**：Markdown 結構切塊器容易產出只包含一行 `## Title` 的無內容廢塊。必須在後處理中堅決過濾它們，或將其自動吸附至下一個切塊的首段。

**語義漂移（Semantic drift）**：當整篇文件自始至終皆圍繞同一主題展開時，語義分群切塊器會出現「過度貪婪不願切割」的病態現象，產出長達 5000 字元的超巨型切塊，將海量細節稀釋進泛化的平均向量中。必須為語義分群切塊器強制設定字元上限。

**過期的 embedding（Stale embeddings）**：語義分群會使用 embedding 模型。若更換模型，切塊也會改變。請將切塊模型與檢索模型分開固定，或一併重建索引。

## 免測選型的經驗法則

三大物理屬性，決定了面對未知全新語料庫時的最優預設選型：

| 語料庫關鍵特徵 | 具體取值形態 | 推薦的預設切塊策略 |
|---|---|---|
| 文件類型 | 無其他結構的散文 | 遞迴階層切塊（目標 800 字元） |
| 文件類型 | Markdown / RFC 標準 / API 技術文件 | Markdown 結構標題切塊 |
| 文件類型 | 原始碼程式碼檔案 | AST 語法樹感知切塊（參閱專案實戰 02） |
| 段落特徵 | 長段落，單段聚焦單一主題 | 句子邊界切塊（目標 500 字元） |
| 段落特徵 | 短段落，段內話題頻繁跳轉 | 語義分群切塊（相似度閾值 0.6） |

拿不定主意時，**可選擇遞迴階層切塊（Recursive Split）**。它是工程表現最為穩健的單一泛用型對照基準。

## Use It｜實際應用

正式環境實務做法：

- 在將全新 RAG 管線交付上線前，強制跑一次切塊策略對比評測；切勿盲目信賴第三方開源庫自帶的粗暴預設值。
- 每當更換底層 embedding 模型或調整語料庫來源時，重新運作該評估；最優切塊策略高度依賴於語料分佈。
- 在切塊的中繼資料中強制持久化儲存當前所採用的策略名稱，方便在後續排查檢索退化時精準溯源。

## Exercises｜練習

1. 引入第六種切塊策略：基於 `tiktoken` 統計真實 token 數量的滑動視窗切塊，而非單純計算字元數。在完全相同的夾具上與固定字元視窗展開對比。
2. 人為向純文字夾具中故意注入 30% 的程式碼區塊，重新執行對比矩陣。觀察除了 Markdown 結構切塊之外，其餘策略的召回率是否下降。
3. 將確定性模擬 embedding 替換為你專案所用提供者的真實 embedding 模型。重新度量語義分群的召回率變動 Delta，觀察各策略之間的差距是進一步拉大還是縮小。
4. 為每個切塊新增一個 `summary` 欄位，內容是一句話的質心描述。將該摘要拼接入分塊主體後重新測試 Recall@K，量化其帶來的召回增益。

## Key Terms｜關鍵術語

| 術語 | 常見說法 | 實際含義 |
|------|-----------------|------------------------|
| Recall@k | 「找到正確切塊了嗎？」 | 檢索召回率：被檢索出的 Top-K 個切塊中，成功覆蓋黃金標準答案區間的提問佔比 |
| Chunk overlap | 「滑動視窗」 | 在下一個分塊的開頭處，重複包含上一個分塊末尾的 N 個字元，用於保持跨邊界語義連續性 |
| Structural splitter | 「依標題切塊」 | 嚴格在 H1/H2/H3 等 Markdown 標題邊界處切割；標題文字本身是分塊內容的一部分 |
| Semantic chunker | 「依主題切塊」 | 對句子進行向量化，依據與動態質心的餘弦相似度分群，在話題漂移處實施切割 |
| Centroid drift | 「主題轉移」 | 當前累積段落的平均向量與下一句新輸入向量之間的餘弦相似度跌破安全閾值的現象 |
