# 影子流量、金絲雀發布與 LLM 漸進式交付（Shadow Traffic, Canary Rollout, and Progressive Deployment for LLMs）

> LLM 的上線發布融合了軟體工程中最艱難的挑戰：缺乏單元測試、故障模式極其發散瀰漫、線上回饋訊號嚴重滯後。標準發布順序為：(1) 影子模式（Shadow mode）——將正式環境的請求複製給候選模型，記錄並比較，不影響使用者；能有效排查顯著的輸入分佈異常，但絕非品質保證的充分條件；(2) 金絲雀發布（Canary rollout）——將真實使用者流量按 10% → 25% → 50% → 75% → 100% 階梯漸進切換，並在每個階段設立嚴格的發布閘門；追蹤延遲百分位數、單請求成本、錯誤與拒絕回答率、輸出長度分佈以及使用者回饋率；(3) A/B 測試——唯有在系統穩定性得到客觀證實後，才針對具備顯著行為差異的候選方案展開 A/B 測試。不可消除的隨機非確定性（Non-determinism）是全新常態——由於 GPU 浮點數運算不滿足結合律加上動態批次尺寸的隨機性，在完全相同的輸入下跨執行批次仍會產生高達 15% 的準確率波動。推論成本是一項動態變數，絕非固定常數——一個品質提升 20% 的模型，單次呼叫成本可能暴增 3 倍。回滾（Rollback）速度具有決定性意義：若回滾需要重新部署，那就太慢了。路由策略應當長駐於動態 Feature Flags 設定中；模型則存放於模型登錄（model registry）中，並固定 digest；秒級回滾 = 翻轉動態策略開關 + 還原閾值 + 鎖定舊版本 Digest。

**Type:** Learn
**Languages:** Python (stdlib, toy canary-progression simulator)
**Prerequisites:** Phase 17 · 13 (Observability), Phase 17 · 21 (A/B Testing)
**Time:** ~60 minutes

## Learning Objectives｜學習目標

- 嚴格區分影子模式（零使用者影響的被動對比）、金絲雀發布（真實線上流量的階梯漸進放量）與 A/B 測試（在系統已驗證穩定前提下的行為對比）三者的生命週期邊界。
- 列出 LLM 專屬的五項金絲雀指標（延遲百分位數、單請求成本、錯誤／拒答率、輸出長度分佈、使用者回饋）。
- 深刻解釋 LLM 的不可消除非確定性（高達 15% 波動）如何重新定義了發布過程中的「系統穩定」概念。
- 設計一套能在數秒內極速完成（純策略開關翻轉）、而非耗時數小時（重新部署）的標準回滾架構。

## The Problem｜問題

你剛剛交付了一款新模型。線下評測集顯示其準確率提升了 3%。你滿懷信心地在正式環境中全量切換上線。在短短 24 小時之內，雲端推論帳單暴增了 40%，使用者點踩（Thumbs-down）比例飆升了 8%，客服信箱收到了三起關於「回答邏輯荒腔走板」的緊急投訴。你匆忙啟動回滾。重新部署需要 3 個小時。團隊的週末徹底泡湯。

上述情況都可以避免。影子模式可在任何使用者看到成本增加 40% 前發現問題。金絲雀發布可在點踩率上升時於 10% 停止。使用策略開關回滾需時 30 秒。這種工程紀律填補了「線下評測看起來良好」與「真實使用者滿意」之間的落差。

## The Concept｜核心概念

### 影子模式（Shadow mode）

候選新模型接收與正式環境完全相同的真實請求；其輸出會被記錄，不會回傳給使用者。不影響使用者體驗。監控紀錄：

- 輸出文本內容（與當前線上模型逐行比對 Diff）。
- 產出 Token 消耗總量（評估實質成本增量）。
- 端到端延遲表現。
- 拒絕回答率與報錯異常。

能有效排查：成本失控暴增、輸出長度異常膨脹、明顯的拒答變化，以及底層崩潰硬報錯。無法排查：使用者肉眼可見的真實主觀語義滿意度。影子模式本質上是一場冒煙測試（Smoke test），絕非終極的品質保證。

### 金絲雀發布（Canary rollout）

配備多道自動化閘門的階梯式流量遞進切換。經典放量步長：1% → 10% → 25% → 50% → 75% → 100%。在每一個流量台階上，系統自動對照五大黃金指標進行硬性驗收：

1. **延遲百分位數（Latency percentiles）**——全面監控 P50、P95 與 P99。違規條件：金絲雀通道的 P99 延遲超過基準值的 1.5 倍。
2. **單請求成本（Cost per request）**——平均綜合費用（美元/請求）。違規條件：比基準線成本高出 20% 以上。
3. **錯誤與拒答率（Error / refusal rate）**——包含 5xx 伺服器錯誤以及模型明確拒答。違規條件：超過基準線的 2 倍。
4. **輸出長度分佈（Output length distribution）**——監控均值與 P99 長尾長度。違規條件：出現顯著的長度分佈漂移。
5. **使用者回饋率（User-feedback rate）**——點踩頻率與客服客訴工單量。違規條件：超過基準線的 1.5 倍。

### 非確定性是全新的隨機變異數（Non-determinism is the new variance）

在深度學習推論中，完全相同的輸入無法保證產出百分之百相同的輸出。根因在於：

- GPU 浮點數運算不滿足結合律（在高度並行環境下，求和歸約 Reduction 的物理順序隨批次動態變化）。
- 批次大小的差異。
- 取樣隨機性（溫度係數 Temperature > 0）。

實測證實：在完全相同的評測集上多次執行，得分會產生高達 15% 的天然隨機波動。在金絲雀放量中，「系統穩定」的定義絕非指標與歷史完全分毫不差，而是指標穩定收斂在預期的雜訊容差範圍之內。在配置發布閘門時，閾值必須設定在底層物理雜訊基準線之上。

### 成本是變數，絕非固定常數（Cost is a variable）

一個表現提升 20% 的模型，其單次呼叫的實質成本可能高達原先的 3 倍。單請求成本是五個閘門之一。發布的模型雖然表現更好，卻破壞單位經濟效益（Unit economics），這就可作為回滾理由。

### 回滾是武器（Rollback is the weapon）

- **策略開關（Policy flag，動態功能標記系統）**：直接在配置中秒級翻轉流量切分比例；耗時僅需數秒。
- **模型版本鎖定（Model pinning，模型登錄摘要）**：嚴格鎖定不可變的二進位 Digest 雜湊，堅決杜絕任何自動隱式升級。
- 秒級回滾實務 = 翻轉動態策略開關 + 將鎖定的 Digest 立即指向歷史前一個穩定版本。耗時以秒計算，絕非耗費數小時重新部署。

若你的技術堆疊需要重新部署才能回滾，請在發布前修正回滾流程。

### 工具鏈生態（Tooling）

**Argo Rollouts** / **Flagger**——Kubernetes 雲原生漸進式交付控制器。與 Istio / Linkerd 等服務網格深度整合，進行權重導流。

**Istio 加權路由（Weighted routing）**——在服務網格層級精確切分流量百分比。

**KServe / Seldon Core**——內建金絲雀功能的模型服務框架。

**功能開關系統（Feature flags）**——LaunchDarkly、Flagsmith、Unleash。在業務邏輯與策略層級，不需重新部署即可在數秒內切換旗標。

### 指標觀測節奏（Metrics cadence）

金絲雀閘門的評估週期通常設定為 5 至 15 分鐘，深度取決於實體流量規模。在每分鐘僅有 10 次請求的小流量系統中，1% 的流量切分在單個窗口內僅能收集到 50 至 150 個資料點——這足以評估基礎延遲，但對於使用者點踩等稀疏訊號而言充斥著劇烈雜訊。切換至 10% 則能獲得 10 倍樣本。在每個流量台階上必須強制停留足夠的觀測時間，累積充足的統計樣本量。

### A/B 測試是可選的進階步驟（The A/B step is optional）

若新模型差異明顯（行為、成本曲線或語氣不同），金絲雀通過後在 50% 流量上進行 A/B 測試。若只是改良版，金絲雀閘門通過後可直接提升至 100%。

### 務必銘記的核心數字指標（Numbers you should remember）

- 標準金絲雀放量階梯：1% → 10% → 25% → 50% → 75% → 100%。
- 模型非確定性天花板：在相同輸入下跨次執行存在高達 15% 的天然準確率波動。
- 五大金絲雀守護閘門：延遲百分位數、單請求成本、錯誤與拒答率、輸出長度、使用者回饋。
- 成本警戒條件：單請求成本高於基準線 20% 即為違規。
- 合格回滾標準耗時：必須在數秒內完成，絕不可耗費數小時。

## Exercises｜練習

1. 執行 `code/main.py`。主動注入一項增加 25% 的成本回歸缺陷。金絲雀控制器會在放量的哪一個具體百分比階梯強制終止發布？
2. 你的新模型在線下評測中展現出 3% 的準確率提升，但正式環境單請求成本增加了 18%。這項改動是否應該上線？依據策略，寫出兩種決策路徑。
3. 設計一套能在 60 秒內完成的端到端回滾流程，並列出所需基礎設施。
4. 由於底層非確定性，你的離線評測在相同條件下展現出 ±7% 的正常波動。在此物理現實下，你該如何科學設定金絲雀發布閘門的容差係數，以避免引發頻繁的假警報？
5. 影子模式在正式放量前成功攔截了一次潛在的 40% 成本暴漲事故。為影子通道撰寫會觸發警報的規則。

## Key Terms｜關鍵術語

| 術語 | 常見俗稱 | 實際工程意義 |
|------|----------------|------------------------|
| Shadow mode | 「複製到新版本」 | 將請求送給候選版本並記錄，不影響使用者 |
| Canary | 「逐步調整流量」 | 透過閘門逐步將新版本提供給使用者 |
| Gates | 「發布檢查」 | 阻止發布流程的指標門檻 |
| Non-determinism | 「LLM 輸出差異」 | 每次執行間無法消除的差異 |
| Policy flag | 「策略開關回滾」 | 在設定層級回滾，耗時以秒計而非小時 |
| Model pin | 「模型登錄摘要」 | 指向模型版本的不可變參照 |
| Argo Rollouts | 「Kubernetes 漸進式發布」 | Kubernetes 原生的金絲雀發布／回滾控制器 |
| KServe | 「Kubernetes 推論」 | 具備金絲雀機制的模型服務 |
| Istio weighted | 「網格流量切分」 | 服務網格流量切分器 |
