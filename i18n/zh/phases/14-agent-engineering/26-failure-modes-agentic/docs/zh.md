# 失效模式：智能体为何出问题

> MASFT（伯克利，2025）将 14 种多智能体失效模式归为 3 个类别。Microsoft 的分类法记录了现有 AI 失效在智能体（agentic）场景中如何被放大。行业现场数据收敛于五种反复出现的模式：幻觉动作、范围蔓延、级联错误、上下文丢失、工具误用。

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 05（Self-Refine 与 CRITIC），Phase 14 · 24（可观测性）
**Time:** 约 60 分钟

## 学习目标

- 说出 MASFT 的三个失效类别，以及每个类别中至少四种具体模式。
- 解释为什么智能体失效会放大现有的 AI 失效模式（偏见、幻觉）。
- 描述五种行业反复出现的模式及其缓解措施。
- 实现一个基于标准库的检测器，为智能体轨迹打上失效模式标签。

## 问题

团队上线的智能体在 90% 的轨迹上运行正常。那 10% 的失败并非随机噪声——它们落入少数几个反复出现的类别。一旦你能命名它们，就能监控并修复它们。

## 核心概念

### MASFT（伯克利，arXiv:2503.13657）

多智能体系统失效分类法（Multi-Agent System Failure Taxonomy）。14 种失效模式聚为 3 个类别。标注者间 Cohen's Kappa 为 0.88——这些类别是可可靠区分的。

核心主张：失效是多智能体系统中的根本性设计缺陷，而不是能靠更好的基座模型来修复的 LLM 局限。

### Microsoft 智能体 AI 系统失效模式分类法

- 现有 AI 失效（偏见、幻觉、数据泄露）在智能体场景中被放大。
- 自主性带来新的失效：大规模的意外动作、工具误用、使命漂移。
- 该白皮书是智能体产品的风险登记册。

### 智能体 AI 中的故障特征刻画（arXiv:2603.06847）

- 失效源于编排、内部状态演化以及环境交互。
- 而不仅仅是“坏代码”或“坏的模型输出”。

### LLM 智能体幻觉综述（arXiv:2509.18970）

两种主要表现形式：

1. **指令遵循偏离** — 智能体不遵循系统提示。
2. **长程上下文误用** — 智能体遗忘或误用早前轮次的上下文。

子意图错误：遗漏（缺失步骤）、冗余（重复步骤）、乱序（步骤顺序错乱）。

### 五种行业反复出现的模式

Arize、Galileo、NimbleBrain 2024–2026 的现场分析收敛于：

1. **幻觉动作。** 智能体调用不存在的工具或编造参数。
2. **范围蔓延。** 智能体将任务扩展到超出用户的要求（创建额外的 PR、发送额外的邮件）。
3. **级联错误。** 一次错误调用触发下游连锁反应。一次虚构 SKU 的幻觉触发四个 API 调用——一场多系统事故。
4. **上下文丢失。** 长时程任务遗忘早前轮次的约束。
5. **工具误用。** 用错误的参数调用正确的工具，或完全调用了错误的工具。

级联是最致命的。智能体无法区分“我失败了”和“任务不可能完成”，常常在收到 400 错误时幻觉出一个成功消息来“闭环”。

### 缓解措施：每一步都设关卡

在推理链的每一步设置自动化验证关卡，对照环境状态检查事实依据。具体包括：

- 逐步安全分类器（第 21 课）。
- 工具调用参数校验（第 06 课）。
- 将检索到的内容与已知事实交叉核对（第 05 课，CRITIC）。
- 通过重新探测状态来检测成功幻觉（文件真的被创建了吗？）。

### 失效监控的常见误区

- **只标记崩溃。** 大多数智能体失效产生看似有效的输出。需要内容级别的检查。
- **没有基线。** 漂移检测需要最近已知良好状态；没有它你就无法说“情况在变糟”。
- **告警过多。** 每个失效都触发一次呼叫。应聚类并限流。

## 动手构建

`code/main.py` 实现了一个基于标准库的失效模式标记器：

- 一个覆盖五种模式的合成轨迹数据集。
- 每种模式的检测函数（针对工具调用、输出、重复动作的签名模式）。
- 一个为每条轨迹打标签并报告模式分布的标记器。

运行方式：

```
python3 code/main.py
```

输出：逐轨迹标签 + 聚合分布，是对 Phoenix 轨迹聚类功能的一次低成本复现。

## 实际使用

- **Phoenix** 用于生产环境漂移聚类（第 24 课）。
- **Langfuse** 用于会话回放 + 标注。
- **自建方案** 用于你的可观测性平台无法检测的领域特定签名。

`outputs/skill-failure-detector.md` 生成针对你所在领域定制的失效模式检测器，并接入轨迹存储。

## 练习

1. 为“成功幻觉”添加一个检测器：智能体返回成功，但目标状态未改变。
2. 从你构建过的产品中标记 100 条真实轨迹。哪种模式占主导？修复它的成本是多少？
3. 实现一个“级联半径”指标：给定第 N 步的失效，它影响了多少下游步骤？
4. 阅读 MASFT 的 14 种失效模式。选出三种适用于你产品的模式，并编写检测器。
5. 将一个检测器接入 CI 任务：如果 >=5% 的轨迹标记出某种模式，则使构建失败。

## 关键术语

| 术语 | 人们的说法 | 实际含义 |
|------|----------------|------------------------|
| MASFT | “多智能体失效分类法” | 伯克利 14 模式分类体系 |
| 级联错误 | “涟漪式失败” | 一个早期错误在 N 步中传播 |
| 上下文丢失 | “忘了那个约束” | 长时程对话丢失早前轮次的事实 |
| 工具误用 | “错误的工具 / 错误的参数” | 调用有效，但调用方式错误 |
| 成功幻觉 | “伪造完成” | 智能体在收到 400 时声称成功；状态未改变 |
| 范围蔓延 | “越界” | 智能体做了超出要求的事 |
| 指令遵循偏离 | “不听话” | 忽视系统提示或用户约束 |
| 子意图错误 | “计划 bug” | 计划执行中的遗漏、冗余、乱序 |
