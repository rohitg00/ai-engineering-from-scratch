# 工具接口——为什么智能体需要结构化 I/O

> 语言模型产生的是 token，程序执行的是动作。二者之间的鸿沟就是工具接口：一份契约，让模型请求某个动作，由宿主来执行它。2026 年的每一个技术栈——OpenAI、Anthropic 和 Gemini 的 function calling；MCP 的 `tools/call`；A2A 的 task parts——都是同一个四步循环的不同编码方式。本课命名这个循环，并展示运行它所需的最小机制。

**Type:** Learn
**Languages:** Python (stdlib, no LLM)
**Prerequisites:** Phase 11 (LLM completion APIs)
**Time:** ~45 minutes

## 学习目标

- 解释为什么一个只能生成文本的 LLM 无法仅凭自身对现实世界采取行动。
- 画出四步工具调用循环（describe → decide → execute → observe），并说出每一步由谁负责。
- 将工具描述写成三个部分：名称、JSON Schema 输入，以及一个确定性的执行函数。
- 区分纯工具和有副作用的工具，并说明这种区分对安全性为何重要。

## 问题所在

LLM 输出的是下一个 token 的概率分布。这就是它全部的输出面。如果你问一个聊天模型“班加罗尔现在的天气如何”，它可以写出一个看似合理的句子，但它无法调用天气 API。这个句子可能是碰巧正确，也可能是三天前的过期信息。

弥合这一鸿沟正是工具接口的目的。宿主程序——你的智能体运行时、Claude Desktop、ChatGPT、Cursor 或自定义脚本——向模型公布一份可调用工具的列表。当模型判断需要执行某个动作时，它输出一个结构化的负载，指明工具名称及其参数。宿主解析该负载，真正运行该工具，并把结果反馈回来。循环持续进行，直到模型判断不再需要调用为止。

这一契约的第一个版本于 2023 年 6 月以 OpenAI 的 "functions" 参数形式发布。Anthropic 随后在 Claude 2.1 中引入了 `tool_use` 块。Gemini 几个月后加入了 `functionDeclarations`。如今每家提供商都暴露同样的形态：输入一个 JSON Schema 类型化的工具列表，输出一个 JSON 负载的工具调用。Model Context Protocol（2024 年 11 月）将这一契约通用化，使得一份工具注册表可以服务所有模型。A2A（2026 年 4 月，v1.0）则为智能体之间的委托叠加了同样的原语。

四步循环是所有这些方案之下的不变量。Phase 13 中的其余内容都是对它的展开。

## 概念

### 第一步：describe

宿主用三个字段声明每个工具。

- **名称。** 一个稳定、机器可读的标识符。用 `get_weather`，而不是"weather thing"。
- **描述。** 一段自然语言的简短说明。“当用户询问某个特定城市的当前天气状况时使用。不要用于历史数据。”
- **输入模式。** 一个 JSON Schema 对象（draft 2020-12），描述工具的参数。

模型接收这份列表。现代提供商使用特定于提供商的模板把这些声明序列化进系统提示词中，因此作为调用方，你只需处理结构化的形式。

### 第二步：decide

给定用户消息和可用工具，模型从三种行为中选择一种。

1. **直接以文本回答。** 不调用工具。
2. **调用一个或多个工具。** 输出结构化的调用对象。在 `parallel_tool_calls: true` 下（OpenAI 和 Gemini 默认开启，Anthropic 可选开启），模型可以在一轮中输出多个调用。
3. **拒绝。** 严格模式的结构化输出可以生成一个类型化的 `refusal` 块，而不是调用。

一个工具调用负载有三个稳定字段：一个调用 `id`、一个工具 `name`，以及一个 JSON `arguments` 对象。id 的存在使宿主能把后续结果与具体的调用关联起来——当并行调用乱序返回时，这一点很重要。

### 第三步：execute

宿主接收调用，根据声明的模式校验参数，然后运行执行器。参数无效意味着模型幻觉出了一个字段或使用了错误的类型——这在弱模型上是非常常见的失败模式。生产环境的宿主在参数无效时做以下三件事之一：快速失败并把错误呈现给模型、用受约束的解析器修复 JSON，或把校验错误包含在提示词中重试模型。

执行器本身是普通的代码。Python、TypeScript、shell 命令、数据库查询。它产生一个结果，通常是一个字符串，但也可以是任何 JSON 值或结构化的内容块（MCP 中的文本、图像或资源引用）。结果必须可序列化。

### 第四步：observe

宿主把工具结果追加到对话中（作为一条带有匹配 `id` 的 `tool` 角色消息），并重新调用模型。模型现在在上下文中拥有了工具输出，可以生成最终答案或请求更多调用。这一过程持续进行，直到模型停止输出调用，或宿主达到迭代次数的安全上限。

### 信任区分

就安全性而言，工具分为两种类型。

- **纯工具。** 只读、确定性、无副作用。如 `get_weather`、`search_docs`、`get_current_time`。可以推测性地调用。
- **后果性工具。** 会改变状态、花钱、触及用户数据。如 `send_email`、`delete_file`、`execute_trade`。必须加以管控。

Meta 在 2026 年针对智能体安全提出的“二选一规则”指出，单轮中最多只能同时包含以下三项中的两项：不可信输入、敏感数据、后果性动作。工具接口正是你执行这一规则的地方——通过拒绝调用、要求用户确认，或提升权限范围。完整的安全章节见 Phase 13 · 15，智能体级权限策略见 Phase 14 · 09。

### 循环存在于何处

| 场景 | 谁来 describe | 谁来 decide | 谁来 execute |
|---------|---------------|-------------|--------------|
| 单轮 function calling（OpenAI/Anthropic/Gemini） | 应用开发者 | LLM | 应用开发者 |
| MCP | MCP 服务器 | 通过 MCP 客户端的 LLM | MCP 服务器 |
| A2A | Agent Card 发布者 | 调用方智能体 | 被调用方智能体 |
| Web 浏览器（function calling 智能体） | 浏览器扩展 / WebMCP | LLM | 浏览器运行时 |

无论在哪里，都是同样的四步。列名会变，结构不变。

### 为什么不直接提示模型输出 JSON？

“让模型以 JSON 回复”是 function calling 出现之前的模式。它在前沿模型上约有 5% 到 15% 的失败率，在小模型上失败率更高。失败模式包括缺失大括号、尾随逗号、幻觉字段和类型错误。接下来你就需要 JSON 修复步骤、重试，或一个受约束的解码器。

原生 function calling 更好，原因有三。第一，提供商针对确切的调用形态对模型进行了端到端训练，因此在严格模式下有效 JSON 的比率可攀升至 98% 到 99%。第二，调用负载位于自己的协议槽位中，而不是自由文本之内——因此工具调用绝不会泄漏到用户可见的回复中。第三，提供商使用受约束解码来强制模式合规（OpenAI 的 strict mode、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`）。输出保证能通过校验。

### 熔断机制

当模型停止输出调用，或宿主达到最大轮数上限时，循环终止。生产环境的宿主通常将其设在 5 到 20 轮之间。超过这个范围，你几乎肯定陷入了模型无法自行退出的循环。Claude Code 默认为 20；OpenAI Assistants 为 10；Cursor 的智能体模式为 25。

另一种选择——无界循环——每半年就会以“智能体一夜之间花了 400 美元 API 调用费”的事后复盘形式出现。没有上限就不要上线。

## 动手使用

`code/main.py` 在没有 LLM 的情况下运行这个四步循环。一个模拟的“决策器”函数通过模式匹配用户消息来模拟模型；而执行器、模式校验器和 observe 步骤的测试框架都是真实的。运行它，可以看到带有可打印中间状态的完整请求/响应编排，然后在后续课程中用任何真实提供商替换这个模拟决策器。

值得关注的地方：

- 工具注册表为每个工具保存三个字段：名称、描述、模式，以及一个执行器引用。
- 校验器是一个极简的 JSON Schema 子集（类型、required、enum、min/max），仅用标准库编写。Phase 13 · 04 提供了一个更完整的版本。
- 循环将迭代次数限制为五次。生产环境的智能体正需要这种熔断器。

## 交付成果

本课产出 `outputs/skill-tool-interface-reviewer.md`。给定一份工具定义草稿（名称 + 描述 + 模式 + 执行器大纲），该技能会审查其循环适配性：名称是否机器稳定、描述是否是完整的使用说明、模式是否正确使用 JSON Schema 2020-12，以及纯工具与后果性工具的分类是否明确。

## 练习

1. 在 `code/main.py` 中添加第四个工具，命名为 `get_stock_price(ticker)`。将其描述写为“当用户按股票代码查询当前股价时使用。不要用于历史价格或市场综述。”运行测试框架，确认模拟决策器把提到股票代码的查询路由到新工具。

2. 破坏模式校验器。传入一个 `arguments` 对象缺少必填字段的调用，确认宿主在执行之前拒绝它。然后传入一个带有额外未知字段的调用。判断：宿主应该拒绝还是忽略？用安全性论证来为你的选择辩护。

3. 将测试框架中的每个工具分类为纯工具或后果性工具。为需要的注册表条目添加一个 `consequential: true` 标志，并修改循环，使得每当选择后果性工具时打印一行“would confirm with user”。这就是每个生产环境宿主所需的确认门控的雏形。

4. 在纸上画出四步循环，并针对你最喜欢的客户端（Claude Desktop、Cursor、ChatGPT 或自定义技术栈）填写上面的提供商列。与 Phase 13 · 06 中的 MCP 专用变体进行交叉对照。

5. 从头到尾阅读 OpenAI 的 function calling 指南。找出一个存在于请求中但不属于本课所呈现的四步循环的字段。解释它增加了什么，以及为什么它是便利性的而非必需的。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|------------------------| 
| 工具 | “模型可以调用的东西” | 名称 + JSON Schema 类型化输入 + 执行器函数的三元组 |
| Function calling | “原生工具使用” | 提供商层面的 API 支持，用于输出结构化的工具调用而非普通文本 |
| 工具调用 | “模型发出的行动请求” | 由模型输出的包含 `id`、`name`、`arguments` 的 JSON 负载 |
| 工具结果 | “工具返回了什么” | 执行器的输出，封装在带有匹配 id 的 `tool` 角色消息中 |
| 并行工具调用 | “一次调用多个” | 一个模型轮次中的多个调用对象，相互独立且可按 id 排序 |
| 严格模式 | “保证 JSON” | 受约束解码，强制模型输出通过所声明模式的校验 |
| 纯工具 | “只读工具” | 无副作用；可安全重复运行 |
| 后果性工具 | “动作工具” | 会改变外部状态；需要门控、审计或用户确认 |
| 四步循环 | “工具调用周期” | describe → decide → execute → observe |
| 宿主 | “智能体运行时” | 持有工具注册表、调用模型并运行执行器的程序 |
