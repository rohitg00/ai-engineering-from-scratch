# 百万级 Token 上下文下的长视频理解

> 一段 1 小时、24 FPS 的 4K 视频，经过分块和嵌入后，大约产生 6000 万个 token。一段转写后的 2 小时播客是 3 万个 token。一部完整的蓝光电影，即使经过激进池化压缩，也有数十万个 token。Google 的 Gemini 1.5(2024 年 3 月)以 1000 万 token 的上下文开启了这一时代，能够在长达一小时的视频上实现可靠的“大海捞针”式召回。LWM(Liu et al.,2024 年 2 月)展示了环形注意力(ring attention)的扩展路径。LongVILA 和 Video-XL 进一步扩展了视频摄取能力。VideoAgent 用代理式检索替代了原始上下文。每种方法都是在算力、召回率和工程复杂度之间的不同权衡。本课将把它们并排对照讲解。

**Type:** Build
**Languages:** Python(标准库，大海捞针模拟器 + 代理式检索路由)
**Prerequisites:** Phase 12 · 17(视频时间 token)
**Time:** ~180 分钟

## 学习目标

- 计算长视频在不同 FPS 和池化设置下的视觉 token 总数。
- 解释三条扩展路径：暴力上下文(Gemini 1.5)、环形注意力(LWM)、token 压缩(LongVILA / Video-XL)。
- 在准确率和延迟上比较原始上下文视频 VLM 与代理式检索视频 VLM(VideoAgent)。
- 为一段 30 分钟的视频设计大海捞针测试，并测量在特定分钟处的召回率。

## 问题

单个帧若使用与 Qwen2.5-VL 相同大小的 patch、384 原生分辨率，约为 729 个 token。经 3x3 池化后每帧为 81 个 token。一段 1 FPS 的 30 分钟视频 = 1800 帧 = 145,800 个 token。以 2025 年的开源 VLM 来说可行，但很紧张。2 FPS 时则是 291,600 个 token——只有最大的上下文才能容纳。

一部 1 FPS 的 2 小时电影是 58.3 万 token。超出大多数 2026 年开源模型的能力；需要 Gemini 2.5 Pro 或更激进的池化。

由此出现了三条扩展路径。

## 概念

### 路径 1:暴力上下文(Gemini 1.5、Claude Opus)

用硬件硬砸这个问题。把上下文扩展到数百万 token,一次前向传播处理所有内容。

Gemini 1.5 Pro 发布时支持 100 万 token;Gemini 1.5 Ultra 达到 1000 万;2026 年的 Gemini 2.5 Pro 能可靠地处理数小时的视频。该论文(arXiv:2403.05530)记录了在高达约 950 万 token 上 99.7% 的大海捞针召回率。

工程实现：自定义注意力实现，带有内存层级(局部 + 全局 + 稀疏)，再加上用于长上下文效率的 MoE 专家路由。完整细节未公开，也不是开源的。

### 路径 2:环形注意力(LWM、LongVILA)

环形注意力将长序列分布到“环形”排列的多个设备上，每个设备持有一个分块。通过对整个序列的注意力，是靠每个设备把自己的分块按环形模式发送给下一个设备、计算部分注意力、再进行聚合来实现的。

LWM(Liu et al.,2024)以这种方式训练了一个 100 万 token 上下文的模型。训练算力随上下文线性增长，而非平方级——注意力的平方级开销被摊分到环上各设备之间。

LongVILA(arXiv:2408.10188)将这一模式适配到 VLM。1400 帧视频、每帧 192 个 token = 26.8 万上下文，使用环形注意力在 8 路并行下训练。

### 路径 3:token 压缩(Video-XL、LongVA)

比暴力上下文更省：在 LLM 看到序列之前先进行激进压缩。

Video-XL(arXiv:2409.14485)使用视觉摘要 token:每段 N 帧的片段生成一个“摘要” token,它对这 N 帧进行注意力。推理时，LLM 每个片段只看到一个摘要 token,从而大幅缩减上下文。

LongVA 通过“长上下文迁移”技术将 LLM 上下文从 20 万扩展到 200 万。先在长上下文文本上训练，再通过共享表示迁移到长上下文视频。

token 压缩以牺牲特定时间戳上的召回为代价换取可扩展性。模型大致知道发生了什么，但有时会错过确切的帧。

### 路径 4:代理式检索(VideoAgent)

不要把完整视频喂给 LLM。而是把视频当作数据库，用 LLM 来查询它。

VideoAgent(arXiv:2403.10517):

1. LLM 读取问题。
2. LLM 向检索工具请求相关片段(“给我看有猫的片段”)。
3. 工具返回匹配片段的时间戳。
4. LLM 通过 VLM 读取这些片段。
5. LLM 组合出答案或继续追问。

这是把 LLM 作为代理的模式应用于长视频。推理更便宜(只编码相关片段)，但工程更难(检索质量成为瓶颈)。

### 大海捞针基准测试

标准的长上下文测试：在视频中的随机位置插入一个独特的视觉或文本标记，然后提出一个需要回忆该标记的查询。

指标：Recall@k,沿视频长度和标记位置两个维度。

Gemini 2.5 Pro 在长达 90 分钟的视频上召回率超过 99%。开源 72B 模型(Qwen2.5-VL-72B、InternVL3-78B)在 30 分钟处得分约 85-90%,超过 60 分钟后退化。

如果工具足够好，VideoAgent 在 2 小时以上的视频上可以匹敌甚至超越原始上下文模型，因为检索能命中目标。

### 选择哪条路径

15 分钟的片段、要前沿级准确率：开源 72B + 原生上下文通常可行。选 Qwen2.5-VL-72B。

30 分钟到 1 小时的内容：开源选 LongVILA 或 Video-XL;闭源选 Gemini 2.5 Pro。质量门槛很重要——要前沿水平就得用闭源。

2 小时以上的内容：VideoAgent 或类似的检索模式。或者，先摘要成较小的块，再进行分层摘要喂入。

### 2026 年的生产模式

在实践中，生产级长视频流水线是混合式的：

1. 对整个视频运行动态 FPS 采样 + 激进池化(得到 10 万 token 的全局表示)。
2. 交给 72B VLM 生成全局摘要。
3. 当用户提出细节问题时，以摘要为索引运行代理式检索。

这结合了暴力上下文用于全局理解、检索用于局部细节。

## 使用它

`code/main.py`:

- 计算从 1 分钟到 3 小时的视频在不同 FPS + 池化下的 token 预算。
- 模拟一次大海捞针运行：在随机时间戳注入标记，提出问题，对召回率打分。
- 包含一个代理式检索路由模拟器，它会挑选特定片段喂给下游 VLM。

运行预算表，感受规模的差距。

## 练习

1. 一段 1 FPS、每帧 81 个 token 的 45 分钟讲座。总 token 数是多少？能放入哪些模型的上下文？

2. 设计一个大海捞针测试：在第几分钟注入标记？确切的查询格式是什么？

3. 在一段 1 小时的视频上，比较暴力上下文的 Qwen2.5-VL-72B(80k 上下文)与 VideoAgent(Claude 3.5 + 检索)。哪个召回率更高？哪个延迟更低？

4. 环形注意力的内存成本随序列长度线性增长，也随设备数线性增长。解释原因，以及如果去掉环形轮转阶段会出什么问题。

5. 阅读 Gemini 1.5 中关于大海捞针的第 5 节。论文关于 100 万与 1000 万 token 边界处的召回率发现了什么？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------------|------------------------|
| 暴力上下文 | "就是更多 token" | 把 LLM 上下文扩展到数百万 token;一次处理所有内容 |
| 环形注意力 | "LWM 式并行" | 分布式注意力模式，每个设备持有一个分块并轮转 |
| Token 压缩 | "摘要 token" | 在 LLM 之前通过学习到的压缩器减少每片段的 token |
| 大海捞针 | "NIH 测试" | 在随机位置插入独特标记，测试时要求模型回忆它 |
| 代理式检索 | "LLM 作为查询规划器" | LLM 向检索工具请求相关片段，通过 VLM 读取它们，组合出答案 |
| VideoAgent | "视频检索模式" | 典型的代理式检索设计：问题 -> 工具 -> 片段 -> 答案 |
