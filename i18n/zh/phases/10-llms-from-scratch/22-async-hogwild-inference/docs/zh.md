# 异步与 Hogwild! 推理

> 投机解码(Phase 10 · 15)在单条序列内实现 token 级并行。多智能体框架可以在整个序列之间并行,但需要显式的协调机制(投票、子任务拆分)。Hogwild! Inference(Rodionov et al., arXiv:2504.06261)另辟蹊径:让同一个 LLM 的 N 个实例并行运行,并共享同一个键值缓存。每个 worker 能即时看到其他 worker 生成的 token。现代推理模型——QwQ、DeepSeek-R1——无需任何微调,即可通过这个共享缓存实现自协调。该方法仍处于实验阶段,但它开辟了一个全新的推理并行维度,与投机解码相互正交。本课用标准库 Python 实现一个双 worker 的 Hogwild! 模拟器,并解释这种共享缓存协作如何从现有模型的推理能力中自然涌现。

**Type:** Build
**Languages:** Python(标准库)
**Prerequisites:** Phase 10 · 12(推理优化),Phase 10 · 15(投机解码)
**Time:** 约 60 分钟

## 学习目标

- 描述三种常见的并行 LLM 拓扑(投票、子任务、Hogwild!),并说明各自针对的问题类型。
- 阐述 Hogwild! 的核心设定:多个 worker、一个共享 KV 缓存、通过自我提示实现涌现式协调。
- 推导 Hogwild! 的实际耗时加速比,表示为 worker 数量 `N`、任务级并行度 `p` 和协调开销 `c` 的函数。
- 在一个玩具问题上实现双 worker 的 Hogwild! 模拟器,并观察涌现的任务分工。

## 问题所在

现代 LLM 通过生成很长的推理链来解难题——5000 个 token 的逐步逻辑推理很常见,深的数学题上甚至会出现数万个 token。以 70B 模型 35 token/秒的解码速度计算,50k token 需要 24 分钟。这谈不上交互性。

投机解码(Phase 10 · 15)通过在单条序列内并行,可获得 3-5 倍的加速。但自回归解码的顺序依赖是硬性上限。每个新 token 依赖于之前所有的 token。

一个显而易见的问题:我们能否跨序列并行?在同一个问题上运行同一个模型的多个副本,让它们协作、分工?

已有工作包括:投票集成(运行 N 个模型,选多数答案)、思维树(分支推理路径再重组)以及多智能体框架(给每个智能体分配子任务,使用协调者)。它们都在特定任务领域有效,但也都引入了显式的协调机制——投票规则、分支剪枝逻辑、智能体间通信协议。

Hogwild! Inference 采用了不同的思路。N 个 worker 共享一个 KV 缓存。每个 worker 立即看到其他 worker 生成的 token,就像看到自己的上下文一样。这些 worker——无需任何训练或微调——自行决定如何分工。现代推理模型(QwQ、DeepSeek-R1、Claude 系列的推理模式)能读取共享缓存,并说出诸如"我看到 worker 2 已经处理了基础情形,那我来做归纳步骤"这样的话。

加速效果取决于工作负载,且截至 2026 年 4 月仍属实验性。但这个想法值得了解,因为它开辟了一个新的推理并行维度。

## 核心概念

### 基本设定

初始化 N 个 worker 进程,都运行同一个 LLM。不使用每 worker 独立的 KV 缓存,而是维护唯一的一个共享缓存。当 worker `i` 生成 token `t_j` 时,该 token 被写入共享缓存的下一个位置。当 worker `k` 执行下一步时,它读取缓存的当前状态(其中包含所有 N 个 worker 迄今生成的全部内容)。

在步进时,worker 们竞争写入 token。没有每 worker 的位置索引——缓存是一条不断增长的单序列。顺序由写入到达时间决定。

### 协调为何涌现

worker 们共享一个提示词。通常是类似"你是共同解决此问题的 N 个实例之一。每个实例读取共享内存,可以看到其他实例写下的内容。避免重复工作。"这样的内容。提示词加上共享缓存就足够了。推理模型读取缓存,注意到问题的哪些部分已被尝试过,然后(通常但并非总是)转向未探索的部分。

Hogwild! 论文(Rodionov et al., 2025)报告了如下观察:

- worker 制定计划,并通过缓存将其传达给其他 worker。
- worker 注意到其他 worker 推理中的错误并指出。
- worker 在计划失败时进行调整并提出替代方案。
- 当被提示检查冗余时,worker 能检测到冗余并转向。

这一切都不需要微调。涌现行为源自模型已有的推理能力。

### 命名由来

论文的名称致敬 Hogwild! SGD(Recht et al., 2011),一种异步更新优化器。类比:SGD 的异步 worker 都写入一个共享参数向量;Hogwild! Inference 的 worker 都写入一个共享 KV 缓存。两者都依赖经验性收敛,而非同步保证。

### RoPE 使这一切可行

旋转位置编码(RoPE,Su et al. 2021)通过 Q 和 K 向量中的旋转来编码位置信息。由于位置是旋转而非内嵌的偏移量,token 的位置可以平移而无需重算 KV 缓存条目。当 worker `i` 将 token 写入共享缓存的位置 `p` 时,读取该位置的其他 worker 可以直接使用缓存条目——无需重新旋转。

在使用可学习位置或绝对位置的模型中,Hogwild! 需要在每次并发写入时使缓存失效。RoPE 让缓存保持稳定。

### 实际耗时计算

设 `T_serial` 为单个 worker 独立解决该问题所需的时间。设 `p` 为任务级可并行的比例。设 `c` 为每步协调开销(读取扩展后的缓存、决定写什么)。

单 worker 时间:`T_serial`。
N worker 的 Hogwild! 时间(协调免费时):`T_serial * ((1 - p) + p / N)`。经典的 Amdahl 定律。
加上协调开销后:`T_serial * ((1 - p) + p / N) + c * steps_per_worker`。

要让 worker 保持高效,`c` 必须相对每步解码时间足够小。对于生成 5k+ token 的推理模型,worker 可以承受数百 token 的协调开销仍然占优。而在短对话任务上,协调开销占主导,Hogwild! 反而不如串行。

### 具体例子

推理问题:10k token 的思维链。假设该问题有 `p = 0.7` 的可并行内容(不同的证明策略、不同的情形分析)和每个 worker `c = 200` 的协调开销 token。使用 `N = 4` 个 worker:

- 串行时间:10000 个解码步。
- Hogwild! 时间:10000 * (0.3 + 0.7 / 4) + 200 * 4 = 10000 * 0.475 + 800 = 5550 个解码步。
- 加速比:10000 / 5550 = 1.8 倍。

这只是中等水平。但在更长的推理问题(50k token)上,协调开销被摊薄,加速比可达 2.5-3 倍。Hogwild! 相当于推理版的线程级并行,而且是在一种可以自然编写多线程代码的语言中。

### 何时使用 Hogwild!

- 长推理问题(数千 token),且任务可以跨独立子目标并行。
- 经过逐步思考训练的推理模型。非推理模型无法很好地自协调。
- 单节点部署,且有足够 VRAM 容纳共享缓存加 N 个 worker 进程。缓存是共享的,但每个 worker 有自己的激活内存。

### 何时不使用

- 短交互对话。协调开销占主导。
- 无法并行化的任务(单条线性证明、单次编译)。N=1 是上限。
- 非推理模型。不会涌现协调。
- 多节点部署。共享缓存需要极快的跨 worker 同步。节点内没问题;跨节点是延迟灾难。

### 实验状态

截至 2026 年 4 月,Hogwild! 是一种有开源 PyTorch 实现的研究方法。尚未进入生产采用。三个障碍:

1. 跨并发进程的共享 KV 缓存管理是非平凡的工程问题。
2. 涌现式协调依赖于任务;基准测试仍在构建中。
3. 相比投机解码已提供的加速,其加速幅度有限;两者可以结合,但结合后的工程又是一层额外复杂度。

值得了解。值得实验。还不值得押注产品。

## 动手构建

`code/main.py` 实现了一个玩具 Hogwild! 模拟器:

- 两个 worker 进程,每个是一个确定性的"LLM",以已知概率生成几类 token 之一(工作 token、观察 token、协调 token)。
- 一个共享缓存(就是一个 token 列表),两个 worker 都可读写。
- 一个简单的协调逻辑:当某个 worker 发现另一个 worker 在某一类别已产出足够多的工作 token 时,它就切换到另一个类别。

模拟器运行固定的步数预算并报告:

- 产出的工作 token 总数。
- 总实际耗时(worker 步数)。
- 相对单 worker 的有效加速比。
- 哪个 worker 写入了哪个 token 的轨迹。

### 第 1 步:共享缓存

一个两个 worker 都向其追加的列表。真实实现中需要简单的锁(Python 的 `threading.Lock`);这里用计数器模拟。

### 第 2 步:worker 循环

每个 worker 每步:

- 读取当前共享缓存。
- 根据已有内容决定写入哪个类别的 token。
- 写入一个 token。

### 第 3 步:协调启发式

如果类别 X 在缓存中已有 K 个 token,而 worker 打算写入的类别是 X,则 worker 切换到类别 Y。这是推理模型"注意到这里已被覆盖,改做别的事"行为的玩具替身。

### 第 4 步:测量加速比

用 N=1 个 worker 和 N=2 个 worker 运行模拟器,总步数预算相同。统计产出的工作 token 数。N=2 应产出大约 1.5-1.8 倍的工作 token,这归功于协调驱动的任务分工。

### 第 5 步:压力测试协调机制

降低协调启发式的灵敏度,再次运行。观察到缺乏良好协调时,N=2 会冗余地生成相同的 token,加速比降到 1 以下。这与论文的观察一致:只有当 worker 具备自协调的推理能力时,这个技巧才有效。

## 实际应用

截至 2026 年 4 月,Hogwild! 在生产中的集成仍属研究级别。来自 Yandex/HSE/IST 的参考实现基于 PyTorch,面向 DeepSeek-R1 和 QwQ 模型的单节点多进程部署。

务实的采用路径:

1. 分析你的推理任务工作负载。测量探索性 token(多种策略、情形分析、搜索)与线性 token 的比例。
2. 如果探索占主导,运行双 worker 的 Hogwild! 实验,测量实际耗时改进。
3. 如果改进低于 1.3 倍,你处于协调主导区间。回退到单 worker。
4. 如果改进超过 1.5 倍,推到 N=4 并再次测量。收益递减通常在 N=4-8 左右出现。

与投机解码结合:每个 Hogwild! worker 可以独立使用投机解码。两个加速比(大致)相乘,3 倍的投机解码与 1.8 倍的 Hogwild! 合计相当于比朴素单 worker 解码快 5.4 倍。

## 关键术语

| 术语 | 人们的说法 | 实际含义 |
|------|----------------|------------------------|
| Hogwild! | "并行 worker,共享缓存" | 同一 LLM 的 N 个实例并发运行,共享一个 KV 缓存;通过自我提示涌现协调 |
| 共享 KV 缓存 | "协调媒介" | 一条持续增长的 KV 缓冲区,所有 worker 读写;使 token 在 worker 间即时可见 |
| 涌现式协调 | "无需训练" | 具备推理能力的 LLM 可以读取共享缓存并分工,无需任何微调或显式协议 |
| 协调开销 (c) | "用于定向的 token" | 每 worker 读取扩展缓存并决定下一步的成本;相对总解码时间必须保持很小 |
| 可并行比例 (p) | "能并行运行的部分" | 任务级并行:总工作中非内在串行的比例 |
| RoPE 使 Hogwild! 可行 | "旋转位置是平移不变的" | 由于位置是旋转,写入共享缓存无需重算先前的 token |
| 投票集成 | "运行 N 个,选多数" | 最简单的并行推理拓扑;对分类有用,对长篇推理帮助较小 |
| 思维树 | "分支并剪枝" | 探索多个分支并剪枝的推理策略;显式的协调逻辑 |
| 多智能体框架 | "分配子任务" | 每个智能体获得一个角色;由协调者编排;协议开销大 |
