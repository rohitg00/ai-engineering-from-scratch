# LLM 的 FinOps —— 单位经济与多租户归因

> 传统 FinOps 在 LLM 支出面前失效了。成本是 token 交易,而非资源运行时间。标签映射不上——一次 API 调用是一笔交易,而不是一项资产。工程决策(prompt 设计、上下文窗口、输出长度)就是财务决策。2026 年的实践手册要求在第一天就埋点三个归因维度:按用户(`user_id`)用于席位定价与扩展,按任务(`task_id` + `route`)用于产品界面成本与优先级排序,按租户(`tenant_id`)用于单位经济与续约。四个 token 层——prompt、工具、记忆、响应——合并为一个桶会掩盖支出。面向多租户产品的执行阶梯:按租户速率限制(预期峰值的 2-3 倍,清晰的 429 + retry-after);每日支出上限(合同上限的 1.5-3 倍;触发速率收紧 + 告警);支出 z-score > 4 时触发 kill switch(自动暂停 + 呼叫值班)。归因模式:标签聚合、遥测关联(trace-ID → 账单;准确度最高)、抽样外推、基于模型的分摊、事件溯源、实时流式处理。单位指标:每个已解决查询的成本、每个生成产物的成本——而不是 $/M tokens。事后打标总会遗漏;在请求创建时埋点。

**Type:** Learn
**Languages:** Python (标准库,带 kill switch 的简易成本归因模拟器)
**Prerequisites:** Phase 17 · 13(可观测性)、Phase 17 · 14(缓存)
**Time:** 约 60 分钟

## 学习目标

- 解释为什么传统 FinOps(标签 + 分层)在 LLM 支出面前失效,并说出三个新的归因维度。
- 列举四个 token 层(prompt、工具、记忆、响应)以及为什么单桶计费会掩盖成本。
- 为多租户产品设计执行阶梯(速率 → 支出上限 → kill switch)。
- 选择单位指标(每个已解决查询 / 产物的成本),而非 $/M tokens。

## 问题所在

你的账单显示 $40,000。但你不知道:
- 哪个租户花的。
- 哪个产品功能导致的。
- 是否有某个用户存在滥用行为。
- 罪魁祸首是 prompt 膨胀、工具调用,还是记忆放大。

在提供商侧做标签聚合适用于云资源(EC2、S3),因为标签会传递到账单条目。LLM API 调用不会自动打标——你必须在调用点标注用户/任务/租户并一路传递。事后归因总会遗漏边缘情况。

## 核心概念

### 三个归因维度

**按用户**(`user_id`):谁在花什么钱。驱动席位定价、扩展谈判,识别重度用户。

**按任务**(`task_id` + `route`):哪个产品界面花什么钱。驱动功能优先级排序、砍掉昂贵功能的决策。

**按租户**(`tenant_id`):哪个客户是盈利的。驱动单位经济、续约定价、分层阈值。

第一天就在调用点埋点这三者。事后补做总是更糟。

### 四个 token 层

| 层 | 示例 | 占总成本典型比例 |
|-------|---------|---------------------|
| Prompt | system + 用户输入 | 40-60% |
| 工具 | 工具调用结果回传 | 20-40%(agent 工作负载) |
| 记忆 | 历史对话 / 检索文档 | 10-30% |
| 响应 | 模型输出 | 10-30% |

把四层合在一起会让优化失去方向。在归因 schema 中将它们拆开。

### 执行阶梯

1. 按租户的**速率限制**。预期峰值的 2-3 倍。返回 429 并附带 `Retry-After`。租户感受到限流;账单不会出现意外。

2. 按租户的**每日支出上限**。合同上限的 1.5-3 倍。触发动作:收紧速率限制 + 告警客户成功团队。

3. 支出相对租户基线的 **z-score > 4 时触发 kill switch**。自动暂停租户;呼叫值班;升级至运维 + 客户成功。

### 归因模式

- **标签聚合**:打上元数据 header,之后聚合。简单;粗糙。
- **遥测关联**:通过 trace ID 将 trace 与账单关联。准确度最高。成熟团队的做法。
- **抽样 + 外推**:抽样 5-10%,乘以倍数。对粗略支出估算性价比高;会遗漏尾部。
- **基于模型的分摊**:用回归推断成本驱动因素。适用于没有标签的遗留数据。
- **事件溯源**:成本作为事件写入流(Kafka / Kinesis)。实时。
- **实时流式处理**:仪表盘亚秒级更新。

### 每单位 X 的成本是单位指标

$/M tokens 是供应商话语。产品指标应该是:

- 每个已解决支持工单的成本。
- 每篇生成文章的成本。
- 每个成功 agent 任务的成本。
- 每用户会话分钟的成本。

把成本与产品成果挂钩。否则优化就失去了锚点。

### 成本归因 trace 的结构

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用都输出。存入数据湖。按维度聚合。Phase 17 · 13 的可观测性栈就是它的归属地。

### 复利式节省栈

栈:缓存 + 批处理 + 路由 + 网关。四者叠加:
- L2 缓存(Phase 17 · 14):输入便宜约 10 倍。
- 批处理(Phase 17 · 15):五折。
- 路由到便宜模型(Phase 17 · 16):成本降低 60%。
- 网关效率(Phase 17 · 19):去重 + 重试。

最佳叠加效果:约为朴素基线的 5-10%。大多数团队只启用了 2-3 个杠杆;很少有团队四者叠加。

### 你应该记住的数字

- 归因维度:按用户、按任务、按租户。
- 四个 token 层:prompt、工具、记忆、响应。
- Kill switch:支出 z-score > 4。
- 单位指标:每个已解决查询的成本,而非 $/M tokens。
- 叠加优化:可达基线的约 5-10%。

## 关键术语

| 术语 | 人们的说法 | 实际含义 |
|------|----------------|------------------------|
| 按用户归因 | "用户级成本" | 每次调用都打上 `user_id` |
| 按任务归因 | "功能成本" | `task_id` + `route` 标识产品界面 |
| 按租户归因 | "客户成本" | `tenant_id`;驱动单位经济 |
| 四个 token 层 | "成本层" | prompt + 工具 + 记忆 + 响应 |
| 速率限制 | "429 防线" | 在网关处执行的按租户上限 |
| 每日支出上限 | "每日天花板" | 带告警的租户级预算 |
| Kill switch | "自动暂停" | 支出 z-score > 4 触发自动暂停 |
| 每次已解决的成本 | "产品单位指标" | 成本与产品成果挂钩,而非 tokens |
| 遥测关联 | "trace 到账单" | 准确度最高的归因模式 |
| 叠加优化 | "缓存+批处理+路由+网关" | 复合节省至基线的约 5-10% |
