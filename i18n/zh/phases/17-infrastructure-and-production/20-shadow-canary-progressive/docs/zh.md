# LLM 的影子流量、金丝雀发布与渐进式部署

> LLM 发布结合了软件部署中最棘手的部分:没有单元测试、失败模式分散、信号延迟。流程是:(1) 影子模式 —— 将生产请求复制给候选模型,记录日志并比较,对用户零影响;能发现明显的分布问题,但不是质量保证;(2) 金丝雀发布 —— 渐进式流量切换 10% → 25% → 50% → 75% → 100%,每一步都设有门禁;跟踪延迟分位数、单次请求成本、错误/拒答率、输出长度分布、用户反馈率;(3) 在稳定性确认后,对不同方案进行 A/B 测试。非确定性是不可消除的 —— 由于 GPU 浮点数非结合性加上批大小差异,相同输入的多次运行之间准确率波动可达 15%。成本是一个变量,而非常量 —— 一个性能提升 20% 的模型,单次调用成本可能是 3 倍。回滚速度是决定性的:如果回滚需要重新部署,那你就太慢了。策略放在配置/开关中;模型放在注册表中并固定摘要;回滚 = 切换策略 + 回退阈值 + 固定旧模型,只需几秒。

**Type:** Learn
**Languages:** Python (标准库,玩具金丝雀进度模拟器)
**Prerequisites:** 阶段 17 · 13 (可观测性), 阶段 17 · 21 (A/B 测试)
**Time:** 约 60 分钟

## 学习目标

- 区分影子模式(零影响比较)、金丝雀(真实流量渐进)和 A/B(稳定性确认后的比较)。
- 列举五个 LLM 特有的金丝雀指标(延迟、单次请求成本、错误/拒答、输出长度分布、用户反馈)。
- 解释为什么 LLM 非确定性(高达 15%)改变了发布中"稳定"的含义。
- 设计以秒计(切换策略)而非以小时计(重新部署)的回滚路径。

## 问题所在

你发布了一个新模型。离线评估显示准确率提升 3%。你将其切换到生产环境。24 小时内,成本上升 40%,用户点踩增加 8%,三个客户工单报告"回答很奇怪"。你回滚。重新部署花了 3 小时。你的周末泡汤了。

这一切的每一环都可以避免。影子模式本可以在任何用户看到之前就发现 40% 的成本飙升。当点踩上升时,金丝雀本会在 10% 处停下。基于策略开关的回滚本只需 30 秒。纪律就是用来填补"离线评估看起来不错"和"真实用户满意"之间的鸿沟的。

## 概念

### 影子模式

候选模型接收与生产环境相同的请求;输出只记录日志,不返回给用户。对用户零影响。记录:

- 输出内容(与生产环境做对比)。
- Token 数量(成本差异)。
- 延迟。
- 拒答和错误。

能发现:成本爆炸、长度回退、明显的拒答变化、硬错误。不能发现:用户能感知的质量差异。影子是冒烟测试,不是质量测试。

### 金丝雀发布

设有门禁的渐进式流量切换。典型进度:1% → 10% → 25% → 50% → 75% → 100%。每一步对 5 项指标设门禁:

1. **延迟分位数** — P50、P95、P99。违规:金丝雀的 P99 > 基线的 1.5 倍。
2. **单次请求成本** — 混合美元。违规:高于基线 20% 以上。
3. **错误/拒答率** — 5xx 加显式拒答。违规:基线的 2 倍。
4. **输出长度分布** — 均值 + P99。违规:分布偏移。
5. **用户反馈率** — 点踩/工单提交。违规:基线的 1.5 倍。

### 非确定性是新的方差

相同输入产生不相同输出。原因:

- GPU 浮点数非结合性(浮点归约顺序随批而变)。
- 批大小方差(同一提示在批大小 128 与 16 中表现不同)。
- 采样(temperature > 0)。

实测:在相同评估集上,多次运行间准确率波动可达 15%。发布中的"稳定"意味着指标在预期方差范围内,而不是与基线完全相同。将门禁设在噪声底线之上。

### 成本是变量

一个性能提升 20% 的模型,单次调用成本可能是 3 倍。单次请求成本是五项门禁之一。发布一个破坏单位经济性的"更好"模型属于回滚情形。

### 回滚是武器

- 策略开关(feature flag 系统):在配置中切换百分比;只需几秒。
- 模型固定(注册表摘要):被固定的模型不会自动升级。
- 回滚 = 回退开关 + 将固定摘要设置为前一个版本。几秒,而不是几小时。

如果你的技术栈需要重新部署才能回滚,先修好它再上线。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进式交付控制器。与 Istio/Linkerd 加权路由集成。

**Istio 加权路由** — 服务网格级别的流量切分。

**KServe / Seldon Core** — 内置金丝雀的模型服务。

**Feature flags** — LaunchDarkly、Flagsmith、Unleash。策略级切换,无需重新部署。

### 指标节奏

金丝雀门禁每 5-15 分钟检查一次,取决于流量大小。1% 流量、每分钟 10 次请求,每个窗口只能得到 50-150 个数据点 —— 对延迟够用,但对用户反馈噪声较大。10% 则多约 10 倍。进度切换应停顿足够长的时间,以便每一步累积足够的样本。

### A/B 步骤是可选的

如果新模型明显不同(行为不同、成本曲线不同、语气不同),则在金丝雀通过后以 50% 流量进行 A/B 测试。如果只是改进版本,金丝雀门禁通过后直接跳到 100%。

### 你应该记住的数字

- 金丝雀进度:1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限:相同输入多次运行的方差高达 15%。
- 五项金丝雀指标:延迟、成本、错误/拒答、输出长度、用户反馈。
- 成本门禁:高于基线 20% 以上即为违规。
- 回滚:以秒计,而非以小时计。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|----------------|------------------------|
| 影子模式 | "复制给新模型" | 零影响地发送给候选模型以记录日志 |
| 金丝雀 | "渐进流量" | 带门禁的渐进式用户可见发布 |
| 门禁 | "发布检查" | 阻止推进的指标阈值 |
| 非确定性 | "LLM 方差" | 不可消除的多次运行间差异 |
| 策略开关 | "切换开关回滚" | 配置级回滚,以秒计而非以小时计 |
| 模型固定 | "注册表摘要" | 指向模型版本的不可变引用 |
| Argo Rollouts | "K8s 渐进交付" | Kubernetes 原生金丝雀/回滚控制器 |
| KServe | "推理 K8s" | 带金丝雀原语的模型服务 |
| Istio 加权 | "网格切分" | 服务网格流量切分器 |
