# Авторизация MCP в продакшне — регистрация, обновление JWKS, токены с закреплённой аудиторией

> Урок 16 поднял конечный автомат OAuth 2.1 в памяти. К 2026 году каждый MCP-сервер, который вы поставляете в реальную организацию, работает за продакшн-авторизацией: регистрация клиентов, масштабируемая на неограниченную популяцию клиентов (сначала документы метаданных Client ID, затем динамическая регистрация клиента как обратно совместимый резервный вариант), обнаружение метаданных сервера авторизации (RFC 8414 *либо* OpenID Connect Discovery), обновление кеша JWKS, которое не ломает проверку токена в 3 часа ночи, и токены с закреплённой аудиторией, отклоняющие повторное использование между ресурсами. В этом уроке моделируется вся поверхность через три роли — сервер авторизации, сервер ресурсов (MCP-сервер) и клиент, — чтобы можно было проследить каждый шаг от обнаружения до провалидированного вызова инструмента.
>
> **Замечание о спецификации (2025-11-25):** ноябрьская спецификация авторизации MCP 2025 года понизила динамическую регистрацию клиента с `SHOULD` до `MAY` и сделала **документы метаданных Client ID (CIMD)** рекомендуемым механизмом регистрации по умолчанию. В этом уроке разбираются оба механизма в порядке приоритета из спецификации, а код сохраняет DCR для практической части, поскольку он полностью самодостаточен в одном процессе.

**Тип:** Build**Языки:** Python (stdlib)**Предварительные требования:** Фаза 13 · 16 (конечный автомат OAuth 2.1), Фаза 13 · 17 (шлюзы)**Время:** ~90 минут
## Цели обучения

- Обнаружить сервер авторизации через метаданные RFC 8414 и проверить контракт.
- Реализовать динамическую регистрацию клиента RFC 7591, чтобы MCP-клиенты регистрировались без вмешательства администратора.
- Кешировать и обновлять ключи JWKS по расписанию, чтобы проверка подписи переживала ротацию ключей.
- Закрепить токены за единственным ресурсом MCP с помощью индикаторов ресурсов RFC 8707 и отклонять повторное использование по типу confused deputy.
- Чётко разделить три роли — сервер авторизации, сервер ресурсов, клиент, — чтобы каждый выполнял только те проверки, которые ему принадлежат.
- Прочитать матрицу возможностей поставщика удостоверений (IdP) и отказаться от развёртывания, если IdP не удовлетворяет профилю авторизации MCP.

## Проблема

Симулятор из урока 16 выполняет OAuth 2.1 в памяти. В продакшне есть три эксплуатационных пробела, которые симулятор только в памяти не видит.

Первый пробел — регистрация. В реальной организации работают сотни MCP-серверов и тысячи MCP-клиентов. Операторы не регистрируют вручную каждого пользователя Cursor как клиента OAuth. Спецификация от 2025-11-25 задаёт клиентам порядок приоритета для решения этой проблемы: использовать предварительно зарегистрированный `client_id`, если он есть, иначе использовать **документ метаданных Client ID** (клиент идентифицирует себя HTTPS-URL, который он контролирует, а сервер авторизации *забирает* метаданные), иначе перейти к **динамической регистрации клиента RFC 7591** (клиент *отправляет* `POST /register` и сразу получает `client_id`), иначе — запросить пользователя. CIMD — рекомендуемый вариант по умолчанию, поскольку он полностью устраняет регистрацию для каждого сервера, сохраняя при этом модель доверия, укоренённую в DNS; DCR сохранён для обратной совместимости. Оба механизма обнаруживают свои точки входа из метаданных сервера авторизации: `client_id_metadata_document_supported` для CIMD, `registration_endpoint` для DCR.

Второй пробел — ротация ключей. Проверка JWT зависит от ключей подписи сервера авторизации, публикуемых как JSON Web Key Set (JWKS). Сервер авторизации ротирует их по расписанию (часто раз в час, иногда чаще в рамках реагирования на инциденты). MCP-сервер, который получает JWKS один раз при запуске, проверяет токены нормально до окна ротации — затем каждый запрос отказывает вплоть до перезапуска. В продакшне JWKS подключается как кешируемое значение с заданием обновления, которое перезаписывает кеш до истечения срока действия предыдущих ключей, плюс резервный запрос при промахе кеша на случай, если придёт токен, подписанный ключом новее, чем в кеше.

Третий пробел — привязка аудитории. Урок 16 ввёл индикаторы ресурсов RFC 8707. В продакшне этот индикатор становится жёсткой проверкой claim при каждом запросе. MCP-сервер сравнивает `token.aud` с собственным каноническим URL ресурса и отклоняет несовпадения с HTTP 401. Это единственная защита от повторного использования токена вышестоящим MCP-сервером (или вредоносным клиентом, держащим токен, предназначенный для одного сервера) против другого сервера в той же mesh-сети доверия.

Этот урок отображает каждый пробел на конкретную часть поверхности. Документ метаданных — это HTTP-конечная точка. Обновление кеша JWKS — это запланированное задание плюс кеш «ключ-значение». Проверка JWT — это процедура, которую сервер ресурсов запускает перед диспетчеризацией любого инструмента. Держите три роли раздельно, и пусть каждая выполняет только те проверки, которыми владеет: сервер авторизации выдаёт и ротирует ключи, сервер ресурсов кеширует и проверяет, клиент обнаруживает и регистрируется.

## Концепция

### RFC 8414 — метаданные сервера авторизации OAuth

Документ по адресу `/.well-known/oauth-authorization-server` описывает всё, что нужно клиенту:

```json
{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "jwks_uri": "https://auth.example.com/.well-known/jwks.json",
  "registration_endpoint": "https://auth.example.com/register",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "code_challenge_methods_supported": ["S256"],
  "scopes_supported": ["mcp:tools.read", "mcp:tools.invoke"],
  "token_endpoint_auth_methods_supported": ["none", "private_key_jwt"]
}
```

Клиент, получивший URL ресурса MCP, выстраивает цепочку обнаружения: `oauth-protected-resource` из RFC 9728 (документ сервера ресурсов) называет issuer, затем `oauth-authorization-server` (этот RFC) называет каждую конечную точку. Клиент никогда не зашивает URL авторизации жёстко.

Контракт, который вы проверяете перед тем, как доверять IdP для MCP:

- `code_challenge_methods_supported` включает `S256` (PKCE по RFC 7636). Спецификация однозначна: если это поле **отсутствует**, сервер авторизации не поддерживает PKCE, и клиент **ДОЛЖЕН** отказаться от продолжения.
- `grant_types_supported` включает `authorization_code` и отвергает `password` и `implicit`.
- Заявлен хотя бы один путь регистрации: `client_id_metadata_document_supported: true` (CIMD, предпочтительно) **либо** `registration_endpoint` (RFC 7591 DCR, резервный вариант). Любого из них достаточно для соблюдения контракта; жёстко требовать DCR больше не нужно.
- `response_types_supported` равен ровно `["code"]` для OAuth 2.1.

Если `S256` отсутствует, MCP-сервер отказывается развёртываться против этого IdP — для PKCE нет деградированного режима. Если *ни один* из путей регистрации не заявлен и у вас нет предварительно зарегистрированного `client_id`, зарегистрироваться тоже нельзя; в этом случае неверен манифест развёртывания, а не код.

### RFC 9728 (повтор) — метаданные защищённого ресурса

Урок 16 разобрал RFC 9728. Дельта в продакшне: этот документ — единственное место, где клиент ищет серверы авторизации, которым доверяет *этот конкретный* MCP-сервер. Один MCP-сервер может принимать токены от нескольких IdP (один для сотрудников, один для партнёров). RFC 9728 объявляет этот набор; RFC 8414 документирует, что поддерживает каждый IdP.

```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com", "https://partners.example.com"],
  "scopes_supported": ["mcp:tools.invoke"],
  "bearer_methods_supported": ["header"],
  "resource_documentation": "https://notes.example.com/docs"
}
```

### Документы метаданных Client ID (рекомендуемый вариант по умолчанию)

CIMD переворачивает регистрацию с *отправки* на *получение*. Вместо того чтобы просить сервер авторизации выдать `client_id`, клиент использует контролируемый им HTTPS-URL **в качестве** своего `client_id`. URL разрешается в JSON-документ метаданных; сервер авторизации получает его по требованию в ходе потока OAuth. Доверие укоренено в DNS: если оператор сервера доверяет `app.example.com`, он доверяет клиенту, обслуживаемому с `https://app.example.com/client.json`. Нет цикла регистрации, нет пространства имён `client_id`, которое можно исчерпать, нет состояния на каждый сервер, которое нужно синхронизировать.

Документ метаданных, который размещает клиент:

```json
{
  "client_id": "https://app.example.com/oauth/client.json",
  "client_name": "Example MCP Client",
  "client_uri": "https://app.example.com",
  "redirect_uris": ["http://127.0.0.1:7333/callback", "http://localhost:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

Значение `client_id` в документе **ДОЛЖНО** совпадать с URL, с которого он обслуживается (сервер авторизации это проверяет; несовпадения отклоняются). Сервер авторизации заявляет поддержку через `client_id_metadata_document_supported: true` в своих метаданных RFC 8414.

Спецификация прямо называет два факта о безопасности:

- **SSRF.** Сервер авторизации получает URL, предоставленный злоумышленником. Он должен защищаться от подделки запросов на стороне сервера (никаких запросов к внутренним/административным конечным точкам).
- **Имитация localhost.** Сам по себе CIMD не может помешать локальному злоумышленнику присвоить себе URL метаданных легитимного клиента и привязать любой redirect на `localhost`. Сервер авторизации **ДОЛЖЕН** чётко отображать хост redirect URI при согласии и **СЛЕДУЕТ** предупреждать о redirect только на `localhost`.

Поскольку CIMD не требует состояния на стороне сервера, регистратора, который нужен для DCR, разворачивать не нужно. Сторона клиента доступна только для чтения: разместите документ метаданных на статической HTTPS-конечной точке и позвольте серверу авторизации забрать его.

### RFC 7591 — динамическая регистрация клиента (резервный вариант / обратная совместимость)

DCR теперь имеет статус `MAY` и сохранён для обратной совместимости с развёртываниями до 2025-11-25 и IdP, которые ещё не поддерживают CIMD. Без него (и без CIMD или предварительной регистрации) каждому MCP-клиенту (Cursor, Claude Desktop, кастомный агент) нужен внеполосный обмен с администратором IdP. С DCR клиент отправляет:

```json
POST /register
Content-Type: application/json

{
  "redirect_uris": ["http://127.0.0.1:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none",
  "scope": "mcp:tools.invoke",
  "client_name": "Cursor",
  "software_id": "com.cursor.cursor",
  "software_version": "0.42.0"
}
```

Сервер отвечает `client_id` и `registration_access_token` для последующих обновлений:

```json
{
  "client_id": "c_3e7f1a",
  "client_id_issued_at": 1769472000,
  "redirect_uris": ["http://127.0.0.1:7333/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "registration_access_token": "regt_b2...",
  "registration_client_uri": "https://auth.example.com/register/c_3e7f1a"
}
```

`token_endpoint_auth_method: none` — правильное значение по умолчанию для MCP-клиентов, работающих на устройстве пользователя. Они получают только `client_id` — без `client_secret`, который можно похитить. PKCE даёт доказательство владения, необходимое публичным клиентам.

Три эксплуатационных подводных камня:

- Конечная точка регистрации должна ограничивать частоту запросов по исходному IP. Без этого злоумышленник скриптует миллионы поддельных регистраций и исчерпывает пространство имён `client_id`. Запускайте проверку ограничения частоты запросов до того, как регистратор обработает запрос.
- Некоторые корпоративные IdP требуют `software_statement` (JWT с подписью, подтверждающий клиента). Мок в этом уроке пропускает его; в продакшне подключается шаг проверки, отклоняющий неподписанные регистрации от всего, кроме redirect URI на localhost.
- `registration_access_token` должен храниться как хеш, а не в открытом виде. Кража этого токена означает, что злоумышленник может переписать redirect URI клиента.

### RFC 8707 (повтор) — индикаторы ресурсов

Урок 16 задал форму. Правило продакшна: каждый запрос токена включает `resource=<canonical-mcp-url>`, а MCP-сервер проверяет, что `token.aud` совпадает с его собственным URL ресурса при каждом вызове. Канонический URI — это *самый специфичный* идентификатор сервера: он использует схему и хост в нижнем регистре, без фрагмента и, по соглашению, без завершающего слеша. Компонент пути **не** удаляется по правилу — спецификация сохраняет его, когда он нужен для идентификации конкретного MCP-сервера. `https://mcp.example.com`, `https://mcp.example.com/mcp`, `https://mcp.example.com:8443` и `https://mcp.example.com/server/mcp` — все допустимые канонические URI. Выберите один на сервер и закрепите `aud` ровно за ним. (Мок в этом уроке использует аудитории по голому хосту вроде `https://notes.example.com` для краткости; развёртывание, размещающее несколько MCP-серверов на одном origin, различает их по пути.)

### RFC 7636 (повтор) — PKCE

PKCE обязателен в OAuth 2.1. Поток кода авторизации в этом уроке всегда несёт `code_challenge` и `code_verifier`. Сервер отклоняет любой запрос токена без верификатора или с верификатором, чей хеш не совпадает с сохранённым challenge.

### Профиль авторизации MCP-спецификации 2025-11-25

Спецификация MCP (2025-11-25) точно определяет, что должен делать уровень авторизации MCP-сервера:

- Реализовать метаданные защищённого ресурса RFC 9728 и предоставлять их местоположение либо через заголовок `WWW-Authenticate: Bearer resource_metadata="..."` на 401, **либо** через well-known URI `/.well-known/oauth-protected-resource` (SEP-985 сделала заголовок необязательным при наличии резервного well-known варианта). Поле `authorization_servers` в метаданных **ДОЛЖНО** называть хотя бы один сервер.
- Принимать токены только через `Authorization: Bearer ...` при **каждом** запросе — никогда в строке запроса, никогда с проверкой только в начале сессии.
- Проверять `aud`, `iss`, `exp` и требуемые области доступа при каждом запросе. Сервер **ДОЛЖЕН** проверять, что токен выдан именно для него (аудитория); отсутствующий или несовпадающий `aud` отклоняется, а не трактуется как wildcard.
- При 401/403 возвращать `WWW-Authenticate: Bearer` с параметром `error=...`, параметром `resource_metadata="<PRM-URL>"` (URL документа метаданных, а *не* голый ресурс) и `scope="..."` при `insufficient_scope` (403). Примечание: параметр называется `resource_metadata` — это указатель на обнаружение; параметра `resource` в challenge нет.
- Обнаружение сервера авторизации принимает **либо** метаданные OAuth RFC 8414, **либо** OpenID Connect Discovery 1.0; клиенты должны пробовать оба well-known суффикса в порядке приоритета.
- Клиент (а не сервер) защищается от **атак mix-up**: он записывает ожидаемый `issuer` перед редиректом и проверяет параметр `iss` из ответа авторизации (RFC 9207) перед обменом кода на токен. Один только PKCE не останавливает mix-up, потому что клиент передаёт свой `code_verifier` той конечной точке токена, к которой его направили.

Черновик OAuth 2.1 — субстрат; RFC 8414/7591/8707/9728/9207 + RFC 7636 + CIMD — поверхность; спецификация MCP — профиль.

### Матрица возможностей IdP

Не каждый IdP поддерживает полный профиль MCP. Матрица ниже документирует фактические утверждения о возможностях по состоянию на спецификацию 2025-11-25. Это *шлюз развёртывания*, а не рекомендация.

CIMD появился в спецификации 2025-11-25, а базовый черновик OAuth был принят только в октябре 2025 года, так что поддержка вендоров всё ещё формируется — воспринимайте «CIMD» ниже как «текущее состояние, проверяйте в своём тенанте», а не как постоянное утверждение.

| Категория IdP | Метаданные AS (8414/OIDC) | CIMD | RFC 7591 DCR | RFC 8707 resource | RFC 7636 S256 PKCE | Примечания |
|---|---|---|---|---|---|---|
| Self-hosted (Keycloak) | да | формируется | да | да (с версии 24.x) | да | Эталонный IdP для профиля MCP в этом уроке; полный путь DCR end-to-end, CIMD отслеживает новую спецификацию. |
| Корпоративный SSO (Microsoft Entra ID) | да | формируется | да (премиум-тарифы) | да | да | Доступность DCR различается по тарифу тенанта; проверяйте в целевом тенанте перед развёртыванием. |
| Корпоративный SSO (Okta) | да | формируется | да (Okta CIC / Auth0) | да | да | DCR доступен на Auth0 (теперь Okta CIC); классические организации Okta требуют предварительной регистрации администратором. |
| Социальные IdP (общий случай) | варьируется | нет | редко | редко | да | Большинство социальных IdP относятся к клиентам как к статическим партнёрам; нет самостоятельной регистрации. Используйте как источник идентификации, надстраивая собственный MCP-совместимый сервер авторизации сверху. |
| Кастомный / самописный | зависит | зависит | зависит | зависит | зависит | Если вы поставляете собственный, поставляйте полный профиль и предпочитайте CIMD. Пропуск PKCE или привязки аудитории нарушает контракт авторизации MCP. |

Правило отказа для манифеста развёртывания: если выбранный IdP не заявляет `S256` в `code_challenge_methods_supported`, MCP-сервер отказывается запускаться — у PKCE нет деградированного режима. Регистрация — более мягкий шлюз: нужен *один* рабочий путь (предварительно зарегистрированный `client_id`, `client_id_metadata_document_supported: true` или `registration_endpoint`). Отсутствие DCR само по себе больше не является триггером отказа, поскольку CIMD или предварительная регистрация могут его покрыть.

### Паттерн обновления JWKS (ротация на AS, обновление на сервере ресурсов)

Держите два глагола раздельно, потому что их смешение — реальная продакшн-ошибка:

- **Ротация** — это то, что делает *сервер авторизации*: выпускает новый ключ подписи, публикует его в JWKS, позже выводит старый из обращения. Сервер ресурсов не участвует в этом и не может это делать — он не владеет приватными ключами IdP.
- **Обновление** — это то, что делает *сервер ресурсов*: повторно выполняет `GET` опубликованного JWKS в свой кеш. Это единственное действие с JWKS, которое когда-либо выполняет сервер ресурсов.

Продакшн-режим сбоя — устаревший кеш. Решайте его запланированным заданием обновления плюс кешем «ключ-значение». Сервер ресурсов запускает задание (cron, таймер — что предоставляет ваша среда выполнения), которое с фиксированным интервалом получает `<issuer>/.well-known/jwks.json` и перезаписывает `cache[issuer] = {keys, fetched_at}`. Валидатор читает из этого кеша. Токен, чей `kid` отсутствует в кеше, запускает **одно** синхронное обновление как резервный вариант, затем перепроверяет. Это покрывает сразу два случая: плановое обновление и окна перекрытия ключей, когда токен, подписанный совсем новым ключом, приходит до следующего планового обновления.

Резервный вариант **должен быть повторным запросом, а не ротацией**. Если подключить путь промаха кеша к ротации с выпуском нового ключа, ломаются две вещи: (1) выпуск свежего ключа даёт `kid`, который *всё равно* не совпадает с токеном, поэтому поиск всё равно не удаётся; и (2) злоумышленник, рассылающий токены со случайными значениями `kid`, вынуждает к неограниченной серии создания ключей — самонаведённый DoS. Повторный запрос идемпотентен, так что поддельный `kid` стоит не больше одного потраченного впустую запроса.

Форма кеша:

```json
{
  "https://auth.example.com": {
    "keys": [
      {"kid": "k_2026_03", "kty": "RSA", "n": "...", "e": "AQAB", "alg": "RS256", "use": "sig"},
      {"kid": "k_2026_04", "kty": "RSA", "n": "...", "e": "AQAB", "alg": "RS256", "use": "sig"}
    ],
    "fetched_at": 1772668800
  }
}
```

Два ключа одновременно — это устойчивое состояние. Серверы авторизации ротируют, вводя следующий ключ (`k_2026_04`) до вывода из обращения предыдущего (`k_2026_03`), поэтому токены, выданные под старым ключом, остаются действительными до истечения их срока. Кеш хранит объединение; валидатор выбирает по `kid`.

### Процедура проверки

MCP-сервер запускает проверку перед диспетчеризацией любого инструмента. Форма, которую использует `code/main.py`:

```python
result = server.validate(bearer_token, required_scope="mcp:tools.invoke")
if not result["valid"]:
    return {"status": result["status"], "WWW-Authenticate": result["www_authenticate"]}
```

`validate` декодирует JWT, разрешает ключ подписи из кеша JWKS (обновляя один раз при промахе), проверяет подпись, затем сверяет `iss` со списком разрешённых, `aud` — с каноническим ресурсом этого сервера, `exp` и требуемую область доступа, возвращая challenge `WWW-Authenticate` при первом сбое. То, что это единая процедура на сервере ресурсов, означает, что каждая точка входа (каждый вызов инструмента, каждый транспорт) проходит одни и те же проверки; нет пути, достигающего инструмента без предварительной проверки.

### Разбор повторного использования аудитории (ограничение привилегий токена доступа)

Сервер A (`notes.example.com`) и сервер B (`tasks.example.com`) оба регистрируются на одном сервере авторизации. Сервер A скомпрометирован. Злоумышленник берёт токен пользователя для заметок и предъявляет его серверу B.

Валидатор сервера B:

1. Декодирует JWT, получает JWKS по `kid`, проверяет подпись.
2. Проверяет `iss` по списку `authorization_servers` из своих метаданных защищённого ресурса. (Пройдено — тот же IdP.)
3. Проверяет `aud == "https://tasks.example.com"`. (Провал — `aud` токена равен `https://notes.example.com`.)
4. Возвращает 401 с `WWW-Authenticate: Bearer error="invalid_token", error_description="audience mismatch", resource_metadata="https://tasks.example.com/.well-known/oauth-protected-resource"`.

Claim аудитории — единственная защита от этой атаки на уровне протокола. Пропуск этой проверки ради производительности — самая распространённая продакшн-ошибка; валидатор должен запускаться на каждом запросе, а не только в начале сессии. Спецификация называет это **ограничением привилегий токена доступа**: MCP-сервер `MUST` отклонять любой токен, который не называет его в аудитории.

> **Примечание об именовании.** Спецификация резервирует термин *confused deputy* для смежной, но отдельной проблемы: MCP-сервер, действующий как OAuth-**прокси** к стороннему API, использующий статический client ID, пересылающий токен без получения согласия пользователя для каждого клиента. Привязка аудитории устраняет описанное выше повторное использование; исправление confused deputy — это согласие для каждого клиента **плюс** отказ от передачи входящего токена вышестоящим API (MCP-сервер `MUST` получать собственный отдельный вышестоящий токен).

### Атаки mix-up (клиентская защита, которую сервер обеспечить не может)

Клиент за свою жизнь общается со многими серверами авторизации. Вредоносный AS может попытаться заставить клиента обменять код авторизации честного AS на конечной точке токена атакующего. Привязка аудитории здесь не помогает — атака происходит до того, как появляется какой-либо токен. Защита живёт в клиенте (RFC 9207):

1. Перед редиректом клиент записывает ожидаемый `issuer` из проверенных метаданных AS.
2. В ответе авторизации клиент сравнивает возвращённый параметр `iss` с этим записанным issuer (простое сравнение строк, без нормализации), прежде чем отправлять код куда-либо.
3. Несовпадение (или отсутствие `iss`, когда AS заявлял `authorization_response_iss_parameter_supported`) → отказ, причём даже без отображения полей `error`.

Один только PKCE не останавливает mix-up, потому что клиент передаёт свой `code_verifier` той конечной точке токена, к которой его направили. Именно поэтому спецификация фиксирует issuer для каждого запроса наряду с верификатором PKCE и `state`.

### Режимы сбоя

- **Устаревший JWKS.** Валидатор отклоняет действительные токены после того, как AS ротирует ключ. Исправление — паттерн cron-обновления + повторного запроса при промахе кеша выше. Никогда не кешируйте JWKS без задания обновления.
- **Ротация как резервный вариант.** Подключение пути промаха кеша к ротации с выпуском нового ключа вместо повторного запроса — реальная ошибка: она никогда не производит недостающий `kid`, и превращает контролируемые злоумышленником значения `kid` в DoS через создание ключей. Резервный вариант должен быть идемпотентным `refresh-jwks`.
- **Отсутствующий claim `aud`.** Некоторые IdP по умолчанию пропускают `aud`, если в запросе токена не было `resource`. Валидатор должен отклонять токены с отсутствующим `aud`, а не трактовать отсутствие как wildcard.
- **Mix-up из-за отсутствующей проверки `iss`.** Клиент, не проверяющий параметр ответа авторизации `iss` из RFC 9207 против записанного перед редиректом issuer, может быть направлен на обмен кода честного AS на конечной точке токена атакующего. Это клиентский сбой; сервер ресурсов не может его компенсировать.
- **Гонка повышения области доступа.** Два одновременных потока пошаговой авторизации для одного пользователя могут оба завершиться успешно и произвести два токена доступа с разными областями доступа. Валидатор должен использовать токен, предъявленный в запросе, а не искать «текущую область доступа пользователя» — это создаёт окно TOCTOU.
- **Кража токена регистрации.** Утёкший `registration_access_token` позволяет злоумышленнику переписать redirect URI. Храните их как хеш, требуйте от клиента предъявлять открытый текст при каждом обновлении, ротируйте при подозрении.
- **Незакреплённый `iss`.** Валидатор, принимающий любой `iss`, позволяет злоумышленнику поднять собственный сервер авторизации, зарегистрировать клиента для целевой аудитории и выдавать токены. Список `authorization_servers` из метаданных защищённого ресурса — это список разрешённых; применяйте его.

```figure
t3-jwks-rotate
```

## Практика

`code/main.py` проходит полный продакшн-поток на stdlib Python с тремя ролями — `AuthorizationServer`, `ResourceServer` и `Client`. Поток:

1. Сервер авторизации публикует метаданные RFC 8414 по `/.well-known/oauth-authorization-server`.
2. MCP-клиент вызывает конечную точку метаданных и проверяет варианты регистрации (`client_id_metadata_document_supported` для CIMD, `registration_endpoint` для DCR) и поддержку `S256` PKCE.
3. Практическая часть идёт по резервному пути DCR: клиент отправляет POST на `/register` (RFC 7591) и получает `client_id`. (Клиент CIMD вместо этого предъявил бы собственный HTTPS-URL `client_id` и пропустил этот шаг.)
4. MCP-клиент проходит защищённый PKCE поток кода авторизации (RFC 7636) с индикатором `resource` (RFC 8707).
5. MCP-клиент вызывает инструмент на MCP-сервере с `Authorization: Bearer ...`.
6. MCP-сервер запускает `validate`, разрешая ключ подписи из кеша JWKS.
7. IdP ротирует ключ; плановое обновление повторно подтягивает JWKS в кеш.
8. Следующий вызов проверяется по обновлённым ключам без перезапуска, а предыдущий токен по-прежнему проверяется в окне перекрытия.
9. Попытка повторного использования между аудиториями против другого ресурса MCP получает 401 с `audience mismatch` и указателем `resource_metadata`.

JWT здесь использует HS256 с общим секретом (чтобы урок работал только на stdlib). В продакшне используется RS256 или EdDSA с описанным выше паттерном JWKS; логика проверки при этом идентична. Поскольку IdP и сервер ресурсов живут в одном процессе, `refresh_jwks` читает список ключей сервера авторизации напрямую; по сети это HTTP `GET` к `jwks_uri`.

## Поставка

Этот урок производит `outputs/skill-mcp-auth.md`. По конфигурации MCP-сервера и набору возможностей IdP навык выдаёт поверхность авторизации, которую нужно поднять: метаданные защищённого ресурса, путь регистрации (CIMD, предварительная регистрация или резервный DCR), расписание обновления JWKS, отображение областей доступа и правила отказа на случай, если IdP не поддерживает полный профиль RFC.

## Упражнения

1. Запустите `code/main.py`. Проследите поток. Отметьте, как IdP ротирует ключ на шаге 6, плановая `refresh_jwks` повторно подтягивает опубликованный набор, и как старый токен (в окне перекрытия), так и свежий токен проверяются без перезапуска.

2. Добавьте новый IdP в список `authorization_servers` метаданных защищённого ресурса. Выдайте токен, подписанный новым IdP, и убедитесь, что валидатор его принимает. Выдайте токен, подписанный незаявленным IdP, и убедитесь, что валидатор отклоняет его с `WWW-Authenticate: Bearer error="invalid_token", error_description="iss not allowed"`.

3. Добавьте проверку ограничения частоты запросов в `register_client`, которая запускается до того, как регистратор примет запрос. Используйте token bucket на исходный IP, хранимый в небольшом словаре с ключом по IP.

4. Прочитайте RFC 7591 и найдите два поля, которые обработчик `/register` в уроке не проверяет. Добавьте проверку. (Подсказка: `software_statement` и схема URI `redirect_uris`.)

5. Добавьте путь документа метаданных Client ID. Разместите `client.json`, чей `client_id` равен собственному URL, и заставьте сервер авторизации получить и проверить его (отклонять, если `client_id` ≠ URL). Убедитесь, что CIMD-клиент регистрируется без вызова `register_client`.

6. Докажите исправление DoS. Отправьте валидатору токен со случайным `kid` и убедитесь, что `refresh_jwks` запускается не более одного раза, а число ключей сервера авторизации не растёт. Затем намеренно переподключите резервный вариант к ротации с выпуском нового ключа и понаблюдайте, как число ключей растёт на каждый поддельный токен — после этого восстановите повторный запрос.

7. Реализуйте клиентскую проверку `iss` из RFC 9207 из раздела о mix-up: запишите ожидаемый issuer перед запросом авторизации, затем отклоните ответ авторизации, чей `iss` не совпадает.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| ASM | «Документ метаданных OAuth» | JSON `/.well-known/oauth-authorization-server` из RFC 8414 |
| CIMD | «URL метаданных клиента» | Client ID Metadata Document — HTTPS-URL, используемый как `client_id`; AS его забирает. Рекомендуемый вариант по умолчанию с 2025-11-25 |
| DCR | «Самостоятельная регистрация клиента» | Поток `POST /register` из RFC 7591; понижен до резервного `MAY` в 2025-11-25 |
| JWKS | «Публичные ключи для проверки JWT» | JSON Web Key Set, получаемый из `jwks_uri`, индексированный по `kid` |
| Rotate vs refresh | «Обновление ключей» | *Rotate* — AS выпускает/выводит из обращения ключи подписи; *refresh* — сервер ресурсов повторно получает опубликованный набор. Серверы ресурсов только когда-либо делают refresh |
| Resource indicator | «Параметр аудитории» | Параметр `resource` из RFC 8707, закрепляющий токен за одним сервером |
| `aud` claim | «Аудитория» | Claim JWT, который валидатор сравнивает с каноническим URL ресурса |
| Audience replay | «Повторное использование токена» | Токен, выданный для сервера A, предъявлен серверу B; от этого защищает проверка аудитории (в спецификации: ограничение привилегий токена доступа) |
| Confused deputy | «Злоупотребление прокси-токеном» | MCP-прокси со статическим client ID, пересылающий токен без согласия для каждого клиента; отличается от повторного использования аудитории |
| Mix-up attack | «Неверная конечная точка токена» | Клиент направлен на обмен кода честного AS на конечной точке атакующего; защита клиентская, через `iss` из RFC 9207 |
| `iss` allow-list | «Доверенные серверы авторизации» | Набор, названный в `authorization_servers` метаданных защищённого ресурса |
| `resource_metadata` | «Где найти документ PRM» | Параметр `WWW-Authenticate`, называющий URL метаданных RFC 9728 на 401/403 |
| Public client | «Нативный или браузерный клиент» | OAuth-клиент без `client_secret`; PKCE компенсирует это |
| `WWW-Authenticate` | «Заголовок ответа 401/403» | Несёт директивы `Bearer error=...`, управляющие восстановлением на стороне клиента |
