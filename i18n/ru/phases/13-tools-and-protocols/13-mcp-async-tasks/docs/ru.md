# Асинхронные задачи (SEP-1686) — вызов сейчас, получение результата позже для долгих операций

> Реальная агентная работа занимает от минут до часов: прогоны CI, синтез глубоких исследований, пакетный экспорт. Синхронные вызовы инструментов разрывают соединения, истекают по таймауту или блокируют UI. SEP-1686, объединённый 25.11.2025, добавляет примитив Tasks: любой запрос может быть дополнен, чтобы стать задачей, а результат можно получить позже или транслировать через уведомления о состоянии. Примечание о риске устаревания: Tasks экспериментальны вплоть до первой половины 2026 года; поверхность SDK всё ещё проектируется вокруг спецификации.

**Тип:** Build**Языки:** Python (stdlib, async task state machine)**Предварительные требования:** Фаза 13 · 07 (MCP server), Фаза 13 · 09 (transports)**Время:** ~75 минут
## Цели обучения

- Определять, когда следует повысить инструмент с синхронного до дополненного задачей (>30 секунд серверной работы).
- Пройти по жизненному циклу задачи: `working` → `input_required` → `completed` / `failed` / `cancelled`.
- Сохранять состояние задачи так, чтобы сбои не теряли работу в процессе выполнения.
- Правильно опрашивать `tasks/status` и получать `tasks/result`.

## Проблема

Инструмент `generate_report` выполняет многоминутный конвейер извлечения данных. Варианты в рамках синхронной модели:

1. Держать соединение открытым три минуты. Удалённые транспорты его разрывают; клиенты истекают по таймауту; UI зависают.
2. Немедленно вернуть заглушку; потребовать от клиента опрашивать пользовательский endpoint. Ломает единообразие MCP.
3. Запустить и забыть; результата нет.

Ни один вариант не хорош. SEP-1686 добавляет четвёртый: дополнение задачей. Любой запрос (как правило, `tools/call`) можно пометить как задачу. Сервер немедленно возвращает id задачи. Клиент опрашивает `tasks/status` и получает `tasks/result`, когда всё готово. Серверное состояние переживает перезапуски.

## Концепция

### Дополнение задачей

Запрос становится задачей путём установки `params._meta.task.required: true` (или `optional: true`, решает сервер). Сервер немедленно отвечает:

```json
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "_meta": {
      "task": {
        "id": "tsk_9f7b...",
        "state": "working",
        "ttl": 900000
      }
    }
  }
}
```

`ttl` — это обещание сервера сохранять состояние; после истечения ttl результат задачи отбрасывается.

### Согласие для каждого инструмента

Аннотации инструмента могут объявлять поддержку задач:

- `taskSupport: "forbidden"` — этот инструмент всегда выполняется синхронно. Безопасно для быстрых инструментов.
- `taskSupport: "optional"` — клиент может запросить дополнение задачей.
- `taskSupport: "required"` — клиент ОБЯЗАН использовать дополнение задачей.

Инструмент `generate_report` был бы `required`. Инструмент `notes_search` был бы `forbidden`.

### Состояния

```
working  -> input_required -> working  (loop via elicitation)
working  -> completed
working  -> failed
working  -> cancelled
```

Машина состояний устроена только на добавление: как только задача становится `completed`, `failed` или `cancelled`, она терминальна.

### Методы

- `tasks/status {taskId}` — возвращает текущее состояние и подсказку о прогрессе.
- `tasks/result {taskId}` — блокирует или возвращает 404, если ещё не готово.
- `tasks/cancel {taskId}` — идемпотентен; терминальные состояния игнорируются.
- `tasks/list` — опционально; перечисляет активные и недавно завершённые задачи.

### Трансляция изменений состояния

Когда сервер это поддерживает, клиент может подписаться на уведомления о состоянии:

```
server -> notifications/tasks/updated {taskId, state, progress?}
```

Клиенты, которые транслируют вместо опроса, получают лучший UX. Опрос всегда поддерживается как минимальная поверхность.

### Долговечное состояние

Спецификация требует, чтобы серверы, объявляющие поддержку задач, сохраняли состояние. Сбой не должен терять завершённые результаты в пределах ttl. Хранилища варьируются от SQLite до Redis и файловой системы. Харнесс урока 13 использует файловую систему.

### Семантика отмены

`tasks/cancel` идемпотентен. Если задача выполняется, сервер пытается её остановить (проверьте кооперативную отмену на уровне исполнителя). Если задача уже терминальна, запрос — не более чем пустая операция.

### Восстановление после сбоя

Когда процесс сервера перезапускается:

1. Загрузить все сохранённые состояния задач.
2. Пометить любые задачи в состоянии `working`, чей процесс погиб, как `failed` с ошибкой `CRASH_RECOVERY`.
3. Сохранить `completed` / `failed` / `cancelled` на срок их ttl.

### Асинхронные задачи вместе со sampling

Задача может сама вызывать `sampling/createMessage`. Так работают долгие исследовательские задачи: поток задачи на сервере сэмплирует модель клиента по мере необходимости, а UI клиента показывает задачу как `working` с периодическими обновлениями прогресса.

### Почему это экспериментально

SEP-1686 вышел 25.11.2025, но более широкая дорожная карта называет три открытых вопроса: долговечные примитивы подписки, подзадачи (отношения родитель-потомок между задачами) и стандартизация ttl результата. Ожидайте, что спецификация будет развиваться в течение 2026 года. Продакшен-код должен рассматривать Tasks как стабильные только для типового случая и подстраховываться от будущих изменений SDK в отношении подзадач.

```figure
tp-task-lifecycle
```

## Практика

`code/main.py` реализует долговечное хранилище задач (на файловой системе) и инструмент `generate_report`, который выполняется в фоновом потоке. Клиенты вызывают инструмент, немедленно получают id задачи, опрашивают `tasks/status`, пока воркер обновляет прогресс, и получают `tasks/result`, когда всё готово. Отмена работает; восстановление после сбоя симулируется убийством потока воркера и перезагрузкой состояния.

На что обратить внимание:

- Состояние задачи в формате JSON сохраняется в `/tmp/lesson-13-tasks/<id>.json`.
- Поток воркера обновляет поле `progress`; опрос показывает его продвижение.
- Отмена со стороны клиента устанавливает событие; воркер проверяет его и завершается раньше срока.
- Перезагрузка состояния при «сбое» помечает выполнявшуюся задачу как `failed` с `CRASH_RECOVERY`.

## Поставка

Этот урок производит `outputs/skill-task-store-designer.md`. Учитывая долго выполняющийся инструмент (исследование, сборка, экспорт), навык проектирует хранилище задач (форма состояния, ttl, долговечность), выбирает правильный флаг taskSupport и набрасывает уведомления о прогрессе.

## Упражнения

1. Запустите `code/main.py`. Запустите задачу `generate_report`, опросите статус, затем получите результат.

2. Добавьте вызов `tasks/cancel` в середине выполнения. Убедитесь, что воркер его учитывает, а состояние становится `cancelled`.

3. Симулируйте восстановление после сбоя: убейте поток воркера, перезапустите загрузчик и понаблюдайте за режимом отказа `CRASH_RECOVERY`.

4. Расширьте хранилище до SQLite. Выигрыш в долговечности тот же; открываются варианты запросов (перечислить все задачи из сессии X).

5. Прочитайте пост о дорожной карте MCP на 2026 год. Определите один открытый вопрос, связанный с Tasks, который наиболее вероятно повлияет на проектирование API SDK в следующем году.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Task | «Долго выполняющийся вызов инструмента» | Запрос, дополненный `_meta.task` для асинхронного выполнения |
| SEP-1686 | «Спецификация Tasks» | Spec Evolution Proposal, добавивший Tasks 25.11.2025 |
| `_meta.task` | «Конверт задачи» | Метаданные запроса, содержащие id, состояние, ttl |
| taskSupport | «Флаг инструмента» | `forbidden` / `optional` / `required` для каждого инструмента |
| `tasks/status` | «Метод опроса» | Получение текущего состояния и опциональной подсказки о прогрессе |
| `tasks/result` | «Получение результата» | Возвращает завершённую полезную нагрузку или 404, если ещё не готово |
| `tasks/cancel` | «Остановить это» | Идемпотентный запрос отмены |
| ttl | «Бюджет удержания» | Миллисекунды, в течение которых сервер обещает хранить состояние задачи |
| `notifications/tasks/updated` | «Пуш состояния» | Инициированное сервером событие изменения состояния |
| Durable store | «Устойчивое к сбоям состояние» | Слой хранения на файловой системе / SQLite / Redis |
