# Шлюзы и реестры MCP — корпоративные плоскости управления

> Предприятия не могут позволить каждому разработчику устанавливать произвольные MCP-серверы. Шлюз централизует авторизацию, RBAC, аудит, ограничение частоты запросов, кеширование и обнаружение отравления инструментов, а затем предоставляет объединённую поверхность инструментов как единую конечную точку MCP. Официальный реестр MCP (Anthropic + GitHub + PulseMCP + Microsoft, с верификацией namespace) — канонический вышестоящий источник. Этот урок определяет место шлюза, разбирает минимальную реализацию и обозревает ландшафт вендоров 2026 года.

**Тип:** Learn**Языки:** Python (stdlib, минимальный шлюз)**Предварительные требования:** Фаза 13 · 15 (отравление инструментов), Фаза 13 · 16 (OAuth 2.1)**Время:** ~45 минут
## Цели обучения

- Объяснить, где располагается шлюз MCP (между MCP-клиентами и несколькими вышестоящими MCP-серверами).
- Реализовать пять обязанностей шлюза: авторизация, RBAC, аудит, ограничение частоты запросов, политика.
- Обеспечить закрепление хешей инструментов на уровне шлюза.
- Отличать официальный реестр MCP от метареестров (Glama, MCPMarket, MCP.so, Smithery, LobeHub).

## Проблема

У компании из списка Fortune 500 есть 30 одобренных MCP-серверов, 5000 разработчиков, требования комплаенса и аудита, а также команда безопасности, которой нужна централизованная политика. Позволить каждому разработчику устанавливать произвольные серверы в своих IDE — неприемлемо.

Паттерн шлюза:

1. Шлюз работает как единая конечная точка Streamable HTTP, к которой подключаются разработчики.
2. Шлюз хранит учётные данные для каждого вышестоящего MCP-сервера.
3. Каждый запрос разработчика аутентифицируется и ограничивается по области доступа через собственный OAuth шлюза.
4. Шлюз маршрутизирует вызов на вышестоящий сервер, применяя политику.
5. Все вызовы логируются для аудита.

Cloudflare MCP Portals, Kong AI Gateway, IBM ContextForge, MintMCP, TrueFoundry, Envoy AI Gateway — все поставили шлюзы или функции шлюзов в 2025-2026 годах.

Тем временем официальный реестр MCP запустился как канонический вышестоящий источник: курируемые, верифицированные по namespace серверы с обратными DNS-именами, из которого шлюз может подтягивать данные. Метареестры (Glama, MCPMarket, MCP.so, Smithery, LobeHub) агрегируют серверы из нескольких источников.

## Концепция

### Пять обязанностей шлюза

1. **Авторизация.** OAuth 2.1 для идентификации разработчика; сопоставление с ролями пользователя.
2. **RBAC.** Политика для каждого пользователя: какие серверы, какие инструменты, какие области доступа.
3. **Аудит.** Каждый вызов логируется с указанием кто, что, когда, результат.
4. **Ограничение частоты запросов.** Лимиты на пользователя / инструмент / сервер для предотвращения злоупотреблений.
5. **Политика.** Отклонение отравленных описаний, применение Rule of Two, редактирование PII.

### Шлюз как единая конечная точка

Для разработчиков шлюз выглядит как один MCP-сервер. Внутри он маршрутизирует к N вышестоящим серверам. Идентификаторы сессий (Phase 13 · 09) переписываются на границе.

### Хранение учётных данных

Разработчики никогда не видят вышестоящие токены. Шлюз хранит их сам (либо проксирует к поставщику удостоверений, который их хранит). Разработчик с `notes:read` на шлюзе может транзитивно получить доступ к серверу заметок с собственными учётными данными шлюза — но только по политике, которая связывает транзитивный доступ.

### Закрепление хешей инструментов на шлюзе

Шлюз хранит манифест одобренных описаний инструментов (хеши SHA256). На этапе обнаружения он получает `tools/list` каждого вышестоящего сервера, сравнивает хеши с манифестом и удаляет любой инструмент, чьё описание изменилось. Это защита от rug-pull из Phase 13 · 15, применённая централизованно.

### Политика как код

Продвинутые шлюзы выражают политику в OPA/Rego, Kyverno или Styra. Правила вроде «пользователь `alice` может вызывать `github.open_pr` только для репозиториев в организации `acme`» кодируются декларативно. Простые шлюзы используют написанный вручную Python. Оба подхода допустимы.

### Маршрутизация с учётом сессий

Когда сессия пользователя включает несколько серверов, шлюз мультиплексирует: единая MCP-сессия разработчика содержит N вышестоящих сессий, по одной на сервер. Уведомления от любого вышестоящего сервера маршрутизируются через шлюз в сессию разработчика.

### Слияние namespace

Шлюзы сливают пространства имён инструментов от всех вышестоящих серверов, обычно добавляя префикс при коллизии. `github.open_pr`, `notes.search`. Это делает маршрутизацию однозначной.

### Реестры

- **Официальный реестр MCP (`registry.modelcontextprotocol.io`).** Запущен под управлением Anthropic, GitHub, PulseMCP, Microsoft. Верифицирован по namespace (обратный DNS: `io.github.user/server`). Предварительно отфильтрован по базовому качеству.
- **Glama.** Метареестр, ориентированный на поиск, агрегирующий множество источников.
- **MCPMarket.** Каталог с коммерческим уклоном и списками вендоров.
- **MCP.so.** Общественный каталог; открытые заявки.
- **Smithery.** Поток установки в стиле пакетного менеджера.
- **LobeHub.** Реестр, интегрированный в интерфейс их приложения LobeChat.

Корпоративные шлюзы по умолчанию подтягивают данные из официального реестра, допускают добавления, курируемые администратором, из метареестров, и отклоняют всё незакреплённое.

### Обратные DNS-имена

Официальный реестр требует обратных DNS-имён для публичных серверов: `io.github.alice/notes`. Пространства имён предотвращают захват имён и делают делегирование доверия более явным.

## Практика

`code/main.py` поставляет минимальный шлюз объёмом ~150 строк: аутентифицирует пользователей по фиктивному Bearer-токену, хранит политику RBAC для каждого пользователя, маршрутизирует запросы к двум вышестоящим MCP-серверам, записывает каждый вызов в журнал аудита, применяет ограничение частоты запросов и отклоняет любой инструмент вышестоящего сервера, чей хеш описания не совпадает с закреплённым манифестом.

На что обратить внимание:

- Словарь `RBAC`, ключом которого служит `user_id`, с разрешёнными записями `server_tool`.
- `AUDIT_LOG` — список событий только для добавления.
- Ограничение частоты запросов использует token bucket на пользователя.
- Закреплённый манифест — словарь `server::tool -> hash`.

## Упражнения

1. Запустите `code/main.py`. Сделайте вызов от имени разрешённого пользователя; затем от имени неразрешённого пользователя; затем всплеск запросов, превышающий лимит частоты. Проверьте все три сценария.

2. Добавьте политику, редактирующую PII в результатах перед возвратом клиенту. Используйте простой проход по регулярному выражению для строк, похожих на SSN; отметьте пробел (email, номера телефонов).

3. Расширьте журнал аудита, чтобы он выдавал спаны OpenTelemetry GenAI. Phase 13 · 20 разбирает точные атрибуты.

4. Спроектируйте политику RBAC для команды из 50 разработчиков с пятью вышестоящими серверами (заметки, github, postgres, jira, slack). Кто получает доступ только на чтение к каждому? Кто получает запись?

5. Прочитайте статью Cloudflare о корпоративном MCP от начала до конца. Найдите одну функцию, которую Cloudflare поставляет, а этот шлюз на stdlib — нет.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Gateway | «Прокси MCP» | Централизующий сервер между клиентами и вышестоящими серверами |
| Credential vaulting | «Вышестоящие токены остаются на стороне сервера» | Разработчики никогда не видят вышестоящие токены |
| Session-aware routing | «Сессия с несколькими вышестоящими серверами» | Шлюз мультиплексирует N вышестоящих сессий на одну сессию разработчика |
| Tool-hash pinning | «Одобренный манифест» | SHA256 каждого одобренного описания инструмента; централизованно блокирует rug-pull |
| RBAC | «Политика для каждого пользователя» | Управление доступом на основе ролей для инструментов и серверов |
| Policy-as-code | «Декларативные правила» | Политики OPA/Rego, Kyverno, Styra, применяемые на шлюзе |
| Audit log | «Кто, что, когда» | Журнал событий только для добавления, для комплаенса |
| Rate limit | «Token bucket на пользователя» | Лимиты в минуту для предотвращения злоупотреблений |
| Official MCP Registry | «Канонический вышестоящий источник» | `registry.modelcontextprotocol.io`, верифицирован по namespace |
| Reverse-DNS naming | «Пространство имён реестра» | Соглашение `io.github.user/server` |
