# Слой маршрутизации LLM — LiteLLM, OpenRouter, Portkey

> Привязка к одному провайдеру дорого обходится. Разные задачи с вызовом инструментов подходят разным моделям. Шлюзы маршрутизации дают единую поверхность API, повторные попытки, отказоустойчивость, учёт затрат и защитные ограничения. Три архетипа доминируют в 2026 году: LiteLLM (открытый исходный код, self-hosted), OpenRouter (управляемый SaaS), Portkey (production-grade, с открытым исходным кодом с марта 2026 года). В этом уроке называются критерии выбора и разбирается шлюз маршрутизации на stdlib.

**Тип:** Learn**Языки:** Python (stdlib, маршрутизация + отказоустойчивость + учёт затрат)**Предварительные требования:** Фаза 13 · 02 (вызов функций), Фаза 13 · 17 (шлюзы)**Время:** ~45 минут
## Цели обучения

- Различать варианты маршрутизации: self-hosted, управляемый и production-grade.
- Реализовать цепочку резервных вариантов, повторяющую попытки при сбоях провайдера в заданном порядке приоритета.
- Отслеживать затраты и использование токенов на каждый запрос по разным провайдерам.
- Выбирать между LiteLLM, OpenRouter и Portkey для заданного производственного ограничения.

## Проблема

Сценарии, где маршрутизация провайдеров имеет значение:

1. **Стоимость.** Claude Sonnet стоит в 3 раза больше, чем Haiku. Для задачи триажа достаточно Haiku; для задачи синтеза Sonnet того стоит. Маршрутизируйте по запросу.

2. **Отказоустойчивость.** У OpenAI плохой час. Все запросы падают. Вы хотите автоматический переход на резервный вариант к Anthropic без повторного развёртывания.

3. **Задержка.** Живому чат-интерфейсу нужно быстрое время до первого токена. Пакетному суммаризатору — нет. Маршрутизируйте по SLA задержки.

4. **Соответствие требованиям.** Пользователи из ЕС должны оставаться в регионах ЕС. Маршрутизируйте по региону.

5. **Экспериментирование.** A/B-тестирование двух моделей на одной и той же нагрузке. Маршрутизируйте по тестовому бакету.

Вручную кодировать всё это для каждой интеграции — повторяющаяся работа. Шлюз маршрутизации даёт один API в стиле OpenAI и берёт остальное на себя.

## Концепция

### Форма прокси, совместимого с OpenAI

Все говорят в формате OpenAI. Шлюз маршрутизации предоставляет `/v1/chat/completions`, принимает схему OpenAI и внутри проксирует в Anthropic / Gemini / Cohere / Ollama / что угодно. Клиенту это безразлично.

### Псевдонимы моделей

Вместо идентификатора конкретного снимка модели ваш код использует `our_smart_model`. Шлюз сопоставляет псевдонимы с реальными моделями. Когда провайдер выпускает новое поколение моделей, вы меняете псевдоним на стороне сервера; ваш код ничего не трогает.

### Цепочки резервных вариантов

```
primary: openai/gpt-4o
on 5xx: anthropic/claude-3-5-sonnet
on 5xx: google/gemini-1.5-pro
on 5xx: refuse
```

Шлюзы определяют это в конфигурации. Повторные попытки учитываются в бюджете, чтобы каскады резервных вариантов не взрывали стоимость.

### Семантическое кеширование

Идентичные или почти идентичные промпты попадают в кеш вместо провайдера. Экономия на повторяющихся циклах агента может составлять от 30 до 60 процентов. Ключи основаны на эмбеддингах; почти идентичные промпты используют один и тот же слот кеша.

### Защитные ограничения

На уровне шлюза:

- **Редактирование PII.** Проход на основе регулярных выражений или ML перед отправкой промптов.
- **Нарушения политики.** Отклонение промптов с запрещённым содержимым.
- **Фильтры вывода.** Очистка завершений от утечек.

И Portkey, и Kong поставляют готовые защитные ограничения. LiteLLM оставляет их опциональными.

### Ограничения частоты запросов на ключ

Один API-ключ = одна команда. Бюджеты на ключ не дают одной команде потреблять общую квоту. Большинство шлюзов это поддерживают.

### Компромиссы self-hosted и управляемых решений

| Фактор | LiteLLM (self-hosted) | OpenRouter (managed) | Portkey (production) |
|--------|----------------------|----------------------|----------------------|
| Код | Открытый исходный код, Python | Управляемый SaaS | Открытый исходный код (март 2026) + управляемый |
| Настройка | Развернуть прокси | Зарегистрироваться | Любой вариант |
| Провайдеры | 100+ | 300+ | 100+ |
| Биллинг | Ваши собственные ключи | Кредиты OpenRouter | Ваши собственные ключи |
| Наблюдаемость | OpenTelemetry | Дашборд | Полный OTel + редактирование PII |
| Лучше всего для | Команд, желающих полного контроля | Быстрого прототипирования | Продакшена с требованиями соответствия |

LiteLLM выигрывает, когда у вас есть SRE-команда и нужен суверенитет данных. OpenRouter выигрывает, когда нужна единая подписка и никакой инфраструктуры. Portkey выигрывает, когда нужны защитные ограничения и соответствие требованиям из коробки.

### Учёт затрат

Каждый запрос несёт `provider`, `model`, `input_tokens`, `output_tokens`. Умножьте на цену за токен для каждой модели (взятую из тарифного листа, который ведёт шлюз). Агрегация по пользователю / команде / проекту.

### MCP плюс маршрутизация

Шлюз может маршрутизировать как вызовы LLM, так и запросы MCP-сэмплирования. Когда modelPreferences запроса сэмплирования предпочитают конкретную модель, шлюз транслирует это в нужный бэкенд. Здесь Phase 13 · 17 (шлюз MCP) и шлюз маршрутизации этого урока иногда объединяются в один сервис.

### Стратегии маршрутизации

- **Статический приоритет.** Первый в списке; переход на резервный вариант при ошибке.
- **Балансировка нагрузки.** По кругу или взвешенно.
- **С учётом стоимости.** Выбор самой дешёвой модели, удовлетворяющей задержке / качеству.
- **С учётом задержки.** Выбор самой быстрой модели за последние N минут.
- **С учётом задачи.** Классификатор промптов направляет код в одну модель, суммаризацию — в другую.

```figure
tp-router-failover
```

## Практика

`code/main.py` реализует шлюз маршрутизации примерно в 150 строк: принимает запросы в формате OpenAI, транслирует их в заглушки для каждого провайдера, выполняет цепочку резервных вариантов по приоритету, отслеживает затраты на каждый запрос и применяет проход редактирования PII к входным данным. Запустите его с тремя сценариями: обычный запрос, отказ основного провайдера, вызывающий переход на резервный вариант, утечка PII, перехваченная редактированием.

На что смотреть:

- Словарь `ROUTES`: псевдоним -> упорядоченный по приоритету список конкретных провайдеров.
- Цикл резервных вариантов повторяет попытки при 5xx.
- Трекер затрат умножает использование токенов на ставки для каждой модели.
- Редактор PII вычищает шаблоны, похожие на SSN, перед пересылкой.

## Поставка

Этот урок производит `outputs/skill-routing-config-designer.md`. По профилю нагрузки (задержка, стоимость, соответствие требованиям) навык выбирает LiteLLM / OpenRouter / Portkey и производит конфигурацию маршрутизации.

## Упражнения

1. Запустите `code/main.py`. Вызовите сценарий отказа; убедитесь, что резервный вариант переходит на второго провайдера, а стоимость приписывается корректно.

2. Добавьте семантическое кеширование: SHA256 промпта служит ключом поиска; попадания в кеш возвращаются мгновенно. Измерьте экономию на повторяющемся вызове.

3. Добавьте классификатор промптов, направляющий промпты «code ...» на псевдоним, ориентированный на интеллект, а промпты «summarize ...» — на псевдоним, ориентированный на скорость.

4. Спроектируйте бюджеты по командам: у каждой команды месячный лимит расходов; шлюз отклоняет запросы после достижения лимита. Выберите гранулярность применения (на запрос или оконная).

5. Прочитайте документацию LiteLLM, OpenRouter и Portkey бок о бок. Назовите одну функцию, которую поставляет каждый из них и не поставляют два других.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Routing gateway | «Прокси LLM» | Слой с единой поверхностью API перед множеством провайдеров |
| OpenAI-compatible | «Говорит на схеме OpenAI» | Принимает форму `/v1/chat/completions`, транслирует в любой бэкенд |
| Model alias | «our_smart_model» | Имя в вашем коде, которое шлюз сопоставляет с конкретной моделью |
| Fallback chain | «Список повторных попыток» | Упорядоченный список провайдеров, к которым обращаются при сбое |
| Semantic caching | «Кеш на эмбеддингах промпта» | Ключ — эмбеддинг промпта; почти дубликаты используют один кеш-хит |
| Guardrails | «Фильтры ввода/вывода» | Редактирование PII, отклонение нарушений политики |
| Per-key rate limit | «Бюджет команды» | Квота, привязанная к API-ключу |
| Cost tracking | «Расход на запрос» | Агрегированное использование токенов x цена за модель |
| LiteLLM | «Открытый прокси» | Self-hosted шлюз маршрутизации с открытым кодом |
| OpenRouter | «Управляемый SaaS» | Хостируемый шлюз с биллингом на основе кредитов |
| Portkey | «Production-вариант» | Открытый исходный код + управляемый вариант со встроенными защитными ограничениями |
