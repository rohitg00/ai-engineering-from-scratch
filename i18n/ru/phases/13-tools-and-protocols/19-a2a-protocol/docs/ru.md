# A2A — протокол «агент-агенту»

> MCP — это протокол «агент-инструменту». A2A (Agent2Agent) — это протокол «агент-агенту»: открытый протокол, позволяющий непрозрачным агентам на разных фреймворках взаимодействовать друг с другом. Выпущен Google в апреле 2025 года, передан Linux Foundation в июне 2025 года, достиг версии v1.0 в апреле 2026 года при поддержке более 150 организаций, включая AWS, Cisco, Microsoft, Salesforce, SAP и ServiceNow. Протокол поглотил ACP от IBM и добавил расширение платежей AP2. В этом уроке разбираются Agent Card, жизненный цикл Task и два транспортных биндинга.

**Тип:** Build**Языки:** Python (stdlib, Agent Card + инфраструктура Task)**Предварительные требования:** Фаза 13 · 06 (основы MCP), Фаза 13 · 08 (MCP-клиент)**Время:** ~75 минут
## Цели обучения

- Различать сценарии агент-инструменту (MCP) и агент-агенту (A2A).
- Публиковать Agent Card по адресу `/.well-known/agent.json` с метаданными навыков и конечной точки.
- Пройти жизненный цикл Task (submitted → working → input-required → completed / failed / canceled / rejected).
- Использовать сообщения с частями (Parts: text, file, data) и артефакты (Artifacts) как выходные данные.

## Проблема

Агенту обслуживания клиентов нужно делегировать написание отчёта специализированному агенту-писателю. Варианты до появления A2A:

- Кастомный REST API. Работает, но каждая пара агентов — разовое решение.
- Общая кодовая база. Требует, чтобы оба агента работали на одном фреймворке.
- MCP. Не подходит: MCP предназначен для вызова инструментов, а не для совместной работы двух агентов с сохранением непрозрачности внутренних рассуждений каждого агента.

A2A закрывает этот пробел. Он моделирует взаимодействие как отправку одним агентом Task другому, с жизненным циклом, сообщениями и артефактами. Внутреннее состояние вызываемого агента остаётся непрозрачным — вызывающий видит только переходы состояний задачи и итоговые выходные данные.

A2A — это протокол «пусть агенты из разных фреймворков разговаривают друг с другом». Он не заменяет MCP; эти два протокола дополняют друг друга.

## Концепция

### Agent Card

Каждый A2A-совместимый агент публикует карточку по адресу `/.well-known/agent.json`:

```json
{
  "schemaVersion": "1.0",
  "name": "research-agent",
  "description": "Summarizes academic papers and drafts citations.",
  "url": "https://research.example.com/a2a",
  "version": "1.2.0",
  "skills": [
    {
      "id": "summarize_paper",
      "name": "Summarize a paper",
      "description": "Read a paper PDF and produce a 3-paragraph summary.",
      "inputModes": ["text", "file"],
      "outputModes": ["text", "artifact"]
    }
  ],
  "capabilities": {"streaming": true, "pushNotifications": true}
}
```

Обнаружение основано на URL: получить карточку, узнать URL конечной точки A2A, перечислить навыки.

### Подписанные Agent Card (AP2)

Расширение AP2 (сентябрь 2025) добавляет криптографические подписи к Agent Card. Издатель подписывает свою карточку JWT; потребители проверяют подпись. Это предотвращает имперсонацию.

### Жизненный цикл Task

```
submitted -> working -> completed | failed | canceled | rejected
             -> input_required -> working (loop via message)
```

Клиенты инициируют задачу через `tasks/send`. Вызываемый агент переходит между состояниями; клиенты подписываются на обновления состояния через SSE либо опрашивают.

### Сообщения и части

Сообщение несёт одну или несколько частей (Parts):

- `text` — обычный текст.
- `file` — base64-блоб с mimeType.
- `data` — типизированная JSON-нагрузка (структурированный вход для вызываемого агента).

Пример:

```json
{
  "role": "user",
  "parts": [
    {"type": "text", "text": "Summarize this paper."},
    {"type": "file", "file": {"name": "paper.pdf", "mimeType": "application/pdf", "bytes": "..."}},
    {"type": "data", "data": {"targetLength": "3 paragraphs"}}
  ]
}
```

### Артефакты

Выходные данные — это артефакты (Artifacts), а не сырые строки. Артефакт — именованный типизированный вывод:

```json
{
  "name": "summary",
  "parts": [{"type": "text", "text": "..."}],
  "mimeType": "text/markdown"
}
```

Артефакты можно передавать потоком по частям. Вызывающая сторона накапливает их.

### Два транспортных биндинга

1. **JSON-RPC поверх HTTP.** Конечная точка `/a2a`, POST для запросов, опциональный SSE для потоковой передачи. Биндинг по умолчанию.
2. **gRPC.** Для корпоративных сред, где gRPC — родной протокол.

Оба биндинга несут одну и ту же логическую форму сообщения.

### Сохранение непрозрачности

Ключевой принцип проектирования: внутреннее состояние вызываемого агента непрозрачно. Вызывающая сторона видит состояние задачи и артефакты. Цепочка рассуждений вызываемого агента, его вызовы инструментов, делегирование под-агентам — всё это невидимо. Это отличается от MCP, где вызовы инструментов прозрачны.

Обоснование: A2A позволяет конкурентам сотрудничать, не раскрывая внутреннее устройство. A2A может звучать как «вызови этого агента обслуживания клиентов», при этом вызывающая сторона не узнаёт, как этот агент реализует сервис.

### Соотношение с MCP

| Измерение | MCP | A2A |
|-----------|-----|-----|
| Сценарий использования | Агент-инструменту | Агент-агенту |
| Непрозрачность | Прозрачные вызовы инструментов | Непрозрачные внутренние рассуждения |
| Типичный вызывающий | Среда выполнения агента | Другой агент |
| Состояние | Результат вызова инструмента | Task с жизненным циклом |
| Авторизация | OAuth 2.1 (Phase 13 · 16) | Agent Card с подписью JWT (AP2) |
| Транспорт | Stdio / Streamable HTTP | JSON-RPC поверх HTTP / gRPC |

Используйте MCP, когда нужно вызвать конкретный инструмент. Используйте A2A, когда нужно делегировать целую задачу другому агенту. Многие продакшн-системы используют оба: агент применяет MCP для слоя инструментов и A2A для слоя совместной работы.

## Практика

`code/main.py` реализует минимальную инфраструктуру A2A: агент-исследователь публикует свою карточку, агент-писатель получает `tasks/send` с частями, включающими PDF и текстовую инструкцию, проходит через working → input_required → working → completed и возвращает текстовый артефакт. Всё на stdlib; используется транспорт в памяти, чтобы сосредоточиться на формах сообщений.

На что обратить внимание:

- Форма JSON Agent Card.
- Присвоение id задачи и переходы состояний.
- Сообщения со смешанными типами частей.
- Ветка input-required в середине задачи.
- Возврат артефакта при завершении.

## Поставка

Этот урок производит `outputs/skill-a2a-agent-spec.md`. По новому агенту, который должен быть вызываем другими агентами, навык производит JSON Agent Card, схему навыков и чертёж конечной точки.

## Упражнения

1. Запустите `code/main.py`. Проследите полный жизненный цикл Task, включая паузу input-required, где вызываемый агент запрашивает уточнение.

2. Добавьте подписанный Agent Card. Подпишите с помощью HMAC над каноническим JSON карточки. Напишите верификатор и убедитесь, что он отклоняет изменённую карточку.

3. Реализуйте потоковую передачу задачи: агент-писатель выдаёт три инкрементальных фрагмента артефакта через SSE, а вызывающая сторона накапливает их.

4. Спроектируйте A2A-агента, оборачивающего MCP-сервер. Сопоставьте каждый инструмент MCP с навыком A2A. Отметьте компромиссы — какая непрозрачность теряется?

5. Прочитайте анонс A2A v1.0 и найдите одну функцию, которая по состоянию на апрель 2026 года ещё не реализована ни одним фреймворком. (Подсказка: она связана с многошаговым делегированием задач.)

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| A2A | «Протокол агент-агенту» | Открытый протокол для непрозрачной совместной работы агентов |
| Agent Card | «`.well-known/agent.json`» | Опубликованные метаданные, описывающие навыки и конечную точку агента |
| Skill | «Вызываемая единица» | Именованная операция, поддерживаемая агентом (аналог инструмента MCP) |
| Task | «Единица делегирования» | Рабочий элемент с жизненным циклом и итоговым артефактом |
| Message | «Вход задачи» | Несёт части (Parts: text, file, data) |
| Part | «Типизированный фрагмент» | Элемент сообщения `text` / `file` / `data` |
| Artifact | «Выход задачи» | Именованный типизированный вывод, возвращаемый при завершении |
| AP2 | «Agent Payments Protocol» | Расширение подписанных Agent Card для доверия и платежей |
| Opacity | «Совместная работа как чёрный ящик» | Внутреннее устройство вызываемого агента скрыто от вызывающей стороны |
| Input-required | «Пауза задачи» | Состояние жизненного цикла, когда агенту нужна дополнительная информация |
