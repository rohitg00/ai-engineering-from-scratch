# Параллельные вызовы инструментов и стриминг с инструментами

> Три независимых запроса погоды, выполненные последовательно, — это три круговых обхода. Запустите их параллельно, и общее время схлопывается до времени самого медленного вызова. Каждый передовой провайдер теперь выдаёт несколько вызовов инструментов за один ход. Выгода реальна; обвязка тонкая. Этот урок разбирает обе половины: параллельное разветвление и пересборку потоковых аргументов, с акцентом на ловушку корреляции по идентификатору.

**Тип:** Build
**Языки:** Python (стандартная библиотека, пул потоков + обвязка для стриминга)
**Предварительные требования:** Фаза 13 · 02 (углублённый разбор вызова функций)
**Время:** ~75 минут

## Цели обучения

- Объяснять, зачем существует `parallel_tool_calls: true` и когда его отключать.
- Соотносить потоковые фрагменты аргументов с нужным идентификатором вызова инструмента при параллельном разветвлении.
- Пересобирать частичные строки `arguments` в полный JSON, не разбирая их преждевременно.
- Запускать бенчмарк погоды по трём городам, демонстрирующий последовательную и параллельную задержку.

## Проблема

Без параллельных вызовов агент, отвечающий на вопрос «какая погода в Бангалоре, Токио и Цюрихе», делает так:

```
user -> LLM
LLM -> call get_weather(Bengaluru)
host -> run executor, reply with result
LLM -> call get_weather(Tokyo)
host -> run executor, reply with result
LLM -> call get_weather(Zurich)
host -> run executor, reply with result
LLM -> final text answer
```

Три круговых обхода большой языковой модели (LLM), каждый из которых дополнительно увеличивает задержку на время работы исполнителя. В итоге реальное время выполнения примерно в 4 раза превышает идеальное.

С параллельными вызовами:

```
user -> LLM
LLM -> call get_weather(Bengaluru); call get_weather(Tokyo); call get_weather(Zurich)
host -> run all three executors concurrently, reply with three results
LLM -> final text answer
```

Один круговой обход LLM. Время исполнителя — это максимум из трёх, а не сумма. Продакшен-бенчмарки на OpenAI, Anthropic и Gemini показывают снижение реального времени выполнения на 60–70 процентов на нагрузках с разветвлением.

Цена — сложность корреляции. Когда три вызова завершаются не по порядку, ваши результаты обязаны нести совпадающий `tool_call_id`, чтобы модель могла их сопоставить. Когда результаты приходят потоково, нужно собрать частичные фрагменты аргументов в полный JSON перед выполнением. Gemini 3 добавила уникальные идентификаторы отчасти для решения реальной проблемы: два параллельных вызова одного и того же инструмента были неразличимы.

## Концепция

### Включение параллельного режима

- **OpenAI.** `parallel_tool_calls: true` включён по умолчанию. Установите `false`, чтобы принудить последовательный режим.
- **Anthropic.** Параллельный режим через `disable_parallel_tool_use: false` (по умолчанию начиная с Claude 3.5). Установите `true` для последовательного режима.
- **Gemini.** Всегда способен на параллельность; `tool_config.function_calling_config.mode = "AUTO"` позволяет модели решать самой.

Отключайте параллельный режим, когда у инструментов есть зависимости по порядку (`create_file`, затем `write_file`), когда вывод одного вызова влияет на вход другого, или когда ограничитель частоты запросов не справляется с разветвлением.

### Корреляция по идентификатору

У каждого вызова, который выдаёт модель, есть `id`. Каждый результат, который возвращает хост, обязан включать тот же идентификатор. Без этого результаты неоднозначны.

- **OpenAI.** `tool_call_id` в каждом сообщении с ролью tool.
- **Anthropic.** `tool_use_id` в каждом блоке `tool_result`.
- **Gemini.** `id` в каждом `functionResponse` (Gemini 3 и новее; Gemini 2 сопоставляла по имени, что ломалось при параллельных вызовах с одинаковым именем).

### Параллельный запуск вызовов

Хост запускает исполнитель каждого вызова в собственном потоке, корутине или удалённом воркере. Простейшая обвязка использует пул потоков; в продакшене применяется asyncio с `asyncio.gather` или структурированной конкурентностью. Порядок завершения непредсказуем — идентификатор является связующим элементом.

Распространённая ошибка: отвечать результатами в порядке списка вызовов, а не в порядке завершения. Обычно это работает, потому что модель ориентируется только на `tool_call_id`, но если результат теряется или дублируется, ответ не по порядку усложняет отладку. Предпочтительно отвечать в порядке завершения с явными идентификаторами.

### Потоковые вызовы инструментов

Когда модель работает в потоковом режиме, `arguments` приходят по частям. Три отдельных потока фрагментов для трёх параллельных вызовов чередуются в канале. Нужен один аккумулятор на идентификатор.

Форма по провайдерам:

- **OpenAI.** Каждый фрагмент — это `choices[0].delta.tool_calls[i].function.arguments` (частичная строка). Фрагмент несёт `index` (позицию в списке вызовов). Вы накапливаете по индексу, считываете `id` при первом появлении и разбираете JSON, когда `finish_reason = "tool_calls"`.
- **Anthropic.** Потоковые события — это `message_start`, затем по одному `content_block_start` на блок с типом `tool_use` (содержащим id, name, пустой input). События `content_block_delta` несут фрагменты `input_json_delta`. `content_block_stop` закрывает каждый блок.
- **Gemini.** `streamFunctionCallArguments` (Gemini 3 и новее) выдаёт фрагменты с `functionCallId`, поэтому вызовы чисто чередуются. До Gemini 3 стриминг возвращал по одному полному вызову за раз.

### Частичный JSON и ловушка преждевременного разбора

Нельзя разбирать `arguments`, пока они не завершены. Частичный JSON вроде `{"city": "Beng` невалиден и вызовет ошибку. Правильный барьер — сигнал провайдера о конце вызова: `finish_reason = "tool_calls"` у OpenAI, `content_block_stop` у Anthropic или событие конца потока у Gemini. Только тогда стоит пытаться выполнить `json.loads`. Более надёжный подход использует инкрементальный JSON-парсер, выдающий события по мере завершения структуры; руководство OpenAI по стримингу рекомендует это для UX с живым индикатором «думаю». Подсчёт скобок ненадёжен как тест полноты (скобки внутри строк в кавычках или экранированного содержимого дают ложные срабатывания) и должен использоваться только как неформальная эвристика для отладки.

### Завершение не по порядку

```
call_A: fast API, returns first
call_B: slow API, returns second
call_C: median API, returns third
```

Ответ хоста всё равно должен указывать идентификаторы:

```
[{role: "tool", tool_call_id: "call_A", content: ...},
 {role: "tool", tool_call_id: "call_B", content: ...},
 {role: "tool", tool_call_id: "call_C", content: ...}]
```

Порядок в ответе не влияет на корректность у OpenAI или Anthropic. Gemini принимает любой порядок, если идентификаторы совпадают.

### Бенчмарк: последовательный против параллельного

Обвязка в `code/main.py` симулирует три исполнителя с задержкой 400, 600 и 800 мс. Последовательный запуск выполняет их за 1800 мс суммарно. Параллельный запуск выполняет их за max(400, 600, 800) = 800 мс. Разница постоянна, а не пропорциональна, поэтому выигрыш растёт с числом инструментов.

Оговорка из реального мира: параллельные вызовы нагружают нижестоящие API. Разветвление на 10 сторон к сервису с ограничением частоты запросов провалится. Фаза 13 · 17 покрывает противодавление на уровне шлюза; семантика повторов запланирована на будущую фазу.

### Реальное время выполнения при потоковом разветвлении

Если сама модель работает в потоковом режиме, вы можете начать выполнение сразу, как только аргументы одного вызова завершены, не дожидаясь финализации всех вызовов. Это оптимизация, которую документирует OpenAI, но не все SDK её раскрывают. Обвязка в этом уроке делает именно так: как только симулированный поток выдаёт полный объект аргументов, хост запускает этот вызов.

```figure
tp-parallel-fanout
```

## Применяем

`code/main.py` состоит из двух половин. Первая запускает три симулированных вызова погоды последовательно и параллельно с помощью `concurrent.futures.ThreadPoolExecutor` и печатает реальное время выполнения. Вторая половина воспроизводит фиктивный потоковый ответ — фрагменты `arguments` для трёх параллельных вызовов, чередующиеся в одном потоке, — и пересобирает их по идентификатору с помощью `StreamAccumulator`. Ни LLM, ни сети, только логика пересборки.

На что обратить внимание:

- Последовательный таймер показывает 1,8 секунды. Параллельный таймер показывает 0,8 секунды на тех же фиктивных задержках.
- Аккумулятор обрабатывает фрагменты, приходящие не по порядку, буферизуя их по идентификатору и разбирая JSON только когда аргументы каждого вызова завершены.
- Исполнитель запускается сразу, как только аргументы идентификатора финализированы, а не после завершения всех потоков.

## Публикуем

Этот урок производит `outputs/skill-parallel-call-safety-check.md`. Получив реестр инструментов, скилл проверяет, какие инструменты безопасно распараллеливать, у каких есть зависимости по порядку, а какие перегрузят нижестоящие ограничения частоты запросов, — и возвращает обновлённый реестр с флагами `parallel_safe` для каждого инструмента.

## Упражнения

1. Запустите `code/main.py` и меняйте симулированные задержки. Убедитесь, что соотношение параллельного и последовательного времени примерно равно `max/sum` (реальные запуски слегка отклоняются от идеала из-за планирования потоков, сериализации и накладных расходов обвязки). При каком распределении задержек параллельность перестаёт иметь значение?

2. Расширьте аккумулятор, чтобы он обрабатывал случай «вызов был отменён посреди потока», сбрасывая свой буфер и выдавая событие `cancelled`. Какой провайдер явно документирует этот случай? Проверьте семантику `content_block_stop` у Anthropic и поведение `finish_reason: "length"` у OpenAI.

3. Замените пул потоков на `asyncio.gather`. Сравните оба варианта в бенчмарке. Вы должны увидеть небольшой выигрыш у асинхронного варианта из-за меньшей стоимости переключения контекста, но только если исполнители выполняют реальный ввод-вывод.

4. Выберите два инструмента, которые НЕ должны распараллеливаться (например, `create_file`, затем `write_file`). Добавьте граф `ordering_dependency` в реестр и заблокируйте параллельное разветвление на основе этого графа. Это минимальная обвязка для планирования с учётом зависимостей, которую формализует будущая фаза инженерии агентов.

5. Прочитайте раздел OpenAI о параллельном вызове функций и документацию Anthropic по `disable_parallel_tool_use`. Определите единственный реальный тип инструмента, для которого Anthropic рекомендует отключать параллельность. (Подсказка: изменения одного и того же ресурса с существенными последствиями.)

## Ключевые термины

| Термин | Как обычно говорят | Что это на самом деле означает |
|------|----------------|------------------------|
| Параллельные вызовы инструментов | «Разветвление за один ход» | Модель выдаёт несколько вызовов инструментов в одном сообщении ассистента |
| `parallel_tool_calls` | «Флаг OpenAI» | Включает или отключает выдачу нескольких вызовов |
| `disable_parallel_tool_use` | «Инверсия у Anthropic» | Флаг отказа; по умолчанию параллельность включена |
| Идентификатор вызова инструмента | «Идентификатор корреляции» | Идентификатор вызова, который должно повторить сообщение с результатом |
| Аккумулятор | «Буфер потока» | Строковый буфер по идентификатору для частичных фрагментов `arguments` |
| Завершение не по порядку | «Сначала самый быстрый» | Параллельные вызовы завершаются в непредсказуемом порядке; идентификаторы — связующий элемент |
| Граф зависимостей | «Ограничения по порядку» | Инструменты, чей вывод поступает на вход других инструментов; распараллелить нельзя |
| Ловушка преждевременного разбора | «Сбой JSON.parse» | Попытка разобрать неполную строку `arguments` |
| `streamFunctionCallArguments` | «Функция Gemini 3» | Потоковые фрагменты аргументов с уникальным идентификатором для каждого вызова |
| Ответ в порядке завершения | «Не ждать всех» | Отвечать результатами по мере поступления, сопоставляя их по идентификатору |
