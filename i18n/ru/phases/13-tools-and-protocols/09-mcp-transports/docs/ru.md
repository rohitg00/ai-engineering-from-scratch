# Транспорты MCP — stdio против Streamable HTTP против миграции с SSE

> stdio работает локально и больше нигде. Streamable HTTP (2025-03-26) — стандарт для удалённого взаимодействия. Старый транспорт HTTP+SSE устарел и удаляется в середине 2026 года. Выбор неверного транспорта обходится миграцией; выбор верного даёт удалённо размещаемый сервер MCP с непрерывностью сессии и защитой от DNS-rebinding.

**Тип:** Learn**Языки:** Python (stdlib, Streamable HTTP endpoint skeleton)**Предварительные требования:** Фаза 13 · 07, 08 (MCP server and client)**Время:** ~45 минут
## Цели обучения

- Выбирать между stdio и Streamable HTTP исходя из формы развёртывания (локально или удалённо, один процесс или флот).
- Реализовать паттерн единой конечной точки Streamable HTTP: POST для запросов, GET для потока сессии.
- Обеспечивать проверку `Origin` и семантику id сессии, чтобы противостоять DNS-rebinding.
- Мигрировать устаревший сервер HTTP+SSE на Streamable HTTP до дедлайнов удаления в середине 2026 года.

## Проблема

Первый удалённый транспорт MCP (2024-11) — это HTTP+SSE: две конечные точки, одна для POST-запросов клиента и одна для канала Server-Sent-Events для потока от сервера к клиенту. Он работал. Он же был неуклюжим: две конечные точки на сессию, ломающиеся кеши перед некоторыми CDN и жёсткая зависимость от долгоживущих SSE-соединений, которые некоторые WAF агрессивно обрывают.

Спецификация 2025-03-26 заменила его Streamable HTTP: одна конечная точка, POST для запросов клиента, GET для установления потока сессии, оба разделяют заголовок `Mcp-Session-Id`. Каждый сервер, построенный или мигрировавший с тех пор, использует Streamable HTTP. Старый режим SSE выводится из эксплуатации — Atlassian Rovo убрал его 30 июня 2026 года; Keboola — 1 апреля 2026 года; большинство оставшихся корпоративных серверов — к концу 2026 года.

А stdio по-прежнему важен для локальных серверов. Claude Desktop, VS Code и любой клиент в форме IDE порождают серверы через stdio. Правильная ментальная модель: stdio для «этой машины», Streamable HTTP для «по сети». Смешения нет.

## Концепция

### stdio

- Транспорт на дочернем процессе. Клиент порождает сервер, общается через stdin/stdout.
- Один JSON-объект на строку. С разделением по строкам.
- Нет id сессии; идентичность процесса — это сессия.
- Авторизация не нужна (дочерний процесс наследует границу доверия родителя).
- Никогда не используйте для удалённых серверов — понадобился бы SSH или socat для туннелирования, а в этом случае лучше использовать Streamable HTTP.

### Streamable HTTP

Единая конечная точка `/mcp` (или любой путь). Поддерживает три метода HTTP:

- **POST /mcp.** Клиент отправляет сообщение JSON-RPC. Сервер отвечает либо одним JSON-ответом, либо SSE-потоком из одного или нескольких ответов (полезно для пакетных ответов и уведомлений, связанных с этим запросом).
- **GET /mcp.** Клиент открывает долгоживущий SSE-канал. Сервер использует его для запросов от сервера к клиенту (sampling, уведомления, elicitation).
- **DELETE /mcp.** Клиент явно завершает сессию.

Сессии идентифицируются заголовком `Mcp-Session-Id`, который сервер устанавливает в первом ответе, а клиент повторяет в каждом последующем запросе. Id сессии ДОЛЖНЫ быть криптографически случайными (128+ бит); id, выбранные клиентом, отклоняются из соображений безопасности.

### Одна конечная точка против двух

Двухконечный режим из старой спецификации по-прежнему вызываем в 2026 году — спецификация объявляет его «поддерживаемым для совместимости». Но все новые серверы должны быть с одной конечной точкой. Официальные SDK выдают режим с одной конечной точкой; используйте устаревший режим только при общении с немигрировавшим удалённым сервером.

### Проверка `Origin` и DNS-rebinding

Браузеры не являются клиентами MCP (пока), но злоумышленник может сконструировать веб-страницу, которая убедит браузер отправить POST на `localhost:1234/mcp` — где слушает локальный сервер MCP пользователя. Если сервер не проверяет `Origin`, политика same-origin браузера не спасёт, потому что `Origin: http://evil.com` — валидный кросс-ориджин.

Спецификация 2025-11-25 требует от серверов отклонять запросы, чей `Origin` не входит в белый список. Белый список обычно содержит хост клиента MCP (`https://claude.ai`, `vscode-webview://*`) и варианты localhost для локальных UI.

### Жизненный цикл id сессии

1. Клиент отправляет первый запрос без `Mcp-Session-Id`.
2. Сервер назначает случайный id, устанавливает `Mcp-Session-Id` в заголовке ответа.
3. Клиент повторяет этот заголовок во всех последующих запросах и в `GET /mcp` для потока.
4. Сессия может быть отозвана сервером; клиент видит 404 в последующих запросах и должен заново инициализироваться.
5. Клиент может явно вызвать DELETE для сессии для чистого завершения.

### Keepalive и переподключение

Соединения SSE рвутся. Клиент восстанавливает их, снова выполняя GET с тем же `Mcp-Session-Id`. Сервер ДОЛЖЕН ставить в очередь события, пропущенные во время сбоя (в разумном окне), и воспроизводить их через заголовок `last-event-id`, который повторяет клиент.

Phase 13 · 13 разбирает Tasks, которые позволяют долгой работе пережить даже полное переподключение сессии.

### Проверка обратной совместимости

Клиент, который хочет поддерживать и старые, и новые серверы:

1. Отправляет POST на `/mcp`.
2. Если ответ `200 OK` с JSON или SSE — это Streamable HTTP.
3. Если ответ `200 OK` с `Content-Type: text/event-stream` И заголовком `Location`, указывающим на вторичную конечную точку — это устаревший HTTP+SSE; нужно перейти по `Location`.

### Cloudflare, ngrok и хостинг

Продакшн-серверы MCP с удалённым доступом в 2026 году работают на Cloudflare Workers (с их MCP Agents SDK), Vercel Functions или контейнеризированном Node/Python. Ключевое: ваш хостинг должен поддерживать долгоживущие HTTP-соединения для GET SSE. Бесплатный тариф Vercel ограничен 10 секундами и непригоден. Cloudflare Workers поддерживают неограниченные по времени потоки.

### Композиция шлюзов

Когда вы ставите шлюз (Phase 13 · 17) перед несколькими серверами MCP, шлюз — это единая конечная точка Streamable HTTP, которая переписывает id сессий и мультиплексирует запросы к вышестоящим серверам. Инструменты сливаются на уровне шлюза; клиент видит один логический сервер.

### Режимы сбоя транспорта

- **SIGPIPE в stdio.** Смерть дочернего процесса посреди записи вызывает SIGPIPE; серверы должны завершаться чисто. Клиенты должны обнаруживать EOF и помечать сессию мёртвой.
- **HTTP 502 / 504.** Cloudflare, nginx и другие прокси выдают их при сбое вышестоящего сервера. Клиенты Streamable HTTP должны повторить запрос один раз после короткой задержки.
- **Разрыв SSE-соединения.** TCP RST, таймаут прокси или смена сети клиентом закрывают поток. Клиент переподключается с `Mcp-Session-Id` и опциональным `last-event-id` для восстановления.
- **Отзыв сессии.** Сервер аннулирует id сессии; клиент видит 404 в следующем запросе. Клиент должен провести рукопожатие заново.
- **Расхождение часов.** Расчёты TTL ресурса на клиенте расходятся с сервером. Клиент должен считать временные метки сервера авторитетными.

### Когда обходить Streamable HTTP

Некоторые компании разворачивают серверы MCP за транспортами gRPC или очередей сообщений внутри собственных сетей. Это нестандартно — спецификация MCP формально не определяет такие варианты. Шлюзы могут выставлять поверхность Streamable HTTP для клиентов MCP, используя gRPC внутри. Держите внешнюю поверхность соответствующей спецификации; трансляцию берёт на себя шлюз.

```figure
tp-transport-handshake
```

## Практика

`code/main.py` реализует минимальную конечную точку Streamable HTTP на `http.server` (stdlib). Он обрабатывает POST, GET и DELETE на `/mcp`, устанавливает `Mcp-Session-Id` в первом ответе, проверяет `Origin` и отклоняет запросы от источников не из белого списка. Обработчик переиспользует логику диспетчеризации сервера заметок из урока 07.

На что смотреть:

- Обработчик POST читает тело JSON-RPC, диспетчеризует и пишет JSON-ответ (вариант с одним ответом; SSE-вариант структурно похож).
- Проверка `Origin` отклоняет стандартный пробный запрос `http://evil.example`, но принимает `http://localhost`.
- Id сессии — случайные 128-битные шестнадцатеричные строки; сервер хранит состояние по каждой сессии в памяти.

## Упражнения

1. Запустите `code/main.py`. Отправьте `initialize` через `curl` и понаблюдайте за заголовком ответа `Mcp-Session-Id`. Отправьте второй запрос, повторив заголовок, и проверьте непрерывность сессии.

2. Добавьте GET-обработчик, открывающий SSE-поток. Отправляйте одно событие `notifications/progress` каждые пять секунд. Переподключитесь, снова выполнив GET с тем же id сессии, и подтвердите, что сервер его принимает.

3. Реализуйте логику воспроизведения `last-event-id`. При переподключении воспроизводите все события, сгенерированные после этого id.

4. Расширьте проверку `Origin` для поддержки шаблона с подстановочным знаком (`https://*.example.com`) и подтвердите, что она принимает `https://app.example.com`, но отклоняет `https://evil.example.com.attacker.net`.

5. Возьмите устаревший сервер HTTP+SSE из официального реестра (их несколько) и набросайте миграцию: что меняется в обработке конечных точек, генерации id сессии и семантике заголовков.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| stdio transport | «Локальный дочерний процесс» | JSON-RPC поверх stdin/stdout, с разделением по строкам |
| Streamable HTTP | «Удалённый транспорт» | Единая конечная точка POST + GET + опциональный SSE, спецификация от 2025-03-26 |
| HTTP+SSE | «Устаревший» | Двухконечная модель, удаляемая в середине 2026 года |
| `Mcp-Session-Id` | «Заголовок сессии» | Случайный id, назначенный сервером и повторяемый в каждом последующем запросе |
| `Origin` allowlist | «Защита от DNS-rebinding» | Отклонение запросов, чей Origin не одобрен |
| Single endpoint | «Один URL» | `/mcp` обрабатывает POST / GET / DELETE для всех операций сессии |
| `last-event-id` | «Воспроизведение SSE» | Заголовок, используемый для возобновления оборванного потока без потери событий |
| Backwards-compat probe | «Определение старого и нового» | Проверка формы ответа клиентом, автоматически выбирающая транспорт |
| Long-lived HTTP | «SSE-стриминг» | Сервер проталкивает события минутами или часами по одному TCP-соединению |
| Session revocation | «Принудительная переинициализация» | Сервер аннулирует id сессии; клиент должен провести рукопожатие заново |
