# Создание клиента MCP — обнаружение, вызов, управление сессиями

> Большинство материалов по MCP предлагают туториалы по серверу и лишь машут рукой в сторону клиента. Именно в коде клиента живёт сложная оркестрация: порождение процессов, согласование возможностей, слияние списков инструментов от нескольких серверов, обратные вызовы sampling, переподключение и разрешение коллизий пространства имён. Этот урок собирает мультисерверный клиент, который поднимает три разных сервера MCP в одно плоское пространство имён инструментов для модели.

**Тип:** Build**Языки:** Python (stdlib, multi-server MCP client)**Предварительные требования:** Фаза 13 · 07 (building an MCP server)**Время:** ~75 минут
## Цели обучения

- Породить сервер MCP как дочерний процесс, завершить `initialize` и отправить `notifications/initialized`.
- Поддерживать состояние сессии для каждого сервера (возможности, список инструментов, id последних увиденных уведомлений).
- Слить списки инструментов от нескольких серверов в одно пространство имён с обработкой коллизий.
- Маршрутизировать вызов инструмента к серверу, которому он принадлежит, и собрать ответ.

## Проблема

Реальный хост агента (Claude Desktop, Cursor, Goose, Gemini CLI) загружает несколько серверов MCP одновременно. У пользователя могут одновременно работать сервер файловой системы, сервер Postgres и сервер GitHub. Задачи клиента:

1. Породить каждый сервер.
2. Провести рукопожатие с каждым независимо.
3. Вызвать `tools/list` на каждом и свести результат в единый список.
4. Когда модель выдаёт `notes_search`, найти его в объединённом пространстве имён и маршрутизировать к нужному серверу.
5. Обрабатывать уведомления от любого сервера (`tools/list_changed`), не блокируясь.
6. Переподключаться при сбое транспорта.

Собрать всё это вручную — вот что отличает «игрушку» от «пригодного к использованию». Официальные SDK оборачивают это за вас, но ментальная модель должна быть вашей.

## Концепция

### Порождение дочернего процесса

`subprocess.Popen` с `stdin=PIPE, stdout=PIPE, stderr=PIPE`. Установите `bufsize=1` и используйте текстовый режим для построчного чтения. Каждый сервер — один процесс; клиент держит по одному дескриптору `Popen` на сервер.

### Состояние сессии для каждого сервера

Объект `Session` для каждого сервера хранит:

- `process` — дескриптор Popen.
- `capabilities` — то, что сервер объявил при `initialize`.
- `tools` — последний результат `tools/list`.
- `pending` — соответствие id запроса промису/future, ожидающему ответа.

Запросы по своей природе асинхронны; `tools/call`, отправленный серверу A, пока сервер B находится в процессе вызова, не должен блокировать. Используйте либо потоки с очередями, либо asyncio.

### Объединённое пространство имён

Когда клиент видит агрегированный список инструментов, имена могут сталкиваться. Два сервера могут выставлять `search`. У клиента есть три варианта:

1. **Префикс по имени сервера.** `notes/search`, `files/search`. Понятно, но некрасиво.
2. **Молчаливый приоритет первого.** `search` более позднего сервера перезаписывает более ранний. Рискованно; скрывает коллизии.
3. **Отклонение коллизии.** Отказаться загружать второй сервер; уведомить пользователя. Безопаснее всего для хостов, чувствительных к безопасности.

Claude Desktop использует префикс по имени сервера. Cursor использует отклонение коллизии с понятной ошибкой. VS Code MCP тоже принял префикс по имени сервера.

### Маршрутизация

После слияния таблица диспетчеризации сопоставляет `tool_name -> session`. Модель выдаёт вызов по имени; клиент находит сессию и пишет сообщение `tools/call` в stdin этого сервера, затем ожидает ответ.

### Обратный вызов sampling

Если сервер объявил возможность `sampling` при `initialize`, он может отправить `sampling/createMessage`, попросив клиент запустить свою LLM. Клиент должен:

1. Заблокировать дальнейшие запросы к этому серверу до разрешения sampling — или конвейеризовать, если его реализация поддерживает конкурентность.
2. Вызвать своего провайдера LLM.
3. Отправить ответ обратно на сервер.

Урок 11 разбирает sampling целиком. Этот урок делает лишь заглушку для полноты картины.

### Обработка уведомлений

`notifications/tools/list_changed` означает: заново вызвать `tools/list`. `notifications/resources/updated` означает: перечитать ресурс, если он используется. Уведомления не должны порождать ответы — не пытайтесь их подтверждать.

Частая ошибка клиента: блокировка цикла чтения на `tools/call`, пока в потоке лежит уведомление. Используйте фоновый поток-читатель, который проталкивает каждое сообщение в очередь; основной поток извлекает и диспетчеризует.

### Переподключение

Транспорт может выйти из строя: сервер упал, ОС убила процесс, канал stdio разорвался. Клиент обнаруживает EOF на stdout и считает сессию мёртвой. Варианты:

- Молча перезапустить сервер и провести рукопожатие заново. Подходит для чисто read-only серверов.
- Показать сбой пользователю. Подходит для сессионных серверов с видимым пользователю состоянием.

Phase 13 · 09 разбирает семантику переподключения Streamable HTTP; stdio проще.

### Keepalive и id сессии

Streamable HTTP использует заголовок `Mcp-Session-Id`. У stdio нет id сессии — идентичность процесса И ЕСТЬ сессия. Пинги keepalive опциональны; каналы stdio не рвутся из-за простоя.

## Практика

`code/main.py` порождает три симулированных сервера MCP как подпроцессы, проводит рукопожатие с каждым, сливает их списки инструментов и маршрутизирует вызовы инструментов к нужному серверу. «Серверы» на самом деле — другие процессы Python, запускающие игрушечные обработчики (без реальной LLM). Запустите его, чтобы увидеть:

- Три инициализации, каждая со своим набором возможностей.
- Три результата `tools/list`, слитых в пространство имён из 7 инструментов.
- Решение о маршрутизации на основе имени инструмента.
- Предотвращённую коллизию за счёт префиксации пространства имён.

На что смотреть:

- Датакласс `Session` аккуратно хранит состояние для каждого сервера.
- Фоновый поток-читатель извлекает каждую строку из stdout, не блокируя основной поток.
- Таблица диспетчеризации — это простой `dict[str, Session]`.
- Обработка коллизий явная: когда два сервера объявляют одинаковое имя, более поздний переименовывается с префиксом.

## Поставка

Этот урок производит `outputs/skill-mcp-client-harness.md`. По декларативному списку серверов MCP (имя, команда, аргументы) навык производит обвязку, которая порождает их, сливает списки инструментов и поставляет функцию маршрутизации с разрешением коллизий.

## Упражнения

1. Запустите `code/main.py` и понаблюдайте за логом порождения серверов. Убейте один из симулированных серверных процессов сигналом SIGTERM и понаблюдайте, как клиент обнаруживает EOF и помечает эту сессию мёртвой.

2. Реализуйте префиксацию пространства имён. Когда два сервера выставляют `search`, переименуйте второй в `<server>/search`. Обновите таблицу диспетчеризации и убедитесь, что вызовы инструментов маршрутизируются корректно.

3. Добавьте задержку в стиле connection-pool-backoff для перезапуска сервера: экспоненциальная задержка при последовательных сбоях, ограничение в 30 секунд, уведомление пользователя после трёх сбоев.

4. Набросайте клиент, поддерживающий 100 одновременных серверов MCP. Какая структура данных заменит простой словарь диспетчеризации? (Подсказка: бор (trie) для префиксного пространства имён плюс метрика количества инструментов на сервер.)

5. Перенесите клиент на официальный Python SDK MCP. SDK оборачивает `stdio_client` и `ClientSession`. Код должен сократиться примерно с 200 строк до ~40, сохранив маршрутизацию между несколькими серверами.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| MCP client | «Хост агента» | Процесс, порождающий серверы и оркестрирующий вызовы инструментов |
| Session | «Состояние на сервер» | Учёт возможностей, списка инструментов и ожидающих запросов |
| Merged namespace | «Один список инструментов» | Плоский набор имён инструментов по всем активным серверам |
| Namespace collision | «Два сервера — один инструмент» | Клиент должен префиксировать, отклонить или выбрать первый по приоритету дубликат |
| Routing | «Кто обрабатывает этот вызов?» | Диспетчеризация от имени инструмента к владеющему серверу |
| Background reader | «Неблокирующий stdout» | Поток или задача, вычерпывающая stdout сервера в очередь |
| Sampling callback | «LLM как сервис» | Обработчик клиента для `sampling/createMessage` от сервера |
| `notifications/*_changed` | «Примитив изменился» | Сигнал клиенту заново обнаружить или перечитать данные |
| Reconnection policy | «Когда сервер умирает» | Семантика перезапуска при сбое транспорта |
| Stdio session | «Процесс = сессия» | Нет id сессии; жизненный цикл дочернего процесса и есть сессия |
