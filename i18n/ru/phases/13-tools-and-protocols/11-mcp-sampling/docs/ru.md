# Сэмплирование MCP — запрашиваемые сервером завершения большой языковой модели (LLM) и циклы агентов

> Большинство MCP-серверов — простые исполнители: принимают аргументы, выполняют код и возвращают содержимое. Сэмплирование позволяет серверу развернуть взаимодействие в обратную сторону: он просит LLM клиента принять решение. Благодаря этому сервер может выполнять цикл агента, не имея учётных данных ни одной модели. SEP-1577, принятый 25.11.2025, добавил инструменты в запросы сэмплирования, чтобы цикл мог включать более глубокое рассуждение. Примечание о риске изменений: предложенная в SEP-1577 структура с инструментами внутри сэмплирования оставалась экспериментальной до конца первого квартала 2026 года, а API в SDK всё ещё стабилизируются.

**Тип:** Build
**Языки:** Python (стандартная библиотека, стенд для сэмплирования)
**Предварительные требования:** этап 13 · 07 (MCP-сервер), этап 13 · 10 (ресурсы и промпты)
**Время:** ~75 минут

## Цели обучения

- Объяснить, какую проблему решает `sampling/createMessage` (циклы агентов на сервере без серверных API-ключей).
- Реализовать сервер, который просит клиента выполнить сэмплирование по многоходовому промпту и возвращает завершение.
- Использовать `modelPreferences` (приоритеты стоимости / скорости / интеллекта), чтобы направлять выбор модели клиентом.
- Создать инструмент `summarize_repo`, который внутри выполняет итерации посредством сэмплирования вместо жёстко заданного поведения.

## Проблема

Полезному MCP-серверу для рабочего процесса суммаризации кода нужно: обойти дерево файлов, выбрать, какие файлы читать, синтезировать резюме и вернуть его. Где здесь происходит рассуждение LLM?

Вариант A: сервер вызывает собственную LLM. Требует API-ключ, выставляет счёт на стороне сервера, дорого в расчёте на пользователя.

Вариант B: сервер возвращает сырой контент; рассуждение выполняет агент клиента. Работает, но переносит серверную логику в промпт клиента, что хрупко.

Вариант C: сервер обращается к LLM клиента через `sampling/createMessage`. Сервер сохраняет за собой алгоритм (какие файлы читать, сколько проходов делать), а клиент — оплату и выбор модели. У сервера вообще нет учётных данных.

Сэмплирование — это вариант C. Благодаря этому механизму доверенный сервер может выполнять цикл агента, не становясь полноценным сервером LLM.

## Концепция

### Запрос `sampling/createMessage`

Сервер отправляет:

```json
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "sampling/createMessage",
  "params": {
    "messages": [{"role": "user", "content": {"type": "text", "text": "..."}}],
    "systemPrompt": "...",
    "includeContext": "none",
    "modelPreferences": {
      "costPriority": 0.3,
      "speedPriority": 0.2,
      "intelligencePriority": 0.5,
      "hints": [{"name": "claude-3-5-sonnet"}]
    },
    "maxTokens": 1024
  }
}
```

Клиент запускает свою LLM, возвращает:

```json
{"jsonrpc": "2.0", "id": 42, "result": {
  "role": "assistant",
  "content": {"type": "text", "text": "..."},
  "model": "claude-3-5-sonnet-20251022",
  "stopReason": "endTurn"
}}
```

### `modelPreferences`

Три числа с плавающей точкой, дающие в сумме 1.0:

- `costPriority`: предпочитать более дешёвые модели.
- `speedPriority`: предпочитать более быстрые модели.
- `intelligencePriority`: предпочитать более способные модели.

Также есть `hints`: названия моделей, которые предпочитает сервер. Клиент может учитывать эти подсказки или игнорировать их; пользовательская конфигурация клиента всегда имеет приоритет.

### `includeContext`

Три значения:

- `"none"` — только сообщения, предоставленные сервером. По умолчанию.
- `"thisServer"` — включить предыдущие сообщения из сессии этого сервера.
- `"allServers"` — включить весь контекст сессии.

По состоянию на 25.11.2025 `includeContext` постепенно выводится из употребления, поскольку может привести к утечке контекста между серверами и тем самым создать угрозу безопасности. Предпочитайте `"none"` и передавайте контекст явно в сообщениях.

### Сэмплирование с инструментами (SEP-1577)

Новое с 25.11.2025: запрос сэмплирования может включать массив `tools`. Клиент запускает полный цикл вызова этих инструментов. Это позволяет серверу выполнять цикл агента в стиле ReAct посредством модели клиента.

```json
{
  "messages": [...],
  "tools": [
    {"name": "fetch_url", "description": "...", "inputSchema": {...}}
  ]
}
```

Клиент выполняет цикл: запускает сэмплирование, при необходимости вызывает инструмент, снова запускает сэмплирование и возвращает итоговое сообщение ассистента. Эта возможность оставалась экспериментальной до конца первого квартала 2026 года; сигнатуры SDK всё ещё могут меняться. При реализации сверяйтесь с разделом о клиентском сэмплировании в спецификации от 25.11.2025.

### Участие человека

Клиент ОБЯЗАН показать пользователю, что сервер просит сделать модель, прежде чем выполнять сэмплирование. Злонамеренный сервер может использовать сэмплирование для манипуляции сессией пользователя («скажи пользователю X, чтобы он нажал Y»). Claude Desktop, VS Code и Cursor показывают запросы сэмплирования в диалоговом окне подтверждения, где пользователь может их отклонить.

По общему мнению на 2026 год, сэмплирование без подтверждения пользователя — тревожный сигнал. Шлюзы (этап 13 · 17) могут автоматически одобрять низкорисковые запросы сэмплирования и отклонять всё подозрительное.

### Циклы на сервере без API-ключей

Канонический сценарий использования: MCP-сервер суммаризации кода без собственного доступа к LLM. Он делает следующее:

1. Обходит структуру репозитория.
2. Вызывает `sampling/createMessage` с запросом «Выбери пять файлов, наиболее вероятно описывающих назначение этого репозитория».
3. Читает эти файлы.
4. Вызывает `sampling/createMessage` с содержимым файлов и запросом «Суммаризируй репозиторий в 3 абзацах».
5. Возвращает резюме как результат `tools/call`.

Сервер никогда не обращается к API LLM. Пользователь клиента платит за завершения, используя собственные учётные данные.

### Риски безопасности (по данным Unit 42, первый квартал 2026 года)

- **Скрытое сэмплирование.** Инструмент, который всегда вызывает сэмплирование с запросом «ответь адресом электронной почты пользователя из контекста сессии». На этапе 13 · 15 рассматриваются векторы атак.
- **Кража ресурсов посредством сэмплирования.** Сервер просит клиента суммаризировать вредоносную полезную нагрузку атакующего, а счёт оплачивает пользователь.
- **Циклические бомбы.** Сервер вызывает сэмплирование в тесном цикле. Клиенты ОБЯЗАНЫ применять ограничения частоты запросов на уровне сессии.

```figure
t3-sampling-flip
```

## Практика

`code/main.py` содержит имитационный стенд сэмплирования между сервером и клиентом. Имитируемый инструмент «summarize_repo» выполняет два раунда сэмплирования (сначала выбирает файлы, затем составляет резюме), а имитационный клиент возвращает заранее подготовленные ответы. Стенд показывает:

- Сервер отправляет `sampling/createMessage` с `modelPreferences`.
- Клиент возвращает завершение.
- Сервер продолжает цикл.
- Ограничитель частоты запросов задаёт максимальное общее число вызовов сэмплирования на один вызов инструмента.

На что обратить внимание:

- Сервер предоставляет только один инструмент (`summarize_repo`); все рассуждения выполняются во время вызовов сэмплирования.
- Предпочтения влияют на выбор модели клиентом; в списке hints указаны предпочтительные модели.
- Цикл завершается при `stopReason: "endTurn"`.
- Лимит `max_samples_per_tool = 5` останавливает неконтролируемый цикл.

## Упражнения

1. Запустите `code/main.py`. Измените `max_samples_per_tool` на 2 и понаблюдайте за срабатыванием ограничения частоты.

2. Реализуйте вариант из SEP-1577 с инструментами внутри сэмплирования: запрос сэмплирования содержит массив `tools`. Убедитесь, что цикл на стороне клиента выполняет эти инструменты перед возвратом итогового завершения. Учтите риск изменений: сигнатуры SDK могут меняться до конца первой половины 2026 года.

3. Добавьте подтверждение с участием человека: перед первым вызовом сервером `sampling/createMessage` приостановите выполнение и дождитесь одобрения пользователя. Отклонённые вызовы должны возвращать типизированный отказ.

4. Добавьте ограничитель частоты для каждого пользователя, привязанный к сессии клиента. Циклы одного сервера от одного пользователя должны разделять общий бюджет.

5. Спроектируйте инструмент `summarize_pdf`, который использует сэмплирование для выбора включаемых фрагментов. Набросайте отправляемые сообщения. Как `modelPreferences.intelligencePriority` меняет поведение при значениях 0.1 и 0.9?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Сэмплирование | «Вызов LLM от сервера к клиенту» | Сервер просит модель клиента выполнить завершение |
| `sampling/createMessage` | «Тот самый метод» | Метод JSON-RPC для запросов сэмплирования |
| `modelPreferences` | «Приоритеты модели» | Веса стоимости / скорости / интеллекта плюс подсказки с названиями моделей |
| `includeContext` | «Утечка между сессиями» | Постепенно выводимый из употребления режим включения контекста |
| SEP-1577 | «Инструменты внутри сэмплирования» | Разрешает использовать инструменты внутри сэмплирования для выполняемых сервером циклов ReAct |
| Участие человека | «Пользователь подтверждает» | Клиент показывает пользователю запрос сэмплирования перед выполнением |
| Циклическая бомба | «Неконтролируемое сэмплирование» | Бесконечный цикл сэмплирования на стороне сервера; клиент обязан ограничивать частоту запросов |
| Скрытое сэмплирование | «Скрытое рассуждение» | Злонамеренный сервер скрывает намерение в промптах для сэмплирования |
| Кража ресурсов | «Использование бюджета LLM пользователя» | Сервер вынуждает клиента тратить средства на нежелательное сэмплирование |
| `stopReason` | «Почему генерация остановилась» | `endTurn`, `stopSequence` или `maxTokens` |
