# Ресурсы и промпты MCP — выставление контекста помимо инструментов

> Инструментам достаётся 90 процентов внимания к MCP. Два других серверных примитива решают другие задачи. Ресурсы (resources) выставляют данные для чтения; промпты (prompts) выставляют переиспользуемые шаблоны в виде слэш-команд. Многим серверам стоило бы использовать ресурсы вместо того, чтобы оборачивать чтение в инструменты, и промпты вместо того, чтобы зашивать рабочие процессы прямо в промпты клиента. Этот урок называет правило принятия решения и разбирает сообщения `resources/*` и `prompts/*`.

**Тип:** Build**Языки:** Python (stdlib, resource + prompt handler)**Предварительные требования:** Фаза 13 · 07 (MCP server)**Время:** ~45 минут
## Цели обучения

- Выбирать между выставлением возможности как инструмента, ресурса или промпта для конкретной предметной области.
- Реализовать `resources/list`, `resources/read`, `resources/subscribe` и обработку `notifications/resources/updated`.
- Реализовать `prompts/list` и `prompts/get` с шаблонами аргументов.
- Распознавать, когда хост показывает промпты как слэш-команды, а когда — как автоматически внедряемый контекст.

## Проблема

Наивный сервер MCP для приложения заметок выставляет всё как инструменты: `notes_read`, `notes_list`, `notes_search`. Это оборачивает каждый доступ к данным в вызов инструмента, управляемый моделью. Последствия:

- Модели приходится решать, вызывать ли `notes_read` для каждого запроса, которому мог бы пригодиться контекст.
- Контент, доступный только для чтения, нельзя подписать или транслировать в боковую панель хоста.
- UI клиента (панель прикрепления ресурсов Claude Desktop, пикер «Include file» в Cursor) не может показать эти данные.

Правильное разделение: выставлять данные как ресурс, выставлять мутирующие или вычисляемые действия как инструменты, выставлять переиспользуемые многошаговые рабочие процессы как промпты. У каждого примитива свой UX-аффорданс и свой паттерн доступа.

## Концепция

### Инструменты против ресурсов против промптов — правило принятия решения

| Возможность | Примитив |
|------------|-----------|
| Пользователь хочет искать, фильтровать или преобразовывать данные | инструмент |
| Пользователь хочет, чтобы хост включил эти данные как контекст | ресурс |
| Пользователь хочет шаблонный рабочий процесс, который можно повторно запускать | промпт |

Ориентир: если модели было бы полезно вызывать это при каждом связанном запросе — это инструмент. Если пользователю было бы полезно прикрепить это к разговору — это ресурс. Если единицей переиспользования пользователь хочет сделать целый многошаговый рабочий процесс — это промпт.

### Ресурсы

`resources/list` возвращает `{resources: [{uri, name, mimeType, description?}]}`. `resources/read` принимает `{uri}` и возвращает `{contents: [{uri, mimeType, text | blob}]}`.

URI могут быть любыми адресуемыми идентификаторами:

- `file:///Users/alice/notes/mcp.md`
- `postgres://my-db/query/SELECT ...`
- `notes://note-14` (пользовательская схема)
- `memory://session-2026-04-22/recent` (специфично для сервера)

`contents[]` поддерживает и текст, и бинарные данные. Для бинарных используется `blob` — строка в base64 — плюс `mimeType`.

### Подписки на ресурсы

Объявите `{resources: {subscribe: true}}` в возможностях. Клиент вызывает `resources/subscribe {uri}`. Сервер отправляет `notifications/resources/updated {uri}`, когда ресурс меняется. Клиент перечитывает его.

Сценарий использования: сервер заметок, чьи ресурсы — файлы на диске; наблюдатель за файлами запускает уведомления об обновлении; Claude Desktop заново подтягивает файл в контекст, когда его редактируют вне хоста.

### Шаблоны ресурсов (дополнение спецификации 2025-11-25)

`resourceTemplates` позволяют выставить параметризованный шаблон URI: `notes://{id}`, где `id` — цель автодополнения. Клиент может автодополнять id в пикере ресурсов.

### Промпты

`prompts/list` возвращает `{prompts: [{name, description, arguments?}]}`. `prompts/get` принимает `{name, arguments}` и возвращает `{description, messages: [{role, content}]}`.

Промпт — это шаблон, разворачивающийся в список сообщений, который хост передаёт своей модели. Например, промпт `code_review` принимает аргумент `file_path` и возвращает последовательность из трёх сообщений: системное сообщение, пользовательское сообщение с телом файла и стартовое сообщение ассистента с шаблоном рассуждения.

### Хосты и промпты

Claude Desktop, VS Code и Cursor показывают промпты как слэш-команды в UI чата. Пользователь вводит `/code_review` и выбирает аргументы из формы. Промпт сервера — это контракт между «пользовательским сокращением» и «полным промптом, отправленным модели».

Не каждый клиент пока поддерживает промпты — проверяйте согласование возможностей. Если сервер объявил поддержку промптов, а клиент её не поддерживает, слэш-команды просто не появятся.

### Уведомление «список изменился»

И ресурсы, и промпты выдают `notifications/list_changed`, когда набор меняется. Сервер заметок, который только что импортировал 20 новых заметок, выдаёт `notifications/resources/list_changed`; клиент заново вызывает `resources/list`, чтобы подхватить добавления.

### Соглашения о типах контента

Для текста: `mimeType: "text/plain"`, `text/markdown`, `application/json`.
Для бинарных данных: `image/png`, `application/pdf`, плюс поле `blob`.
Для MCP Apps (Урок 14): `text/html;profile=mcp-app` в URI `ui://`.

### Динамические ресурсы

URI ресурса не обязан соответствовать статичному файлу. `notes://recent` может возвращать пять последних заметок при каждом чтении. `db://query/users/active` может выполнять параметризованный запрос. Сервер волен вычислять контент динамически.

Правило: если клиент может кешировать по URI, URI должен быть стабильным. Если вычисление одноразовое, URI должен включать метку времени или nonce, чтобы кеш клиента не устаревал незаметно.

### Подписки против опроса

Клиенты с поддержкой подписок получают серверный push через `notifications/resources/updated`. Клиенты без поддержки подписок или хосты, не поддерживающие её, опрашивают, перечитывая данные. Оба варианта соответствуют спецификации. Объявление возможностей сервера сообщает клиенту, что именно он поддерживает.

Цена подписок: состояние на сервере для каждой сессии (кто на что подписан). Держите множество подписчиков ограниченным; отключившиеся клиенты должны отваливаться по тайм-ауту.

### Промпты против системных промптов

Промпты в MCP — это не системные промпты. Системный промпт хоста (его собственные операционные инструкции) и промпты MCP (шаблоны от сервера, вызываемые пользователем) существуют бок о бок. Корректно работающий клиент никогда не позволяет промпту сервера переопределить свой собственный системный промпт; он их накладывает слоями.

## Практика

`code/main.py` расширяет сервер заметок из Урока 07:

- Ресурсы для каждой заметки (`notes://note-1` и т. д.) с поддержкой `resources/subscribe`.
- Промпт `review_note`, отрисовывающийся в шаблон из трёх сообщений.
- Симуляция наблюдателя за файлами, выдающая `notifications/resources/updated` при изменении заметки.
- Динамический ресурс `notes://recent`, всегда возвращающий пять последних заметок.

Запустите демо, чтобы увидеть весь поток целиком.

## Поставка

Этот урок производит `outputs/skill-primitive-splitter.md`. По заданному предполагаемому серверу MCP навык классифицирует каждую возможность как инструмент / ресурс / промпт с обоснованием.

## Упражнения

1. Запустите `code/main.py`. Понаблюдайте за начальным списком ресурсов, затем спровоцируйте редактирование заметки и убедитесь, что событие `notifications/resources/updated` срабатывает.

2. Добавьте эмиттер `resources/list_changed`: когда создаётся новая заметка, отправляйте уведомление, чтобы клиенты заново её обнаружили.

3. Спроектируйте три промпта для сервера MCP для GitHub: `summarize_pr`, `triage_issue`, `release_notes`. У каждого — схема аргументов. Тело промпта должно быть готово к запуску без доработок.

4. Возьмите существующий инструмент из сервера Урока 07 и классифицируйте, должен ли он остаться инструментом или быть разделён на пару ресурс + инструмент. Обоснуйте одним предложением.

5. Прочитайте разделы `server/resources` и `server/prompts` спецификации. Найдите одно поле в `resources/read`, которое редко заполняется, но поддерживается спецификацией. Подсказка: посмотрите на `_meta` в контенте ресурса.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Resource | «Выставленные данные» | Контент, адресуемый по URI, который хост может прочитать |
| Resource URI | «Указатель на данные» | Идентификатор со схемой-префиксом (`file://`, `notes://` и т. д.) |
| `resources/subscribe` | «Следить за изменениями» | Опциональная для клиента подписка на серверные push-обновления для конкретного URI |
| `notifications/resources/updated` | «Ресурс изменился» | Сигнал клиенту, что у подписанного ресурса новое содержимое |
| Resource template | «Параметризованный URI» | Шаблон URI с подсказками автодополнения для пикера хоста |
| Prompt | «Шаблон слэш-команды» | Именованный шаблон из нескольких сообщений со слотами для аргументов |
| Prompt arguments | «Входы шаблона» | Типизированные параметры, которые хост собирает перед отрисовкой |
| `prompts/get` | «Отрисовать шаблон» | Сервер возвращает заполненный список сообщений |
| Content block | «Типизированный кусок» | `{type: text \| image \| resource \| ui_resource}` |
| Slash-command UX | «Пользовательское сокращение» | Хост показывает промпты как команды, начинающиеся с `/` |
