# Итоговый проект — построение полной экосистемы инструментов

> Фаза 13 научила каждому отдельному элементу. Этот итоговый проект связывает их в одну систему, приближенную к продакшену: MCP-сервер с инструментами + ресурсами + промптами + задачами + UI, OAuth 2.1 на границе, шлюз RBAC, мультисерверный клиент, вызов суб-агента A2A, трассировка OTel в коллектор, обнаружение отравления инструментов в CI и пакет AGENTS.md + SKILL.md. К концу вы сможете обосновать каждое архитектурное решение.

**Тип:** Build**Языки:** Python (stdlib, end-to-end ecosystem harness)**Предварительные требования:** Фаза 13 · 01 through 21**Время:** ~120 минут
## Цели обучения

- Скомпоновать MCP-сервер, предоставляющий инструменты, ресурсы, промпты и задачу с приложением `ui://`.
- Разместить перед сервером шлюз OAuth 2.1, применяющий RBAC и закреплённые хеши.
- Написать мультисерверный клиент, трассирующий сквозь атрибуты OTel GenAI от начала до конца.
- Делегировать часть нагрузки суб-агенту A2A; убедиться, что непрозрачность сохраняется.
- Упаковать весь стек с AGENTS.md + SKILL.md, чтобы другие агенты могли им управлять.

## Проблема

Поставьте систему «исследование и отчёт»:

- Пользователь спрашивает: «суммируй три наиболее цитируемые статьи arXiv 2026 года об агентных протоколах».
- Система: ищет в arXiv через MCP; делегирует суммаризацию статей специализированному агенту-писателю через A2A; агрегирует результаты; рендерит интерактивный отчёт как ресурс MCP Apps `ui://`; логирует каждый шаг в OTel.

Все примитивы из Phase 13 здесь задействованы. Это не игрушка — production-системы research-ассистентов, выпущенные в 2026 году Anthropic (продукт Claude Research), OpenAI (GPTs с Apps SDK) и третьими сторонами, имеют именно такую форму.

## Концепция

### Архитектура

```
[user] -> [client] -> [gateway (OAuth 2.1 + RBAC)] -> [research MCP server]
                                                      |
                                                      +- MCP tool: arxiv_search (pure)
                                                      +- MCP resource: notes://recent
                                                      +- MCP prompt: /research_topic
                                                      +- MCP task: generate_report (long)
                                                      +- MCP Apps UI: ui://report/current
                                                      +- A2A call: writer-agent (tasks/send)
                                                      |
                                                      +- OTel GenAI spans
```

### Иерархия трассировки

```
agent.invoke_agent
 ├── llm.chat (kick off)
 ├── mcp.call -> tools/call arxiv_search
 ├── mcp.call -> resources/read notes://recent
 ├── mcp.call -> prompts/get research_topic
 ├── a2a.tasks/send -> writer-agent
 │    └── task transitions (opaque internals)
 ├── mcp.call -> tools/call generate_report (task-augmented)
 │    └── tasks/status polling
 │    └── tasks/result (completed, returns ui:// resource)
 └── llm.chat (final synthesis)
```

Один trace id. У каждого спана правильные атрибуты `gen_ai.*`.

### Модель безопасности

- OAuth 2.1 + PKCE с индикатором ресурса, закрепляющим аудиторию за шлюзом.
- Шлюз хранит вышестоящие учётные данные; пользователь их никогда не видит.
- RBAC: у `alice` есть `research:read`, `research:write`, она может вызывать все инструменты. У `bob` есть `research:read`, он не может вызывать `generate_report`.
- Манифест с закреплёнными описаниями: любой сервер, у которого изменились хеши инструментов, отбрасывается.
- Аудит «правила двух»: ни один инструмент не сочетает недоверенный ввод, чувствительные данные и значимое действие.

### Рендеринг

Итоговая задача `generate_report` возвращает блоки содержимого плюс ресурс `ui://report/current`. Хост клиента (Claude Desktop и т. д.) рендерит интерактивный дашборд в песочнице iframe. Дашборд содержит отсортированный список статей, число цитирований и кнопку, вызывающую `host.callTool('summarize_paper', {arxiv_id})` для любой статьи, на которую нажимает пользователь.

Всё это поставляется как:

```
research-system/
```

## Практика

`code/main.py` сшивает паттерны предыдущих уроков в одно запускаемое демо. Всё на stdlib, всё в одном процессе, чтобы вы могли прочитать это от начала до конца. Оно выполняет полный поток для сценария «исследование и отчёт»: рукопожатие со шлюзом, симулированный OAuth 2.1, объединённый tools/list, generate_report как задача, вызов A2A к писателю, возвращённый ресурс ui://, сгенерированные спаны OTel.

На что смотреть:

- Один trace id на всех этапах.
- Политика шлюза блокирует второго пользователя, пытающегося писать.
- Жизненный цикл задачи проходит working → completed и возвращает как текст, так и содержимое ui://.
- Внутреннее состояние вызова A2A непрозрачно для оркестратора.
- AGENTS.md и SKILL.md — единственные файлы, нужные другому агенту, чтобы воспроизвести рабочий процесс.

## Поставка

Этот урок производит `outputs/skill-ecosystem-blueprint.md`. По заданной потребности продукта (исследование, суммаризация, автоматизация) навык производит полную архитектуру: какие примитивы MCP, какие элементы управления шлюза, какие вызовы A2A, какая телеметрия, какая упаковка.

## Упражнения

1. Запустите `code/main.py`. Отметьте единый trace id и то, как вкладываются спаны. Посчитайте, сколько примитивов из Phase 13 затрагивает демо.

2. Расширьте демо: добавьте второй бэкенд MCP-сервер (например, `bibliography`) и убедитесь, что шлюз объединяет его инструменты в то же пространство имён.

3. Замените фиктивного агента-писателя A2A настоящим, работающим в подпроцессе. Используйте тестовый стенд из урока 19.

4. Добавьте шаг редактирования PII в шлюзе маршрутизации между оркестратором и LLM. Убедитесь, что email-адреса в запросе пользователя вычищаются.

5. Напишите AGENTS.md для коллеги, который будет поддерживать эту систему. Его должно быть можно прочитать менее чем за пять минут, и он должен дать всё необходимое, чтобы управлять итоговым проектом в Cursor или Codex.
