# Безопасность MCP II — OAuth 2.1, индикаторы ресурсов, пошаговые области доступа

> Удалённым MCP-серверам нужна не только аутентификация, но и авторизация. Спецификация от 2025-11-25 опирается на OAuth 2.1 + PKCE + индикаторы ресурсов (RFC 8707) + метаданные защищённого ресурса (RFC 9728). SEP-835 добавляет пошаговое согласие на расширение области доступа (scope) со ступенчатой авторизацией по ответу 403 с заголовком WWW-Authenticate. В этом уроке ступенчатый поток реализован как конечный автомат, чтобы был виден каждый шаг.

**Тип:** Build**Языки:** Python (stdlib, симулятор конечного автомата OAuth)**Предварительные требования:** Фаза 13 · 09 (транспорты), Фаза 13 · 15 (безопасность I)**Время:** ~75 минут
## Цели обучения

- Различать обязанности сервера ресурсов и сервера авторизации.
- Пройти защищённый PKCE поток кода авторизации OAuth 2.1.
- Использовать параметр `resource` (RFC 8707) и метаданные защищённого ресурса (RFC 9728) для предотвращения атак типа confused deputy.
- Реализовать пошаговую авторизацию: сервер отвечает 403 с заголовком WWW-Authenticate, запрашивающим более широкую область доступа; клиент повторно запрашивает согласие пользователя и повторяет запрос.

## Проблема

Ранний MCP (до 2025 года) поставлял удалённые серверы с самодельными API-ключами или вовсе без авторизации. Спецификация от 2025-11-25 закрывает этот пробел полным профилем OAuth 2.1.

Три реальные потребности:

- **Обычные удалённые серверы.** Пользователь устанавливает удалённый MCP-сервер, который обращается к его Notion / GitHub / Gmail. OAuth 2.1 с PKCE — подходящая форма.
- **Расширение области доступа.** Серверу заметок, получившему `notes:read`, позже может понадобиться `notes:write` для конкретного действия. Вместо повторения всего потока пошаговое согласие (SEP-835) запрашивает дополнительную область доступа.
- **Предотвращение confused deputy.** Клиент держит токен, чья аудитория ограничена сервером A. Сервер A вредоносен и пытается предъявить токен серверу B. Индикаторы ресурсов (RFC 8707) закрепляют токен за его предполагаемой аудиторией.

OAuth 2.1 сам по себе не нов. Новым является профиль MCP: конкретные обязательные потоки (только код авторизации + PKCE; ни implicit, ни client credentials по умолчанию), обязательные индикаторы ресурсов при каждом запросе токена и публикуемые метаданные защищённого ресурса, чтобы клиенты знали, куда обращаться.

## Концепция

### Роли

- **Клиент.** MCP-клиент (Claude Desktop, Cursor и т. д.).
- **Сервер ресурсов.** MCP-сервер (заметки, GitHub, Postgres — что угодно).
- **Сервер авторизации.** Выдаёт токены. Может быть тем же сервисом, что и сервер ресурсов, либо отдельным поставщиком удостоверений (Auth0, Keycloak, Cognito).

В профиле MCP сервер ресурсов и сервер авторизации МОГУТ быть одним и тем же хостом, но ДОЛЖНЫ различаться по URL.

### Код авторизации + PKCE

Поток:

1. Клиент генерирует `code_verifier` (случайное значение) и `code_challenge` (SHA256).
2. Клиент перенаправляет пользователя на `/authorize?response_type=code&client_id=...&redirect_uri=...&scope=notes:read&code_challenge=...&resource=https://notes.example.com`.
3. Пользователь даёт согласие. Сервер авторизации перенаправляет на `redirect_uri?code=...`.
4. Клиент отправляет POST на `/token?grant_type=authorization_code&code=...&code_verifier=...&resource=...`.
5. Сервер авторизации сверяет хеш верификатора с сохранённым challenge и выдаёт токен доступа.
6. Клиент использует токен: `Authorization: Bearer ...` в каждом запросе к серверу ресурсов.

PKCE предотвращает перехват кода авторизации. Индикаторы ресурсов не дают токену быть действительным где-либо ещё.

### Метаданные защищённого ресурса (RFC 9728)

Сервер ресурсов публикует документ `.well-known/oauth-protected-resource`:

```json
{
  "resource": "https://notes.example.com",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:read", "notes:write", "notes:delete"]
}
```

Клиент обнаруживает сервер авторизации через сервер ресурсов. Это упрощает настройку — клиенту нужен только URL ресурса.

### Индикаторы ресурсов (RFC 8707)

Параметр `resource` в запросе токена закрепляет предполагаемую аудиторию токена. Выданный токен содержит `aud: "https://notes.example.com"`. Другой MCP-сервер, получив такой токен, проверяет `aud` и отклоняет его.

### Модель областей доступа

Области доступа (scope) — строки, разделённые пробелами. Распространённые соглашения MCP:

- `notes:read`, `notes:write`, `notes:delete`
- `admin:*` для административных возможностей (использовать экономно)
- `profile:read` для идентификации

Выбор области доступа должен следовать принципу наименьших привилегий: запрашивайте то, что нужно сейчас, и расширяйте по мере необходимости.

### Пошаговая авторизация (SEP-835)

Пользователь предоставляет `notes:read`. Позже он просит агента удалить заметку. Сервер отвечает:

```
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
    scope="notes:delete", resource="https://notes.example.com"
```

Клиент видит ошибку insufficient_scope, показывает пользователю диалог согласия на дополнительную область доступа, выполняет мини-поток OAuth для неё и повторяет запрос с новым токеном.

### Проверка аудитории токена

При каждом запросе: сервер проверяет `token.aud == self.resource_url`. Несовпадение = 401. Это останавливает повторное использование токена между серверами.

### Короткоживущие токены и ротация

Токены доступа ДОЛЖНЫ быть короткоживущими (по умолчанию 1 час). Refresh-токены ротируются при каждом обновлении. Клиент обрабатывает тихое обновление в фоне.

### Отсутствие передачи токена дальше

Серверы сэмплирования (Phase 13 · 11) НЕ ДОЛЖНЫ передавать токен клиента другим сервисам. Запрос сэмплирования — это граница.

### Предотвращение confused deputy

Токен привязан к `aud`. Клиент привязан к `client_id`. Каждый запрос проверяется по обоим значениям. Спецификация явно запрещает старый паттерн «передачи токена дальше», распространённый в экосистемах удалённых инструментов до появления MCP.

### Обнаружение client ID

Каждый MCP-клиент публикует свои метаданные по фиксированному URL. Серверы авторизации могут получить документ метаданных клиента, чтобы узнать redirect URI и контактную информацию. Это устраняет необходимость ручной регистрации клиента.

### Шлюзы и OAuth

Phase 13 · 17 показывает, как корпоративный шлюз обрабатывает OAuth: шлюз хранит учётные данные для вышестоящих серверов, токены клиенту выдаёт сам шлюз, а вышестоящие токены никогда не покидают шлюз. Это переворачивает модель доверия: пользователи аутентифицируются в шлюзе один раз, а шлюз обрабатывает авторизацию на N серверах.


## Практика

`code/main.py` симулирует полный ступенчатый поток OAuth 2.1 как конечный автомат. Он реализует:

- Генерацию code-verifier / challenge для PKCE.
- Поток кода авторизации с индикатором ресурса.
- Конечную точку метаданных защищённого ресурса.
- Проверку токена с проверкой аудитории.
- Пошаговое расширение при `insufficient_scope`.

В этом уроке нет HTTP-сервера; конечный автомат выполняется в памяти, чтобы можно было проследить каждый шаг. Урок Phase 13 · 17 про шлюз подключает это к реальному транспорту.

## Упражнения

1. Запустите `code/main.py`. Проследите поток пошагового расширения с двумя областями доступа. Отметьте, какие шаги повторяются при расширении.

2. Добавьте ротацию refresh-токенов: каждое обновление выдаёт новый refresh-токен и делает недействительным старый. Смоделируйте использование украденного refresh-токена после ротации и убедитесь, что он не срабатывает.

3. Реализуйте конечную точку метаданных защищённого ресурса как настоящий HTTP-ответ с помощью stdlib http.server. Отразите конечную точку /mcp из урока 09.

4. Спроектируйте иерархию областей доступа для MCP-сервера GitHub: чтение репозитория, запись PR, одобрение PR, слияние PR, администрирование. Используйте пошаговое расширение между каждым уровнем.

5. Прочитайте RFC 8707 и RFC 9728. Найдите одно поле в 9728, которое MCP использует иначе, чем в примере из RFC. (Подсказка: оно касается `scopes_supported`.)

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| OAuth 2.1 | «Современный OAuth» | Консолидированный RFC, обязывающий использовать PKCE и запрещающий implicit-поток |
| PKCE | «Доказательство владения» | Code verifier + challenge, предотвращающие перехват кода авторизации |
| Resource indicator | «Аудитория токена» | Параметр `resource` из RFC 8707, закрепляющий токен за одним сервером |
| Protected-resource metadata | «Документ обнаружения» | `.well-known/oauth-protected-resource` из RFC 9728 |
| Step-up authorization | «Пошаговое согласие» | Поток SEP-835 для добавления областей доступа по требованию |
| `insufficient_scope` | «403 с WWW-Authenticate» | Сигнал сервера о необходимости повторного согласия на более широкую область доступа |
| Confused deputy | «Повторное использование токена между сервисами» | Атака, при которой доверенный держатель токена неуместно пересылает его дальше |
| Short-lived token | «Время жизни токена доступа» | Bearer-токен с коротким сроком действия; refresh-токен его обновляет |
| Scope hierarchy | «Стек наименьших привилегий» | Градуированный набор областей доступа с пошаговым расширением между уровнями |
| Client ID metadata | «Документ обнаружения клиента» | URL, по которому клиент публикует собственные метаданные OAuth |
