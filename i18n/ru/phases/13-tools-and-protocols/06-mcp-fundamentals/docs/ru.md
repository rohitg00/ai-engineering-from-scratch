# Основы MCP — примитивы, жизненный цикл, базовый JSON-RPC

> До MCP каждая интеграция делалась разово. Model Context Protocol — протокол, впервые выпущенный Anthropic в ноябре 2024 года и теперь курируемый Agentic AI Foundation при Linux Foundation, — стандартизирует обнаружение и вызов, так что любой клиент может общаться с любым сервером. Спецификация 2025-11-25 называет шесть примитивов (три серверных, три клиентских), трёхфазный жизненный цикл и формат передачи данных JSON-RPC 2.0. Освойте их — и остальная часть главы про MCP в этой фазе станет просто чтением.

**Тип:** Learn
**Языки:** Python (стандартная библиотека, парсер JSON-RPC)
**Предварительные требования:** Фаза 13 · уроки 01–05 (интерфейс инструментов и вызов функций)
**Время:** ~45 минут

## Цели обучения

- Назвать все шесть примитивов MCP (инструменты, ресурсы, промпты на сервере; корни (roots), сэмплирование (sampling), запрос данных (elicitation) на клиенте) и привести по одному сценарию использования для каждого.
- Пройти по трёхфазному жизненному циклу (инициализация, работа, завершение) и указать, кто отправляет какое сообщение на каждой фазе.
- Разобрать и сформировать конверты запроса, ответа и уведомления JSON-RPC 2.0.
- Объяснить, что такое согласование возможностей (capability negotiation) при `initialize` и что ломается без него.

## Проблема

До MCP у каждого агента, использующего инструменты, был свой протокол. У Cursor была MCP-подобная, но несовместимая система инструментов. Claude Desktop поставлялся с другой. У расширения Copilot в VS Code была третья. Команда, построившая инструмент «запрос к Postgres», писала его трижды — по разу под API каждого хоста. Чтобы переиспользовать код, приходилось его копировать.

Результат — кембрийский взрыв разовых интеграций и потолок для скорости развития экосистемы.

MCP решает эту проблему, стандартизируя формат передачи данных. Один сервер MCP работает в любом клиенте MCP: Claude Desktop, ChatGPT, Cursor, VS Code, Gemini, Goose, Zed, Windsurf — 300+ клиентов к апрелю 2026 года. 110 млн загрузок SDK в месяц. 10,000+ публичных серверов. Linux Foundation взял на себя кураторство в декабре 2025 года в рамках нового Agentic AI Foundation.

Ревизия спецификации, используемая в этой фазе, — **2025-11-25**. Она добавляет асинхронные задачи (Tasks, SEP-1686), запрос данных в режиме URL (SEP-1036), сэмплирование с инструментами (SEP-1577), поэтапное согласие на расширение области доступа (SEP-835) и семантику индикатора ресурса для OAuth 2.1. Уроки 09–16 фазы 13 разбирают эти расширения. Этот урок останавливается на базовой части.

## Концепция

### Три серверных примитива

1. **Инструменты (tools).** Вызываемые действия. Тот же цикл из четырёх шагов, что и в уроке 01 фазы 13.
2. **Ресурсы (resources).** Выставленные данные. Доступный только для чтения контент, адресуемый по URI: `file:///path`, `db://query/...`, произвольные пользовательские схемы.
3. **Промпты (prompts).** Переиспользуемые шаблоны. Слэш-команды в UI хоста; сервер поставляет шаблон, клиент заполняет аргументы.

### Три клиентских примитива

4. **Корни (roots).** Набор URI, к которым серверу разрешено обращаться. Клиент объявляет их; сервер соблюдает эти ограничения.
5. **Сэмплирование (sampling).** Сервер просит модель клиента выполнить завершение (completion). Позволяет размещать циклы агента на сервере без API-ключей на стороне сервера.
6. **Запрос данных (elicitation).** Сервер запрашивает у пользователя клиента структурированный ввод прямо во время работы. Для этого используются формы или URL (SEP-1036).

Каждая возможность в MCP относится ровно к одному из этих шести примитивов. Уроки 10–14 фазы 13 подробно разбирают каждый из них.

### Формат передачи данных: JSON-RPC 2.0

Каждое сообщение — это JSON-объект со следующими полями:

- Запросы: `{jsonrpc: "2.0", id, method, params}`.
- Ответы: `{jsonrpc: "2.0", id, result | error}`.
- Уведомления: `{jsonrpc: "2.0", method, params}` — без `id`, ответ не ожидается.

В базовой спецификации ~15 методов, сгруппированных по примитивам. Важнейшие из них:

- `initialize` / `initialized` (рукопожатие)
- `tools/list`, `tools/call`
- `resources/list`, `resources/read`, `resources/subscribe`
- `prompts/list`, `prompts/get`
- `sampling/createMessage` (от сервера к клиенту)
- `notifications/tools/list_changed`, `notifications/resources/updated`, `notifications/progress`

### Трёхфазный жизненный цикл

**Фаза 1: инициализация.**

Клиент отправляет `initialize` со своими `capabilities` и `clientInfo`. Сервер отвечает своими `capabilities`, `serverInfo` и версией спецификации, которую он поддерживает. Клиент отправляет `notifications/initialized`, когда обработал ответ. С этого момента любая сторона может отправлять запросы в рамках согласованных возможностей.

**Фаза 2: работа.**

Обмен данными двунаправленный. Клиент вызывает `tools/list` для обнаружения, затем `tools/call` для вызова. Сервер может отправить `sampling/createMessage`, если объявил эту возможность. Сервер может отправить `notifications/tools/list_changed`, когда его набор инструментов меняется. Клиент может отправить `notifications/roots/list_changed`, когда пользователь меняет область корней.

**Фаза 3: завершение работы.**

Любая из сторон закрывает транспорт. У MCP нет структурированного метода завершения; транспорт (stdio или Streamable HTTP, урок 09 фазы 13) передаёт сигнал о завершении соединения.

### Согласование возможностей

`capabilities` в рукопожатии `initialize` — это контракт. Пример от сервера:

```json
{
  "tools": {"listChanged": true},
  "resources": {"subscribe": true, "listChanged": true},
  "prompts": {"listChanged": true}
}
```

Сервер объявляет, что может выдавать уведомления `tools/list_changed` и поддерживает `resources/subscribe`. Клиент соглашается, объявляя свои:

```json
{
  "roots": {"listChanged": true},
  "sampling": {},
  "elicitation": {}
}
```

Если клиент не объявил `sampling`, сервер не должен вызывать `sampling/createMessage`. Симметрично: если сервер не объявил `resources.subscribe`, клиент не должен пытаться подписаться.

Именно это предотвращает расхождение экосистемы. Клиент, не поддерживающий сэмплирование, всё равно остаётся корректным клиентом MCP; сервер, не вызывающий `sampling`, всё равно остаётся корректным сервером MCP. Они просто не используют эту возможность вместе.

### Структурированный контент и формы ошибок

`tools/call` возвращает массив `content` из типизированных блоков: `text`, `image`, `resource`. Урок 14 фазы 13 добавляет к этому списку MCP Apps (интерактивный интерфейс `ui://`).

Ошибки используют коды ошибок JSON-RPC. Дополнения, определённые спецификацией: `-32002` «Ресурс не найден», `-32603` «Внутренняя ошибка», а также специфичные для MCP данные ошибки в `error.data`.

### Возможности клиента и детали вызова инструмента

Частая путаница: `capabilities.tools` — это про то, поддерживает ли клиент уведомления об изменении списка инструментов. А вот будет ли клиент вызывать конкретные инструменты — это решение времени выполнения, продиктованное его моделью, а не флагом возможностей. Флаг возможностей — это контракт на уровне спецификации. Выбор модели ортогонален ему.

### Почему JSON-RPC, а не REST?

JSON-RPC 2.0 (2010) — лёгкий двунаправленный протокол. В REST взаимодействие инициирует клиент. MCP нужны были сообщения, инициируемые сервером (сэмплирование и уведомления), поэтому симметричная форма «запрос — ответ» JSON-RPC подошла естественным образом. JSON-RPC также удобно работает поверх stdio и WebSocket/Streamable HTTP, не изобретая заново форму запроса HTTP.

```figure
mcp-tool-call
```

## Практика

`code/main.py` содержит минимальный парсер и эмиттер JSON-RPC 2.0, а затем вручную проходит последовательность `initialize` → `tools/list` → `tools/call` → `shutdown`, печатая каждое сообщение. Реального транспорта нет — только формы сообщений. Сравните с спецификацией из раздела «Дополнительное чтение», чтобы проверить каждый конверт.

На что смотреть:

- `initialize` объявляет возможности в обе стороны; в ответе есть `serverInfo` и `protocolVersion: "2025-11-25"`.
- `tools/list` возвращает массив `tools`; в каждой записи есть `name`, `description`, `inputSchema`.
- `tools/call` использует `params.name` и `params.arguments`.
- Ответный `content` — это массив блоков `{type, text}`.

## Упражнения

1. Запустите `code/main.py`. Найдите строку, где происходит согласование возможностей, и опишите, что изменится, если сервер не объявит `tools.listChanged`.

2. Расширьте парсер для обработки `notifications/progress`. Форма сообщения: `{method: "notifications/progress", params: {progressToken, progress, total}}`. Отправьте его во время выполнения долгого `tools/call` и подтвердите, что обработчик клиента отобразил бы индикатор прогресса.

3. Прочитайте спецификацию MCP 2025-11-25 от начала до конца — весь документ занимает около 80 страниц. Определите тот единственный флаг возможностей, который большинству серверов НЕ нужен. Подсказка: он связан с подпиской на ресурсы.

4. Набросайте на бумаге, к какому примитиву относилась бы гипотетическая функция «cron-задачи». (Подсказка: сервер хочет, чтобы клиент вызывал её по расписанию. Ни один из шести примитивов сегодня не подходит.) В дорожной карте MCP на 2026 год есть черновой SEP для этого.

5. Разберите один лог сессии открытого сервера MCP с GitHub. Посчитайте количество сообщений-запросов, ответов и уведомлений. Вычислите, какая доля трафика приходится на жизненный цикл, а какая — на работу.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| MCP | «Model Context Protocol» | Открытый протокол для обнаружения и вызова инструментов моделью |
| Серверный примитив | «То, что предоставляет сервер» | инструменты (действия), ресурсы (данные), промпты (шаблоны) |
| Клиентский примитив | «То, что клиент разрешает использовать серверам» | корни (область доступа), сэмплирование (обратные вызовы LLM), запрос данных (пользовательский ввод) |
| JSON-RPC 2.0 | «Формат передачи данных» | Симметричные конверты запроса/ответа/уведомления |
| Рукопожатие `initialize` | «Согласование возможностей» | Первая пара сообщений; сервер и клиент объявляют поддерживаемые функции |
| `tools/list` | «Обнаружение» | Клиент запрашивает у сервера его текущий набор инструментов |
| `tools/call` | «Вызов» | Клиент просит сервер выполнить инструмент с аргументами |
| `notifications/*_changed` | «События мутации» | Сервер сообщает клиенту, что его список примитивов изменился |
| Блок контента | «Типизированный результат» | `{type: "text" \| "image" \| "resource" \| "ui_resource"}` в результате вызова инструмента |
| SEP | «Предложение по развитию спецификации» | Именованное черновое предложение (например, SEP-1686 для асинхронных задач) |
