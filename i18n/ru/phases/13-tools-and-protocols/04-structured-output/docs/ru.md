# Структурированный вывод — JSON Schema, Pydantic, Zod, ограниченное декодирование

> «Вежливо попросить модель вернуть JSON» не срабатывает в 5–15 процентах случаев даже на топовых моделях. Структурированный вывод закрывает этот разрыв ограниченным декодированием: модели буквально не дают выдать токен, который нарушил бы схему. Строгий режим OpenAI, типизированное схемой использование инструментов у Anthropic, `responseSchema` у Gemini, `output_type` у Pydantic AI и `.parse` у Zod — это пять поверхностных форм одной и той же идеи. Этот урок строит валидатор схемы и контракт строгого режима, которым учащиеся будут пользоваться в каждом продакшен-конвейере извлечения данных.

**Тип:** Build
**Языки:** Python (stdlib, подмножество JSON Schema 2020-12)
**Предварительные требования:** Фаза 13 · 02 (углублённый разбор вызова функций)
**Время:** ~75 минут

## Цели обучения

- Писать JSON Schema 2020-12 для цели извлечения, используя нужные ограничения (enum, min/max, required, pattern).
- Объяснять, почему строгий режим и ограниченное декодирование дают иные гарантии, чем «валидация после генерации».
- Различать три режима неуспешного исхода: ошибка разбора, нарушение схемы, отказ модели.
- Поставлять конвейер извлечения с типизированной починкой и типизированной обработкой отказа.

## Проблема

Агенту, читающему письмо с заказом на покупку, нужно превратить свободный текст в `{customer, line_items, total_usd}`. Три подхода.

**Подход первый: попросить JSON промптом.** «Ответь в JSON с полями customer, line_items, total_usd». Работает в 85–95 процентах случаев на топовых моделях. Ломается шестью способами: пропущенная скобка, лишняя запятая, неверные типы, галлюцинированные поля, обрезка по лимиту токенов, просочившаяся проза вроде «Вот ваш JSON:».

**Подход второй: валидация после генерации.** Генерировать свободно, разобрать, провалидировать по схеме, повторить при неудаче. Надёжно, но дорого — вы платите за каждый повтор, а баги обрезки стоят один лишний ход за каждый случай.

**Подход третий: ограниченное декодирование.** Провайдер обеспечивает соответствие схеме во время декодирования. Недопустимые токены маскируются из распределения сэмплирования. Вывод гарантированно разбирается и гарантированно проходит валидацию. Остаётся один режим неуспешного исхода: отказ модели (модель решает, что вход не подходит под схему).

Каждый топовый провайдер 2026 года поставляет некоторую форму подхода три.

- **OpenAI.** `response_format: {type: "json_schema", strict: true}` плюс `refusal` в ответе, если модель отказывается.
- **Anthropic.** Обеспечение схемы на входных данных `tool_use`; значения `stop_reason: "refusal"` нет, но сигналом служит `end_turn` без вызова инструмента.
- **Gemini.** `responseSchema` на уровне запроса; в 2026 году Gemini поставляет ограничения грамматики на уровне токенов для избранных типов.
- **Pydantic AI.** `output_type=InvoiceModel` выдаёт структурированный `RunResult`, типизированный под `InvoiceModel`.
- **Zod (TypeScript).** Парсер времени выполнения, валидирующий вывод провайдера по схеме Zod; сочетается с `beta.chat.completions.parse` у OpenAI.

Общая нить: объявить схему один раз, обеспечивать её соблюдение сквозным образом.

## Концепция

### JSON Schema 2020-12 — общий язык

Каждый провайдер принимает JSON Schema 2020-12. Конструкции, которые вы используете чаще всего:

- `type`: одно из `object`, `array`, `string`, `number`, `integer`, `boolean`, `null`.
- `properties`: отображение имени поля на подсхему.
- `required`: список имён полей, которые обязаны присутствовать.
- `enum`: закрытое множество допустимых значений.
- `minimum` / `maximum` (числа), `minLength` / `maxLength` / `pattern` (строки).
- `items`: подсхема, применяемая к каждому элементу массива.
- `additionalProperties`: `false` запрещает лишние поля (значение по умолчанию зависит от режима).

Строгий режим OpenAI добавляет три требования: каждое свойство должно быть перечислено в `required`, `additionalProperties: false` везде, и никаких неразрешённых `$ref`. При нарушении этих правил API возвращает 400 во время запроса.

### Pydantic, привязка для Python

Pydantic v2 генерирует JSON Schema из моделей в форме датаклассов через `model_json_schema()`. Pydantic AI оборачивает это, так что вы пишете:

```python
class Invoice(BaseModel):
    customer: str
    line_items: list[LineItem]
    total_usd: Decimal
```

а фреймворк агента переводит схему в строгий режим OpenAI, `input_schema` у Anthropic или `responseSchema` у Gemini на границе. Вывод модели возвращается как типизированный экземпляр `Invoice`. Ошибки валидации выбрасывают `ValidationError` с типизированными путями ошибок.

### Zod, привязка для TypeScript

Zod (`z.object({customer: z.string(), ...})`) — это эквивалент для TS. Node SDK у OpenAI выставляет `zodResponseFormat(Invoice)`, который переводится в полезную нагрузку JSON Schema API.

### Отказы

Строгий режим не может заставить модель ответить. Если вход не может уместиться в схему («письмо было стихотворением, а не счётом»), модель выдаёт поле `refusal`, содержащее причину. Ваш код должен обрабатывать это как полноценный исход, а не как сбой. Отказ также полезен как сигнал безопасности: модель, которую попросили извлечь номер кредитной карты из письма с защищённым содержимым, возвращает отказ с приложенной причиной безопасности.

### Ограниченное декодирование в открытых моделях

Реализации с открытыми весами используют три техники.

1. **Декодирование на основе грамматики** (`outlines`, `guidance`, `lm-format-enforcer`): построить детерминированный конечный автомат из схемы; на каждом шаге маскировать логиты токенов, которые нарушили бы этот автомат.
2. **Маскирование логитов с JSON-парсером**: запускать потоковый JSON-парсер в лок-степе с моделью; на каждом шаге вычислять множество допустимых следующих токенов.
3. **Спекулятивное декодирование с верификатором**: дешёвая черновая модель предлагает токены, верификатор обеспечивает соблюдение схемы.

Коммерческие провайдеры выбирают одну из этих техник за кулисами. Передовые решения по состоянию на 2026 год работают быстрее обычной генерации для коротких структурированных выводов и примерно с той же скоростью для длинных.

### Три режима неуспешного исхода

1. **Ошибка разбора.** Вывод не является валидным JSON. Не может произойти в строгом режиме. Может произойти у нестрогих провайдеров.
2. **Нарушение схемы.** Вывод разбирается, но нарушает схему. Не может произойти в строгом режиме. Распространено вне его.
3. **Отказ.** Модель отказывается. Должен обрабатываться как типизированный исход.

### Стратегия повтора

Когда вы вне строгого режима (использование инструментов у Anthropic, нестрогий OpenAI, старая Gemini), паттерн восстановления такой:

```
generate -> parse -> validate -> if fail, inject error and retry, max 3x
```

Обычно достаточно одного повтора. Три повтора улавливают сбои слабых моделей. Больше трёх — признак плохой схемы: модель не может удовлетворить её для некоторых входов, и нужно чинить промпт или схему.

### Поддержка малых моделей

Ограниченное декодирование работает на малых моделях. Открытая модель с 3 миллиардами параметров и обеспечением грамматики превосходит модель на 70 миллиардов параметров с обычным промптингом на структурированных задачах. Это главная причина, почему структурированный вывод важен для продакшена: он отделяет надёжность от размера модели.

## Применяем

`code/main.py` поставляет минимальный валидатор JSON Schema 2020-12 на stdlib (типы, required, enum, min/max, pattern, items, additionalProperties). Он оборачивает схему `Invoice` и пропускает фиктивный вывод LLM через валидатор, демонстрируя пути ошибки разбора, нарушения схемы и отказа. Замените фиктивный вывод реальным ответом любого провайдера в продакшене.

На что обратить внимание:

- Валидатор возвращает типизированный список `[ValidationError]` с путём и сообщением. Именно эту форму нужно показывать в промпте повтора.
- Ветка отказа НЕ повторяет запрос. Она логирует и возвращает типизированный отказ. Фаза 14 · 09 использует отказы как сигнал безопасности.
- Проверка `additionalProperties: false` срабатывает на враждебном тестовом входе, показывая, почему строгий режим закрывает дверь перед галлюцинированными полями.

## Упражнения

1. Запустите `code/main.py`. Добавьте четвёртый тестовый случай, у которого `total_usd` — отрицательное число. Убедитесь, что валидатор отклоняет его с путём ограничения `minimum`.

2. Расширьте валидатор, чтобы он поддерживал `oneOf` с дискриминатором. Типичный случай: `line_item` — это либо продукт, либо услуга, помеченные полем `kind`. У строгого режима здесь тонкие правила; сверьтесь с руководством OpenAI по структурированному выводу.

3. Напишите ту же схему Invoice как Pydantic BaseModel и сравните вывод `model_json_schema()` с вашей схемой, написанной вручную. Определите единственное поле, которое Pydantic устанавливает по умолчанию, а версия, написанная вручную, опускает.

4. Измерьте частоту отказов. Составьте десять входов, которые не должны извлекаться (текст песни, математическое доказательство, пустое письмо), и пропустите их через реального провайдера со строгим режимом. Посчитайте отказы против галлюцинированных выводов. Это ваша эталонная база для повторов с учётом отказов.

5. Прочитайте руководство OpenAI по структурированному выводу от начала до конца. Определите единственную конструкцию, которую оно явно запрещает в строгом режиме, но которую допускает обычная JSON Schema. Затем спроектируйте схему, которая использует запрещённую конструкцию несущественным образом, и переработайте её так, чтобы она стала совместима со строгим режимом.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| JSON Schema 2020-12 | «Спецификация схемы» | Диалект схем на основе черновых спецификаций IETF, который поддерживает каждый современный провайдер |
| Строгий режим | «Гарантированная схема» | Флаг OpenAI, обеспечивающий соответствие схеме через ограниченное декодирование |
| Ограниченное декодирование | «Маскирование логитов» | Обеспечение соответствия во время декодирования, маскирующее недопустимые следующие токены |
| Отказ | «Модель отказывается» | Типизированный исход, когда вход не может уместиться в схему |
| Ошибка разбора | «Невалидный JSON» | Вывод не удалось разобрать как JSON; в строгом режиме такая ошибка невозможна |
| Нарушение схемы | «Неверная форма» | Вывод разобран, но нарушает ограничения типов / required / enum / диапазона |
| `additionalProperties: false` | «Лишнее запрещено» | Запрещает неизвестные поля; обязательно в строгом режиме OpenAI |
| Pydantic BaseModel | «Типизированный вывод» | Класс Python, выдающий и валидирующий JSON Schema |
| Схема Zod | «Тип вывода TypeScript» | Схема времени выполнения TS для валидации вывода провайдера |
| Обеспечение соответствия грамматике | «Ограниченное декодирование в открытых моделях» | Маскирование логитов на основе конечного автомата, как в outlines / guidance |
