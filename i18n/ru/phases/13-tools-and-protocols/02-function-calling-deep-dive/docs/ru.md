# Глубокое погружение в вызов функций — OpenAI, Anthropic, Gemini

> Три ведущих провайдера сошлись на одном и том же цикле вызова инструмента в 2024 году, а затем разошлись во всём остальном. OpenAI использует `tools` и `tool_calls`. Anthropic использует блоки `tool_use` и `tool_result`. Gemini использует `functionDeclarations` и корреляцию по уникальному идентификатору. Этот урок сравнивает три подхода бок о бок, чтобы код, работающий у одного провайдера, не ломался при переносе к другому.

**Тип:** Build
**Языки:** Python (стандартная библиотека, трансляторы схем)
**Предварительные требования:** Фаза 13 · 01 (интерфейс инструментов)
**Время:** ~75 минут

## Цели обучения

- Называть три отличия форм полезных нагрузок вызова функций у OpenAI, Anthropic и Gemini (объявление, вызов, результат).
- Переводить одно объявление инструмента во все три формата провайдеров и предсказывать, где будут различаться ограничения строгого режима.
- Использовать `tool_choice` у каждого провайдера, чтобы принудить, запретить или предоставить модели автоматический выбор вызова инструмента.
- Знать жёсткие лимиты каждого провайдера (число инструментов, глубина схемы, длина аргументов) и сигнатуры ошибок, которые он выдаёт при нарушении лимитов.

## Проблема

Форма запроса на вызов функции различается у разных провайдеров. Три конкретных примера из продакшен-стеков 2026 года.

**OpenAI Chat Completions / Responses API.** Вы передаёте `tools: [{type: "function", function: {name, description, parameters, strict}}]`. Ответ модели содержит `choices[0].message.tool_calls: [{id, type: "function", function: {name, arguments}}]`, где `arguments` — строка JSON, которую нужно разобрать самостоятельно. Строгий режим (`strict: true`) обеспечивает соответствие схеме через ограниченное декодирование.

**Anthropic Messages API.** Вы передаёте `tools: [{name, description, input_schema}]`. Ответ приходит как `content: [{type: "text"}, {type: "tool_use", id, name, input}]`. `input` уже разобран (объект, а не строка). Вы отвечаете новым сообщением с ролью `user`, содержащим блок `{type: "tool_result", tool_use_id, content}`.

**Google Gemini API.** Вы передаёте `tools: [{functionDeclarations: [{name, description, parameters}]}]` (вложено внутрь `functionDeclarations`). Ответ приходит как `candidates[0].content.parts: [{functionCall: {name, args, id}}]`, где `id` уникален начиная с Gemini 3 для корреляции параллельных вызовов. Вы отвечаете `{functionResponse: {name, id, response}}`.

Один и тот же цикл. Разные имена полей, разная вложенность, разные соглашения строка-против-объекта, разные механизмы корреляции. Команда, написавшая агента для погоды на OpenAI, платит два дня переноса на Anthropic и ещё день на Gemini только за обвязку.

Этот урок строит транслятор, который объединяет три формата в одно каноническое объявление инструмента и маршрутизирует их на границе системы. Фаза 13 · 17 обобщает тот же паттерн в шлюз LLM.

## Концепция

### Общая структура

Каждому провайдеру нужны пять вещей:

1. **Список инструментов.** Имя, описание и схема входных данных для каждого инструмента.
2. **Выбор инструмента.** Принудить конкретный инструмент, запретить инструменты или дать модели решить самой.
3. **Выдача вызова.** Структурированный вывод, называющий инструмент и аргументы.
4. **Идентификатор вызова.** Соотнести ответ с нужным вызовом (важно для параллельных вызовов).
5. **Внедрение результата.** Сообщение или блок, связывающий результат с вызовом.

### Различия в форме, поле за полем

| Аспект | OpenAI | Anthropic | Gemini |
|--------|--------|-----------|--------|
| Оболочка объявления | `{type: "function", function: {...}}` | `{name, description, input_schema}` | `{functionDeclarations: [{...}]}` |
| Поле схемы | `parameters` | `input_schema` | `parameters` |
| Контейнер ответа | `tool_calls[]` в сообщении ассистента | `content[]` типа `tool_use` | `parts[]` типа `functionCall` |
| Тип аргументов | JSON в виде строки | разобранный объект | разобранный объект |
| Формат идентификатора | `call_...` (генерирует OpenAI) | `toolu_...` (генерирует Anthropic) | UUID (Gemini 3+) |
| Блок результата | роль `tool`, `tool_call_id` | `user` с `tool_result`, `tool_use_id` | `functionResponse` с соответствующим `id` |
| Принудительный выбор инструмента | `tool_choice: {type: "function", function: {name}}` | `tool_choice: {type: "tool", name}` | `tool_config: {function_calling_config: {mode: "ANY"}}` |
| Запрет инструментов | `tool_choice: "none"` | `tool_choice: {type: "none"}` | `mode: "NONE"` |
| Строгая схема | `strict: true` | схема всегда обязательна | `responseSchema` на уровне запроса |

### Лимиты, с которыми вы реально столкнётесь

- **OpenAI.** 128 инструментов на запрос. Глубина схемы 5. Строка аргументов <= 8192 байт. Строгий режим требует отсутствия `$ref`, отсутствия пересекающихся `oneOf`/`anyOf`/`allOf`, и чтобы каждое свойство было перечислено в `required`.
- **Anthropic.** 64 инструмента на запрос. Глубина схемы формально неограничена, но практический предел — 10. Флага строгого режима нет; схема — это контракт, и модель обычно ему следует.
- **Gemini.** 64 функции на запрос. Типы схемы — подмножество OpenAPI 3.0 (небольшое расхождение с JSON Schema 2020-12). Параллельные вызовы с уникальными идентификаторами — начиная с Gemini 3.

### Поведение `tool_choice`

Три режима поддерживают все, но называют их по-разному.

- **Автоматический режим.** Модель выбирает инструмент или текст. Используется по умолчанию.
- **Обязательный / любой инструмент.** Модель обязана вызвать хотя бы один инструмент.
- **Без инструментов.** Модель не должна вызывать инструменты.

Плюс один режим, уникальный для каждого провайдера:

- **OpenAI.** Принудить конкретный инструмент по имени.
- **Anthropic.** Принудить конкретный инструмент по имени; флаг `disable_parallel_tool_use` разделяет одиночный и множественный режимы.
- **Gemini.** `mode: "VALIDATED"` пропускает каждый ответ через валидатор схемы независимо от намерения модели.

### Параллельные вызовы

`parallel_tool_calls: true` у OpenAI (по умолчанию) выдаёт несколько вызовов в одном сообщении ассистента. Вы запускаете их все и отвечаете пакетным сообщением с ролью инструмента, содержащим по одной записи на `tool_call_id`. Anthropic исторически выполняла только одиночные вызовы; `disable_parallel_tool_use: false` (по умолчанию начиная с Claude 3.5) включает множественные. Gemini 2 допускал параллельные вызовы, но не давал стабильных идентификаторов; Gemini 3 добавляет UUID, чтобы ответы, пришедшие не по порядку, корректно соотносились.

### Стриминг

Все три провайдера поддерживают потоковую передачу вызовов инструментов. Формат передачи различается:

- **OpenAI.** Фрагменты изменений `tool_calls[i].function.arguments` приходят постепенно. Вы накапливаете их до `finish_reason: "tool_calls"`.
- **Anthropic.** События начала, приращения и завершения блока. Фрагменты `input_json_delta` содержат части аргументов.
- **Gemini.** `streamFunctionCallArguments` (новое в Gemini 3) выдаёт фрагменты с `functionCallId`, поэтому несколько параллельных вызовов могут чередоваться.

Фаза 13 · 03 подробно разбирает пересборку параллельных и потоковых вызовов. Этот урок фокусируется на формах объявления и одиночного вызова.

### Ошибки и починка

Ошибки некорректных аргументов тоже выглядят по-разному.

- **OpenAI (нестрогий режим).** Модель возвращает `arguments: "{bad json}"`, разбор JSON у вас не проходит, вы вставляете сообщение об ошибке и вызываете модель заново.
- **OpenAI (строгий режим).** Валидация происходит во время декодирования; некорректный JSON невозможен, но может появиться `refusal`.
- **Anthropic.** `input` может содержать неожиданные поля; схема носит рекомендательный характер. Валидируйте на стороне сервера.
- **Gemini.** Особенность OpenAPI 3.0: `enum` на полях объекта молча игнорируется; валидируйте самостоятельно.

### Паттерн транслятора

Каноническое объявление инструмента в вашем коде выглядит так (форму выбираете вы сами):

```python
Tool(
    name="get_weather",
    description="Use when ...",
    input_schema={"type": "object", "properties": {...}, "required": [...]},
    strict=True,
)
```

Три крошечные функции переводят его в три формы провайдеров. Обвязка в `code/main.py` делает именно это, а затем пропускает фиктивный вызов инструмента через форму ответа каждого провайдера. Сеть не требуется — этот урок учит формам, а не HTTP.

Продакшен-команды оборачивают этот транслятор в `AbstractToolset` (Pydantic AI), `UniversalToolNode` (LangGraph) или `BaseTool` (LlamaIndex). Фаза 13 · 17 поставляет шлюз, который выставляет API в форме OpenAI перед любым из трёх провайдеров.


## Применяем

`code/main.py` определяет один канонический датакласс `Tool` и три транслятора, выдающих JSON-объявления в формате OpenAI, Anthropic и Gemini. Затем он разбирает вручную составленный ответ провайдера каждой формы в один и тот же канонический объект вызова, демонстрируя, что семантика идентична под капотом. Запустите его и сравните три объявления бок о бок.

На что обратить внимание:

- Три блока объявления различаются только оболочкой и именами полей.
- Три блока ответа различаются тем, где живёт вызов (`tool_calls` верхнего уровня, блок `content[]`, запись `parts[]`).
- Одна функция `canonical_call()` извлекает `{id, name, args}` из всех трёх форм ответа.

## Публикуем

Этот урок производит `outputs/skill-provider-portability-audit.md`. Получив интеграцию вызова функций для одного провайдера, скилл производит аудит переносимости: от каких лимитов провайдера она зависит, какие поля нужно переименовать и что сломается при переносе к каждому из двух других провайдеров.

## Упражнения

1. Запустите `code/main.py` и убедитесь, что все три JSON-объявления провайдеров сериализуют один и тот же исходный объект `Tool`. Измените канонический инструмент, добавив параметр-перечисление, и убедитесь, что только транслятору Gemini нужно обрабатывать особенность OpenAPI.

2. Добавьте парсер `ListToolsResponse` для каждого провайдера, извлекающий список инструментов, который модель возвращает после вызова `list_tools` или обнаружения. У OpenAI нативно такого нет; отметьте эту асимметрию.

3. Реализуйте преобразование `tool_choice`: отобразите канонический `ToolChoice(mode="force", tool_name="x")` во все три формы провайдеров. Затем отобразите `mode="any"` и `mode="none"`. Сверьтесь с таблицей различий из урока.

4. Выберите одного из трёх провайдеров и прочитайте его руководство по вызову функций от начала до конца. Найдите одно поле в его спецификации схемы, которое не поддерживают два других. Кандидаты: `strict` у OpenAI, `disable_parallel_tool_use` у Anthropic, `function_calling_config.allowed_function_names` у Gemini.

5. Напишите тестовый вектор: вызов инструмента, чьи аргументы нарушают объявленную схему. Пропустите его через валидатор каждого провайдера (валидатор из стандартной библиотеки в Уроке 01 подойдёт как заменитель) и зафиксируйте, какие ошибки срабатывают. Задокументируйте, какого провайдера вы бы выбрали для продакшена ради строгости.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Вызов функций | «Использование инструментов» | Поддержка на уровне API для выдачи структурированных вызовов инструментов |
| Объявление инструмента | «Спецификация инструмента» | Полезная нагрузка, состоящая из имени, описания и схемы входных данных JSON Schema |
| `tool_choice` | «Принудить / запретить» | Режимы автоматического выбора, обязательного вызова, запрета и выбора конкретного инструмента |
| Строгий режим | «Обеспечение соответствия схеме» | Флаг OpenAI, ограничивающий декодирование так, чтобы результат соответствовал схеме |
| Блок `tool_use` | «Форма вызова у Anthropic» | Встроенный блок содержимого с идентификатором, именем и входными данными |
| Часть `functionCall` | «Форма вызова у Gemini» | Запись `parts[]`, содержащая имя, аргументы и идентификатор |
| Аргументы в виде строки | «JSON в виде строки» | OpenAI возвращает аргументы как строку JSON, а не как объект |
| Параллельные вызовы инструментов | «Разветвление за один ход» | Несколько вызовов инструментов в одном сообщении ассистента |
| Отказ | «Модель отказывается» | Блок отказа вместо вызова, доступный только в строгом режиме |
| Подмножество OpenAPI 3.0 | «Особенность схемы у Gemini» | Gemini использует диалект, похожий на JSON Schema, с небольшими отличиями |
