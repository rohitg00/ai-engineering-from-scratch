# Гибридная память: вектор + граф + KV

> Гибридная память использует три параллельных хранилища: векторное — для семантического сходства, KV — для быстрого поиска фактов, графовое — для рассуждений о связях между сущностями. При поиске слой скоринга объединяет результаты из всех трёх. Это широко используемый в продакшене паттерн внешней памяти; Mem0 (Chhikara et al., 2025) — один из примеров его реализации.

**Тип:** Build
**Языки:** Python (stdlib)
**Предварительные требования:** Фаза 14 · 07 (MemGPT), Фаза 14 · 08 (Letta Blocks)
**Время:** ~75 минут

## Цели обучения

- Объяснить, почему одно хранилище (только вектор, только граф, только KV) недостаточно для памяти агента.
- Назвать три параллельных хранилища Mem0 и то, для чего оптимизировано каждое из них.
- Описать оценку слияния (fusion scoring) в Mem0 — релевантность, важность, актуальность — и почему это взвешенная сумма, а не иерархия.
- Реализовать игрушечную трёхкомпонентную память на stdlib с `add()`, который пишет во все три хранилища, и `search()`, который сливает результаты.

## Проблема

Одно хранилище не подходит хотя бы для одного из трёх классов запросов:

- **Семантическое сходство** — «о чём мы говорили насчёт дрейфа агента на прошлой неделе?» Побеждает вектор; KV и граф промахиваются.
- **Поиск факта** — «какой номер телефона у пользователя?» Побеждает KV; вектор расточителен, граф избыточен.
- **Рассуждение о связях** — «какие клиенты используют одну и ту же платёжную сущность?» Побеждает граф; вектор и KV не могут ответить.

Производственные агенты выдают все три типа запросов в рамках одной сессии. Память с одним хранилищем всегда ошибается для двух из них. Вклад Mem0 в том, чтобы подключить все три хранилища за единым интерфейсом `add`/`search` со скоринговой функцией, которая их объединяет.

## Концепция

### Три хранилища параллельно

Mem0 (arXiv:2504.19413, апрель 2025) при вызове `add(text, user_id, metadata)`:

1. Извлекает кандидатов-факты из текста (шаг на основе LLM).
2. Записывает каждый факт в векторное хранилище (эмбеддинг) для семантического поиска.
3. Записывает каждый факт в KV-хранилище с ключом (user_id, fact_type, entity) для поиска за O(1).
4. Записывает каждый факт в графовое хранилище (Mem0g) как типизированные рёбра для запросов о связях.

При вызове `search(query, user_id)`:

1. Векторное хранилище возвращает top-k по косинусной близости эмбеддингов.
2. KV-хранилище возвращает прямые совпадения по производным от запроса (user_id, type, entity).
3. Графовое хранилище возвращает подграф, достижимый от сущностей запроса.
4. Слой скоринга объединяет результаты всех трёх.

### Оценка слияния

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **Релевантность (relevance)** — косинус вектора, точное совпадение KV, вес пути в графе.
- **Важность (importance)** — размечается при записи или обучается (некоторые факты важнее: имена, идентификаторы, политики).
- **Актуальность (recency)** — экспоненциальное затухание с течением времени с момента последней записи или чтения.

Веса настраиваются под конкретный продукт. Более высокий `w_recency` — для чат-агентов; более высокий `w_importance` — для комплаенс-агентов; более высокий `w_relevance` — для поисковых агентов.

### Mem0g и временные рассуждения

Mem0g добавляет детектор конфликтов. Когда новый факт противоречит существующему ребру, существующее ребро помечается как недействительное, но не удаляется. Временные запросы («каким был город пользователя в марте?») обходят подграф, действительный на указанный момент времени.

Паттерн инвалидации Letta обобщает это поведение, отвечающее требованиям комплаенса.

### Результаты бенчмарков

Статья Mem0 сообщает (2025):

- **LoCoMo** (память для длинных диалогов): 91.6
- **LongMemEval** (эпизодическая память на длинном горизонте): 93.4
- **BEAM 1M** (бенчмарк памяти на 1M токенов): 64.1

Базовые сравнения (LLM с полным контекстом 128k, плоское векторное хранилище, плоское KV-хранилище) проигрывают на 10+ пунктов. Одни бенчмарки не оправдывают выбор — операционная форма важнее, — но цифры показывают, что дизайн слияния не является статистической погрешностью.

### Таксономия областей видимости

Mem0 разделяет память по области видимости (scope):

- **Память пользователя (user memory)** — сохраняется между сессиями, с ключом по `user_id`.
- **Память сессии (session memory)** — сохраняется в рамках одного треда.
- **Память агента (agent memory)** — состояние конкретного экземпляра агента.

Каждая запись выбирает одну область видимости. Поиск может обращаться сразу к нескольким областям с весами для каждой из них. Бездумное смешение областей видимости — это то, как возникают инциденты вида «ассистент рассказал Алисе о проекте Боба».

### Где этот паттерн ломается

- **Дрейф эмбеддингов.** Результаты векторного поиска, которые выглядят корректно на первых ста запросах, деградируют по мере роста корпуса. Добавьте периодическое переэмбеддинг наиболее используемых записей.
- **Разрастание схемы KV.** `(user_id, type, entity)` выглядит просто, пока каждая команда не начинает добавлять собственный `type`. Проводите ревизию набора типов ежеквартально.
- **Взрыв графа.** Один зашумлённый экстрактор добавляет 50 рёбер на сообщение. Ограничьте число записей в граф на один вызов `add`; отбрасывайте рёбра с низкой уверенностью.

## Реализация

`code/main.py` реализует паттерн трёх хранилищ на stdlib:

- `VectorStore` — наивное сходство по перекрытию токенов как замена эмбеддингов.
- `KVStore` — словарь с ключом `(user_id, fact_type, entity)`.
- `GraphStore` — типизированные рёбра (subject, relation, object, valid).
- `Mem0` — верхнеуровневый фасад с `add()`, `search()`, оценкой слияния и поиском с учётом области видимости.
- Разобранная трасса на многопользовательском, многосессионном диалоге.

Запустите:

```
python3 code/main.py
```

Вывод показывает три отдельных пути извлечения плюс слитый top-k. Поменяйте веса скоринга в начале `main()` и посмотрите, как меняется ранжирование.

## Применение

- **Mem0 (Apache 2.0)** — готово к продакшену. Разверните самостоятельно на Postgres + Qdrant + Neo4j, либо используйте управляемое облако.
- **Letta** — трёхуровневая модель core/recall/archival; подключайте собственные векторные и графовые бэкенды.
- **Zep** — коммерческая альтернатива с временным графом знаний и извлечением фактов.
- **Собственные решения** — когда нужен точный контроль над экстрактором (комплаенс) или весами слияния (голосовые агенты, где доминирует актуальность).

## Упражнения

1. Замените игрушечное сходство векторов на реальную модель эмбеддингов (sentence-transformers, Ollama, эмбеддинги OpenAI). Измерьте recall@10 на синтетическом длинном диалоге. Дрейфует ли ранжирование за 1000 записей?
2. Добавьте временной запрос: `search(query, as_of=timestamp)`. Возвращайте только записи, действительные на указанный момент времени или раньше. Какому хранилищу требуется больше всего доработки?
3. Реализуйте детектор конфликтов: если входящий факт противоречит ребру графа, аннулируйте старое ребро и логируйте оба. Проверьте на «пользователь живёт в Берлине» -> «пользователь живёт в Лиссабоне».
4. Перенесите скорер слияния так, чтобы он включал измерение `user_feedback` (лайк на извлечённых записях). Как предотвратить манипуляцию (агент возвращает только те записи, которые ему уже нравились)?
5. Прочитайте документацию Mem0 (`docs.mem0.ai`). Перенесите игрушечную реализацию на вызовы клиента `mem0`. Сравните качество поиска на одних и тех же 20 тестовых запросах.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Гибридная память | «Вектор + граф + KV» | Три хранилища, в которые данные записываются параллельно, а при поиске результаты объединяются |
| Извлечение фактов | «Загрузка данных в память» | Шаг с использованием LLM, на котором текст разбивается на кортежи (сущность, связь, факт) |
| Скоринг слияния | «Ранжирование по релевантности» | Взвешенная сумма релевантности, важности и актуальности |
| Область видимости | «Пространство имён памяти» | Пользователь / сессия / агент — определяет, кому что доступно |
| Mem0g | «Граф памяти» | Типизированные рёбра с временной валидностью для запросов о связях |
| Временная инвалидация | «Мягкое удаление» | Противоречащие рёбра помечаются как недействительные, но никогда не удаляются |
| Дрейф эмбеддингов | «Деградация поиска» | Качество векторного поиска снижается по мере роста корпуса; периодически выполняйте переэмбеддинг |
