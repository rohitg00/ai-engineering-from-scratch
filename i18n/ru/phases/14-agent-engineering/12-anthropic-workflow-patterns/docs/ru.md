# Паттерны рабочих процессов Anthropic: простота вместо сложности

> Шлунц и Чжан (Anthropic, декабрь 2024) разграничивают рабочие процессы (predefined paths) и агентов (dynamic tool-use). Пять паттернов рабочих процессов покрывают большинство случаев. Начинайте с прямых вызовов API. Добавляйте агентов только тогда, когда шаги невозможно предсказать заранее.

**Тип:** Learn + Build**Языки:** Python (stdlib)**Предварительные требования:** Фаза 14 · 01 (цикл агента)**Время:** ~60 минут
## Цели обучения

- Назвать пять паттернов рабочих процессов Anthropic: цепочка промптов, маршрутизация, параллелизация, оркестратор-воркеры, оценщик-оптимизатор.
- Объяснить различие между агентом и рабочим процессом и инженерную цену каждого подхода.
- Определять, когда выбрать рабочий процесс вместо агента (и наоборот).
- Реализовать все пять паттернов на stdlib поверх сценарной LLM (scripted LLM).

## Проблема

Команды хватаются за мультиагентные фреймворки для задач, которым нужен всего один вызов функции. Цена этого реальна: фреймворки добавляют слои, которые скрывают промпты, прячут поток управления и провоцируют преждевременное усложнение. Пост Шлунца и Чжана от декабря 2024 года — самый цитируемый в индустрии контраргумент: начинайте просто, добавляйте сложность только тогда, когда она окупается.

## Концепция

### Рабочие процессы против агентов

- **Рабочий процесс.** LLM и инструменты, оркестрованные через предопределённые пути в коде. Граф принадлежит инженерам.
- **Агент.** LLM динамически управляет собственными инструментами и самостоятельно выбирает шаги. Граф принадлежит модели.

У обоих подходов есть своё место. Рабочие процессы дешевле, быстрее и проще отлаживать. Агенты открывают дорогу к открытым (open-ended) задачам, но затрудняют анализ режимов отказа.

### Расширенная LLM (augmented LLM)

Основа для всех пяти паттернов: одна LLM со встроенными тремя возможностями — поиск (retrieval), инструменты (действия), память (сохранение состояния). Любой вызов API может их использовать.

### Пять паттернов

1. **Цепочка промптов (prompt chaining).** Вывод вызова 1 становится входом для вызова 2. Используйте, когда задача чётко раскладывается на линейную последовательность. Между шагами можно добавить необязательные программные проверки.

2. **Маршрутизация (routing).** LLM-классификатор выбирает, какую LLM или инструмент вызвать дальше. Используйте, когда категорически разные входные данные требуют разной обработки (поддержка первой линии vs возврат средств vs баг vs продажи).

3. **Параллелизация (parallelization).** N вызовов LLM выполняются одновременно, результаты агрегируются. Две формы: секционирование (разные фрагменты) и голосование (один и тот же промпт, N запусков, большинство/синтез).

4. **Оркестратор-воркеры (orchestrator-workers).** LLM-оркестратор динамически решает, каких воркеров (тоже LLM) запустить, и синтезирует их вывод. Похоже на циклы агента, но оркестратор не зацикливается бесконечно.

5. **Оценщик-оптимизатор (evaluator-optimizer).** Одна LLM предлагает ответ, другая его оценивает. Итерации продолжаются, пока оценщик не пропустит результат. Это обобщение Self-Refine (Урок 05).

### Где рабочие процессы превосходят агентов

- **Предсказуемые задачи.** Если шаги можно перечислить заранее, их стоит перечислить.
- **Задачи с ограничением по стоимости.** У рабочих процессов ограниченное число шагов; агенты могут уйти в разгон.
- **Задачи с требованиями комплаенса.** Аудиторы хотят читать граф, а не восстанавливать его по траекториям.

### Где агенты превосходят рабочие процессы

- **Открытые (open-ended) исследовательские задачи.** Когда следующий шаг зависит от того, что вернул предыдущий.
- **Задачи переменной длительности.** От минут до часов работы, когда число шагов заранее неизвестно.
- **Новые предметные области.** Когда правильный рабочий процесс ещё не известен — сначала исследование, формализация потом.

## Реализация

`code/main.py` реализует все пять паттернов рабочих процессов поверх `ScriptedLLM`:

- `prompt_chain(input, steps)` — последовательное выполнение.
- `route(input, classifier, handlers)` — классификация и диспетчеризация.
- `parallel_vote(prompt, n, aggregator)` — N запусков, агрегация.
- `orchestrator_workers(task, workers)` — оркестратор выбирает воркеров.
- `evaluator_optimizer(task, proposer, evaluator, max_iter)` — цикл до прохождения проверки.

Запустите:

```
python3 code/main.py
```

Каждый паттерн печатает свою трассировку. Общий объём кода на паттерн — около 10–15 строк; цена фреймворка измеряется тысячами строк.

## Практика

- Прямые вызовы API для большинства задач.
- Фреймворк — только когда паттерну действительно нужны устойчивое состояние (LangGraph), конкурентность на основе модели акторов (AutoGen v0.4) или шаблонизация ролей (CrewAI).
- Обращайтесь к Claude Agent SDK, когда нужна форма харнесса Claude Code без необходимости пересобирать её самостоятельно.

## Упражнения

1. Реализуйте маршрутизацию с порогом уверенности. Ниже порога — эскалация к человеку. Где должен находиться этот порог для сценария поддержки первой линии?
2. Добавьте тайм-аут в `parallel_vote`. Что происходит, если один из вызовов зависает? Как агрегировать результат при отсутствующих голосах?
3. Превратите `evaluator_optimizer` в бандита: сохраняйте два лучших результата по итерациям, чтобы поздний хороший результат не перезаписывался поздним плохим.
4. Скомбинируйте цепочку промптов с маршрутизацией: роутер выбирает одну из трёх цепочек. Измерьте стоимость в токенах в сравнении с альтернативой в виде одного большого промпта.
5. Возьмите одну из своих продакшн-функций. Нарисуйте граф рабочего процесса. Посчитайте шаги. Действительно ли агент был бы здесь лучше?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Workflow | «Предопределённый поток» | Граф вызовов LLM и инструментов, которым владеет инженер |
| Agent | «Автономный ИИ» | Граф, которым владеет модель; динамическое управление инструментами |
| Augmented LLM | «LLM с инструментами» | LLM + поиск + инструменты + память; атомарная единица |
| Prompt chaining | «Последовательные вызовы» | Вывод вызова N становится входом для вызова N+1 |
| Routing | «Диспетчеризация через классификатор» | Выбор, какая цепочка/модель обрабатывает вход |
| Parallelization | «Разветвление (fan out)» | N одновременных вызовов; агрегация секционированием или голосованием |
| Orchestrator-workers | «Агент-диспетчер» | LLM-оркестратор динамически выбирает специализированные LLM |
| Evaluator-optimizer | «Предлагающий + судья» | Итерации до прохождения оценщика; обобщение Self-Refine |
