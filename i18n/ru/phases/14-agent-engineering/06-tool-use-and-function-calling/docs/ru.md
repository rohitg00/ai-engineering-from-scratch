# Использование инструментов и вызов функций

> Toolformer (Schick et al., 2023) положил начало самоконтролируемой разметке вызовов инструментов. Berkeley Function Calling Leaderboard V4 (Patil et al., 2025) задаёт планку 2026 года: 40% — агентные задачи, 30% — многоходовые диалоги, 10% — реальные запросы, 10% — синтетические запросы, 10% — галлюцинации. Задача однооборотного вызова инструментов решена. Задачи памяти, динамического принятия решений и длинных цепочек вызовов инструментов — ещё нет.

**Тип:** Build
**Языки:** Python (stdlib)
**Предварительные требования:** этап 14 · 01 («Цикл агента»), этап 13 · 01 («Углублённый разбор вызова функций»)
**Время:** ~60 минут

## Цели обучения

- Объяснить сигнал самоконтролируемого обучения (self-supervised learning) в Toolformer: сохранять разметку вызова инструмента только в том случае, если её выполнение снижает потери на следующем токене.
- Назвать пять категорий оценивания BFCL V4 и что измеряет каждая из них.
- Реализовать реестр инструментов на stdlib с валидацией схемы, приведением аргументов и песочницей выполнения.
- Диагностировать три открытые проблемы 2026 года: длинные цепочки вызовов инструментов, динамическое принятие решений и память.

## Проблема

Ранние сценарии использования инструментов ставили простой вопрос: может ли модель предсказать корректный вызов функции? Современное использование инструментов ставит вопрос сложнее: может ли модель выстроить цепочку из 40 шагов, с памятью, с частичной наблюдаемостью, с восстановлением после сбоев инструментов, не галлюцинируя несуществующие инструменты?

Toolformer заложил базовый уровень: модели способны с помощью самоконтролируемого обучения научиться определять, когда вызывать инструмент. BFCL V4 задаёт целевой уровень оценивания на 2026 год. Пространство между ними — то самое пространство, в котором живут продакшн-агенты.

## Концепция

### Toolformer (Schick et al., NeurIPS 2023)

Идея: пусть модель сама размечает свой корпус предварительного обучения кандидатами на вызовы API. Каждый кандидат выполняется. Разметка сохраняется только в том случае, если включение результата инструмента снижает потери на следующем токене. Дообучение (fine-tuning) проводится на отфильтрованном корпусе.

Охваченные инструменты: калькулятор, система вопросов и ответов, поисковые системы, переводчик, календарь. Сигнал самоконтролируемого обучения касается исключительно того, помогает ли инструмент предсказывать текст — без разметки человеком.

Результат масштабирования: использование инструментов проявляется при увеличении масштаба модели. Небольшим моделям разметка вызовов инструментов вредит; крупным — помогает. Именно поэтому у передовых моделей 2026 года использование инструментов встроено по умолчанию, тогда как большинству моделей с 7 млрд параметров для надёжности требуется отдельное дообучение на использование инструментов.

### Berkeley Function Calling Leaderboard V4 (Patil et al., ICML 2025)

BFCL — фактический стандарт оценивания 2026 года. Состав V4:

- **Агентные задачи (Agentic, 40%)** — полные траектории агента: память, многоходовые диалоги, динамические решения.
- **Многоходовые диалоги (Multi-Turn, 30%)** — интерактивные диалоги с цепочками вызовов инструментов.
- **Реальные запросы (Live, 10%)** — реальные промпты, присланные пользователями (из более сложного распределения).
- **Синтетические запросы (Non-Live, 10%)** — синтетические тестовые случаи.
- **Галлюцинации (Hallucination, 10%)** — обнаружение ситуаций, когда инструмент вызывать не следует.

V3 ввёл оценивание на основе состояния: после последовательности вызовов инструментов проверяется фактическое состояние API (например, «файл действительно создан?»), а не сопоставление AST вызовов. V4 добавил категории веб-поиска, памяти и чувствительности к формату.

Ключевой вывод 2026 года: однооборотный вызов функций практически решён. Сбои концентрируются в памяти (перенос контекста между ходами), динамическом принятии решений (выбор инструмента на основе прежних результатов), длинных цепочках (дрейф после 20+ шагов) и обнаружении галлюцинаций (отказ от вызова, когда ни один инструмент не подходит).

### Схема инструмента

У каждого провайдера своя схема. Детали различаются, но форма одна и та же:

```
name: string
description: string (what it does, when to use it)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic использует `input_schema` напрямую. OpenAI использует `function.parameters`. Оба принимают JSON Schema. Описания критически важны — модель читает их, чтобы выбрать нужный инструмент. Плохие описания инструментов — причина номер один ошибок с выбором не того инструмента.

### Валидация аргументов

Не доверяйте ни одному вызову инструмента. Проверяйте:

1. **Приведение типов.** Модель может вернуть строку "5" там, где схема требует int. Приводите тип, если это однозначно; иначе отклоняйте.
2. **Валидация enum.** Если схема требует `status in {"open", "closed"}`, а модель выдаёт `"in_progress"`, отклоняйте с описательной ошибкой.
3. **Обязательные поля.** Отсутствие обязательного поля -> немедленное сообщение об ошибке обратно модели, а не аварийное завершение.
4. **Валидация формата.** Даты, email, URL — проверяйте конкретными парсерами, а не регулярными выражениями.

Каждый сбой валидации должен возвращать структурированное наблюдение, чтобы модель могла повторить попытку с корректной формой.

### Параллельные вызовы инструментов

Современные провайдеры поддерживают параллельные вызовы инструментов в одном ходе ассистента. Цикл:

1. Модель выдаёт 3 вызова инструментов с разными `tool_use_id`.
2. Среда выполнения исполняет их (параллельно, если они независимы).
3. Каждый результат возвращается как блок `tool_result`, сопоставленный по `tool_use_id`.

Инженерное правило: относитесь к ID корреляции как к критически важным элементам. Перепутаете их — получите маршрутизацию результата не к тому инструменту.

### Песочница

Выполнение инструмента — это граница песочницы (sandbox). Подробности — в уроке 09. Коротко: у каждого инструмента должны быть заданы поверхность чтения/записи, доступ к сети, таймаут, лимит памяти. Универсальный `run_shell(cmd)` — тревожный сигнал; конкретный `git_status()` безопаснее.

```figure
tool-routing
```

## Реализация

`code/main.py` реализует реестр инструментов в продакшн-форме:

- Валидатор подмножества JSON Schema (только stdlib).
- Регистрация инструментов с описанием, входной схемой, таймаутом и исполнителем.
- Приведение аргументов и валидация enum.
- Параллельная диспетчеризация инструментов с ID корреляции.
- Сообщения об ошибках как структурированные строки.

Запуск:

```
python3 code/main.py
```

Трасса показывает мини-агента, вызывающего три инструмента за один ход, включая один намеренно некорректный вызов, который отклоняется с описательной ошибкой, на основе которой модель может действовать.

## Применение

У каждого провайдера своя схема инструментов — Anthropic, OpenAI, Gemini, Bedrock. Используйте слой трансляции (OpenAI Agents SDK, Vercel AI SDK, адаптер инструментов LangChain), если нужна поддержка нескольких провайдеров. BFCL — эталонный бенчмарк: прогоните на нём своего агента перед релизом, если использование инструментов центрально для продукта.

## Поставка

`outputs/skill-tool-registry.md` генерирует каталог инструментов, схему и реестр для заданной предметной области. Включает проверки качества описаний (сообщает ли описание каждого инструмента модели, когда его использовать?).

## Упражнения

1. Добавьте инструмент-«заглушку» (no-op), позволяющий модели явно отказаться от использования любого другого инструмента. Измерьте результат на тесте галлюцинаций в духе BFCL.
2. Реализуйте приведение аргументов для строк, представляющих значения int и float. Где приведение типов начинает маскировать реальные баги?
3. Добавьте таймаут для каждого инструмента и автоматический предохранитель (circuit breaker): отказывайтесь от инструмента на 60 секунд после 3 сбоев подряд. Как это меняет восстановление модели после ошибок?
4. Прочитайте описание BFCL V4. Выберите одну категорию (например, «многоходовые диалоги») и прогоните 10 примеров промптов через своего агента. Сообщите долю успешных прохождений.
5. Перенесите валидатор, реализованный на stdlib, на Pydantic или Zod. Что Pydantic/Zod поймали такого, что упустил игрушечный вариант?
