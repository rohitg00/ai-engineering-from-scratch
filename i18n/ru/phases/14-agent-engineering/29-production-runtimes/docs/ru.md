# Продакшен-рантаймы: очередь, события, cron

> Продакшен-агенты работают в одной из шести форм рантайма: «запрос — ответ» (request-response), потоковая передача, надёжное выполнение, фоновая обработка на основе очереди, событийная модель и запуск по расписанию. Выбирайте форму раньше, чем фреймворк. Наблюдаемость — несущий элемент при любой форме.

**Тип:** Learn
**Языки:** Python (stdlib)
**Предварительные требования:** Фаза 14 · 13 (LangGraph), Фаза 14 · 22 (Голос)
**Время:** ~60 минут

## Цели обучения

- Назвать шесть форм продакшен-рантайма и сопоставить каждую с паттерном фреймворка / продукта.
- Объяснить, почему надёжное выполнение (LangGraph) важно для задач с длинным горизонтом.
- Описать событийный рантайм и когда подходят Claude Managed Agents.
- Объяснить тезис «наблюдаемость — несущий элемент» для многошаговых агентов.

## Проблема

Продакшен-агенты падают так, как это никогда не проявится в Jupyter-ноутбуке: сетевой таймаут на шаге 37, пользователь вешает трубку посреди голосового звонка, cron-задача умирает при перезагрузке машины, фоновый воркер исчерпывает память. Форма рантайма определяет, какие сбои переживаемы.

## Концепция

### Запрос — ответ

- Синхронный HTTP. Пользователь ждёт завершения.
- Годится только для коротких задач (<30 с).
- Стеки: Agno (Python + FastAPI), Mastra (TypeScript + Express/Hono/Fastify/Koa).
- Наблюдаемость: стандартные логи доступа HTTP + спаны OTel.

### Потоковая передача

- SSE или WebSocket для постепенного вывода.
- LiveKit расширяет это до WebRTC для голоса/видео (Урок 22).
- Стеки: любой фреймворк с поддержкой потоковой передачи + фронтенд, который умеет работать с SSE/WS.
- Наблюдаемость: тайминг по каждому фрагменту, задержка до первого токена, хвостовая задержка.

### Надёжное выполнение

- Состояние сохраняется в контрольной точке после каждого шага; автовозобновление при сбое.
- Модель акторов AutoGen v0.4 изолирует сбои в пределах одного агента (Урок 14).
- Ключевое отличие LangGraph (Урок 13).
- Необходимо, когда число шагов заранее неизвестно, а стоимость восстановления высока.

### Очередь / фоновая обработка

- Задача попадает в очередь, воркеры её забирают, результаты возвращаются через вебхуки или pub/sub.
- Необходимо для агентов с длинным горизонтом (от десятков до сотен шагов на задачу, согласно анонсу Anthropic про computer use).
- Стеки: Celery (Python), BullMQ (Node), SQS + Lambda (AWS), собственные решения.
- Наблюдаемость: глубина очереди, распределение задержки по задачам, размер DLQ.

### Событийная модель

- Агенты подписываются на триггеры: новое письмо, открытый PR, срабатывание cron.
- Claude Managed Agents закрывает это «из коробки» (Урок 17).
- CrewAI Flows (Урок 15) структурирует детерминированные событийные рабочие процессы.
- Наблюдаемость: источник триггера, задержка от события до старта, задержка агента.

### По расписанию

- Cron-подобные агенты, которые запускаются периодически.
- Сочетайте с надёжным выполнением, чтобы упавший ночной запуск возобновлялся на следующем тике.
- Стеки: Kubernetes CronJob + фреймворк с надёжным выполнением; хостинг (Render cron, Vercel cron).

### Паттерны развёртывания 2026 года

- **CrewAI Flows** для событийного продакшена.
- **Agno** — FastAPI без состояния для Python-микросервисов.
- **Mastra** — серверные адаптеры (Express, Hono, Fastify, Koa) для встраивания.
- **Pipecat Cloud / LiveKit Cloud** для управляемых голосовых систем (Урок 22).
- **Claude Managed Agents** для размещённого в облаке долгоживущего асинхронного выполнения.

### Наблюдаемость — несущий элемент

Без спанов OpenTelemetry GenAI (Урок 23) и бэкенда Langfuse/Phoenix/Opik (Урок 24) невозможно отладить многошаговый агент, упавший на шаге 40. Для продакшена это не опционально. Это разница между «мы отлаживаем быстро» и «мы воспроизводим всё с нуля с более подробным логированием».

### Где продакшен-рантаймы дают сбой

- **Неверный выбор формы.** Выбор формы «запрос — ответ» для пятиминутной задачи. Пользователи вешают трубку; воркеры накапливаются; повторные попытки складываются друг на друга.
- **Нет DLQ.** Воркеры очереди без очереди недоставленных сообщений. Упавшие задачи исчезают бесследно.
- **Непрозрачная фоновая работа.** Фоновый агент работает без экспорта трасс. Сбои невидимы, пока о них не сообщит пользователь.
- **Пропуск надёжного состояния.** Любой запуск дольше 30 секунд, который нельзя себе позволить перезапустить с нуля, нуждается в надёжном выполнении.

## Реализация

`code/main.py` — демонстрация на stdlib с несколькими формами:

- Конечная точка в форме «запрос — ответ» (обычная функция).
- Обработчик потоковой передачи (генератор).
- Воркер на основе очереди с DLQ.
- Реестр событийных триггеров.
- Планировщик в форме cron.

Запустите:

```bash
python3 code/main.py
```

Вывод: пять трасс, показывающих поведение каждой формы на одной и той же задаче. Одна и та же логика агента, разные внешние оболочки. Надёжное выполнение (шестая форма) намеренно рассматривается в Уроке 13 вместе с контрольными точками LangGraph.

## Применение

- **Запрос — ответ** для UX в стиле чата.
- **Потоковая передача** для постепенных ответов.
- **Надёжное выполнение** для задач с длинным горизонтом.
- **Очередь** для пакетной / асинхронной / долгой обработки.
- **Событие** для реактивности агента.
- **Cron** для служебных задач (консолидация памяти, оценивание, отчёты по стоимости).

## Упражнения

1. Перенесите ваш цикл ReAct из Урока 01 на все шесть форм в вашем стеке. Какая форма подходит какой поверхности продукта?
2. Добавьте DLQ к демонстрации на основе очереди. Смоделируйте 10% сбоев задач; выведите размер DLQ.
3. Напишите событийного оценочного агента, запускаемого по cron, который каждую ночь прогоняет топ-20 трасс дня.
4. Реализуйте потоковую передачу с обратным давлением: если клиент медленный, приостанавливайте агента. Как это взаимодействует с бюджетом хода?
5. Прочитайте документацию Claude Managed Agents. Когда стоит переносить самостоятельно хостингуемого агента с длинным горизонтом на управляемый сервис?

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Запрос — ответ | «Синхронно» | Пользователь ждёт; подходит только для коротких задач |
| Потоковая передача | «SSE / WS» | Постепенный вывод; удобнее для пользователя; задержка наблюдаема для каждого фрагмента |
| Надёжное выполнение | «Возобновление после сбоя» | Состояние сохранено в контрольной точке; перезапуск с последнего шага |
| На основе очереди | «Фоновые задачи» | Продюсер / пул воркеров / DLQ |
| Событийная модель | «На основе триггеров» | Агент реагирует на внешние события |
| DLQ | «Очередь недоставленных сообщений» | Место для хранения упавших задач |
| Claude Managed Agents | «Хостинговая среда выполнения» | Размещённое у Anthropic долгоживущее асинхронное выполнение с кешированием и компактизацией |
