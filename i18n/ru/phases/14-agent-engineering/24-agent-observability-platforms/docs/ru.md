# Наблюдаемость агентов: Langfuse, Phoenix, Opik

> В 2026 году доминируют три платформы наблюдаемости агентов с открытым исходным кодом. Langfuse (MIT) — свыше 6 млн установок в месяц, трассировка + управление промптами + оценивание + воспроизведение сессий. Arize Phoenix (Elastic 2.0) — глубокое агентно-специфичное оценивание, релевантность RAG, автоматическая инструментация OpenInference. Comet Opik (Apache 2.0) — автоматизированная оптимизация промптов, защитные ограничения, обнаружение галлюцинаций методом LLM-судьи.

**Тип:** Learn
**Языки:** Python (stdlib)
**Предварительные требования:** Этап 14 · 23 (OTel GenAI)
**Время:** ~45 минут

## Цели обучения

- Назвать три ведущие платформы наблюдаемости агентов с открытым исходным кодом и их лицензии.
- Определить, в чём каждая из них сильнее всего: Langfuse (управление промптами + сессии), Phoenix (RAG + автоматическая инструментация), Opik (оптимизация + защитные ограничения (guardrails)).
- Объяснить, почему 89% организаций сообщают о наличии наблюдаемости агентов к 2026 году.
- Реализовать конвейер на stdlib от трассировки к дашборду с оцениванием методом LLM-судьи.

## Проблема

OTel GenAI (Урок 23) даёт вам схему. Но всё равно нужна платформа, которая принимает спаны, запускает оценивание, хранит версии промптов и выявляет регрессии. Три претендента делают акцент на разных частях жизненного цикла.

## Концепция

### Langfuse (MIT)

- Более 6 млн установок SDK в месяц, более 19 тыс. звёзд на GitHub.
- Функции: трассировка, управление промптами с версионированием + интерактивная среда, оценивание (LLM-судья (LLM-as-judge), отзывы пользователей, произвольные оценщики), воспроизведение сессий.
- Июнь 2025: ранее коммерческие модули (LLM-as-a-judge, очереди аннотирования, эксперименты с промптами, Playground) стали открытым исходным кодом под лицензией MIT.
- Сильнее всего в: сквозной наблюдаемости с плотным циклом управления промптами.

### Arize Phoenix (Elastic License 2.0)

- Более глубокое агентно-специфичное оценивание: кластеризация трасс, обнаружение аномалий, релевантность поиска для RAG.
- Встроенная автоматическая инструментация OpenInference.
- Сочетается с управляемым Arize AX для продакшена.
- Нет версионирования промптов — позиционируется как инструмент для выявления дрейфа/поведенческой регрессии рядом с более широкими платформами.
- Сильнее всего в: релевантности RAG, поведенческом дрейфе, обнаружении аномалий.

### Comet Opik (Apache 2.0)

- Автоматизированная оптимизация промптов через A/B-эксперименты.
- Защитные ограничения (маскирование PII, тематические ограничения).
- Обнаружение галлюцинаций методом LLM-судьи.
- Бенчмарк по собственным измерениям Comet: логирование и оценивание в Opik занимают 23.44 с против 327.15 с у Langfuse (разница примерно в 14 раз) — воспринимайте вендорские бенчмарки как ориентировочные.
- Сильнее всего в: цикле оптимизации, автоматизированном экспериментировании, применении защитных ограничений.

### Отраслевые данные

По данным Maxim (полевой анализ 2026 года): у 89% организаций уже есть наблюдаемость агентов; проблемы качества — главный барьер в продакшене (об этом сообщают 32% респондентов).

### Выбор платформы

| Потребность | Выбор |
|------|------|
| Всё-в-одном с управлением промптами | Langfuse |
| Глубокое оценивание RAG + дрейф | Phoenix |
| Автоматизированная оптимизация + защитные ограничения | Opik |
| Открытая лицензия, без ELv2 | Langfuse (MIT) или Opik (Apache 2.0) |
| Интеграция с Datadog / New Relic | Любая — все они экспортируют OTel |

### Где этот паттерн ломается

- **Отсутствие стратегии оценивания.** Трассировка без оценивания — это просто дорогое логирование.
- **Самодельный LLM-судья без опоры на внешние источники.** Здесь применим паттерн CRITIC (Урок 05) — судьям нужны внешние инструменты для фактологической проверки.
- **Версии промптов не привязаны к трассам.** Когда в продакшене случается регрессия, невозможно методом бисекции найти промпт, который её вызвал.

```figure
wb-trace-ingest
```

## Реализация

`code/main.py` реализует сборщик трасс на stdlib + оценщик на основе LLM-судьи:

- Принимать спаны в формате GenAI.
- Группировать по сессиям, помечать неуспешные прогоны (срабатывания защитных ограничений, оценки с низкой уверенностью).
- Реализованный скриптом LLM-судья, оценивающий ответы агента по рубрике.
- Сводка в стиле дашборда: доля сбоев, основные причины сбоев, распределение оценок.

Запустите:

```
python3 code/main.py
```

Вывод: оценки по каждой сессии и категоризация сбоев, аналогичные тому, что показали бы Langfuse/Phoenix/Opik.

## Применение

- **Langfuse** самостоятельно развёрнутый или облачный; подключается через OTel или их SDK.
- **Arize Phoenix** самостоятельно развёрнутый; автоматическая инструментация OpenInference.
- **Comet Opik** самостоятельно развёрнутый или облачный; автоматизированный цикл оптимизации.
- **Datadog LLM Observability** для смешанных команд эксплуатации и ML, которые уже используют Datadog.

## Упражнения

1. Экспортируйте недельные OTel-трассы в облако Langfuse (бесплатный тариф). Какие сессии завершились неудачно? Почему?
2. Напишите рубрику для LLM-судьи под вашу предметную область (фактологическая точность, тон, соблюдение границ задачи). Проверьте на 50 трассах.
3. Сравните версионирование промптов в Langfuse с кластеризацией трасс в Phoenix. Что быстрее подсказывает, что сломалось?
4. Прочитайте документацию Opik по защитным ограничениям. Подключите защитное ограничение для маскирования PII к одному из прогонов вашего агента.
5. Проведите бенчмарк всех трёх платформ на вашем корпусе. Игнорируйте опубликованные вендорами цифры; измеряйте собственные.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Трассировка | «Сборщик спанов» | Принимает спаны OTel / SDK и индексирует их по сессиям |
| Управление промптами | «CMS для промптов» | Версионированные промпты, привязанные к трассам |
| LLM-судья | «Автоматизированное оценивание» | Отдельная большая языковая модель оценивает вывод агента по рубрике |
| Воспроизведение сессии | «Воспроизведение трассы» | Позволяет пошагово просматривать прошлые прогоны для отладки |
| Релевантность RAG | «Качество поиска» | Соответствует ли найденный контекст запросу |
| Кластеризация трасс | «Группировка по поведению» | Объединяет похожие прогоны в кластеры для обнаружения дрейфа |
| Применение защитных ограничений | «Политика при логировании» | Проверяет журналируемое содержимое на PII, токсичность и соблюдение границ задачи |
