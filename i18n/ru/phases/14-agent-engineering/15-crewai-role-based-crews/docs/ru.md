# Ролевые команды агентов — роли, задачи, процессы

> Четыре примитива: Agent, Task, Crew, Process. Две базовые формы: Crews (автономное ролевое взаимодействие) и Flows (событийно-ориентированные, детерминированные). CrewAI — эталонная реализация 2026 года, и её документация формулирует это прямо: «для любого production-ready приложения начинайте с Flow».

**Тип:** Learn + Build**Языки:** Python (stdlib)**Предварительные требования:** Фаза 14 · 12 (паттерны рабочих процессов), Фаза 14 · 14 (модель акторов)**Время:** ~75 минут
## Цели обучения

- Назвать четыре примитива CrewAI (Agent, Task, Crew, Process) и то, за что каждый отвечает.
- Различать процессы Sequential, Hierarchical и запланированный Consensus; выбирать подходящий под конкретную нагрузку.
- Отличать Crews (автономное ролевое взаимодействие) от Flows (событийно-ориентированные, детерминированные) и объяснять production-рекомендацию из документации.
- Подключать инструменты через декоратор `@tool` и подкласс `BaseTool`; рассуждать о структурированном выводе в сравнении со свободным текстом.
- Назвать четыре типа памяти CrewAI и когда каждый из них оправдан.
- Реализовать на stdlib crew из трёх агентов (исследователь, автор, редактор), которая производит бриф.
- Замечать три типичных отказа CrewAI: раздувание промпта, налог на manager-LLM, хрупкие передачи между задачами.

## Проблема

Команды, внедряющие мультиагентные фреймворки, упираются в одну и ту же стену. «Автономное взаимодействие» звучит отлично на демо. Затем клиент заводит баг, и вам нужен детерминированный воспроизводимый прогон. Или финансовый отдел спрашивает, сколько стоит один прогон crew, маршрутизируемого LLM. Или дежурный инженер в три часа ночи хочет узнать, какой агент завис.

Свободные crews, маршрутизируемые LLM, не отвечают ни на один из этих вопросов внятно. Чистые DAG отвечают на все, но теряют ту исследовательскую гибкость, которая нужна агенту для brainstorming.

Разделение CrewAI честно отражает этот компромисс. Crews — для совместной, ролевой, исследовательской работы. Flows — для событийно-ориентированной, управляемой кодом, проверяемой production-среды. Один фреймворк, две формы, выбор — под конкретную задачу.

## Концепция

### Четыре примитива

Поверхность CrewAI небольшая. Запомните это, и всё остальное — конфигурация.

- **Agent.** `role + goal + backstory + tools + (optional) llm`. Backstory — несущий элемент. Она задаёт тон, суждения, момент, когда агент останавливается. Tools — это функции, которые агент может вызывать (подробнее ниже).
- **Task.** `description + expected_output + agent + (optional) context + (optional) output_pydantic`. Многократно используемая единица работы. `expected_output` — это контракт. `context` перечисляет предыдущие задачи, чьи результаты передаются на вход. `output_pydantic` задаёт структурированную форму.
- **Crew.** Контейнер. Владеет списком `agents`, списком `tasks`, `process` и опциональными настройками `memory` + `verbose` + `manager_llm`.
- **Process.** Стратегия исполнения. Sequential, Hierarchical, Consensus (запланирован). Определяет форму прогона.

Агенты не видят друг друга напрямую. Task ссылается на agent. Crew выстраивает последовательность задач. Process решает, кто выбирает следующую задачу. Это вся ментальная модель целиком.

> **Проверено на** CrewAI 0.86 (2026-05). В более новых версиях типы process могут быть переименованы или объединены; перед тем как полагаться на конкретную форму, сверьтесь с [документацией CrewAI по Processes](https://docs.crewai.com/concepts/processes).

### Sequential против Hierarchical против Consensus

- **Sequential.** Задачи выполняются в порядке объявления. Результат задачи N доступен как `context` задаче N+1. Наименьшая стоимость. Наиболее предсказуемо. Используйте, когда порядок зафиксирован.
- **Hierarchical.** Manager-agent (отдельный вызов LLM) маршрутизирует между специалистами. CrewAI порождает manager либо из вашей конфигурации `manager_llm`, либо использует значение по умолчанию. Manager выбирает следующую задачу на каждом раунде и может отказать в выполнении или перенаправить её. Используйте, когда у вас четыре и более специалистов, а порядок реально зависит от предыдущего результата.
- **Consensus.** Запланирован, но пока не реализован в публичном API. Документация резервирует это имя за будущим процессом на основе голосования. Сегодня полагаться на него нельзя.

Hierarchical добавляет вызов LLM за раунд (manager) поверх каждого вызова специалиста. Стоимость в токенах может утроиться на прогоне из пяти шагов. Платите за это только тогда, когда вам действительно нужна маршрутизация.

### Crews против Flows

Именно так документация формулирует рамку в 2026 году.

- **Crew.** Автономность, управляемая LLM. Фреймворк сам выбирает форму во время выполнения. Хорошо подходит для: исследований, brainstorming, первых черновиков — везде, где путь к ответу является частью самого ответа. Трудно воспроизвести повторно. Трудно тестировать. Дёшево прототипировать.
- **Flow.** Событийно-ориентированный граф, которым владеете вы. `@start` отмечает точку входа. `@listen(topic)` отмечает шаг, который срабатывает, когда другой шаг публикует этот topic. Каждый шаг — обычный Python (может вызывать Crew изнутри). Хорошо подходит для: production. Наблюдаемо. Тестируемо. Детерминировано.

Production-рекомендация документации 2026 года: начинайте с Flow. Встраивайте Crews как вызовы `Crew.kickoff()` внутри шагов Flow, когда автономность оправдывает свою стоимость. Flow даёт вам аудиторский след, Crew даёт вам исследовательскую гибкость. Компонуйте, а не выбирайте что-то одно.

### Интеграция инструментов

Есть три способа дать agent инструмент. Выбирайте самый простой из тех, что подходит.

1. **Декоратор `@tool`.** Чистые функции превращаются в инструменты. Сигнатура — это схема; docstring — это описание, которое видит LLM. Лучше всего подходит для разовых вспомогательных функций.

   ```python
   from crewai.tools import tool

   @tool("Search the web")
   def search(query: str) -> str:
       """Return top results for the query."""
       return run_search(query)
   ```

2. **Подкласс `BaseTool`.** Инструмент на основе класса с явной схемой аргументов, поддержкой async, повторными попытками. Используйте, когда у инструмента есть состояние (клиент, кеш) или нужны структурированные аргументы.

   ```python
   from crewai.tools import BaseTool
   from pydantic import BaseModel

   class SearchArgs(BaseModel):
       query: str
       limit: int = 10

   class SearchTool(BaseTool):
       name = "web_search"
       description = "Search the web and return top results."
       args_schema = SearchArgs

       def _run(self, query: str, limit: int = 10) -> str:
           return self.client.search(query, limit=limit)
   ```

3. **Встроенные наборы инструментов.** CrewAI поставляется с фирменными адаптерами: `SerperDevTool`, `FileReadTool`, `DirectoryReadTool`, `CodeInterpreterTool`, `RagTool`, `WebsiteSearchTool`. Подключаются одним импортом.

Структурированный вывод использует Pydantic. Передайте `output_pydantic=MyModel` в Task. CrewAI проверяет ответ LLM на соответствие модели и либо приводит его к нужному типу, либо повторяет попытку. Сочетайте это со строгой строкой `expected_output`. Свободный текст на выходе подходит для черновиков; структурированный вывод — это то, что может потребить downstream Flow.

### Хуки памяти

CrewAI поставляется с четырьмя типами памяти «из коробки». Они компонуются: Crew может включить все четыре сразу.

> **Проверено на** CrewAI 0.86 (2026-05). Недавние релизы пропускают всё через унифицированную систему `Memory`, которая оборачивает эти четыре хранилища. Концептуальная модель ниже по-прежнему верна, но публичная поверхность классов в более новых версиях может свернуться до единой точки входа `Memory`; актуальное API проверяйте в [документации CrewAI по memory](https://docs.crewai.com/concepts/memory).

- **Short-term.** Буфер разговора в рамках одного прогона. Стирается по завершении.
- **Long-term.** Сохраняется между прогонами. Хранится в векторной базе данных (по умолчанию Chroma, заменяема). Извлекается по сходству с текущей задачей.
- **Entity.** Факты по конкретной сущности. «Клиент X на enterprise-тарифе». Индексируется по сущности, а не по сходству. Сохраняется между прогонами.
- **Contextual.** Извлечение во время сборки. Подтягивает релевантную память в момент, когда она нужна agent, а не заранее.

Включается на уровне Crew через `memory=True` или конфигурацией по каждому типу отдельно. Опирается на провайдера эмбеддингов, который вы настраиваете (по умолчанию OpenAI, заменяем на локальный). Память — одно из мест, где CrewAI оправдывает себя по сравнению с более лёгкими фреймворками; чистый LangGraph требует, чтобы вы подключали каждый из этих механизмов самостоятельно.

### Когда подходят ролевые команды

- От трёх до шести агентов с именованными ролями и совместным рабочим процессом. Черновики, ревью, планирование, brainstorming.
- Маршрутизация, где суждение LLM о следующем шаге само по себе составляет часть ценности (Hierarchical).
- Везде, где команде удобнее читать `role + goal + backstory`, чем определение графа.

### Когда они не подходят

- Детерминированные DAG со строгим порядком. Используйте LangGraph (урок 13). Форма графа здесь — правильная абстракция; ролевая рамка CrewAI создаёт трение.
- Бюджеты задержки в доли секунды. Hierarchical добавляет дополнительные обращения. Даже Sequential сериализует промпты, включающие backstories и предыдущие результаты.
- Одноагентные циклы. Пропустите фреймворк; agent loop (урок 1) плюс реестр инструментов короче.

Урок 17 (Компромиссы фреймворков для агентов) раскладывает это по матрице. Короткая версия: CrewAI занимает угол «совместная работа на основе ролей».

### Форма зависимостей

Не зависит от LangChain. Python 3.10–3.13. Использует `uv`. Число звёзд: см. [crewAIInc/crewAI](https://github.com/crewAIInc/crewAI) (снимок по состоянию на 2026-05). Интеграция с AWS Bedrock задокументирована; бенчмарки от вендора сообщают о существенном ускорении по сравнению с LangGraph на QA-нагрузках, но методология (набор данных, оборудование, метрика оценки) не опубликована, поэтому цифры от вендора фреймворка стоит воспринимать лишь как ориентир.

### Где этот паттерн ломается

- **Раздувание промпта из-за backstories.** Backstory на 2000 слов на агента и crew из пяти агентов сжигают бюджет контекста ещё до первого вызова инструмента. Держите backstories короче 200 слов. Переиспользуйте формулировки между агентами; не повторяйте фирменный стиль пять раз подряд.
- **Токенный налог manager-LLM.** Hierarchical-процесс добавляет вызов manager LLM перед каждым вызовом специалиста. На crew из пяти задач это шесть вызовов LLM вместо пяти, причём вызов manager несёт полный список задач плюс предыдущие результаты. Переключайтесь на Sequential, если маршрутизация не зависит от результата.
- **Хрупкие передачи между задачами.** `expected_output` задачи N — «план в виде тезисов». Задача N+1 читает его как `context` и пытается разобрать три раздела. LLM выдала четыре. Downstream-agent импровизирует. Чинится через `output_pydantic` на задаче N, чтобы задача N+1 читала типизированный объект, а не свободный текст.
- **Crew в проде как есть.** Свободный Crew отправлен в production без обёртки Flow. Вариативность вывода высокая; повторный прогон невозможен; дежурный инженер не может сравнить неудачный прогон с удачным. Оборачивайте Flow.

## Реализация

`code/main.py` реализует на stdlib обе формы плюс crew из трёх агентов.

Форма:

- Dataclass-ы `Agent`, `Task`, повторяющие поверхность CrewAI.
- `SequentialCrew.kickoff(inputs)` запускает задачи в порядке объявления, прокидывая результаты как `context`.
- `HierarchicalCrew.kickoff(topic)` добавляет manager-agent, выбирающего следующего специалиста на каждом раунде, и останавливается на «done».
- `Flow` с декораторами `@start` и `@listen(topic)`, миниатюрным event loop и трассировкой.
- Декоратор `tool(name)`, повторяющий форму `@tool` из CrewAI.
- `Memory` с хранилищами `short_term`, `long_term`, `entity`; имитация сходства через numpy.
- Ответы mock-LLM — это захардкоженные строки, привязанные к роли плюс префиксу входных данных. Без сети. Детерминированно.

Конкретная демонстрация: crew из исследователя, автора и редактора, производящая бриф на тему «agent engineering 2026». Исследователь достаёт (имитированные) источники. Автор пишет черновик. Редактор дорабатывает текст. Тот же crew прогоняется через Flow, чтобы показать детерминированную форму.

Запустите так:

```bash
python3 code/main.py
```

Трассировка покрывает: sequential crew, прокидывающий результаты через `context`; hierarchical crew с выбором manager (исследователь, автор, редактор, затем «done»); flow, прогоняющий те же три шага с явными topics (`researched`, `drafted`, `edited`); вызовы инструментов, маршрутизируемые через `@tool`; и long-term-память, сохраняющуюся между двумя kickoff.

Трассировка Crew подвижна; manager в принципе мог бы изменить порядок. Трассировка Flow фиксирована. Этот выбор и есть суть урока.

## Практика

- **CrewAI Flow** для production. Даже когда Flow — это один шаг, вызывающий `Crew.kickoff()`. Flow даёт границу аудита.
- **CrewAI Crew (Sequential)** для совместной работы с чётким порядком, особенно для первых черновиков и циклов ревью.
- **CrewAI Crew (Hierarchical)**, когда маршрутизация зависит от результата и у вас четыре и более специалистов.
- **LangGraph** (урок 13) для явных конечных автоматов, устойчивого возобновления, строгого порядка.
- **AutoGen v0.4** (урок 14) для конкурентности на основе модели акторов и изоляции сбоев.
- **OpenAI Agents SDK** (урок 16) для продуктов, ориентированных на OpenAI, с handoffs и guardrails.
- **Claude Agent SDK** (урок 17) для продуктов, ориентированных на Claude, с subagents и хранилищем сессий.

## Подводные камни

- **Backstory как «приправа».** Она формирует результат. Протестируйте три варианта на агента; разброс реален. Выберите один, зафиксируйте.
- **Пропуск `expected_output`.** Без контракта на каждую задачу downstream-задачи подхватывают что придётся из того, что выдала LLM. Crew выполняется; аудит проваливается.
- **Память всегда включена.** Long-term пишет на каждом прогоне. Векторная база данных растёт. Извлечение становится шумным. Ограничивайте запись задачами, где факт действительно устойчив во времени.
- **Дрейф промпта manager.** Промпт manager в Hierarchical неявный. Если маршрутизация ведёт себя странно, включите verbose-режим и прочитайте его.
- **Побочные эффекты инструментов в Crews.** Crew может вызвать инструмент больше раз, чем ожидалось. POST, DELETE, платёж должны быть в шаге Flow, никогда — в инструменте Crew.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Agent | «Персона» | Роль + цель + backstory + инструменты |
| Task | «Единица работы» | Описание + ожидаемый результат + исполнитель + опциональный структурированный вывод |
| Crew | «Команда агентов» | Контейнер для Agents + Tasks + Process |
| Process | «Стратегия исполнения» | Sequential / Hierarchical / Consensus (запланирован) |
| Flow | «Детерминированный рабочий процесс» | Событийно-ориентированный, управляемый кодом, тестируемый |
| Backstory | «Промпт персоны» | Формирователь тона и суждений agent |
| `@tool` | «Функциональный инструмент» | Декоратор, превращающий функцию в инструмент, который может вызвать agent |
| `BaseTool` | «Классовый инструмент» | Инструмент на основе класса со схемой аргументов, повторными попытками, поддержкой async |
| Entity memory | «Факты по сущности» | Память, ограниченная рамками клиента / аккаунта / issue |
| Long-term memory | «Память между прогонами» | Память на основе векторного хранилища, сохраняющаяся между kickoff |
| Contextual memory | «Извлечение точно в срок» | Память, подтягиваемая в момент, когда она нужна agent |
| Manager LLM | «Agent-маршрутизатор» | Дополнительная LLM в Hierarchical-процессе, выбирающая следующую задачу |
| `expected_output` | «Контракт задачи» | Строка, которая сообщает agent (и аудиту), какую форму должен иметь результат |
