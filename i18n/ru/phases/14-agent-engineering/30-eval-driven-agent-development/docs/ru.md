# Разработка агентов на основе оценивания

> Рекомендация Anthropic: «начинайте с простых промптов, оптимизируйте их с помощью всестороннего оценивания и добавляйте многошаговые агентные системы только при необходимости». Оценивание — не последний шаг. Это внешний цикл, который управляет каждым другим решением в Фазе 14.

**Тип:** Learn + Build
**Языки:** Python (stdlib)
**Предварительные требования:** вся фаза 14.
**Время:** ~60 минут

## Цели обучения

- Назвать три уровня оценивания — статические бенчмарки, кастомное офлайн-оценивание, онлайн-оценивание в продакшене — и объяснить, для чего нужен каждый.
- Объяснить тесный цикл оценщика-оптимизатора (evaluator-optimizer).
- Описать лучшую практику 2026 года: проверки оценивания живут рядом с кодом, запускаются в CI и блокируют PR.
- Связать каждый урок Фазы 14 со сценарием оценивания, который он порождает.

## Проблема

Агенты проходят демо. В продакшене они отказывают способами, которые демо не в силах предсказать. Бенчмарки отвечают на вопрос «эта модель в целом способна?», а не «этот агент поставляет правильные патчи для моего продукта?». Ответ: оценивание на трёх уровнях, работающее непрерывно, при котором каждое защитное ограничение и каждое выученное правило сопоставлены со сценарием оценивания.

## Концепция

### Три уровня оценивания

1. **Статические бенчмарки** — SWE-bench Verified для кода (Урок 19), WebArena/OSWorld для браузера и рабочего стола (Урок 20), GAIA для универсальных задач (Урок 19), BFCL V4 для использования инструментов (Урок 06). Используйте для сравнения моделей между собой и для блокировки регрессий. Контаминация — не миф: SWE-bench+ обнаружил утечку решений в 32.67% случаев. Всегда указывайте результаты Verified или результаты, прошедшие аудит SWE-bench+.

2. **Кастомное офлайн-оценивание** — учитывает специфику вашего продукта:
   - LLM в роли судьи (LLM-as-judge; Langfuse, Phoenix, Opik — Урок 24).
   - На основе выполнения (execution-based): запустите патч, проверьте тесты.
   - На основе траектории (trajectory-based): сравните последовательности действий с эталоном (gold); OSWorld-Human показывает, что топовые агенты делают в 1.4-2.7 раза больше шагов, чем эталон.

3. **Онлайн-оценивание** — в продакшене:
   - Повторы сессий (session replays) (Langfuse).
   - Оповещения по срабатыванию защитных ограничений (guardrail) (Уроки 16, 21).
   - Отслеживание стоимости и задержки на каждом шаге (Урок 23, спаны OTel).

### Оценщик-оптимизатор (evaluator-optimizer, Anthropic)

Тесный цикл:

1. Предлагающая модель (proposer) генерирует результат.
2. Оценщик выносит вердикт.
3. Дорабатывайте, пока оценщик не пропустит результат.

Это обобщение паттерна Self-Refine (Урок 05). Любой важный для вас агентный процесс можно обернуть в оценщик-оптимизатор ради надёжности.

### Лучшая практика 2026 года

- Проверки оценивания живут рядом с кодом.
- Запускаются в CI на каждый PR.
- Слияние блокируется по результатам оценивания (например, «регрессия не более 5% относительно main»).
- Каждое защитное ограничение сопоставлено со сценарием оценивания.
- Каждое выученное правило (Reflexion, паттерн learn-rule из pro-workflow) сопоставлено с кейсом отказа.

### Где разработка на основе оценивания даёт сбой

- **Нет базовой линии (baseline).** Результаты оценивания без последнего известного хорошего результата невозможно интерпретировать. Храните базовые линии.
- **LLM-судья без заземления (grounding).** Судьи тоже галлюцинируют. Паттерн CRITIC (Урок 05) — судья заземляется на внешних инструментах.
- **Переобучение под проверки оценивания.** Оптимизация под результаты оценивания расходится с полезностью в продакшене. Ротируйте сценарии.
- **Нестабильное оценивание.** Недетерминированные кейсы вызывают ложные срабатывания. Фиксируйте начальные значения генератора случайных чисел, делайте снапшоты состояния.

## Реализация

`code/main.py` — это стенд оценивания на stdlib:

- Реестр кейсов с категориями (бенчмарк, кастомные, онлайн).
- Скриптованный агент, который тестируется.
- Цикл оценщик-оптимизатор: предложить, оценить, доработать — до успешного прохождения проверки оценивания или достижения максимума раундов.
- CI-ворота (gate): суммарная доля прохождения + регрессия относительно базовой линии.

Запустите:

```
python3 code/main.py
```

Вывод: результат прохождения каждого кейса, флаг регрессии, вердикт CI-ворот.

## Применение

- Пишите сценарии оценивания в том же репозитории, что и код агента.
- Запускайте их на каждый PR через CI.
- Проваливайте сборку при регрессии.
- Отслеживайте долю прохождения во времени.
- Привязывайте каждый отказ в продакшене к новому кейсу.

## Поставка

`outputs/skill-eval-suite.md` строит трёхуровневый набор сценариев оценивания для агентного продукта с CI-воротами и отслеживанием регрессий.

## Упражнения

1. Возьмите один из ваших отказов в продакшене. Напишите сценарий оценивания, который его воспроизводит. Проходит ли его теперь ваш агент?
2. Постройте рубрику для LLM-судьи в вашей предметной области с тремя измерениями (фактическая точность, тон, охват). Оцените 50 сессий.
3. Подключите набор сценариев оценивания к CI. Проваливайте сборку при регрессии >=5%.
4. Добавьте метрику эффективности траектории (trajectory efficiency): сколько шагов сделал агент по сравнению с эталонной (gold) траекторией?
5. Сопоставьте каждый урок Фазы 14 со сценарием оценивания в вашем наборе. Что-то отсутствует? Это пробел, который нужно закрыть.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Статический бенчмарк | «Готовая проверка оценивания» | SWE-bench, GAIA, AgentBench, WebArena, OSWorld |
| Кастомное офлайн-оценивание | «Доменное оценивание» | LLM в роли судьи / выполнение / траектория с учётом специфики вашего продукта |
| Онлайн-оценивание | «Оценивание в продакшене» | Повтор сессий, оповещения защитных ограничений, отслеживание стоимости и задержки |
| Оценщик-оптимизатор | «Предложить — оценить — доработать» | Повторять цикл, пока оценщик не пропустит результат |
| CI-ворота | «Блокировка слияния» | Провалить сборку при регрессии результатов оценивания |
| Базовая линия | «Последний известный хороший результат» | Эталонный результат для выявления регрессии |
| Эффективность траектории | «Шаги относительно эталона» | Число шагов агента, делённое на минимальное число шагов эксперта-человека |
