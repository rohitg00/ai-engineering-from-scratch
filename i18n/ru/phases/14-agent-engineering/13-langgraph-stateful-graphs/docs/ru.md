# Оркестрация графов с состоянием — надёжное выполнение и контрольные точки

> Агент — это конечный автомат; узлы — функции; рёбра — переходы; состояние сохраняется в контрольной точке после каждого узла. После любого сбоя выполнение возобновляется с последней успешной контрольной точки. LangGraph — эталонное решение 2026 года для этой модели низкоуровневой оркестрации с состоянием.

**Тип:** Learn + Build**Языки:** Python (stdlib)**Предварительные требования:** Фаза 14 · 01 (цикл агента), Фаза 14 · 12 (паттерны рабочих процессов)**Время:** ~75 минут
## Цели обучения

- Описать базовую модель LangGraph: конечный автомат с типизированным состоянием, узлами-функциями, условными рёбрами и контрольными точками после каждого узла.
- Назвать четыре возможности, которые выделяет документация: надёжное выполнение, потоковую передачу, участие человека в цикле (human-in-the-loop) и полноценную память.
- Объяснить три топологии оркестрации, которые поддерживает LangGraph: супервизор (supervisor), одноранговая (peer-to-peer, swarm) и иерархическая (вложенные подграфы).
- Реализовать граф состояний на stdlib с типизированным состоянием, условными рёбрами и циклом «контрольная точка / возобновление».

## Проблема

У агентов и рабочих процессов есть общая проблема: когда выполнение из 40 шагов падает на шаге 38, вы хотите возобновить именно с шага 38, а не начинать заново. Модели состояния «второго сорта» вынуждают операторов городить повторные попытки вокруг библиотеки, которая рассчитана только на запуски с нуля.

Архитектурный ответ LangGraph: состояние — это полноценный типизированный объект, изменения явные, а контрольные точки сохраняются после каждого узла. Возобновление — это просто вызов `load_state(session_id)`.

## Концепция

### Граф

Граф определяется следующим:

- **Тип состояния.** Типизированный словарь (или модель Pydantic), который читает и изменяет каждый узел.
- **Узлы.** Чистые функции `(state) -> state_update`. После возврата обновления объединяются с состоянием.
- **Рёбра.** Условные или прямые переходы между узлами.
- **Вход и выход.** Служебные узлы `START` и `END` обозначают границы графа.

Пример: агент с узлами `classify`, `refund`, `bug`, `sales`, `done` — рабочий процесс маршрутизации, представленный в виде графа.

### Надёжное выполнение

После возврата из каждого узла среда выполнения сериализует состояние и записывает его в чекпоинтер (SQLite, Postgres, Redis или собственный). При сбое на шаге N среда выполнения может вызвать `resume(session_id)` и продолжить с шага N+1 с точным состоянием.

В документации LangGraph явно упоминаются продакшн-пользователи, для которых это важно: Klarna, Uber, J.P. Morgan. Суть не в форме графа как таковой — суть в том, что форма графа в сочетании с контрольными точками делает восстановление дешёвым.

### Потоковая передача

Каждый узел может выдавать частичный вывод. Граф передаёт вызывающей стороне события с изменениями по каждому узлу, чтобы интерфейс обновлялся по мере выполнения графа.

### Участие человека в цикле (human-in-the-loop)

Проверяйте и изменяйте состояние между узлами. Варианты реализации: приостановка перед критическим узлом, показ состояния человеку, приём изменений, возобновление. Чекпоинтер упрощает это, поскольку состояние уже сериализовано.

### Память

Кратковременная (в рамках одного запуска — история диалога в состоянии) и долговременная (между запусками — сохраняется через чекпоинтер плюс отдельное долговременное хранилище). LangGraph интегрируется с внешними системами памяти (Mem0, собственными) через инструменты.

### Три топологии

1. **Супервизор (Supervisor).** Центральная LLM-маршрутизатор направляет задачи специализированным субагентам. `create_supervisor()` в `langgraph-supervisor` (хотя команда LangChain в 2026 году рекомендует делать это напрямую через вызовы инструментов для большего контроля над контекстом).
2. **Swarm / одноранговая (peer-to-peer).** Агенты передают задачи друг другу напрямую через общий набор инструментов. Центрального маршрутизатора нет.
3. **Иерархическая.** Супервизоры управляют суб-супервизорами, реализованными как вложенные подграфы.

### Где этот паттерн ломается

- **Слишком мелкие контрольные точки.** Если сохранять в контрольных точках только реплики диалога, состояние инструментов и записи в память становятся невосстановимыми. Сериализовываться должно полное состояние.
- **Недетерминированные узлы.** Возобновление предполагает, что входные данные узла дают то же самое обновление состояния. Случайные seed-значения, показания часов и внешние API нужно фиксировать явно.
- **Злоупотребление условными рёбрами.** Граф, где каждое ребро условное, — это конечный автомат, о поведении которого невозможно рассуждать. Предпочитайте линейные цепочки с редкими ветвлениями.

## Реализация

`code/main.py` реализует граф состояний на stdlib:

- `State` — типизированный словарь с полями `messages`, `step`, `route`, `output`, `human_approval`.
- `Node` — вызываемый объект, принимающий состояние и возвращающий словарь обновлений.
- `StateGraph` — узлы + рёбра + условные рёбра + запуск + возобновление.
- `SQLiteCheckpointer` (заглушка в памяти) — сериализует состояние после каждого узла; `load(session_id)` восстанавливает его.
- Демонстрационный граф: classify -> branch(refund / bug / sales) -> human gate -> send.

Запустите:

```
python3 code/main.py
```

Трасса показывает, что первый запуск падает на human gate, происходит сохранение, а затем возобновление даёт итоговый результат.

## Упражнения

1. Добавьте условное ребро от `classify` к `end` на случай, если уверенность классификации ниже порога. Возобновите выполнение после того, как человек вручную задаст `route`.
2. Замените SQLite-подобную заглушку на настоящий SQLite-чекпоинтер. Измерьте накладные расходы на сериализацию на каждом шаге.
3. Реализуйте параллельные рёбра: два узла выполняются одновременно и объединяются с помощью собственного редьюсера (reducer). Что даёт неизменяемое состояние в этом случае?
4. Изучите справочник `langgraph-supervisor`. Перенесите игрушечный пример на `create_supervisor`. Сравните форму трасс.
5. Добавьте потоковую передачу: пусть каждый узел выдаёт частичное состояние по мере выполнения. Выводите изменения по мере поступления.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| State graph | «Агент как конечный автомат» | Типизированное состояние + узлы + рёбра + редьюсеры |
| Checkpointer | «Бэкенд персистентности» | Сериализует состояние после каждого узла; обеспечивает возобновление |
| Reducer | «Объединитель состояния» | Функция, которая объединяет текущее состояние с обновлением от узла |
| Conditional edge | «Ветвление» | Ребро, выбираемое функцией состояния |
| Subgraph | «Вложенный граф» | Граф, используемый как узел внутри другого графа |
| Durable execution | «Возобновление после сбоя» | Перезапуск с последнего успешного узла с точным состоянием |
| Supervisor | «LLM-маршрутизатор» | Центральный диспетчер для специализированных субагентов |
| Swarm | «P2P-агенты» | Агенты передают задачи через общие инструменты; центрального маршрутизатора нет |
