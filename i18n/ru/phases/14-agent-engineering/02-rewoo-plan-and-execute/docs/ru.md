# ReWOO и Plan-and-Execute: развязанное планирование

> ReAct чередует размышление и действие в одном потоке. ReWOO разделяет их: сначала один большой план, затем выполнение. В 5 раз меньше токенов, +4% точности на HotpotQA, а планировщик можно дистиллировать в модель на 7B. Plan-and-Execute обобщил этот паттерн; Plan-and-Act масштабировал его на навигацию по веб-страницам.

**Тип:** Build**Языки:** Python (stdlib)**Предварительные требования:** Фаза 14 · 01 (Agent Loop)**Время:** ~60 минут
## Цели обучения

- Объясните, почему разделение Planner / Worker / Solver в ReWOO экономит токены и повышает устойчивость по сравнению с чередующимся циклом ReAct.
- Реализуйте DAG плана, исполнитель с порядком по зависимостям и solver, который компонует результаты worker'ов — всё на стандартной библиотеке.
- Решите, должна ли задача выполняться как план-затем-выполнение или как чередующийся ReAct, используя фрейминг 2026 года «пять паттернов workflow» (Anthropic).
- Определите, когда нужны синтетические данные планов Plan-and-Act для долгих задач в вебе или на мобильных устройствах.

## Проблема

Чередующийся цикл размышление-действие-наблюдение в ReAct прост и гибок, но каждый вызов инструмента должен нести полный предыдущий контекст — включая каждое предыдущее размышление. Расход токенов растёт квадратично с глубиной. Хуже того: когда инструмент отказывает посреди цикла, модель должна заново выводить весь план из наблюдения об ошибке.

ReWOO (Xu et al., arXiv:2305.18323, май 2023) заметили это и сделали ставку: спланировать всё заранее, получить доказательства параллельно, составить ответ в конце. Один вызов LLM для планирования, N вызовов инструментов для доказательств (могут быть параллельными), один вызов LLM для решения. Плата за это — меньшая гибкость (план статичен) в обмен на намного лучшую эффективность по токенам и более понятные режимы отказа.

## Концепция

### Три роли

```
Planner:  user_question -> [plan_dag]
Workers:  [plan_dag]     -> [evidence]        (tool calls, possibly parallel)
Solver:   user_question, plan_dag, evidence -> final_answer
```

Planner создаёт DAG. Каждый узел называет инструмент, его аргументы и то, от каких более ранних узлов он зависит (ссылки вида `#E1`, `#E2`). Workers выполняют узлы в топологическом порядке. Solver сшивает всё вместе.

### Почему в 5 раз меньше токенов

В ReAct длина промпта растёт линейно с количеством шагов. На шаге 10 промпт содержит размышление 1, действие 1, наблюдение 1, размышление 2, действие 2, наблюдение 2 и так далее. Каждый промежуточный шаг также избыточно включает исходный промпт.

ReWOO платит за один промпт планировщика (большой), N маленьких промптов worker'ов (каждый — просто вызов инструмента, без цепочки) и один промпт solver'а. На HotpotQA статья измеряет ~5x меньше токенов при росте абсолютной точности на +4.

### Почему это устойчивее

Если worker 3 отказывает в ReAct, цикл должен рассуждать, выходя из ошибки, посреди потока. В ReWOO worker 3 возвращает строку ошибки; solver видит её в контексте вместе с исходным планом и может изящно деградировать. Локализация отказа происходит по узлу, а не по шагу.

### Дистилляция планировщика

Второй результат статьи: поскольку планировщик не видит наблюдений, можно дообучить модель на 7B на выходах планировщика от учителя на 175B. Маленькая модель занимается планированием; большая модель не нужна на инференсе. Сейчас это стандартная практика: многие продакшен-агенты 2026 года используют маленький планировщик и большой исполнитель или наоборот.

### Plan-and-Execute (2023)

Пост команды LangChain от августа 2023 обобщил ReWOO в паттерн с именем Plan-and-Execute. Планировщик заранее выдаёт список шагов, исполнитель выполняет каждый шаг, опциональный реплановщик может пересматривать план после наблюдения результатов. Это ближе к ReAct, чем ReWOO (реплановщик возвращает наблюдения обратно в планирование), но сохраняет экономию токенов.

### Plan-and-Act (Erdogan et al., arXiv:2503.09572, ICML 2025)

Plan-and-Act масштабирует паттерн на долгие задачи веб- и мобильных агентов. Ключевой вклад — синтетические данные планов: генератор размеченных траекторий производит обучающие данные, где план явен. Используется для дообучения моделей-планировщиков, которые продолжают работать после 30–50 шагов на задачах вроде WebArena, где одна траектория ReAct теряет связность.

### Что выбрать

| Pattern | When |
|---------|------|
| ReAct | Короткие задачи, неизвестная среда, нужна реактивная обработка исключений |
| ReWOO | Структурированные задачи с известными инструментами, чувствительность к токенам, параллелизуемые доказательства |
| Plan-and-Execute | Как ReWOO, но с репланированием после частичного выполнения |
| Plan-and-Act | Долгие задачи (>30 шагов), веб/мобильные устройства/computer-use |
| Tree of Thoughts | Поиск стоит своей цены (Урок 04) |

Рекомендация Anthropic от декабря 2024: начинайте с самого простого. Если задача — это один вызов инструмента плюс сводка, не стройте ReWOO. Если задача — это исследовательское задание на 40 шагов, не делайте только ReAct.

## Реализация

`code/main.py` реализует игрушечный ReWOO:

- `Planner` — сценарная политика, выдающая DAG плана из промпта.
- `Worker` — диспетчеризует вызов инструмента каждого узла через реестр.
- `Solver` — сценарная композиция, читающая доказательства и производящая финальный ответ.
- Разрешение зависимостей — ссылки вида `#E1` заменяются на более ранние выходы worker'ов.

Демо отвечает на вопрос «Какое население столицы Франции, округлённое до миллионов?», используя план из двух шагов: (1) найти столицу, (2) найти население, затем решить.

Запустите:

```
python3 code/main.py
```

Трасса показывает сначала полный план, затем результаты worker'ов, затем композицию solver'а. Сравните количество токенов (мы печатаем приблизительный подсчёт символов) с чередующимся запуском в стиле ReAct — ReWOO выигрывает на такой структурированной задаче.

## Применение

LangGraph поставляет Plan-and-Execute как рецепт (`create_react_agent` для ReAct, кастомные графы для plan-execute). Flows в CrewAI кодируют паттерн напрямую: вы определяете задачи заранее, и DAG Flow выполняет их. Подход синтетических данных Plan-and-Act пока в основном исследовательский; паттерн исполнения (явный DAG плана) идёт в продакшен через LangGraph и CrewAI Flows.

## Упражнения

1. Параллелизуйте выполнение worker'ов для независимых узлов плана. Что это даёт на DAG из 6 узлов с 2 параллельными группами?
2. Добавьте узел реплановщика, который срабатывает, если любой worker возвращает ошибку. Какое минимальное изменение делает ReWOO Plan-and-Execute?
3. Замените `Planner` маленькой моделью (класса 7B) и оставьте `Solver` на модели frontier-класса. Сравните итоговое качество — где раздельность отказывает?

5. Перенесите игрушечную реализацию на форму траектории Plan-and-Act: план — это последовательность, а не DAG. Какие компромиссы меняются?

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|--------|--------------------|-------------------------------|
| ReWOO | «Рассуждение без наблюдений» | Сначала составить план, затем параллельно собрать доказательства и получить решение — в промпте планировщика нет наблюдений |
| Plan-and-Execute | «Паттерн plan-execute от LangChain» | ReWOO с опциональным узлом репланировщика после выполнения |
| Plan-and-Act | «Масштабированный plan-execute» | Явное разделение планировщика и исполнителя с синтетическими обучающими данными планов для долгих задач |
| Ссылка на доказательство | «#E1, #E2, ...» | Заполнитель узла плана, который во время диспетчеризации заменяется результатом предыдущего worker'а |
| Дистилляция планировщика | «Маленький планировщик, большой исполнитель» | Дообучение маленькой модели на трассах планировщика от большого учителя |
| Эффективность использования токенов | «Меньше циклов обращения» | В 5 раз меньше токенов на HotpotQA по сравнению с ReAct согласно статье |
| Исполнитель DAG | «Топологический диспетчер» | Выполняет узлы плана в порядке зависимостей; на каждом уровне — параллельно |
