# Сравнение стратегий разбиения на фрагменты

> Разбиение на фрагменты определяет, что вообще сможет найти ваш ретривер. Ошибётесь с границами — и никакая модель эмбеддингов, никакой реранкер, никакая LLM не исправят повреждённый результат ниже по конвейеру.

**Тип:** Build**Языки:** Python**Предварительные требования:** Фаза 11 уроки 04 (embeddings), 06 (RAG), 07 (advanced RAG); Фаза 19 Track B foundations (уроки 20-29)**Время:** ~90 минут
## Цели обучения
- Реализовать с нуля пять стратегий разбиения на фрагменты: fixed-window, по предложениям, рекурсивное разбиение, семантическую кластеризацию и структурное разбиение по заголовкам markdown.
- Измерить recall@k на фикстурном корпусе с эталонными (gold-labeled) диапазонами ответов и объяснить, почему одна стратегия побеждает на прозе, а другая — на технических документах.
- Прочитать распределение длин фрагментов и распознать характерные для каждой стратегии режимы отказа: осиротевшие предложения, разрезы посреди символа, фрагменты, состоящие только из заголовка, семантический дрейф.
- Выбрать стратегию по умолчанию для нового корпуса без запуска бенчмарка, изучив три свойства: тип документа, среднюю длину абзаца и наличие в формате явной структуры.

## Проблема

Любой RAG-конвейер начинается с разрезания исходных документов на части, достаточно маленькие, чтобы модель эмбеддингов могла их обработать, и достаточно большие, чтобы каждая часть несла законченную мысль. Выбор места разреза — не гиперпараметр. Это верхняя граница того, что ретривер вообще может вернуть.

Запрос вида «как выглядит порог аварийного прерывания бюджета» может быть удовлетворён, только если фрагмент, содержащий этот порог, доступен для поиска. Если разбиение с фиксированным окном отрезало значение порога от окружающего контекста, эмбеддинг попадает в другой кластер, оценка BM25 падает, реранкеры видят шум, а ответ, сгенерированный LLM, оказывается неверным. Статья 2024 года «LongRAG: Enhancing Retrieval-Augmented Generation with Long-context LLMs» зафиксировала абсолютное колебание recall при поиске на 35 процентных пунктов исключительно из-за выбора способа разбиения на фрагменты. Последующая работа 2025 года о контекстных заголовках фрагментов сократила разрыв, но не устранила его.

В этом уроке пять стратегий строятся бок о бок, прогоняются на фикстурном корпусе с эталонными диапазонами ответов, а показатели recall вы читаете сами.

### Fixed-window (фиксированное окно)

Грубый базовый вариант. Разрез каждые N символов. Опционально с перекрытием, чтобы предложение, разрезанное в позиции N, целиком появлялось внутри фрагмента, начинающегося с позиции N - overlap. Быстро, детерминированно, ужасно на границах. Используйте как контрольную точку, а не как вариант по умолчанию.

### Sentence (по предложениям)

Разбиение по границам предложений с помощью регулярного выражения или простого конечного автомата. Одно или несколько предложений упаковываются во фрагмент до целевого бюджета символов. Не разрезает слово посередине. Всё ещё разрезает посреди абзаца и посреди раздела. Вариант по умолчанию во многих ранних RAG-конвейерах и разумный выбор для прозы без иной структуры.

### Recursive split (рекурсивное разбиение)

Иерархическая стратегия, популяризированная библиотеками 2023 года. Сначала пробуем разбить по самому сильному разделителю (двойной перевод строки, абзац), затем переходим к следующему (одиночный перевод строки), затем к предложениям, затем к символам. Рекурсия завершается, когда фрагмент укладывается в бюджет. Сильна на документах с непоследовательной структурой, потому что адаптируется по регионам.

### Semantic clustering (семантическая кластеризация)

Эмбеддинг каждого предложения. Кластеризация смежных предложений, разделяющих тематический центроид. Разрез каждый раз, когда текущее сходство с центроидом опускается ниже порога. Границы отражают смысл, а не символы. Медленнее строится и зависит от модели эмбеддингов, но устойчива к документам, меняющим тему внутри абзаца.

### Structural markdown headers (структурное разбиение по заголовкам markdown)

Для документов с явной структурой (markdown, reStructuredText, разделы в стиле RFC с нумерацией) разрез выполняется по границам заголовков. Каждый фрагмент становится заголовком плюс всем, что находится под ним, до следующего заголовка того же или более высокого уровня. Самые маленькие фрагменты на тему, но доступно только когда корпус хорошо оформлен.

### Как recall@k измеряет выбор границ

Эталонный (gold-labeled) запрос несёт точные смещения символов диапазона ответа внутри исходного документа. После разбиения на фрагменты вы спрашиваете: пересекается ли хоть один из top-k фрагментов, возвращённых ретривером, с эталонным диапазоном? Если да, recall@k для этого запроса равен 1. Если нет — 0. Усредните по набору запросов. Запустите то же оценивание для каждой стратегии, и разброс покажет вам, какая политика границ выдерживает именно ваш корпус.

## Реализация

`code/main.py` реализует:

- `fixed_window(text, size, overlap)` - базовый вариант.
- `sentence_chunks(text, target)` - простой упаковщик предложений.
- `recursive_split(text, separators, target)` - иерархическая рекурсия.
- `semantic_chunks(text, similarity_threshold)` - кластеризация на основе центроидов поверх детерминированного mock-эмбеддинга.
- `structural_markdown(text)` - разбиение с учётом заголовков.
- `mock_embed(text, dim)` - эмбеддинг на основе хеша, чтобы цикл работал офлайн.
- `DenseIndex` - та же форма, что используется в уроке о гибридном поиске Phase 19 Track B.
- `eval_recall(strategy, corpus, queries, k)` - цикл сравнения.
- `main()`, который запускает каждую стратегию на фикстурном корпусе и печатает таблицу recall@k.

Запустите:

```bash
python3 code/main.py
```

Вывод - небольшая таблица с одной строкой на стратегию и одним столбцом на k. Sentence проигрывает на структурированной фикстуре. Structural-markdown побеждает на markdown-фикстуре. Recursive держится на смешанной фикстуре, потому что рекурсия адаптируется. Семантическая кластеризация побеждает на фикстуре с прозой, где нет полезных структурных подсказок.

## Режимы отказа, которые таблица не скроет

**Осиротевшие предложения.** Упаковка по предложениям создаёт фрагменты, лишённые тематического предложения. Тогда эмбеддинг указывает на неверный кластер.

**Разрезы посреди символа.** Fixed-window внутри кода или YAML разрежет идентификатор пополам. Обе половины превращаются в эмбеддинг-шум.

**Фрагменты только с заголовком.** Structural markdown выдаёт фрагмент, содержащий только `## Title`. Отфильтровывайте такие или присоединяйте первый абзац следующего фрагмента.

**Семантический дрейф.** Семантическая кластеризация недорезает, если корпус равномерно посвящён одной теме. Фрагмент на 5000 символов упаковывает много конкретных ответов в один размытый эмбеддинг. Сочетайте семантическое разбиение с жёстким ограничением по символам.

**Устаревшие эмбеддинги.** Семантическая кластеризация использует модель эмбеддингов. Если вы меняете модель, вы меняете и фрагменты. Закрепляйте модель для разбиения отдельно от модели поиска либо пересобирайте индекс вместе с ней.

## Выбор варианта по умолчанию без запуска бенчмарка

Три свойства определяют разбиватель по умолчанию для нового корпуса.

| Свойство | Значение | По умолчанию |
|----------|-------|---------|
| Тип документа | Проза без структуры | Recursive split, цель 800 |
| Тип документа | Markdown / RFC / API-документация | Structural markdown |
| Тип документа | Код | AST-aware (вне рамок; см. Phase 19 lesson 02) |
| Длина абзаца | Длинная, одна тема | Sentence, цель 500 |
| Длина абзаца | Короткая, смешанные темы | Semantic, порог 0.6 |

Если сомневаетесь, выбирайте recursive split. Это сильнейший базовый вариант среди одиночных стратегий.

## Применение

Продакшен-паттерны:

- Запускайте оценивание перед выпуском нового конвейера; не доверяйте стратегии, заданной по умолчанию в вашей библиотеке.
- Перезапускайте оценивание при каждой смене модели эмбеддингов или состава корпуса; победитель зависит от корпуса.
- Сохраняйте имя стратегии в метаданных каждого фрагмента, чтобы позже можно было связать регрессии с их источником.

## Упражнения

1. Добавьте шестую стратегию: token-window с использованием `tiktoken` вместо подсчёта символов. Сравните с fixed-window на той же фикстуре.
2. Внедрите долю в 30 процентов блоков кода в прозаическую фикстуру. Перезапустите таблицу. Объясните, почему каждая стратегия, кроме structural markdown, теряет recall.
3. Замените детерминированный эмбеддинг на эмбеддинг реального провайдера вашего проекта. Измерьте изменение recall для семантической кластеризации. Сообщите, расширяется или сужается разброс между стратегиями.
4. Добавьте поле `summary` для каждого фрагмента: однопредложенное описание центроида. Перезапустите оценивание с добавлением summary к телу фрагмента. Измерьте прирост recall.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|------------------------|
| Recall@k | «Мы нашли нужный фрагмент?» | Доля запросов, для которых хотя бы один из top-k фрагментов пересекается с эталонным диапазоном ответа |
| Chunk overlap (перекрытие фрагментов) | «Скользящее окно» | Повторное включение последних N символов предыдущего фрагмента в следующий фрагмент |
| Structural splitter (структурный разбиватель) | «Фрагменты с учётом заголовков» | Разрез по границам H1/H2/H3; текст заголовка входит в состав фрагмента |
| Semantic chunker (семантический разбиватель) | «Фрагменты с учётом темы» | Эмбеддинг предложений, кластеризация по сходству центроидов, разрез при дрейфе |
| Centroid drift (дрейф центроида) | «Смена темы» | Косинусное сходство между текущим средним и следующим предложением опускается ниже порога |
