# Капстоун 16 — автономный агент GitHub Issue-to-PR

> Пометьте issue меткой — получите PR: так выглядит продукт с автономным агентом для написания кода образца 2026 года. Агент запускается в облачной песочнице, проверяет, что тесты проходят, и публикует готовый к ревью PR с обоснованием. AWS Remote SWE Agents, Cursor Background Agents, OpenAI Codex cloud и Google Jules — все они предлагают такой сценарий. Сложные части — это автоматическое воспроизведение окружения сборки репозитория, предотвращение утечки учётных данных, соблюдение бюджетов на репозиторий и гарантия того, что агент не может выполнить force-push. Этот капстоун строит self-hosted-версию и сравнивает её по стоимости и доле успешных прохождений с хостируемыми альтернативами.

## Проблема

Асинхронный облачный агент для кодирования — отдельная категория продуктов по сравнению с интерактивными агентами для написания кода (капстоун 01). UX здесь — это метка GitHub. Вы помечаете issue меткой `@agent fix this`, воркер поднимается в облачной песочнице, клонирует репозиторий, запускает тесты, редактирует файлы, проверяет результат и открывает PR с обоснованием агента в теле. Никакого интерактивного цикла, никакого терминала. AWS Remote SWE Agents, Cursor Background Agents, OpenAI Codex cloud, Google Jules и Factory Droids — все они сходятся к этой модели.

Инженерные сложности здесь конкретны: воспроизведение окружения (агенту приходится собирать репозиторий с нуля, без закешированного образа для разработки), нестабильные тесты (flaky tests) (их нужно перезапускать или изолировать), ограничение области действия учётных данных (GitHub App с минимальным набором прав с точной детализацией), обеспечение бюджета на репозиторий в день и политика запрета force-push. Капстоун измеряет долю успешных прохождений, стоимость и безопасность в сравнении с хостируемыми альтернативами.

## Концепция

Триггер — это GitHub webhook (метка issue или комментарий к PR). Диспетчер помещает задачу в очередь на ECS Fargate или Lambda. Воркер затягивает репозиторий в песочницу Daytona или E2B с обобщённым Dockerfile, выведенным из репозитория (язык, фреймворк). Агент запускает цикл mini-swe-agent или SWE-agent v2 поверх Claude Opus 4.7 или GPT-5.4-Codex. Он итерирует: читает код, предлагает исправление, применяет патч, запускает тесты.

Верификация — это ступень допуска. Полный CI должен пройти в песочнице до того, как откроется PR. Вычисляется дельта покрытия тестами (coverage delta); если она отрицательная сверх порога, PR всё равно открывается, но получает метку `needs-review`. Агент публикует обоснование как описание PR, а также ветку обсуждения `@agent`, в которой ревьюер может запросить доработки.

Безопасность разграничена через две разные поверхности GitHub: приложение (App) выдаёт недолговечный токен установки с правами `workflows: read` и узкими областями действия для contents/PR репозитория; защита веток (branch protection) (а не права приложения) обеспечивает соблюдение правил «никаких прямых записей в `main`» и «никакого force-push» — приложение никогда не добавляется в список исключений (bypass list). Доступ только для чтения, ограниченный путём `.github/workflows`, не является реальным примитивом GitHub App, поэтому allow-list агента на редактирование файлов должен обеспечивать это на уровне воркера. Потолки бюджета на репозиторий в день обеспечиваются на уровне диспетчера (например, максимум 5 PR на репозиторий в день, $20 за PR).

## Архитектура

```
GitHub issue labeled `@agent fix` or PR comment
            |
            v
    GitHub App webhook -> AWS Lambda dispatcher
            |
            v
    ECS Fargate task (or GitHub Actions self-hosted runner)
       - pull repo
       - infer Dockerfile (language, package manager)
       - Daytona / E2B sandbox with target runtime
       - clone -> git worktree -> agent branch
            |
            v
    mini-swe-agent / SWE-agent v2 loop
       Claude Opus 4.7 or GPT-5.4-Codex
       tools: ripgrep, tree-sitter, read/edit, run_tests, git
            |
            v
    verify CI passes in-sandbox + coverage delta check
            |
            v (verified)
    git push + open PR via GitHub App
       PR body = rationale + diff summary + trace URL
       label: needs-review
            |
            v
    operator reviews; can @-mention agent for follow-ups
```

## Стек

- Триггер: GitHub App с токеном с точной детализацией прав; приёмник webhook через Lambda или Fly.io
- Воркер: задача ECS Fargate (или self-hosted runner GitHub Actions)
- Песочница: Daytona devcontainer или E2B sandbox на задачу
- Цикл агента: базовый mini-swe-agent или SWE-agent v2 поверх Claude Opus 4.7 / GPT-5.4-Codex
- Поиск: repo-map на tree-sitter + ripgrep
- Верификация: полный CI в песочнице + гейт по дельте покрытия
- Наблюдаемость: Langfuse с архивом трассировок на каждый PR, привязанным из тела PR
- Бюджет: дневной потолок в долларах на репозиторий; максимум PR на репозиторий в день

## Реализация

1. **GitHub App.** Токен установки с точной детализацией прав: issues read+write, pull_requests write, contents read+write, workflows read. Защита веток (единственная поверхность, способная на это) обеспечивает соблюдение правил «никакого прямого push в `main`» и «никакого force-push»; приложение не входит в список исключений. Воркер обеспечивает соблюдение правила «никаких записей внутри `.github/workflows`» как проверку по allow-list для предложенного diff, поскольку права GitHub App не привязаны к путям.

2. **Приёмник webhook.** Функция Lambda принимает webhook-события по меткам issue / комментариям к PR. Фильтрует по метке `@agent fix this`. Ставит задачу в очередь SQS.

3. **Диспетчер.** Извлекает задачи из SQS. Обеспечивает соблюдение бюджета на репозиторий в день. Поднимает задачу ECS Fargate с URL репозитория, телом issue и свежей песочницей Daytona.

4. **Определение окружения.** Определите язык (Python, Node, Go, Rust) и менеджер пакетов (uv, pnpm, go mod, cargo). Сгенерируйте Dockerfile на лету, если он отсутствует.

5. **Цикл агента.** mini-swe-agent или SWE-agent v2 с Claude Opus 4.7. Инструменты: ripgrep, repo-map на tree-sitter, read_file, edit_file, run_tests, git. Жёсткие ограничения: $20 стоимость, 30 минут по времени выполнения (wall-clock), 30 ходов агента.

6. **Верификация.** После завершения цикла запустите полный набор тестов в песочнице. Вычислите дельту покрытия через jacoco / coverage.py. Если CI красный: остановитесь, не открывайте PR. Если покрытие падает более чем на 2%: откройте PR с меткой `needs-review`.

7. **Публикация PR.** Запушьте ветку агента. Откройте PR через GitHub API с указанием: заголовка, обоснования, сводки diff, URL трассировки, стоимости, числа ходов.

8. **Гигиена учётных данных.** Воркер работает с недолговечным токеном установки GitHub App. Логи очищаются от секретов перед архивацией.

9. **Оценивание.** 30 подготовленных внутренних issue разной сложности. Измерьте долю успешных прохождений, качество PR (размер diff, стиль, покрытие), стоимость, задержку. Сравните с Cursor Background Agents и AWS Remote SWE Agents на тех же issue.

## Упражнения

1. Добавьте режим «исправить нестабильный тест»: метка `@agent stabilize-flake TestX` запускает тест 50 раз в песочнице и предлагает минимальное изменение, которое его стабилизирует.

2. Сравните стоимость с Cursor Background Agents на трёх общих issue. Сообщите, какой инструмент выигрывает и где.

3. Реализуйте дашборд бюджета: стоимость на репозиторий в день, стоимость на пользователя. Оповещайте об аномалиях.

4. Постройте режим «dry-run», который открывает черновик PR без запуска CI, чтобы ревьюеры могли дёшево изучить план.

5. Добавьте политику хранения: ветки PR старше 7 дней без слияния удаляются автоматически.

## Ключевые термины

| Термин | Что говорят люди | Что это означает на самом деле |
|------|-----------------|------------------------|
| GitHub App | «Идентичность бота с разграниченными правами» | Приложение с правами с точной детализацией + недолговечный токен установки |
| Async cloud agent (асинхронный облачный агент) | «Фоновый агент» | Неинтерактивный воркер, который выполняется в облачной песочнице, а не в терминале |
| Environment inference (определение окружения) | «Синтез Dockerfile» | Определение языка и менеджера пакетов, генерация Dockerfile при его отсутствии |
| Verification (верификация) | «CI в песочнице» | Запуск полного набора тестов внутри воркера до открытия PR |
| Coverage delta (дельта покрытия) | «Сохранение покрытия» | Изменение процента покрытия тестами от базовой ветки к ветке агента |
| Per-repo budget (бюджет на репозиторий) | «Дневной потолок» | Лимит в долларах и по числу PR, обеспечиваемый на уровне диспетчера |
| Rationale (обоснование) | «Объяснение в теле PR» | Сводка агента о том, что изменилось и почему; обязательна в теле PR |
