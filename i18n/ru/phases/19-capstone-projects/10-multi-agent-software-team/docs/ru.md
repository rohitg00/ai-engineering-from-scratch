# Капстоун 10 — мультиагентная команда разработки ПО

> К 2026 году сложился единый облик мультиагентной команды разработки: архитектор планирует, N кодеров работают параллельно в собственных worktree, ревьюер пропускает изменения, тестировщик проверяет результат. Архитектура «фабрики» SWE-AF, ролевые промпты MetaGPT, типизированный граф акторов AutoGen 0.4, Devin от Cognition и Droids от Factory пришли к нему независимо друг от друга. Параллельные worktree превращают астрономическое время (wall-clock) в пропускную способность. Общее состояние и протоколы передачи становятся поверхностью отказа. Задача капстоуна — построить такую команду, оценить её на SWE-bench Pro и сообщить, какие передачи ломаются и как часто.

**Тип:** Capstone**Языки:** Python / TypeScript (agents), Shell (worktree scripts)**Предварительные требования:** Фаза 11 (LLM engineering), Фаза 13 (tools), Фаза 14 (agents), Фаза 15 (autonomous), Фаза 16 (multi-agent), Фаза 17 (infrastructure)**Задействованные фазы:** P11 · P13 · P14 · P15 · P16 · P17
**Время:** 40 часов
## Проблема

Одноагентные харнессы для написания кода упираются в потолок на крупных задачах. Не потому, что отдельный агент слаб, а потому, что контекст в 200k токенов не может одновременно вместить план архитектуры, четыре параллельных среза кодовой базы, комментарии ревьюера и вывод тестов. Мультиагентные фабрики разбивают задачу: архитектор владеет планом, кодеры владеют реализацией в параллельных worktree, ревьюер пропускает изменения, тестировщик проверяет. Архитектура «фабрики» SWE-AF, роли MetaGPT, типизированный граф акторов AutoGen — все три формулировки описывают одну и ту же форму.

Поверхность отказа — это передача (handoff). Архитектор планирует то, что кодеры не могут реализовать. Кодеры выдают конфликтующие диффы. Ревьюер одобряет галлюцинированное исправление. Тестировщик попадает в состояние гонки с кодером, который ещё не закончил писать код. Вам предстоит построить одну из таких команд, прогнать её на 50 задачах SWE-bench Pro, отследить каждую передачу и опубликовать разбор инцидентов (post-mortem).

## Концепция

Роли — это типизированные агенты. **Архитектор** (Claude Opus 4.7) читает issue, пишет план и разбивает его на подзадачи с явными интерфейсами. **Кодеры** (Claude Sonnet 4.7, N параллельных инстансов, каждый в собственном `git worktree` + песочнице Daytona) реализуют подзадачи независимо друг от друга. **Ревьюер** (GPT-5.4) читает объединённый дифф и либо одобряет его, либо запрашивает конкретные изменения. **Тестировщик** (Gemini 2.5 Pro) запускает набор тестов изолированно и сообщает pass/fail вместе с артефактами.

Коммуникация идёт через общую доску задач (task board) на основе файлов или Redis. Каждая роль забирает задачи, которые ей разрешено обрабатывать. Передачи — это типизированные сообщения протокола A2A. Вопросы координации: разрешение конфликтов слияния (роль координатора или автоматическое трёхстороннее слияние), синхронизация общего состояния (план фиксируется, как только кодеры приступают к работе; повторное планирование — отдельное событие) и контроль со стороны ревьюера (ревьюер не может одобрить собственные изменения или изменения, которые он сам предложил).

Скрытая цена — усиление расхода токенов (token amplification). Каждая граница между ролями добавляет промпты-сводки и контекст передачи. Прогон, который у одного агента занял бы 40 ходов, у четырёх ролей суммарно превращается в 160 ходов. Рубрика оценки прицельно взвешивает эффективность по токенам относительно одноагентного базового уровня, потому что вопрос не в том, «работает ли мультиагентный подход», а в том, «выигрывает ли он в пересчёте на доллар».

## Архитектура

```
GitHub issue URL
      |
      v
Architect (Opus 4.7)
   reads issue, produces plan with subtasks + interfaces
      |
      v
Task board (file / Redis)
      |
   +-- subtask 1 ---+-- subtask 2 ---+-- subtask 3 ---+-- subtask 4 ---+
   v                v                v                v                v
Coder A          Coder B          Coder C          Coder D          (4 parallel)
 (Sonnet)         (Sonnet)         (Sonnet)         (Sonnet)
 worktree A       worktree B       worktree C       worktree D
 Daytona          Daytona          Daytona          Daytona
      |                |                |                |
      +--------+-------+-------+--------+
               v
           merge coordinator  (three-way merge + conflict resolution)
               |
               v
           Reviewer (GPT-5.4)
               |
               v
           Tester  (Gemini 2.5 Pro)  -> passes? -> open PR
                                     -> fails?  -> route back to coder
```

## Стек

- Оркестрация: LangGraph с общим состоянием + подграфами для каждого агента
- Обмен сообщениями: протокол A2A (Google, 2025) для типизированных межагентных сообщений
- Модели: Opus 4.7 (архитектор), Sonnet 4.7 (кодеры), GPT-5.4 (ревьюер), Gemini 2.5 Pro (тестировщик)
- Изоляция worktree: `git worktree add` на каждого кодера + песочница Daytona
- Координатор слияния: собственное трёхстороннее слияние + разрешение конфликтов силами LLM
- Оценивание: SWE-bench Pro (50 issue), сценарии SWE-AF, HumanEval++ для юнит-тестов
- Наблюдаемость: Langfuse со спанами, размеченными по роли, учёт токенов по каждому агенту
- Развёртывание: K8s, где каждая роль — отдельный Deployment + HPA по объёму бэклога

## Реализация

1. **Доска задач.** JSONL-файл с типизированными сообщениями: `plan_request`, `subtask`, `diff_ready`, `review_needed`, `test_needed`, `approved`, `rejected`, `replan_needed`. Агенты подписываются на теги.

2. **Архитектор.** Читает issue на GitHub, запускает Opus 4.7 с шаблоном плана, требующим явных интерфейсов подзадач (затрагиваемые файлы, публичные функции, влияние на тесты). Выпускает одно сообщение `plan_request` с DAG подзадач.

3. **Кодеры.** N параллельных воркеров, каждый забирает одну подзадачу с доски. Каждый порождает свежую ветку через `git worktree add` и песочницу Daytona. Реализует подзадачу. Выпускает `diff_ready` с патчем и изменениями в тестах.

4. **Координатор слияния.** Когда все кодеры закончили, выполняет трёхстороннее слияние N веток в промежуточную (staging) ветку. Разрешение конфликтов силами LLM применяется только при пересечении на уровне файлов.

5. **Ревьюер.** GPT-5.4 читает объединённый дифф. Не может одобрить дифф, который сам же написал. Выпускает `approved` (без действий) либо `review_feedback` с конкретными запросами на изменения, направленными обратно нужному кодеру.

6. **Тестировщик.** Gemini 2.5 Pro запускает набор тестов в чистой песочнице. Собирает артефакты. Выпускает `test_passed` или `test_failed` со стектрейсами. Упавшие тесты возвращаются кодеру, владеющему сломанной подзадачей.

7. **Учёт передач.** Каждое сообщение, пересекающее границу роли, получает спан в Langfuse с размером полезной нагрузки и использованной моделью. Вычислите усиление расхода токенов на подзадачу (coder_tokens + reviewer_tokens + tester_tokens + architect_share / coder_tokens).

8. **Оценивание.** Прогоните на 50 issue из SWE-bench Pro. Сравните pass@1 и стоимость в долларах за решённую задачу с одноагентным базовым уровнем (один Sonnet 4.7 в единственном worktree).

9. **Разбор инцидентов.** Для каждой провалившейся задачи определите, какая передача сломалась (слишком расплывчатый план, конфликт слияния, ложное одобрение ревьюера, флаки тестировщика). Постройте гистограмму отказов по типам передач.

## Упражнения

1. Внедрите в дифф явный баг посреди прогона (лишний `return None` перед основным телом функции). Измерьте долю ложных одобрений ревьюера. Настраивайте промпт ревьюера, пока доля ложных одобрений не опустится ниже 5%.

2. Сократите число кодеров до двух (архитектор + кодер + ревьюер + тестировщик, кодер выполняет две подзадачи последовательно). Сравните астрономическое время (wall-clock) и долю успешных решений.

3. Замените координатора слияния ограничением «один писатель» (подзадачи затрагивают непересекающиеся наборы файлов). Измерьте, насколько это увеличивает нагрузку планирования на архитектора.

4. Замените ревьюера с GPT-5.4 на Claude Opus 4.7. Измерьте долю ложных одобрений и изменение стоимости токенов.

5. Добавьте пятую роль: документатор (Haiku 4.5). После ревью он готовит запись в changelog. Оцените, оправдывает ли качество документации дополнительный расход токенов.

## Ключевые термины

| Термин | Что говорят люди | Что это означает на самом деле |
|------|-----------------|------------------------|
| Parallel worktree (параллельный worktree) | «Изолированная ветка» | `git worktree add`, создающий отдельное рабочее дерево для каждого кодера |
| Task board (доска задач) | «Общая шина сообщений» | Файловое или Redis-хранилище типизированных сообщений, на которые подписываются агенты |
| Handoff (передача) | «Граница роли» | Любое сообщение, пересекающее границу контекста одной роли и переходящее к другой |
| Token amplification (усиление расхода токенов) | «Накладные расходы мультиагентного подхода» | Суммарные токены по всем ролям, делённые на токены одного агента для той же задачи |
| A2A protocol | «Агент-агенту» | Спецификация Google 2025 года для типизированных межагентных сообщений |
| Merge coordinator (координатор слияния) | «Интегратор» | Компонент, который выполняет трёхстороннее слияние и разрешает конфликты |
| False approval (ложное одобрение) | «Галлюцинация ревьюера» | Ревьюер одобряет дифф с известными багами |
