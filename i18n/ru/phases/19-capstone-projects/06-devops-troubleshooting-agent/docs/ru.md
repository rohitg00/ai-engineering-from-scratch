# Капстоун 06 — Агент устранения неполадок DevOps для Kubernetes

> DevOps Agent от AWS вышел в GA, Resolve AI опубликовала свои плейбуки для K8s, NeuBird продемонстрировала семантический мониторинг, а Metoro привязала AI SRE к SLO на уровне отдельных сервисов. Производственная форма устоялась: срабатывает вебхук оповещения, агент читает телеметрию, обходит граф объектов K8s, ранжирует гипотезы о первопричине и публикует в Slack сводку с кнопками подтверждения. По умолчанию — только чтение. Каждое исправление проходит подтверждение человеком. Этот капстоун — именно такой агент, оценённый на 20 синтетических инцидентах и сопоставленный с агентом AWS на трёх общих кейсах.

## Проблема

Нарратив SRE 2025–2026 годов свёлся к формуле: «AI-агенты проводят триаж инцидентов, люди подтверждают исправления». AWS DevOps Agent, Resolve AI, NeuBird, Metoro, PagerDuty AIOps — все они поставляют эту схему в продакшен. Агент читает метрики Prometheus, логи Loki, трейсы Tempo, kube-state-metrics и граф знаний объектов K8s. Он формирует ранжированную гипотезу о первопричине с телеметрическими ссылками менее чем за пять минут. Он никогда не выполняет деструктивные команды без явного подтверждения человеком через Slack.

Основная сложность — в определении границ и безопасности, а не в рассуждении. Агенту нужна RBAC-поверхность с доступом только на чтение по умолчанию, защищённый сервер инструментов MCP и журналы аудита каждой команды — рассмотренной и выполненной. Он должен понимать, когда выходит за пределы своей компетенции, и эскалировать. И он должен работать достаточно дёшево, чтобы каскады OOM-kill не выливались в счёт за агента в $5k.

## Концепция

Агент работает с графом знаний. Узлы — это объекты K8s (Pods, Deployments, Services, Nodes, HPAs, PVCs) и источники телеметрии (серии Prometheus, потоки Loki, трейсы Tempo). Рёбра кодируют владение (Pod -> ReplicaSet -> Deployment), планирование (Pod -> Node) и наблюдение (Pod -> серия Prometheus). Граф поддерживается в актуальном состоянии синхронизацией kube-state-metrics и пересэмплируется при каждом оповещении.

Когда срабатывает оповещение, агент определяет первопричину, начиная с затронутого объекта. Он обходит рёбра, извлекает нужные срезы телеметрии (за последние 15 минут) и формирует гипотезу. Гипотеза ранжируется по силе доказательств: сколько телеметрических ссылок её подтверждают, насколько они свежие и насколько специфичны. Три лучшие гипотезы отправляются в Slack с визуализациями пути по графу и кнопками подтверждения для действий по исправлению.

Исправления проходят через шлюз подтверждения. Разрешённые по умолчанию действия — только чтение. Деструктивные действия (уменьшение масштаба, откат, удаление Pod) требуют подтверждения в Slack; хуки отката ArgoCD требуют токена авторизации, которым агент никогда не владеет. Журнал аудита фиксирует каждую команду, которую агент *рассмотрел*, — а не только те, что были выполнены, — поэтому в процессе проверки выявляются «near-miss»: случаи, которых едва удалось избежать.

## Стек

- Источники наблюдаемости: Prometheus, Loki, Tempo, kube-state-metrics
- Граф знаний: Neo4j (управляемый) или kuzu (встроенный) для объектов K8s и рёбер телеметрии
- Агент: LangGraph со списком разрешений (allow-list) для каждого инструмента, по умолчанию только чтение
- Транспорт инструментов: FastMCP поверх StreamableHTTP; отдельный сервер для деструктивных инструментов за шлюзом подтверждения
- Модели: Claude Sonnet 4.7 для рассуждений о первопричине, Gemini 2.5 Flash для суммаризации логов
- Исправление: вебхук отката ArgoCD, эскалация PagerDuty, карточка подтверждения Slack
- Аудит: структурированный журнал только на добавление (рассмотрено, выполнено, подтверждено, результат)
- Развёртывание: развёртывание K8s со своей узкой ролью RBAC; отдельное пространство имён

## Реализация

1. **Приём данных графа.** Синхронизируйте kube-state-metrics в Neo4j/kuzu каждые 30 секунд. Узлы: Pod, Deployment, Node, Service, PVC, HPA. Рёбра: OWNED_BY, SCHEDULED_ON, EXPOSES, MOUNTS, SCALES. Рёбра телеметрического наложения: OBSERVED_BY (Pod наблюдается серией Prometheus).

2. **Приёмник оповещений.** Конечная точка FastAPI, принимающая вебхуки PagerDuty или Alertmanager. Извлеките затронутые объекты и нарушение SLO.

3. **Поверхность инструментов только для чтения.** Оберните kubectl, Prometheus query, Loki logql, Tempo traceql через FastMCP. У каждого инструмента — узкий RBAC-глагол ("get", "list", "describe"). Никаких "delete", "exec", "scale" на сервере по умолчанию.

4. **Агент определения первопричины.** LangGraph с тремя узлами: `sample` извлекает срез телеметрии за последние 15 минут, `walk` запрашивает граф на предмет соседних объектов, `hypothesize` формирует ранжированных кандидатов на первопричину с телеметрическими ссылками.

5. **Оценка доказательств.** У каждой гипотезы есть оценка = recency * specificity * graph-path length inverse * citation count. Возвращайте три лучшие.

6. **Сводка в Slack.** Опубликуйте вложение с гипотезой, визуализацией пути по графу (изображение подграфа, отрисованное на сервере) и кнопками подтверждения максимум для одного действия по исправлению.

7. **Шлюз исправлений.** Деструктивные инструменты (уменьшение масштаба, откат, удаление) находятся на втором сервере MCP за токеном подтверждения. Агент может вызывать их только после того, как карточка в Slack подтверждена человеком.

8. **Журнал аудита.** JSONL только на добавление: для каждой кандидатной команды фиксируйте, была ли она рассмотрена, была ли выполнена, кто её подтвердил. Отправляйте в S3 ежедневно.

9. **Набор синтетических инцидентов.** Постройте 20 сценариев: каскад OOMKill, флаппинг DNS, трэшинг HPA, заполнение PVC, шумный сосед, неисправный sidecar, неудачный rollout ConfigMap, ротация сертификата, image-pull backoff и т. д. Оцените агента по точности определения первопричины и времени до гипотезы.

```

```

## Поставка

`outputs/skill-devops-agent.md` — результат поставки. При наличии кластера K8s и источника оповещений агент формирует ранжированные гипотезы о первопричине и процесс исправления, управляемый через Slack.

| Вес | Критерий | Как измеряется |

| 20 | Объяснимость | У каждой гипотезы есть пути по графу и телеметрические ссылки |
| 15 | Полнота интеграции | Сквозная работа PagerDuty, Slack, ArgoCD, Prometheus |
| **100** | | |

## Упражнения

1. Прогоните своего агента на тех же трёх инцидентах, на которых демонстрируется DevOps Agent от AWS. Опубликуйте сравнение бок о бок. Сообщите, где агент расходится с эталоном.

2. Добавьте аудит «near-miss», который отмечает любую *рассмотренную* агентом команду, которая была бы деструктивной без подтверждения. Измерьте частоту near-miss за одну неделю.

3. Замените модель для гипотез с Claude Sonnet 4.7 на самостоятельно развёрнутую Llama 3.3 70B. Измерьте разницу в точности RCA и стоимость в долларах на инцидент.

4. Постройте каузальный фильтр: отличайте коррелирующие всплески телеметрии от истинной первопричины. Обучите небольшой классификатор на метках 20 сценариев.

5. Добавьте пробный прогон отката (dry-run): откат ArgoCD на staging-кластере с тем же манифестом. Проверяйте план отката на живом кластере до нажатия кнопки подтверждения в Slack.

## Ключевые термины

| Термин | Что говорят люди | Что это означает на самом деле |
|------|-----------------|------------------------|
| K8s knowledge graph (граф знаний K8s) | «Граф кластера» | Узлы = объекты K8s + серии телеметрии; рёбра = владение, планирование, наблюдение |
| Read-only-by-default (только чтение по умолчанию) | «Ограниченный RBAC» | У служебной учётной записи агента есть только глаголы get/list/describe; деструктивные глаголы находятся на отдельном сервере за подтверждением |
| Audit log (журнал аудита) | «Рассмотрено против выполнено» | Запись только на добавление о каждой кандидатной команде: была ли она выполнена, кто подтвердил |
| Hypothesis ranking (ранжирование гипотез) | «Оценка доказательств» | Recency × specificity × graph-path length inverse × citation count |
| Slack approval card (карточка подтверждения в Slack) | «Шлюз HITL» | Интерактивное сообщение в Slack с кнопками исправления; агент не может продолжить, пока человек не нажмёт кнопку |
| Telemetry citation (телеметрическая ссылка) | «Указатель на доказательство» | Запрос Prometheus, селектор Loki или URL трейса Tempo, подтверждающий утверждение |
| MTTR | «Время до разрешения» | Астрономическое время (wall-clock) от срабатывания оповещения до восстановления SLO |
