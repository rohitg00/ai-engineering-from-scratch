# Janus-Pro: раздельные энкодеры для унифицированных мультимодальных моделей

> У унифицированных мультимодальных моделей есть неизбежное противоречие. Понимание хочет семантических признаков — SigLIP или DINOv2 выдают векторы, насыщенные информацией на уровне концептов. Генерация хочет кодов, удобных для реконструкции, — VQ-токены, из которых можно собрать чёткие пиксели обратно. Эти две цели несовместимы в одном энкодере. Janus (DeepSeek, октябрь 2024) и Janus-Pro (DeepSeek, январь 2025) утверждают, что решение — перестать пытаться: разделить два энкодера. Для обеих задач используется общее тело трансформера, но понимание направляется через SigLIP, а генерация — через VQ-токенизатор. При 7 млрд параметров Janus-Pro превосходит DALL-E 3 по GenEval и показывает результат на уровне LLaVA по MMMU. Этот урок разбирает, почему два энкодера работают там, где один терпит неудачу.

**Тип:** Build
**Языки:** Python (стандартная библиотека, маршрутизация между двумя энкодерами + сигнал общего тела)
**Предварительные требования:** Фаза 12 · 13 (Transfusion), фаза 12 · 14 (Show-o)
**Время:** ~120 минут

## Цели обучения

- Объяснять, почему один общий энкодер жертвует либо качеством понимания, либо качеством генерации.
- Описывать маршрутизацию Janus-Pro: признаки SigLIP на входной стороне для понимания, VQ-токены и на входе, и на выходе для генерации.
- Прослеживать масштабирование смеси данных, благодаря которому Janus-Pro преуспевает там, где Janus не смог.
- Сравнивать раздельную (Janus-Pro), совмещённо-непрерывную (Transfusion) и совмещённо-дискретную (Show-o) архитектуры.

## Проблема

Унифицированные модели делят одно тело трансформера между пониманием и генерацией. Предыдущие попытки (Chameleon, Show-o, Transfusion) используют один визуальный токенизатор для обоих направлений. Токенизатор — это компромисс:

- Оптимизирован для реконструкции (генерация): VQ-VAE захватывает мелкие детали пикселей, но производит токены со слабой семантической связностью.
- Оптимизирован для семантики (понимание): эмбеддинги SigLIP группируют изображения «кот» рядом с токенами «кот», но не позволяют качественную реконструкцию.

Show-o и Transfusion платят за это заметным налогом на качество в одном из направлений. Janus-Pro спрашивает: зачем требовать один токенизатор, если у задач разные потребности?

## Концепция

### Раздельное визуальное кодирование

Архитектура Janus-Pro разделяет два энкодера:

- Путь понимания. Входное изображение → SigLIP-SO400m → двухслойный MLP → тело трансформера.
- Путь генерации. Входное изображение (если обусловливание идёт на существующем изображении) → VQ-токенизатор → ID токенов → тело трансформера.
- Генерация вывода. Токены изображения, предсказанные трансформером → VQ-декодер → пиксели.

Тело трансформера общее. Всё, что находится до и после него, — задаче-специфично.

Входы различаются форматом промпта: тег `<understand>` направляет через SigLIP; `<generate>` направляет через VQ. Либо маршрутизация неявная, исходя из задачи.

### Почему это работает

Функция потерь понимания получает признаки SigLIP, которые предобучение в стиле CLIP настроило на семантическое сходство. Бенчмарки восприятия модели улучшаются по сравнению с Show-o / Transfusion, потому что входные признаки лучше подходят для этой задачи.

Функция потерь генерации получает VQ-токены, которые токенизатор настроил на реконструкцию. Качество изображений улучшается по сравнению с Show-o, потому что коды VQ чисто собираются обратно в пиксели.

Общее тело трансформера видит два входных распределения (SigLIP и VQ) и учится работать с обоими. Утверждение: при достаточном объёме данных и параметров тело поглощает это переключение.

### Масштабирование данных — Janus против Janus-Pro

Janus (оригинал, arXiv 2410.13848) представил разделение, но на малом масштабе (1.3 млрд параметров, ограниченные данные). Janus-Pro (arXiv 2501.17811) масштабировал:

- 7 млрд параметров (против 1.3 млрд).
- 90 млн пар изображение-текст для этапа 1 (согласование) против 72 млн.
- 72 млн для этапа 2 (унифицированный) против 26 млн.
- Добавлены 200 тыс. примеров для обучения на инструкциях по генерации изображений на этапе 3.

Итог: Janus-Pro-7B показывает результат на уровне LLaVA по MMMU (60.3 против ~58) и превосходит DALL-E 3 по GenEval (0.80 против 0.67). Одна открытая модель, конкурентная по обеим сторонам унифицированного спектра.

### JanusFlow — вариант со спрямленным потоком

JanusFlow (arXiv 2411.07975) заменяет путь генерации VQ на путь генерации через спрямленный поток (rectified flow). Теперь для понимания используется SigLIP, а для генерации — спрямленный поток. Потолок качества поднимается ещё выше. Архитектура по-прежнему основана на раздельных энкодерах и общем теле.

### Задача общего тела

Тело трансформера обрабатывает унифицированную последовательность, но с двумя входными распределениями. Его задача:

- Для понимания: потреблять признаки SigLIP + текстовые токены → выдавать текст авторегрессионно.
- Для генерации: потреблять текстовые токены + (опционально VQ-токены изображения) → выдавать VQ-токены изображения авторегрессионно.

У тела нет модально-специфичных весов на уровне блоков. Это текстовый трансформер того же типа, что вы найдёте внутри Qwen или Llama, плюс два входных адаптера.

Интересно, что это означает, что тело Janus-Pro можно было инициализировать из предобученной LLM. Janus-Pro действительно инициализируется из DeepSeek-MoE-7B. Этот выбор важен: LLM привносит способность к рассуждению, которой чисто с нуля обученным унифицированным моделям трудно достичь.

### Сравнение с InternVL-U

InternVL-U (Урок 12.10) — продолжение 2026 года. Оно объединяет:

- Нативное мультимодальное предобучение (бэкбон InternVL3).
- Маршрутизацию с раздельными энкодерами (SigLIP на входе, головы VQ + диффузии на выходе).
- Унифицированное понимание + генерацию + редактирование.

InternVL-U вбирает архитектурное решение Janus-Pro в более крупный фреймворк. Идея раздельных энкодеров теперь стала выбором по умолчанию для унифицированных моделей на масштабе.

### Ограничения

Раздельные энкодеры добавляют архитектурную сложность. Два токенизатора для обучения, два входных пути для поддержки, два набора режимов отказа. Для продуктов, которым не нужна генерация, Janus-Pro избыточно сложна — выбирайте модель понимания семейства LLaVA.

Для продуктов, которым не нужно понимание, Janus-Pro избыточно квалифицирована — выбирайте модель семейства Stable Diffusion 3 / Flux.

Для продуктов, которым нужно и то, и другое, Janus-Pro теперь эталонная открытая архитектура.


## Применяем

`code/main.py` симулирует маршрутизацию Janus-Pro:

- Два имитационных энкодера: в стиле SigLIP (производит 256-мерные семантические векторы) и в стиле VQ (производит целочисленные коды).
- Маршрутизатор промптов, выбирающий энкодер на основе тега задачи.
- Общее тело (заглушка), обрабатывающее последовательности токенов независимо от того, какой энкодер их произвёл.
- Переключение расписания взвешенного сэмплирования от этапа 1 (согласование) к этапу 3 (обучение на инструкциях).

Выведите маршрутизированные пути для 3 примеров: вопрос-ответ по изображению, T2I, редактирование изображения.

## Публикуем

Этот урок производит `outputs/skill-decoupled-encoder-picker.md`. По заданному продукту, которому нужна унифицированная генерация + понимание на уровне, близком к фронтирному, он выбирает Janus-Pro, JanusFlow или InternVL-U с конкретной рекомендацией по масштабу данных.

1. Janus-Pro-7B превосходит DALL-E 3 по GenEval. Объясните, почему открытая модель на 7 млрд параметров может сравниться с фронтирной проприетарной моделью в генерации, но не в понимании.

2. Реализуйте функцию-маршрутизатор: по тексту промпта классифицируйте как `understand` или `generate`. Как обработать неоднозначные промпты вроде «опиши, а затем нарисуй»?

3. JanusFlow заменяет путь VQ на спрямленный поток. Что теперь выводит тело трансформера и что меняется в функции потерь?

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на практике |
|------|-----------------|------------------------|
| Раздельное кодирование | «Два визуальных энкодера» | Отдельный токенизатор или энкодер для каждого направления: семантический — для понимания, реконструктивный — для генерации |
| Общее тело | «Один трансформер» | Единый трансформер обрабатывает вывод любого из энкодеров; модально-специфичных весов нет |
| SigLIP для понимания | «Семантические признаки» | Визуальный энкодер семейства CLIP, дающий богатые концептуальные признаки, но не обеспечивающий качественную реконструкцию |
| VQ для генерации | «Реконструктивные коды» | Векторно-квантованные токены, которые точно декодируются обратно в пиксели |
| JanusFlow | «Вариант со спрямленным потоком» | Janus-Pro с непрерывной генеративной головой на основе согласования потоков вместо VQ |
| Тег маршрутизации | «Тег задачи» | Маркер промпта (`<understand>` / `<generate>`), выбирающий входной энкодер |
