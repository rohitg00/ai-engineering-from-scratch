# Понимание документов и диаграмм

> Документы — это не фотографии. PDF, научная статья, счёт-фактура или рукописная форма обладают вёрсткой, таблицами, диаграммами, сносками, заголовками и семантической структурой, которые простое понимание изображений уловить не может. Стек до появления VLM представлял собой конвейер: Tesseract OCR + LayoutLMv3 + эвристики извлечения таблиц. Волна VLM заменила его моделями без OCR — Donut (2022), Nougat (2023), DocLLM (2023) — которые сразу выдают структурированную разметку. К 2026 году передний край — это просто «подать изображение страницы Claude Opus 4.7 в нативном разрешении 2576px», а структурированный вывод разметки получается без дополнительных усилий. Этот урок разбирает три эпохи развития ИИ для работы с документами.

**Тип:** Build
**Языки:** Python (стандартная библиотека, каркас парсера документов с учётом вёрстки)
**Предварительные требования:** Этап 12 · 05 (LLaVA), этап 5 (NLP)
**Время:** ~180 минут

## Цели обучения

- Объяснить три эпохи ИИ для документов: конвейер OCR, модели без OCR и модели на основе VLM.
- Описать три входных потока LayoutLMv3: текст, вёрстку (bbox), патчи изображения, с единым маскированием.
- Сравнить Donut (без OCR, изображение → разметка), Nougat (научная статья → LaTeX), DocLLM (генеративная модель с учётом вёрстки), PaliGemma 2 (на основе VLM).
- Выбрать модель для работы с документами под новую задачу (счета, научные статьи, рукописные формы, китайские чеки).

## Проблема

«Разберись в этом PDF» — задача обманчиво сложная. Информация распределена по:

- Текстовому содержимому (90% сигнала).
- Вёрстке (заголовки, сноски, боковые панели, двухколоночный формат).
- Таблицам (строки, столбцы, объединённые ячейки).
- Рисункам и диаграммам.
- Рукописным пометкам.
- Шрифтам и типографике (заголовок против основного текста).

Необработанный OCR извлекает текст и теряет всё остальное. Система, которая работает со счетами, должна знать, что «Итого: $1,245» пришло из нижнего правого угла, а не из сноски.

## Концепция

### Эпоха 1 — конвейер OCR (до 2021)

Классический стек:

1. PDF → изображение на каждую страницу.
2. Tesseract (или коммерческий OCR) извлекает текст с ограничивающей рамкой для каждого слова.
3. Анализатор вёрстки определяет блоки (заголовок, таблица, абзац).
4. Распознаватель структуры таблиц разбирает таблицы.
5. Доменные правила + регулярные выражения извлекают поля.

Работает для чистого печатного текста. Ломается на рукописном тексте, перекошенных сканах, сложных таблицах, неанглийских системах письма. Каждый вид сбоя требует отдельного пути обработки исключений.

### TrOCR (2021)

TrOCR (Li et al., arXiv:2109.10282) заменил классическую CNN-CTC от Tesseract на трансформерный энкодер-декодер, обученный на синтетических и реальных изображениях текста. Явный выигрыш на рукописном и многоязычном тексте. По-прежнему конвейер (детектор, затем TrOCR, затем вёрстка), но этап OCR улучшился радикально.

### Эпоха 2 — без OCR (2022–2023)

Первые модели без OCR предлагали полностью отказаться от детекции и напрямую преобразовывать пиксели изображения в структурированный вывод.

Donut (Kim et al., arXiv:2111.15664):
- Трансформер энкодер-декодер, энкодер — Swin-B.
- Вывод — JSON для понимания форм, markdown для суммаризации или любая схема под конкретную задачу.
- Без OCR, без вёрстки, без детекции.

Nougat (Blecher et al., arXiv:2308.13418):
- Обучена специально на научных статьях.
- Вывод — LaTeX / markdown.
- Обрабатывает уравнения, многоколоночную вёрстку, рисунки.
- Модель, к которой обращается каждый парсер arXiv.

Это специалисты, а не универсалы. Donut на научной статье не справляется; Nougat на счёте не справляется.

### LayoutLMv3 (2022)

Другое направление. LayoutLMv3 (Huang et al., arXiv:2204.08387) сохраняет OCR, но добавляет понимание вёрстки:

- Три входных потока: текстовые токены OCR, двумерные ограничивающие рамки для каждого токена, патчи изображения.
- Задача обучения с маскированием по всем трём модальностям (маскированный текст, маскированные патчи, маскированная вёрстка).
- Прикладные задачи: классификация, извлечение сущностей, QA по таблицам.

LayoutLMv3 — пик понимания документов на основе OCR. Силён на формах и счетах. Требует OCR на входе. Лучшая точность эпохи до появления VLM на стандартизированных бенчмарках документов.

### DocLLM (2023)

DocLLM (Wang et al., arXiv:2401.00908) — генеративный «родственник» LayoutLM. Генерирует ответы в свободной форме, обусловленные токенами вёрстки. Лучше подходит для QA по документам; всё ещё зависит от входного OCR.

### Эпоха 3 — на основе VLM (2024+)

В 2024 году VLM стали достаточно хороши, чтобы полностью заменить конвейер. Подать VLM полное изображение страницы в высоком разрешении, задать вопрос, получить ответ.

- LLaVA-NeXT с AnyRes на тайлах 336 работает для небольших документов.
- Qwen2.5-VL с динамическим разрешением нативно обрабатывает 2048+ пикселей.
- Claude Opus 4.7 поддерживает документы 2576px.
- PaliGemma 2 (апрель 2025) обучена специально для документов и рукописного текста.

Разрыв между моделями на основе VLM и конвейером OCR быстро сократился. К 2026 году модели на основе VLM побеждают в следующих задачах:

- Тексте на сценах (рукописный + печатный, смешанные системы письма).
- Сложных таблицах с объединёнными ячейками.
- Математических уравнениях, встроенных в текст.
- Рисунках с текстовыми аннотациями.

Конвейеры OCR по-прежнему выигрывают в:

- Задачах чистого сканирования в огромном масштабе, где важна задержка на страницу.
- Надёжности конвейера (детерминированные сбои против галлюцинаций VLM).
- Регулируемых средах, требующих проверяемого вывода OCR.

### Передний край Claude 4.7 / GPT-5

При нативном входе 2576 пикселей передовые VLM понимают документы с точностью, близкой к человеческой. Цифры бенчмарков начала 2026 года:

- DocVQA: Claude 4.7 ~95.1, PaliGemma 2 ~88.4, Nougat ~77.3, конвейерный LayoutLMv3 ~83.
- ChartQA: Claude 4.7 ~92.2, GPT-4V ~78.
- VisualMRC: Claude 4.7 ~94.

Разрыв закрытых моделей в основном объясняется разрешением и масштабом базовой LLM. Открытые модели на 7B отстают на несколько пунктов, но догоняют.

### Математические уравнения и вывод LaTeX

Научным статьям нужен точный вывод LaTeX для уравнений. Nougat обучена именно этому. VLM, обученные с целевыми значениями LaTeX (Qwen2.5-VL-Math, производные Nougat), выдают пригодный к использованию LaTeX. Без явного обучения LaTeX VLM выдают читаемые, но неточные транскрипции.

Для конвейеров научных статей в 2026 году: сначала пропустить PDF через Nougat, затем VLM на сложных страницах.

### Рукописный текст

По-прежнему самая сложная подзадача. Смешанный печатный и рукописный текст (записи врачей, заполненные формы) — область, где конвейеры OCR всё ещё выигрывают у VLM по стоимости. VLM для чисто рукописного текста продолжают улучшаться (Claude 4.7, PaliGemma 2).

### Рецепт 2026 года

Для нового проекта ИИ для документов:

- Чисто печатные счета в масштабе: LayoutLMv3 + правила, экономично.
- Смешанные документы (научные + рукописные + формы): модель на основе VLM (PaliGemma 2 или Qwen2.5-VL).
- Полная обработка arXiv: Nougat для математики, VLM для рисунков.
- Регуляторная сфера: конвейер OCR + VLM-валидатор для перекрёстной проверки.

## Применяем

`code/main.py`:

- Игрушечный токенизатор с учётом вёрстки: по парам (text, bbox) формирует вход в стиле LayoutLMv3.
- Генератор схем задач в стиле Donut: JSON-шаблон для форм.
- Сравнение бюджетов токенов на страницу для конвейера OCR, Donut, Nougat и модели на основе VLM.

## Упражнения

1. Ваш проект обрабатывает 10 млн счетов в день. Какой стек минимизирует стоимость на страницу без потери точности?

2. Почему LayoutLMv3 превосходит чистые CLIP-VLM в ответах на вопросы по формам, но уступает в распознавании текста на сценах? Чем жертвует поток bbox?

3. Nougat генерирует LaTeX. Предложите тестовый случай, где вывод модели на основе VLM превосходит Nougat по точности LaTeX, и случай, где побеждает Nougat.

4. Прочитайте статью PaliGemma 2 (Google, 2024). Какое ключевое добавление в обучающие данные подняло точность на документах по сравнению с PaliGemma 1?

5. Спроектируйте регуляторно безопасный гибрид: конвейер OCR как основной, VLM как вторичная перекрёстная проверка. Как разрешать расхождения?

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|-----------------|------------------------|
| Конвейер OCR | «В стиле Tesseract» | Поэтапный стек: детекция -> OCR -> вёрстка -> правила; детерминированный, но хрупкий |
| Без OCR | «В стиле Donut» | Трансформер, преобразующий изображение в вывод без явного OCR; единая модель |
| С учётом вёрстки | «LayoutLM» | Вход включает координаты bbox для каждого токена; единое маскирование по модальностям |
| На основе VLM | «Передовая VLM» | Изображение страницы подаётся напрямую в Claude/GPT/Qwen VLM в высоком разрешении; без конвейера |
| DocVQA | «Бенчмарк документов» | Стандарт VQA для документов; самая цитируемая оценка |
| Вывод разметки | «LaTeX / MD» | Формат структурированного вывода вместо свободного текста; обеспечивает последующую автоматизацию |
