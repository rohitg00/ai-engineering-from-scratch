# Долгоживущие фоновые агенты: устойчивое выполнение

> Продакшн-агенты с длинным горизонтом не работают в `while True`. Каждый вызов большой языковой модели (LLM) становится активностью (activity) с контрольной точкой, повтором и воспроизведением. Интеграция Temporal с OpenAI Agents SDK стала общедоступной (GA) в марте 2026 года. Claude Code Routines (Anthropic) запускает вызовы Claude Code по расписанию без постоянного локального процесса. Сессии приостанавливаются при ожидании ввода от человека, переживают развёртывания и возобновляются с последней контрольной точки, привязанной к `thread_id`. За новой эргономикой стоит старый паттерн — оркестрация рабочих процессов — с одним новым элементом: вызовы LLM как недетерминированные активности, которые при восстановлении нужно детерминированно воспроизводить.

**Тип:** Learn
**Языки:** Python (стандартная библиотека, минимальный автомат состояний устойчивого выполнения)
**Предварительные требования:** Этап 15 · 10 (Режимы разрешений), Этап 15 · 01 (Агенты с длинным горизонтом)
**Время:** ~60 минут

## Проблема

Представьте агента, который работает четыре часа. Он вызывает три инструмента, дважды запрашивает у пользователя подтверждение и делает сорок вызовов LLM. На середине пути хост, на котором он работает, перезагружается. Что произойдёт?

- В наивном цикле `while True`: всё теряется. Запуск начинается с нуля. Три вызова инструментов (с реальными побочными эффектами) выполняются повторно. У пользователя снова запрашивают подтверждение того, что он уже одобрил. Сорок вызовов LLM оплачиваются заново.
- При устойчивом выполнении: запуск возобновляется с последней контрольной точки. Уже завершённые активности не выполняются повторно; их результаты воспроизводятся из устойчивого журнала. Пользователю не нужно повторно подтверждать то, что он уже одобрил. Уже выполненные вызовы LLM не оплачиваются заново.

Это тот же паттерн, который движки рабочих процессов поставляют уже десятилетие (Temporal, Cadence, Cherami от Uber). Новое здесь то, что вызовы LLM теперь представляют собой разновидность активности — недетерминированную, дорогую, с побочными эффектами — и они аккуратно вписываются в этот паттерн.

Сквозная тема урока: надёжность на длинном горизонте деградирует (METR фиксирует «35-минутную деградацию» — доля успешных запусков падает примерно квадратично с ростом горизонта). Устойчивое выполнение позволяет запускам длиться дольше, чем поддерживает профиль надёжности, а это новый способ безопасно ошибаться, если конструкция правильная, и небезопасно, если конструкция неправильная.

## Концепция

### Активности, рабочие процессы и воспроизведение

- **Рабочий процесс (workflow)**: детерминированный код оркестрации. Определяет последовательность активностей, ветвления, ожидания. Должен быть детерминированным, чтобы его можно было воспроизвести по журналу событий без неожиданных расхождений.
- **Активность (activity)**: недетерминированная, потенциально неуспешная единица работы. Вызов LLM, вызов инструмента, запись файла, HTTP-запрос. Каждая активность логируется вместе со своими входными данными и (после завершения) выходными данными.
- **Журнал событий (event log)**: устойчивое хранилище-бэкенд. В нём фиксируется каждый старт, завершение, сбой и повтор активности, а также каждое решение рабочего процесса.
- **Воспроизведение (replay)**: при восстановлении код рабочего процесса заново выполняется с начала; каждая уже завершённая активность возвращает свой залогированный результат без повторного выполнения. Реально выполняются только те активности, которые ещё не были завершены.

Это та же форма, что и повторный рендеринг React относительно виртуального DOM, или пересборка Git рабочего дерева из коммитов. Детерминированность в оркестраторе — вот что делает устойчивость дешёвой.

### Почему вызовы LLM вписываются в этот паттерн

Вызовы LLM:
- Недетерминированны (при температуре > 0; даже при температуре 0 наблюдается дрейф между версиями моделей).
- Дороги (по деньгам и по задержке).
- Потенциально неуспешны (ограничения частоты запросов, тайм-ауты).
- Имеют побочные эффекты (если вызывают инструменты).

Это в точности профиль активности. Оборачивание каждого вызова LLM в активность даёт повтор с экспоненциально нарастающей задержкой, контрольные точки при перезапусках и воспроизводимую трассу для отладки.

### Контрольные точки, привязанные к `thread_id`

LangGraph, Microsoft Agent Framework, Cloudflare Durable Objects и Claude Code Routines независимо сошлись на одной и той же форме API: `thread_id` (или его эквивалент) идентифицирует сессию; каждый переход состояния сохраняется в бэкенд (PostgreSQL по умолчанию, SQLite для разработки, Redis для кеша); возобновление читает последнюю контрольную точку.

Выбор бэкенда имеет значение:

- **PostgreSQL**: устойчив, поддерживает запросы, переживает развёртывания. Вариант по умолчанию для LangGraph.
- **SQLite**: только для локальной разработки; теряет данные при смене хоста.
- **Redis**: быстрый, но эфемерный, если не настроены AOF/снапшоты.
- **Cloudflare Durable Objects**: прозрачно распределён; область действия задаётся уникальным ключом; сохраняется от часов до недель.

### Ввод от человека как полноценное состояние

Схема «предложить, затем применить» (propose-then-commit, Урок 15) требует устойчивого состояния «ожидание ввода от человека». Рабочий процесс приостанавливается, внешняя очередь удерживает отложенный запрос, и подтверждение возобновляет выполнение ровно с этой точки. Без устойчивого выполнения это работает без гарантий; с ним подтверждение, полученное ночью, позволяет рабочему процессу продолжить работу утром.

### 35-минутная деградация

METR обнаружила, что у каждого измеренного класса агентов надёжность деградирует после ~35 минут непрерывной работы. Удвоение длительности задачи примерно вчетверо повышает долю сбоев. Устойчивое выполнение не устраняет эту проблему; оно позволяет работать дольше, чем поддерживает профиль надёжности. Безопасный паттерн — сочетать устойчивость с контрольными точками, которые при повторном входе требуют свежего HITL (human-in-the-loop, вмешательства человека), и с аварийными выключателями бюджета (Урок 13), которые ограничивают суммарные вычисления независимо от фактически прошедшего времени.

### Когда устойчивое выполнение — неверный ответ

- Запуски короче нескольких минут без ввода от человека. Накладные расходы превышают выгоду.
- Извлечение информации исключительно в режиме чтения.
- Задачи, где корректность требует завершения в пределах одного контекстного окна (некоторые задачи на рассуждение; некоторая однократная генерация).

## Применение

`code/main.py` реализует минимальный движок устойчивого выполнения на стандартной библиотеке Python. Он поддерживает:

- Декоратор `@activity`, который логирует входные и выходные данные в JSON-журнал событий.
- Функцию рабочего процесса, которая упорядочивает активности в последовательность.
- Функцию `run_or_replay(workflow, event_log)`, которая воспроизводит завершённые активности, не выполняя их заново.

Драйвер моделирует рабочий процесс из трёх активностей, аварийно завершается на середине и показывает (a) наивный повтор, заново выполняющий всё, в сравнении с (b) воспроизведением, которое запускает только недостающую активность.

## **Поставка**

`outputs/skill-durable-execution-review.md` рецензирует предлагаемое развёртывание долгоживущего агента на предмет корректной формы устойчивого выполнения: активности, детерминированность, бэкенд контрольных точек, состояние ожидания ввода от человека и политика HITL при возобновлении.

## Упражнения

1. Запустите `code/main.py`. Понаблюдайте за разницей в количестве выполненных активностей между наивным повтором и воспроизведением. Измените точку аварийного завершения и покажите, как соответственно меняется количество активностей, реально выполняемых при воспроизведении.

2. Переделайте игрушечный движок так, чтобы он явно использовал `thread_id`. Смоделируйте две параллельные сессии, разделяющие один движок, и убедитесь, что их журналы событий не конфликтуют.

3. Возьмите одну активность в игрушечном движке. Введите недетерминированность (метку текущего времени по системным часам внутри решения рабочего процесса). Продемонстрируйте расхождение при воспроизведении. Объясните, как реальные движки справляются с этим (регистрация побочных эффектов, API вида `Workflow.now()`).

4. Прочитайте пост LangChain «Среда выполнения продакшн-агентов глубокого действия». Перечислите каждое состояние, которое сохраняет рантайм, и укажите, какой режим сбоя закрывает каждое из них.

5. Спроектируйте политику контрольных точек для 6-часовой автономной задачи по написанию кода. Где вы будете ставить контрольные точки? Как выглядит возобновление после сбоя? Что потребует свежего HITL?

## Ключевые термины

| Термин | Как его обычно называют | Что он означает на самом деле |
|---|---|---|
| Рабочий процесс | «Скрипт агента» | Детерминированный код оркестрации, который можно воспроизвести по журналу событий |
| Активность | «Шаг» | Недетерминированная единица работы (вызов LLM, вызов инструмента); логируется до и после выполнения |
| Журнал событий | «Хранилище-бэкенд» | Устойчивый журнал каждого перехода состояния |
| Воспроизведение | «Возобновление» | Повторный запуск рабочего процесса; завершённые активности возвращают результаты из журнала без повторного выполнения |
| Контрольная точка | «Точка сохранения» | Сохранённое состояние, привязанное к thread_id; при возобновлении используется самое последнее |
| thread_id | «Ключ сессии» | Идентификатор, ограничивающий область устойчивого состояния |
| 35-минутная деградация | «Деградация надёжности» | По данным METR, доля успешных запусков падает примерно квадратично с ростом горизонта |
| Недетерминированность | «Дрейф при воспроизведении» | Текущее время, случайные значения, вывод LLM; должны регистрироваться как побочные эффекты |
