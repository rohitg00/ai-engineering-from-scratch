# Человек в цикле: «предложить, затем применить»

> Консенсус 2026 года по HITL (human-in-the-loop, участие человека в цикле) конкретен. Это не «агент спрашивает, пользователь нажимает "Одобрить"». Это схема «предложить, затем применить» (propose-then-commit): предложенное действие сохраняется в устойчивом хранилище (durable store) с ключом идемпотентности (idempotency key); предъявляется рецензенту вместе с намерением, происхождением данных (data lineage), затронутыми правами доступа, радиусом поражения (blast radius) и планом отката (rollback); применяется только после положительного подтверждения; после выполнения проверяется, чтобы убедиться, что побочный эффект действительно произошёл. `interrupt()` в LangGraph вместе с контрольными точками PostgreSQL, `RequestInfoEvent` в Microsoft Agent Framework и `waitForApproval()` в Cloudflare реализуют одну и ту же форму. Типовой сбой — это формальное одобрение (rubber-stamp): кнопку «Одобрить?» нажимают без рассмотрения. Задокументированная мера противодействия — схема «запрос-ответ» (challenge-and-response) с явным чек-листом.

**Тип:** Learn
**Языки:** Python (стандартная библиотека, конечный автомат «предложить, затем применить» с идемпотентностью)
**Предварительные требования:** этап 15 · 12 (устойчивое выполнение), этап 15 · 14 (сигнальные ловушки)
**Время:** ~60 минут

## Проблема

Агент совершает действие. Пользователю нужно решить: одобрить или нет. Если решение принимается мгновенно, это, вероятно, не рассмотрение. Если решение структурировано, оно медленное, но заслуживает доверия. Инженерный вопрос в том, как сделать структурированное рассмотрение путём наименьшего сопротивления.

Паттерн HITL эпохи 2023 года — это синхронный запрос: «Агент хочет отправить письмо X с текстом Y — одобрить?» Пользователь нажимает «Одобрить». Все чувствуют, что система безопасна. На практике эта поверхность в основном получает формальные одобрения: пользователи одобряют быстро, одобрения мало что предсказывают, а когда агент ошибается, журнал аудита показывает длинную историю одобрений, которые пользователь не может вспомнить.

Паттерн 2026 года — «предложить, затем применить» — переносит HITL на устойчивую основу, прикрепляет структурированные метаданные и требует положительного применения. Каждый управляемый SDK для агентов поставляет свою версию: `interrupt()` в LangGraph, `RequestInfoEvent` в Microsoft Agent Framework, `waitForApproval()` в Cloudflare. Названия API различаются; форма — нет.

## Концепция

### Конечный автомат «предложить, затем применить»

1. **Предложение.** Агент формирует предложенное действие. Оно сохраняется в устойчивом хранилище (PostgreSQL, Redis, Durable Object). Включает:
   - намерение (зачем агент это делает)
   - происхождение данных (какой источник привёл к этому предложению)
   - затронутые права доступа (какие области действия / файлы / конечные точки)
   - радиус поражения (каков худший сценарий)
   - план отката (если действие применено, как его отменить)
   - ключ идемпотентности (уникален для каждого предложения; повторная отправка возвращает ту же запись)
2. **Предъявление.** Рецензент видит предложение со всеми метаданными. Рецензент — это человек (а не сам агент, проверяющий себя).
3. **Применение.** Положительное подтверждение. Действие выполняется.
4. **Проверка.** После выполнения побочный эффект считывается заново и подтверждается. Если шаг проверки не проходит, система находится в заведомо плохом состоянии, и включается система оповещений.

### Ключ идемпотентности

Без ключа идемпотентности повтор после временного сбоя может выполнить одобренное действие дважды. Конкретный пример: пользователь одобряет «перевести $100 со счёта A на счёт B». Происходит сетевой сбой. Рабочий процесс повторяет попытку. Пользователь одобрил один раз, но перевод выполняется дважды. Ключ идемпотентности привязывает одобрение к единственному, уникальному побочному эффекту; второе выполнение становится холостой операцией (no-op).

Это тот же паттерн идемпотентности, который используют API Stripe и AWS. Его повторное применение для одобрений агентов явно описано в документации Microsoft Agent Framework.

### Устойчивость: почему одобрения переживают процессы

Зал ожидания одобрения — это фрагмент состояния, которым агент не владеет. Рабочий процесс приостанавливается (урок 12). Когда одобрение приходит, рабочий процесс возобновляется ровно с этой точки. Именно поэтому LangGraph сочетает `interrupt()` с контрольными точками PostgreSQL, а не только с состоянием в памяти — одобрение, пришедшее через два дня, всё равно застаёт рабочий процесс нетронутым.

### Формальные одобрения и мера противодействия «запрос-ответ»

Интерфейс HITL по умолчанию (кнопки «Одобрить» / «Отклонить») порождает быстрые одобрения без подлинного рассмотрения. Задокументированная мера противодействия: чек-лист «запрос-ответ», который требует положительных ответов на конкретные вопросы, прежде чем кнопка «Одобрить» станет активной. Конкретная форма:

- «Понимаете ли вы, какой ресурс это затрагивает? [ ]»
- «Проверили ли вы, что радиус поражения приемлем? [ ]»
- «Есть ли у вас план отката на случай сбоя? [ ]»

Это не бюрократия ради бюрократии, а форсирующий механизм. Рецензент, который не может отметить пункты, либо запрашивает разъяснение (эскалация), либо отклоняет предложение (безопасное значение по умолчанию). Исследования Anthropic по безопасности агентов прямо называют HITL на основе чек-листа мерой противодействия паттернам формального одобрения.

### Что считается значимым действием

Не каждое действие требует схемы «предложить, затем применить». Рекомендации 2026 года:

- **Значимые действия** (всегда HITL): необратимые записи, финансовые транзакции, исходящая коммуникация, изменения продакшн-базы данных, разрушительные операции с файловой системой.
- **Обратимые действия** (иногда HITL): редактирование локальных файлов, изменения в staging-окружении, обратимые записи с чётким планом отката.
- **Чтения и инспекции** (никогда не HITL): чтение файла, получение списка ресурсов, вызов доступного только для чтения API.

### Проверка после выполнения действия

«Применение выполнилось» — это не то же самое, что «побочный эффект произошёл». Разрыв сети и состояния гонки могут привести к тому, что рабочий процесс думает, будто он успешно завершился, хотя бэкенд ничего не сохранил. Шаг проверки заново считывает целевой ресурс после применения, чтобы подтвердить результат. Это тот же паттерн, что и транзакции базы данных с предложением `RETURNING` или вызов `GetObject` после `PutObject` в AWS.

### Статья 14 EU AI Act

Статья 14 требует эффективного человеческого надзора для высокорисковых систем ИИ в ЕС. «Эффективный» — не декоративное слово. Формулировки регламента прямо исключают паттерны формального одобрения. Схема «предложить, затем применить» вместе с механизмом «запрос-ответ» — это форма, которая выдерживает проверку на соответствие статье 14 в документации по соответствию Microsoft Agent Governance Toolkit.

## Применение

`code/main.py` реализует конечный автомат «предложить, затем применить» на стандартной библиотеке Python. Устойчивое хранилище — это JSON-файл. Ключ идемпотентности — это хеш от (thread_id, action_signature). Драйвер моделирует три сценария: чистый поток одобрения, повтор после временного сбоя (который не должен выполнить действие дважды) и вариант с формальным одобрением по умолчанию в сравнении с потоком «запрос-ответ».

## Упражнения

1. Запустите `code/main.py`. Убедитесь, что повтор одобренного предложения использует устойчивую запись и не выполняется повторно. Теперь измените ключ идемпотентности так, чтобы он включал метку времени, и покажите, что повтор выполняет действие дважды.

2. Расширьте запись предложения полем `rollback`. Смоделируйте выполнение, у которого шаг проверки завершается неудачей. Покажите, что откат срабатывает автоматически.

3. Прочитайте документацию `RequestInfoEvent` из Microsoft Agent Framework. Найдите одно поле метаданных, которое есть в API, но отсутствует в игрушечном движке. Добавьте его и объясните, от чего оно защищает.

4. Спроектируйте чек-лист «запрос-ответ» для конкретного действия (например, «опубликовать пост в публичном аккаунте Twitter»). На какие три вопроса должен ответить рецензент? Почему именно эти три?

5. Выберите один случай, когда достаточно синхронного запроса «Одобрить?» (без устойчивого хранилища). Объясните почему и назовите класс риска, который вы принимаете.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|---|---|---|
| Схема «предложить, затем применить» (propose-then-commit) | «Двухэтапное одобрение» | Сохранённое предложение + положительное подтверждение применения + проверка |
| Ключ идемпотентности (idempotency key) | «Токен безопасного повтора» | Уникален для каждого предложения; второе выполнение становится холостой операцией |
| Происхождение данных (data lineage) | «Откуда это взялось» | Конкретное исходное содержимое, которое привело к предложению |
| Радиус поражения (blast radius) | «Худший сценарий» | Масштаб последствий, если действие пойдёт не так |
| Формальное одобрение (rubber-stamp) | «Быстрое одобрение» | Кнопку «Одобрить» нажимают без подлинного рассмотрения |
| Схема «запрос-ответ» (challenge-and-response) | «Обязательный чек-лист» | Рецензент должен явно дать положительные ответы на конкретные вопросы |
| RequestInfoEvent | «Примитив MS Agent Framework» | Устойчивый запрос HITL со структурированными метаданными |
| `interrupt()` / `waitForApproval()` | «Примитивы фреймворков» | Эквиваленты одной и той же схемы в LangGraph и Cloudflare |
