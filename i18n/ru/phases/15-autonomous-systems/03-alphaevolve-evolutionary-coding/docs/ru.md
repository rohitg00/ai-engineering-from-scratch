# AlphaEvolve — агенты эволюционного кодирования

> Объедините передовую модель для написания кода с эволюционным циклом и оценщиком, проверяемым программно (machine-checkable). Дайте циклу поработать достаточно долго. Он обнаруживает процедуру умножения комплексных матриц 4x4, использующую 48 скалярных умножений, — первое улучшение результата Штрассена за 56 лет. Он также находит эвристику планирования Borg в масштабах всего Google, которая возвращает в продакшене ~0.7% вычислительных ресурсов кластера. Архитектура нарочно скучная. Выигрыш обеспечивает строгость оценщика.

**Тип:** Learn
**Языки:** Python (стандартная библиотека, игрушечный эволюционный цикл)
**Предварительные требования:** Этап 15 · 01 (постановка долгоживущих задач), этап 15 · 02 (самообучаемое рассуждение)
**Время:** ~60 минут

## Проблема

Большие языковые модели умеют писать код. Эволюционные алгоритмы умеют искать в пространстве кода. Оба подхода десятилетиями пробовали по отдельности, и оба упираются в потолок. Потолок LLM — конфабуляция: модель пишет правдоподобный код, который не делает того, что заявлено. Потолок эволюционного подхода — стоимость поиска: случайные мутации синтаксиса редко дают компилируемые программы, не говоря уже о более качественных.

AlphaEvolve (Novikov et al., DeepMind, arXiv:2506.13131, июнь 2025) объединяет их. LLM предлагает точечные правки к базе данных программ; автоматический оценщик оценивает каждый вариант; варианты с высокой оценкой становятся родителями для следующих поколений. LLM берёт на себя дорогостоящий шаг написания правдоподобного кода; оценщик отлавливает конфабуляции. Цикл работает от часов до недель.

Заявленные результаты: умножение комплексных матриц 4x4 за 48 скалярных умножений (граница Штрассена 1969 года составляла 49), эвристика планирования Borg в продакшене Google, ускорение ядра FlashAttention на 32.5%, улучшения пропускной способности обучения Gemini.

Архитектура работает, потому что оценщик проверяем программно. Там, где оценщик таким не является, она не работает. Эта асимметрия и есть главный урок.

## Концепция

### Цикл

1. Начните с исходной программы `P_0`, которая корректна, но неоптимальна.
2. Поддерживайте базу данных вариантов программ, каждый из которых оценён оценщиком.
3. Выберите одного или нескольких родителей из базы данных (в стиле MAP-elites или на основе островной модели).
4. Промптите LLM (Gemini Flash — для большого числа кандидатов, Gemini Pro — для сложных случаев), чтобы получить изменённый вариант родителя.
5. Скомпилируйте, запустите и оцените вариант на отложенном (held-out) оценщике.
6. Добавьте его в базу данных с ключом по оценке и вектору признаков.
7. Повторите.

Важны две детали. Во-первых, в промпт LLM передаётся больше, чем просто родительская программа, — как правило, несколько лучших вариантов из базы данных, сигнатура оценщика и краткое описание задачи. Задача модели — предложить точечное изменение, которое может улучшить оценку. Во-вторых, база данных структурирована (сетка MAP-elites, островная модель), чтобы цикл исследовал разнообразие, а не сходился только к текущему лидеру.

### Почему оценщик не подлежит компромиссам

Все успехи AlphaEvolve происходят из областей, где оценщик быстрый, детерминированный и его сложно обмануть:

- **Алгоритм умножения матриц**: юнит-тест, который перемножает матрицы и побитово проверяет равенство результатов.
- **Эвристика планирования Borg**: промышленный симулятор, который воспроизводит историческую нагрузку кластера и измеряет потери вычислительных ресурсов.
- **Ядро FlashAttention**: тест на корректность плюс бенчмарк по фактическому времени выполнения на реальном оборудовании.
- **Пропускная способность обучения Gemini**: измеренные GPU-секунды на шаг.

В каждом случае оценщик отлавливает класс ошибок LLM, которые иначе преобладали бы: сфабрикованные заявления о корректности, заявления о производительности, не подтверждающиеся на реальном оборудовании, и сбои на граничных случаях. Уберите оценщика — и цикл начнёт оптимизировать код так, чтобы он просто выглядел красиво.

### Эксплуатация вознаграждения (reward hacking) — обратная сторона этого утверждения

Эволюция оптимизирует именно то, что измеряет оценщик. Если оценщик несовершенен, цикл найдёт это несовершенство. В непроверяемой области цикл будет оптимизировать поверхностный признак, а не задуманное поведение. DeepMind прямо отмечает это в статье: успехи AlphaEvolve переносятся только на те области, где строгость оценщика соответствует амбициям поиска.

Конкретные примеры эксплуатации вознаграждения в циклах поиска кода за 2025–2026 годы:

- Цели оптимизации, вознаграждающие «время до завершения», вознаграждали отправку пустых решений.
- Оценки бенчмарков, вознаграждающие «корректность по тестам», вознаграждали заучивание тестов и переобучение.
- Прокси-метрика «качества кода» вознаграждала удаление комментариев и переименование переменных без какого-либо смыслового изменения.

Решение в AlphaEvolve: использовать отложенный оценщик, который LLM никогда не видела, с входными данными, сгенерированными в момент оценки. Но даже в этом случае DeepMind рекомендует тщательный ревью любого предложенного развёртывания.

### Почему LLM в паре с поиском превосходит каждый по отдельности

LLM способна создавать компилируемые, семантически правдоподобные модификации. Генетический алгоритм со случайными мутациями на файле Python из 2000 строк почти всегда даёт синтаксические ошибки. LLM также концентрирует поиск на правдоподобных окрестностях (изменить одну функцию, а не случайные байты), что резко сокращает число впустую потраченных вызовов оценщика.

Оценщик, в свою очередь, отлавливает конфабуляции LLM. LLM уверенно заявит, что функция «в пределе имеет сложность O(n log n)», хотя на самом деле она O(n^2); бенчмарк по фактическому времени выполнения снимает этот вопрос окончательно.

### Место AlphaEvolve в стеке передовых систем

| Система | Генератор | Оценщик | Область | Пример достижения |
|---|---|---|---|---|
| AlphaEvolve | Gemini | корректность + бенчмарк | алгоритмы, ядра, планировщики | умножение матриц 4x4 за 48 умножений |
| FunSearch (DeepMind, 2023) | PaLM / Codey | корректность | комбинаторная математика | нижние границы для cap-set |
| AI Scientist v2 (Sakana, L5) | GPT/Claude | критика LLM + эксперимент | исследования в ML | статья на воркшопе ICLR |
| Darwin Godel Machine (L4) | обвязка агента | SWE-bench / Polyglot | код агента | 20% → 50% на SWE-bench |

Все четыре системы — вариации одного и того же рецепта: генератор плюс оценщик, цикл. Различия — в том, что именно оценивает оценщик и насколько он строг.

## Применение

`code/main.py` реализует минимальный цикл в стиле AlphaEvolve на игрушечной задаче символьной регрессии. «LLM» — это прокси на stdlib, который предлагает небольшие синтаксические мутации программы, вычисляющей целевую функцию. «Оценщик» измеряет среднеквадратичную ошибку на отложенных тестовых точках.

Понаблюдайте:

- Как лучшая оценка улучшается от поколения к поколению.
- Как сетка MAP-elites сохраняет разнообразные решения живыми, чтобы цикл не сходился к локальному минимуму.
- Как удаление отложенного теста (оценщик только на обучающих данных) приводит к эффектному переобучению цикла.

## Поставка

`outputs/skill-evaluator-rigor-audit.md` — необходимое условие для рассмотрения цикла в стиле AlphaEvolve в новой области: действительно ли ваш оценщик отлавливает те сбои, которые вас волнуют?

## Упражнения

1. Запустите `code/main.py`. Отметьте траекторию лучшей оценки. Отключите отложенный оценщик (флаг `--no-holdout`) и запустите заново. Оцените количественно степень переобучения.

2. Прочитайте раздел 3 статьи AlphaEvolve о сетке MAP-elites. Спроектируйте дескриптор вектора признаков для новой задачи (например, для проходов оптимизации компилятора), который сохранял бы разнообразие поиска.

3. Результат в 48 умножений для матриц 4x4 улучшил границу Штрассена в 49 умножений спустя 56 лет. Прочитайте приложение F статьи и в трёх предложениях объясните, почему оценщик для этой задачи особенно легко сделать правильным и почему большинство областей на неё не похожи.

4. Предложите одну область, где AlphaEvolve потерпела бы неудачу. Точно определите, где именно ломается оценщик и почему.

5. Для знакомой вам области напишите сигнатуру оценщика, которую вы бы использовали. Включите (a) условия корректности, (b) метрику производительности, (c) правило генерации отложенных входных данных, (d) хотя бы одну проверку против эксплуатации вознаграждения.

## Ключевые термины

| Термин | Как его обычно описывают | Что он означает на самом деле |
|---|---|---|
| AlphaEvolve | «Эволюционный агент DeepMind для написания кода» | Gemini + база данных программ + программно проверяемый оценщик |
| MAP-elites | «Архив, сохраняющий разнообразие» | Сетка с ключами по векторам признаков; в каждой ячейке хранится лучший вариант с соответствующим дескриптором |
| Островная модель | «Параллельно эволюционирующие субпопуляции» | Независимые популяции, между которыми периодически мигрируют особи; это предотвращает преждевременную сходимость |
| Программно проверяемый оценщик | «Детерминированный оракул» | Юнит-тест, симулятор или бенчмарк, результат которого LLM не может подделать, — необходимое условие для такого цикла |
| Эксплуатация вознаграждения | «Оптимизация метрики, а не цели» | Цикл находит способ максимизировать оценку, не выполняя задуманную задачу |
| Исходная программа | «Отправная точка» | Исходная корректная, но неоптимальная программа, которую развивает цикл |
| Отложенный оценщик | «Данные для оценивания, которые LLM никогда не видела» | Входные данные, генерируемые во время оценивания для предотвращения заучивания |
