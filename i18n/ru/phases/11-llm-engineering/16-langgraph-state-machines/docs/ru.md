# Конечные автоматы агентов — графы, узлы, контрольные точки

> ReAct-цикл, написанный вручную, — это `while True`. Тот же цикл, представленный в виде явного графа, можно снабжать контрольными точками, прерывать, разветвлять и перемещаться по нему во времени. Агент не изменился. Изменилась обвязка вокруг него.

**Тип:** Build
**Языки:** Python
**Предварительные требования:** Этап 11 · 09 (Вызов функций), этап 11 · 14 (Model Context Protocol)
**Время:** ~75 минут

## Проблема

Вы выкатываете агента с вызовом функций. Он работает три хода, а затем что-то идёт не так: модель пробует инструмент, который возвращает 500, пользователь меняет решение посреди задачи, или агент решает вернуть деньги за заказ без одобрения человека. У цикла `while True:` нет точек вмешательства. Его нельзя приостановить, нельзя отмотать назад и нельзя разветвить на «а что, если бы модель выбрала другой инструмент». В тот момент, когда это уходит дальше демо, агент превращается в чёрный ящик, который либо сработал, либо нет.

Следующий шаг очевиден, как только его увидишь. Агент уже и есть конечный автомат — системный промпт плюс история сообщений плюс отложенные вызовы инструментов плюс следующее действие. Сделайте конечный автомат явным: узлы (node) для «модель думает», «инструмент выполняется», «человек одобряет» — и рёбра (edge) для условных переходов между ними. Как только граф становится явным, обвязка получает четыре вещи бесплатно: контрольные точки (checkpointing) — сохранение состояния между шагами; прерывания (interrupts) — пауза для участия человека; потоковую передачу (streaming) — трансляцию токенов и промежуточных событий; и путешествия во времени (time-travel) — отмотку к предыдущему состоянию и попытку другой ветки.

Эталонная реализация этой абстракции — LangGraph. Это не агентный фреймворк в духе LangChain («вот вам AgentExecutor, удачи»). Это среда выполнения графов (graph runtime), где состояние, персистентность и прерывания реализованы как сущности первого класса. Цикл агента — это то, что вы рисуете, а не то, что пишете вручную.

## Концепция

![StateGraph в LangGraph: узлы, рёбра и чекпоинтер](../assets/langgraph-stategraph.svg)

У `StateGraph` есть три составляющих.

1. **Состояние (State).** Типизированный словарь (TypedDict или модель Pydantic), который передаётся по графу. Каждый узел получает полное состояние и возвращает частичное обновление, которое LangGraph объединяет с помощью *редьюсера (reducer)* для каждого поля: по умолчанию — перезапись, `operator.add` — для списков, которые должны накапливаться.
2. **Узлы (Nodes).** Функции Python `state -> partial_state`. Каждая — это отдельный шаг: «вызвать модель», «выполнить инструменты», «подвести итог».
3. **Рёбра (Edges).** Переходы между узлами. Статические рёбра ведут в одно место. Условные рёбра используют функцию-маршрутизатор `state -> next_node_name`, чтобы граф мог ветвиться в зависимости от вывода модели.

Граф компилируется. Компиляция фиксирует топологию, подключает чекпоинтер (checkpointer) (необязателен, но необходим для продакшена) и возвращает исполняемый объект. Вы вызываете его с начальным состоянием и `thread_id`. Каждый шаг выполнения сохраняет контрольную точку с ключом `(thread_id, checkpoint_id)`.

### Четыре суперспособности

**Контрольные точки (Checkpointing).** Каждый переход между узлами записывает новое состояние в хранилище (в памяти — для тестов, Postgres/Redis/SQLite — для продакшена). Чтобы возобновить выполнение, вызовите граф снова с тем же `thread_id`. Граф продолжит с того места, где остановился.

**Прерывания (Interrupts).** Пометьте узел через `interrupt_before=["human_review"]`, и выполнение остановится перед запуском этого узла. Состояние сохраняется. Ваш API отвечает пользователю «ожидает одобрения». Более поздний запрос к тому же `thread_id` с `Command(resume=...)` возобновляет выполнение.

**Потоковая передача (Streaming).** `graph.stream(state, mode="updates")` выдаёт изменения состояния по мере их появления. `mode="messages"` транслирует токены LLM внутри узлов модели. `mode="values"` выдаёт полные снимки состояния. Вы сами выбираете, что показывать в UI.

**Путешествия во времени (Time-travel).** `graph.get_state_history(thread_id)` возвращает полный журнал контрольных точек. Передайте любой прежний `checkpoint_id` в `graph.invoke` — и вы разветвитесь от этой точки. Это удобно для отладки («а что, если бы модель выбрала инструмент B?») и для регрессионных тестов, которые воспроизводят продакшен-трейсы.

### Редьюсеры — вот в чём суть

У каждого поля состояния есть редьюсер. В большинстве случаев поведение по умолчанию устраивает — новое значение перезаписывает старое. Но спискам сообщений нужен `operator.add`, чтобы новые сообщения добавлялись, а не заменяли старые. Параллельные рёбра объединяют свои обновления через редьюсер. Если два узла одновременно обновляют `messages`, а вы забыли `Annotated[list, add_messages]`, второе обновление молча побеждает, и вы теряете половину хода. Редьюсер — единственная тонкость во всей библиотеке; разберитесь с ним правильно, и остальное само сложится.

### ReAct-граф в четырёх узлах

Продакшен-агент ReAct — это четыре узла и два ребра:

1. `agent` — вызывает LLM с текущей историей сообщений. Возвращает сообщение ассистента (которое может содержать tool_calls).
2. `tools` — выполняет все tool_calls из последнего сообщения ассистента, добавляет результаты инструментов в виде сообщений tool.
3. Условное ребро из `agent`, которое направляет в `tools`, если у последнего сообщения есть tool_calls, иначе — в `END`.
4. Статическое ребро из `tools` обратно в `agent`.

Вот и всё. Вы получаете полный цикл ReAct (Мысль → Действие → Наблюдение → Мысль → …) с контрольными точками, прерываниями и потоковой передачей — примерно за 40 строк кода.

### StateGraph против Send (параллельное разветвление)

`Send(node_name, state)` позволяет узлу запускать параллельные подграфы. Пример: агент решает одновременно опросить три ретривера. Каждый `Send` порождает параллельное выполнение целевого узла; их результаты объединяются через редьюсер состояния. Именно так LangGraph реализует паттерн «оркестратор — исполнители» без примитивов многопоточности.

### Подграфы

Скомпилированный граф может быть узлом в другом графе. Внешний граф видит единственный узел; внутренний граф имеет собственное состояние и собственные контрольные точки. Так команды строят агентов по схеме «супервизор — исполнитель»: граф-супервизор направляет намерение пользователя в подграф-исполнитель для конкретного домена.

## Соберите это

### Шаг 1: состояние и узлы

```python
from typing import Annotated, TypedDict
from langchain_core.messages import AnyMessage, HumanMessage, AIMessage
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

def agent_node(state: State) -> dict:
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state: State) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

tool_node = ToolNode(tools=[search_web, read_file])

graph = StateGraph(State)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")

app = graph.compile(checkpointer=MemorySaver())
```

`add_messages` — это редьюсер, который заставляет список сообщений накапливаться, а не перезаписываться. Забыть про него — самая распространённая ошибка в LangGraph.

### Шаг 2: запуск с тредом

```python
config = {"configurable": {"thread_id": "user-42"}}
for event in app.stream(
    {"messages": [HumanMessage("find the Anthropic headquarters address")]},
    config,
    stream_mode="updates",
):
    print(event)
```

Каждое обновление — это словарь `{node_name: state_delta}`. Ваш фронтенд может транслировать их в UI, чтобы пользователи видели: «агент думает… вызывает search_web… получил результат… отвечает».

### Шаг 3: добавьте прерывание с участием человека

Пометьте узел так, чтобы выполнение приостанавливалось перед его запуском.

```python
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["tools"],  # pause before every tool call
)

state = app.invoke({"messages": [HumanMessage("delete the production database")]}, config)
# state["__interrupt__"] is set. Inspect proposed tool calls.
# If approved:
from langgraph.types import Command
app.invoke(Command(resume=True), config)
# If denied: write a rejection message and resume
app.update_state(config, {"messages": [AIMessage("Blocked by human reviewer.")]})
```

Состояние, контрольная точка и тред сохраняются на протяжении всего прерывания. В памяти ничего не остаётся, кроме как во время самого выполнения.

### Шаг 4: путешествие во времени для отладки

```python
history = list(app.get_state_history(config))
for snapshot in history:
    print(snapshot.values["messages"][-1].content[:80], snapshot.config)

# Fork from a prior checkpoint
target = history[3].config  # three steps back
for event in app.stream(None, target, stream_mode="values"):
    pass  # replay from that point forward
```

Если передать `None` в качестве входа, выполнение воспроизводится с указанной контрольной точки; если передать значение, оно добавляется как обновление к состоянию этой контрольной точки перед возобновлением. Так вы воспроизводите неудачный запуск агента, не прогоняя весь диалог заново.

### Шаг 5: замените чекпоинтер для продакшена

```python
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string("postgresql://...") as checkpointer:
    checkpointer.setup()
    app = graph.compile(checkpointer=checkpointer)
```

SQLite, Redis и Postgres поставляются из коробки. `MemorySaver` — для тестов. Всё, что должно переживать перезапуски, нуждается в настоящем хранилище.

## Навык

> Вы строите агентов как графы, а не как циклы `while True`.

Прежде чем браться за LangGraph, потратьте 60 секунд на проектирование:

1. **Назовите узлы.** Каждое дискретное решение или действие с побочным эффектом — это узел. «Агент думает», «инструмент выполняется», «рецензент одобряет», «ответ транслируется». Если вы не можете их перечислить, задача ещё не готова быть агентной.
2. **Опишите состояние.** Минимальный TypedDict с редьюсером для каждого поля-списка. Не сваливайте всё в `messages`; вынесите специфичные для задачи поля (рабочий `plan`, счётчик `budget`, список `retrieved_docs`) на верхний уровень.
3. **Нарисуйте рёбра.** Статические — если следующий шаг не зависит от вывода модели. Каждому условному ребру нужна функция-маршрутизатор с именованными ветками.
4. **Выберите чекпоинтер заранее.** `MemorySaver` для тестов, Postgres/Redis/SQLite — для всего остального. Не выкатывайте без него: нет чекпоинтера — нет возобновления, нет прерываний, нет путешествий во времени.
5. **Решайте вопрос прерываний до выполнения инструментов, а не после.** Одобрения ставятся на ребро, ведущее в узел с побочным эффектом, — чтобы можно было отменить действие до того, как случится вред; валидация ставится на ребро, выходящее из модели, — чтобы дёшево отклонять плохие вызовы.
6. **Транслируйте по умолчанию.** `mode="updates"` — для UI, `mode="messages"` — для потоковой передачи на уровне токенов внутри узлов модели, `mode="values"` — для полных снимков состояния при оценивании.

Откажитесь выкатывать агента LangGraph без чекпоинтера. Откажитесь выкатывать агента, который прерывается *после* побочного эффекта. Откажитесь выкатывать поле `messages` без `add_messages` в качестве редьюсера.

## Упражнения

1. **Лёгкое.** Реализуйте описанный выше четырёхузловой ReAct-граф с инструментом-калькулятором и инструментом веб-поиска. Убедитесь, что `list(app.get_state_history(config))` возвращает не менее четырёх контрольных точек для диалога из двух ходов.
2. **Среднее.** Добавьте узел `planner`, который выполняется перед `agent` и записывает в состояние структурированный `plan: list[str]`. Пусть `agent` отмечает шаги плана как выполненные. Тест должен падать, если `plan` теряется при возобновлении с контрольной точки (неверный редьюсер).
3. **Сложное.** Постройте граф-супервизор, который маршрутизирует между тремя подграфами (`researcher`, `writer`, `reviewer`) с помощью `Send`. У каждого подграфа своё состояние и свой чекпоинтер. Добавьте `interrupt_before=["writer"]` во внешнем графе, чтобы человек мог одобрить бриф исследования. Убедитесь, что путешествие во времени с прежней контрольной точки заново прогоняет только разветвлённую ветку.

## Ключевые термины

| Термин | Как его обычно называют | Что он означает на самом деле |
|------|-----------------|-----------------------|
| StateGraph | «Граф LangGraph» | Объект-билдер, в который вы добавляете узлы и рёбра перед компиляцией. |
| Редьюсер (Reducer) | «Как объединяется поле» | Функция `(old, new) -> merged`, применяемая, когда узел возвращает обновление для этого поля; по умолчанию — перезапись, `add_messages` — добавление. |
| Тред (Thread) | «ID диалога» | Строка `thread_id`, которая ограничивает область действия всех контрольных точек одной сессии. |
| Контрольная точка (Checkpoint) | «Приостановленное состояние» | Сохранённый снимок полного состояния графа после перехода между узлами, с ключом `(thread_id, checkpoint_id)`. |
| Прерывание (Interrupt) | «Пауза для человека» | `interrupt_before` / `interrupt_after` останавливают выполнение на границе узла; возобновление — через `Command(resume=...)`. |
| Путешествие во времени (Time-travel) | «Разветвиться от предыдущего шага» | `graph.invoke(None, config_with_old_checkpoint_id)` воспроизводит выполнение от этой контрольной точки вперёд. |
| Send | «Параллельный запуск подграфов» | Конструктор, который узел может вернуть, чтобы породить N параллельных выполнений целевого узла. |
| Подграф (Subgraph) | «Скомпилированный граф как узел» | Скомпилированный StateGraph, используемый как узел в другом графе; сохраняет собственную область состояния. |
