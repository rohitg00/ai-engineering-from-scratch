# Масштабирование в продакшене — очереди, контрольные точки, долговечность

> Масштабирование мультиагентных систем до тысяч параллельных запусков требует **долговечного выполнения (durable execution)** — очередей задач и контрольных точек, чтобы после любого сбоя любой воркер мог возобновить любой запуск при условии правильной обработки аренды, идемпотентности побочных эффектов и детерминированного воспроизведения. Эталонный пример — рантайм LangGraph: он записывает контрольную точку (checkpoint) после каждого супершага, привязанную к `thread_id` (по умолчанию в Postgres); при аварийном завершении воркера аренда (lease) освобождается, и работу подхватывает другой воркер. Агенты могут бесконечно «спать» в ожидании ввода от человека. **MegaAgent** (arXiv:2408.09955) использовал очередь производитель-потребитель для каждого агента с тремя состояниями (Idle / Processing / Response) и двухуровневой координацией (чат внутри группы + административный чат между группами). **Файберы/асинхронность (Fiber/async)** превосходят подход «поток на задачу» для потоковой передачи LLM: потоки простаивают 99% времени в ожидании токенов, а файберы кооперативно уступают управление на операциях ввода-вывода. Контраргумент: в статье Ashpreet Bedi «Scaling Agentic Software» отстаивается позиция **FastAPI + Postgres и ничего больше**, пока нагрузка не докажет обратное — простые архитектуры выдерживают больше, чем принято ожидать. В этом уроке строится долговечный журнал контрольных точек, очередь работы для каждого агента с переходами состояний, демонстрация async против потоков, и формулируется прагматичное правило «начинай просто».

**Тип:** Learn + Build**Языки:** Python (stdlib, `asyncio`, `sqlite3`)**Предварительные требования:** Фаза 16 · 09 (Parallel Swarm Networks), Фаза 16 · 13 (Shared Memory)**Время:** ~75 минут
## Проблема

Прототип мультиагентной системы работает на одном ноутбуке с тремя агентами в цикле событий, хранящемся в памяти. Вы переходите в продакшен:

- Агенты иногда работают часами (долгие исследования, ожидания участия человека).
- Процессы-воркеры аварийно завершаются. Перезапуск теряет состояние.
- Пиковая нагрузка в 10 раз выше средней; нужно горизонтальное масштабирование.
- Пользователи платят за каждый запуск агента; для списаний нужна семантика «ровно один раз» (exactly-once).

Цикл событий в памяти не решает ни одну из этих задач. Под ним нужен слой долговечного выполнения. Канонические варианты 2026 года:

1. Движок рабочих процессов с контрольными точками (Temporal, рантайм LangGraph).
2. Очередь сообщений с хранилищем состояния (Postgres + SQS/RabbitMQ).
3. Фреймворки на акторной модели (очередь производитель-потребитель на агента в MegaAgent).
4. Самописное решение на FastAPI + Postgres (аргумент Bedi).

В этом уроке строится миниатюра каждого из них.

## Концепция

### Долговечное выполнение: паттерн

Движок долговечного выполнения сохраняет полное состояние программы после каждого «шага» (супершага — на языке LangGraph). При аварийном завершении:

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

Требования для этого:

- **Сериализуемое состояние.** Всё состояние агента должно поддаваться сохранению. Замыкания функций с живыми соединениями к базе данных не переживают сохранение.
- **Детерминированное возобновление.** При одинаковом состоянии и одинаковых входных данных агент производит одинаковые действия (либо делегирует вызовы LLM внешнему детерминированному оракулу).
- **Идемпотентные побочные эффекты.** Внешние вызовы (вызовы инструментов, платежи) должны быть идемпотентными либо использовать ключ дедупликации.

LangGraph записывает контрольную точку после каждого супершага; Temporal — после каждой activity; Restate использует журналы, построенные на event sourcing. Все три реализуют один и тот же паттерн.

### Рантайм с контрольной точкой на каждом шаге

В качестве рабочего примера рассмотрим рантайм LangGraph: у каждого агента есть `thread_id`; состояние — типизированный словарь; каждый супершаг записывает строку в таблицу контрольных точек. При возобновлении рантайм воспроизводит выполнение с последней контрольной точки, а не с нуля. Агенты могут вызывать `interrupt()`, ожидая ввода от человека; рантайм сохраняет состояние и освобождает воркера. Когда ввод поступает, возобновить выполнение может любой воркер.

Это эталонный продакшен-дизайн по состоянию на апрель 2026 года.

### Очередь для каждого агента в MegaAgent

arXiv:2408.09955 описывает эксперимент по масштабированию: тысячи параллельных агентов в одном кластере. Архитектура:

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

Двухуровневая координация позволяет вести плотный обмен сообщениями внутри группы, оставляя обмен между группами разреженным — этот паттерн используется, чтобы сохранить линейный рост стоимости при тысячах агентов.

### Async против «поток на задачу»

Вызовы LLM ограничены вводом-выводом. Поток, ожидающий следующий токен, простаивает 99% времени. Каждый поток стоит ~1 МБ ОЗУ; при 10 000 параллельных вызовов это 10 ГБ только на стеки.

Файберы (Python `asyncio`, горутины Go, `tokio` в Rust) кооперативно уступают управление на операциях ввода-вывода. Те же 10 000 вызовов свободно помещаются в один процесс. В масштабе LLM-агентов асинхронность — не оптимизация, а сама архитектура.

Исключение: пост-обработка, ограниченная процессором (эмбеддинги, трюки токенизатора), по-прежнему требует потоков или процессов. Разделяйте слой ввода-вывода и слой вычислений на CPU.

### Контраргумент Bedi

«Scaling Agentic Software» (Ashpreet Bedi, 2026) утверждает, что большинство команд переусложняют архитектуру ещё до того, как измерили нагрузку. Прагматичный вариант по умолчанию:

- FastAPI + Postgres.
- Каждый запуск агента — это строка; состояние обновляется на месте с оптимистичной конкурентностью.
- Фоновые задачи через `pg_notify` или простой воркер Celery.
- Политика повторов в коде приложения.

При нагрузке до ~100 параллельных запусков агентов на посильных задачах этого часто достаточно. Переходите на более сложное решение, когда измерения покажут отказ.

Правило: внедряйте фреймворки долговечного выполнения, когда сталкиваетесь с конкретной проблемой, которую не решают простые архитектуры. Преждевременное внедрение сжигает время на ритуалы, которые не окупаются.

### Семантика exactly-once

Для платных запусков агентов нужна эффективная семантика «ровно один раз» (exactly-once): доставка «как минимум один раз» (at-least-once) плюс идемпотентный потребитель. Инженерные приёмы:

- **Ключ дедупликации на запуск.** Включайте его в каждый вызов с побочным эффектом.
- **Паттерн outbox.** Побочные эффекты сначала записываются в таблицу, затем отдельный процесс их выполняет. Оба шага идемпотентны.
- **Компенсирующие транзакции.** Если побочный эффект выполнился успешно, но запись об этом не удалась, планируется компенсирующее действие.

Это паттерны инженерии баз данных, а не специфика LLM. «Налог» LLM — лишь то, что вызовы LLM медленные; всё остальное — стандартные распределённые системы.

### Rainbow-развёртывание

Мультиагентная исследовательская система Anthropic использует «rainbow-развёртывания»: несколько версий рантайма агента работают одновременно, чтобы долгоживущие агенты не приходилось убивать при каждом деплое кода. Новые версии выкатываются canary-способом на часть трафика; старые версии выводятся из эксплуатации, когда их агенты завершают работу.

Это стандартная практика для долгоживущих систем с состоянием; адаптация 2026 года в том, что агенты могут жить часами, и циклы деплоя должны это учитывать.

### Канонический продакшен-чек-лист

- Долговечное состояние (контрольные точки, снапшоты, либо outbox + воспроизводимый журнал).
- Идемпотентные побочные эффекты.
- Асинхронный слой ввода-вывода для вызовов LLM.
- Доставка at-least-once с дедупликацией.
- Rainbow/canary-развёртывание для нагрузок с состоянием.
- Наблюдаемость: трассировки на агента, аудит супершагов, счётчик повторов.

## Реализация

`code/main.py` реализует:

- `CheckpointStore` — журнал контрольных точек на SQLite с ключами по thread-id. Каждый супершаг добавляет строку.
- `run_with_checkpoint(agent, thread_id)` — имитирует аварийное завершение в середине выполнения; второй воркер возобновляет работу с последней контрольной точки.
- `AgentQueue` — конечный автомат Idle / Processing / Response для каждого агента с небольшой очередью работы.
- `demo_async_vs_threads()` — запускает 500 параллельных имитированных «вызовов LLM» через asyncio и через потоки; сообщает фактическое (wall-clock) время и пиковую память (приблизительно).

Запустите:

```
python3 code/main.py
```

Ожидаемый результат: возобновление с контрольной точки после имитированного сбоя проходит успешно; асинхронная версия обрабатывает 500 параллельных вызовов менее чем за 1 с; версия на потоках занимает несколько секунд и расходует на порядки больше памяти на единицу параллелизма.

## Поставка

Канонические меры укрепления продакшена:

- **Начинайте просто (правило Bedi).** FastAPI + Postgres, пока измерения не покажут отказ.
- **Инструментируйте всё до оптимизации.** Гистограмма задержки на запуск, время на шаг, число повторов, категоризация сбоев.
- **Паттерн outbox для побочных эффектов.** Особенно для платежей и вызовов внешних API.
- **Rainbow-деплои.** Никогда не убивайте выполняющиеся запуски агентов во время деплоя.
- **Внедряйте движки долговечного выполнения (Temporal / LangGraph / Restate), когда** сталкиваетесь с конкретными проблемами: часовые ожидания участия человека, координация между регионами, сложные политики повторов/компенсаций.
- **Асинхронность для слоя ввода-вывода.** Потоки — только для пост-обработки, ограниченной процессором.

## Упражнения

1. Запустите `code/main.py`. Убедитесь, что возобновление с контрольной точки работает; измерьте разницу в параллелизме между async и потоками.
2. Реализуйте таблицу **outbox**: каждый вызов инструмента сначала записывается в outbox, затем выполняется отдельной горутиной/задачей. Проверьте идемпотентность, выполнив вызов инструмента дважды.
3. Смоделируйте **rainbow-деплой**: две параллельные версии рантайма; направляйте половину новых thread_id на каждую из них; убедитесь, что выполняющиеся threads на старой версии не прерываются.
4. Прочитайте документацию по рантайму LangGraph (ссылка ниже). Определите, какие возможности рантайма дольше всего воспроизводить в самописной версии на FastAPI + Postgres. Это повод для внедрения — или можно отложить?
5. Прочитайте раздел 3 статьи MegaAgent (arXiv:2408.09955). Двухуровневая координация (внутригрупповой чат + административный чат между группами) описана явно. Набросайте, как вы бы отобразили это на очередь сообщений с двумя семействами очередей.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Долговечное выполнение | «Сохраняем состояние программы» | Движок записывает состояние после каждого супершага; восстановление после сбоя детерминировано. |
| Супершаг | «Граница транзакции» | Единица работы между контрольными точками. Термин LangGraph. |
| thread_id | «Идентификатор запуска агента» | Ключ, связывающий контрольные точки и логику возобновления. |
| Идемпотентность | «Можно безопасно повторять» | Повторение побочного эффекта даёт тот же результат, что и одна попытка. |
| Паттерн outbox | «Отделить побочные эффекты» | Намерение записывается в таблицу; отдельный исполнитель выполняет действие и помечает его завершённым. |
| Доставка at-least-once | «Возможны дубликаты» | Семантика очереди сообщений; ключ дедупликации делает потребителя фактически однократным. |
| Rainbow-деплой | «Пересекающиеся версии» | Несколько версий рантайма работают одновременно во время выполнения долгоживущих задач. |
| Асинхронный файбер | «Кооперативная уступка управления» | Параллелизм в пользовательском режиме; дёшев по сравнению с потоками для нагрузок, ограниченных вводом-выводом. |
| Контрольная точка | «Снимок состояния» | Сериализованное состояние на границе супершага; ключ для возобновления. |
