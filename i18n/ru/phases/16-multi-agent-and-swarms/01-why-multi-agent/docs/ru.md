# Зачем нужны мультиагентные системы?

> Один агент упирается в потолок возможностей. Разумный шаг — не агент покрупнее, а агентов побольше.

**Тип:** Learn
**Языки:** TypeScript
**Предварительные требования:** этап 14 («Инженерия агентов»)
**Время:** ~60 минут

## Цели обучения

- Определять потолок возможностей одного агента (переполнение контекста, смешанная экспертиза, последовательное узкое место) и объяснять, когда переход к нескольким агентам — правильное решение
- Сравнивать паттерны оркестрации (конвейер, параллельное разветвление, супервизор, иерархия) и выбирать подходящий под структуру конкретной задачи
- Проектировать мультиагентную систему с чёткими границами ролей, общим состоянием и контрактом взаимодействия
- Анализировать компромиссы мультиагентной сложности (задержка, стоимость, сложность отладки) в сравнении с простотой одного агента

## Проблема

Вы построили одного агента на этапе 14. Он работает. Он умеет читать файлы, запускать команды, вызывать API и рассуждать о результатах. Затем вы направляете его на реальную кодовую базу: 200 файлов, три языка, тесты, зависящие от инфраструктуры, и требование исследовать внешние API перед написанием кода.

Агент захлёбывается. Не потому, что LLM глупа, а потому, что задача превышает то, что способен обработать один цикл агента. Контекстное окно заполняется содержимым файлов. Агент забывает, что он прочитал 40 вызовов инструментов назад. Он пытается одновременно быть исследователем, программистом и рецензентом — и делает все три роли плохо.

Это и есть потолок возможностей одного агента. Вы упираетесь в него каждый раз, когда задача требует:

- **Больше контекста, чем помещается в одно окно** — чтение 50 файлов выходит далеко за 200 тыс. токенов
- **Разной экспертизы на разных этапах** — исследование требует иного промптинга, чем генерация кода
- **Работы, которую можно выполнять параллельно** — зачем читать три файла последовательно, если их можно прочитать одновременно?

## Концепция

### Потолок возможностей одного агента

Один агент — это один цикл, одно контекстное окно, один системный промпт. Представьте это так:

```
┌─────────────────────────────────────────┐
│            SINGLE AGENT                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         Context Window            │  │
│  │                                   │  │
│  │  research notes                   │  │
│  │  + code files                     │  │
│  │  + test output                    │  │
│  │  + review feedback                │  │
│  │  + API docs                       │  │
│  │  + ...                            │  │
│  │                                   │  │
│  │  ██████████████████████ FULL ███  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  One system prompt tries to cover       │
│  research + coding + review + testing   │
│                                         │
│  Result: mediocre at everything         │
└─────────────────────────────────────────┘
```

Ломаются три вещи:

1. **Насыщение контекста** — результаты вызовов инструментов накапливаются. К 30-му ходу агент израсходовал 150 тыс. токенов на содержимое файлов, вывод команд и предыдущие рассуждения. Важные детали из 5-го хода теряются.

2. **Путаница ролей** — системный промпт вида «ты исследователь, программист, рецензент и тестировщик» порождает агента, который наполовину исследует, наполовину пишет код и никогда не заканчивает ревью.

3. **Последовательное узкое место** — агент читает файл A, затем файл B, затем файл C. Три последовательных вызова LLM. Три последовательных выполнения инструментов. Никакого параллелизма.

### Мультиагентное решение

Разделите работу. Дайте каждому агенту одну задачу, одно контекстное окно и один системный промпт, настроенный под эту задачу:

```
┌──────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR                          │
│                                                          │
│  "Build a REST API for user management"                  │
│                                                          │
│         ┌──────────┬──────────┬──────────┐               │
│         │          │          │          │               │
│         ▼          ▼          ▼          ▼               │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │RESEARCHER│ │  CODER   │ │ REVIEWER │ │  TESTER  │  │
│   │          │ │          │ │          │ │          │  │
│   │ Reads    │ │ Writes   │ │ Checks   │ │ Runs     │  │
│   │ docs,    │ │ code     │ │ code     │ │ tests,   │  │
│   │ finds    │ │ based on │ │ quality, │ │ reports  │  │
│   │ patterns │ │ research │ │ finds    │ │ results  │  │
│   │          │ │ + spec   │ │ bugs     │ │          │  │
│   └─────┬────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│         │           │            │             │         │
│         └───────────┴────────────┴─────────────┘         │
│                          │                               │
│                     Merge results                        │
└──────────────────────────────────────────────────────────┘
```

У каждого агента есть:
- Сфокусированный системный промпт («Ты — ревьюер кода. Твоя единственная задача — находить баги»)
- Своё собственное контекстное окно (не загрязнённое работой других агентов)
- Чёткий контракт входа/выхода (получает заметки исследования, выдаёт код)

### Реальные системы, которые так работают

**Субагенты Claude Code** — когда Claude Code порождает субагента через `Task`, он создаёт дочернего агента с ограниченной задачей. Родитель сохраняет свой контекст чистым. Дочерний агент выполняет сфокусированную работу и возвращает сводку.

**Devin** — запускает агента-планировщика, агента-программиста и агента-браузер. Планировщик разбивает работу на шаги. Программист пишет код. Браузер исследует документацию. У каждого свой отдельный контекст.

**Мультиагентные команды программирования (SWE-bench)** — системы с лучшими результатами на SWE-bench используют исследователя, читающего кодовую базу, планировщика, проектирующего исправление, и программиста, реализующего его. Одноагентные системы показывают более низкие результаты.

**ChatGPT Deep Research** — порождает несколько поисковых агентов параллельно, каждый исследует свой угол, затем синтезирует результаты.

### Спектр

Мультиагентность — это не бинарный выбор. Это спектр:

```
SIMPLE ──────────────────────────────────────────── COMPLEX

 Single        Sub-         Pipeline      Team         Swarm
 Agent         agents

 ┌───┐       ┌───┐        ┌───┐───┐    ┌───┐───┐    ┌─┐┌─┐┌─┐
 │ A │       │ A │        │ A │ B │    │ A │ B │    │ ││ ││ │
 └───┘       └─┬─┘        └───┘─┬─┘    └─┬─┘─┬─┘    └┬┘└┬┘└┬┘
               │                │        │   │       ┌┴──┴──┴┐
             ┌─┴─┐          ┌───┘───┐    │   │       │shared │
             │ a │          │ C │ D │  ┌─┴───┴─┐    │ state │
             └───┘          └───┘───┘  │  msg   │    └───────┘
                                       │  bus   │
 1 loop      Parent +      Stage by    │       │    N peers,
 1 context   child tasks   stage       └───────┘    emergent
                                       Explicit      behavior
                                       roles
```

**Один агент** — один цикл, один промпт. Хорош для простых задач.

**Субагенты** — родитель порождает дочерних агентов для сфокусированных подзадач. Родитель ведёт план. Дочерние агенты отчитываются обратно. Именно так работает Claude Code.

**Конвейер** — агенты работают последовательно. Вывод агента A становится вводом агента B. Хорош для многоэтапных рабочих процессов: исследование → код → ревью → тест.

**Команда** — агенты работают параллельно с общей шиной сообщений. У каждого своя роль. Оркестратор координирует их. Хорошо, когда одновременно нужны разные навыки.

**Рой (swarm)** — множество идентичных или почти идентичных агентов с общим состоянием. Нет фиксированного оркестратора. Агенты забирают работу из очереди. Хорошо для высокопроизводительных параллельных задач.

### Четыре мультиагентных паттерна

#### Паттерн 1: Конвейер

```
Input ──▶ Agent A ──▶ Agent B ──▶ Agent C ──▶ Output
          (research)  (code)      (review)
```

Каждый агент преобразует данные и передаёт их дальше. Прост для понимания. Сбой на одном этапе блокирует остальные.

#### Паттерн 2: Разветвление / слияние (fan-out / fan-in)

```
                ┌──▶ Agent A ──┐
                │              │
Input ──▶ Split ├──▶ Agent B ──├──▶ Merge ──▶ Output
                │              │
                └──▶ Agent C ──┘
```

Работа разделяется между параллельными агентами, затем результаты сливаются. Хорошо для задач, разбивающихся на независимые подзадачи.

#### Паттерн 3: Оркестратор-воркер

```
                    ┌──────────┐
                    │  Orch.   │
                    └──┬───┬───┘
                  task │   │ task
                 ┌─────┘   └─────┐
                 ▼               ▼
           ┌──────────┐   ┌──────────┐
           │ Worker A │   │ Worker B │
           └──────────┘   └──────────┘
```

Умный оркестратор решает, что делать, делегирует работу воркерам и синтезирует результаты. Сам оркестратор — это агент с инструментами для порождения воркеров.

#### Паттерн 4: Одноранговый рой (peer swarm)

```
         ┌───┐ ◄──── msg ────▶ ┌───┐
         │ A │                  │ B │
         └─┬─┘                  └─┬─┘
           │                      │
      msg  │    ┌───────────┐     │ msg
           └───▶│  Shared   │◄────┘
                │  State    │
           ┌───▶│  / Queue  │◄────┐
           │    └───────────┘     │
      msg  │                      │ msg
         ┌─┴─┐                  ┌─┴─┐
         │ C │ ◄──── msg ────▶ │ D │
         └───┘                  └───┘
```

Центрального оркестратора нет. Агенты общаются напрямую друг с другом. Решения возникают из взаимодействия. Сложнее отлаживать, но масштабируется на множество агентов.

### Когда НЕ использовать мультиагентность

Мультиагентность добавляет сложность. Каждое сообщение между агентами — потенциальная точка сбоя. Отладка превращается из «прочитать один диалог» в «отследить сообщения по пяти агентам».

**Оставайтесь на одном агенте, когда:**
- Задача помещается в одно контекстное окно (менее ~100 тыс. токенов рабочих данных)
- Вам не нужны разные системные промпты для разных этапов
- Последовательное выполнение достаточно быстрое
- Задача достаточно простая, и разделение добавит больше накладных расходов, чем пользы

**Цена сложности:**
- Каждая граница между агентами — это шаг с потерей информации при сжатии: полный контекст агента A сжимается в сообщение для агента B
- Логика координации (кто что делает, когда, в каком порядке) сама становится источником багов
- Растёт задержка: N агентов означает минимум N последовательных вызовов LLM, а если им нужно переписываться туда-сюда — ещё больше
- Стоимость умножается: каждый агент расходует токены независимо

Эмпирическое правило: если задача требует менее 20 вызовов инструментов и помещается в 100 тыс. токенов, оставайтесь на одном агенте.

## Реализация

### Шаг 1: Перегруженный одиночный агент

Вот одиночный агент, пытающийся делать всё сразу. У него один огромный системный промпт и одно контекстное окно, хранящее исследование, код и ревью:

```typescript
type AgentResult = {
  content: string;
  tokensUsed: number;
  toolCalls: number;
};

async function singleAgentApproach(task: string): Promise<AgentResult> {
  const systemPrompt = `You are a full-stack developer. You must:
1. Research the requirements
2. Write the code
3. Review the code for bugs
4. Write tests
Do ALL of these in a single conversation.`;

  const contextWindow: string[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const research = await fakeLLMCall(systemPrompt, `Research: ${task}`);
  contextWindow.push(research.output);
  totalTokens += research.tokens;
  totalToolCalls += research.calls;

  const code = await fakeLLMCall(
    systemPrompt,
    `Given this research:\n${contextWindow.join("\n")}\n\nNow write code for: ${task}`
  );
  contextWindow.push(code.output);
  totalTokens += code.tokens;
  totalToolCalls += code.calls;

  const review = await fakeLLMCall(
    systemPrompt,
    `Given all previous context:\n${contextWindow.join("\n")}\n\nReview the code.`
  );
  contextWindow.push(review.output);
  totalTokens += review.tokens;
  totalToolCalls += review.calls;

  return {
    content: contextWindow.join("\n---\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

Проблемы такого подхода:
- Контекстное окно растёт с каждым этапом. К шагу ревью оно содержит заметки исследования, И код, И предыдущие рассуждения.
- Системный промпт общий. Его нельзя настроить под каждый этап.
- Ничего не выполняется параллельно.

### Шаг 2: Агенты-специалисты

Теперь разделите его. Каждый агент получает одну задачу:

```typescript
type SpecialistAgent = {
  name: string;
  systemPrompt: string;
  run: (input: string) => Promise<AgentResult>;
};

function createSpecialist(name: string, systemPrompt: string): SpecialistAgent {
  return {
    name,
    systemPrompt,
    run: async (input: string) => {
      const result = await fakeLLMCall(systemPrompt, input);
      return {
        content: result.output,
        tokensUsed: result.tokens,
        toolCalls: result.calls,
      };
    },
  };
}

const researcher = createSpecialist(
  "researcher",
  "You are a technical researcher. Read documentation, find patterns, and summarize findings. Output only the facts needed for implementation."
);

const coder = createSpecialist(
  "coder",
  "You are a senior TypeScript developer. Given requirements and research notes, write clean, tested code. Nothing else."
);

const reviewer = createSpecialist(
  "reviewer",
  "You are a code reviewer. Find bugs, security issues, and logic errors. Be specific. Cite line numbers."
);
```

У каждого специалиста сфокусированный промпт. Каждый получает чистое контекстное окно только с необходимым вводом.

### Шаг 3: Координация через сообщения

Свяжите специалистов явной передачей сообщений:

```typescript
type AgentMessage = {
  from: string;
  to: string;
  content: string;
  timestamp: number;
};

async function multiAgentApproach(task: string): Promise<AgentResult> {
  const messages: AgentMessage[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const researchResult = await researcher.run(task);
  messages.push({
    from: "researcher",
    to: "coder",
    content: researchResult.content,
    timestamp: Date.now(),
  });
  totalTokens += researchResult.tokensUsed;
  totalToolCalls += researchResult.toolCalls;

  const coderInput = messages
    .filter((m) => m.to === "coder")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const codeResult = await coder.run(coderInput);
  messages.push({
    from: "coder",
    to: "reviewer",
    content: codeResult.content,
    timestamp: Date.now(),
  });
  totalTokens += codeResult.tokensUsed;
  totalToolCalls += codeResult.toolCalls;

  const reviewerInput = messages
    .filter((m) => m.to === "reviewer")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const reviewResult = await reviewer.run(reviewerInput);
  messages.push({
    from: "reviewer",
    to: "orchestrator",
    content: reviewResult.content,
    timestamp: Date.now(),
  });
  totalTokens += reviewResult.tokensUsed;
  totalToolCalls += reviewResult.toolCalls;

  return {
    content: messages.map((m) => `[${m.from} -> ${m.to}]: ${m.content}`).join("\n\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}
```

Каждый агент получает только сообщения, адресованные ему. Никакого загрязнения контекста. 50 тыс. токенов чтения документации исследователем никогда не попадают в контекст рецензента.

### Шаг 4: Сравнение

```typescript
async function compare() {
  const task = "Build a rate limiter middleware for an Express.js API";

  console.log("=== Single Agent ===");
  const single = await singleAgentApproach(task);
  console.log(`Tokens: ${single.tokensUsed}`);
  console.log(`Tool calls: ${single.toolCalls}`);

  console.log("\n=== Multi-Agent ===");
  const multi = await multiAgentApproach(task);
  console.log(`Tokens: ${multi.tokensUsed}`);
  console.log(`Tool calls: ${multi.toolCalls}`);
}
```

Мультиагентная версия расходует больше токенов в сумме (три агента, три отдельных вызова LLM), но контекст каждого агента остаётся чистым. Качество каждого этапа улучшается, потому что системный промпт специализирован.

## Применение

Этот урок производит переиспользуемый промпт для решения, когда переходить к мультиагентности. См. `outputs/prompt-multi-agent-decision.md`.

## Упражнения

1. Добавьте четвёртого специалиста: агента-«тестировщика», который получает код от программиста и отзыв ревью от рецензента, а затем пишет тесты
2. Измените конвейер так, чтобы рецензент мог отправлять отзыв обратно программисту для цикла доработки (максимум 2 раунда)
3. Преобразуйте последовательный конвейер в разветвление: запустите исследователя и агента-«анализатора требований» параллельно, затем слейте их результаты перед передачей программисту

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|----------------------|
| Рой (swarm) | «Коллективный разум ИИ-агентов» | Набор одноранговых агентов с общим состоянием и без постоянного лидера. Поведение возникает в результате локальных взаимодействий. |
| Оркестратор | «Главный агент» | Агент, среди инструментов которого есть порождение других агентов и управление ими. Он планирует и делегирует, но может не выполнять саму работу. |
| Координатор | «Регулировщик» | Неагентный компонент (часто это просто код, а не LLM), который направляет сообщения между агентами по заданным правилам. |
| Консенсус | «Агенты согласны» | Протокол, согласно которому несколько агентов должны прийти к согласию, прежде чем продолжить работу. Применяется, когда нужно разрешить противоречия между результатами. |
| Эмерджентное поведение | «Агенты сами во всём разобрались» | Паттерны на уровне системы, которые возникают из взаимодействий агентов, хотя явно запрограммированы не были. Они могут быть как полезными, так и вредными. |
| Разветвление / слияние (fan-out / fan-in) | «MapReduce для агентов» | Разделение задачи между параллельными агентами (разветвление) с последующим объединением их результатов (слиянием). |
| Передача сообщений | «Агенты разговаривают друг с другом» | Механизм взаимодействия агентов: структурированные данные передаются от одного агента другому, заменяя общие контекстные окна. |
