# Наследие FIPA-ACL и речевых актов

> Ещё до MCP, ещё до A2A существовал FIPA-ACL. В 2000 году IEEE Foundation for Intelligent Physical Agents ратифицировал язык коммуникации агентов с двадцатью перформативами, двумя языками содержимого и набором протоколов взаимодействия — contract net, subscribe/notify, request-when. Он исчез из индустрии, потому что накладные расходы на онтологии оказались слишком тяжёлыми для веба, но возрождение мультиагентных систем на базе LLM тихо реализует те же идеи заново, только без формальной семантики: JSON-контракты заменяют перформативы, естественный язык заменяет онтологии. Этот урок серьёзно разбирает FIPA-ACL, чтобы вы могли увидеть, какие решения протоколов 2026 года — переизобретение, какие — новизна, и где текущая волна заново столкнётся с проблемами, уже решёнными в 2000-х.

**Тип:** Learn
**Языки:** Python (stdlib)
**Предварительные требования:** Фаза 16 · 01 (Зачем нужна мультиагентность)

## Проблема

Ландшафт протоколов агентов 2026 года переполнен: MCP для инструментов, A2A для агентов, ACP для корпоративного аудита, ANP для децентрализованного доверия, NLIP для контента на естественном языке, плюс CA-MCP и ещё два десятка исследовательских предложений. Каждая спецификация объявляет себя основополагающей.

Честный взгляд состоит в том, что большинство из них заново открывают очень конкретное дерево решений двадцатилетней давности. Теория речевых актов Остина (1962) и Сёрла (1969) дала нам идею «высказывания — это действия». KQML (1993) превратил это в проводной протокол. FIPA-ACL (ратифицирован в 2000 году) произвёл эталонную стандартизацию: двадцать перформативов, языки содержимого SL0/SL1, протоколы взаимодействия для contract-net и subscribe-notify. JADE и JACK были эталонными Java-платформами. Усилия угасли около 2010 года, потому что накладные расходы на онтологии были слишком велики, а веб побеждал.

Когда вы смотрите на `tools/call` в MCP, жизненный цикл задачи в A2A или общее хранилище контекста в CA-MCP, вы смотрите на более мягкий, JSON-нативный пересказ решений FIPA. Знание этого наследия даёт вам две вещи: какие новые «инновации» на самом деле переизобретения, и какие старые режимы сбоя новые спецификации заново откроют.

## Концепция

### Речевые акты в одном абзаце

Остин заметил, что некоторые предложения не описывают мир — они его изменяют. «Я обещаю». «Я прошу». «Я объявляю». Он назвал их перформативными высказываниями. Сёрл формализовал пять категорий: ассертивы, директивы, комиссивы, экспрессивы, декларативы. KQML (Finin et al., 1993) сделал это операциональным для программных агентов: сообщение — это перформатив (действие) плюс содержимое (то, о чём это действие). FIPA-ACL устранил пробелы KQML и стандартизировал около двадцати перформативов.

### Двадцать перформативов FIPA (частичный список)

| Перформатив | Намерение |
|---|---|
| `inform` | «Я сообщаю тебе, что P истинно» |
| `request` | «Я прошу тебя сделать X» |
| `query-if` | «Истинно ли P?» |
| `query-ref` | «Каково значение X?» |
| `propose` | «Я предлагаю сделать X» |
| `accept-proposal` | «Я принимаю предложение» |
| `reject-proposal` | «Я отклоняю предложение» |
| `agree` | «Я согласен сделать X» |
| `refuse` | «Я отказываюсь делать X» |
| `confirm` | «Я подтверждаю, что P истинно» |
| `disconfirm` | «Я отрицаю P» |
| `not-understood` | «Ваше сообщение не удалось разобрать» |
| `cfp` | «Запрос предложений по X» |
| `subscribe` | «Уведоми меня, когда X изменится» |
| `cancel` | «Отмени выполняющийся X» |
| `failure` | «Я попытался выполнить X и потерпел неудачу» |

Полный список — в `fipa00037.pdf` (FIPA ACL Message Structure). Смысл не в том, чтобы заучить его наизусть, — смысл в том, что каждому из этих перформативов в итоге соответствует примитив, который заново добавляет протокол LLM.

### Каноническое сообщение FIPA-ACL

```
(inform
  :sender       agent1@platform
  :receiver     agent2@platform
  :content      "((price IBM 83))"
  :language     SL0
  :ontology     finance
  :protocol     fipa-request
  :conversation-id   conv-42
  :reply-with   msg-17
)
```

Семь полей несут конверт протокола; одно поле (`content`) несёт полезную нагрузку. Остальные поля — это в точности то, что вы переизобретаете каждый раз, когда навешиваете повторы, потоки и онтологию поверх JSON-протокола.

### Две устаревшие платформы

**JADE** (Java Agent DEvelopment framework, 1999–2020-е) была самой используемой FIPA-совместимой средой выполнения. Агенты наследовались от базового класса, обменивались ACL-сообщениями, работали внутри контейнеров и координировались через «поведения» (behaviors). Библиотека протоколов взаимодействия поставлялась с contract-net, subscribe-notify, request-when и propose-accept.

**JACK** (Agent Oriented Software, коммерческая) делала упор на BDI-рассуждения (Belief-Desire-Intention, «убеждение-желание-намерение») поверх сообщений FIPA. Более формальная, менее распространённая.

Обе пришли в упадок, когда веб-стек поглотил сценарии мультиагентности. MCP и A2A — это «контейнеры» времени выполнения 2026 года.

### Почему FIPA угасла

- **Накладные расходы на онтологии.** FIPA требовала общей онтологии для разбора `content`. Согласование онтологий — это многолетний процесс стандартизации. Веб просто использовал HTTP + JSON.
- **Формальная семантика, которой никто не пользовался.** SL (Semantic Language) давал строгие условия истинности, но большинство продакшн-систем использовали произвольное содержимое и игнорировали формализм.
- **Привязка к инструментам.** JADE был только на Java; JACK — коммерческим. Многоязычные команды обходили оба стороной.
- **Интернет выиграл битву за стек.** REST, затем JSON-RPC, затем gRPC заменили транспорт ACL.

### Возрождение на базе LLM — это облегчённая FIPA

Сравните FIPA `request` с `tools/call` в MCP:

```
(request                                {
  :sender  agent1                         "jsonrpc": "2.0",
  :receiver tool-server                   "method":  "tools/call",
  :content "(lookup stock IBM)"           "params":  {"name":"lookup_stock",
  :ontology finance                                   "arguments":{"symbol":"IBM"}},
  :conversation-id c42                    "id": 42
)                                        }
```

Один и тот же конверт, разный синтаксис. Оба несут: кто, кому, намерение, полезную нагрузку, идентификатор корреляции. Ни один не является революцией по сравнению с другим — это разные компромиссы на основе одного и того же дизайна.

Обзор 2025 года авторства Liu et al. («A Survey of Agent Interoperability Protocols: MCP, ACP, A2A, ANP», arXiv:2505.02279) делает эту преемственность явной: MCP соответствует речевым актам использования инструментов, A2A — речевым актам между агентами-пирами, ACP — речевым актам аудиторского следа, ANP — расширениям децентрализованной идентичности. Новые спецификации — это потомки ACL с JSON-синтаксисом и более слабой семантикой.

### Компромисс без прикрас

**Что давала FIPA и чего лишены современные спецификации:**

- Формальную семантику — можно доказать, что `inform` подразумевает, что отправитель считает содержимое истинным.
- Канонический каталог перформативов — не нужно заново спорить, «нужен ли нам `cancel`?».
- Десятилетия паттернов протоколов взаимодействия — contract-net, subscribe-notify, propose-accept — с известными свойствами корректности.

**Что дают современные спецификации, чего не давала FIPA:**

- JSON-нативные полезные нагрузки, совместимые с любым современным инструментом.
- Содержимое на естественном языке, которое LLM могут интерпретировать без ручной онтологии.
- Транспорт веб-стека (HTTP, SSE, WebSocket).
- Обнаружение возможностей через самоописывающиеся документы (`listTools` в MCP, Agent Card в A2A).

Более слабая семантика намерений в обмен на более простую реализацию. Это и есть точный компромисс.

### Протоколы взаимодействия, стоящие переноса

FIPA поставляла около 15 протоколов взаимодействия. Три стоит перенести в мультиагентные системы на базе LLM:

1. **Contract Net Protocol (CNP).** Менеджер выпускает `cfp` (запрос предложений); участники торгов отвечают `propose`; менеджер принимает/отклоняет. Это канонический паттерн рынка задач (Фаза 16 · 16 «Переговоры»).
2. **Subscribe/Notify.** Подписчик отправляет `subscribe`; издатель отправляет `inform` при каждом изменении темы. Это любая событийная шина 2026 года.
3. **Request-When.** «Сделай X, когда выполнится условие Y». Отложенное действие с предусловиями. Аналог 2026 года — отложенные задачи в устойчивых движках рабочих процессов (Фаза 16 · 22 «Масштабирование в продакшне»).

Каждый из них чисто ложится на современные очереди сообщений, HTTP с опросом или потоковую передачу SSE.

### Что ломается, когда вы отказываетесь от онтологии

Без общей онтологии агенты выводят смысл из содержимого на естественном языке. Задокументированный режим сбоя 2026 года — это **семантический дрейф**: два агента используют одно и то же слово (`"customer"`) для чуть разных понятий, агент-получатель действует на основе неверной интерпретации, и ни один валидатор схемы этого не ловит. Требование онтологии в FIPA отклонило бы такое сообщение ещё на этапе разбора.

Смягчения без перехода к полной онтологии:

- JSON Schema на `content` — отклоняет структурные ошибки на уровне канала передачи.
- Типизированные артефакты (A2A) — отклоняют неверную модальность.
- Явный перформатив в конверте — делает намерение однозначным, даже когда содержимое на естественном языке.

### Спецификации 2026 года в сопоставлении с наследием речевых актов

| Современная спецификация | Аналог в FIPA | Что сохраняется | Что отбрасывается |
|---|---|---|---|
| MCP `tools/call` | `request` | явное намерение, идентификатор корреляции | формальная семантика, онтология |
| MCP `resources/read` | `query-ref` | явное намерение, идентификатор корреляции | формальная семантика |
| Жизненный цикл задачи A2A | contract-net + request-when | асинхронный жизненный цикл, переходы состояний | формальные гарантии полноты |
| Потоковые события A2A | subscribe/notify | асинхронная отправка | подписка с типизированным предикатом |
| Общий контекст CA-MCP | доска объявлений (blackboard, Hayes-Roth 1985) | общая память с множественной записью | модель логической согласованности |
| NLIP | содержимое на естественном языке | нативность для LLM | схема |

Если читать таблицу сверху вниз, паттерн такой: сохранить структурный примитив, отбросить формализм, позволить LLM сглаживать неоднозначность.

```figure
sw-contract-net
```

## Реализация

`code/main.py` реализует транслятор FIPA-ACL на чистой стандартной библиотеке. Он кодирует и декодирует канонический конверт ACL и показывает, как каждая форма сообщения MCP / A2A сводится к тем же семи полям. Демонстрация:

- Кодирует пять сообщений в стиле MCP и A2A как FIPA-ACL.
- Декодирует FIPA-ACL обратно в современный эквивалент.
- Запускает игрушечные переговоры Contract Net между одним менеджером и тремя участниками торгов, используя `cfp`, `propose`, `accept-proposal`, `reject-proposal`.

Запуск:

```
python3 code/main.py
```

Вывод — это параллельная трассировка, показывающая каждое современное сообщение и в его JSON-форме 2026 года, и в форме FIPA-ACL, а затем цикл «туда-обратно» для заявки contract-net. Одни и те же протокольные примитивы переживают этот цикл — различается только синтаксис.

## Применение

`outputs/skill-fipa-mapper.md` — это навык, который читает любую спецификацию протокола агентов и строит её отображение на FIPA-ACL. Используйте его перед принятием нового протокола, чтобы ответить на вопрос: «Это действительно новое, или это `inform` с JSON-синтаксисом?»

## Поставка

Не возвращайте FIPA-ACL. Верните его чек-лист:

- Какой примитив намерения (перформатив) у каждого сообщения?
- Есть ли идентификатор корреляции для запроса-ответа и отмены?
- Есть ли явный язык содержимого (JSON-RPC, обычный текст, структурированный типизированный артефакт)?
- Являются ли протоколы взаимодействия полноценными сущностями первого класса, или вы заново реализуете contract-net с нуля?
- Что происходит, когда два агента расходятся в понимании смысла содержимого (семантический дрейф)?

Задокументируйте эти пять вопросов для любого нового протокола перед тем, как выпускать его в продакшн.

## Упражнения

1. Запустите `code/main.py`. Понаблюдайте за циклом кодирования «туда-обратно». Определите, какой перформатив FIPA соответствует `tools/call`, `resources/read` и созданию задачи в A2A.
2. Расширьте демонстрацию contract-net перформативом `cancel`, позволяющим менеджеру отозвать задачу в середине торгов. Какой случай сбоя решает `cancel`, но не решают одни только повторы?
3. Прочитайте FIPA ACL Message Structure (http://www.fipa.org/specs/fipa00037/), разделы 4.1–4.3. Выберите один перформатив, не рассмотренный в этом уроке, и опишите его современный аналог в JSON-RPC.
4. Прочитайте Liu et al., arXiv:2505.02279. Для каждого из MCP, A2A, ACP, ANP перечислите семейства перформативов FIPA, которые они сохраняют и которые отбрасывают.
5. Спроектируйте минимальную JSON Schema для поля `content` перформатива `request` в вашей собственной системе. Что даёт эта схема по сравнению с чистым естественным языком, и чего это стоит?

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Речевой акт | «Высказывание, которое что-то делает» | По Остину и Сёрлу: высказывания как действия. Теоретическая основа ACL. |
| FIPA | «Та старая штука с XML» | IEEE Foundation for Intelligent Physical Agents — организация, стандартизировавшая ACL в 2000 году. |
| ACL | «Agent Communication Language» | Формат конверта FIPA: перформатив + содержимое + метаданные. |
| Перформатив | «Глагол» | Класс намерения сообщения: `inform`, `request`, `propose`, `cfp` и т. д. |
| KQML | «Предшественник FIPA» | Knowledge Query and Manipulation Language (1993). Проще и у́же. |
| Онтология | «Общий словарь» | Формальное определение понятий, о которых может говорить язык содержимого. |
| SL0 / SL1 | «Языки содержимого FIPA» | Уровни 0 и 1 Semantic Language — семейство формальных языков содержимого. |
| Contract Net | «Рынок задач» | Менеджер выпускает cfp; участники торгов предлагают заявки; менеджер принимает предложение. Канонический протокол взаимодействия. |
| Протокол взаимодействия | «Паттерн сообщений» | Последовательность перформативов с известными свойствами корректности: request-when, subscribe-notify и т. д. |
