# Модель примитивов мультиагентных систем

> Четыре примитива, не больше — агент, передача управления (handoff), общее состояние и оркестратор — образуют четырёхмерное пространство проектирования, а основные мультиагентные фреймворки, поставляемые в 2026 году (AutoGen, LangGraph, CrewAI, OpenAI Agents SDK, Microsoft Agent Framework), представляют собой точки в нём. Этот урок строит их с нуля, запускает на них игрушечную систему, а затем проецирует каждый крупный фреймворк на те же оси, чтобы вы могли понять любой новый релиз за один абзац.

**Языки:** Python (stdlib)
**Предварительные требования:** Фаза 14 (Инженерия агентов), фаза 16 · 01 (Зачем нужны мультиагентные системы)

## Проблема

Каждые полгода выходит новый мультиагентный фреймворк. AutoGen в 2023-м. CrewAI в 2024-м. LangGraph и OpenAI Swarm в 2024-м. Google ADK в апреле 2025-го. Microsoft Agent Framework RC в феврале 2026-го. Каждый пресс-релиз утверждает, что это «правильная абстракция».

Если пытаться изучать их по одному, вы выгорите. API выглядят по-разному. Документации расходятся в том, что такое «агент». Один фреймворк называет своё общее состояние «доской объявлений» (blackboard), другой — «пулом сообщений», третий — «StateGraph». Начинаешь подозревать, что вся область просто топчется на месте.

Это не так. Под маркетингом четыре примитива стабильны. Выучите их один раз — и сможете прочитать любой новый фреймворк за один абзац.

## Концепция

### Четыре примитива

1. **Агент (Agent)** — системный промпт плюс список инструментов. Не хранит состояние; каждый запуск начинается с его системного промпта и текущей истории сообщений.
2. **Передача управления (Handoff)** — структурированная передача управления от одного агента к другому. Механически — это либо вызов инструмента, возвращающий нового агента, либо ребро графа, следующее условию.
3. **Общее состояние (Shared state)** — любая структура данных, которую могут читать (иногда — писать) несколько агентов. Пул сообщений, доска объявлений, хранилище ключ-значение, векторная память.
4. **Оркестратор (Orchestrator)** — тот, кто решает, кто говорит следующим. Варианты: явный граф (детерминированный), селектор говорящего на основе большой языковой модели (LLM, мягкий вариант), вызов передачи управления последним говорившим (OpenAI Swarm) или планировщик над очередью (архитектура роя).

Это всё пространство проектирования. Каждый фреймворк выбирает значения по умолчанию для каждой оси; остальное — поверхностный синтаксис.

### Как каждый фреймворк 2026 года отображается на эту модель

| Фреймворк | Агент | Передача управления | Общее состояние | Оркестратор |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | инструмент возвращает Agent | забота вызывающей стороны | следующий вызов передачи управления от LLM |
| AutoGen v0.4 / AG2 | `ConversableAgent` | селектор говорящего в GroupChat | пул сообщений | функция-селектор (LLM или циклический перебор) |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | выходы Task в цепочке | менеджер-LLM или статичный порядок |
| LangGraph | функция-узел | ребро графа + условие | редьюсер `StateGraph` | граф, детерминированно |
| Microsoft Agent Framework | агент + паттерны оркестрации | зависит от паттерна | тред / контекст | зависит от паттерна |
| Google ADK | агент + карточка A2A | задача A2A | артефакты A2A | решает хост |

Поверхностные различия выглядят огромными. Под ними — те же четыре рычага.

### Почему это важно

Как только вы увидели примитивы, сравнение фреймворков превращается в короткий чек-лист:

- Доверяет ли оркестратор маршрутизацию LLM (Swarm) или фиксирует маршрутизацию в коде (LangGraph)?
- Общее состояние — это полная история (GroupChat) или проекция (редьюсер StateGraph)?
- Могут ли агенты изменять промпты друг друга (менеджер CrewAI) или только передавать управление (Swarm)?

Эти три вопроса отвечают на 80% того, какой фреймворк подходит под конкретную задачу. Вы перестаёте искать «лучший мультиагентный фреймворк» и начинаете проектировать под ту ось, которая вам действительно важна.

### Инсайт о состоянии

Каждый примитив, кроме общего состояния, не хранит состояние. Агент — функция от (промпт, инструменты). Передача управления — вызов функции. Оркестратор — планировщик. **Единственная стейтфул-часть системы — общее состояние.** Именно там живут все интересные баги: отравление памяти (Урок 15), порядок сообщений, версионирование, конкуренция при записи.

Фреймворки, скрывающие общее состояние (Swarm), перекладывают проблему на вызывающую сторону. Фреймворки, централизующие его (контрольная точка LangGraph, пул AutoGen), делают его инспектируемым, но перекладывают стоимость координации на реализацию общего состояния.

### Анатомия одного примитива

#### Агент

```
Agent = (system_prompt, tools, model, optional_name)
```

Никакой памяти. Никакого состояния. Два агента с одинаковым системным промптом и инструментами взаимозаменяемы. Всё, что выглядит как состояние конкретного агента, на самом деле находится в общем состоянии или в протоколе передачи управления.

#### Передача управления

```
Handoff = (from_agent, to_agent, reason, payload)
```

Доминируют три реализации:

- **Возвращаемое значение функции** — инструмент возвращает следующего агента. Это паттерн OpenAI Swarm. Агенты несут маршрутизацию в своих схемах инструментов.
- **Ребро графа** — LangGraph. Рёбра декларативны. LLM выдаёт значение; условие выбирает следующий узел.
- **Выбор говорящего** — AutoGen GroupChat. Функция-селектор (иногда сама являющаяся вызовом LLM) читает пул и выбирает, кто говорит следующим.

#### Общее состояние

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

Как минимум — список сообщений. Часто больше: структурированные артефакты (выходы Task в CrewAI), типизированный контекст (редьюсеры LangGraph), внешняя память (MCP, векторная БД).

Две топологии: **полный пул** (каждый агент видит каждое сообщение) и **проекция** (агенты видят представление, ограниченное ролью). Полные пулы просты и плохо масштабируются. Проекции масштабируются, но требуют заранее спроектированной схемы.

#### Оркестратор

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

Четыре разновидности:

- **Статичная** — граф фиксирован на этапе сборки (детерминированный LangGraph, CrewAI Sequential).
- **Выбор LLM** — LLM читает пул и выбирает следующего говорящего (AutoGen, CrewAI Hierarchical).
- **Управляемая передачей** — текущий агент решает, вызывая инструмент передачи управления (Swarm).
- **Управляемая очередью** — воркеры забирают задачи из общей очереди; явного «следующего говорящего» нет (архитектуры роя, Matrix).

### Что меняется между фреймворками

Как только примитивы зафиксированы, остальные проектные решения — это:

- **Стратегия памяти** — эфемерное состояние или долговременное сохранение контрольных точек (механизм сохранения контрольных точек LangGraph).
- **Граница безопасности** — кто может одобрить передачу управления (с участием человека).
- **Учёт стоимости** — бюджеты токенов на агента.
- **Наблюдаемость** — трассировка передач управления, сохранение состояния для повтора.

Всё это реализуемо поверх примитивов. Ни одно из них не является новым примитивом.

## Реализация

`code/main.py` реализует четыре примитива в ~150 строках Python, используя только стандартную библиотеку. Никакой реальной LLM — каждый агент представляет собой заданную в коде политику, чтобы основное внимание оставалось на структуре координации.

Файл экспортирует:

- `Agent` — класс данных с именем, системным промптом, инструментами и функцией-политикой.
- `Handoff` — функция, возвращающая нового агента.
- `SharedState` — потокобезопасный пул сообщений.
- `Orchestrator` — три варианта: `StaticOrchestrator`, `HandoffOrchestrator`, `LLMSelectorOrchestrator` (симулированный).

Демо прогоняет один и тот же трёхагентный конвейер (исследование → написание → рецензия) через все три типа оркестратора и печатает пул сообщений в конце. Видно, что выходы различаются только тем, *кто выбирает следующего*; агенты и общее состояние идентичны во всех прогонах.

Запуск:

```
python3 code/main.py
```

Ожидаемый вывод: три прогона оркестратора, по одному на паттерн. Каждый печатает финальный пул сообщений. Прогон с управлением через передачу достигает меньшего числа агентов, если исследователь решает, что закончил раньше, — это компромисс LLM-маршрутизации в миниатюре.

## Упражнения

1. Запустите `code/main.py` три раза с разными политиками агентов. Понаблюдайте, как выбор оркестратора меняет то, какие агенты запускаются.
2. Реализуйте четвёртый тип оркестратора: управляемый очередью, где агенты опрашивают общее состояние на предмет работы. Какой дедлок может возникнуть и как его обнаружить?
3. Возьмите быстрый старт LangGraph (https://docs.langchain.com/oss/python/langgraph/workflows-agents) и перепишите его как четыре примитива. Какие абстракции LangGraph отображаются 1:1, а какие являются удобными обёртками?

5. Найдите в этой таблице один фреймворк, полностью скрывающий общее состояние. Объясните, что ломается, когда агентам нужно координироваться через передачи управления без повторного чтения истории.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Агент | «LLM с инструментами» | Тройка `(system_prompt, tools, model)`. Не хранит состояние. |
| Передача управления | «Передача управления» | Структурированный вызов, называющий следующего агента и опциональную полезную нагрузку. Три реализации: возвращаемое значение функции, ребро графа, выбор говорящего. |
| Общее состояние | «Память» / «контекст» | Единственная часть мультиагентной системы, хранящая состояние. Пул сообщений или доска объявлений. |
| Оркестратор | «Координатор» | Тот, кто решает, кто выполняется следующим. Статический граф, LLM-селектор, управляемый передачами или очередью. |
| Примитив | «Абстракция» | Одна из четырёх осей, которые параметризует каждый фреймворк. Не отдельная возможность фреймворка. |
| Пул сообщений | «Общая история чата» | Общее состояние с полной историей. Легко анализировать, плохо масштабируется. |
| Проецируемое состояние | «Ограниченное представление» | Специфичный для роли срез общего состояния. Масштабируется, требует проектирования схемы. |
| Выбор говорящего | «Кто говорит следующим» | Паттерн оркестрации, где функция (часто LLM) выбирает следующего агента из группы. |
