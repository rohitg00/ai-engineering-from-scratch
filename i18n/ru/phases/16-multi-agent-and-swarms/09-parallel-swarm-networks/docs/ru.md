# Параллельные / роевые / сетевые архитектуры

> В отличие от супервизора: нет центрального узла принятия решений. Агенты читают общую шину событий, забирают работу асинхронно и записывают результаты обратно. LangGraph явно поддерживает «Swarm Architecture» для децентрализованных, динамических сред. Matrix (arXiv:2511.21686) представляет и поток управления, и поток данных как сериализованные сообщения, передаваемые через распределённые очереди, чтобы устранить узкое место в виде оркестратора. Компромисс явный: детерминированность и прослеживаемость обмениваются на масштабируемость. Рой подходит для задач со множеством независимых подзадач; он не подходит для задач, которым нужен единый согласованный план.

**Тип:** Learn + Build**Языки:** Python (stdlib, `threading`, `queue`)**Предварительные требования:** Фаза 16 · 05 (Supervisor Pattern), Фаза 16 · 04 (Primitive Model)**Время:** ~75 минут
## Проблема

Супервизор масштабируется на несколько воркеров. А что насчёт сотен? Сам супервизор становится узким местом: каждое решение о том, кто что делает, проходит через одного агента. Один медленный шаг плана останавливает всю систему.

Роевые архитектуры переворачивают этот дизайн. Вместо центрального планировщика, распределяющего работу, воркеры сами забирают работу из общей очереди. «Координация» встроена прямо в семантику шины событий. Нет оркестратора; система масштабируется, пока масштабируется очередь.

## Концепция

### Форма

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

Нет оркестратора. Каждый воркер повторяет: забрать задачу, обработать, записать результат (и опционально поставить в очередь последующие задачи).

### Когда рой подходит

- **Много независимых задач.** Скрапинг, преобразование, классификация. Задачи не зависят друг от друга.
- **Работа с переменной длительностью.** Если одни задачи занимают 100 мс, а другие — 10 с, рой автоматически балансирует нагрузку — быстрые воркеры забирают следующие задания. Супервизору же приходится заранее предугадывать длительность.
- **Пропускная способность важнее детерминированности.** Вас интересует общее время завершения, а не строгий порядок.

### Когда рой не работает

- **Упорядоченные рабочие процессы.** Если шагу 3 нужен вывод шага 2, рой рискует запустить шаг 3 раньше, чем завершится шаг 2.
- **Задачи с глобальным планом.** Сложные исследовательские вопросы выигрывают от наличия планировщика. Рой исследователей выдаёт независимые факты, а не связный отчёт.
- **Отладка.** Без центрального журнала и при асинхронной работе воспроизвести баг дорого.

### Matrix (arXiv:2511.21686)

Matrix — статья 2025 года, доводящая идею роя до её естественного завершения: и поток управления, и поток данных — это сериализованные сообщения в распределённых очередях. Нет центрального координатора. Отказоустойчивость обеспечивается долговечностью сообщений. Масштабируемость — забота брокера сообщений, а не самой системы.

Вклад: модель программирования, в которой мультиагентная координация сводится к вопросу «на какой топик сообщений подписан этот агент?», а не «какого агента супервизор выберет следующим?». Это делает систему похожей на pub/sub-сеть событий.

### Рой в графовых фреймворках

Документация LangGraph 2025 года явно описывает «Swarm Architecture» как один из паттернов мультиагентности: агенты — это узлы, но рёбра образуют направленный граф с циклами, и любой узел может быть активирован из общего пула. Воркер выбирает доступную работу по условию, а не по назначению супервизора.

### Режим отказа: голодание и хот-споттинг

Если все воркеры забирают самую быструю доступную задачу, длительные задачи никогда не выбираются, пока не останутся единственными. Классическое голодание очереди (queue starvation).

Способы смягчения:
- Приоритетные очереди с явным старением (повышение приоритета с ростом времени ожидания).
- Специализация воркеров: некоторые воркеры берут только «длинные» задачи.
- Обратное давление: ограничьте, сколько быстрых задач попадает в очередь.

### Связь с маршрутизацией по содержимому

Рой естественно сочетается с маршрутизацией по содержимому (Урок 22). Вместо одной универсальной очереди используйте отдельную очередь для каждого типа сообщений. Специализированные воркеры подписываются только на свой тип. Это основа архитектур на базе шины сообщений, масштабируемых до тысяч агентов.

## Реализация

`code/main.py` реализует рой из 4 воркер-потоков, забирающих задачи из общей `queue.Queue`. Задачи имеют переменную длительность (одни быстрые, другие медленные). Демонстрация сравнивает:

- **Последовательный базовый вариант:** один воркер обрабатывает все задачи по очереди.
- **Фиксированное назначение:** каждая задача заранее закреплена за конкретным воркером (в стиле супервизора).
- **Рой:** воркеры забирают задачи из общей очереди.

Рой автоматически балансирует нагрузку; при фиксированном назначении быстрые воркеры простаивают, если назначенная им задача медленная.

Запустите:

```
python3 code/main.py
```

Вывод показывает количество задач на воркера (рой распределяет их неравномерно, но оптимально) и фактическое (wall-clock) время выполнения.

## Применение

`outputs/skill-swarm-fit.md` оценивает, должна ли задача использовать рой или супервизора. Входные данные: независимость задач, разброс длительности, требования к порядку, потребности в отлаживаемости.

## Поставка

Чек-лист:

- **Приоритетная очередь со старением.** Предотвращает голодание длительных задач.
- **Идемпотентность воркеров.** Задача может быть забрана более одного раза, если воркер аварийно завершится в процессе выполнения. Воркеры должны быть идемпотентными.
- **Долговечная очередь.** Используйте Kafka, Redis Streams или очередь на основе базы данных для продакшена. `queue.Queue` работает только в памяти.
- **Наблюдаемость на уровне задачи.** У каждой задачи есть trace ID; каждый воркер логирует начало и конец с этим ID.
- **Обратное давление.** Если очередь растёт быстрее, чем воркеры её разбирают, замедлите источник задач (producer).

## Упражнения

1. Запустите `code/main.py`. Насколько рой быстрее последовательного варианта на нагрузке с переменной длительностью? Насколько быстрее, чем фиксированное назначение?
2. Добавьте вариант с приоритетной очередью (используйте `queue.PriorityQueue`). Назначайте приоритет по полю задачи «importance». Понаблюдайте, голодают ли задачи с низким приоритетом при непрерывной нагрузке.
3. Реализуйте детектор хот-спотов: логируйте случаи, когда какой-либо воркер обрабатывает в 3 раза больше задач, чем самый медленный воркер. О чём это говорит о распределении длительности задач?
4. Прочитайте аннотацию и раздел 3 статьи Matrix (arXiv:2511.21686). Определите один конкретный компромисс, на который идёт Matrix (выигрыш в масштабируемости), и один, от которого она отказывается (прослеживаемость, детерминированность).
5. Переделайте демонстрацию роя так, чтобы использовать `queue.Queue` из кортежей (task_type, payload), где воркеры подписываются только на конкретные типы. Какие правила маршрутизации имеют смысл, когда задачи неоднородны?

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|----------------|------------------------|
| Роевая архитектура | «Децентрализованные агенты» | Воркеры забирают работу из общей очереди; нет центрального оркестратора. |
| Шина событий | «Агенты подписываются на топики» | Брокер сообщений, который маршрутизирует задачи воркерам по типу или содержимому. |
| Голодание | «Задача так и не выполняется» | Задача с низким приоритетом никогда не выбирается, потому что более приоритетная работа поступает непрерывно. |
| Хот-споттинг | «Один воркер захлёбывается» | Дисбаланс нагрузки, при котором один воркер получает большинство задач. |
| Обратное давление | «Замедлить источник» | Механизм, сигнализирующий вышестоящему звену остановить генерацию, когда очередь заполняется. |
| Идемпотентный воркер | «Безопасно перезапускать» | Задача, обработанная дважды, даёт одинаковый результат. Требуется потому, что воркеры могут аварийно завершаться в процессе выполнения. |
| Долговечная очередь | «Переживает сбои» | Очередь на диске или реплицированном хранилище; задачи не теряются при аварийном завершении воркера. |
| Фреймворк Matrix | «Полноценный рой на передаче сообщений» | И поток данных, и поток управления — сериализованные сообщения в распределённых очередях. |
