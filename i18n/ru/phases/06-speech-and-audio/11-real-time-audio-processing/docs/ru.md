# Обработка аудио в реальном времени

> Пакетные конвейеры обрабатывают файл. Конвейеры реального времени обрабатывают следующие 20 миллисекунд до того, как поступят следующие 20. Любой разговорный ИИ, вещательная студия и телефонный бот живут и умирают по этому бюджету задержки.

**Тип:** Build**Языки:** Python**Предварительные требования:** Фаза 6 · 02 (Spectrograms), Фаза 6 · 04 (ASR), Фаза 6 · 07 (TTS)**Время:** ~75 минут
## Проблема

Вы хотите голосового ассистента, который ощущается живым. Задержка человеческого разговорного чередования реплик (turn-taking) составляет ~230 мс (от тишины до ответа). Всё, что выше 500 мс, ощущается роботизированным; выше 1500 мс — сломанным. Бюджет полного цикла **услышать → понять → ответить → сказать** в 2026 году таков:

| Этап | Бюджет |
|-------|--------|
| Микрофон → буфер | 20 мс |
| VAD | 10 мс |
| ASR (потоковый) | 150 мс |
| LLM (первый токен) | 100 мс |
| TTS (первый фрагмент) | 100 мс |
| Рендер → динамик | 20 мс |
| **Итого** | **~400 мс** |

Moshi (Kyutai, 2024) показала 200 мс в полнодуплексном режиме. GPT-4o-realtime (2024) показывает ~320 мс. Каскадные конвейеры в 2022 году поставлялись с задержкой 2500 мс. Десятикратное улучшение достигнуто за счёт трёх приёмов: (1) потоковая обработка везде, (2) асинхронный конвейер с частичными результатами, (3) прерываемая генерация.

## Концепция

![Потоковый аудиоконвейер с кольцевым буфером, VAD-затвором, прерыванием](../assets/real-time.svg)

**Кадр / фрагмент / окно.** Аудио в реальном времени поступает блоками фиксированного размера. Распространённый выбор: 20 мс (320 сэмплов при 16 кГц). Всё, что идёт дальше по конвейеру, должно успевать за этим темпом.

**Кольцевой буфер.** Циклический буфер фиксированного размера. Поток-производитель записывает новые кадры, поток-потребитель их читает. Предотвращает выделения памяти на горячем пути. Размер ≈ максимальная задержка × частота дискретизации; 2-секундное кольцо при 16 кГц = 32 000 сэмплов.

**VAD (Voice Activity Detection, детектор голосовой активности).** Перекрывает дальнейшую обработку, когда никто не говорит. Silero VAD 4.0 (2024) выполняется <1 мс на 30-мс кадр на CPU. `webrtcvad` — более старая альтернатива.

**Потоковый ASR.** Модели, выдающие частичные транскрипты по мере поступления аудио. Parakeet-CTC-0.6B в потоковом режиме (NeMo, 2024) даёт 2–5% WER при задержке 320 мс. Whisper-Streaming (Macháček et al., 2023) разбивает Whisper на фрагменты для почти-потоковой работы с задержкой ~2 с.

**Прерывание (interruption).** Когда пользователь говорит, пока ассистент говорит, нужно (а) обнаружить перебивание (barge-in), (б) остановить TTS, (в) отбросить оставшийся вывод LLM. Всё это в пределах 100 мс, иначе пользователь воспримет ассистента как «глухого».

**Транспорт WebRTC Opus.** Кадры по 20 мс, 48 кГц, адаптивный битрейт 8–128 кбит/с. Стандарт для браузера и мобильных устройств. LiveKit, Daily.co, Pion — стеки 2026 года для построения голосовых приложений.

**Джиттер-буфер.** Сетевые пакеты приходят не по порядку / с опозданием. Джиттер-буфер переупорядочивает и сглаживает их; слишком маленький → слышимые провалы, слишком большой → задержка. Типично 60–80 мс.

### Типичные подводные камни

- **Конкуренция потоков.** GIL Python + тяжёлые модели могут морить голодом аудиопоток. Используйте библиотеку аудио с C-колбэками (sounddevice, PortAudio) и держите Python вне горячего пути.
- **Задержка от передискретизации.** Ресемплинг внутри конвейера добавляет 5–20 мс. Либо выполняйте ресемплинг заранее, либо используйте ресемплер с нулевой задержкой (PolyPhase, `soxr_hq`).
- **Прогрев TTS.** Даже быстрый TTS вроде Kokoro имеет разогрев 100–200 мс на первом запросе. Кешируйте модель и прогрейте её фиктивным запуском перед первой реальной репликой.
- **Подавление эха.** Без AEC вывод TTS повторно попадает в микрофон и запускает ASR на собственном голосе бота. WebRTC AEC3 — стандарт с открытым исходным кодом по умолчанию.

## Постройте это

### Шаг 1: кольцевой буфер

```python
import collections

class RingBuffer:
    def __init__(self, capacity):
        self.buf = collections.deque(maxlen=capacity)
    def write(self, frame):
        self.buf.extend(frame)
    def read(self, n):
        return [self.buf.popleft() for _ in range(min(n, len(self.buf)))]
    def level(self):
        return len(self.buf)
```

Ёмкость определяет максимальную задержку буферизации. 32 000 сэмплов при 16 кГц = 2 с.

### Шаг 2: VAD-затвор

```python
def simple_energy_vad(frame, threshold=0.01):
    return sum(x * x for x in frame) / len(frame) > threshold ** 2
```

## Ловушки

- **Буферизация 500 мс «на всякий случай».** Буфер *и есть* ваш порог задержки. Уменьшайте его.
- **Отсутствие закрепления потоков.** Аудиоколбэк на потоке с приоритетом ниже, чем у UI, = сбои под нагрузкой.
- **Слишком маленькие фрагменты TTS.** Фрагменты короче 200 мс делают артефакты вокодера слышимыми. 320-мс фрагменты — оптимальная точка.
- **Отсутствие джиттер-буфера.** Реальные сети подвержены джиттеру; без сглаживания вы получаете щелчки.
- **Обработка ошибок в одну попытку.** Аудиоконвейеры должны быть устойчивы к сбоям. Одно исключение убивает сессию.

## Упражнения

1. **Лёгкое.** Запустите `code/main.py`. Симулирует кольцевой буфер + энергетический VAD; выводит задержки этапов для фиктивного 10-секундного потока.
2. **Среднее.** Используя `sounddevice`, постройте сквозной (passthrough) цикл, который обрабатывает ваш микрофон кадрами по 20 мс и выводит состояние VAD на каждом кадре.
3. **Сложное.** Постройте полнодуплексный эхо-тест с `aiortc`: браузер → WebRTC → Python → WebRTC → браузер. Измерьте сквозную задержку (glass-to-glass) с помощью импульса 1 кГц.

## Ключевые термины

| Термин | Что говорят люди | Что это на самом деле означает |
|------|-----------------|-----------------------|
| Кольцевой буфер | Циклическая очередь | FIFO фиксированного размера, без блокировок (или с SPSC-блокировкой) для аудиокадров. |
| VAD | Затвор тишины | Модель или эвристика, отмечающая речь и не-речь. |
| Потоковый ASR | STT в реальном времени | Выдаёт частичный текст по мере поступления аудио; ограниченное упреждение (lookahead). |
| Джиттер-буфер | Сетевой сглаживатель | Очередь, переупорядочивающая пакеты, пришедшие не по порядку; типично 60–80 мс. |
| AEC | Подавление эха | Вычитает путь обратной связи «динамик → микрофон». |
| Barge-in | Перебивание пользователем | Система обнаруживает речь пользователя посреди TTS; должна отменить воспроизведение. |
| Полный дуплекс | Одновременно в обе стороны | Пользователь и бот могут говорить одновременно; Moshi работает в полном дуплексе. |
