# Хаос-инжиниринг для LLM в продакшене

> Хаос-инжиниринг (chaos engineering) для LLM — самостоятельная дисциплина в 2026 году. Пререквизиты перед запуском экспериментов в продакшене: определённые SLI/SLO, наблюдаемость по трассам, метрикам и логам, автоматизированный откат, операционные инструкции (runbook'и), дежурство (on-call). Архитектура состоит из четырёх плоскостей: управления (control; планировщик экспериментов), целевой (target; сервисы, инфраструктура, хранилища данных), безопасности (safety; защита + прерывание + фильтры трафика) и наблюдаемости (observability; метрики + трассы + логи). Отдельный цикл обратной связи (feedback) ведёт к корректировке SLO. Защитные ограничения (guardrails) обязательны: алерты по скорости расходования бюджета (burn-rate alerts) приостанавливают эксперименты, если дневное расходование бюджета ошибок превышает ожидаемое более чем в 2 раза; окна подавления + корреляция по trace-ID устраняют шум алертов. Периодичность: еженедельно — небольшой канареечный эксперимент + обзор SLO; ежемесячно — командные учения (game day) + постмортем; ежеквартально — межкомандный аудит устойчивости + картирование зависимостей. LLM-специфичные эксперименты: перегрузка памяти, сетевые сбои, отказы провайдера, некорректные промпты, штормы вытеснения KV-кеша. Инструменты: Harness Chaos Engineering (рекомендации на основе LLM, снижение радиуса воздействия, интеграция MCP-инструментов); LitmusChaos (CNCF); Chaos Mesh (CNCF, нативный для Kubernetes).

**Тип:** Learn
**Языки:** Python (стандартная библиотека, учебный симулятор хаос-экспериментов)
**Пререквизиты:** Фаза 17 · 23 (SRE для ИИ), фаза 17 · 13 (Наблюдаемость)
**Время:** ~60 минут

## Цели обучения

- Назвать пять пререквизитов хаос-инжиниринга (SLI/SLO, наблюдаемость, откат, операционные инструкции, дежурство) и объяснить, почему пропуск любого из них ломает практику.
- Схематично представить четыре плоскости (управления, целевую, безопасности и наблюдаемости) и цикл обратной связи в SLO.
- Перечислить пять LLM-специфичных экспериментов (перегрузка памяти, сетевой сбой, отказ провайдера, некорректный промпт, шторм вытеснения KV).
- Выбрать инструмент — Harness, LitmusChaos, Chaos Mesh — исходя из стека.

## Проблема

Хаос-тестирование в традиционных стеках — устоявшаяся практика. Стеки LLM добавляют новые режимы отказа. Промпт на 4K токенов с «отравляющим» символом останавливает токенизатор на 12 секунд. Вышестоящий провайдер возвращает 429; ваш шлюз повторяет запрос; ваш сервис уходит в OOM из-за усиленного повторами параллелизма. Шторм вытеснения KV-кеша при всплеске нагрузки вызывает каскады повторного предзаполнения (prefill), которые насыщают вычислительные ресурсы.

Ничего из этого не проявляется в юнит-тестах. Хаос-инжиниринг — это способ обнаружить такие проблемы раньше, чем это сделают пользователи.

## Концепция

### Пререквизиты

Не запускайте хаос в продакшене без:

1. **SLI/SLO** — определённые индикаторы и цели уровня обслуживания.
2. **Наблюдаемость (observability)** — трассы, метрики, логи, подключённые к панелям мониторинга.
3. **Автоматизированный откат** — откат переключением политики (policy-flag rollback), фаза 17 · 20.
4. **Операционные инструкции (runbook'и)** — структурированные, фаза 17 · 23.
5. **Дежурство (on-call)** — есть кто отреагирует.

Отсутствие любого из них означает, что хаос превращается в реальный инцидент.

### Четыре плоскости + обратная связь

**Плоскость управления (control plane)** — планировщик экспериментов (рабочий процесс Litmus, расписание Chaos Mesh, интерфейс Harness).

**Целевая плоскость (target plane)** — сервисы, поды, узлы, балансировщики нагрузки, хранилища данных.

**Плоскость безопасности (safety plane)** — аварийный выключатель, окна подавления, ограничения радиуса воздействия, проверка по бюджету ошибок.

**Плоскость наблюдаемости (observability plane)** — обычные метрики + корреляция по trace-ID для различения сбоев, вызванных хаосом, и естественных сбоев.

**Цикл обратной связи (feedback loop)** — результаты используются для корректировки SLO, обновления операционных инструкций и исправлений кода.

### Защитные ограничения (guardrails) обязательны

- **Алерт по скорости расходования бюджета (burn-rate alert)**: приостановить эксперимент, если дневное расходование бюджета ошибок превышает ожидаемое более чем в 2 раза.
- **Окна подавления (suppression windows)**: отключать алерты, не связанные с экспериментом, в пределах радиуса воздействия на время эксперимента.
- **Корреляция по trace-ID**: все ошибки, вызванные экспериментом, помечаются тегом, чтобы дежурный (on-call) мог отфильтровать дубликаты.

### Пять LLM-специфичных экспериментов

1. **Перегрузка памяти (memory overload)** — вызвать шторм вытеснения KV-кеша (KV cache preemption storm), отправляя запросы с длинным контекстом при высокой степени параллелизма. Наблюдайте: сервис плавно сбрасывает нагрузку или падает?

2. **Сетевой сбой (network failure)** — разорвать связь между шлюзом инференса и провайдером. Наблюдайте: срабатывает ли резервный вариант (fallback) в рамках SLA? (Фаза 17 · 19)

3. **Симуляция отказа провайдера (provider outage simulation)** — 100% ответов 429 от OpenAI. Наблюдайте: переключается ли маршрутизация на Anthropic (failover)? (Фаза 17 · 16, 19)

4. **Некорректный промпт (malformed prompt)** — внедрить данные, останавливающие токенизатор (например, глубоко вложенный Unicode, огромная кодовая точка UTF-8). Наблюдайте: блокирует ли один запрос воркер?

5. **Шторм вытеснения KV (KV eviction storm)** — вызвать вытеснение, исчерпав бюджет блоков vLLM. Наблюдайте: восстанавливается ли LMCache, или сервис деградирует?

### Периодичность

- **Еженедельно** — небольшие канареечные эксперименты в тестовой среде, возможно на 5% прод-трафика.
- **Ежемесячно** — запланированные командные учения по конкретному сценарию; участие нескольких команд; постмортем.
- **Ежеквартально** — межкомандный аудит устойчивости; обновление карты зависимостей.

### Инструментарий

- **Harness Chaos Engineering** — коммерческий; рекомендации по экспериментам на основе ИИ; снижение радиуса воздействия; интеграция MCP-инструментов.
- **LitmusChaos** — проект CNCF уровня Graduated; построен на рабочих процессах Kubernetes.
- **Chaos Mesh** — проект CNCF уровня Sandbox; нативный для Kubernetes, в стиле CRD.
- **Gremlin** — коммерческий; широкая поддержка.
- **AWS FIS** / **Azure Chaos Studio** — управляемые облачные предложения.

### Начинаем с малого

Первый эксперимент: уничтожение пода одной реплики декодирования при стабильном трафике. Наблюдайте перенаправление трафика и восстановление. Если это работает и выглядит безопасно, переходите к сетевому хаосу.

Первый LLM-специфичный эксперимент: в течение 5 минут подменять ответы одного провайдера на 429. Наблюдайте переход к резервному варианту (fallback). Большинство команд обнаруживают, что этот механизм не был полностью протестирован.

### Цифры, которые стоит запомнить

- Четыре плоскости: управления, целевая, безопасности, наблюдаемости.
- Пауза по скорости расходования бюджета: превышение ожидаемого дневного расходования бюджета в 2 раза.
- Периодичность: еженедельный канареечный эксперимент, ежемесячные командные учения, ежеквартальный аудит.
- Пять LLM-экспериментов: память, сеть, провайдер, некорректный промпт, шторм KV.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|--------|--------------------|-------------------------------|
| SLI / SLO | «целевые показатели сервиса» | Индикатор + цель; обязательный пререквизит |
| Радиус воздействия (blast radius) | «область охвата» | Набор сервисов и пользователей, затронутых экспериментом |
| Алерт по скорости расходования бюджета (burn-rate alert) | «проверка бюджета» | Срабатывает, когда скорость расходования бюджета ошибок более чем в 2 раза превышает ожидаемую |
| Командные учения (game day) | «ежемесячная тренировка» | Запланированное межкомандное учение по хаос-инжинирингу |
| LitmusChaos | «рабочий процесс CNCF» | Инструмент хаос-инжиниринга для Kubernetes, проект CNCF уровня Graduated |
| Chaos Mesh | «CRD CNCF» | Нативный для Kubernetes инструмент хаос-инжиниринга, проект CNCF уровня Sandbox |
| Harness CE | «коммерческий, с поддержкой ИИ» | Хаос-инжиниринг Harness с рекомендациями на основе ИИ |
| Некорректный промпт (malformed prompt) | «бомба для токенизатора» | Входные данные, останавливающие токенизацию |
| Шторм вытеснения KV (KV eviction storm) | «каскад вытеснений» | Массовое вытеснение, запускающее повторные предзаполнения |
