# Нагрузочное тестирование LLM API — почему k6 и Locust лгут

> Традиционные инструменты нагрузочного тестирования (load testing) не были рассчитаны на потоковые ответы, переменную длину вывода, метрики на уровне токенов или насыщение GPU. Большинство команд попадают в две ловушки. Ловушка GIL: измерение на уровне токенов в Locust выполняет токенизацию на стороне клиента под Python GIL, который конкурирует с генерацией запросов при высокой конкурентности; накопившаяся очередь токенизации завышает сообщаемую межтокенную задержку (inter-token latency) — узким местом оказывается клиент, а не сервер. Ловушка единообразия промптов: одинаковые промпты в цикле тестируют только одну точку распределения токенов; реальный трафик имеет переменную длину и разнообразные совпадения по префиксу. LLMPerf решает эту проблему флагами `--mean-input-tokens` + `--stddev-input-tokens`. Карта инструментов на 2026 год: LLM-специализированные (GenAI-Perf, LLMPerf, LLM-Locust, guidellm) — для точности на уровне токенов; **k6 v2026.1.0** + **k6 Operator 1.0 GA (сентябрь 2025)** — с поддержкой стриминга и распределённого тестирования, нативного для Kubernetes, через CRD TestRun/PrivateLoadZone, лучший выбор для гейтов CI/CD; Vegeta — для насыщения с постоянной частотой запросов на Go; Locust 2.43.3 — только с расширением LLM-Locust для стриминга. Паттерны нагрузки: установившаяся нагрузка (steady-state), нарастание (ramp), всплеск (spike; тест автомасштабирования), длительная нагрузка (soak; выявление утечек памяти).

**Тип:** Build
**Языки:** Python (стандартная библиотека, игрушечный генератор реалистичных промптов + сборщик задержек)
**Предварительные требования:** Фаза 17 · 08 (метрики инференса), Фаза 17 · 03 (автомасштабирование GPU)
**Время:** ~75 минут

## Цели обучения

- Объяснить два антипаттерна (ловушка GIL, ловушка единообразия промптов), из-за которых обычные инструменты нагрузочного тестирования лгут для LLM API.
- Выбрать инструмент под конкретную задачу: LLMPerf (бенчмарк-прогон), k6 + расширение для стриминга (гейт CI), guidellm (крупномасштабный синтетический тест), GenAI-Perf (референсный инструмент NVIDIA).
- Спроектировать четыре паттерна нагрузки (установившаяся нагрузка, нарастание, всплеск, длительная нагрузка) и назвать режим отказа, который выявляет каждый из них.
- Построить реалистичное распределение промптов на основе среднего и стандартного отклонения длины входа, а не фиксированной длины.

## Проблема

Вы протестировали свою конечную точку LLM API в k6 на 500 одновременных пользователях. Она выдержала. Вы задеплоили. В продакшене при 200 реальных пользователях сервис лёг — P99 TTFT взлетел, GPU оказались загружены под завязку.

Произошли две вещи. Во-первых, k6 отправлял 500 одинаковых промптов — объединение запросов (request coalescing) и кеширование префиксов создавали иллюзию, что вы обрабатываете 500 параллельных декодирований, тогда как на самом деле обрабатывалось одно. Во-вторых, k6 не отслеживает межтокенную задержку в потоковых ответах так, как её воспринимает глаз; он видит одно HTTP-соединение, а не 500 токенов, приходящих с разными интервалами.

Нагрузочное тестирование LLM — отдельная дисциплина.

## Концепция

### Ловушка GIL (Locust)

Locust написан на Python и выполняет токенизацию на стороне клиента под GIL. При высокой конкурентности токенизатор выстраивается в очередь позади генерации запросов. Сообщаемая межтокенная задержка включает накопившуюся на клиенте очередь токенизации. Вам кажется, что медленный сервер, а на самом деле медленный тестовый харнесс.

Решение: расширение LLM-Locust переносит токенизацию в отдельные процессы, либо используйте харнесс на компилируемом языке (k6, LLMPerf с tokenizers.rs).

### Ловушка единообразия промптов

Все известные инструменты нагрузочного тестирования позволяют настроить один промпт. В цикле из 10 000 итераций каждый раз отправляется абсолютно одинаковый промпт. Сервер каждый раз видит один и тот же префикс — попадания в кеш префиксов приближаются к 100%, пропускная способность выглядит отлично.

Решение: сэмплировать промпты из распределения. LLMPerf использует `--mean-input-tokens 500 --stddev-input-tokens 150` — разная длина, разное содержание.

### Четыре паттерна нагрузки

1. **Установившаяся нагрузка** — постоянный RPS в течение 30-60 минут. Выявляет: базовые регрессии производительности.
2. **Нарастание** — линейное увеличение RPS от 0 до целевого значения за 15 минут. Выявляет: точку излома по ёмкости (capacity breakpoint), аномалии разогрева.
3. **Всплеск** — внезапный рост RPS в 3-10 раз на 2 минуты, затем возврат к норме. Выявляет: задержку автомасштабирования, насыщение очереди, влияние холодного старта.
4. **Длительная нагрузка** — установившаяся нагрузка в течение 4-8 часов. Выявляет: утечки памяти, дрейф пула соединений, переполнение системы наблюдаемости.

### Карта инструментов 2026 года

**LLMPerf** (Anyscale) — Python, но токенизация на Rust. Распределение промптов задаётся средним и стандартным отклонением. С поддержкой стриминга. Лучший выбор по умолчанию для прогонов производительности.

**NVIDIA GenAI-Perf** — референсный инструмент NVIDIA. Использует клиент Triton; всеобъемлющее покрытие метрик. Обратите внимание: его ITL исключает TTFT, а у LLMPerf — включает. Два инструмента выдают разный TPOT для одного и того же сервера.

**LLM-Locust** (TrueFoundry) — расширение Locust, устраняющее ловушку GIL. Знакомый DSL Locust + метрики стриминга.

**guidellm** — синтетический бенчмаркинг большого масштаба.

**k6 v2026.1.0** + **k6 Operator 1.0 GA (сентябрь 2025)**:
- Сам k6 (Go, компилируемый, без GIL) добавил метрики с поддержкой стриминга.
- k6 Operator использует CRD TestRun / PrivateLoadZone для распределённого тестирования, нативного для Kubernetes.
- Лучший выбор для гейтов CI/CD и тестирования SLA.

**Vegeta** — Go, проще, чем k6. Насыщение HTTP с постоянной частотой запросов. Не рассчитан на специфику LLM, но хорош для тестирования шлюзов и ограничений частоты запросов.

**Locust 2.43.3 «из коробки»** — подвержен ловушке GIL для LLM. Только с расширением LLM-Locust.

### SLA-гейт в CI

Запускайте k6 на PR со следующими параметрами:

- 30-50 итераций на базовом уровне RPS.
- Гейт: P50/P95 TTFT, доля 5xx < 5%, TPOT ниже порога.
- Ломайте сборку при нарушении.

### Реалистичное распределение промптов

Стройте распределение на основе реальных выборок трафика (если они есть) или опубликованных распределений (например, промпты ShareGPT для чата, HumanEval для кода). Передавайте среднее и стандартное отклонение в LLMPerf. Любой ценой избегайте цикла с одним промптом.

### Цифры, которые стоит запомнить

- k6 Operator 1.0 GA: сентябрь 2025 года.
- k6 v2026.1.0: метрики с поддержкой стриминга.
- Типичный прогон LLMPerf: 100-1000 запросов при конкурентности X.
- Типичный CI-гейт: 30-50 итераций на PR.
- Четыре паттерна: установившаяся нагрузка, нарастание, всплеск, длительная нагрузка.
