# Разделение prefill и decode — NVIDIA Dynamo и llm-d

> Prefill ограничен вычислениями (compute-bound), decode ограничен пропускной способностью памяти (memory-bound). Совмещение обоих на одном GPU впустую растрачивает один из ресурсов. Разделение распределяет их по отдельным пулам и передаёт KV-кеш между ними через NIXL (RDMA/InfiniBand или резервный вариант — TCP). NVIDIA Dynamo (анонс на GTC 2025, релиз 1.0 GA) работает поверх vLLM/SGLang/TRT-LLM — её Planner Profiler и SLA Planner автоматически подбирают соотношение prefill:decode для соблюдения SLO. NVIDIA публикует прирост пропускной способности примерно такого порядка — developer.nvidia.com (2025-06) показывает прирост ~6x для DeepSeek-R1 MoE на GB200 NVL72 + Dynamo в режиме средней задержки, а страница продукта Dynamo (developer.nvidia.com, без даты) заявляет о приросте MoE-пропускной способности до 50x на GB300 NVL72 + Dynamo по сравнению с Hopper. Цифра «30x» — это агрегированная оценка сообщества по отчётам о полном стеке Blackwell + Dynamo + DeepSeek-R1; мы не нашли ни одного первичного источника, указывающего ровно 30x, поэтому относитесь к ней как к ориентировочному утверждению. llm-d (Red Hat + AWS) — решение, нативное для Kubernetes: prefill / decode / router работают как независимые Services с HPA для каждой роли. llm-d 0.5 добавляет иерархическую выгрузку KV (KV offloading), маршрутизацию LoRA с учётом кеша, сетевой уровень UCCL, scale-to-zero. Экономика: внутренняя сводка по нескольким раскрытиям клиентов показывает экономию 30–40% при инференс-бюджете уровня $2M (то есть $600-800K/год) при переходе с совмещённого обслуживания на разделённое с Dynamo при неизменном SLA; конкретная цифра $2M→$600-800K — это внутренний композит, а не единый опубликованный кейс — используйте её как ориентир порядка величины, а не как ссылку на источник. Короткие промпты (<512 токенов, короткий вывод) не оправдывают затрат на передачу.

## Проблема

Вы запускаете Llama 3.3 70B на 8 H100. При смешанной нагрузке (длинные промпты + короткие ответы) GPU простаивают во время decode, потому что основная часть вычислений уходит на prefill. При другой нагрузке (короткие промпты + длинные ответы) происходит обратное. Совмещённые prefill и decode означают избыточное резервирование обоих ресурсов.

Влияние на бюджет: 20-40% времени GPU тратится впустую на не тот ресурс. Вы платите за вычислительную мощность H100, чтобы выполнять ограниченный памятью decode, или платите за пропускную способность HBM H100, чтобы выполнять ограниченный вычислениями prefill. И то, и другое — дорогие потери.

Разделение распределяет prefill и decode по отдельным пулам, размер каждого из которых подобран под его узкое место. KV-кеш передаётся из пула prefill в пул decode через высокоскоростное межсоединение.

## Концепция

### Почему узкие места различаются

**Prefill** — прогон трансформера по всему входному промпту за один forward-проход. Доминируют матричные умножения; ограничение по вычислениям. H100 FP8 даёт ~2000 TFLOPS полезной пропускной способности. Эффективность батчинга высокая — один forward-проход обрабатывает много токенов.

**Decode** — генерация по одному токену за раз с чтением всех весов на каждой итерации. Ограничение по пропускной способности памяти. HBM3 даёт ~3 ТБ/с. Эффективность батчинга высокая только при высокой конкурентности — чтение весов амортизируется по пакету.

Совмещение: вы покупаете GPU, оптимизированные под оба режима. H100 хорош в обоих, но стоит одинаково в любом случае. На масштабе вам нужен пул prefill на H100 с упором на вычисления и пул decode на H200 с упором на память, либо с агрессивным квантованием.

### Архитектура

```
            ┌──────────────┐
  Request → │    Router    │ ───────────────────────┐
            └──────┬───────┘                        │
                   │                                │
                   ▼ (prompt only)                  │
            ┌──────────────┐    KV cache    ┌───────▼──────┐
            │ Prefill pool │ ─── NIXL ────► │ Decode pool  │
            │  (compute)   │                │  (memory)    │
            └──────────────┘                └──────┬───────┘
                                                   │ tokens
                                                   ▼
                                                 Client
```

NIXL — это межузловой транспорт NVIDIA. Использует RDMA/InfiniBand, когда доступны, иначе — резервный вариант TCP. Задержка передачи реальна — обычно 20-80 мс для KV-кеша промпта на 4K токенов на модели 70B FP8. Именно поэтому короткие промпты не оправдывают разделение: издержки передачи превышают экономию.

### Dynamo и llm-d

**NVIDIA Dynamo** (анонс на GTC 2025, релиз 1.0 GA):
- Работает поверх vLLM, SGLang, TRT-LLM как оркестратор.
- Planner Profiler измеряет нагрузку, SLA Planner автоматически настраивает соотношение prefill:decode.
- Ядро на Rust, расширяемость на Python.
- Прирост пропускной способности: NVIDIA сообщает о 6x для DeepSeek-R1 MoE на GB200 NVL72 + Dynamo в режиме средней задержки (developer.nvidia.com, 2025-06); сообщения сообщества о «до 30x» на полных стеках Blackwell + Dynamo + DeepSeek-R1 не подкреплены единым первичным источником, их стоит считать ориентировочными.
- GB300 NVL72 + Dynamo: до 50x MoE-пропускной способности по сравнению с Hopper согласно странице продукта Dynamo (developer.nvidia.com, без даты).

**llm-d** (Red Hat + AWS, нативное решение для Kubernetes):
- Prefill / decode / router работают как независимые Kubernetes Services.
- HPA для каждой роли с сигналами глубины очереди (prefill) / использования KV (decode).
- `topologyConstraint packDomain: rack` размещает клики prefill+decode на одной стойке для высокоскоростной передачи KV.
- llm-d 0.5 (2026): иерархическая выгрузка KV, маршрутизация LoRA с учётом кеша, сетевой уровень UCCL, scale-to-zero.

Используйте Dynamo, если нужен управляемый оркестратор-надстройка. Используйте llm-d, если нужны нативные для Kubernetes примитивы и вы привержены экосистеме CNCF.

### Экономика

Внутренний композит (не единый опубликованный кейс — ориентир порядка величины):

- $2M/год расходов на инференс при совмещённом обслуживании.
- Переход на разделённое обслуживание с Dynamo.
- Тот же объём запросов, тот же SLA по P99 задержке.
- Заявленная экономия: $600K–$800K/год (снижение на 30–40%).
- Без нового оборудования.

Мы синтезируем эту цифру из нескольких раскрытий клиентов, а не из единого цитируемого кейса; ближайшая опубликованная точка данных — у Baseten: TTFT быстрее в 2 раза / пропускная способность выше на 61% с маршрутизацией по KV в Dynamo (baseten.co, 2025-10), и прогноз VAST + CoreWeave о 60–130% больше токенов на доллар при коэффициенте попаданий KV 40–60% (vastdata.com, 2025-12). Экономия достигается за счёт правильного подбора размера каждого пула; нагрузки с большим весом prefill (RAG с префиксами от 8K токенов) выигрывают больше, чем сбалансированные.

### Когда НЕ стоит разделять

- Промпты < 512 токенов и вывод < 200 токенов: издержки передачи перевешивают выигрыш.
- Маленький кластер (< 4 GPU): недостаточно разнообразия пулов.
- Команда не может обслуживать два GPU-пула с масштабированием по ролям: Dynamo помогает, но не тривиально.
- Нет фабрики RDMA: издержки передачи по TCP выше.

### Маршрутизатор интегрируется с Phase 17 · 11

Разделённые маршрутизаторы учитывают KV-кеш (Phase 17 · 11). Запрос попадает в пул decode, который хранит его префикс, — если совпадения нет, он проходит путь prefill → decode. Коэффициент попаданий и разделение усиливают друг друга — маршрутизатор с учётом кеша определяет, нужен ли вообще новый prefill.

### Настоящие цифры — у MoE на Blackwell

GB300 NVL72 + Dynamo показывает 50x MoE-пропускной способности по сравнению с базовыми показателями Hopper. Маршрутизация экспертов MoE тяжела по вычислениям на prefill, но тяжела по памяти на decode (кеши экспертов), поэтому разделение даёт двойной выигрыш. Обслуживание передовых моделей 2026 года в основном строится на MoE (DeepSeek-V3, будущие варианты GPT-5).

### Цифры, которые стоит запомнить

Бенчмарк-цифры со временем меняются — NVIDIA и разработчики инференс-стека публикуют обновлённые результаты каждый квартал. Перепроверяйте перед цитированием.

- DeepSeek-R1 на GB200 NVL72 + Dynamo: ~6x пропускной способности относительно базового уровня в режиме средней задержки (developer.nvidia.com, 2025-06); заявления сообщества о «до 30x» на полных стеках Blackwell + Dynamo — ориентировочные агрегаты без единого первичного источника.
- GB300 NVL72 + Dynamo: до 50x MoE-пропускной способности по сравнению с Hopper (developer.nvidia.com, без даты).
- Ориентир экономии (внутренний композит, не единый кейс): $600-800K/год от годового бюджета $2M при неизменном SLA.
- Порог разделения: промпты >512 токенов + вывод >200 токенов.
- Передача KV через NIXL: 20-80 мс для KV промпта на 4K токенов на модели 70B FP8.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|--------|--------------------|-------------------------------|
| Разделённое обслуживание | «разделить prefill/decode» | Отдельные GPU-пулы для каждой фазы |
| NIXL | «транспорт NVIDIA» | Межузловая передача KV в Dynamo (RDMA/TCP) |
| NVIDIA Dynamo | «оркестратор» | Координатор-надстройка для vLLM/SGLang/TRT-LLM |
| llm-d | «нативное решение для Kubernetes» | Разделённый стек Red Hat + AWS для K8s |
| Planner Profiler | «автонастройка Dynamo» | Измеряет нагрузку и настраивает соотношение пулов |
