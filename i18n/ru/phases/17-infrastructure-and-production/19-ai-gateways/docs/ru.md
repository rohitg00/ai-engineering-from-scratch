# AI-шлюзы — LiteLLM, Portkey, Kong AI Gateway, Bifrost

> Шлюз располагается между вашими приложениями и провайдерами моделей. Ключевые функции — маршрутизация между провайдерами, резервный вариант (fallback), повторные попытки, ограничение частоты запросов, ссылки на секреты, наблюдаемость, защитные ограничения (guardrails). Расклад рынка в 2026 году: **LiteLLM** — MIT OSS со 100+ провайдерами, совместим с OpenAI, но «ломается» примерно при 2000 RPS (8 ГБ памяти, каскадные отказы в опубликованных бенчмарках); лучше всего подходит для Python, <500 RPS, разработки/прототипирования. **Portkey** позиционируется как control plane (защитные ограничения, редактирование PII, обнаружение джейлбрейков, аудиторские журналы), перешёл на Apache 2.0 open-source в марте 2026 года, накладные расходы на задержку 20-40 мс, продакшен-тариф $49/mo production tier. **Kong AI Gateway** построен на Kong Gateway — в собственном бенчмарке Kong на тех же 12 CPU он на 228% быстрее Portkey и на 859% быстрее LiteLLM; $100/модель/месяц (максимум 5 на тарифе Plus); подходит корпоративным клиентам, уже использующим Kong. **Bifrost** (Maxim AI) — автоматические повторные попытки с настраиваемой задержкой с увеличением интервала (backoff), переход к резервному варианту на Anthropic при 429 от OpenAI. **Cloudflare / Vercel AI Gateways** — управляемые, без эксплуатационных затрат (zero-ops), базовые повторные попытки. Резидентность данных определяет решение о самостоятельном хостинге; Portkey и Kong занимают промежуточное положение с OSS + опциональным управляемым вариантом.

## Проблема

Ваш продукт обращается к OpenAI, Anthropic и самостоятельно развёрнутой Llama. У каждого провайдера свой SDK, своя модель ошибок, своё ограничение частоты запросов и своя схема аутентификации. Вам нужно аварийное переключение (если OpenAI отвечает 429, попробовать Anthropic), единое хранилище учётных данных, унифицированная наблюдаемость и ограничения частоты запросов по каждому арендатору (tenant).

Изобретать это заново на уровне приложения означает связать каждый сервис с каждым провайдером. Слой шлюза консолидирует всё в один процесс с одним API (обычно совместимым с OpenAI), который распределяет запросы по провайдерам.

## Концепция

### Шесть ключевых функций

1. **Маршрутизация между провайдерами** — OpenAI, Anthropic, Gemini, самостоятельно развёрнутые модели и т. д. за одним API.
2. **Резервный вариант (fallback)** — при 429, 5xx или сбое качества повторить попытку у другого провайдера.
3. **Повторные попытки** — задержка с увеличением интервала (backoff), ограниченное число попыток.
4. **Ограничения частоты запросов** — по арендатору, по ключу, по модели.
5. **Ссылки на секреты** — получение учётных данных из хранилища секретов во время выполнения (никогда не в приложении).
6. **Наблюдаемость** — OTel + атрибуты GenAI (Phase 17 · 13) + атрибуция затрат.
7. **Защитные ограничения (guardrails)** — редактирование PII, обнаружение джейлбрейков, фильтры разрешённых тем.

### LiteLLM — MIT OSS, Python

- 100+ провайдеров, совместим с OpenAI, конфигурация роутера, резервный вариант, базовая наблюдаемость.
- «Ломается» примерно при 2000 RPS в бенчмарке Kong; footprint памяти 8 ГБ, каскадные отказы при устойчивой нагрузке.
- Лучше всего подходит для: Python-приложений, <500 RPS, шлюзов для разработки/стейджинга, экспериментальной маршрутизации.
- Стоимость: $0 за OSS; есть бесплатный уровень в облаке.

### Portkey — позиционирование control plane

- Apache 2.0 OSS с марта 2026 года. Защитные ограничения, редактирование PII, обнаружение джейлбрейков, аудиторские журналы.
- Накладные расходы на задержку 20-40 мс на запрос.
- $49/мес за продакшен-тариф с хранением данных + SLA.
- Лучше всего подходит для: регулируемых отраслей, которым нужны защитные ограничения + наблюдаемость в одном пакете.

### Kong AI Gateway — ставка на масштаб

- Построен на Kong Gateway (зрелый продукт API-шлюза, lua+OpenResty).
- Собственный бенчмарк Kong на эквиваленте 12 CPU: на 228% быстрее Portkey, на 859% быстрее LiteLLM.
- Цена: $100/модель/месяц, максимум 5 на тарифе Plus.
- Лучше всего подходит для: тех, кто уже использует Kong; >1000 RPS; готовности лицензировать.

### Bifrost (Maxim AI)

- Автоматические повторные попытки с настраиваемой задержкой с увеличением интервала (backoff).
- Переход к резервному варианту на Anthropic при 429 от OpenAI — типовой рецепт.
- Более новый игрок; коммерческий продукт.

### Cloudflare AI Gateway / Vercel AI Gateway

- Управляемые, без эксплуатационных затрат (zero-ops). Базовые повторные попытки и наблюдаемость.
- Лучше всего подходит для: JavaScript-приложений, обслуживаемых на границе сети (edge), на Cloudflare/Vercel.
- Ограничены по сравнению с Kong/Portkey в части защитных ограничений и ограничений частоты запросов.

### Самостоятельный хостинг или управляемый вариант

Резидентность данных — определяющий фактор. Здравоохранение и финансы по умолчанию выбирают самостоятельный хостинг (LiteLLM, Portkey OSS или Kong). Потребительские продукты по умолчанию выбирают управляемый вариант (Cloudflare AI Gateway) или промежуточный уровень (Portkey managed). Гибридный подход: самостоятельный хостинг для регулируемого арендатора, управляемый вариант для остальных.

### Бюджет задержки

- LiteLLM: обычно 5-15 мс накладных расходов.
- Portkey: 20-40 мс накладных расходов.
- Kong: 3-8 мс накладных расходов.
- Cloudflare/Vercel: 1-3 мс накладных расходов (преимущество границы сети).

Задержка шлюза напрямую добавляется к TTFT. Для SLA по TTFT P99 < 100 мс — Kong или Cloudflare. Для P99 < 500 мс — подойдёт любой.

### Семантика ограничения частоты запросов имеет значение

Простой token-bucket работает до умеренного масштаба. Мультиарендная (multi-tenant) архитектура требует sliding-window + допуск на всплески + многоуровневую политику по арендатору. LiteLLM поставляется с token-bucket; Kong — со sliding-window; Portkey — с многоуровневой политикой.

### Шлюз + наблюдаемость + маршрутизация складываются вместе

Phase 17 · 13 (наблюдаемость) + 16 (маршрутизация моделей) + 19 (шлюзы) — это один и тот же слой в продакшене. Выберите один инструмент, который покрывает все три задачи, либо тщательно соедините их вручную: большинство развёртываний 2026 года сочетают Helicone (наблюдаемость) или Portkey (защитные ограничения) с Kong (масштаб) для разделения ролей.

### Цифры, которые нужно запомнить

- LiteLLM: «ломается» примерно при 2000 RPS, 8 ГБ памяти.
- Portkey: накладные расходы 20-40 мс; Apache 2.0 с марта 2026 года.
- Kong: на 228% быстрее Portkey, на 859% быстрее LiteLLM.
- Цена Kong: $100/модель/месяц, максимум 5 на тарифе Plus.
- Cloudflare/Vercel: накладные расходы 1-3 мс на границе сети.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Шлюз | «API-брокер» | Процесс между приложениями и провайдерами |
| LiteLLM | «тот, что под MIT» | OSS на Python, 100+ провайдеров, «ломается» при 2K RPS |
| Portkey | «шлюз с защитными ограничениями» | Control plane + наблюдаемость, Apache 2.0 |
| Kong AI Gateway | «тот, что для масштаба» | Построен на Kong Gateway, лидер бенчмарка |
| Bifrost | «шлюз Maxim» | Повторные попытки + типовой переход к резервному варианту на Anthropic |
| Cloudflare AI Gateway | «управляемый шлюз на границе сети» | Управляемый шлюз, развёрнутый на границе сети, без эксплуатационных затрат (zero-ops) |
| Редактирование PII | «очистка данных» | Маскирование с помощью регулярных выражений + NER перед отправкой модели |
| Обнаружение джейлбрейков | «защита от инъекции промпта» | Классификатор пользовательского ввода |

| Sliding-window | «точное ограничение частоты запросов» | Ограничитель частоты запросов на основе временного окна; более справедливое распределение квоты |
