# Безопасность — секреты, ротация API-ключей, журналы аудита, защитные ограничения

> Устраните разрастание секретов (secret sprawl) с помощью централизованных хранилищ (vault) — HashiCorp Vault, AWS Secrets Manager, Azure Key Vault. Никогда не храните учётные данные в конфигурационных файлах, env-файлах в VCS, электронных таблицах. Используйте роли IAM вместо статических ключей; OIDC для CI/CD. Паттерн AI-шлюза (AI gateway) — решение 2026 года: приложения → шлюз → провайдер модели, при этом шлюз получает учётные данные из хранилища во время выполнения запроса. Ротация в хранилище — и все приложения подхватывают новый ключ за минуты: без повторных развёртываний, без сообщений в Slack «у кого новый ключ». Политика ротации ≤90 дней; сканирование с помощью TruffleHog / GitGuardian / Gitleaks при каждом коммите. Zero-trust: MFA, SSO, RBAC/ABAC, короткоживущие токены, проверка состояния устройства (device posture). Очистка PII использует распознавание сущностей (entity recognition) для маскирования PHI/PII перед отправкой; согласованная токенизация (подход Mesh) сопоставляет чувствительные значения со стабильными плейсхолдерами, чтобы LLM сохраняла семантику кода и связей. Сетевой исходящий трафик (egress): LLM-сервисы в выделенной подсети VPC/VNet с белым списком только `api.openai.com`, `api.anthropic.com` и т. д.; весь остальной исходящий трафик блокируется. Причина инцидента 2026 года: атака на цепочку поставок (supply-chain attack) на Vercel через скомпрометированные учётные данные CI/CD привела к утечке переменных окружения в тысячах развёртываний клиентов.

**Предварительные требования:** Фаза 17 · 19 (AI-шлюзы), Фаза 17 · 13 (Наблюдаемость)

## Цели обучения

- Перечислите четыре антипаттерна управления секретами (secrets management) — конфигурационные файлы в VCS, захардкоженные переменные окружения, электронные таблицы, статические ключи — и назовите их замены.
- Объясните паттерн «AI-шлюз получает секреты из хранилища» как производственный стандарт 2026 года.
- Реализуйте PII-скраббер с согласованной токенизацией (одно и то же значение → один и тот же плейсхолдер), сохраняющей семантику.
- Назовите инцидент цепочки поставок (supply-chain incident) Vercel 2026 года и чему он научил в отношении гигиены учётных данных CI/CD.

## Проблема

Стажёр коммитит `.env` с API-ключами. Он быстро удаляет его. Ключи уже в истории git — сканирование GitGuardian их обнаруживает, а ваш процесс ротации — это «написать всей команде в Slack, обновить 40 конфигурационных файлов, передеплоить все сервисы». Через 8 часов половина ваших сервисов уже работает на новых ключах, а другая половина ждёт окна для развёртывания.

Отдельно: промпты пользователей содержат фразы вроде «Мой SSN — 123-45-6789». Промпт уходит в OpenAI. У вас есть BAA, но внутренняя политика требует маскировать PII перед отправкой. Вы этого не сделали.

Отдельно: LLM-под в вашем кластере EKS может обратиться к любому хосту в интернете. Кто-то эксфильтрует данные через DNS-запрос к домену, контролируемому злоумышленником. Ничто этому не помешало.

Безопасность LLM-сервисов должна закрывать все три вектора. Учётные данные на основе хранилища (vault-backed credentials). Очистка PII. Фильтрация исходящего сетевого трафика. Журналы аудита.

## Концепция

### Централизованное хранилище + получение через роль IAM

**Хранилище (vault)**: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager. Единый источник истины.

**Роль IAM**: приложение/шлюз аутентифицируется через свою идентичность IAM, а не статический ключ. Хранилище возвращает секрет на время жизни токена.

**Паттерн AI-шлюза**: шлюз получает `OPENAI_API_KEY` из хранилища во время запроса. Ротация выполняется в хранилище; следующий запрос получит новый ключ. Без повторных развёртываний.

### Политика ротации ≤ 90 дней

Все API-ключи, корневые токены хранилища, учётные данные CI/CD. Автоматическая ротация там, где это возможно. Ручная ротация регистрируется в журнале и отслеживается.

### Сканирование секретов

- **TruffleHog** — регулярные выражения + анализ энтропии по коммитам.
- **GitGuardian** — коммерческий, высокая точность.
- **Gitleaks** — с открытым исходным кодом, запускается в CI.

Запускается при каждом коммите. Блокирует PR, если обнаружен новый секрет.

### Позиция zero-trust

- MFA обязательна для всех учётных записей.
- SSO через SAML/OIDC.
- RBAC (на основе ролей) или ABAC (на основе атрибутов) для детального контроля доступа.
- Короткоживущие токены (часы, а не дни).
- Проверка состояния устройства (device posture) — только корпоративные устройства с шифрованием диска.

### Очистка PII / PHI

Перед тем как промпт покинет вашу инфраструктуру:

1. Распознавание сущностей (entity recognition): spaCy NER, Presidio или коммерческие решения.
2. Маскирование найденных сущностей: `"My SSN is 123-45-6789"` → `"My SSN is [SSN_TOKEN_A3F]"`.
3. Согласованная токенизация (подход Mesh): одно и то же значение сопоставляется с одним и тем же плейсхолдером, чтобы LLM сохраняла связи.
4. Опциональное обратное сопоставление для ответа LLM.

Статические regex-фильтры ловят базовые шаблоны; NER ловит больше. Используйте оба подхода.

### Защитные ограничения на входе и выходе

Вход: блокировка известных джейлбрейков (jailbreak), запрещённых тем; ограничение частоты запросов на пользователя.

Выход: regex-очистка от утёкших секретов (шаблоны API-ключей, шаблоны email в контексте отказов), классификатор нарушений политики.

### Белый список исходящего сетевого трафика

LLM-сервисы в выделенной подсети:
- Белый список: `api.openai.com`, `api.anthropic.com`, конечные точки векторной базы данных, конечные точки хранилища.
- Всё остальное: отбрасывается.
- DNS через резолвер, работающий только со списком разрешённых доменов, чтобы избежать эксфильтрации через DNS-туннелирование.

### Журнал аудита

Неизменяемый журнал каждого вызова LLM со следующими полями:
- Временная метка.
- Пользователь / арендатор (tenant).
- Хеш промпта (не сам промпт — из соображений приватности).
- Модель + версия.
- Количество токенов.
- Стоимость.
- Хеш ответа.
- Любые срабатывания защитных ограничений.

Хранение согласно регуляторным требованиям (SOC 2 — 1 год, HIPAA — 6 лет).

### Инцидент с Vercel 2026 года

Атака на цепочку поставок: скомпрометированные учётные данные CI/CD привели к утечке переменных окружения в тысячах развёртываний клиентов. Урок: учётные данные CI/CD эквивалентны продакшен-доступу. Храните их в хранилище. Ограничивайте область действия. Ротируйте агрессивно.

### Цифры, которые стоит запомнить

- Политика ротации: ≤ 90 дней.
- Сканирование при каждом коммите: TruffleHog / GitGuardian / Gitleaks.
- Vercel 2026: скомпрометированные учётные данные CI/CD → утечка переменных окружения тысяч клиентов.
- Хранение журнала аудита: SOC 2 = 1 год, HIPAA = 6 лет.

## Применение

`code/main.py` реализует игрушечный PII-скраббер с согласованной токенизацией и журнал аудита, в который можно только добавлять записи.

## Поставка

Этот урок производит `outputs/skill-llm-security-plan.md`. По заданным регуляторным требованиям и текущему состоянию планирует миграцию в хранилище, скраббер, исходящий трафик, журнал аудита.

## Упражнения

1. Запустите `code/main.py`. Отправьте два промпта, ссылающихся на один и тот же SSN. Убедитесь, что оба получают один и тот же плейсхолдер.
2. Спроектируйте политику исходящего сетевого трафика для развёртывания vLLM на EKS, обращающегося к OpenAI + Anthropic + Weaviate.
3. Вы обнаруживаете ключ в истории git (двухлетней давности). Каков правильный ответ — ротировать ключ, очистить историю или сделать и то, и другое? Обоснуйте.
4. Ваш журнал аудита растёт на 10 ГБ/день. Спроектируйте уровни хранения (горячий — 30 дней, тёплый — 12 месяцев, холодный — 6 лет).
5. Обоснуйте, стоит ли обратная токенизация (подстановка реальных значений обратно в ответ LLM) дополнительной сложности по сравнению с сохранением видимых плейсхолдеров.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на самом деле |
|------|----------------|------------------------|
| Хранилище (vault) | «хранилище секретов» | Централизованный сервис управления учётными данными |
| Роль IAM | «аутентификация на основе идентичности» | Роль, которую принимает приложение и которая предоставляет короткоживущие учётные данные |
| OIDC для CI/CD | «токены, выпущенные облачным провайдером» | В CI нет статических ключей: идентичность подтверждается через OIDC |
| TruffleHog / GitGuardian / Gitleaks | «сканеры секретов» | Обнаружение секретов во время коммита |
| RBAC / ABAC | «контроль доступа» | Контроль на основе ролей или атрибутов |
| Очистка PII | «маскирование данных» | Удаление или токенизация чувствительных сущностей |
| Согласованная токенизация | «стабильные плейсхолдеры» | Одно и то же значение каждый раз преобразуется в один и тот же токен |
| Подход Mesh | «токенизация Mesh» | Паттерн токенизации, сохраняющий семантику |
| Белый список исходящего трафика | «список разрешённых исходящих соединений» | Доступны только разрешённые домены |
| Журнал аудита | «неизменяемая история» | Журнал только для добавления записей, используемый для соблюдения нормативных требований |
