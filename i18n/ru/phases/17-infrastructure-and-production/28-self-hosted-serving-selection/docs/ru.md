# Выбор движка для самостоятельного развёртывания с учётом оборудования и масштаба

> Выбор движка определяется оборудованием, масштабом и экосистемой, а не местом в рейтинге. В 2026 году в инференсе на собственной инфраструктуре доминируют четыре движка: llama.cpp, Ollama, vLLM и SGLang, а TGI отстаёт, находясь в режиме поддержки. **llama.cpp** быстрее всего работает на CPU — самая широкая поддержка моделей, полный контроль над квантованием и многопоточностью. **Ollama** — установка одной командой для ноутбука разработчика, ~на 15-30% медленнее, чем llama.cpp (Go + CGo + сериализация HTTP), разрыв в пропускной способности в 3 раза при нагрузке, близкой к продакшену. **TGI перешёл в режим поддержки 11 декабря 2025 года** — только исправления багов, примерно на 10% ниже сырая пропускная способность, чем у vLLM, но исторически лучшая наблюдаемость и интеграция с экосистемой HF. Этот статус поддержки делает его рискованной долгосрочной ставкой — SGLang или vLLM являются более безопасным выбором по умолчанию для новых проектов. **vLLM** — универсальный продакшен-выбор по умолчанию — v0.15.1 (февраль 2026 года) добавляет PyTorch 2.10, RTX Blackwell SM120, оптимизацию под H200. **SGLang** — специалист по агентным многоходовым (multi-turn) сценариям и нагрузкам с интенсивным использованием общих префиксов — 400 000+ GPU в продакшене (xAI, LinkedIn, Cursor, Oracle, GCP, Azure, AWS). Ограничения по оборудованию: приоритет CPU → llama.cpp. AMD / не-NVIDIA → vLLM — вариант с наиболее полной поддержкой (TRT-LLM привязан к NVIDIA). Паттерн конвейера 2026 года: разработка = Ollama, тестовая среда = llama.cpp, продакшен = vLLM или SGLang. Движки используют разные форматы весов — GGUF для семейства llama.cpp и HF safetensors для GPU-движков, — поэтому между этапами может потребоваться преобразование формата.

## Проблема

Ваша команда начинает новый проект с самостоятельным развёртыванием LLM. Один инженер говорит про Ollama, другой — про vLLM, третий спрашивает: «А разве TGI не работает из коробки?» Все трое правы для разных контекстов. Никто не прав для всех сразу.

В 2026 году важно дерево решений: сначала оборудование, затем масштаб, затем нагрузка. И одно конкретное событие 2025 года — переход TGI в режим поддержки 11 декабря — меняет выбор по умолчанию для новых проектов.

## Концепция

### Пять движков

| Движок | Лучше всего подходит для | Примечания |
|--------|----------|-------|
| **llama.cpp** | CPU / периферия (edge) / минимум зависимостей / самая широкая поддержка моделей | Быстрее всего на CPU, полный контроль |
| **Ollama** | Ноутбуки разработчиков, один пользователь, установка одной командой | На 15-30% медленнее llama.cpp; разрыв в 3 раза в продакшен-пропускной способности |
| **TGI** | Экосистема HF, регулируемые отрасли | **Режим поддержки с 11 декабря 2025 года** |
| **vLLM** | Универсальный продакшен, 100+ пользователей | Широкий выбор по умолчанию для продакшена; v0.15.1, февраль 2026 |
| **SGLang** | Агентные многоходовые сценарии, нагрузки с интенсивным использованием общих префиксов | 400 000+ GPU в продакшене |

### Оборудование — первый критерий

**Приоритет CPU** → llama.cpp. Ollama тоже работает, но медленнее. Никакой другой движок не конкурентоспособен на CPU.

**AMD GPU** → vLLM — вариант с наиболее полной поддержкой (поддержка AMD ROCm). SGLang тоже работает. TRT-LLM привязан к NVIDIA, поэтому не подходит.

**NVIDIA Hopper (H100 / H200)** → vLLM, SGLang или TRT-LLM. Все три — топовый уровень.

**NVIDIA Blackwell (B200 / GB200)** → лидер по пропускной способности — TRT-LLM (Фаза 17 · 07). vLLM и SGLang следуют вплотную за ним.

**Apple Silicon (серия M)** → llama.cpp (Metal). Ollama оборачивает это решение.

### Масштаб — второй критерий

**1 пользователь / локальная разработка** → Ollama. Одна команда, первый токен за секунды.

**10-100 пользователей / небольшая команда** → vLLM на одном GPU.

**100-10 000 пользователей / продакшен** → продакшен-стек vLLM (Фаза 17 · 18) или SGLang.

**10 000+ пользователей / уровень предприятия** → продакшен-стек vLLM + разделённая архитектура (disaggregated, Фаза 17 · 17) + LMCache (Фаза 17 · 18).

### Нагрузка — третий критерий

**Общий чат / вопросы-ответы** → vLLM выигрывает как широкий выбор по умолчанию.

**Агентные многоходовые сценарии (инструменты, планирование, память)** → доминирует RadixAttention от SGLang (Фаза 17 · 06).

**RAG с интенсивным повторным использованием префиксов** → SGLang.

**Генерация кода** → vLLM подходит; SGLang немного лучше за счёт кеша.

**Длинный контекст (128K+)** → vLLM + фрагментированное предварительное заполнение (chunked prefill); SGLang + многоуровневый KV.

### Ловушка режима поддержки TGI

Hugging Face TGI перешёл в режим поддержки 11 декабря 2025 года — далее только исправления багов. Исторически: наблюдаемость топового уровня, лучшая в своём классе интеграция с экосистемой HF (карточки моделей, инструменты безопасности), немного отстаёт от vLLM по сырой пропускной способности.

Для новых проектов в 2026 году: по умолчанию не выбирайте TGI. Существующие развёртывания TGI могут продолжать работать, но со временем должны мигрировать. SGLang и vLLM — более безопасный выбор по умолчанию.

### Паттерн конвейера

Разработка (Ollama) → тестовая среда (llama.cpp) → продакшен (vLLM). Движки используют разные форматы весов — GGUF для семейства llama.cpp и HF safetensors для GPU-движков, — поэтому между этапами может потребоваться преобразование формата. Инженеры быстро итерируют на ноутбуках; тестовая среда воспроизводит продакшен-квантование; продакшен — целевая среда обслуживания.

### Оговорка про Ollama

Ollama отлично подходит для разработки. Но не годится для общего продакшена: сериализация Go HTTP добавляет накладные расходы, управление конкурентностью проще, чем у vLLM, поддержка OpenTelemetry отстаёт. Используйте Ollama там, где она блистает — один пользователь, одна команда — и переключайтесь на vLLM для общего доступа.

### Самостоятельное или управляемое развёртывание — отдельное решение

Фаза 17 · 01 (управляемые гиперскейлеры), · 02 (платформы инференса) охватывают управляемый вариант. Этот урок предполагает, что вы уже решили развернуть систему самостоятельно. Причины для самостоятельного развёртывания: резидентность данных, кастомное дообучение, совокупная стоимость владения при масштабе, доменная модель, недоступная в управляемом варианте.

### Цифры, которые стоит запомнить

- Режим поддержки TGI: 11 декабря 2025 года.
- vLLM v0.15.1: февраль 2026 года; PyTorch 2.10; поддержка Blackwell SM120.
- Продакшен-присутствие SGLang: 400 000+ GPU.
- Разрыв в пропускной способности Ollama относительно llama.cpp: на 15-30% медленнее; в 3 раза при продакшен-нагрузке.
