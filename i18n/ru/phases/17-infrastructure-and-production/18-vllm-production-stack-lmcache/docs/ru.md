# Стек обслуживания моделей в продакшене — выгрузка KV и маршрутизация с учётом кеша

> Продакшен-стек обслуживания моделей объединяет маршрутизатор, движки и наблюдаемость в одном развёртывании Kubernetes — и рассматривает KV-кеш как ресурс, который можно перемещать за пределы GPU. Выгрузка KV-кеша извлекает KV-кеш из памяти GPU и повторно использует его между запросами и движками (сначала CPU DRAM, затем диск/Ceph). production-stack от vLLM — это эталонное развёртывание, а LMCache — слой выгрузки. KV Offloading Connector vLLM 0.11.0 (январь 2026) делает этот процесс асинхронным и подключаемым через Connector API (v0.9.0+). Путь выгрузки обычно не затрагивает критический путь запроса, однако промахи кеша и перенос данных на более быстрый уровень могут увеличить сквозную задержку. LMCache полезен даже без общих префиксов — когда у GPU заканчиваются слоты KV, вытесненные запросы можно восстановить из CPU вместо повторного вычисления prefill. Опубликованные бенчмарки на 16x H100 (80GB HBM) на 4 узлах a3-highgpu-4g: когда KV-кеш превышает объём HBM, и нативная выгрузка на CPU, и LMCache существенно повышают пропускную способность; при небольшом объёме KV все конфигурации сравнимы с базовой линией с небольшими накладными расходами.

## Цели обучения

- Изобразить на диаграмме слои vLLM production-stack: маршрутизатор, движки, выгрузку KV, наблюдаемость.

- Количественно оценить, когда CPU-DRAM в LMCache помогает (KV > HBM), а когда добавляет накладные расходы (KV достаточно мал, чтобы поместиться в HBM).
- Выбрать между нативной выгрузкой vLLM на CPU и коннектором LMCache с учётом ограничений развёртывания.

## Проблема

Ваше обслуживание vLLM показывает GPU при 100% заполнении HBM с событиями вытеснения при каждом росте конкурентности. Запросы вытесняются, ставятся обратно в очередь, и вы заново выполняете prefill для одного и того же промпта на 2K токенов четыре раза в минуту. Вычислительные ресурсы GPU тратятся на избыточные prefill; goodput существенно ниже сырой пропускной способности.

Добавление GPU обходится линейно дорого. Добавить больше HBM невозможно. Но CPU DRAM дёшев — один сокет даёт 512 ГБ+ с задержкой на порядки хуже, чем у HBM, но вполне пригодной для «временно тёплого» KV-кеша.

LMCache извлекает KV-кеш в CPU DRAM, чтобы вытесненные запросы восстанавливались быстро, а повторяющиеся префиксы между движками использовали общий кеш без повторного prefill в каждом движке.

## Концепция

### vLLM production-stack

`github.com/vllm-project/production-stack` — эталонное развёртывание в Kubernetes:

- **Маршрутизатор** — учитывающий кеш (cache-aware, Фаза 17 · 11). Потребляет события KV.
- **Движки** — воркеры vLLM. Один на GPU или на группу TP/PP.
- **Выгрузка KV-кеша** — развёртывание LMCache или нативный коннектор.
- **Наблюдаемость** — сбор метрик Prometheus, дашборды Grafana, трассировки OTel.
- **Control plane** — service discovery, конфигурация, скользящие обновления (rolling updates).

Поставляется как Helm chart + оператор.

### KV Offloading Connector API (v0.9.0+)

vLLM 0.9.0 представил Connector API для подключаемых бэкендов KV-кеша. Ваш движок выгружает блоки в коннектор; коннектор хранит их (RAM, диск, объектное хранилище, LMCache). Когда запросу нужен блок, коннектор загружает его обратно.

vLLM 0.11.0 (январь 2026) добавляет асинхронный путь выгрузки — выгрузка может происходить в фоне, так что в типичном случае движок на ней не блокируется. Сквозная задержка и пропускная способность всё равно зависят от формы нагрузки, коэффициента попаданий в KV-кеш и загруженности системы; в собственных заметках vLLM отмечается, что выгрузка через кастомные ядра может снижать пропускную способность при низком коэффициенте попаданий, а у асинхронного планирования есть известные проблемы взаимодействия со спекулятивным декодированием.

### Нативная выгрузка на CPU vs LMCache

**Нативная выгрузка vLLM на CPU**: локальна для движка. Хранит блоки KV в RAM хоста. Быстро реализуется, ноль сетевых переходов. Не работает между движками.

**Коннектор LMCache**: масштаб кластера. Хранит блоки на общем сервере LMCache (CPU DRAM + уровень Ceph/S3). Блоки доступны любому движку. Опубликованы бенчмарки на 16x H100.

Выбирайте нативную выгрузку, когда под нагрузкой HBM находится один движок. Выбирайте LMCache, когда несколько движков делят общие префиксы (RAG с общими системными промптами, мультитенантность с общими шаблонами).

### Поведение в бенчмарках

Тест на 16x H100 (80 ГБ HBM), распределённых по 4 узлам a3-highgpu-4g:

- Небольшой объём KV (короткие промпты, низкая конкурентность): все конфигурации сравнимы с базовой линией, LMCache добавляет ~3-5% накладных расходов.
- Умеренный объём: LMCache начинает помогать за счёт повторного использования префиксов между движками.
- KV превышает HBM: и нативная выгрузка на CPU, и LMCache существенно повышают пропускную способность; у LMCache выигрыш больше за счёт совместного использования между движками.

### Когда LMCache становится решающим фактором

- Мультитенантное обслуживание, где системные промпты общие для всех тенантов.
- RAG, где фрагменты документов повторяются между запросами.
- Дообученные варианты (LoRA) на одной базовой модели, где повторное использование KV базовой модели сокращает избыточную работу.
- Нагрузки с интенсивным вытеснением: восстановление из CPU дешевле повторного prefill.

### Когда не стоит включать

- Небольшая нагрузка на HBM — вы платите накладные расходы без выгоды.
- Короткие контексты (<1K токенов) — время передачи больше, чем повторный prefill.
- Нагрузка с одним тенантом и одним промптом — нечего повторно использовать.

### Интеграция с disaggregated serving

Дизагрегированное обслуживание (disaggregated serving) из Фазы 17 · 17 в сочетании с LMCache усиливает эффект: KV, передаваемый из пула prefill в пул decode, попадает в LMCache, если не используется; последующие запросы забирают его из LMCache. Маршрутизатор с учётом кеша (cache-aware) из Фазы 17 · 11 может направлять запрос на движок, чей локальный кеш ИЛИ общий кеш LMCache совпадает.

### Цифры, которые стоит запомнить

- vLLM 0.9.0: выпущен Connector API.
- vLLM 0.11.0 (январь 2026): асинхронный путь выгрузки; влияние на сквозную задержку зависит от нагрузки, коэффициента попаданий KV и загруженности системы (это не абсолютная гарантия).
- Бенчмарк на 16x H100: LMCache помогает, когда объём KV превышает HBM.
- Небольшая нагрузка на HBM: 3-5% накладных расходов без выгоды.

## Применение

`code/main.py` симулирует нагрузку с интенсивным вытеснением с LMCache и без него. Выводит количество избежавших повторного prefill запросов, прирост пропускной способности и точку безубыточности по использованию HBM.

## Ключевые термины

| Термин | Как обычно говорят | Что это означает на практике |
|------|----------------|------------------------|
| Production-stack | «эталонное развёртывание» | Helm chart Kubernetes и оператор от vLLM |
| Connector API | «интерфейс бэкенда KV» | Интерфейс подключаемого хранилища KV в vLLM 0.9.0+ |
| Нативная выгрузка на CPU | «выгрузка внутри движка» | Хранение KV в оперативной памяти хоста того же движка |
| LMCache | «кластерный KV-кеш» | Общий для движков сервер KV-кеша на CPU DRAM + диске |
| Асинхронный режим 0.11.0 | «неблокирующая выгрузка» | Выгрузка скрыта за потоком выполнения движка |
| Вытеснение | «освободить место путём вытеснения» | Перераспределение KV-кеша при заполнении HBM |
| Повторное использование префикса | «тот же системный промпт» | Несколько запросов имеют общее начало, что приводит к попаданию в кеш |
| Уровень Ceph | «дисковый уровень» | Долговременное хранилище ниже DRAM в иерархии кеша |
