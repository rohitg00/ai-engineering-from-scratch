## Проблема

Ваша модель обучается три часа, а затем функция потерь становится NaN. Вы добавляете print. Логиты в порядке на шаге 9 000. На шаге 9 001 они `inf`. К шагу 9 002 каждый градиент — `nan`, и обучение мертво.

Или: ваша модель обучается до конца, но точность на 2% хуже, чем заявлено в статье. Вы проверяете всё. Архитектура совпадает. Гиперпараметры совпадают. Данные совпадают. Проблема в том, что в статье использовался float32, а вы использовали float16 без правильного масштабирования. Тридцать два бита накопленной ошибки округления незаметно съели вашу точность.

Или: вы реализуете cross-entropy loss с нуля. На маленьких логитах всё работает. Когда логиты превышают 100, функция возвращает `inf`. Softmax переполнился, потому что `exp(100)` больше, чем может представить float32. Каждый ML-фреймворк решает это двумя строками кода. Вы не знали, что этот приём существует.

Численная стабильность — это не теоретическая забота. Это разница между обучающим прогоном, который завершается успехом, и тем, который тихо проваливается. Каждый серьёзный ML-баг, который вы будете отлаживать, в конце концов сводится к плавающей точке.

## Концепция

### IEEE 754: как компьютеры хранят вещественные числа

Компьютеры хранят вещественные числа как значения с плавающей точкой согласно стандарту IEEE 754. У float три части: бит знака, экспонента и мантисса (значащая часть).

```
Float32 layout (32 bits total):
[1 sign] [8 exponent] [23 mantissa]

Value = (-1)^sign * 2^(exponent - 127) * 1.mantissa
```

Мантисса определяет точность (сколько значащих цифр). Экспонента определяет диапазон (насколько большим или маленьким может быть число).

```
Format     Bits   Exponent  Mantissa  Decimal digits  Range (approx)
float64    64     11        52        ~15-16          +/- 1.8e308
float32    32     8         23        ~7-8            +/- 3.4e38
float16    16     5         10        ~3-4            +/- 65,504
bfloat16   16     8         7         ~2-3            +/- 3.4e38
```

float32 даёт около 7 десятичных знаков точности. Это значит, что он различает 1.0000001 и 1.0000002, но не различает 1.00000001 и 1.00000002. После 7 знаков всё — шум округления.

float16 даёт около 3 знаков. Наибольшее число, которое он может представить, — 65 504. Это тревожно мало для ML, где логиты, градиенты и активации регулярно превышают это значение.

bfloat16 — ответ Google на проблему диапазона float16. У него та же 8-битная экспонента, что и у float32 (тот же диапазон, до 3.4e38), но только 7 бит мантиссы (меньше точности, чем у float16). Для обучения нейросетей диапазон важнее точности, поэтому bfloat16 обычно выигрывает.

### Почему 0.1 + 0.2 != 0.3

Число 0.1 нельзя представить точно в двоичной плавающей точке. В базе 2 это периодическая дробь:

```
0.1 in binary = 0.0001100110011001100110011... (repeating forever)
```

Float32 обрезает это до 23 бит мантиссы. Хранимое значение приблизительно равно 0.100000001490116. Аналогично, 0.2 хранится приблизительно как 0.200000002980232. Их сумма — 0.300000004470348, а не 0.3.

```
In Python:
>>> 0.1 + 0.2
0.30000000000000004

>>> 0.1 + 0.2 == 0.3
False
```

Это важно для ML, потому что:

1. Сравнения потерь вроде `if loss < threshold` могут давать неверные результаты
2. Накопление множества маленьких значений (обновления градиента за тысячи шагов) уходит от истинной суммы
3. Контрольные суммы и тесты воспроизводимости проваливаются, если сравнивать float с `==`

Решение: никогда не сравнивайте float с `==`. Используйте `abs(a - b) < epsilon` или `math.isclose()`.

### Катастрофическое сокращение разрядов

Когда вы вычитаете два почти равных числа с плавающей точкой, значащие цифры сокращаются, и остаётся шум округления, вышедший на первые разряды.

```
a = 1.0000001    (stored as 1.00000011920929 in float32)
b = 1.0000000    (stored as 1.00000000000000 in float32)

True difference:  0.0000001
Computed:         0.00000011920929

Relative error: 19.2%
```

Это 19% относительной ошибки от одного вычитания. В ML это происходит всякий раз, когда вы:

- Вычисляете дисперсию данных с большим средним: `E[x^2] - E[x]^2`, когда E[x] велико
- Вычитаете почти равные логарифмы вероятностей
- Вычисляете градиенты методом конечных разностей со слишком малым epsilon

Решение: перестройте формулы так, чтобы избежать вычитания больших, почти равных чисел. Для дисперсии используйте алгоритм Уэлфорда или сначала центрируйте данные. Для логарифмов вероятностей работайте всё время в лог-пространстве.

### Переполнение и underflow

Переполнение случается, когда результат слишком велик, чтобы его представить. Underflow случается, когда он слишком мал (ближе к нулю, чем наименьшее представимое положительное число).

```
Float32 boundaries:
  Maximum:  3.4028235e+38
  Minimum positive (normal): 1.175e-38
  Minimum positive (denorm): 1.401e-45
  Overflow:  anything > 3.4e38 becomes inf
  Underflow: anything < 1.4e-45 becomes 0.0
```

Функция `exp()` — главный источник переполнения в ML:

```
exp(88.7)  = 3.40e+38   (barely fits in float32)
exp(89.0)  = inf         (overflow)
exp(-87.3) = 1.18e-38   (barely above underflow)
exp(-104)  = 0.0         (underflow to zero)
```

Функция `log()` бьёт в противоположную сторону:

```
log(0.0)   = -inf
log(-1.0)  = nan
log(1e-45) = -103.3      (fine)
log(1e-46) = -inf        (input underflowed to 0, then log(0) = -inf)
```

В ML `exp()` встречается в softmax, sigmoid и вычислениях вероятностей. `log()` встречается в cross-entropy, log-likelihood и KL-дивергенции. Сочетание `log(exp(x))` — минное поле без правильных приёмов.

### Приём log-sum-exp

Вычисление `log(sum(exp(x_i)))` напрямую численно опасно. Если любое `x_i` велико, `exp(x_i)` переполняется. Если все `x_i` очень отрицательны, каждое `exp(x_i)` уходит в underflow до нуля, и `log(0)` равно `-inf`.

Приём: вычесть максимальное значение перед экспонированием.

```
log(sum(exp(x_i))) = max(x) + log(sum(exp(x_i - max(x))))
```

Почему это работает: после вычитания `max(x)` наибольшая экспонента — `exp(0) = 1`. Переполнение невозможно. Хотя бы одно слагаемое в сумме равно 1, значит сумма не меньше 1, и `log(1) = 0`. Underflow до `-inf` невозможен.

Доказательство:

```
log(sum(exp(x_i)))
= log(sum(exp(x_i - c + c)))                    (add and subtract c)
= log(sum(exp(x_i - c) * exp(c)))               (exp(a+b) = exp(a)*exp(b))
= log(exp(c) * sum(exp(x_i - c)))               (factor out exp(c))
= c + log(sum(exp(x_i - c)))                    (log(a*b) = log(a) + log(b))
```

Положив `c = max(x)`, мы устраняем переполнение.

Этот приём встречается повсюду в ML:
- Нормализация softmax
- Вычисление cross-entropy loss
- Суммирование логарифмов вероятностей в последовательных моделях
- Смеси гауссиан
- Вариационный вывод

### Почему softmax нужен приём вычитания максимума

Softmax преобразует логиты в вероятности:

```
softmax(x_i) = exp(x_i) / sum(exp(x_j))
```

Без приёма логиты [100, 101, 102] вызывают переполнение:

```
exp(100) = 2.69e43
exp(101) = 7.31e43
exp(102) = 1.99e44
sum      = 2.99e44

These overflow float32 (max ~3.4e38)? No, 2.69e43 < 3.4e38? Actually:
exp(88.7) is already at the float32 limit.
exp(100) = inf in float32.
```

С приёмом вычтите max(x) = 102:

```
exp(100 - 102) = exp(-2) = 0.135
exp(101 - 102) = exp(-1) = 0.368
exp(102 - 102) = exp(0)  = 1.000
sum = 1.503

softmax = [0.090, 0.245, 0.665]
```

Вероятности идентичны. Вычисление безопасно. Это не оптимизация. Это требование корректности.

### NaN и Inf: обнаружение и предотвращение

`nan` (Not a Number) и `inf` (infinity) распространяются вирусно через вычисления. Один `nan` в обновлении градиента делает вес `nan`, что делает каждый последующий выход `nan`. Обучение мертво в течение одного шага.

Как появляется `inf`:
- `exp()` от большого положительного числа
- Деление на ноль: `1.0 / 0.0`
- Переполнение `float32` при накоплении

Как появляется `nan`:
- `0.0 / 0.0`
- `inf - inf`
- `inf * 0`
- `sqrt()` от отрицательного числа
- `log()` от отрицательного числа
- Любая арифметика с участием уже существующего `nan`

Обнаружение:

```python
import math

math.isnan(x)       # True if x is nan
math.isinf(x)       # True if x is +inf or -inf
math.isfinite(x)    # True if x is neither nan nor inf
```

Стратегии предотвращения:

1. Ограничьте входы для `exp()`: `exp(clamp(x, -80, 80))`
2. Добавьте epsilon в знаменатели: `x / (y + 1e-8)`
3. Добавьте epsilon внутрь `log()`: `log(x + 1e-8)`
4. Используйте устойчивые реализации (log-sum-exp, устойчивый softmax)
5. Обрезка градиентов (gradient clipping) для предотвращения взрыва весов
6. Проверяйте на `nan`/`inf` после каждого прямого прохода во время отладки

### Численная проверка градиентов

Аналитические градиенты (из обратного распространения ошибки) могут содержать баги. Численная проверка градиентов верифицирует их, вычисляя градиенты методом конечных разностей.

Формула центральной разности:

```
df/dx ~= (f(x + h) - f(x - h)) / (2h)
```

Она имеет точность O(h^2), что намного лучше прямой разности `(f(x+h) - f(x)) / h`, которая имеет точность лишь O(h).

Выбор h: слишком большое значение — приближение неверно. Слишком маленькое — катастрофическое сокращение разрядов разрушает ответ. Типично `h = 1e-5` до `1e-7`.

Проверка: вычислите относительную разницу между аналитическим и численным градиентами.

```
relative_error = |grad_analytical - grad_numerical| / max(|grad_analytical|, |grad_numerical|, 1e-8)
```

Практические правила:
- relative_error < 1e-7: идеально, градиент корректен
- relative_error < 1e-5: приемлемо, вероятно корректен
- relative_error > 1e-3: что-то не так
- relative_error > 1: градиент полностью неверен

Всегда проверяйте градиенты при реализации нового слоя или функции потерь. PyTorch предоставляет `torch.autograd.gradcheck()` для этого.

### Обучение со смешанной точностью

Современные GPU имеют специализированное оборудование (Tensor Cores), которое вычисляет умножения матриц float16 в 2-8 раз быстрее, чем float32. Обучение со смешанной точностью использует это:

```
1. Maintain float32 master copy of weights
2. Forward pass in float16 (fast)
3. Compute loss in float32 (prevents overflow)
4. Backward pass in float16 (fast)
5. Scale gradients to float32
6. Update float32 master weights
```

Проблема с чистым обучением на float16: градиенты часто очень малы (1e-8 или меньше). Float16 уходит в underflow до нуля для всего ниже ~6e-8. Ваша модель прекращает обучение, потому что все обновления градиента равны нулю.

Решение — масштабирование потерь (loss scaling):

```
1. Multiply loss by a large scale factor (e.g., 1024)
2. Backward pass computes gradients of (loss * 1024)
3. All gradients are 1024x larger (pushed above float16 underflow)
4. Divide gradients by 1024 before updating weights
5. Net effect: same update, but no underflow
```

Динамическое масштабирование потерь автоматически подстраивает коэффициент масштаба. Начните с большого значения (65536). Если градиенты переполняются до `inf`, уменьшите его вдвое. Если N шагов проходят без переполнения, удвойте его.

### bfloat16 против float16: почему bfloat16 выигрывает для обучения

```
float16:   [1 sign] [5 exponent]  [10 mantissa]
bfloat16:  [1 sign] [8 exponent]  [7 mantissa]
```

float16 имеет больше точности (10 бит мантиссы против 7), но ограниченный диапазон (макс. ~65 504). bfloat16 имеет меньше точности, но тот же диапазон, что и float32 (макс. ~3.4e38).

Для обучения нейросетей:

- Активации и логиты регулярно превышают 65 504 во время всплесков обучения. float16 переполняется; bfloat16 справляется.
- Масштабирование потерь необходимо с float16, но обычно не нужно с bfloat16, потому что его диапазон покрывает весь спектр величин градиентов.
- bfloat16 — это простое усечение float32: отбрасываются младшие 16 бит мантиссы. Преобразование тривиально и не теряет данных в экспоненте.

float16 предпочтителен для инференса, где значения ограничены, а точность важнее. bfloat16 предпочтителен для обучения, где важнее диапазон. Именно поэтому TPU и современные GPU NVIDIA (A100, H100) имеют нативную поддержку bfloat16.

### Обрезка градиентов

Взрывающиеся градиенты случаются, когда градиенты растут экспоненциально через множество слоёв (обычное дело в RNN, глубоких сетях и трансформерах). Один большой градиент может испортить все веса за один шаг.

Два типа обрезки:

**Обрезка по значению:** ограничивает каждый элемент градиента независимо.

```
grad = clamp(grad, -max_val, max_val)
```

Просто, но может изменить направление вектора градиента.

**Обрезка по норме:** масштабирует весь вектор градиента так, чтобы его норма не превышала порог.

```
if ||grad|| > max_norm:
    grad = grad * (max_norm / ||grad||)
```

Сохраняет направление градиента. Именно это делает `torch.nn.utils.clip_grad_norm_()`. Это стандартный выбор.

Типичные значения: `max_norm=1.0` для трансформеров, `max_norm=0.5` для RL, `max_norm=5.0` для более простых сетей.

Обрезка градиентов — это не костыль. Это механизм безопасности. Без неё один аномальный пакет данных может создать градиент, достаточно большой, чтобы разрушить недели обучения.

### Слои нормализации как численные стабилизаторы

Batch normalization, layer normalization и RMS normalization обычно представляют как регуляризаторы, которые помогают обучению сходиться. Они также являются численными стабилизаторами.

Без нормализации активации могут расти или сжиматься экспоненциально через слои:

```
Layer 1: values in [0, 1]
Layer 5: values in [0, 100]
Layer 10: values in [0, 10,000]
Layer 50: values in [0, inf]
```

Нормализация перецентрирует и перемасштабирует активации на каждом слое:

```
LayerNorm(x) = (x - mean(x)) / (std(x) + epsilon) * gamma + beta
```

`epsilon` (обычно 1e-5) предотвращает деление на ноль, когда все активации идентичны. Обучаемые параметры `gamma` и `beta` позволяют сети восстановить любой нужный масштаб.

Это удерживает значения в численно безопасном диапазоне на протяжении всей сети, предотвращая как переполнение в прямом проходе, так и взрыв градиентов в обратном проходе.

### Типичные численные баги в ML

**Баг: функция потерь становится NaN через несколько эпох.**
Причина: логиты выросли слишком большими, softmax переполнился. Или скорость обучения слишком высока, и веса разошлись.
Решение: используйте устойчивый softmax (вычитание максимума), уменьшите скорость обучения, добавьте обрезку градиентов.

**Баг: функция потерь застряла на log(num_classes).**
Причина: выходы модели близки к равномерному распределению вероятностей. Часто означает, что градиенты затухают или модель вообще не обучается.
Решение: проверьте, что метки данных корректны, проверьте функцию потерь, проверьте на мёртвые ReLU.

**Баг: точность на валидации ниже ожидаемой на 1-3%.**
Причина: смешанная точность без надлежащего масштабирования потерь. Underflow градиентов незаметно обнуляет маленькие обновления.
Решение: включите динамическое масштабирование потерь или переключитесь на bfloat16.

**Баг: нормы градиентов равны 0.0 для некоторых слоёв.**
Причина: мёртвые нейроны ReLU (все входы отрицательны) или underflow float16.
Решение: используйте LeakyReLU или GELU, используйте масштабирование градиентов, проверьте инициализацию весов.

**Баг: модель работает на одном GPU, но даёт разные результаты на другом.**
Причина: недетерминированный порядок накопления с плавающей точкой. Параллельные редукции на GPU суммируют в разном порядке на разном оборудовании, а сложение с плавающей точкой не ассоциативно.
Решение: примите небольшие расхождения (1e-6) или установите `torch.use_deterministic_algorithms(True)` и примите штраф по скорости.

**Баг: `exp()` возвращает `inf` при вычислении функции потерь.**
Причина: сырые логиты переданы в `exp()` без приёма вычитания максимума.
Решение: используйте `torch.nn.functional.log_softmax()`, который реализует log-sum-exp внутри.

**Баг: обучение расходится после перехода с float32 на float16.**
Причина: float16 не может представить величины градиентов ниже 6e-8 или активации выше 65 504.
Решение: используйте смешанную точность с масштабированием потерь (AMP) или используйте вместо этого bfloat16.

```python
print("=== Floating Point Precision ===")
```

### Шаг 2: Реализовать наивный и устойчивый softmax

```python
import math

def softmax_naive(logits):
    exps = [math.exp(z) for z in logits]
    total = sum(exps)
    return [e / total for e in exps]

def softmax_stable(logits):
    max_logit = max(logits)
    exps = [math.exp(z - max_logit) for z in logits]
    total = sum(exps)
    return [e / total for e in exps]

safe_logits = [2.0, 1.0, 0.1]
print(f"Naive:  {softmax_naive(safe_logits)}")
print(f"Stable: {softmax_stable(safe_logits)}")

dangerous_logits = [100.0, 101.0, 102.0]
print(f"Stable: {softmax_stable(dangerous_logits)}")
# softmax_naive(dangerous_logits) would return [nan, nan, nan]
```

### Шаг 3: Реализовать устойчивый log-sum-exp

```python
def logsumexp_naive(values):
    return math.log(sum(math.exp(v) for v in values))

def logsumexp_stable(values):
    c = max(values)
    return c + math.log(sum(math.exp(v - c) for v in values))

safe = [1.0, 2.0, 3.0]
print(f"Naive:  {logsumexp_naive(safe):.6f}")
print(f"Stable: {logsumexp_stable(safe):.6f}")

large = [500.0, 501.0, 502.0]
print(f"Stable: {logsumexp_stable(large):.6f}")
# logsumexp_naive(large) returns inf
```

### Шаг 4: Реализовать устойчивую cross-entropy

```python
def cross_entropy_naive(true_class, logits):
    probs = softmax_naive(logits)
    return -math.log(probs[true_class])

def cross_entropy_stable(true_class, logits):
    max_logit = max(logits)
    shifted = [z - max_logit for z in logits]
    log_sum_exp = math.log(sum(math.exp(s) for s in shifted))
    log_prob = shifted[true_class] - log_sum_exp
    return -log_prob

logits = [2.0, 5.0, 1.0]
true_class = 1
print(f"Naive:  {cross_entropy_naive(true_class, logits):.6f}")
print(f"Stable: {cross_entropy_stable(true_class, logits):.6f}")
```

### Шаг 5: Проверка градиентов

```python
def numerical_gradient(f, x, h=1e-5):
    grad = []
    for i in range(len(x)):
        x_plus = x[:]
        x_minus = x[:]
        x_plus[i] += h
        x_minus[i] -= h
        grad.append((f(x_plus) - f(x_minus)) / (2 * h))
    return grad

def check_gradient(analytical, numerical, tolerance=1e-5):
    for i, (a, n) in enumerate(zip(analytical, numerical)):
        denom = max(abs(a), abs(n), 1e-8)
        rel_error = abs(a - n) / denom
        status = "OK" if rel_error < tolerance else "FAIL"
        print(f"  param {i}: analytical={a:.8f} numerical={n:.8f} "
              f"rel_error={rel_error:.2e} [{status}]")

def f(params):
    x, y = params
    return x**2 + 3*x*y + y**3

def f_grad(params):
    x, y = params
    return [2*x + 3*y, 3*x + 3*y**2]

point = [2.0, 1.0]
analytical = f_grad(point)
numerical = numerical_gradient(f, point)
check_gradient(analytical, numerical)
```

```python
import struct

def float32_to_float16_round(x):
    packed = struct.pack('f', x)
    f32 = struct.unpack('f', packed)[0]
    packed16 = struct.pack('e', f32)

def simulate_bfloat16(x):

    truncated = as_int & 0xFFFF0000
    repacked = truncated.to_bytes(4, 'little')
```

### Обрезка градиентов

```python
def clip_by_norm(gradients, max_norm):
    total_norm = math.sqrt(sum(g**2 for g in gradients))
    if total_norm > max_norm:
        scale = max_norm / total_norm
        return [g * scale for g in gradients]
    return gradients

grads = [10.0, 20.0, 30.0]
clipped = clip_by_norm(grads, max_norm=5.0)
print(f"Original norm: {math.sqrt(sum(g**2 for g in grads)):.2f}")
print(f"Clipped norm:  {math.sqrt(sum(g**2 for g in clipped)):.2f}")
print(f"Direction preserved: {[c/clipped[0] for c in clipped]} == {[g/grads[0] for g in grads]}")
```

## Ключевые термины

| Термин | Что говорят | Что это на самом деле означает |
|------|----------------|----------------------|
| IEEE 754 | «Стандарт float» | Международный стандарт, определяющий двоичные форматы плавающей точки, правила округления и специальные значения (inf, nan). Реализован в каждом современном CPU и GPU. |
| Машинный epsilon | «Предел точности» | Наименьшее значение e, такое что 1.0 + e != 1.0 в данном формате float. Для float32 это около 1.19e-7. |
| Катастрофическое сокращение разрядов | «Потеря точности от вычитания» | При вычитании почти равных чисел с плавающей точкой значащие цифры сокращаются, и шум округления доминирует в результате. |
| Переполнение | «Число слишком большое» | Результат превышает максимальное представимое значение и становится inf. exp(89) переполняет float32. |
| Underflow | «Число слишком маленькое» | Результат ближе к нулю, чем наименьшее представимое положительное число, и становится 0.0. exp(-104) уходит в underflow для float32. |
| Приём log-sum-exp | «Сначала вычесть максимум» | Вычисление log(sum(exp(x))) путём вынесения exp(max(x)) за скобки, чтобы предотвратить переполнение и underflow. Используется в softmax, cross-entropy и математике логарифмов вероятностей. |
| Устойчивый softmax | «Softmax, который не взрывается» | Вычитание max(logits) перед экспонированием. Численно идентичный результат, переполнение невозможно. |
| Проверка градиентов | «Проверьте ваш backprop» | Сравнение аналитических градиентов из обратного распространения ошибки с численными градиентами из конечных разностей для выявления ошибок реализации. |
| Смешанная точность | «Float16 вперёд, float32 назад» | Использование float меньшей точности для критичных по скорости операций и float большей точности для численно чувствительных операций. Типичное ускорение — 2-3x. |
| Масштабирование потерь | «Предотвратить underflow градиентов» | Умножение функции потерь на большую константу перед backprop, чтобы градиенты оставались в представимом диапазоне float16, с последующим делением на ту же константу перед обновлением весов. |
| bfloat16 | «Brain floating point» | 16-битный формат Google с 8 битами экспоненты (тот же диапазон, что у float32) и 7 битами мантиссы (меньше точности, чем у float16). Предпочтителен для обучения. |
| Обрезка градиентов | «Ограничить норму градиента» | Масштабирование вектора градиента так, чтобы его норма не превышала порог. Предотвращает разрушение весов взрывающимися градиентами. |
| NaN | «Not a Number» | Специальное значение float из неопределённых операций (0/0, inf-inf, sqrt(-1)). Распространяется через всю последующую арифметику. |
| Inf | «Infinity» | Специальное значение float из переполнения или деления на ноль. Может сочетаться, порождая NaN (inf - inf, inf * 0). |
| Численный градиент | «Грубая сила производной» | Приближение производной вычислением f(x+h) и f(x-h) с делением на 2h. Медленно, но надёжно для верификации. |
