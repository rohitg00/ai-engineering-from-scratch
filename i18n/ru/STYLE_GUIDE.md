# Руководство по переводу уроков на русский язык

Это руководство обязательно для переводчиков и рецензентов файлов `docs/ru.md`. Русский документ должен точно передавать содержание соседнего `docs/en.md`, оставаясь естественным техническим текстом.

## Главный принцип

Переводите объяснения, а не программные артефакты. Нельзя добавлять утверждения, примеры, рекомендации или оговорки, которых нет в оригинале. Нельзя «улучшать» код или исправлять фактическое содержание без отдельного изменения английского источника.

## Что переводить

- заголовки и обычный текст;
- подписи ссылок и изображений;
- текстовые ячейки Markdown-таблиц;
- примечания, предупреждения, списки и вопросы для самопроверки внутри урока;
- видимые подписи метаданных (`Type`, `Time`, `Prerequisites` и подобные), сохраняя их порядок и структуру;
- обычные комментарии вне программных блоков.

## Что сохранять буквально

Следующие элементы должны совпадать с `docs/en.md` побайтно либо по указанной структурной последовательности. Автоматический аудит проверяет fenced code blocks, inline code, URL ссылок и уровни заголовков; остальные элементы обязательно сопоставляет смысловой рецензент:

- содержимое всех fenced code blocks вместе с языковым тегом;
- inline code в обратных кавычках;
- URL и якоря ссылок;
- пути файлов и каталогов;
- команды CLI, флаги и переменные окружения;
- имена API, классов, функций, методов, параметров, пакетов и моделей;
- формулы, LaTeX и числовые значения;
- HTML-теги и машинные идентификаторы;
- количество и уровни Markdown-заголовков;
- порядок секций, списков, таблиц и изображений.

Сохраняйте относительный порядок фрагментов inline code и ссылок во всём документе, даже если для естественного русского предложения меняется порядок окружающих слов. Не переводите текст внутри блоков `mermaid`, `json`, `yaml`, `toml`, shell, Python, JavaScript и других fenced blocks. Блоки без языкового тега и нестандартные блоки вроде `figure` также копируются буквально. Это защищает исполняемые и проверяемые фрагменты от повреждения.

## Стиль русского текста

1. Пишите ясным современным техническим русским языком, без канцелярита.
2. Обращайтесь к читателю нейтрально: «создайте», «проверьте», «рассмотрим».
3. Сохраняйте тон оригинала и не увеличивайте объём без необходимости.
4. Не калькируйте английский порядок слов. Сначала добивайтесь точности, затем естественности.
5. Используйте `ё` последовательно там, где она устраняет неоднозначность; допустимо общеупотребительное написание с `е`.
6. Названия продуктов, библиотек и стандартов оставляйте в официальном написании: Claude, OpenAI, LangChain, PyTorch, REST, JSON.
7. При первом появлении неоднозначного термина используйте русский эквивалент и английский термин в скобках. Далее применяйте выбранный русский вариант.
8. Аббревиатуры расшифровывайте только если это делает оригинал или если русскому читателю необходим первый ввод; не повторяйте расшифровку в каждом уроке.
9. Не переводите устоявшиеся команды интерфейса, если они относятся к буквальным названиям элементов англоязычного инструмента; оформляйте их как inline code.
10. Не используйте рекламные формулировки и не приписывайте инструментам новые свойства.

## Терминология

Перед переводом прочитайте `i18n/ru/GLOSSARY.md`. Указанный там вариант обязателен. Если контекст требует исключения, не вводите новый вариант молча: отметьте вопрос для рецензента. Имена сущностей в коде никогда не заменяются русскими эквивалентами.

## Markdown и ссылки

- Переводите стандартные служебные заголовки последовательно: `Key Terms` → «Ключевые термины», `Step N` → «Шаг N»; не оставляйте английский заголовок над русским текстом.
- В потенциально неоднозначном техническом термине при первом содержательном упоминании используйте форму «русский эквивалент (English term)». Сам заголовок пишите естественно по-русски, если это не официальное имя продукта, модели или стандарта.
- Сохраняйте один русский заголовок на каждый английский заголовок того же уровня.
- Переводите текст ссылки, но не её destination.
- Не меняйте относительные пути и регистр символов.
- Сохраняйте alt-текст изображения как единственную переводимую часть Markdown-изображения.
- Не преобразовывайте таблицы в списки и наоборот.
- Не меняйте fenced blocks на отступные блоки кода.
- Не добавляйте служебные комментарии переводчика в итоговый файл.

## Метаданные урока

Сохраняйте порядок, выделение, двоеточия, значения-коды и ссылки. Допускается перевод видимой подписи и описательного значения, но технические значения (`Python`, `JavaScript`, `Build`, версии, пути) остаются без изменений. Не создавайте frontmatter, если его нет в оригинале.

## Процесс переводчика

1. Полностью прочитайте `docs/en.md` и соседние материалы урока.
2. Проверьте glossary.
3. Создайте только соответствующий `docs/ru.md`.
4. Сопоставьте все секции с оригиналом и проверьте отсутствие пропусков.
5. Запустите структурный аудит для назначенного пути.
6. Исправьте все blocking findings.
7. Убедитесь, что другие файлы не изменены.

## Критерии рецензента

Рецензент сравнивает файлы построчно и оценивает:

- полноту: нет пропущенных предложений, списков и оговорок;
- точность: причинно-следственные связи, модальность и ограничения сохранены;
- терминологию: glossary соблюдён во всём пакете;
- естественность: текст читается как профессиональный русский материал;
- техническую целостность: код, inline code, URL, формулы и структура не повреждены;
- отсутствие добавлений: переводчик не внёс новые факты;
- отсутствие метатекста: нет «перевод выполнен», TODO и комментариев агенту.

Вердикт может быть только `APPROVED` или `CHANGES_REQUESTED` с конкретным списком проблем по файлам. Автоматический аудит обязателен, но не заменяет смысловое ревью.
