# 毕业设计 10 — 多智能体软件工程团队

> SWE-AF 的工厂架构、MetaGPT 的基于角色的提示工程、AutoGen 0.4 的类型化参与者图、Cognition 的 Devin 以及 Factory 的 Droids，都在 2026 年汇合成了同一个形态：一个架构师负责规划，N 个编码者在并行工作树中工作，一个评审者把关，一个测试者验证。并行工作树将挂钟时间转化为吞吐量。共享状态和交接协议成为故障面。本毕业设计的目标是组建这个团队，在 SWE-bench Pro 上进行评估，并报告哪些交接环节会出问题以及出问题的频率。

**类型：** 毕业设计
**语言：** Python / TypeScript（智能体），Shell（工作树脚本）
**前置条件：** 阶段 11（LLM 工程）、阶段 13（工具）、阶段 14（智能体）、阶段 15（自主系统）、阶段 16（多智能体）、阶段 17（基础设施）
**涉及阶段：** P11 · P13 · P14 · P15 · P16 · P17
**时间：** 40 小时

## 问题

单智能体编码框架在处理大型任务时遇到了瓶颈。不是因为单个智能体能力不足，而是因为 20 万个 token 的上下文无法同时容纳架构规划、四份并行的代码库切片、评审者的评语以及测试输出。多智能体工厂将问题拆分开来：架构师负责规划，编码者在并行工作树中独立实现，评审者把关，测试者验证。SWE-AF 的"工厂"架构、MetaGPT 的角色系统、AutoGen 的类型化参与者图——这三种框架描述的都是同一个形态。

故障面在于交接环节。架构师规划的东西编码者无法实现。编码者产生冲突的差异。评审者批准了虚构的修复。测试者与仍在写代码的编码者竞争。你将构建这样一个团队，在 50 个 SWE-bench Pro 问题上运行它，跟踪每一次交接，并发布事后分析报告。

## 概念

角色是类型化的智能体。**架构师**（Claude Opus 4.7）阅读问题，编写计划，并将其分解为带有明确接口的子任务。**编码者**（Claude Sonnet 4.7，N 个并行实例，每个在独立的 `git worktree` + Daytona 沙箱中）独立实现子任务。**评审者**（GPT-5.4）阅读合并后的差异，批准或要求特定修改。**测试者**（Gemini 2.5 Pro）在隔离环境中运行测试套件，并附带构件报告通过/失败。

通过共享任务面板（基于文件或 Redis）进行通信。每个角色消费其被允许处理的任务。交接通过 A2A 协议类型化消息进行。协调关注点包括：合并冲突解决（协调者角色或自动三方合并）、共享状态同步（规划一旦编码者开始工作即被冻结；重新规划作为独立事件处理）、以及评审者把关（评审者不能批准自己提出的或自己参与的变更）。

Token 放大是隐藏成本。每一个角色边界都会增加摘要提示和交接上下文。一个 40 轮的单智能体运行会在四个角色间变成总共 160 轮。评分标准特别重视 token 效率与单智能体基线的对比，因为问题不在于"多智能体是否有效"，而在于"它是否每花一美元都能胜出"。

      +--------+-------+-------+--------+

## 技术栈

- 编排：LangGraph，带有共享状态 + 每个智能体的子图
- 消息传递：A2A 协议（Google 2025），用于类型化的智能体间消息
- 模型：Opus 4.7（架构师）、Sonnet 4.7（编码者）、GPT-5.4（评审者）、Gemini 2.5 Pro（测试者）
- 工作树隔离：每个编码者一个 `git worktree add` + Daytona 沙箱
- 合并协调者：自定义三方合并 + LLM 介导的冲突解决
- 评测：SWE-bench Pro（50 个问题）、SWE-AF 场景、HumanEval++（单元测试）
- 可观测性：Langfuse，带有角色标记的 span，每个智能体的 token 核算
- 部署：K8s，每个角色作为独立的 Deployment + 基于积压的 HPA

## 构建

1. **任务面板。** 基于文件的 JSONL，带有类型化消息：`plan_request`（规划请求）、`subtask`（子任务）、`diff_ready`（差异就绪）、`review_needed`（需要评审）、`test_needed`（需要测试）、`approved`（已批准）、`rejected`（已拒绝）、`replan_needed`（需要重新规划）。智能体订阅标签。

2. **架构师。** 读取 GitHub 问题，运行 Opus 4.7，使用要求明确子任务接口（涉及的文件、公开函数、测试影响）的规划模板。生成一个包含子任务 DAG（有向无环图）的 `plan_request`。

3. **编码者。** N 个并行工作者，每个从面板认领一个子任务。每个创建一个新的 `git worktree add` 分支以及一个 Daytona 沙箱。实现子任务。生成带有补丁 + 测试差异的 `diff_ready`。

4. **合并协调者。** 在所有编码者完成后，将 N 个分支三方合并到一个暂存分支。仅在存在文件级重叠时才使用 LLM 介导的冲突解决。

5. **评审者。** GPT-5.4 读取合并后的差异。不能批准自己编写的差异。生成 `approved`（无操作）或带有具体修改请求的 `review_feedback`，路由回相关的编码者。

6. **测试者。** Gemini 2.5 Pro 在干净的沙箱中运行测试套件。捕获构件。生成 `test_passed` 或带有堆栈跟踪的 `test_failed`。失败的测试循环返回给负责失败子任务的编码者。

7. **交接核算。** 每一条跨越角色边界的消息在 Langfuse 中获得一个 span，包含载荷大小和使用的模型。计算每个子任务的 token 放大率（编码者 token + 评审者 token + 测试者 token + 架构师分摊 / 编码者 token）。

8. **评测。** 在 50 个 SWE-bench Pro 问题上运行。将 pass@1 和每解决一个问题的花费与单智能体基线（一个 Sonnet 4.7 在单个工作树中）进行比较。

9. **事后分析。** 对于每个失败的问题，识别出故障的交接环节（计划过于模糊、合并冲突、评审者误批准、测试者不稳定）。生成交接失败直方图。

## 交付

`outputs/skill-multi-agent-team.md` 是交付物。给定一个问题的 URL 和并行度，该团队生成一个可合并的 PR，附带每个角色的 token 核算。

| 权重 | 标准 | 衡量方式 |
|:-:|---|---|
| 25 | SWE-bench Pro pass@1 | 匹配的 50 问题子集，pass@1 |
| 20 | 并行加速比 | 挂钟时间 vs 单智能体基线 |
| 20 | 评审质量 | 注入缺陷探测中的误批准率 |
| 15 | 协调工程 | 合并冲突解决、交接失败直方图 |
| 10 | Token 效率 | 每解决一个问题的总 token 数 vs 单智能体 |
| **100** | | |

## 练习

1. 在运行过程中向差异中注入一个明显的缺陷（在主体前额外加一个 `return None`）。测量评审者的误批准率。调整评审者提示，直到误批准率低于 5%。

2. 减少为两个编码者（架构师 + 编码者 + 评审者 + 测试者，编码者顺序执行两个子任务）。比较挂钟时间和通过率。

3. 用单写入者约束（子任务操作不相交的文件集）替换合并协调者。衡量架构师的规划负担。

4. 将评审者从 GPT-5.4 替换为 Claude Opus 4.7。测量误批准率和 token 成本差异。

5. 添加第五个角色：文档编写者（Haiku 4.5）。在评审之后，它生成变更日志条目。衡量文档质量是否值得额外的 token 开销。

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|-----------|---------|
| 并行工作树 | "隔离分支" | `git worktree add` 为每个编码者生成一个独立的工作树 |
| 任务面板 | "共享消息总线" | 智能体订阅的类型化消息的文件或 Redis 存储 |
| 交接 | "角色边界" | 从一个角色的上下文传递到另一个角色的任何消息 |
| Token 放大 | "多智能体开销" | 跨角色的总 token 数 / 同一任务的单智能体 token 数 |
| A2A 协议 | "智能体间协议" | Google 2025 年用于类型化智能体间消息的规范 |
| 合并协调者 | "集成者" | 执行三方合并并调解冲突的组件 |
| 误批准 | "评审者幻觉" | 评审者批准带有已知缺陷的差异 |
