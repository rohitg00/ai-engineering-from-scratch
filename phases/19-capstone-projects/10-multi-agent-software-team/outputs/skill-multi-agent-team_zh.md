给定一个 GitHub 问题 URL 和一个并行度级别，部署一个多智能体软件团队，生成一个合并就绪的 PR。在 50 个 SWE-bench Pro 问题上评估，并发布交接失败直方图。

构建计划：

1. 任务板：文件支持（或 Redis）的类型化消息 JSONL 存储。消息类型：plan_request、subtask、diff_ready、review_needed、review_feedback、approved、test_needed、test_passed、test_failed、replan_needed。
2. 架构师（Opus 4.7）：阅读问题，编写计划，输出子任务的 DAG，带有明确的接口（接触的文件、公共函数、测试影响）。
3. N 个编码者（Sonnet 4.7）：每个认领一个子任务，生成一个全新的 `git worktree add` + Daytona 沙箱，独立实现。
4. 合并协调器：三方合并；仅在文件级重叠时进行 LLM 调解的冲突解决。
5. 审阅者（GPT-5.4）：阅读合并后的差异；不能批准自己编写的差异；输出 approved 或 review_feedback 路由到相关的编码者。
6. 测试者（Gemini 2.5 Pro）：在干净的沙箱中运行测试套件；输出 test_passed 或 test_failed（带工件）。
7. 交接记账：每个跨角色消息成为 Langfuse 跨度，包含负载大小和模型。计算令牌放大率 = 总令牌数 / 单智能体基线令牌数。
8. 注入明显的错误探测（10% 的运行）以测量审阅者的误批准率。
9. 在 50 个 SWE-bench Pro 问题上运行；发布 pass@1、墙上时钟 vs 单智能体基线、按角色划分的令牌分解、交接失败直方图。

评估量规：

| 权重 | 标准 | 衡量方法 |
|:-:|---|---|
| 25 | SWE-bench Pro pass@1 | 50 问题子集 pass@1 |
| 20 | 并行加速 | 墙上时钟 vs 单智能体基线 |
| 20 | 审查质量 | 注入错误探测的误批准率 |
| 20 | 令牌效率 | 每个已解决问题的总令牌数 vs 单智能体 |
| 15 | 协调工程 | 合并冲突解决、交接失败直方图 |

硬性拒绝：

- 审阅者可以批准自己编写或提出的差异。硬性约束。
- 没有匹配的单智能体基线运行的报告。多智能体必须*按每美元*胜出，而不仅仅是 pass@1。
- 消息是自由格式字符串而非类型化 A2A 消息的任务板。
- 静默丢弃冲突差异而不是路由回重新计划的合并协调器。

拒绝规则：

- 拒绝在没有每角色预算上限（令牌 + 美元）的情况下运行。
- 拒绝打开 PR 而测试者未在干净沙箱中验证。
- 拒绝在单次运行中将编码者扩展到超过 8 个。超过此数的协调开销占主导地位。

输出：一个包含任务板 + 角色工作者、50 问题 SWE-bench Pro 运行日志、匹配的单智能体基线运行、带有角色标记跨度和按角色令牌分解的 Langfuse 仪表板、注入错误探测报告，以及一份指出最常出问题的三种交接及减少每种问题的消息模式或提示变更的事后分析报告的仓库。
