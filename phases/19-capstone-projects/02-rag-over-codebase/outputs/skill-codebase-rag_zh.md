给定 10 个以上总计至少 200 万行代码的仓库，构建一个摄取管道、一个混合索引和一个强制引用的查询智能体，能够以可验证的 file:line 锚点回答跨仓库问题。

构建计划：

1. 使用 tree-sitter 解析每个文件。在函数和类节点边界进行分块。存储 `{repo, path, start_line, end_line, symbol, body}`。
2. 使用 Claude Haiku 4.5 或 Gemini 2.5 Flash（带提示缓存系统提示）总结每个块。将一句话摘要存储到块旁边。
3. 索引到三个结构中：Qdrant（稠密，Voyage-code-3 或 nomic-embed-code）、Tantivy（带字段权重的 BM25）和 kuzu（用于 import、call、inheritance 的符号图边）。
4. 构建一个 LangGraph 查询智能体，包含三个节点：检索（稠密并行 BM25）、重新排序（Cohere rerank-3 或 bge-reranker-v2-gemma-2b）、合成（Claude Sonnet 4.7，带提示缓存和 file:line 引用要求）。
5. 后过滤：拒绝任何没有可验证 `(repo/path:start-end)` 锚点的声明；重新询问或丢弃。
6. 连接 git push webhook，计算符号级差异，仅重新嵌入更改的块。目标：在 200 万行代码的代码库中，50 个文件的提交在 60 秒内可搜索。
7. 使用 100 个问题的保留集进行评估。报告 MRR@10、nDCG@10、引用忠实度和延迟百分位数。
8. 运行每周漂移任务，重新执行评估，并在 MRR@10 下降超过 5% 时发出警报。

评估量规：

| 权重 | 标准 | 衡量方法 |
|:-:|---|---|
| 25 | 检索质量 | 100 问题保留集上的 MRR@10 和 nDCG@10 |
| 20 | 引用忠实度 | 具有可验证 file:line 锚点的答案声明比例 |
| 20 | 延迟和扩展性 | 在索引语料库大小上，10k QPS 下的 p95 查询延迟 |
| 20 | 增量索引正确性 | 从 git push 到 50 文件提交可搜索的时间 |
| 15 | 用户体验和答案格式 | 引用可点击性、片段预览、后续追问能力 |

硬性拒绝：

- 使用固定大小令牌分块而不是 AST 感知分块。会污染生成代码密集的语料库。
- 仅使用余弦检索而不使用 BM25 或重新排序。已知在精确符号名称查询上会失败。
- 没有强制 file:line 引用的答案。
- 每次 git push 都重新嵌入整个语料库；必须是增量的。

拒绝规则：

- 拒绝索引未经许可读取的仓库。有些禁止在第三方向量存储中嵌入。
- 拒绝回答声称引用索引从未见过的文件的查询；始终在返回前验证锚点。
- 拒绝在 p95 延迟超过 4 秒时提供答案；改为返回部分结果并附带后续处理句柄。

输出：一个包含摄取管道、LangGraph 查询智能体、100 问题标记评估集、Langfuse 仪表板链接和一份说明您修复的三种检索故障模式（生成代码污染、长尾符号召回、跨仓库符号解析）及确切变更的仓库。
