# 人在回路中：提议-然后-提交 (Propose-Then-Commit)

> 2026 年关于人在回路（HITL）的共识非常明确。它不是"智能体提问，用户点击批准"。而是**提议-然后-提交**：将提议的操作持久化到具有幂等键的持久存储中；连同意图、数据血统、所涉权限、影响范围以及回滚计划一起呈现给审核人；只有在获得明确确认后才提交；执行后验证以确保副作用确实发生。LangGraph 的 `interrupt()` 配合 PostgreSQL 检查点、Microsoft Agent Framework 的 `RequestInfoEvent` 以及 Cloudflare 的 `waitForApproval()` 都实现了相同的模式。典型的失败模式是**橡皮图章式批准**："批准？"未经审查就被点击。有文档记载的缓解方案是带有明确检查清单的质询-应答机制。

**类型：** 学习
**语言：** Python（标准库，带有幂等性的提议-然后-提交状态机）
**前置知识：** 阶段 15 · 12（持久化执行），阶段 15 · 14（绊网）
**时间：** 约 60 分钟

## 问题

智能体执行了一个操作。用户必须决定：批准还是不批准。如果决定是瞬间做出的，那很可能不是真正的审查。如果决定是有结构的，那会很慢但值得信赖。工程问题是如何让结构化审查成为阻力最小的路径。

2023 年时代的 HITL 模式是一个同步提示："智能体想要向 X 发送正文为 Y 的邮件——批准吗？"用户点击批准。每个人都觉得系统是安全的。但实际上，这种界面被严重橡皮图章化：用户快速批准，批准行为几乎无法预测任何问题，而当智能体出错时，审计追踪显示出一长串用户记不起的批准记录。

2026 年的模式——提议-然后-提交——将 HITL 迁移到持久化基础之上，附加结构化元数据，并要求主动提交。每个可管理的智能体 SDK 都提供了一个版本：LangGraph 的 `interrupt()`、Microsoft Agent Framework 的 `RequestInfoEvent`、Cloudflare 的 `waitForApproval()`。API 名称不同，但形态一致。

## 概念

### 提议-然后-提交状态机

1. **提议。** 智能体生成一个提议的操作。持久化到持久存储（PostgreSQL、Redis、Durable Object）中。包括：
   - 意图（智能体为什么要做这件事）
   - 数据血统（什么数据源导致了该提议）
   - 所涉权限（哪些作用域/文件/端点）
   - 影响范围（最坏情况是什么）
   - 回滚计划（如果提交了，如何撤销）
   - 幂等键（每个提议唯一；重复提交返回相同记录）
2. **呈现。** 审核人看到包含所有元数据的提议。审核人必须是人类（而非智能体自我审查）。
3. **提交。** 明确确认。操作被执行。
4. **验证。** 执行后，回读并确认副作用。如果验证步骤失败，系统处于已知的异常状态，警报机制启动。

### 幂等键

没有幂等键，在瞬时故障后的重试可能会导致已批准的操作被重复执行。具体例子：用户批准"从 A 转账 100 美元到 B"。网络波动。工作流重试。用户只批准了一次，但转账执行了两次。幂等键将批准与唯一的、单一的副作用绑定；第二次执行是空操作。

这与 Stripe 和 AWS API 使用的幂等模式相同。Microsoft Agent Framework 文档明确说明将其复用于智能体批准。

### 持久性：为什么批准能跨进程存活

批准的等待室是智能体不拥有的一块状态。工作流被暂停（第 12 课）。当批准到达时，工作流从该精确点恢复执行。这就是为什么 LangGraph 将 `interrupt()` 与 PostgreSQL 检查点配对，而非仅使用内存状态——两天后的批准仍然能找到完整的工作流。

### 橡皮图章式批准与质询-应答缓解方案

HITL 的默认 UI（"批准"/"拒绝"按钮）产生快速批准，但没有真正的审查。有文档记载的缓解方案：一个质询-应答检查清单，要求在启用批准按钮之前肯定地回答特定问题。具体形态：

- "你理解这个操作涉及什么资源吗？[ ]"
- "你确认影响范围是可接受的吗？[ ]"
- "如果失败，你有回滚计划吗？[ ]"

这不是为了繁琐而繁琐——而是一种强制机制。无法勾选这些框的审核人要么要求澄清（升级），要么拒绝（安全默认）。Anthropic 的智能体安全性研究明确引用了基于检查清单的 HITL 作为缓解橡皮图章式批准模式的方案。

### 什么算作重大操作

并非每个操作都需要提议-然后-提交。2026 年的指导原则：

- **重大操作**（始终需要 HITL）：不可逆的写入、金融交易、对外通信、生产数据库变更、破坏性文件系统操作。
- **可逆操作**（有时需要 HITL）：对本地文件的编辑、预发布环境的变更、具有明确回滚计划的可逆写入。
- **读取和检查**（永远不需要 HITL）：读取文件、列出资源、调用只读 API。

### 操作后验证

"提交已运行"不等于"副作用已发生"。网络分区和竞态条件可能导致工作流认为自己成功了，而后端并未持久化。验证步骤在提交后重新读取目标资源以确认。这与使用 `RETURNING` 子句的数据库事务或 AWS 的 `PutObject` 后跟 `GetObject` 是相同的模式。

### 欧盟人工智能法案第 14 条

第 14 条强制要求对高风险 AI 系统进行有效的人类监督。"有效"不是装饰性的。监管语言特别排除了橡皮图章模式。在 Microsoft Agent 治理工具包的合规文档中，带有质询-应答的提议-然后-提交是能够通过第 14 条审查的形态。

## 使用它

`code/main.py` 使用标准库 Python 实现了一个提议-然后-提交状态机。持久存储是一个 JSON 文件。幂等键是（线程 ID，操作签名）的哈希值。驱动模拟了三种情况：干净的批准流程、瞬时故障后的重试（不能重复执行），以及橡皮图章默认流程与质询-应答流程的对比。

## 交付

`outputs/skill-hitl-design.md` 审核了一个提议的 HITL 工作流，检查其提议-然后-提交形态，并标记缺失的元数据、幂等性、验证或质询-应答层。

## 练习

1. 运行 `code/main.py`。确认已批准提议的重试会使用持久化记录且不会重新执行。然后修改幂等键使其包含时间戳，并展示重试会重复执行。

2. 在提议记录中添加一个 `rollback` 字段。模拟一个验证步骤失败的执行。展示回滚自动触发。

3. 阅读 Microsoft Agent Framework 的 `RequestInfoEvent` 文档。找出该 API 包含但简易引擎缺失的一个元数据字段。添加该字段并解释它防范什么。

4. 为某个具体操作设计一个质询-应答检查清单（例如"发布到公开的 Twitter 账户"）。审核人必须回答哪三个问题？为什么是这三个？

5. 选择一个场景，说明何时同步的"批准？"提示就足够了（无需持久存储）。解释原因，并说明你接受的是哪类风险。

## 关键术语

| 术语 | 人们说它是什么 | 它实际意味着什么 |
|---|---|---|
| 提议-然后-提交 | "两阶段批准" | 持久化提议 + 主动提交 + 验证 |
| 幂等键 | "重试安全的令牌" | 每个提议唯一；第二次执行为空操作 |
| 数据血统 | "它从哪里来" | 导致该提议的特定源内容 |
| 影响范围 | "最坏情况" | 如果操作出错的影响范围 |
| 橡皮图章 | "快速批准" | "批准"被点击但未经过真正审查 |
| 质询-应答 | "强制检查清单" | 审核人必须肯定地回答特定问题 |
| RequestInfoEvent | "MS Agent Framework 原语" | 带有结构化元数据的持久化 HITL 请求 |
| `interrupt()` / `waitForApproval()` | "框架原语" | LangGraph / Cloudflare 的相同形态等价实现 |
