给定一个拟议的长期运行智能体部署（Temporal + OpenAI Agents SDK、带 PostgreSQL 检查点的 LangGraph、Microsoft Agent Framework、Claude Code Routines、Cloudflare Durable Objects 或内部等效实现），对照持久执行模式审计设计。

生成以下内容：

1. **活动清单**。列出每个活动（LLM 调用、工具调用、HTTP 请求、文件写入）。确认每个活动都被包装为具有重试策略、超时和幂等键的活动。活动边界之外的原始 LLM 调用是可靠性漏洞。
2. **工作流确定性**。识别工作流代码内部的每个非确定性读取（挂钟时间、随机数、外部状态）。每个都必须注册为副作用活动，以便重放返回相同的值。隐藏的非确定性是重放漂移的最常见原因。
3. **检查点后端**。命名后端（PostgreSQL、SQLite、Redis、Durable Objects）。确认其在部署后仍能存活。SQLite 仅限开发环境。Redis 需要 AOF 或快照配置。Cloudflare Durable Objects 透明但需要唯一键约束。
4. **人工输入状态**。确认用于 HITL 的暂停是一等工作流状态，而非轮询循环。工作流应阻塞等待外部信号（审批队列、webhook、`interrupt()` 原语），该信号在审批到达时精确恢复。
5. **恢复时 HITL 策略**。对于崩溃后的任何恢复，说明在执行下一个活动之前是否需要新的 HITL。如果没有此策略，持久执行加上崩溃前已授予的审批可能会在上下文已改变时重新触发已批准的操作。对于长时间范围至关重要。

硬性拒绝：
- LLM 调用未包装为活动的 Agent SDK 使用方式。
- 无法在部署后存活的检查点后端。
- 嵌入了挂钟时间或随机数但未进行活动包装的工作流。
- 建模为轮询循环而非信号的人工输入。
- 超过一小时的长时间运行且没有恢复时 HITL 策略。
- 在持久性之上没有预算应急开关（第 13 课）的运行。

拒绝规则：
- 如果用户提议的持久化工作流没有对副作用活动明确的幂等性，则拒绝并要求先提供幂等性键。否则重试将导致双重执行。
- 如果用户无法展示重放测试（运行工作流、中途崩溃、重放、断言没有双重副作用），则拒绝并要求在生产前进行该测试。
- 如果用户提议 24 小时无人值守运行且没有 HITL 检查点，则拒绝。即使持久性正确，35 分钟的退化（第 12 课说明）也会使其成为可靠性问题。

输出格式：

返回一份设计审查备忘录，包含：
- **活动表格**（活动、重试策略、超时、幂等键）
- **确定性审计**（非确定性读取及其处理方式）
- **检查点后端**（名称、部署后存活 y/n、重放测试状态）
- **HITL 状态形态**（一等状态 / 轮询 / 缺失）
- **恢复时 HITL 策略**（明确说明，附理由）
- **就绪性**（生产 / 预演 / 仅研究）
