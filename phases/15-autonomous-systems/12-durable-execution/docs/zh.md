# 长期运行的后台智能体：持久化执行

> 生产级长周期智能体不会在 `while True` 循环中运行。每一次 LLM 调用都成为一个带有检查点、重试和重放的活动。Temporal 的 OpenAI Agents SDK 集成已于 2026 年 3 月正式发布。Claude Code Routines（Anthropic）按计划调用 Claude Code，无需持久的本地进程。会话在等待人工输入时暂停，在部署后存活，并从由 `thread_id` 键定的最新检查点恢复。在新的易用性背后，是一种古老的模式——工作流编排——只是加入了一个新的输入：将 LLM 调用作为非确定性活动，在恢复时必须能够确定性地重放。

**类型：** 学习
**语言：** Python（标准库，最小化持久化执行状态机）
**前置条件：** 阶段 15 · 10（权限模式），阶段 15 · 01（长周期智能体）
**时长：** ~60 分钟

## 问题

考虑一个运行四小时的智能体。它调用了三个工具，两次提示用户，并进行了四十次 LLM 调用。运行到一半时，其所运行的主机重启了。会发生什么？

- 在朴素的 `while True` 循环中：一切都会丢失。运行从头开始重新执行。已执行的三次工具调用（具有真实副作用）会再次执行。用户会被再次提示他们已经批准过的事项。四十次 LLM 调用会被重新计费。
- 采用持久化执行：运行从最近的检查点恢复。已完成的活动不会重新执行；其结果从持久化日志中重放。用户无需重新批准已经批准过的事项。已完成的 LLM 调用不会再次计费。

这是工作流引擎十年来一直在使用的模式（Temporal、Cadence、Uber 的 Cherami）。新的变化在于，LLM 调用现在成为一种活动——非确定性、成本高昂、具有副作用——并且它们完美地适配了这种模式。

本课的核心主题：长周期可靠性会衰减（METR 观察到"35 分钟退化"——成功率大致随运行时间呈二次方下降）。持久化执行允许运行时长超过可靠性曲线的支撑范围，这是一种新的失败模式：设计正确时可以安全地失败，设计错误时则可能不安全。

## 概念

### 活动、工作流与重放

- **工作流**：确定性编排代码。定义活动的序列、分支和等待。必须是确定性的，以便能够从事件日志中重放而不会出现意外的偏差。
- **活动**：一个非确定性、可能失败的工作单元。LLM 调用、工具调用、文件写入、HTTP 请求。每个活动都记录其输入和（完成后）其输出。
- **事件日志**：持久化后端存储。每个活动的开始、完成、失败、重试以及每个工作流决策都被记录下来。
- **重放**：恢复时，工作流代码从头开始重新运行；每个已完成的活动返回其记录的结果而不重新执行。只有尚未完成的活动才会实际运行。

这与 React 针对虚拟 DOM 重新渲染，或 Git 从提交重建工作树是相同的模式。编排器的确定性使得持久化变得廉价。

### 为什么 LLM 调用适配此模式

LLM 调用具有以下特性：
- 非确定性（温度 > 0；即使温度为 0，在不同模型版本间也会漂移）。
- 成本高昂（金钱和延迟）。
- 可能失败（速率限制、超时）。
- 具有副作用（如果调用工具）。

这正是活动的特征。将每次 LLM 调用包装为活动，即可获得指数退避重试、跨重启的检查点以及可重放的调试追踪。

### 由 `thread_id` 键定的检查点

LangGraph、Microsoft Agent Framework、Cloudflare Durable Objects 和 Claude Code Routines 都收敛到了相同的 API 形式：`thread_id`（或等效标识）标识会话；每次状态转换持久化到后端（PostgreSQL 为默认，SQLite 用于开发，Redis 用于缓存）；恢复时读取最新的检查点。

后端的选择很重要：

- **PostgreSQL**：持久化、可查询、可在部署后存活。LangGraph 的默认选择。
- **SQLite**：仅限本地开发；跨主机时会丢失数据。
- **Redis**：速度快但生命周期短，除非配置了 AOF 或快照。
- **Cloudflare Durable Objects**：透明分布式；由唯一键限定范围；可持续数小时到数周。

### 人工输入作为一等状态

先提方案再确认（阶段 15）要求一个持久的"等待人工输入"状态。工作流暂停，外部队列持有待处理请求，审批从该确切点恢复。没有持久化，这只能是尽力而为；有了持久化，隔夜的审批到达时，工作流可在第二天早上继续执行。

### 35 分钟退化

METR 观察到，所有被测量的智能体类别在连续运行约 35 分钟后都会出现可靠性衰减。将任务时长加倍，故障率大致会翻两番。持久化执行并不能解决这个问题；它只是允许你的运行时长超过可靠性曲线的支撑范围。安全的模式是将持久化与以下两者结合：要求在重新进入时进行新的人工确认（HITL）的检查点，以及设置预算终止开关（阶段 13）以限制总计算量（无论挂钟时间如何）。

### 何时持久化执行不是正确的答案

- 运行时间短于几分钟且无需人工输入。开销大于收益。
- 严格只读的信息检索。
- 需要端到端在单个上下文窗口内完成才能保证正确性的任务（某些推理任务；某些一次性生成任务）。

## 使用它

`code/main.py` 使用标准库 Python 实现了一个最小化的持久化执行引擎。它支持：

- `@activity` 装饰器，将输入和输出记录到 JSON 事件日志中。
- 一个编排活动序列的工作流函数。
- 一个 `run_or_replay(workflow, event_log)` 函数，重放已完成的活动而不重新执行它们。

驱动程序模拟了一个三活动的工作流，在运行中途"崩溃"，并展示了：(a) 朴素的重新尝试会重新执行所有活动，而 (b) 重放仅运行缺失的活动。

## 交付

`outputs/skill-durable-execution-review.md` 对一个拟议的长期运行智能体部署进行评审，检查其持久化执行形态是否正确：活动、确定性、检查点后端、人工输入状态以及恢复时的人工确认策略。

## 练习

1. 运行 `code/main.py`。观察朴素重试与重放之间活动执行次数的差异。改变崩溃点，观察重放计数的相应变化。

2. 将实验引擎改造为显式使用 `thread_id`。模拟两个并发会话共享同一引擎，并确认它们的事件日志不会冲突。

3. 在实验引擎中选择一个活动。引入一个非确定性因素（例如在工作流决策中使用挂钟时间戳）。展示重放时的偏差。解释真实引擎如何处理这个问题（副作用注册、`Workflow.now()` API）。

4. 阅读 LangChain 的"生产级深度智能体背后的运行时"一文。列出运行时持久化的每一个状态，并说明每个状态覆盖了哪种故障模式。

5. 为一个 6 小时的自主编码任务设计检查点策略。你在哪里设置检查点？崩溃后恢复是什么样的？哪些地方需要新的人工确认？

## 关键术语

| 术语 | 人们通常说的 | 实际含义 |
|---|---|---|
| 工作流 | "智能体的脚本" | 确定性编排代码；可从事件日志重放 |
| 活动 | "一个步骤" | 非确定性单元（LLM 调用、工具调用）；前后均有日志记录 |
| 事件日志 | "后端存储" | 每个状态转换的持久化记录 |
| 重放 | "恢复" | 重新运行工作流；已完成的活动返回记录的结果而不重新执行 |
| 检查点 | "保存点" | 由 thread_id 键定的持久化状态；恢复时取最新的 |
| thread_id | "会话键" | 限定持久化状态的标识符 |
| 35 分钟退化 | "可靠性衰减" | METR：成功率随运行时间大致呈二次方下降 |
| 非确定性 | "重放时的漂移" | 挂钟时间、随机数、LLM 输出；必须注册为副作用 |
