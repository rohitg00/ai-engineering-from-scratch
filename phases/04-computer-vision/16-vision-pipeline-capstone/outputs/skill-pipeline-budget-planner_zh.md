# 流水线预算规划器

将延迟/吞吐量目标转化为逐阶段预算，让每个团队成员都知道自己正在向什么指标努力。

## 使用时机

- 在构建新的视觉服务之前，为每个阶段设定预期。
- 首次基准测试后，查看哪个阶段离预算最远。
- 当 SLA 变更且需要重新协商预算时。

## 输入

- `p95_latency_target_ms`：每个请求的预算。
- `target_qps`：每个副本的吞吐量。
- `stages`：`{ name: str, current_ms: float }` 的列表。

## 分配规则

如果没有提供当前测量值，七个标准阶段的默认分配为：

| 阶段 | 占比 |
|-------|-------|
| 解码 + 预处理 | 15% |
| 检测器前向 | 55% |
| 检测后处理（NMS，裁剪） | 5% |
| 为分类器裁剪+调整大小 | 5% |
| 分类器前向 | 15% |
| 模式验证 | <1% |
| 响应序列化 | 4% |

在 GPU 密集型流水线（云端）中，检测器的占比通常会上升到 70%。在 CPU 上，预处理和分类器批处理消耗更多。

## 报告

```
[budget plan]
  p95 target:  <ms>
  throughput:  <每个副本的 qps>

| 阶段               | 目标_ms | 当前_ms | 余量 | 门限 |
|---------------------|-----------|------------|----------|------|
| 解码+预处理         | ...       | ...        | ...      | ok|X |
| 检测器              | ...       | ...        | ...      | ok|X |
| ...                 | ...       | ...        | ...      |      |

[bottleneck]
  stage:  <名称>
  miss:   <超出预算的毫秒数>
  lever:  <具体操作>

[levers]
  解码+预处理：     Pillow-SIMD, libjpeg-turbo, 通过 NVJPEG 在 GPU 上解码
  检测器：          更小的骨干网络、更低的输入分辨率、INT8、TensorRT
  后处理：          GPU 端 NMS（torchvision.ops）、融合掩码
  裁剪+调整大小：   使用 grid_sample 的 GPU 裁剪、批处理插值
  分类器：          更小的骨干网络、INT8、预热缓存、批处理
  模式验证：        在热路径中跳过验证，仅在边界验证
  响应：            orjson、流式 protobuf
```

## 规则

- 绝不建议从生产路径中删除模式验证；建议将其移到边界处。
- 如果预处理超出预算，在更换模型之前始终先尝试 Pillow-SIMD 或 NVJPEG。
- 如果检测器超出目标 30% 以上，应切换模型而非优化当前模型。
- 当 current_ms > 1.1 * target_ms 时将门限标记为 `X`；如果在预算的 10% 以内则标记为 `ok`。
