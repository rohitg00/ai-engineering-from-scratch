# LLM 成本优化模式

在构建需要控制成本的 LLM 应用时，应用此决策框架。

## 何时优化

**立即优化当：**
- 每月 LLM 支出超过 $500 或基础设施预算的 10%
- 消费产品的每查询成本高于 $0.01
- 系统提示超过 1,000 token 且随每个请求发送
- 超过 30% 的查询是重复或近似重复的
- 从 100 扩展到 10,000+ 日活跃用户

**暂不优化当：**
- 日活跃用户少于 100，仍在验证产品-市场匹配
- 月支出低于 $100 且增长缓慢
- 仍在迭代提示设计（缓存会将你锁定在一个提示上）

## 缓存策略选择

### 精确缓存

**使用当：** temperature=0，相同提示重复，需要确定性输出。

```python
key = sha256(json.dumps({"model": m, "messages": msgs, "temp": 0}))
```

- 实施：30 分钟
- 命中率：大多数应用 10-25%，FAQ 机器人 40-60%
- 延迟：<1ms（字典查找）
- 风险：底层数据变化时响应过时

**跳过当：** temperature > 0，每个查询都唯一，需要实时数据。

### 语义缓存

**使用当：** 用户用不同措辞问同一问题，FAQ 密集型产品，客户支持。

- 实施：2-4 小时（嵌入 + 相似度 + 存储）
- 命中率：在精确缓存之上增加 15-35%
- 延迟：10-50ms（嵌入 + ANN 搜索）
- 风险：假阳性（为相似但不同的问题返回错误的缓存答案）

**阈值指南：**
- 0.98+：非常保守，几乎没有假阳性，命中率较低
- 0.95：对事实性问答的良好平衡
- 0.90：激进，命中率更高但有错误答案风险
- 0.85：仅用于低风险应用（建议、自动完成）

**跳过当：** 每个查询都有唯一上下文（代码生成），响应必须反映最新数据，查询空间无界。

### 提供者提示缓存

**使用当：** 系统提示 > 1,024 token（OpenAI）或模型特定最小值，相同前缀重复发送。

| 提供者 | 操作 | 节省 |
|----------|--------|---------|
| Anthropic | 在系统消息中添加 `cache_control: {"type": "ephemeral"}` | 缓存前缀节省 90%（25% 写入溢价后） |
| OpenAI | 无操作（自动） | 缓存前缀节省 50% |
| Google | 使用带显式 TTL 的 Context Caching API | 缓存上下文节省约 75% |

**跳过当：** 系统提示每请求变化，提示低于最小长度。

## 模型路由规则

### 基于关键词（简单、快速）

```
简单：  <= 5 个词 或 匹配 FAQ 关键词 -> gpt-4o-mini ($0.15/$0.60)
中等：  通用查询、摘要        -> claude-sonnet ($3/$15)
复杂：  "分析"、"比较"、"调试"     -> gpt-4o ($2.50/$10)
```

- 实施：1 小时
- 准确率：70-80%
- 节省：模型成本的 40-60%

### 基于嵌入（更准确）

每类别嵌入 50-100 个标记查询。通过最近邻分类新查询。

- 实施：4-8 小时
- 准确率：85-92%
- 节省：模型成本的 50-70%
- 额外成本：分类嵌入约 $0.02/1M token（可忽略）

### 基于 ML（生产级）

在历史查询/模型对上训练小分类器（逻辑回归或小型 BERT）。

- 实施：1-2 周
- 准确率：90-95%
- 节省：模型成本的 60-75%
- 需要：来自生产流量的标记训练数据

## 限速配置

### 按层级划分的令牌桶参数

| 层级 | 桶大小 | 补充速率 | 最大 RPM | 每日上限 |
|------|-------------|-------------|---------|-----------|
| 免费 | 50K token | 500/秒 | 10 | 50K |
| Pro | 500K token | 5K/秒 | 60 | 500K |
| 企业 | 5M token | 50K/秒 | 300 | 5M |

### 实施检查清单

1. 在 Redis 中存储桶（非内存中）以用于多实例应用
2. 使用原子操作（MULTI/EXEC）防止竞态条件
3. 拒绝响应中返回 `Retry-After` 头
4. 将拒绝请求作为指标跟踪（> 5% 拒绝 = 层级限制太紧）
5. 实现优雅降级：先拒绝昂贵的模型请求，保持便宜的模型访问

## 预算控制

### 三阈值断路器

| 阈值 | 操作 | 可逆 |
|-----------|--------|------------|
| 月预算的 70% | 记录警告，通过 Slack/PagerDuty 通知团队 | 是（自动） |
| 月预算的 85% | 将所有流量路由到最便宜的模型 | 是（自动，下个计费周期） |
| 月预算的 95% | 仅提供缓存响应，拒绝新的 LLM 调用 | 是（手动重置或下个周期） |

### 每用户成本跟踪

跟踪每个用户的累计成本。标记超出中位数 10 倍的用户。常见原因：
- 合法的高频用户（升级他们的层级）
- 提示注入循环（发送自动化请求的机器人）
- 低效的集成（每次错误客户端都重试）

## 成本跟踪字段

记录每个 API 调用，包含以下字段：

```json
{
  "timestamp": "2026-04-02T10:30:00Z",
  "model": "gpt-4o",
  "input_tokens": 1523,
  "output_tokens": 487,
  "cached_input_tokens": 1024,
  "latency_ms": 1847,
  "cost_usd": 0.006142,
  "user_id": "user_abc123",
  "cache_status": "partial_hit",
  "request_category": "customer_support",
  "complexity_class": "medium",
  "routed_from": "gpt-4o"
}
```

### 要在仪表盘上显示的关键指标

- **每查询成本**（P50、P95、P99）——按模型、按功能、按用户层级
- **缓存命中率**——精确 vs 语义，随时间趋势
- **模型分布**——各模型的流量百分比和成本
- **预算消耗速率**——当前支出 vs 按当前速度的月预计
- **拒绝率**——被限速的请求百分比，按层级

## 常见错误

| 错误 | 为什么有害 | 修复 |
|---------|-------------|-----|
| 使用 temperature > 0 进行缓存 | 非确定性输出，过时缓存给出错误多样性 | 仅缓存 temp=0 的调用，或接受缓存响应失去随机性 |
| 语义缓存阈值过低 | 为表面上相似的查询返回错误答案 | 从 0.95 开始，仅在测量假阳性率后降低 |
| 无缓存失效 | 底层数据变化时响应过时 | 设置 TTL（动态数据 1 小时，静态数据 24 小时），数据更新时失效 |
| 将所有流量路由到最便宜的模型 | 质量下降，用户能注意到 | 按复杂度路由，按层级测量质量，设置最低质量阈值 |
| 无每用户限制 | 一个滥用用户耗尽整个预算 | 始终实施每用户配额，即使设置得很宽松 |
| 忽略输出 token | 输出成本每 token 比输入高 2-5 倍 | 适当设置 max_tokens，使用停止序列，压缩输出 |
| 提示稳定前缓存 | 缓存填充来自旧提示的响应 | 仅在提示最终确定后启用缓存，提示更改时刷新缓存 |
