# 微调决策指南

在微调之前，按顺序尝试以下步骤：

```
1. 提示工程（几分钟，$0）
2. 提示中的少样本示例（几分钟，$0）
3. RAG 用于知识检索（几天，$10-100/月）
4. 使用 LoRA/QLoRA 微调（几天，每个实验 $5-50）
5. 全微调（几周，每次运行 $100-10,000）
```

仅当上一步明显不足时才进入下一步。

## 何时微调

- 模型需要提示工程无法实现的一致输出风格或格式
- 正在蒸馏更大的模型（8B 模型的 GPT-4 质量）
- 延迟重要且少样本示例增加太多 token
- 需要模型可靠地遵循复杂推理模式
- 有 1,000+ 个期望输入-输出行为的高质量示例

## 何时不微调

- 模型已经用正确的提示做你想要的
- 需要模型知道事实（使用 RAG 替代）
- 训练示例少于 500 个（可能过拟合）
- 任务频繁变化（重新训练成本高）
- 需要审计哪些数据影响了特定输出（微调是一个黑盒）

## 方法选择

| GPU VRAM | 7B 模型 | 13B 模型 | 70B 模型 |
|----------|----------|-----------|-----------|
| 16GB（T4） | QLoRA | 不可行 | 不可行 |
| 24GB（3090/4090） | QLoRA 或 LoRA | QLoRA | 不可行 |
| 40GB（A100） | LoRA 或 全量 | QLoRA 或 LoRA | QLoRA |
| 80GB（A100/H100） | 全量 | LoRA 或 全量 | QLoRA 或 LoRA |

## LoRA 配置检查清单

1. 从 r=16、alpha=32 开始（大多数任务的安全默认值）
2. 首先针对 q_proj 和 v_proj（最小可行 LoRA）
3. QLoRA 使用学习率 2e-4，LoRA fp16 使用 5e-5
4. 设置 lora_dropout=0.05
5. 训练 1-3 轮（更多有过度拟合风险）
6. 每 100 步在保留集上评估
7. 保存检查点，按评估损失选择最佳

## 常见错误

- 训练轮次太多（小数据集上在 2-3 轮后过拟合）
- 使用与全微调相同的学习率（LoRA 需要更高的学习率）
- 忘记设置填充 token（导致 Llama 模型的 NaN 损失）
- 未冻结基础模型（违背 LoRA 的目的）
- 仅在训练数据上评估（始终保留 10-20% 用于评估）
- 跳过提示工程基线（微调提示工程已解决的问题）

## 质量验证

训练后，在 200+ 个保留示例上比较：
1. 带最佳提示的基础模型（基线）
2. 带 LoRA 适配器的基础模型（微调后的模型）
3. 带相同提示的 GPT-4 或 Claude（天花板）

如果 LoRA 模型未超过提示基线，则训练数据或配置有问题，不是需要更多计算的问题。

## 适配器管理

- 为多任务服务保持适配器分离（按请求切换适配器）
- 为单一任务部署将适配器合并到基础权重中
- 在 Hugging Face Hub 上存储适配器（10-100MB，易于版本管理和共享）
- 部署前测试合并模型输出与未合并输出是否匹配
- 使用 TIES-Merging 或 DARE 将多个适配器合并为一个

## 调试训练

如果损失不下降：
1. 检查学习率（对 LoRA 太低，尝试 2e-4）
2. 验证 LoRA 层是否实际接收梯度
3. 确认基础模型权重已冻结
4. 检查数据格式化（分词器必须匹配模型的预期格式）

如果损失下降但评估质量差：
1. 训练数据质量问题（垃圾进，垃圾出）
2. 过拟合（减少轮次、增加丢弃率、添加更多数据）
3. 错误的目标模块（为复杂任务添加 MLP 层）
4. 秩太低（尝试 r=32 或 r=64）
