# RAG 流水线模式

每个 RAG 系统遵循此模式：

```
文档 -> 分块 -> 嵌入 -> 存储
查询 -> 嵌入 -> 搜索(top_k) -> 构建提示 -> 生成
```

索引每文档发生一次。查询在每个用户请求时发生。

## 何时使用 RAG

- LLM 需要访问私有或近期文档
- 微调太昂贵或更新太慢
- 需要为答案引用来源
- 知识库频繁变化

## 何时不使用 RAG

- 答案是 LLM 已有的通用知识
- 任务是创意性的（写作、头脑风暴），而非事实性的
- 需要模型采用特定的推理风格（使用微调）

## 实现检查清单

1. 将文档分块为 256-512 token 的段，带 50 token 重叠
2. 使用一致的嵌入模型嵌入每个块
3. 将嵌入存储在向量数据库中，附带原始文本
4. 查询时，使用相同模型嵌入用户的问题
5. 通过余弦相似度检索 top-k（5-10）最相似的块
6. 构建提示：系统指令 + 检索上下文 + 用户问题
7. 生成答案，将其基于检索到的上下文
8. 返回答案及源引用

## 常见错误

- 索引和查询使用不同的嵌入模型（向量不兼容）
- 块太小（丢失上下文）或太大（稀释相关性）
- 块之间不包含重叠（在边界处拆分句子）
- 文档更改时忘记重新索引
- 向用户返回检索到的块而不生成连贯的答案
- 事实性 RAG 查询未设置 temperature=0（更高温度 = 更多幻觉）

## 调试检索

如果未检索到正确的块：
1. 打印查询嵌入并验证其非零
2. 对已知相关块手动检查余弦相似度
3. 尝试重新表述查询以匹配文档词汇
4. 验证嵌入模型在索引和查询时一致
5. 检查相关内容是否在分块期间丢失

## 生产参数

- 块大小：256-512 token
- 重叠：50 token（块大小的 10-20%）
- Top-k：大多数用例 5-10
- 温度：事实性答案用 0
- 嵌入模型：text-embedding-3-small（成本效益）或 text-embedding-3-large（更高准确率）
