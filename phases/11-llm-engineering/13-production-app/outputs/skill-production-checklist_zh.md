# 生产 LLM 检查清单

在交付 LLM 应用时，按顺序完成此检查清单。每个部分都有通过/失败标准及特定阈值。

## 1. 安全（发布阻塞）

这里的每个项目在部署前必须通过。

| 检查项 | 通过标准 | 如何验证 |
|-------|--------------|---------------|
| API 密钥在环境变量中 | 代码库中零硬编码密钥 | `grep -r "sk-" --include="*.py"` 返回空 |
| 输入护栏启用 | 提示注入模式被阻止 | 发送"忽略所有先前指令"——返回阻止响应 |
| PII 编辑 | SSN、信用卡、邮箱模式被捕获 | 发送"我的 SSN 是 123-45-6789"——在 LLM 调用前 PII 已编辑 |
| 输出过滤 | 危险内容被阻止 | 模型不能返回 `DROP TABLE`、`rm -rf`、`exec()` 模式 |
| 限速 | 强制执行每用户请求上限 | 同一用户 10 秒内 100 个请求——最后 50+ 被拒绝 |
| 所有端点均有认证 | 无未经认证的 LLM 访问 | `curl /v1/chat` 无 token 返回 401 |
| CORS 受限 | 仅允许生产域名 | `Origin: evil.com` 请求被拒绝 |
| 最大输入 token | 超过限制的请求被拒绝 | 发送 50K token 输入——返回 413 或截断 |

## 2. 可靠性（第一周生存）

这些防止你的第一次值班事故。

| 检查项 | 通过标准 | 如何验证 |
|-------|--------------|---------------|
| 带退避的重试 | 5xx 时重试 3 次，指数延迟 | 请求中途杀死 LLM mock——日志中可见重试 |
| 回退模型链 | 链中有 2+ 个模型 | 主要模型不可用——响应仍然从回退返回 |
| 请求超时 | 所有外部调用最多 30s | 慢 LLM mock（60s）——请求在 30s 超时 |
| 优雅降级 | 缓存/RAG 失败不使服务崩溃 | 停止缓存——请求仍然成功（更慢、更贵） |
| 健康检查端点 | 返回依赖状态 | `GET /health` 返回 `{"status": "healthy", "cache": ..., "llm": ...}` |
| 流式传输正常工作 | 首 token 在 500ms 内 | 首 token 时间测量，持续 < 500ms |
| 错误消息安全 | 内部错误从不泄露给用户 | 强制 500——用户看到通用错误，不是堆栈跟踪 |

## 3. 成本控制（第一个月经济）

这些防止 $50K 的意外账单。

| 检查项 | 通过标准 | 如何验证 |
|-------|--------------|---------------|
| 每请求成本跟踪 | 每个请求记录 token 数 + 美元成本 | 请求日志有 `input_tokens`、`output_tokens`、`cost_usd` 字段 |
| 语义缓存启用 | 重复模式 > 20% 命中率 | 1000 个测试请求后缓存统计显示命中率 |
| 缓存 TTL 配置 | 条目过期（默认：1 小时） | 条目插入——TTL 后不再返回 |
| 每用户成本跟踪 | 按 user_id 聚合成本 | 仪表盘/API 显示按成本排序的前 10 用户 |
| 成本告警 | 每日预算 80% 时告警 | 设置 $10 日预算，发送 $8.50 的请求——告警触发 |
| 按成本模型路由 | 低复杂度查询使用更便宜的模型 | 简单问题路由到 gpt-4o-mini，复杂到 gpt-4o |
| 设置最大输出 token | 按模板限制响应 | 模板 max_output_tokens=512——响应从不超出 |

**成本估算公式：**
```
月 LLM 成本 = DAU x queries_per_user x 30 x (1 - cache_hit_rate) x (avg_input_tokens x input_price + avg_output_tokens x output_price) / 1,000,000
```

**按规模的基准阈值：**

| DAU | 目标成本/请求 | 月度预算 |
|-----|-------------------|----------------|
| 1K | < $0.005 | < $750 |
| 10K | < $0.003 | < $4,500 |
| 100K | < $0.001 | < $15,000 |

## 4. 可观测性（在生产中调试）

看不到就无法修复。

| 检查项 | 通过标准 | 如何验证 |
|-------|--------------|---------------|
| 结构化 JSON 日志 | 每个请求产生一行 JSON 日志 | 日志包含：request_id、user_id、model、tokens、latency_ms、cost |
| 请求追踪 | 带组件计时的端到端追踪 | 单个请求显示：护栏（5ms）+ 缓存（2ms）+ llm（3200ms）+ 评估（1ms） |
| 延迟跟踪 | 测量 P50、P95、P99 | 1000 个请求后：P50 < 2s，P99 < 10s |
| 错误率监控 | 错误被计数和分类 | 仪表盘显示：0.5% API 错误、0.1% 护栏阻止、0.01% 超时 |
| 缓存指标 | 命中率、未命中率、条目数可见 | `GET /v1/cache/stats` 返回当前数据 |
| A/B 测试指标 | 每变体质量指标记录 | 每个请求记录 prompt_template + 版本以进行比较 |
| 评估记录 | 每请求记录质量信号 | 响应长度、延迟、模型、模板版本存储用于离线分析 |

## 5. 提示管理

提示就是代码。像对待代码一样对待它们。

| 检查项 | 通过标准 | 如何验证 |
|-------|--------------|---------------|
| 版本化模板 | 每个模板有名称 + 版本字符串 | 模板更改创建新版本，旧版本保留 |
| A/B 测试支持 | 按确定性用户哈希分流流量 | 同一用户始终在实验内看到相同变体 |
| 回滚能力 | < 1 分钟内恢复到先前版本 | 更改实验配置——流量立即切换 |
| 模板验证 | 渲染前验证变量 | 模板中缺少变量引发明确错误，而非 KeyError |
| 系统提示分离 | 系统和用户消息在单独字段中 | 系统提示不拼接进用户消息 |

## 6. 扩展就绪

启动时不需要。扩展到 10 倍时需要。

| 检查项 | 通过标准 | 如何验证 |
|-------|--------------|---------------|
| 异步 LLM 调用 | API 调用不阻塞线程 | 50 个并发请求——服务器 CPU 保持在 < 30% |
| 连接池 | HTTP 连接重用 | 网络跟踪显示与 LLM 提供者的持久连接 |
| 水平扩展 | 无状态服务器设计 | 负载均衡器后的 2 个实例——所有请求成功 |
| 队列支持 | 非实时任务进入队列 | 摘要请求返回 job_id，结果通过轮询可用 |
| 负载测试 | 100 个并发用户，< 5% 错误率 | `wrk` 或 `locust` 测试在目标并发下通过 |

## 新项目的实施顺序

1. **第 1 天：** API 服务器 + 提示模板 + 带重试的单一 LLM 调用
2. **第 2 天：** 输入护栏 + 输出护栏 + 错误处理
3. **第 3 天：** 语义缓存 + 每请求成本跟踪
4. **第 4 天：** 流式传输（SSE）+ 健康检查端点
5. **第 5 天：** 结构化日志 + 请求追踪 + 评估记录
6. **第 2 周：** A/B 测试 + 提示版本管理 + 回滚
7. **第 3 周：** 回退模型链 + 优雅降级
8. **第 4 周：** 负载测试 + 异步优化 + 水平扩展

## 快速诊断

如果生产中出现问题，按此顺序检查：

1. **用户抱怨错误？** 检查健康端点，然后检查日志中的错误率，然后检查 LLM 提供者状态页面
2. **响应慢？** 检查 P99 延迟，然后检查缓存命中率，然后检查追踪中的 LLM 响应时间
3. **成本激增？** 检查每请求成本趋势，然后检查缓存命中率，然后检查按成本排序的 top 用户，然后查找增加 token 数的提示模板更改
4. **质量下降？** 检查是否部署了新提示版本，检查 RAG 检索准确率是否改变，检查模型提供者是否更改了默认模型版本
5. **安全事件？** 检查护栏阻止率（突然下降 = 护栏被禁用），检查请求日志中是否有异常模式，立即轮换 API 密钥
