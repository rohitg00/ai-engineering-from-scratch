# 奖励模型设计师

在构建 RLHF 流水线以使语言模型与目标行为（有用性、编程能力、安全性、诚实性）对齐时，使用此框架设计数据收集协议、训练奖励模型和配置 PPO。

## 输入要求

提供：
- **目标行为**（例如"有用且无害的助手"、"Python 编程专家"、"带安全措施的医疗问答"）
- **基础模型**（例如 SFT 后的 Llama 3 8B、Mistral 7B Chat）
- **奖励模型大小**（通常与策略模型相同或更大）
- **标注预算**（可用人工小时或比较对）
- **计算预算**（奖励模型训练 + PPO 的 GPU 小时数）

## 第 1 步：偏好数据收集

### 标注协议

1. **提示选择**：从 SFT 训练分布中采样，加上分布外提示（10-20% 新颖）
2. **响应生成**：使用 SFT 模型，以不同温度（0.3、0.7、1.0）为每个提示生成 2-4 个响应
3. **比较格式**：向标注员展示恰好 2 个响应，询问"哪个响应更好？"
4. **标准细则**：为您的用例定义"更好"的含义

### 细则模板

| 标准 | 权重 | 描述 |
|-----------|--------|-------------|
| 有用性 | 40% | 是否完整且正确地回答了问题？ |
| 无害性 | 25% | 是否避免有害、有偏见或误导性内容？ |
| 诚实性 | 20% | 是否承认不确定性而非产生幻觉？ |
| 简洁性 | 15% | 响应长度是否适合问题？ |

根据用例调整权重。编程助手可能将正确性权重设为 60%、简洁性设为 20%。

### 数据规模指南

| 规模 | 比较对 | 标注工时 | 预期 RM 准确率 |
|-------|-----------------|-----------------|---------------------|
| 最小可行 | 5,000-10,000 | 400-800 | 60-65% |
| 生产 v1 | 20,000-50,000 | 1,600-4,000 | 65-72% |
| 生产 v2 | 100,000-500,000 | 8,000-40,000 | 72-78% |

InstructGPT 使用了来自 40 名承包商的 33,000 个比较对。Anthropic 的初始论文使用了来自 20 名标注员的 22,000 个比较对。标注员间一致率通常为 70-75%——奖励模型无法超越人类一致水平。

### 质量控制

- **一致率过滤**：丢弃少于 70% 标注员同意的比较对
- **标注员校准**：在实际标注前使用已知正确的比较对进行校准轮次
- **偏差检测**：监控标注员是否一致偏好更长的响应、正式语言或特定模式
- **对抗性示例**：包含 5-10% 旨在捕捉未认真阅读的标注员的示例

## 第 2 步：奖励模型架构

### 架构决策

| 决策 | 推荐 | 理由 |
|----------|---------------|-----------|
| 基础架构 | 与策略相同的 transformer | 从 SFT 检查点初始化权重提供强大的起始特征 |
| 输出头 | 从最后隐藏状态的单线性投影 | 从最完整位置表示中获取标量奖励 |
| 模型大小 | >= 策略模型大小 | 较小的 RM 产生不可靠的信号，使 PPO 不稳定 |
| 初始化 | 带新输出头的 SFT 检查点 | 预训练特征已捕捉语言质量 |

### 训练配置

| 参数 | 范围 | 备注 |
|-----------|-------|-------|
| 学习率 | 1e-5 到 5e-5 | 低于 SFT，因为任务更简单 |
| 轮次 | 1-3 | 过拟合是有限比较数据下的主要风险 |
| 批处理大小 | 64-256 | 每个"示例"是一个对，所以有效数据为 2 倍 |
| 损失函数 | Bradley-Terry：-log(sigmoid(r_preferred - r_rejected)) | 成对比较的标准 |
| 验证集划分 | 10-20% | 监控在保留对上的准确率 |

### 评估指标

1. **成对准确率**：RM 正确排序的保留偏好对比例？目标：> 65%
2. **边际分布**：绘制 (r_preferred - r_rejected) 的分布。应围绕高于 0 居中，有少量负值。
3. **校准**：sigmoid(r_preferred - r_rejected) 是否接近实际的人类偏好概率？
4. **OOD 泛化**：在与训练集不同的提示分布上测试。准确率下降应 < 10%。

## 第 3 步：PPO 配置

### 超参数

| 参数 | 典型值 | 过高影响 | 过低影响 |
|-----------|--------------|-------------------------|------------------------|
| KL 系数（beta） | 0.01-0.05 | 模型几乎不学习，离 SFT 太近 | 奖励黑客攻击，输出退化 |
| 学习率 | 5e-6 到 3e-5 | 训练不稳定，发散 | 收敛慢，浪费计算 |
| 裁剪比（epsilon） | 0.1-0.3 | 大幅更新可能不稳定 | 非常保守的更新，学习慢 |
| 每批 PPO 轮数 | 1-4 | 过拟合当前批次 | 未充分利用每批 |
| 生成批处理大小 | 128-512 | 内存问题 | 梯度估计有噪声 |
| 最大响应长度 | 256-1024 | 生成慢，内存问题 | 截断有用的响应 |

### 监控仪表盘

PPO 训练期间跟踪这些指标：

1. **平均奖励**：应在训练期间增加。平台期可接受；下降意味着不稳定。
2. **KL 散度**：应保持在 10-20 nats 以下。剧增 = 奖励黑客攻击。
3. **响应长度**：应保持稳定。单调增加 = 冗长奖励黑客攻击。
4. **熵**：token 分布熵应缓慢下降。快速下降 = 模式崩溃。
5. **奖励模型一致率**：用奖励模型评分 PPO 响应；一致率应改善。

### PPO 期间的警告信号

| 症状 | 可能原因 | 修复 |
|---------|-------------|-----|
| 奖励增加但输出退化 | 奖励黑客攻击 | 增加 KL 系数，在对抗性示例上重新训练 RM |
| KL 散度爆炸 | 学习率过高或 KL 系数过低 | 降低 lr，增加 beta |
| 响应长度单调增长 | RM 奖励冗长 | 在奖励中添加长度惩罚，使用长度控制对重新训练 RM |
| 所有响应变得相同 | 模式崩溃 | 增加生成温度，减少 PPO 轮次 |
| 奖励剧烈振荡 | PPO 不稳定 | 降低学习率，增加裁剪比 |

## 第 4 步：端到端验证

在部署 RLHF 训练模型之前：

1. **A/B 测试 vs SFT**：在 200+ 个测试提示上运行 SFT 和 RLHF 模型。让 3+ 名评估员比较响应。RLHF 模型应赢得 > 60% 的时间。
2. **安全评估**：在已知对抗性提示（越狱、有害请求）上测试。RLHF 模型应适当拒绝。
3. **回归检查**：运行标准基准（MMLU、HumanEval、MT-Bench）以确认 RLHF 模型未失去核心能力。
4. **遗忘检查**：测量通用文本语料库上的困惑度。相比 SFT 模型增加应 < 10%。
5. **长度分析**：比较 SFT 和 RLHF 模型的平均响应长度。如果 RLHF 长 > 50%，奖励模型可能具有冗长偏差。
