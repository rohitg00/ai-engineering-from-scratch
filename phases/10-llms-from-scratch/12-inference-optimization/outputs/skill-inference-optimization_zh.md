# LLM 推理优化模式

两个阶段：预填充（计算受限，并行）和解码（内存受限，顺序）。
每次优化针对其中一个或两个。

```
请求 -> 预填充（处理提示） -> 解码（生成 token） -> 响应
             |                            |
        计算受限                   内存受限
        优化：融合、              优化：批处理、
        前缀缓存                  量化、投机
```

## 决策框架

### 第 1 步：识别瓶颈

测量工作负载的操作:字节比：

| 操作:字节 | 瓶颈 | 优化方向 |
|----------|-------|-----------------|
| < 50 | 内存 | 量化 KV 缓存，增加批处理大小 |
| 50-200 | 过渡区 | 两者都重要，从批处理开始 |
| > 200 | 计算 | 内核融合、张量并行、FP8 |

### 第 2 步：选择引擎

- **默认**：vLLM（最广泛的模型支持、PagedAttention、OpenAI 兼容 API）
- **多轮 / 结构化输出**：SGLang（RadixAttention 前缀缓存、约束解码）
- **最大 NVIDIA 吞吐量**：TensorRT-LLM（内核融合、H100 上的 FP8）

### 第 3 步：按顺序应用优化

1. **KV 缓存**——始终开启，无负面影响
2. **连续批处理**——始终开启，无负面影响（vLLM/SGLang 默认执行）
3. **前缀缓存**——如果有共享系统提示则启用（大多数聊天机器人有）
4. **量化**——KV 缓存 INT8/FP8 以最小质量损失减少内存 2-4 倍
5. **投机解码**——当延迟比吞吐量更重要时添加
6. **张量并行**——当模型无法放上一个 GPU 时跨 GPU 分割

## KV 缓存内存公式

```
每 token = 2 * num_layers * num_kv_heads * head_dim * bytes_per_param
总计 = 每 token * 序列长度 * 并发用户数
```

常见模型的快速参考（BF16）：

| 模型 | 每 token | 100 用户 @ 4K |
|-------|-----------|----------------|
| Llama 3 8B | 32 KB | 12.5 GB |
| Llama 3 70B | 320 KB | 125 GB |
| Llama 3 405B | 504 KB | 197 GB |

## 投机解码检查清单

- 草稿模型应比目标小 5-10 倍（例如 8B 草稿用于 70B）
- 接受率 > 70% 才能有意义地加速
- 在可预测文本上最佳（代码、结构化输出、自然语言）
- 在创意/采样密集型任务上最差（低温度有帮助）
- EAGLE > 草稿-目标 > n-gram 适用于大多数工作负载

## 常见错误

- 在 batch=1 时运行解码（内存受限，GPU 计算 95% 空闲）
- 分配连续的 KV 缓存块（使用 PagedAttention，接近零浪费）
- 当 80% 的请求共享相同系统提示时忽略前缀缓存
- 为模型权重过度分配 GPU 内存，没给 KV 缓存留空间
- 测量吞吐量时不测量延迟（10 秒 TTFT 的高吞吐量无意义）
- 在高温度下使用投机解码（接受率降至 50% 以下）

## 监控检查清单

- 首 token 时间（TTFT）：预填充延迟，交互式使用目标 < 500ms
- token 间延迟（ITL）：解码速度，流式传输目标 < 50ms
- 吞吐量（tokens/秒）：所有并发用户的总和
- KV 缓存利用率：已分配缓存的使用百分比
- 批次利用率：每次迭代填充的批次槽位百分比
- 队列深度：等待批次槽位的请求数
