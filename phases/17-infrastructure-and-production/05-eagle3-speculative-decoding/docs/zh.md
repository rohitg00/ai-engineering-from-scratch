# 生產環境中的 EAGLE-3 推測解碼

> 推測解碼把一個快速的草稿模型與目標模型配起來。草稿提出 K 個詞元；目標模型在一次前向裡驗證；被接受的詞元等於免費。2026 年 EAGLE-3 是那個生產級的變體 —— 它把草稿頭訓練在目標模型的隱藏狀態上，而不是原始詞元上，把接受率 alpha 推進到一般聊天上的 0.6-0.8 區間。該問的問題不是「這個草稿有多快」，而是「在我的流量上 alpha 是多少？」若 alpha 掉到約 0.55 以下，在高併發下推測解碼就是淨負面的，因為每一次被拒絕的草稿都要付出第二次目標前向。這一課教你先量 alpha、再翻那個旗標。

**類型：** 學習
**程式語言：** Python (stdlib, toy acceptance-rate simulator)
**先修單元：** 階段 17 · 04（服務引擎內部）、階段 10 · 18（多詞元預測）
**時間：** 約 60 分鐘

## 學習目標

- 說出推測解碼的三個世代，並解釋 EAGLE-3 相對於 EAGLE-2 與經典草稿模型改變了什麼。
- 定義接受率 alpha、由 alpha 與 K（草稿長度）算出預期加速，並找出你目標併發下的損益平衡 alpha。
- 解釋為何在 2026 年的 vLLM 中推測解碼是選擇加入（不是預設），以及為何沒量 alpha 就打開它是一種生產反模式。
- 寫一份量測計畫：用哪個基準、哪種提示詞分布、哪個併發點、以哪個指標把關。

## 問題所在

解碼是記憶體受限的。在一張跑 Llama 3.3 70B FP8 的 H100 上，每解出一個詞元就要讀約 140 GB/s 的權重，然後吐出一個詞元。解碼期間 GPU 的運算幾乎閒著 —— 瓶頸是 HBM 頻寬，不是矩陣乘法的吞吐量。

推測解碼利用那個落差。用一個便宜的草稿模型產出 K 個候選詞元，然後要目標模型在一次前向裡把 K 個全部驗證掉。每個被驗證的詞元實際上是免費的（攤進一次「K 個一批」的前向裡，而那次前向目標模型本來就得做）。

經典的草稿模型做法，是用同家族的較小模型（用 Llama 3.2 1B 替 Llama 3.3 70B 起草）。它行得通，但接受率平庸 —— 較小模型的分布會偏離目標。EAGLE、接著 EAGLE-2、再接著 EAGLE-3，把一個輕量草稿頭直接訓練在目標模型的內部狀態上，於是草稿的分布緊追目標得多。這就是為什麼 alpha 從草稿模型的 0.4 提升到 EAGLE-3 的 0.6-0.8。

陷阱是：EAGLE-3 在 2026 年的 vLLM 中是選擇加入的。`speculative_config` 必須明確設定。沒有旗標，就沒有加速。那些沒在自己真實流量上量 alpha 就打開它的團隊，常常看到尾端延遲變糟，而不是變好。

## 核心概念

### 推測解碼實際上買到了什麼

沒有推測解碼時，每個詞元的成本是一次目標前向。在草稿長度 K 與接受率 alpha 之下，每次目標前向的預期詞元數是 `1 + K * alpha`。加速比是 `(1 + K * alpha) / (1 + epsilon)`，其中 epsilon 是草稿加驗證的開銷。以 K=5、alpha=0.7 來算：`(1 + 5*0.7) / (1 + 0.1) = 4.5 / 1.1 = 4.1 倍`。真實世界的數字群聚在 2-3 倍，因為在生產流量上 alpha 很少那麼高，而 epsilon 又會隨批次變大而增長。

### 為什麼 alpha 是唯一要緊的指標

被拒絕的詞元不會憑空消失 —— 它們會逼出第二次目標前向去產出那第一個被拒絕的詞元。在一份 alpha 掉到 0.4 的工作負載上，你付的是草稿開銷加驗證加重擲。在高併發下（例如 256 併發），解碼批次本身已經夠大，「純目標」與「目標帶驗證」之間的記憶體頻寬落差就縮小了。在 2026 年多數硬體上，alpha 低於 0.55 時推測解碼就是淨負面的。

Alpha 隨工作負載而變。在 ShareGPT 式的一般聊天上，用 ShareGPT 訓練的 EAGLE-3 可以打到 0.6-0.8。在領域專屬的流量上（程式碼、醫療、法律），以一般資料訓練的草稿頭會掉到 0.4-0.6。訓練一個領域專屬的草稿頭可以把 alpha 救回來 —— 相對於微調目標模型，那是一份輕量、很快的訓練工作。

### 一眼看完 EAGLE 的各世代

- **經典草稿模型**：同家族的小模型。Alpha 0.3-0.5。基礎設施簡單 —— 載入兩個模型，每次目標前向前草稿跑 K 次前向。
- **EAGLE-1（2024）**：一個訓練在目標隱藏狀態（最後一層）上的草稿頭。Alpha 約 0.5-0.6。在目標之上多一點點參數開銷。
- **EAGLE-2（2025）**：自適應草稿長度與樹狀草稿（一次目標前向驗證多條分支）。Alpha 約 0.6-0.7。草稿排程器更複雜。
- **EAGLE-3（2025-2026）**：草稿頭訓練在目標的多個層上（不只最後一層），對齊更好。一般聊天上 Alpha 約 0.6-0.8。

### 2026 年的生產配方

1. 先出貨純目標模型。在目標併發下量測基線 TTFT、ITL、吞吐量。
2. 透過 vLLM 的 `speculative_config` 啟用 EAGLE-3 草稿。重跑那份基準。
3. 記錄接受率 alpha。vLLM V1 把它回報成 `spec_decode_metrics.accepted_tokens_per_request`。除以要求的草稿長度就得到 alpha。
4. 若在生產流量分布上 alpha < 0.55，就停用推測解碼，或訓練一個領域專屬的 EAGLE-3 草稿。
5. 在生產併發下重跑。確認 P99 ITL 沒有變糟。

### 那個生產陷阱：P99 尾端

平均 ITL 會因推測解碼而下降。若你不調校，P99 可能變糟。被拒絕的草稿會觸發一次兩趟的序列（草稿 + 驗證失敗 + 重擲）。在滿批次之下，那兩趟會串行化。要盯 P99 ITL，不是 P50。

### EAGLE-3 已經被部署在哪裡

Google 在 2025 年把推測解碼部署進 AI Overviews（品質相同、回應更快）。vLLM V1 以 `speculative_config` 作為有文件的介面出貨，而它的功能矩陣把推測解碼標為與分塊預填相容。SGLang 支援 EAGLE-3，並把它當成前綴吃重工作負載的建議草稿路徑。

### 一行的損益平衡數學

預期加速：`S(alpha, K) = (1 + K*alpha) / (1 + verify_overhead)`。令 `S = 1` 可解出 alpha：`alpha_breakeven = verify_overhead / K`。以典型的 verify_overhead 約 0.15 與 K=5 來算：`alpha_breakeven = 0.03`。但那是原始的解碼數學。在高併發下，驗證開銷上升，而解碼批次本身已經把記憶體讀取攤到各序列上了，所以實務上有效的 alpha_breakeven 會爬到約 0.45-0.55。

### 什麼時候不要用推測解碼

- 延遲不重要的批次 1 離線生成。用純目標模型。
- 非常短的輸出（50 個詞元以下）。草稿開銷與驗證成本會主導。
- 沒有領域訓練草稿頭的特化領域。Alpha 太低。
- 假設每一對功能都能組合。對照你所用版本的 vLLM 相容性矩陣：v0.18.0 把推測解碼標為與分塊預填相容。

## 框架應用

`code/main.py` 在一系列 alpha 值與草稿長度 K 上，模擬有與沒有推測解碼的解碼迴圈。它會印出損益平衡 alpha、量到的加速，以及尾端行為。用好幾組 (alpha, K) 跑它，看推測解碼確切在哪裡就不再划算。

## 練習

1. 跑 `code/main.py`。在 K=5 時，你需要多少 alpha 才有 2 倍加速？3 倍呢？那對 verify_overhead 有多敏感？
2. 想像生產流量是 70% 一般聊天、30% 程式碼。一般聊天在 ShareGPT 訓練的 EAGLE-3 上打到 alpha 0.7；程式碼打到 0.4。混合後的 alpha 是多少，推測解碼是淨正面的嗎？
3. 讀 vLLM 的 `speculative_config` 文件。說出那三種模式（草稿模型、EAGLE、N-gram），並檢查在你的 vLLM 版本中，每一種能與哪些功能組合。
4. 你看到啟用 EAGLE-3 後平均 ITL 掉了 25%，但 P99 ITL 上升 15%。診斷並提出一項緩解。
5. 算出 Llama 3.3 70B 的 EAGLE-3 草稿頭的記憶體成本。它跟拿 Llama 3.2 1B 當經典草稿相比如何？

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 推測解碼 | 「草稿加驗證」 | 用便宜模型提出 K 個詞元，在一次目標前向裡驗證全部 K 個 |
| 接受率 alpha | 「推測接受率」 | 被目標接受的草稿詞元比例；唯一要緊的指標 |
| 草稿長度 K | 「spec k」 | 每次目標前向草稿提出幾個詞元；典型 4-8 |
| 驗證開銷 epsilon | 「推測開銷」 | 相對純目標前向，驗證與重擲多出來的成本；隨批次增長 |
| EAGLE-3 | 「最新的 EAGLE」 | 2025-2026 的變體；草稿頭訓練在目標的多個層上；一般聊天 alpha 0.6-0.8 |
| `speculative_config` | 「vLLM 的推測設定」 | vLLM V1 中那個明確的選擇加入；沒有預設就代表沒有加速 |
| N-gram 推測解碼 | 「N-gram 草稿」 | 用提示詞中的 N-gram 查找在 GPU 側起草；與分塊預填相容 |
| 損益平衡 alpha | 「不賺不賠的 alpha」 | 推測解碼加速為零的那個 alpha；在生產併發下要盯著它 |
| 草稿被拒的兩趟 | 「重擲成本」 | 草稿被拒時的兩次目標前向；它驅動 P99 尾端 |
