# LLM 的 FinOps — 单位经济模型与多租户归因

> 传统 FinOps 在 LLM 支出上失效了。成本是 Token 交易，而非资源运行时长。标签无法映射——API 调用是一次交易，而非一项资产。工程决策（提示词设计、上下文窗口、输出长度）就是财务决策。2026 年的最佳实践有三个归因维度需要从第一天就开始埋点：按用户（`user_id`）用于席位定价和扩展，按任务（`task_id` + `route`）用于产品面成本与优先级排序，按租户（`tenant_id`）用于单位经济模型和续约。四个 Token 层——提示词、工具调用、记忆、响应——一个桶会掩盖真实支出。多租户产品的执行阶梯：按租户限速（2-3 倍预期峰值，明确的 429 + Retry-After）；每日消费上限（1.5-3 倍合同上限；触发限速收紧 + 告警）；消费 Z 分数 > 4 时的终止开关（自动暂停 + 呼叫值班人员）。归因模式：标签聚合、遥测关联（Trace-ID → 账单；精度最高）、采样外推、基于模型的分配、事件溯源、实时流式处理。单位指标：每次解决查询的成本、每个生成产物的成本——而不是 $/M Token。追溯式标签总会遗漏；应在请求创建时就埋点。

**类型：** 学习
**语言：** Python（标准库，带终止开关的玩具级成本归因模拟器）
**前置要求：** 阶段 17 · 13（可观测性），阶段 17 · 14（缓存）
**时长：** 约 60 分钟

## 学习目标

- 解释为什么传统 FinOps（标签 + 层级）在 LLM 支出上失效，并说出三个新的归因维度。
- 列举四个 Token 层（提示词、工具调用、记忆、响应），以及为什么单桶计费会掩盖成本。
- 为多租户产品设计执行阶梯（限速 → 消费上限 → 终止开关）。
- 选择单位指标（每次解决查询 / 每次产物的成本）而非 $/M Token。

## 问题

你的账单显示 $40,000，但你不知道：
- 是哪个租户花的。
- 是哪个产品功能驱动的。
- 是否有某个用户存在滥用行为。
- 是提示词膨胀、工具调用还是记忆放大导致的。

在云资源（EC2、S3）上，供应商侧的标签聚合是有效的，因为标签可以传播到账单明细项。但 LLM API 调用不会自动打标签——你必须在调用处标记 user/task/tenant，并一直携带到账单。追溯式归因总会遗漏边界情况。

## 概念

### 三个归因维度

**按用户**（`user_id`）：谁花了多少钱。驱动席位定价、扩展对话，识别高频用户。

**按任务**（`task_id` + `route`）：哪个产品面的成本是多少。驱动功能优先级排序、关闭高成本功能等决策。

**按租户**（`tenant_id`）：哪个客户是盈利的。驱动单位经济模型、续约定价、服务层级阈值。

从第一天起就在调用处埋点这三个维度。追溯式永远更差。

### 四个 Token 层

| 层 | 示例 | 占总量的典型比例 |
|-------|---------|---------------------|
| 提示词（Prompt） | 系统提示 + 用户输入 | 40-60% |
| 工具调用（Tool） | 工具调用结果回填 | 20-40%（Agent 工作负载） |
| 记忆（Memory） | 历史对话 / 检索文档 | 10-30% |
| 响应（Response） | 模型输出 | 10-30% |

将四层混在一起会让优化变得盲目。在你的归因模式中将其分开。

### 执行阶梯

1. **按租户限速**。2-3 倍预期峰值。返回 429 并附带 `Retry-After`。租户会感知到限制，不会出现意外账单。

2. **按租户设置每日消费上限**。1.5-3 倍合同上限。触发：收紧限速 + 通知客户成功团队。

3. **消费 Z 分数 > 4 时的终止开关**（相对于该租户的基线）。自动暂停租户；呼叫值班人员；升级到运维和客户成功团队。

### 归因模式

- **标签聚合**：在元数据头中打标签；后续聚合。简单但粗略。
- **遥测关联**：通过 Trace ID 将追踪链路关联到账单。精度最高。成熟团队的做法。
- **采样外推**：采样 5-10%，乘以倍数。适合粗略支出估算的成本效益方案；会遗漏尾部数据。
- **基于模型的分配**：通过回归推断成本驱动因素。适用于没有标签的遗留数据。
- **事件溯源**：将成本作为流中的事件（Kafka / Kinesis）。实时处理。
- **实时流式处理**：仪表盘亚秒级更新。

### 每次 X 的成本是单位指标

$/M Token 是供应商的术语。产品指标应是：

- 每次解决的支持工单的成本。
- 每次生成的文章的成本。
- 每次成功的 Agent 任务的成本。
- 每次用户会话分钟的成本。

将成本与产品产出绑定。否则优化就没有锚点。

### 成本归因追踪链路示例

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用都发送。存储在数据湖中。按维度聚合。阶段 17 · 13 的可观测性栈是存放这些数据的地方。

### 复合节省堆栈

堆栈：缓存 + 批处理 + 路由 + 网关。四层全部启用：
- 缓存 L2（阶段 17 · 14）：输入成本约降低 10 倍。
- 批处理（阶段 17 · 15）：节省 50%。
- 路由到廉价模型（阶段 17 · 16）：成本降低 60%。
- 网关效率（阶段 17 · 19）：冗余 + 重试。

最佳情况叠加：约为原始基线的 5-10%。大多数团队启用了 2-3 个杠杆，很少有团队全部四个都启用。

### 你应该记住的数字

- 归因维度：按用户、按任务、按租户。
- 四个 Token 层：提示词、工具调用、记忆、响应。
- 终止开关：消费 Z 分数 > 4。
- 单位指标：每次解决查询的成本，而非 $/M Token。
- 叠加优化：可降至基线的约 5-10%。

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------------|------------------------|
| 按用户归因 | "用户级成本" | 每次调用都打上 `user_id` 标签 |
| 按任务归因 | "功能成本" | `task_id` + `route` 标识产品面 |
| 按租户归因 | "客户成本" | `tenant_id`；驱动单位经济模型 |
| 四个 Token 层 | "成本层级" | 提示词 + 工具调用 + 记忆 + 响应 |
| 限速 | "429 防护" | 在网关层面执行的按租户上限 |
| 每日消费上限 | "每日天花板" | 租户级别的预算和告警 |
| 终止开关 | "自动暂停" | 消费 Z 分数 > 4 触发自动暂停 |
| 每次解决的成本 | "产品单位指标" | 成本与产品产出挂钩，而非 Token |
| 遥测关联 | "Trace 到账单" | 精度最高的归因模式 |
| 叠加优化 | "缓存 + 批处理 + 路由 + 网关" | 复合节省至基线的约 5-10% |
