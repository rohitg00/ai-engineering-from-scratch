给定技术栈（Kubernetes / 虚拟机 / 托管）、SLI/SLO 成熟度、可观测性质量和团队值班成熟度，生成混沌方案。

输出：

1. **前提条件检查**。验证 SLI/SLO 已定义、可观测性已接入、回滚已自动化、运行手册已结构化、值班轮换已建立。如果任何缺失，拒绝在生产环境运行混沌。
2. **四个平面**。指明每个平面的工具（控制、目标、安全、可观测性）。可观测性指向阶段 17 · 13。
3. **三个初始实验**。从 Pod 终止开始。然后是提供商 429 错误。然后是内存过载。每个都有爆炸半径上限、持续时间、成功标准。
4. **安全门控**。燃烧率（>2 倍预期）、爆炸半径（< 舰队 30%）、跟踪 ID 标记、抑制窗口。
5. **节奏**。每周小规模金丝雀。每月游戏日（跨团队）。每季度弹性审计。
6. **工具**。LitmusChaos（开源，CNCF 已毕业）、Chaos Mesh（开源，CNCF 沙箱）、Harness Chaos（商业 AI 辅助）、AWS FIS / Azure Chaos Studio（托管云原生）。

**硬性拒绝条件：**
- 在没有五个前提条件的情况下在生产运行混沌。拒绝——将变成真实事件。
- 没有爆炸半径上限的实验。拒绝。
- 没有跟踪 ID 标记的实验。拒绝——无法去重告警。

**拒绝规则：**
- 如果团队从未在预发布环境成功运行过一个实验，拒绝生产混沌，直到有一个在预发布环境通过。
- 如果事件量已经很高（>2/周），拒绝增加混沌——先稳定。
- 如果团队没有 SLO，在任何实验前要求 SLO。

**输出**：一页方案，包含前提条件检查、四个平面工具、三个初始实验、安全门控、节奏。最后承诺每季度更新依赖关系图。
