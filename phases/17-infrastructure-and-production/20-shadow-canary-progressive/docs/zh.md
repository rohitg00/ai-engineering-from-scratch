# LLM 的流量影子、金丝雀发布与渐进式部署

> LLM 发布集齐了软件部署中最棘手的部分：没有单元测试、故障模式弥散、信号延迟。部署顺序为：（1）**影子模式** — 将生产请求复制一份发给候选模型，记录日志、对比结果，零用户影响；能捕获明显的分布问题，但不是质量保证；（2）**金丝雀发布** — 渐进式流量切换 10% → 25% → 50% → 75% → 100%，每一步设置门禁；跟踪延迟百分位、每次请求成本、错误/拒绝率、输出长度分布、用户反馈率；（3）**A/B 测试** — 在稳定性确认后，对有明显差异的备选方案进行对比。非确定性不可化简 — 由于 GPU 浮点数非结合性以及批次大小的差异，相同输入的多次运行间准确率波动最高可达 15%。成本是一个变量而非常量 — 一个效果好 20% 的模型，每次调用成本可能高出 3 倍。回滚速度是关键：如果回滚需要重新部署，你就太慢了。策略存在于配置/开关中；模型存在于注册表中，附带固定的摘要哈希；回滚 = 切换策略 + 恢复阈值 + 锁定旧模型，几秒内完成。

**类型：** 学习
**语言：** Python（标准库，玩具版金丝雀进度模拟器）
**前置知识：** 阶段 17 · 13（可观测性），阶段 17 · 21（A/B 测试）
**时长：** 约 60 分钟

## 学习目标

- 区分影子模式（零影响对比）、金丝雀发布（线上流量渐进式）和 A/B 测试（确认稳定性后的对比）。
- 列举五个 LLM 特有的金丝雀指标（延迟、每次请求成本、错误/拒绝率、输出长度分布、用户反馈）。
- 解释 LLM 非确定性（最高 15%）如何改变发布中"稳定"的含义。
- 设计一条以秒计（策略切换）而非以小时计（重新部署）的回滚路径。

## 问题

你发布了一个新模型。离线评估显示准确率提升了 3%。你在生产环境打开了它。24 小时内，成本上升了 40%，用户点踩率上升了 8%，三个客户工单反馈"回答很奇怪"。你回滚了。重新部署花了 3 小时。你的周末泡汤了。

每一步都是可以避免的。影子模式会在任何用户看到之前就捕获 40% 的成本飙升。金丝雀会在点踩率变化时停在 10%。策略开关回滚只需 30 秒。这套纪律填补了"离线评估看起来不错"和"真实用户满意"之间的鸿沟。

## 概念

### 影子模式

候选模型接收与生产模型相同的请求；输出被记录，但不返回给用户。零用户影响。记录：

- 输出内容（与生产模型的差异对比）。
- Token 数量（成本差异）。
- 延迟。
- 拒绝率和错误率。

能捕获：成本暴涨、长度退化、明显的拒绝率变化、硬错误。不能捕获：用户能感知的质量差异。影子模式是冒烟测试，不是质量测试。

### 金丝雀发布

渐进式流量切换，每步设置门禁。典型进度：1% → 10% → 25% → 50% → 75% → 100%。每一步在 5 个指标上设门禁：

1. **延迟百分位** — P50、P95、P99。触发条件：金丝雀的 P99 超过基线的 1.5 倍。
2. **每次请求成本** — 混合平均。触发条件：高于基线 20% 以上。
3. **错误/拒绝率** — 5xx 加上显式拒绝。触发条件：等于基线的 2 倍。
4. **输出长度分布** — 均值 + P99。触发条件：分布发生偏移。
5. **用户反馈率** — 点踩/工单提交。触发条件：等于基线的 1.5 倍。

### 非确定性是新的方差

相同的输入产生不完全相同的输出。原因：

- GPU 浮点数非结合性（浮点归约顺序因批次而异）。
- 批次大小差异（同一提示在 128 条批次 vs 16 条批次中的表现不同）。
- 采样（温度 > 0）。

实测：在完全相同的评估集上，多次运行间准确率变化最高达 15%。发布中的"稳定"意味着指标在预期的方差范围内，而非与基线完全相同。将门禁设置在噪声水平之上。

### 成本是一个变量

一个效果好 20% 的模型，每次调用成本可能高出 3 倍。每次请求成本是五个门禁之一。发布一个"更好"但却破坏了单位经济模型的模型，属于需要回滚的情况。

### 回滚是利器

- **策略开关**（功能开关系统）：在配置中切换百分比，几秒完成。
- **模型固定**（注册表摘要）：固定的模型不会自动升级。
- **回滚 = 恢复开关 + 设置固定摘要为上一个版本**。以秒计，而非以小时计。

如果你的系统需要重新部署才能回滚，在发布之前先修复这个问题。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进式交付控制器。与 Istio/Linkerd 加权路由集成。

**Istio 加权路由** — 服务网格层面的流量拆分。

**KServe / Seldon Core** — 内置金丝雀能力的模型服务。

**功能开关** — LaunchDarkly、Flagsmith、Unleash。策略级别切换，无需重新部署。

### 指标节奏

金丝雀门禁每 5-15 分钟检查一次，具体取决于流量规模。1% 的流量，每分钟 10 个请求，每个窗口内产生 50-150 个数据点 — 对延迟指标足够，但对用户反馈来说噪声较大。10% 的流量则数据量大约多 10 倍。每个阶段应暂停足够长的时间，以收集充足的样本。

### A/B 测试步骤是可选的

如果新模型有明显差异（行为不同、成本曲线不同、语气不同），在金丝雀通过后在 50% 流量下做 A/B 测试。如果只是改进版本，金丝雀门禁通过后直接切换到 100%。

### 你应该记住的数字

- 金丝雀进度：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性上限：相同输入下多次运行间最高 15% 的方差。
- 五个金丝雀指标：延迟、成本、错误/拒绝率、输出长度、用户反馈。
- 成本门禁：高于基线 20% 以上即触发。
- 回滚：以秒计，而非以小时计。

## 关键术语

| 术语 | 大家常说的 | 实际含义 |
|------|-----------|---------|
| 影子模式 (Shadow mode) | "复制一份给新的" | 零影响发送到候选模型做日志记录 |
| 金丝雀 (Canary) | "渐进式流量" | 逐步面向用户的带门禁发布 |
| 门禁 (Gates) | "发布检查" | 阻止进度的指标阈值 |
| 非确定性 (Non-determinism) | "LLM 方差" | 不可化简的多次运行间差异 |
| 策略开关 (Policy flag) | "开关回滚" | 配置级别的回滚，以秒计而非以小时计 |
| 模型固定 (Model pin) | "注册表摘要" | 指向某个模型版本的不可变引用 |
| Argo Rollouts | "K8s 渐进式" | Kubernetes 原生的金丝雀/回滚控制器 |
| KServe | "推理 K8s" | 带金丝雀原语的模型服务 |
| Istio 加权路由 | "网格拆分" | 服务网格流量分发器 |
