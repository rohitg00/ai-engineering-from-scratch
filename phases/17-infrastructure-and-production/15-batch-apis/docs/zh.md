# 批量 API——50% 折扣成为行业标准

> 各大主流提供商都提供了异步批量 API，享受 50% 折扣，约 24 小时周转。OpenAI、Anthropic、Google 以及大多数推理平台（Fireworks batch tier、Together batch）都实现了相同的模式。将批量与提示缓存叠加，隔夜管道的成本可降至同步无缓存的约 10%。规则极其简单：如果不是交互式的，就应该走批量。内容生成管道、文档分类、数据提取、报告生成、批量标注、目录标记——任何能容忍 24 小时延迟的任务，如果不迁移到批量，就是在浪费钱。2026 年的生产模式是将每个新的 LLM 工作负载分流到三个车道：交互式（带缓存的同步）、半交互式（带降级的异步队列）、批量（隔夜，缓存输入叠加）。那些假装是交互式但能容忍数分钟延迟的工作负载，浪费最大。

**类型：** 学习
**语言：** Python（标准库，玩具级批量 vs 同步成本模拟器）
**前置知识：** 阶段 17 · 14（提示与语义缓存）
**时长：** 约 45 分钟

## 学习目标

- 说出三大提供商的批量 API（OpenAI、Anthropic、Google）以及共同的 50% 折扣 + 24 小时周转保证。
- 计算在隔夜分类工作负载上叠加批量 + 缓存输入的成本，并与同步无缓存基线进行比较。
- 将工作负载分流为交互式 / 半交互式 / 批量，并证明该车道选择的合理性。
- 说出两大陷阱：部分交互性（用户期望快于 24 小时）和输出模式偏移（批量文件格式因提供商而异）。

## 问题

你的团队维护一个夜间报告生成管道。50,000 个文档，每个需要摘要，对摘要进行聚类，起草一份高管简报。同步运行需要 4 小时，每晚花费 2,000 美元。你听说了批量 API。

批量让你享受 50% 折扣。你还对系统提示（所有 50k 次调用共享）启用了提示缓存。叠加后，费用降至每晚 180 美元——约为基线的 9%。同一管道，三个配置变更。

批量是 LLM 成本工具箱中最便宜但没人去动的杠杆。原因主要是组织层面的：当 SLA 实际上是"明早之前"时，团队却想着"实时"。这节课就是关于不要把 90% 的费用白白浪费。

## 概念

### 三大批量 API

**OpenAI Batch API**：上传 JSONL 文件，包含一系列请求。承诺 24 小时周转（实际通常约 2-8 小时）。输入和输出令牌享受 50% 折扣。使用 `/v1/batches` 端点。符合条件的缓存输入还可叠加缓存输入定价。

**Anthropic Message Batches**：JSONL 上传。24 小时周转。50% 折扣。支持 `cache_control`——缓存写入是显式的，读取在批次内自动进行。

**Google Vertex AI Batch Prediction**：BigQuery 或 GCS 输入。Gemini 享受类似的 50% 折扣。与 Vertex 管道集成。

### 语义：异步，而非慢速

批量是"我承诺在 24 小时内返回"——而不是"这需要 24 小时"。典型的 P50 是 2-6 小时。提供商会把你的批次安排在非高峰时段，此时 GPU 资源利用率较低。

### 与缓存叠加

一个 50k 文档摘要任务，使用相同的 4K 令牌系统提示：

- 同步无缓存：50000 ×（$input × 4000 + $output × 200），全价。
- 同步已缓存：系统提示在首次写入后缓存；剩余 49999 次调用输入成本降低 10 倍。
- 批量已缓存：以上所有优势，加上读写均享受 50% 折扣。

叠加效果：批量 + 缓存 ≈ 同步无缓存账单的 10%。任何隔夜运行且共享系统提示的工作负载都应当使用此方案。

### 工作负载分流

**交互式**——用户等待响应。TTFT（首令牌时间）至关重要。使用带提示缓存的同步调用。不能走批量。

**半交互式**——用户提交任务，几分钟后回来看结果。异步队列，如果批量不可用则降级到同步。比如中等规模的 RAG 索引。

**批量**——用户期望"到早上"或"下一小时"得到结果。内容管道、大规模分类、离线分析。始终走批量，始终叠加缓存。

常见错误：因为管道是生产环境，就把所有东西归类为交互式。生产环境不是延迟规格——SLA 才是。

### 部分交互性陷阱

有些功能看起来是交互式的，但实际上能容忍 5-10 分钟。例如：一个带有"刷新"按钮的夜间客户健康报告。用户点击刷新，等 10 分钟完全没问题。团队却把它做成同步。50 个并发刷新的成本是走批量并通过电子邮件交付的 10 倍。

要问的问题是："24 小时对这个用户来说意味着什么？"如果答案是"他们不会注意到"，那就走批量。

### 输出模式陷阱

批量文件格式因提供商而异：

- OpenAI：JSONL，每行一个请求。
- Anthropic：JSONL，每行一条消息；响应格式内嵌。
- Vertex：BigQuery 表或 GCS 前缀，使用 TFRecord。

编写"一个批量客户端"以支持多个提供商，意味着需要为每个提供商编写适配代码。那些宣称支持多提供商批量的网关（Portkey、LiteLLM 的某些层级）仍然只是对原始格式的简单包装。

### 你应该记住的数字

- 各提供商的批量折扣：输入 + 输出统一 50%。
- 周转 SLA：保证 24 小时，典型 P50 为 2-6 小时。
- 批量 + 缓存输入叠加：约为同步无缓存成本的 10%。
- 工作负载分流规则：如果 24 小时延迟可接受，始终走批量。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| Batch API（批量 API） | "异步折扣" | 50% 折扣，24 小时周转 |
| JSONL | "批量格式" | 每行一个 JSON 请求；OpenAI/Anthropic 标准 |
| Message Batches | "Anthropic 批量" | Anthropic 的批量 API 产品名称 |
| Batch prediction（批量预测） | "Vertex 批量" | Vertex AI 的批量 API 产品 |
| Turnaround SLA（周转 SLA） | "24 小时承诺" | 保证值，非典型值；典型值为 2-6 小时 |
| Workload triage（工作负载分流） | "交互性决策" | 交互式 / 半交互式 / 批量路由决策 |
| Output schema（输出模式） | "响应格式" | 按提供商不同的 JSONL 布局；不可移植 |
| Stacked discount（叠加折扣） | "批量 + 缓存" | 两者叠加时约为无缓存同步账单的 10% |
