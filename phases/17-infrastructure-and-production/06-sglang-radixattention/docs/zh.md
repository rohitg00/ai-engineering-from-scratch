# SGLang 与 RadixAttention：面向前缀密集型工作负载

> SGLang 将 KV 缓存视为存储在以基数树（radix tree）中的一等可复用资源。vLLM 按 FCFS（先到先服务）调度请求，而 SGLang 的缓存感知调度器优先处理具有较长共享前缀的请求——本质上是一种深度优先的基数树遍历，让热分支驻留在 HBM 中。在 Llama 3.1 8B 上，使用类似 ShareGPT 的 1K 提示词，SGLang 达到约 16,200 tok/s，vLLM 约 12,500 tok/s，性能优势约 29%。在前缀密集的 RAG 工作负载上，优势可达 6.4 倍。在语音克隆类工作负载上，缓存命中率超过 86%。2026 年已在 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS 等平台的 40 万+ GPU 上部署。需要注意的是，当前缀排序不一致时，6.4 倍的优势就会消失——排序是工程师手中的杠杆。

- 解释缓存感知调度，以及为什么 FCFS 不适用于前缀密集型流量。

- 指出使 6.4 倍加速成为现实而非失去优势的提示词排序规范。

## 问题

经典的服务化方案将每个请求的提示词视为不透明整体。即使 5,000 个 RAG 请求都以相同的 2,000 token 系统提示词和相同的检索前言开头，vLLM 也会对那 2,000 token 的前缀执行 5,000 次预填充。GPU 一遍又一遍地做着相同的工作。

关键在于：在智能体和 RAG 工作负载中，提示词几乎总是共享长前缀。系统提示词、工具模式、少样本示例、检索头、对话历史——这些都在请求之间重复出现。如果你能将该前缀的 KV 缓存存储一次并重复使用，就不需要再次预填充它。

RadixAttention 正是这样做的。Token 被索引到一棵基数树中；每个节点持有从根到该节点路径上 token 序列的 KV 块。新请求遍历这棵树：任何匹配的节点都会重用其 KV 块。预填充成本变得与"新"后缀成正比，而不是整个提示词。

挑战在于调度。如果两个请求共享一个 2,000 token 的前缀，而第三个请求只共享其中 200 个 token，你最希望将两个长共享请求一起服务，使长前缀保留在 HBM 中。FCFS 则相反——它服务最先到达的请求，可能会在下一次长前缀请求到来之前就将热分支逐出。

## 概念

### 作为 KV 索引的基数树

基数树（紧凑字典树）存储 token 序列。每个节点持有一个 token 范围以及为该范围计算出的 KV 块。子节点将序列扩展一个或多个 token。

```
根
 |- "你是一个有用的助手..."  (2,000 token, 124 个 KV 块)
      |- "上下文：<文档 A>..."        (500 token, 31 个块)
           |- "问题：Alice..."    (80 token, 5 个块)
           |- "问题：Bob..."      (95 token, 6 个块)
      |- "上下文：<文档 B>..."        (520 token, 33 个块)
```

一个新请求带来系统提示词 + "上下文：<文档 A>" + "问题：Carol"。调度器遍历：系统前缀匹配（重用 124 个块），文档 A 分支匹配（重用 31 个块），然后仅为"问题：Carol"分配新块（4 个块）。预填充成本：4 个新 token 块。没有这棵树则是 160 个块。预填充节省约 40 倍。

### 缓存感知调度

如果缓存频繁刷新，基于基数树的复用就毫无意义。有两个关键策略：

1. **深度优先调度**。从队列中选择下一个请求时，优先选择与当前运行集合同根分支的请求。这使热分支保持驻留。
2. **分支级 LRU，而非块级 LRU**。逐出整个分支（从使用最少的叶子开始），而不是单个块，使缓存形状与基数树形状匹配。

FCFS 违反了这两个策略。一个共享 2,000 token 的请求排在只共享 50 token 的请求后面，结果 2,000 token 的分支被逐出以容纳那个仅 50 token 的请求。

### 你应该记住的基准数据

- Llama 3.1 8B，H100，ShareGPT 1K 提示词：SGLang ~16,200 tok/s vs vLLM ~12,500（约 29% 优势）。
- 前缀密集的 RAG（相同系统提示词 + 相同文档，问题变化）：SGLang 上最高达 6.4 倍。
- 语音克隆工作负载：86.4% 的前缀缓存命中率。
- SGLang 客户的生产环境命中率：50-99%，取决于提示词规范。
- 2026 年已在 40 万+ GPU 上部署。

### 排序的陷阱

6.4 倍加速建立在一致的提示词模板排序之上。如果你的客户端在某些请求中以 `[system, tools, context, history, question]` 顺序构建提示词，在其他请求中又以 `[system, context, tools, history, question]` 顺序构建，那么基数树就无法找到共享前缀。对人类来说是共享前缀的内容，对基数树来说是两条不同的序列。

工程师的杠杆：你的提示词模板就是缓存键。固定排序。将所有不可变内容（系统提示词、工具、模式）放在最前面。检索上下文放在其次。用户问题放在最后。不要将动态内容穿插到前缀中。

来自研究的真实案例：将动态内容移出可缓存前缀，一次变更就将缓存命中率从 7% 提升到 74%。

### RadixAttention 的优势与不足

优势：
- RAG（相同检索前言，问题变化）。
- 智能体（相同工具模式，查询变化）。
- 带有长系统提示词的聊天。
- 带有重复前言的语音/视觉工作负载。

不足（回退到 vLLM 级别的吞吐量）：
- 具有唯一提示词的单次生成（代码补全、无系统提示词的开放式聊天）。
- 动态提示词，其中每个请求在前缀中穿插了独特的内容。

### 为什么这是调度问题，而不仅仅是内核问题

你可以将 KV 复用实现为一种内核技巧。SGLang 的洞察是：只有当调度器保持热分支驻留时，复用才有价值。在混合负载下，一个天真的"可用就复用"策略会导致缓存频繁刷新。基于基数树索引的调度器才是将内核技巧转化为 29% 生产环境优势的关键。

### 与 vLLM 的互操作

这两个系统并非严格意义上的竞争对手。2026 年，vLLM 添加了前缀缓存（`--enable-prefix-caching`）和缓存感知路由器（基于 Rust 的 vLLM Router）。差距有所缩小但并未完全消失——SGLang 的整个栈以基数树为先；vLLM 则是后来移植的。对于以前缀复用为主的工作负载，SGLang 仍是默认选择。对于没有明显前缀模式的通用服务场景，vLLM 仍然相当或更优。

## 关键术语

| 术语 | 通常说法 | 实际含义 |
|------|---------|---------|
| RadixAttention | "那个 SGLang 的东西" | KV 缓存以基数树索引，共享前缀复用块 |
| 基数树（Radix tree） | "紧凑字典树" | 每个节点持有一个 token 范围及其 KV 块 |
| 缓存感知调度器 | "热分支优先" | 优先选择与驻留分支共享的请求的调度器 |
| 前缀缓存命中率 | "你的提示词中有多少是免费的" | 从复用的 KV 块服务的提示词 token 比例 |
| FCFS | "先到先服务" | 破坏前缀局部性的默认调度策略 |
| 分支级 LRU | "逐出叶子节点" | 与基数树形状匹配的逐出策略 |
| 提示词模板排序 | "缓存键" | 提示词的组件顺序决定了树能共享什么 |
| 系统提示词驻留 | "驻留前缀" | 保持不可变系统部分驻留，避免逐出抖动 |
