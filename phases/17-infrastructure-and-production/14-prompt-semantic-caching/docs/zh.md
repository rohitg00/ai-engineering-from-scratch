# 提示缓存与语义缓存经济学

> **定价快照日期：2026年4月。** 下文中的数据基于本课程发布时的厂商价目表；在引用之前，请对照链接文档核实。

> 缓存发生在两个层面。L2（提供商级别）的提示/前缀缓存对重复前缀复用注意力 KV——Anthropic 的提示缓存文档称其可在长提示上实现高达 90% 的成本降低和 85% 的延迟降低；对于 Claude 3.5 Sonnet，缓存读取为 $0.30/M，而新鲜读取为 $3.00/M，TTL 为 5 分钟，1 小时 TTL 选项的写入溢价为 2 倍（docs.anthropic.com，2026-04）。OpenAI 的提示缓存自动应用于 ≥1024 个 token 的提示，缓存输入的定价约为新鲜输入的 10% 折扣（platform.openai.com，2026-04）；具体按模型的缓存费率取决于实时价目表。L1（应用级别）的语义缓存在嵌入相似度命中时完全跳过 LLM。厂商声称的"95% 准确率"指的是匹配正确性，而非命中率——生产环境报告的命中率范围从 10%（开放式聊天）到 70%（结构化 FAQ）不等；两家提供商均未发布官方基线，因此请将这些视为社区遥测数据而非保证。生产环境中的陷阱：并行化会杀死缓存（N 个并行请求在第一次缓存写入之前发出，可能导致开支数倍增长），而前缀中的动态内容会完全阻止缓存命中。ProjectDiscovery 报告通过将动态文本移出可缓存前缀，命中率从 7% 提升至 74%（2025-11）。

## 学习目标

- 区分 L2 提示/前缀缓存（提供商端 KV 复用）与 L1 语义缓存（相似提示时绕过 LLM）。
- 解释 Anthropic 的 `cache_control` 显式标记以及两种 TTL 选项（5 分钟 vs 1 小时）及其价格乘数。
- 根据命中率、提示/回复混合比例和 token 价格计算预期的月度节省。
- 指出导致账单膨胀 5-10 倍的并行化反模式和导致命中率崩溃的动态内容反模式。

## 问题

你在你的 RAG 服务中加入了提示缓存。账单纹丝不动。你测量了命中率；是 7%。你的提示看起来是静态的，但并非如此——系统提示包含了精确到分钟的当前时间、一个请求 ID 以及一个为了多样性而随机排序的示例。每个请求都写入一个新的缓存条目，读取数为零。

另一方面，你的智能体对每个用户问题发出十个并行的工具调用。这十个请求都在第一次缓存写入完成之前到达提供商。十次写入，零次读取。你的账单是"启用缓存"本应达到的 5-10 倍。

缓存是一种协议，而不是一个开关。两个层面，两种不同的失败模式。

## 概念

### L2——提供商提示/前缀缓存

提供商会存储可缓存前缀的注意力 KV，并在下一次匹配该前缀的请求时复用它。你支付一次写入成本，读取几乎免费。

**Anthropic（Claude 3.5 / 3.7 / 4 系列）：** 在请求中使用显式的 `cache_control` 标记。你标记哪些块是可缓存的。TTL：5 分钟（写入成本为基准价的 1.25 倍）或 1 小时（写入成本为基准价的 2 倍）。缓存读取：Claude 3.5 Sonnet 上 $0.30/M 对比新鲜读取 $3.00/M——便宜 10 倍（docs.anthropic.com，截至 2026-04）。不同模型的费率不同（Opus/Haiku 分别发布）；始终核对实时定价页面。

**OpenAI：** 对 ≥1024 个 token 的提示自动缓存（platform.openai.com，2026-04）。无需显式标记。在当前 gpt-4o/gpt-5 的价目表上，缓存输入大约比新鲜输入便宜 10 倍。文档和发布说明均未发布官方的命中率基线；社区报告在精心设计提示的情况下集中在 30-60% 左右。监控 `usage.cached_tokens` 以测量你自己的数据。

**Google（Gemini）：** 通过显式 API 进行上下文缓存；100 万 token 的上下文意味着缓存带来的收益更大。

**自托管（vLLM, SGLang）：** 阶段 17 · 06 涵盖 RadixAttention——在你自己的计算资源上使用相同的模式。

### L1——应用级语义缓存

在调用 LLM 之前，对提示进行哈希、嵌入，并查找相似的缓存请求（余弦相似度高于阈值，通常为 0.95+）。命中时，返回缓存的响应。未命中时，调用 LLM 并缓存结果。

开源方案：Redis Vector Similarity、GPTCache、Qdrant。商业方案：Portkey Cache、Helicone Cache。

厂商声称的准确率指的是返回的缓存响应在语义上合适的频率——而非你的命中率。生产环境命中率：

- 开放式聊天：10-15%。
- 结构化 FAQ / 支持：40-70%。
- 代码问题：20-30%（微小变化就会导致命中失效）。
- 重复提示的语音助手：50-80%（语音归一化固定集合）。

### 并行化反模式

你的智能体并行发出 10 个工具调用。这 10 个调用都有相同的 4K token 系统提示。Anthropic 的缓存写入是按请求进行的；第一次缓存写入在提供商看到提示后约 300 毫秒完成。请求 2-10 在同一毫秒窗口内到达，每个都看到缓存未命中。你支付了 10 次写入溢价，0 次读取折扣。

修复方法：采用顺序优先的批处理——先单独发出请求 1，等请求 1 的缓存填充完毕后再发出请求 2-10。这会为第一个工具调用增加 300 毫秒，但可节省 5-10 倍的账单。

### 动态内容反模式

你的系统提示看起来像这样：

```
你是一个有用的助手。当前时间是 14:32:17。
用户 ID：abc123。今天是星期二……
```

每个请求都是唯一的。每个请求都写入。零次命中。

修复方法：将所有真正静态的内容移动到可缓存前缀中；将动态内容附加在缓存边界之后：

```
[可缓存]
你是一个有用的助手。[规则、示例、指令]
[/可缓存]
[动态，不缓存]
当前时间：14:32:17。用户：abc123。
```

ProjectDiscovery 通过这种方式将缓存命中率从 7% 提升到了 74%，并发布了详细分析。

### 为隔夜工作负载叠加批处理 + 缓存

批处理 API（阶段 17 · 15）在 24 小时周转时间下提供 50% 折扣。在此基础上叠加缓存输入可再获得约 10 倍的优惠。隔夜分类、标注和报告生成工作负载通过叠加可将成本降至同步非缓存成本的约 10%。

### 你应该记住的数据

定价数据于 2026-04 从链接的厂商文档中获取，每隔几个月就会变动——在依赖这些数据之前请重新核对。

- Anthropic 缓存读取：Claude 3.5 Sonnet 上 $0.30/M，约为新鲜输入的 10 分之一（docs.anthropic.com）。
- Anthropic 缓存写入溢价：1.25 倍（5 分钟 TTL）或 2 倍（1 小时 TTL）。
- OpenAI 自动缓存：适用于 ≥1024 个 token 的提示；按当前价目表，缓存输入定价约为新鲜输入的 10%（platform.openai.com）。
- 语义缓存命中率（社区报告）：开放式聊天约 10%；结构化 FAQ 高达约 70%。并非厂商记录的基线。
- ProjectDiscovery：通过将动态内容移出前缀，命中率从 7% 提升至 74%（项目博客，2025-11）。
- 并行化反模式：典型报告显示，当 N 个并行请求错过第一次缓存写入时，账单膨胀 5-10 倍。

## 练习

1. 运行 `code/main.py`。切换并行化标志。账单变化了多少？
2. 你的系统提示中包含日期。将其移出。展示之前和之后的命中率计算。
3. 根据你的请求到达率，计算 1 小时 TTL（2 倍写入）与 5 分钟 TTL（1.25 倍写入）的盈亏平衡点。
4. 语义缓存在 0.95 阈值下命中率为 20%。在 0.85 阈值下命中率为 50%，但你看到了不正确的缓存响应。选择合适的阈值并说明理由。
5. 你对每个用户问题批处理 10 个并行子查询。在不增加端到端延迟的前提下，将其重写为缓存友好的形式。

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|-----------|---------|
| L2 提示缓存 | "前缀缓存" | 提供商会存储重复前缀的 KV |
| `cache_control` | "Anthropic 缓存标记" | 标记可缓存块的显式属性 |
| 缓存写入溢价 | "写入税" | 首次未命中到缓存的额外成本（1.25 倍或 2 倍） |
| L1 语义缓存 | "嵌入缓存" | 调用 LLM 之前的应用级哈希与嵌入 |
| GPTCache | "LLM 缓存库" | 流行的开源 L1 缓存库 |
| 缓存命中率 | "命中数 / 总数" | 从缓存中服务的请求比例 |
| 并行化反模式 | "N 次写入陷阱" | N 个并行请求导致 N 次缓存未命中 |
| 动态内容陷阱 | "时间在提示中陷阱" | 前缀中的动态字节导致命中率归零 |
| RadixAttention | "副本内缓存" | SGLang 的前缀缓存实现 |
