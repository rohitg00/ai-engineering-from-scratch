# 无服务器 LLM 的冷启动缓解

> 一个 20 GB 的模型镜像从冷启动到提供推理服务需要 5-10 分钟（7B）到 20+ 分钟（70B）。在真正的无服务器世界中，这不仅是预热，而是一次故障。缓解方案在五个层面运作：预填充节点镜像（AWS 上的 Bottlerocket，双卷架构）、模型流式加载（NVIDIA Run:ai Model Streamer，vLLM 内置）、GPU 内存快照（Modal 检查点，重启速度提升 10 倍）、温池（`min_workers=1`）、分层加载（ServerlessLLM 的 NVMe→DRAM→HBM 流水线，延迟降低 10-200 倍），以及传输输入令牌（KB）而非 KV 缓存（GB）的热迁移。Modal 宣称冷启动低至 2-4 秒；Baseten 默认 5-10 秒，预预热后可达亚秒级。本课教你如何测量、预算并叠加这五个层面。

**类型：** 学习
**语言：** Python（标准库，玩具级冷启动路径模拟器）
**前置条件：** 阶段 17 · 02（推理平台经济学），阶段 17 · 03（GPU 自动扩缩）
**时间：** 约 60 分钟

## 学习目标

- 列举冷启动缓解的五个层面，并在每个层面说出一种工具或模式。
- 计算 70B 模型的总冷启动时间，作为（节点预配 + 权重下载 + 权重加载到 HBM + 引擎初始化）之和。
- 解释为什么热迁移传输的是输入令牌（KB）而非 KV 缓存（GB），以及其代价（重计算）。
- 说出温池的权衡（为空闲 GPU 付费或承受冷启动尾部延迟）以及 `min_workers > 0` 成为必须的 SLA 阈值。

## 问题

你的无服务器 LLM 端点夜间缩放到零。早上 8 点流量高峰。第一个请求需要等待以下步骤：

1. Karpenter 预配 GPU 节点：45-60 秒。
2. 容器拉取包含权重的 30 GB 镜像：120-300 秒。
3. 引擎将权重加载到 HBM：45-120 秒，取决于模型大小和存储速度。
4. vLLM 或 TRT-LLM 初始化 CUDA 图、KV 缓存池、分词器：10-30 秒。

总计：220-510 秒（约 3-8 分钟）才能返回第一个令牌。你的 SLA 是 2 秒。你部署了温池（`min_workers=1`），问题似乎消失了——但现在你 24x7 为一台空闲 GPU 付费。如果你的服务有 5 个产品，每个都有一个温副本，那就是 5 × 24 × 30 = 每月 3,600 GPU 小时，无论是否有用户调用。

冷启动缓解就是在保持无服务器经济性的同时，逼近常开模式的延迟。

## 概念

### 第 1 层——预填充节点镜像（Bottlerocket）

在 AWS 上，Bottlerocket 的双卷架构将操作系统与数据分离。将已预拉取容器镜像的数据卷做快照；在 `EC2NodeClass` 中引用该快照 ID。新节点启动时权重已位于本地 NVMe 上——步骤 2 和部分步骤 3 被消除。与 Karpenter 原生兼容。对于大模型，典型的节省是每次冷启动 2-4 分钟。

GCP 上的等效方案：预置容器层的自定义 VM 镜像。Azure 上：采用相同模式的托管磁盘快照。

### 第 2 层——模型流式加载（Run:ai Model Streamer）

无需在响应第一个请求前加载完整文件，而是逐层将权重流式传输到 GPU 内存，并在第一个 Transformer 块就绪后立即开始处理。NVIDIA Run:ai Model Streamer 在 vLLM 2026 中原生提供。支持 S3、GCS 和本地 NVMe。通过将 I/O 与计算设置重叠，大模型的权重加载时间大约减半。

### 第 3 层——GPU 内存快照（Modal）

Modal 在首次加载后对 GPU 状态（权重、CUDA 图、KV 缓存区域）进行检查点。后续重启直接反序列化到 HBM——比重新初始化快 10 倍。这是最接近"在 2 秒内启动一个热 GPU"的方案。权衡：快照是每 GPU 拓扑的，所以如果 Karpenter 将你迁移到不同的 SKU，你需要重新检查点。

### 第 4 层——温池（min_workers=1）

最简单的缓解方案：始终保持一个副本就绪。代价是一台 GPU 每小时 24x7 的费用。该算术对小模型很残酷（你付 $0.85-$1.50/小时来避免 30 秒的冷启动），对大模型则较友好（付 $4/小时来避免 5 分钟的冷启动）。温池成为必须的 SLA 阈值：通常对于 70B+ 模型，TTFT P99 < 60 秒。

### 第 5 层——分层加载（ServerlessLLM）

ServerlessLLM 将存储视为一个层次结构：NVMe（快速但容量大）、DRAM（中等但分层次）、HBM（容量小但访问即时）。权重预加载到 DRAM；按需加载到 HBM。论文报告相对于天真的磁盘到 HBM 方式，冷加载延迟降低 10-200 倍。生产环境采用尚处早期，但已有与 vLLM 的集成。

### 第 6 层——热迁移（奖励模式）

当节点不可用时（竞价实例回收、节点排空），传统模式是冷启动另一个副本并排空请求队列。热迁移将输入令牌（KB）传输到已加载模型的目标节点，并在目标节点上重新计算 KV 缓存。重计算比通过网络传输 GB 级别的 KV 缓存更经济。适用于分离式部署。

### 温池数学

对于一个 P99 TTFT SLA 为 2 秒的服务，问题不是"是否使用温池"，而是"需要多少个温副本，以及哪些路径使用它们"。

- 高价值交互路径（实时聊天、语音代理）：`min_workers=1-2`。
- 后台批处理路径（夜间分类）：接受缩放到零，5-10 分钟的冷启动可容忍。
- 高级用户层：每个租户的 `min_workers` 配合专用容量。

### 先测量，再优化

70B 模型在全新节点上的冷启动剖析（示意）：

| 阶段 | 时间 | 缓解方案 |
|------|------|---------|
| 节点预配 | 50 秒 | Bottlerocket + 预填充镜像，温池 |
| 镜像拉取 | 180 秒 | 预填充数据卷（消除） |
| 权重到 HBM | 75 秒 | 模型流式加载（减半）；GPU 快照（消除） |
| 引擎初始化 | 20 秒 | 持久化 CUDA 图缓存 |
| 首次前向传播 | 3 秒 | 最低固有延迟 |
| **冷启动总计** | **328 秒** | |
| **缓解后总计** | **约 15 秒** | 降低 22 倍 |

### 你应该记住的数字

- Modal 冷启动：2-4 秒（使用 GPU 快照）。
- Baseten 默认冷启动：5-10 秒；预预热后亚秒级。
- 原始 70B 冷启动：3-8 分钟。
- Run:ai Model Streamer：约 2 倍权重加载加速。
- ServerlessLLM 分层加载：延迟降低 10-200 倍（论文数据）。

## 关键术语

| 术语 | 一般说法 | 实际含义 |
|------|---------|---------|
| 冷启动 | "长时间停顿" | 从请求到新副本返回第一个令牌的时间 |
| 温池 | "常开最小值" | `min_workers >= 1` 以保持至少一个副本就绪 |
| 预填充镜像 | "烘焙好的 AMI" | 已预置容器权重的节点镜像 |
| Bottlerocket | "AWS 节点操作系统" | AWS 容器优化操作系统，支持双卷快照 |
| 模型流式加载 | "流式加载" | 将权重 I/O 与计算设置重叠 |
| GPU 快照 | "检查点到 HBM" | 序列化加载后的 GPU 状态；重启时反序列化 |
| 分层加载 | "NVMe + DRAM + HBM" | 存储层次的层级结构；按需加载 |
| 热迁移 | "移动令牌" | 传输输入（KB），在目标节点重计算 KV |
| `min_workers` | "温副本" | 无服务器最小存活数 |
| 缩放到零 | "完全无服务器" | 空闲时无成本；承受完整的冷启动代价 |
