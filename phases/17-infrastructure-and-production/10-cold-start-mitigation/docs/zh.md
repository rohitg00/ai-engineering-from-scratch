# 無伺服器 LLM 的冷啟動緩解

> 一份 20 GB 的模型映像，從冷到能服務要 5-10 分鐘（7B）到 20 分鐘以上（70B）。在真正的無伺服器世界裡，那不是暖機 —— 那是一次停擺。緩解手段作用在五個層次上：預先播種的節點映像（AWS 上的 Bottlerocket、雙磁碟區架構）、模型串流（NVIDIA Run:ai Model Streamer，在 vLLM 中已原生支援）、GPU 記憶體快照（Modal 的檢查點，重啟最多快 10 倍）、暖池（`min_workers=1`）、分層載入（ServerlessLLM 的 NVMe→DRAM→HBM 管線，延遲降低 10-200 倍），以及搬移輸入詞元（KB）而不是 KV 快取（GB）的即時遷移。Modal 公布 2-4 秒的冷啟動作為地板；Baseten 預設 5-10 秒，有預熱時可到次秒級。這一課教你量測、編列預算，並把這五層疊起來。

**類型：** 學習
**程式語言：** Python (stdlib, toy cold-start path simulator)
**先修單元：** 階段 17 · 02（推論平台的經濟學）、階段 17 · 03（GPU 自動擴縮）
**時間：** 約 60 分鐘

## 學習目標

- 列舉冷啟動緩解的五個層次，並在每一層說出一項工具或模式。
- 把一個 70B 模型的總冷啟動時間，算成（節點配置）+（權重下載）+（權重載入 HBM）+（引擎初始化）的總和。
- 解釋為何即時遷移轉移的是輸入詞元（KB）而不是 KV 快取（GB），以及代價是什麼（重新計算）。
- 說出暖池的取捨（替閒置 GPU 付錢，或接受冷啟動的尾端），以及 `min_workers > 0` 變成必要的那個 SLA 門檻。

## 問題所在

你的無伺服器 LLM 端點在夜裡縮到零。早上八點流量湧入。第一個請求在等待期間會發生：

1. Karpenter 配置一個 GPU 節點：45-60 秒。
2. 容器拉一份含權重的 30 GB 映像：120-300 秒。
3. 引擎把權重載入 HBM：依模型大小與儲存速度 45-120 秒。
4. vLLM 或 TRT-LLM 初始化 CUDA graph、KV 快取池、分詞器：10-30 秒。

總計：220-510 秒（大約 3-8 分鐘）才吐回第一個詞元。你的 SLA 是 2 秒。你出貨了一個暖池（`min_workers=1`），問題看似消失 —— 但現在你全天候替一張閒置的 GPU 付錢。若你的服務有 5 條產品線、每條各一個暖副本，那就是每月 5 × 24 × 30 = 3,600 GPU 小時，不管有沒有一個使用者呼叫過。

冷啟動緩解，就是怎麼在保住無伺服器經濟性的同時，逼近常駐的延遲。

## 核心概念

### 第 1 層 —— 預先播種的節點映像（Bottlerocket）

在 AWS 上，Bottlerocket 的雙磁碟區架構把作業系統與資料分開。把你的容器映像預先拉好、對資料磁碟區做快照；在你的 `EC2NodeClass` 中引用那個快照 ID。新節點開機時權重就已經在本地 NVMe 上 —— 第 2 步與第 3 步的一部分就消失了。與 Karpenter 原生相容。對大模型的典型節省：每次冷啟動 2-4 分鐘。

GCP 上的對應物：預先烘好容器層的自訂 VM 映像。Azure 上：同樣模式的受管磁碟快照。

### 第 2 層 —— 模型串流（Run:ai Model Streamer）

不要在回答第一個請求之前把整份檔案載完，而是逐層把權重串進 GPU 記憶體，並在第一個 transformer 區塊常駐之後就開始處理。NVIDIA Run:ai Model Streamer 在 2026 年的 vLLM 中原生出貨。可搭配 S3、GCS 與本地 NVMe。透過把 I/O 與運算設定重疊，對大模型大約把權重載入時間砍一半。

### 第 3 層 —— GPU 記憶體快照（Modal）

Modal 在第一次載入之後，對 GPU 狀態（權重、CUDA graph、KV 快取區）取一份檢查點。之後的重啟直接反序列化進 HBM —— 比重新初始化快 10 倍。這是最接近「兩秒開機一張暖 GPU」的東西。取捨：快照是綁 GPU 拓撲的，所以若 Karpenter 把你遷到不同的 SKU，你就得重新做檢查點。

### 第 4 層 —— 暖池（min_workers=1）

最簡單的緩解：永遠留一個副本待命。成本是一張 GPU 全天候的時薪。這筆算術對小模型很殘酷（你付每小時 0.85-1.50 美元，只為了躲掉 30 秒的冷啟動），對大模型則很友善（付每小時 4 美元，躲掉 5 分鐘的冷啟動）。暖池變成必要的 SLA 門檻：在 70B 以上的模型上，通常是 TTFT P99 < 60 秒。

### 第 5 層 —— 分層載入（ServerlessLLM）

ServerlessLLM 把儲存當成一個階層：NVMe（快但大）、DRAM（中等且分層）、HBM（很小但即時）。權重預先載到 DRAM；按需載入 HBM。論文回報相對於天真的「磁碟到 HBM」，冷載入延遲降低 10-200 倍。生產採用還在早期，但與 vLLM 的整合已經存在。

### 第 6 層 —— 即時遷移（附加模式）

當一個節點變得不可用時（競價實例被回收、節點排空），傳統做法是冷啟動另一個副本並排空請求佇列。即時遷移則是把輸入詞元（幾 KB）搬到一台已經載好模型的目的地，並在目的地重新計算 KV 快取。重新計算比在網路上轉移好幾 GB 的 KV 快取便宜。適用於分離式部署。

### 暖池的數學

對一個 P99 TTFT SLA 為 2 秒的服務，問題不是「要不要暖池」，而是「要幾個暖副本、哪些路徑拿得到」。

- 高價值的互動路徑（即時聊天、語音代理）：`min_workers=1-2`。
- 背景批次路徑（夜間分類）：可以接受縮到零，5-10 分鐘的冷啟動忍得住。
- 高階方案：逐租戶的 `min_workers` 配專屬容量。

### 先量測再最佳化

一個 70B 模型在全新節點上的冷啟動解剖（示意）：

| 階段 | 時間 | 緩解 |
|-------|------|-----------|
| 節點配置 | 50 秒 | Bottlerocket + 預先播種的映像、暖池 |
| 拉映像 | 180 秒 | 預先播種的資料磁碟區（消除） |
| 權重進 HBM | 75 秒 | 模型串流（減半）；GPU 快照（消除） |
| 引擎初始化 | 20 秒 | 持久的 CUDA graph 快取 |
| 第一次前向 | 3 秒 | 固有的最小延遲 |
| **冷啟動總計** | **328 秒** | |
| **加上緩解後總計** | **約 15 秒** | 減少 22 倍 |

### 你該記住的數字

- Modal 冷啟動：2-4 秒（有 GPU 快照）。
- Baseten 預設冷啟動：5-10 秒；有預熱時次秒級。
- 未經處理的 70B 冷啟動：3-8 分鐘。
- Run:ai Model Streamer：權重載入約 2 倍加速。
- ServerlessLLM 的分層載入：延遲降低 10-200 倍（論文數字）。

## 練習

1. 跑 `code/main.py`。算出那個請求速率的損益平衡點：超過它之後，一個暖副本會比「在 SLO 上多丟請求所付的冷啟動稅」更便宜。
2. 你部署一個 13B 模型、P99 TTFT SLA 為 3 秒。挑出達成它所需、層數最少的那套緩解堆疊。
3. Bottlerocket 的預先播種消除了拉映像，但權重仍要從快照載進 HBM。若快照支撐的 NVMe 讀取速度是 7 GB/s，算出 70B 模型的牆鐘時間。
4. 你的無伺服器供應商提供 GPU 快照（Modal），但你的團隊拒絕，因為「快照會洩漏 PII」。替兩邊各論證一次 —— 實際的風險是什麼，而緩解又是什麼（短暫快照、加密、命名空間隔離）？
5. 設計一套分層的暖池政策：付費使用者、試用使用者與批次工作負載各要幾個暖副本？把數學算出來。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 冷啟動 | 「那個大停頓」 | 在一個全新副本上，從請求到第一個詞元的時間 |
| 暖池 | 「常駐的最低量」 | 用 `min_workers >= 1` 至少留一個副本待命 |
| 預先播種的映像 | 「烘好的 AMI」 | 容器權重已常駐其中的節點映像 |
| Bottlerocket | 「AWS 的節點作業系統」 | AWS 為容器最佳化、支援雙磁碟區快照的作業系統 |
| 模型串流 | 「串流式載入」 | 把權重 I/O 與運算設定重疊起來 |
| GPU 快照 | 「對 HBM 做檢查點」 | 把載入後的 GPU 狀態序列化；重啟時反序列化 |
| 分層載入 | 「NVMe + DRAM + HBM」 | 儲存層級的階層；按需載入 |
| 即時遷移 | 「搬詞元」 | 轉移輸入（KB），在目的地重新計算 KV |
| `min_workers` | 「暖副本」 | 無伺服器的最低保活數量 |
| 縮到零 | 「完全無伺服器」 | 閒置時零成本；接受完整的冷啟動稅 |
