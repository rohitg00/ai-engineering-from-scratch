# 多区域 LLM 服务与 KV 缓存局部性

> 轮询负载均衡对有缓存的 LLM 推理有严重负面影响。未命中持有其前缀的节点的请求需支付完整预填充成本——长提示词 P50 约 800 毫秒，而缓存命中仅约 80 毫秒。2026 年的生产模式是使用缓存感知路由器（vLLM Router 基于 Rust，llm-d router），它消费 KV 缓存事件并基于前缀哈希匹配进行路由。近期研究（GORGO）将跨区域网络延迟显式纳入路由目标。商业化的"跨区域推理"产品（Bedrock 跨区域推理、GKE 多集群网关）将推理视为黑盒——它们处理可用性，而非 TTFT。摩根大通和梅奥诊所于 2024 年 11 月在 us-east-1 进行故障转移演练，耗时约 22 分钟。灾难恢复的现实：32% 的 LLM 灾难恢复失败是因为团队备份了权重却忘记分词器文件或量化配置文件。

**类型：** 学习
**语言：** Python（标准库，简易前缀缓存感知路由器模拟器）
**前置知识：** 阶段 17 · 04（vLLM 服务），阶段 17 · 06（SGLang RadixAttention）
**时间：** 约 60 分钟

## 学习目标

- 解释为什么轮询负载均衡会破坏缓存推理，并量化 TTFT 惩罚。
- 绘制缓存感知路由器示意图：输入（KV 缓存事件）、算法（前缀哈希匹配）、决胜策略（GPU 利用率）。
- 指出 LLM 32% 灾难恢复失败的原因（缺少分词器文件/量化配置文件），并列出三文件灾难恢复检查清单。
- 区分商业跨区域产品（Bedrock CRI、GKE Multi-Cluster Gateway）与 KV 感知路由。

## 问题

你的服务运行在 us-east-1、us-west-2 和 eu-west-1。你在前面放了一个 ALB 并使用轮询策略。生产中前缀缓存命中率降至 8%。TTFT P50 翻了三倍。你的 vLLM 日志显示每个请求都在支付完整的预填充成本。

轮询对无状态服务是最优的。LLM 推理本质上是**有状态的**——KV 缓存编码了模型所见的一切。盲目路由就是路由到错误的缓存。

另外，你的团队有一个灾难恢复计划。你将模型权重备份到 S3 的跨区域存储。某区域发生故障；你尝试故障转移；副本拒绝启动。你忘了 `tokenizer.json`、量化配置和 RoPE 缩放配置在另一个未同步的存储桶中。

多区域 LLM 服务是一个缓存问题、一个路由问题和一个灾难恢复规范问题——而不是一个负载均衡器问题。

## 概念

### 缓存感知路由

请求到达时带有提示词。路由器对前缀（例如前 512 个 token）进行哈希；它向每个副本询问"你是否缓存了这个前缀？"。副本在分配和驱逐块时通过发布/订阅频道发布 KV 缓存事件。路由器选择匹配的副本；如果没有匹配，则回退到基于 GPU 利用率的决胜策略。

**vLLM Router**（Rust，2026 年生产栈）：订阅 `kv.cache.block_added` 事件，维护前缀哈希 → 副本索引，以 O(1) 查找路由。无匹配时回退到最小队列深度。

**llm-d router**：相同模式，Kubernetes 原生。通过 ControlPlane API 发布事件。

**SGLang RadixAttention**（阶段 17 · 06）是副本内部的等价物。跨副本路由严格在上游进行。

### 数据

2K token 提示词下 Llama 3.3 70B FP8、H100 的 TTFT P50：
- 缓存命中（同一副本，前缀常驻）：约 80 毫秒。
- 缓存未命中（冷预填充）：约 800 毫秒。

10 倍差距。如果你的路由器在副本间达到 60-80% 的前缀缓存命中率，你可以在 N 副本容量下接近单副本性能。如果命中率只有 10%，你得到的只是朴素扩展的效果。

### 跨区域有一个新的约束——网络延迟

区域间 RTT：
- us-east-1 ↔ us-west-2：约 65 毫秒。
- us-east-1 ↔ eu-west-1：约 75 毫秒。
- us-east-1 ↔ ap-southeast-1：约 220 毫秒。

如果路由将请求从 us-east-1 发送到 ap-southeast-1 的热前缀，节省的预填充时间（800 → 80 毫秒）会被 440 毫秒的往返时间所抵消。GORGO（2026 年研究）使其显式化——联合最小化 `prefill_time + network_latency`，而非仅优化预填充。通常答案是保持路由在区域内，除非是大型多 MB 前缀，此时预填充时间占主导。

### 商业化的"跨区域推理"在这里没有帮助

AWS Bedrock 跨区域推理在容量压力下自动将请求路由到其他区域。它优化的是**可用性**，而非 TTFT，并将推理视为黑盒。GKE Multi-Cluster Gateway 同理——服务级故障转移，不感知 KV 缓存。

即使使用这些产品，你仍然需要应用层的缓存感知路由器。它们处理"us-east-1 着火了"的情况。缓存感知路由处理 TTFT 的情况。

### 灾难恢复规范——32% 的文件缺失问题

2026 年被广泛引用的统计数据：32% 的 LLM 灾难恢复失败是因为团队备份了权重但忘记了：

- `tokenizer.json` 或 `tokenizer.model`
- 量化配置（`quantize_config.json`、AWQ 缩放系数、GPTQ 零点）
- 模型特定配置（RoPE 缩放、注意力掩码、聊天模板）
- 引擎配置（`vllm_config.yaml`、采样默认值、LoRA 适配器清单）

解决方案是最少三文件的灾难恢复清单：

1. HF 模型仓库下的所有文件（权重 + 配置 + 分词器）。
2. 引擎特定的服务配置。
3. 部署清单（K8s YAML、Dockerfile、依赖锁定文件）。

此外：每季度进行一次灾难恢复演练。摩根大通在 2024 年 11 月的 us-east-1 演练中达到 22 分钟恢复时间，这仅因为操作手册经过了演练。

### 数据驻留是正交问题

欧盟客户的 PHI 不能离开欧盟。如果你的缓存感知路由器将巴黎发起的请求发送到 us-east-1 以匹配前缀，无论 TTFT 收益如何，你都违反了 GDPR。在优化缓存之前，先按数据驻留边界划分路由器。

### 你需要记住的数据

- 缓存命中与未命中的 TTFT 差距：约 10 倍（2K 提示词下 80 毫秒 vs 800 毫秒）。
- 区域间 RTT 美欧：约 75 毫秒。
- 灾难恢复失败：32% 缺少分词器/量化配置。
- 摩根大通 us-east-1 故障转移 2024 年 11 月：22 分钟（30 分钟 SLA）。

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------|----------|
| 缓存感知路由 | "智能负载均衡" | 基于前缀哈希匹配路由到持有 KV 缓存的副本 |
| KV 缓存事件 | "缓存发布-订阅" | 副本发布块的添加/驱逐；路由器建立索引 |
| 前缀哈希 | "缓存键" | 前 N 个 token 的哈希，用作路由器查找 |
| GORGO | "跨区域路由研究" | arXiv 2602.11688；网络延迟作为显式项 |
| 跨区域推理 | "Bedrock CRI" | AWS 产品；可用性故障转移，非 TTFT 感知 |
| 灾难恢复清单 | "备份列表" | 恢复所需的每个文件——不仅仅是权重 |
| 数据驻留 | "GDPR 边界" | 法律约束：哪些区域可以处理用户数据 |
| RTT | "往返时间" | 网络延迟；美欧 75 毫秒，美亚太 220 毫秒 |
| LLM 感知负载均衡 | "缓存命中负载均衡" | 缓存感知路由器作为一个产品类别 |
