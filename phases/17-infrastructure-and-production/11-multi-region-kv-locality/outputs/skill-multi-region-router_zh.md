给定涉及的区域、数据驻留边界、预期前缀缓存多样性和 TTFT SLA，生成多区域路由和灾难恢复方案。

输出：

1. **路由器选择**。选择缓存感知路由器（vLLM Router、llm-d router）并描述 KV 事件通道。说明前缀哈希算法（例如，512-Token 滚动）和决胜规则（最小队列深度）。
2. **路由策略**。区域优先还是全局（GORGO 风格）最小化预填充 + RTT？根据提示长度分布论证——长提示（>8K Token）受益于跨区域路由；短提示则不然。
3. **数据驻留分区**。在任何优化之前：哪些请求因法律原因（GDPR、HIPAA）绑定到哪些区域。即使能改善 TTFT，也禁止跨驻留路由。
4. **商用 CRI 层**。建议是否启用 Bedrock Cross-Region Inference 或 GKE Multi-Cluster Gateway 作为可用性层。明确指出该层不是 TTFT 优化手段。
5. **灾难恢复清单**。最少三个文件（HF 仓库 + 引擎配置 + 部署清单）。验证 tokenizer、量化配置、RoPE、聊天模板、LoRA 适配器已包含。说明存储方案（S3 跨区域复制、多区域 GCS）。
6. **故障转移演练**。每季度一次。谁执行、测量什么（RTO、RPO、缓存预热时间）。目标：30 分钟 RTO，与真实的 2024 年 JPMorgan 演练一致。

**硬性拒绝条件：**
- 为路由优化而忽略数据驻留。拒绝——GDPR 违规比 TTFT 提升更严重。
- 声称 Bedrock CRI"解决"了跨区域路由。拒绝——CRI 是针对可用性，而非 TTFT。
- 仅备份权重。拒绝——指明 32% 的灾难恢复失败统计数据并要求三文件清单。

**拒绝规则：**
- 如果仅涉及一个区域，拒绝该方案——单区域有不同的故障模式（阶段 17 · 03 覆盖）。
- 如果数据驻留和 TTFT SLA 不兼容（例如，欧盟驻留强制每次请求在冷前缀上预填充，且 P99 TTFT < 100 ms 用于 8K 提示），拒绝承诺 SLA 并升级产品需求。

**输出**：一页方案，指明路由器、路由策略、驻留分区、CRI 层状态、灾难恢复清单、季度演练负责人。最后给出需要告警的单一指标：跨区域前缀缓存命中率低于方案指定的阈值。
