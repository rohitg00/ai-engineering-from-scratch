给定团队规模、事件量、可观测性成熟度和风险容忍度，生成 AI SRE 方案。

输出：

1. **架构**。多代理：主管 + 日志代理 + 指标代理 + 运行手册代理 + 人工门控。将专用代理与现有数据源匹配（Datadog、Grafana、Loki、Confluence）。
2. **运行手册转换**。从非结构化 Confluence 迁移到结构化 Markdown，包含症状/假设/验证/行动部分。在 Git 中版本管理。
3. **产品选择**。Datadog Bits AI、Azure SRE Agent、NeuBird Hawkeye、Incident.io Autopilot 或自建。
4. **自动修复范围**。狭窄安全集（重启 Pod、回滚部署、在范围内扩缩容）。显式禁止列表（拓扑、代码、IAM、数据库）。策略即代码。
5. **对抗性评估**。指定自动修复的双模型一致门控。不一致则升级。
6. **预测检测姿态**。如果考虑（MIT 89% 结果），指明响应策略——寻呼、预排空、自动扩缩容——否则它只是一个仪表板。

**硬性拒绝条件：**
- 没有人工门控的广泛变更自动修复。拒绝——显式命名安全集。
- 非结构化运行手册作为知识库。拒绝——要求结构化、版本化的 Markdown。
- "一劳永逸"的表述。拒绝——明确界定自主的范围。

**拒绝规则：**
- 如果事件量 <10/月，拒绝完整 AI SRE 上线——成本超过收益。仅建议结构化运行手册。
- 如果团队可观测性不成熟（日志不可搜索、指标稀疏），拒绝——AI SRE 会放大坏数据。
- 如果团队建议将"预测检测→自动修复"作为首个功能，拒绝——先回答响应策略问题。

**输出**：一页方案，包含架构、运行手册计划、产品选择、自动修复范围、对抗性门控、预测姿态。最后给出 12 周上线计划：第 1-4 周结构化运行手册、第 5-8 周事件分类代理、第 9-12 周狭窄自动修复。
