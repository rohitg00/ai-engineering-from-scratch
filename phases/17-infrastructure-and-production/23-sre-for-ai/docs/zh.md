# AI 的 SRE——多智能体事件响应、Runbook、预测检测

> AI SRE 利用基于基础设施数据（日志、runbook、服务拓扑）通过 RAG 增强的 LLM，来自动化调查、文档记录和协调阶段。2026 年的架构模式是多智能体编排——由监督者协调专门化智能体（日志、指标、runbook）；AI 提出假设并查询，人类审批决策。Datadog Bits AI 和 Azure SRE Agent 已将此作为托管产品交付。Runbook 正在演进：NeuBird Hawkeye 采用对抗性评估（两个模型分析同一事件；一致 = 可信，分歧 = 不确定）；运营记忆跨越团队变动而持久存在。自动修复保持谨慎：AI 建议，人类审批。完全自主的行动范围很窄（重启 Pod、回滚特定部署），并有严格的防护措施——任何声称"一劳永逸"的人都在夸大其词。新兴前沿：事件前预测。MIT 研究报告指出，基于历史日志、GPU 温度和 API 错误模式训练的 LLM 能够提前 10-15 分钟预测 89% 的故障。预测：到 2026 年底，95% 的企业 LLM 将拥有自动故障转移能力。

**类型：** 学习
**语言：** Python（标准库，玩具级多智能体事件分类模拟器）
**前置知识：** 阶段 17 · 13（可观测性），阶段 17 · 24（混沌工程）
**时长：** 约 60 分钟

## 学习目标

- 绘制多智能体 AI SRE 架构图：监督者 + 专门化智能体（日志、指标、runbook）+ 人工审批关卡。
- 解释为什么自动修复范围很窄（重启 Pod、回滚部署）而非宽泛（重新设计服务架构）。
- 说出对抗性评估模式（NeuBird Hawkeye）：两个模型一致 = 可信；不一致 = 上报。
- 引用 MIT 89% 早期检测结果及其运营约束：没有执行动作的预测只是仪表盘。

## 问题场景

一名值班工程师凌晨 3 点被叫醒。"结账服务错误率过高。"他们检查 Datadog、Loki、三个 runbook、部署日志。30 分钟后，他们发现根本原因是 vLLM 因 KV 缓存激增导致 OOM。重启 Pod，错误消失。

到 2026 年，那次调查的前 20 分钟是可以自动化的。按服务分组日志、与最近部署关联、与 runbook 匹配——这些都是 RAG 加工具调用的工作。一个受监督的智能体可以在人类打开 Datadog 之前完成第一轮分类并提出假设。

完全自主的修复是另一个问题。重启 Pod：安全。扩缩 GPU 池：如果策略允许则安全。重新设计服务架构：绝对不行。这门学科的关键在于划定这条窄线。

## 核心理念

### 多智能体架构

```
          事件
            │
            ▼
        监督者
        /    |    \
       ▼     ▼     ▼
  日志智能体  指标智能体  Runbook 智能体
       │     │     │
       └─────┴─────┘
            │
            ▼
       假设 + 证据
            │
            ▼
        人工审批
            │
            ▼
       动作（窄集）
```

监督者将事件拆解为子查询。专门化智能体拥有工具访问权限（日志搜索、PromQL、文档检索）。监督者综合信息，将假设和证据呈现给人类。人类批准或重新指引方向。

### 自动修复范围

**安全（窄）：** 重启 Pod、回滚特定部署、在预先批准的范围内扩缩池、启用预先批准的功能开关。

**不安全（宽）：** 更改服务拓扑、修改资源限制、部署新代码、更改 IAM、修改数据库。

任何声称"一劳永逸"的人都在夸大其词。随着 AI SRE 的成熟，安全集会不断扩大，但边界是真实存在的。

### 对抗性评估（NeuBird Hawkeye）

两个模型独立分析同一事件。如果它们对根本原因的看法一致，置信度高。如果不一致，则将两个假设都呈现给人类进行上报处理。简单的模式，有效过滤幻觉导致的根本原因。

### 运营记忆

团队人员流动是传统 SRE 的无声杀手——隐性知识随之流失。AI SRE 将 runbook 和事后复盘存储在向量数据库中；智能体在处理每个新事件时进行检索。当新工程师加入时，AI 拥有完整的历史信息。

### 事件前预测

MIT 2025 年研究：基于历史日志、GPU 温度、API 错误模式训练的 LLM，在测试集上提前 10-15 分钟预测了 89% 的故障。

现实检验：没有执行动作的预测只是仪表盘。运营问题是"当我们预测到时，我们该做什么？"预防性排空？呼叫值班？自动扩缩？答案取决于具体策略。

### 2026 年的产品

- **Datadog Bits AI** —— Datadog 内部的托管 SRE 副驾驶。
- **Azure SRE Agent** —— Azure 原生。
- **NeuBird Hawkeye** —— 对抗性评估 + 运营记忆。
- **PagerDuty AIOps** —— 分类 + 去重。
- **Incident.io Autopilot** —— 事件指挥官 + 协调。

### Runbook 即代码

Runbook 从 Confluence 页面演进为带有结构化章节（症状、假设、验证、行动）的版本化 Markdown。结构化 runbook 有助于更好的 RAG 检索。任何 AI SRE 的推广都应从将非结构化 runbook 转变为结构化开始。

### 你应该记住的数据

- MIT 早期检测：89% 的故障，提前 10-15 分钟。
- 多智能体分类：监督者 +（日志、指标、runbook）+ 人类。
- 安全的自动修复集：重启 Pod、回滚部署、在范围内扩缩。
- 对抗性评估：两个模型独立分析；一致 = 可信。

## 使用它

`code/main.py` 模拟了多智能体分类：日志智能体发现错误，指标智能体发现 CPU 激增，runbook 智能体匹配到已知问题。监督者对假设进行排序。

## 交付它

本课程产出 `outputs/skill-ai-sre-plan.md`。根据当前值班情况、事件量、团队成熟度，设计一个 AI SRE 推广方案。

## 练习

1. 运行 `code/main.py`。如果日志智能体和指标智能体意见不一致怎么办？监督者如何解决？
2. 为你的服务定义三个"安全"的自动修复动作。说明每个动作的理由。
3. 编写一个结构化的 runbook 模板：章节、必填字段、验证命令。
4. 预测性检测提前 12 分钟触发。你的策略是什么——呼叫值班、预防性排空，还是两者兼有？
5. 讨论一个 3 人团队是否应在 2026 年采用 AI SRE，还是应等待。考虑成熟度、事件量、风险等方面。

## 关键术语

| 术语 | 人们说的意思 | 实际含义 |
|------|----------------|------------------------|
| AI SRE | "值班智能体" | 基于 LLM 的事件调查 + 协调 |
| 监督者智能体 | "编排器" | 顶层智能体，将事件拆解为子查询 |
| 专门化智能体 | "领域智能体" | 拥有工具访问权限的子智能体（日志、指标、runbook） |
| 自动修复 | "AI 修复它" | 狭窄的预先批准的动作；并非广泛的重新架构 |
| 运营记忆 | "向量 runbook" | 将事后复盘 + runbook 存入向量数据库供 RAG 使用 |
| 对抗性评估 | "双模型检查" | 独立分析；一致 = 可信 |
| NeuBird Hawkeye | "对抗性那个" | 采用对抗性评估 + 记忆模式的产品 |
| Bits AI | "Datadog 的 SRE 智能体" | Datadog 托管的 AI SRE |
| 事件前预测 | "早期检测" | 故障预测提前 10-15 分钟 |
