# 角色专业化 —— 规划者、评审者、执行者、验证者

> 2026 年最常见的多智能体分解方式：一个智能体负责规划，一个负责执行，一个负责评审或验证。MetaGPT（arXiv:2308.00352）将其形式化为编码到角色提示中的标准操作流程（SOP）——产品经理、架构师、项目经理、工程师、QA 工程师，遵循 `Code = SOP(Team)` 的范式。ChatDev（arXiv:2307.07924）通过"聊天链"和"沟通性去幻觉"（智能体主动请求缺失的细节）将设计师、程序员、评审员、测试员串联起来。验证者角色至关重要：Cemri 等人（MAST，arXiv:2503.13657）表明，每一次多智能体失败都可以追溯到缺失或失效的验证环节。普华永道报告称，在 CrewAI 中使用结构化验证循环可将准确率提升 7 倍（从 10% 提升至 70%）。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置条件：** 第 16 阶段 · 04（原始模型），第 16 阶段 · 05（监督者）
**时长：** 约 60 分钟

## 问题

通用的多智能体系统产生通用的输出。三个程序员在群聊中写出三种大同小异的平庸代码。你可以增加更多的智能体，增加更多的轮次，但仍然无法跨越质量的阈限。

解决办法不在于增加更多智能体，而在于使用*不同*的智能体。分配不同的角色。给评审者提供规划者没有的工具。给验证者一套客观的测试套件。这样一来，系统内部就有了基于实际修正的分歧，而不仅仅是平行的猜测。

## 概念

### 四种经典角色

**规划者（Planner）。** 阅读目标，生成步骤列表或规格说明。工具：知识检索、文档。输出：结构化计划。

**执行者（Executor）。** 每次执行一个计划步骤，产出制品。工具：实际工作工具（代码编译器、Shell、API 客户端）。输出：制品。

**评审者（Critic）。** 对照规划者的意图评审执行者的输出。工具：对制品的只读访问、静态分析。输出：接受/拒绝并附理由。

**验证者（Verifier）。** 读取制品并执行确定性检查。工具：测试运行器、类型检查器、模式验证器。输出：通过/失败并附证据。

评审者是主观的、有见地的，通常基于大语言模型。验证者是客观的、确定性的，通常基于代码。它们不是同一个角色。

### MetaGPT 的 SOP 模式

MetaGPT（arXiv:2308.00352）将软件工程 SOP 编码为角色提示：

- **产品经理**编写产品需求文档（PRD）。
- **架构师**产出系统设计。
- **项目经理**拆分任务。
- **工程师**实现代码。
- **QA 工程师**运行测试。

每个角色都有严格的输入/输出模式。角色提示说明了该角色*是什么*以及*必须产出什么*。`Code = SOP(Team)` 的表述——确定性的 SOP 将一组大语言模型转变为可预测的流水线。

### ChatDev 的沟通性去幻觉

ChatDev 增加了一个关键举措：当执行者需要计划中未包含的特定细节时，它在继续之前会明确向设计师提问。这防止了大语言模型经典失败模式——似有道理地凭空编造细节。

实现方式：角色提示中包含"当你需要未被提供的特定信息时，在产出输出之前，通过名称向相关角色提问。"

### 为什么验证者最重要

Cemri 等人（MAST）追溯了 1642 个多智能体执行失败案例。其中 21.3% 是验证缺口——系统交付了没有人检查过的答案。其余 79% 通常可以追溯到"存在某项检查，但它静默失败或从未运行过。"验证者是承载关键的角色。

普华永道报告（CrewAI 部署，2025 年）指出，增加结构化验证循环将准确率从 10% 提升至 70%。仅一个角色就带来了 7 倍的提升。

### 评审者 vs 验证者

- 评审者是一个审查制品质量的大语言模型。主观的。可能被看似合理的文字所迷惑。
- 验证者是一个运行在制品上的确定性程序。客观的。给出通过/失败并附证据。

两者都要用。评审者发现验证者无法表达的风格问题。验证者捕获评审者无法察觉的缺陷，因为这些缺陷只有在运行时才会显现。

### 反模式

系统中的每个角色都是大语言模型，每个角色的输出都是"看起来没问题"。经典的 MAST 失败模式。至少添加一个通过/失败由代码而非大语言模型决定的验证者。

### 框架映射

- **CrewAI** — `Agent(role, goal, backstory)` 是教科书式的专业化接口。
- **LangGraph** — 节点可以拥有专门的提示；边强制执行流水线。
- **AutoGen** — 在 GroupChat 中使用带有一字名称的角色特定 ConversableAgent。
- **OpenAI Agents SDK** — 角色专业化智能体之间的交接工具。

## 构建

`code/main.py` 实现了一个 4 角色流水线，用于构建一个简单的 Python 函数：

- **规划者**生成规格说明。
- **执行者**生成代码字符串。
- **评审者**（模拟大语言模型）标记明显的问题。
- **验证者**在沙箱（`exec`）中针对测试用例运行生成的代码。

演示运行两次：一次是执行者生成正确代码（评审者和验证者均通过），一次是执行者生成不符合规格的代码（评审者因代码看似合理而漏掉了缺陷，验证者因测试失败而捕获了缺陷）。

运行方式：

```
python3 code/main.py
```

## 使用

`outputs/skill-role-designer.md` 接收一个任务，生成角色名单（3-5 个角色）、每个角色的输入/输出模式以及验证者检查项。在将智能体接入框架之前使用此工具。

## 交付

检查清单：

- **至少一个确定性验证者。** 永远不要全是 LLM。
- **每个角色有明确的输入/输出模式。** 规划者返回的是规格说明，而不是散文；执行者读取该模式。
- **沟通性去幻觉。** 执行者在信息缺失时必须向规划者提问；绝不能自行编造。
- **评审者/验证者顺序。** 先运行评审者（成本低，捕获设计问题），再运行验证者（速度慢，捕获缺陷）。
- **循环预算。** 在升级到人工之前，评审者-执行者修订循环最多 2 轮。

## 练习

1. 运行 `code/main.py` 并观察验证者如何捕获评审者漏掉的缺陷。添加一个静态分析检查（统计 `return` 出现的次数）作为额外的验证者。它能捕获运行时测试漏掉的什么？
2. 添加第 5 个角色："需求分析师"，将用户愿望转化为可供规划者使用的规格说明。哪些沟通性去幻觉请求应该向上流向它？
3. 阅读 MetaGPT 第 3 节（"Agents"）。列出 MetaGPT 5 个角色各自的输入/输出模式。
4. 阅读 ChatDev 的聊天链图（arXiv:2307.07924 图 3）。指出沟通性去幻觉在何处打破了原本可能是无限循环的环路。
5. 普华永道 7 倍的准确率提升来自于验证循环。假设三个任务，在这些任务中添加验证者不会有帮助——即对正确性进行确定性检查不可能或代价过高。

## 关键术语

| 术语 | 人们常说的意思 | 实际含义 |
|------|----------------|------------------------|
| 角色专业化（Role specialization） | "不同的智能体，不同的工作" | 针对规划者/执行者/评审者/验证者角色调整的不同系统提示。 |
| SOP 模式（SOP pattern） | "编码的标准操作流程" | MetaGPT 的框架：每个角色严格的 I/O 模式将团队转变为流水线。 |
| 沟通性去幻觉（Communicative dehallucination） | "先问再编" | ChatDev 模式：执行者在细节缺失时向规划者提问，而非自行编造。 |
| 评审者（Critic） | "LLM 审查者" | 主观的、有见地的审查者。发现风格问题。可能被看似合理的文字迷惑。 |
| 验证者（Verifier） | "确定性检查" | 基于代码的通过/失败。测试运行器、类型检查器、模式验证器。不可被迷惑。 |
| 验证缺口（Verification gap） | "没人检查" | 占 MAST 失败的 21.3%。答案交付时没有经过本可捕获缺陷的检查。 |
| 修订循环（Revision loop） | "评审者打回重做" | 评审者拒绝触发执行者根据反馈重新运行。需要有预算限制。 |
| 全 LLM 反模式（All-LLM anti-pattern） | "看起来没问题" | 每个角色都是 LLM，没有确定性检查。经典的 MAST 失败模式。 |
