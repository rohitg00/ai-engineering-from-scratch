# 角色特化 —— 規劃者、批評者、執行者、查證者

> 2026 年最常見的多代理分解：一個代理規劃、一個執行、一個批評或查證。MetaGPT（arXiv:2308.00352）把它形式化成編碼進角色提示詞的 SOP —— 產品經理、架構師、專案經理、工程師、QA 工程師 —— 遵循 `Code = SOP(Team)`。ChatDev（arXiv:2307.07924）把設計師、程式設計師、審查者、測試者用一條「聊天鏈」串起來，並帶「溝通式去幻覺」（代理明確地去要缺少的細節）。查證者是承重的：Cemri 等人（MAST，arXiv:2503.13657）顯示每一次多代理失敗，都可以追溯到查證缺席或壞掉。PwC 回報，在 CrewAI 中導入結構化驗證迴圈帶來 7 倍的準確率增益（10% → 70%）。

**類型：** 學習 + 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 16 · 04（原語模型）、階段 16 · 05（Supervisor）
**時間：** 約 60 分鐘

## 問題

泛用的多代理系統產出泛用的輸出。群聊裡的三個寫程式代理，會寫出同一份平庸程式碼的三種口味。你可以加更多代理、加更多回合，卻仍然跨不過那道品質門檻。

修法不是更多代理 —— 而是*不同的*代理。指派不同的角色。給批評者一些規劃者沒有的工具。給查證者一份客觀的測試套件。現在這個系統擁有的是「帶接地修正的內部分歧」，而不只是平行猜測。

## 概念

### 四種典範角色

**規劃者。** 讀目標，產出一份步驟清單或一份規格。工具：知識檢索、文件。輸出：結構化計畫。

**執行者。** 一次讀一個計畫步驟，產出那份產物。工具：真正的工作工具（程式碼編譯器、shell、API 客戶端）。輸出：那份產物。

**批評者。** 對照規劃者的意圖去讀執行者的輸出。工具：對產物的唯讀存取、靜態分析。輸出：接受／拒絕，附理由。

**查證者。** 讀那份產物並跑一項決定性檢查。工具：測試執行器、型別檢查器、schema 驗證器。輸出：通過／失敗，附證據。

批評者是主觀的、有立場的，通常基於 LLM。查證者是客觀的、決定性的，通常基於程式碼。它們不是同一個角色。

### MetaGPT 的 SOP 模式

MetaGPT（arXiv:2308.00352）把軟體工程的 SOP 編碼成角色提示詞：

- **產品經理**寫 PRD。
- **架構師**產出系統設計。
- **專案經理**切分任務。
- **工程師**實作。
- **QA 工程師**跑測試。

每個角色都有嚴格的輸入／輸出 schema。角色提示詞說明這個角色*是什麼*，以及它*必須產出什麼*。那條 `Code = SOP(Team)` 的表述 —— 決定性的 SOP 把一群 LLM 變成一條可預期的管線。

### ChatDev 的溝通式去幻覺

ChatDev 加了一個關鍵動作：當執行者需要一項計畫裡沒有的具體細節時，它會在繼續之前明確地去問設計師。這防止了 LLM 那個經典失敗 —— 看似合理地把細節發明出來。

實作方式：角色提示詞裡寫著「當你需要一項沒有被給定的具體資訊時，在產出之前先指名去問相關角色」。

### 為什麼查證者最要緊

Cemri 等人（MAST）追蹤了 1642 次多代理執行失敗。其中 21.3% 是查證缺口 —— 系統出貨了一個沒人檢查過的答案。其餘 79% 也常常追溯到「本來有一項檢查，但它無聲失敗，或根本沒被跑過」。查證是那個承重的角色。

PwC 回報（CrewAI 部署，2025），加入一條結構化的驗證迴圈，把準確率從 10% 拉到 70%。單一個角色帶來 7 倍增益。

### 批評者 vs 查證者

- 批評者是一個審查產物品質的 LLM。主觀。可能被看似合理的散文唬弄。
- 查證者是一支跑在產物上的決定性程式。客觀。給出帶證據的通過／失敗。

兩個都用。批評者抓得到查證者說不出口的品味問題。查證者抓得到批評者看不見的臭蟲，因為那些臭蟲只在執行期才現形。

### 那個反模式

你系統裡每個角色都是 LLM，而每個角色的輸出都是「我看沒問題」。經典的 MAST 失敗模式。至少加一個查證者，它的通過／失敗由程式碼決定，不是由 LLM。

### 框架對映

- **CrewAI** —— `Agent(role, goal, backstory)` 是教科書式的特化表面。

## 動手實作

`code/main.py` 實作一條 4 角色的管線，用來建出一支簡單的 Python 函數：

- **規劃者**產出一份規格。
- **執行者**產出一個程式碼字串。
- **批評者**（LLM 模擬）標出明顯問題。
- **查證者**在沙箱（`exec`）中對一個測試案例跑那段生成的程式碼。

示範跑兩次：一次執行者產出正確的程式碼（批評者與查證者都通過），一次執行者產出偏離規格的程式碼（批評者因為它看起來合理而漏掉那個臭蟲，查證者則因為測試失敗而抓到）。

跑：

```
python3 code/main.py
```

## 框架應用

`outputs/skill-role-designer.md` 接收一項任務，並產出角色名單（3-5 個角色）、每個角色的輸入／輸出 schema，以及那項查證檢查。在把代理接進框架之前用它。

## 產出交付

檢查清單：

- **至少一個決定性查證者。** 絕不要全部都是 LLM。
- **每個角色都有明寫的 I/O schema。** 規劃者回傳一份規格，不是散文；執行者讀那份 schema。
- **溝通式去幻覺。** 資訊缺失時執行者必須去問規劃者；絕不自己發明。
- **批評者／查證者的順序。** 先跑批評者（便宜，抓設計問題），再跑查證者（慢，抓臭蟲）。
- **迴圈預算。** 升級給人之前，最多 2 輪批評者—執行者的修訂。

## 練習

1. 跑 `code/main.py`，觀察查證者如何抓到批評者漏掉的那個臭蟲。加一項靜態分析檢查（數 `return` 出現的次數）當成額外的查證者。它抓到了什麼執行期測試漏掉的東西？
2. 加上第 5 個角色：「需求分析師」，把使用者的願望翻譯成規劃者可用的規格。有哪些溝通式去幻覺的請求應該往上流到它那裡？
3. 讀 MetaGPT 第 3 節（「Agents」）。列出 MetaGPT 那 5 個角色各自的輸入／輸出 schema。
4. 讀 ChatDev 的聊天鏈圖（arXiv:2307.07924 圖 3）。指認出溝通式去幻覺在哪裡打斷了一個否則會無限下去的迴圈。
5. PwC 那 7 倍的準確率增益來自驗證迴圈。假設出三種「加了查證者也幫不上忙」的任務 —— 也就是對正確性做決定性檢查不可能、或代價高到不划算的那些。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 角色特化 | 「不同的代理、不同的工作」 | 為規劃者／執行者／批評者／查證者角色調校過、彼此不同的系統提示詞。 |
| SOP 模式 | 「被編碼的標準作業程序」 | MetaGPT 的框架：每個角色嚴格的 I/O schema，把一個團隊變成一條管線。 |
| 溝通式去幻覺 | 「發明之前先問」 | ChatDev 的模式：執行者在細節缺失時去問規劃者，而不是自己編一個。 |
| 批評者 | 「LLM 審查者」 | 主觀、有立場的審查者。抓品味問題。可能被看似合理的散文唬弄。 |
| 查證者 | 「決定性檢查」 | 基於程式碼的通過／失敗。測試執行器、型別檢查器、schema 驗證器。唬弄不了。 |
| 查證缺口 | 「沒人檢查」 | MAST 失敗中的 21.3%。答案在沒有那項本來抓得到臭蟲的檢查之下就出貨了。 |
| 修訂迴圈 | 「批評者把它退回去」 | 批評者拒絕就觸發執行者帶回饋重跑。需要一份預算。 |
| 全 LLM 反模式 | 「我看沒問題」 | 每個角色都是 LLM，沒有決定性檢查。經典的 MAST 失敗。 |
