# 主管/编排器-工作节点模式

> 一个主导智能体负责规划和委派；专门化的工作节点在独立的上下文环境中并行执行并汇报结果。这是 Anthropic 的 Research 系统（Claude Opus 4 作为主导，Sonnet 4 作为子智能体）背后的模式，在内部研究评估中比单智能体的 Opus 4 提升了 +90.2%。Anthropic 的工程文章指出，BrowseComp 上 80% 的方差可以由 token 用量单独解释——多智能体胜出的主要原因是每个子智能体都获得一个全新的上下文窗口。本节课从基础原语构建主管模式，并涵盖 2026 年生产部署中的工程经验教训。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`）
**前置条件：** 第 16 阶段 · 04（基础模型）
**时间：** ~75 分钟

## 问题

研究是典型单智能体系统会失败的任务。你问"2023 到 2026 年间多智能体系统发生了什么变化？"一个单智能体顺序阅读五篇论文，用它们的文本填满自己一半的上下文，然后不得不对它们一起进行推理。等它读到第五篇时，已经忘记了第一篇。它无法并行化。

主管模式解决了这个问题：一个主导智能体规划搜索，将每个子问题委派给一个工作节点，然后进行综合。每个工作节点针对一个狭窄的问题获得自己的 20 万 token 窗口。主导智能体从不看到原始论文——它只看到工作节点的摘要。

Anthropic 的生产级 Research 系统在内部研究评估中比单 Opus 4 提升了 +90.2%。同一篇文章指出，BrowseComp 上 80% 的方差可以用 *token 用量单独* 解释。每个子智能体拥有全新的上下文是主要的机制。

## 概念

### 模式

```
                 ┌──────────────┐
                 │   主导       │  规划、分解、
                 │  (Opus 4)    │  综合
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ 工作节点1│  │ 工作节点2│  │ 工作节点3│
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
        全新        全新         全新
        上下文      上下文       上下文
```

主导智能体从不阅读原始材料。工作节点之间的工作互相不可见，直到主导智能体进行综合。每个箭头都是一次仅传递狭窄工件的交接。

### 为何胜出

三种机制：

1. **每个子智能体获得全新上下文。** 一个探索"FIPA-ACL 传统"的工作节点不会携带主导智能体规划时花费的 4 万 token。它针对一个问题获得一个 20 万 token 的窗口。
2. **通过提示词实现专门化。** 主导智能体的提示词是"分解并综合"，而不是"做研究"。每个工作节点的提示词很狭窄："找出 X 发生了什么变化。"聚焦的提示词产生聚焦的输出。
3. **并行化。** 工作节点并发运行。挂钟时间大致为 `max(工作节点时间) + 规划 + 综合`，而不是 `sum(工作节点时间)`。

### 工程经验教训（Anthropic 2025）

Anthropic 的文章列出了几条仍然在 2026 年适用的生产经验教训：

- **按查询复杂度调整投入。** 简单查询：一个智能体，3-10 次工具调用。复杂查询：10 个以上的智能体。主导智能体必须自行评估这一点，而不是由调用者来决定。
- **先广泛再深入。** 先分解为广泛的子问题，然后如果答案值得深入，再为每个子问题派生出更多工作节点。
- **彩虹部署。** 智能体是长期运行且带有状态的。传统的蓝绿部署行不通。Anthropic 使用彩虹部署：逐步推出新版本，同时让旧版本自然排空。
- **token 用量占主导。** 多智能体消耗的 token 量大约是单智能体的 15 倍。只有在任务价值能够证明成本合理时才运行它。

### LangGraph 的转向

LangGraph 最初发布了 `langgraph-supervisor` 库，带有一个高级的 `create_supervisor` 辅助函数。2025 年，LangChain 将推荐做法改为通过工具调用直接实现主管模式，因为工具调用在*主管能看到什么*（上下文工程）方面提供了更多控制。该库仍然可用，但文档现在推荐使用工具调用的形式。

### 失败模式

- **主导智能体产生幻觉式的规划。** 如果主导智能体生成的子问题未能真正分解原始问题，工作节点就会在错误的目标上做精确的研究。
- **工作节点过度探索。** 如果没有明确的边界范围，工作节点会偏离分配的子问题，从而污染综合步骤。
- **综合冲突。** 两个工作节点返回矛盾的事实。主导智能体必须要么重新提问（增加一轮），要么明确记录分歧。沉默地选择其中一方是最糟糕的失败方式：用户永远不知道发生了分歧。

### 何时不该使用主管模式

- **顺序性任务。** 如果步骤 2 确实需要步骤 1 的输出，并行化就没有意义。使用流水线（CrewAI Sequential、LangGraph 线性图）。
- **简单查询。** 单智能体处理得更快、更便宜。在派生出工作节点之前，使用主导智能体的"按需投入"检查。
- **严格的确定性要求。** 主管模式使用 LLM 选择的委派。当审计/重放比适应性更重要时，静态图更合适。

## 构建它

`code/main.py` 使用 `threading` 实现了一个包含三个并行工作节点的主管系统。主导智能体将查询分解为子问题，工作节点在各自的子问题上并发运行，然后主导智能体进行综合。没有使用真正的 LLM——工作节点通过脚本模拟抓取和摘要的过程。

关键结构：

- `Lead.plan(query)` 将一个查询分解为 3 个子问题。
- `Worker.run(sub_q)` 返回一个模拟摘要（在生产中可以是任何使用工具的智能体）。
- `Lead.run(query)` 在线程中启动工作节点，等待它们完成，然后进行综合。

运行：

```
python3 code/main.py
```

输出显示规划、带有开始/结束时间戳的并行工作节点追踪，以及最终的综合结果。你可以看到挂钟时间的优势：三个耗时 0.3 秒的工作节点在大约 0.35 秒内完成，而不是 0.9 秒。

## 使用它

`outputs/skill-supervisor-designer.md` 接收用户查询并生成一个主管模式设计：主导系统提示词、工作节点角色、子问题分解规则以及综合模板。在构建新的研究型智能体系统之前使用该文件。

## 交付它

部署主管模式前的检查清单：

- **模型配对。** 主导智能体使用推理级模型（Opus 类、`o3` 类）。工作节点使用更快、更便宜的模型（Sonnet、`o4-mini`）。
- **工作节点超时。** 任何运行时间超过中位数 2 倍的工作节点被终止；主导智能体要么以更窄的范围重新启动，要么在缺少该工作节点的情况下继续。
- **每个工作节点的 token 上限。** 硬性限制（例如，预期的综合输入的 10 倍）防止失控的工作节点超出预算。
- **可观测性。** 追踪主导智能体的规划、每个工作节点的工具调用以及综合结果。这是任何事后调试的基础。
- **彩虹发布。** 有状态的长期运行智能体需要逐步的版本过渡，而不是热切换。

## 练习

1. 运行 `code/main.py`，然后将主导智能体修改为派生出 5 个工作节点而不是 3 个。观察挂钟时间的变化。在这个演示中，工作节点数量达到多少时，派发开销会超过并行节省的时间？
2. 实现一个工作节点超时：终止任何运行超过 0.5 秒的工作节点，并让主导智能体综合剩余的结果。你需要什么样的可观测性才能知道某个工作节点被截断了？
3. 在主导智能体的综合步骤中添加一个冲突检测步骤：如果两个工作节点返回矛盾的答案，主导智能体记录分歧而不是选择其中一个。如何在不调用 LLM 的情况下检测矛盾？
4. 阅读 Anthropic 的 Research 系统工程文章。列出这个玩具演示需要采用哪三种实践才能在生产中运行。
5. 比较 LangGraph 的 `create_supervisor`（旧版）与新的工具调用推荐做法。哪种方式让你对主管能看到什么有更好的控制？为什么 Anthropic 明确只传递子答案而不是原始工作节点上下文给综合步骤？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 主管（Supervisor） | "主导智能体" | 一个编排智能体，负责规划、委派和综合。自身不做具体工作。 |
| 工作节点（Worker） | "子智能体" | 由主管调用的聚焦智能体，具有狭窄的范围和自己的上下文窗口。 |
| 编排器-工作节点（Orchestrator-worker） | "主管模式" | 同一事物，不同名称。2026 年的文献两种说法都有使用。 |
| 全新上下文（Fresh context） | "干净窗口" | 工作节点的上下文从它的系统提示词和分配的问题开始，而不是主导智能体的历史。 |
| 彩虹部署（Rainbow deployment） | "逐步发布" | 长期运行的有状态智能体需要版本化的排空和替换，而不是蓝绿部署。 |
| token 主导（Token dominance） | "上下文就是变量" | 根据 Anthropic 的说法，研究评估中 80% 的方差来自使用的总 token 数量，而非模型选择。 |
| 按需投入（Scale effort） | "根据复杂度匹配合适的智能体数量" | 主导智能体评估查询难度，相应地派生出 1 个或 10 个以上的工作节点。 |
| 综合冲突（Synthesis conflict） | "工作节点意见不一致" | 两个工作节点返回矛盾的事实；主导智能体必须呈现分歧，而不是沉默地选择其中一个。 |
