# 失敗模式 —— MAST、團體迷思、單一栽培、連鎖錯誤

> 2026 年的參考分類法是 **MAST**（Cemri 等人，NeurIPS 2025，arXiv:2503.13657），源自跨 7 套最先進開源多代理系統的 1642 條執行軌跡，顯示**失敗率 41–86.7%**。三個根類別：**規格問題**（41.77%）—— 角色含糊、任務定義不清；**協調失敗**（36.94%）—— 通訊崩解、狀態失步；**查證缺口**（21.30%）—— 缺少驗證、沒有品質檢查。**團體迷思**家族（arXiv:2508.05687）另外加上：單一栽培塌縮（同一個基礎模型 → 相關失敗）、從眾偏誤（代理互相強化彼此的錯誤）、心智理論不足、混合動機的動態，以及連鎖式可靠度失敗。連鎖的例子：重試風暴 —— 一次付款失敗觸發訂單重試，訂單重試又觸發庫存重試，最後把庫存服務淹掉（幾秒內 10 倍負載 —— 需要斷路器）。記憶投毒：某個代理的幻覺進了共享記憶，下游代理把它當成事實；準確率逐漸衰退，讓根因診斷變得很痛苦。**STRATUS**（NeurIPS 2025）回報，透過特化的偵測／診斷／驗證代理，緩解成功率改善 1.5 倍。這一課把失敗模式當成一等的工程標的來處理。

**類型：** 學習
**程式語言：** Python (stdlib)
**先修單元：** 階段 16 · 13（共享記憶）、階段 16 · 14（共識與 BFT）、階段 16 · 15（投票與辯論拓撲）
**時間：** 約 75 分鐘

## 問題

在真實任務上，多代理系統有 41-86.7% 的時間會失敗（Cemri 等人 2025 年跨 7 套開源多代理系統量到的）。那不是「多加幾個代理」就除得掉的錯。這些失敗有結構性成因。MAST 分類法給了你那些類別。這一課把每個類別對映到一套具體的偵測、診斷與緩解模式，好讓那些數字不再看起來像隨口說的。

2026 年的生產實務是把失敗模式當成設計輸入。在你能指著每個 MAST 類別、說出你部署了哪項緩解之前，你的架構都還稱不上「夠好」。

## 概念

### MAST 的各類別

**規格問題（占失敗的 41.77%）。** 代理的任務定義得不夠緊。例子：

- 角色含糊：兩個代理都以為自己是審查者。
- 任務規格不足：使用者要的是某個特定角度，卻只寫了「摘要這個」。
- 成功判準是隱含的：代理判斷不出自己成功了沒有。

緩解：
- 寫明寫的角色契約。每個代理的提示詞都要說它做什麼*以及它不做什麼*。
- 每項任務都有驗收測試。代理開始之前，先定義「完成長什麼樣子」。
- 起飛前的規格檢查：在派工之前，由另一個代理審查任務定義。

**協調失敗（36.94%）。** 通訊或狀態上的崩解。

例子：
- 兩個代理沒有同步就更新共享狀態。
- 訊息在代理之間遺失（佇列失效、逾時）。
- 狀態漂移：代理 A 以為任務完成了；代理 B 還在執行。

緩解：
- 帶版本的共享狀態，配樂觀併發。
- 對關鍵訊息做明確確認（重試到被確認為止）。
- 定期的狀態同步檢查點；及早偵測漂移。

**查證缺口（21.30%）。** 對輸出沒有獨立的檢查。

例子：
- 某個代理宣稱成功；沒有人去查證。
- 一串代理，每一個都信任前一個的輸出。
- 對浮現的組合行為缺少測試覆蓋。

緩解：
- 獨立的查證者代理（第 13 課）。唯讀、具備獨立的來源存取。
- 明寫的交接契約：「A 的輸出必須通過檢查器 C，B 才能開始。」
- 記錄結果供事後分析。

### 團體迷思家族（arXiv:2508.05687）

當代理同質化或互相模仿時，會出現五種相關的失敗：

**單一栽培塌縮。** 同一個基礎模型或訓練資料 → 相關的錯誤。當三個代理共用一個 LLM 時，它們就共用它的幻覺。

**從眾偏誤。** 代理往最大聲或最有自信的同儕靠攏，就算那個同儕是錯的。

**心智理論不足。** 代理模型化不了彼此的信念；協調就垮了（第 18 課）。

**混合動機的動態。** 誘因只部分對齊的代理會往「折衷的中間」漂移，結果誰都不滿意。

**連鎖式可靠度失敗。** 某個元件的錯誤樣式，觸發相依元件的錯誤樣式。

### 連鎖的例子 —— 重試風暴

2026 年一個經典的事故樣式：

```
payment service fails 10% of requests
   ↓
order agent retries payment (exponential backoff but naive)
   ↓
each retry is a new order-inventory check
   ↓
inventory service sees 2x normal load
   ↓
inventory service starts timing out
   ↓
every order retries inventory check
   ↓
inventory service sees 10x normal load
   ↓
cluster goes down
```

修法很經典：**斷路器**。當下游錯誤率超過門檻時，就用快取或預設結果短路掉。再加上每個請求的重試預算上限。

斷路器是少數幾項你可以未經修改就直接從分散式系統借過來的多代理失敗緩解。

### 記憶投毒（再訪）

出自第 13 課：某個代理的幻覺變成共享記憶裡的事實；下游代理在那則被投毒的事實上做推理。用 MAST 的語彙說，這是共享記憶層的一個查證缺口。

漸進式的準確率衰退是那個症狀。你不會拿到一次崩潰；你拿到的是難以追出根因的緩慢漂移。

緩解：僅可附加的日誌、出處、不可寫的查證者。已在第 13 課涵蓋。

### STRATUS —— 專門偵測失敗的特化代理

STRATUS（NeurIPS 2025）回報，當你部署以下三者時，緩解成功率改善 1.5 倍：

- **偵測代理。** 盯著症狀樣式（高度不一致、重試暴增、準確率漂移）。
- **診斷代理。** 給定症狀，從 MAST 分類法推斷可能的根因。
- **驗證代理。** 在套用某項緩解之後，檢查症狀是否消除。

這就是把 SRE 式的事故回應，套用到代理系統上。這三種角色都可以是帶特化提示詞的 LLM 代理。

### 那份失敗模式稽核

2026 年的最佳實務是每年（或每個重大版本）做一次失敗模式稽核：

1. **軌跡取樣。** 收集約 1000 條真實執行軌跡。
2. **分類。** 對每條軌跡的失敗，對映到 MAST + 團體迷思的類別。
3. **算出逐類別的失敗率。** 你的系統由哪些類別主導？
4. **替緩解排序。** 哪一項修法能消除最多失敗？
5. **挑 2-3 項緩解。** 實作；下一季再稽核一次。

紀律比具體選擇更重要。沒有稽核，失敗就融進雜訊裡，永遠不會被系統性地處理。

### 當系統無聲地失敗

最危險的失敗類別是無聲的正確性失敗。一個大聲失敗（崩潰、例外、警示）的系統可以被監控。一個產出看似合理卻錯誤輸出的系統，用例外日誌偵測不到。這就是為什麼查證缺口雖然只占 21.30% 的數量，每次失敗的成本卻最高。

要投資在：
- 基於抽樣的人工審查。
- 黃金資料集的回歸測試。
- 對重要輸出做跨代理的交叉檢查。

### 失敗 vs 慢性失敗

有些失敗是立即的；有些是慢性的。立即失敗（逾時、schema 不符、認證錯誤）偵測起來便宜。慢性失敗（記憶投毒、單一栽培漂移、角色含糊）偵測與預防起來都很貴。

2026 年的工程做法：把慢性失敗的代理指標儀器化，好讓你在漂移變成可見錯誤之前就抓到它。一致率、重試率、輸出長度分布，以及連續代理版本之間的編輯距離，都是有用的代理指標。

## 動手實作

`code/main.py` 實作了：

- `FailureTaxonomy` —— 把模擬事故分類到 MAST + 團體迷思的類別。
- `CircuitBreaker` —— 經典模式；錯誤率超過門檻就開路。
- `RetryStormSimulator` —— 展示那個連鎖失敗；可切換斷路器開／關。
- `DetectionAgent` —— 腳本化的 STRATUS 式症狀比對器。

跑：

```
python3 code/main.py
```

預期輸出：
- 沒有斷路器的重試風暴：庫存錯誤炸開（模擬）。
- 有斷路器：在門檻處封頂；提供降級模式的回應。
- 偵測代理標出那個樣式並說出 MAST 的類別。

`outputs/skill-mast-auditor.md` 對一套多代理系統跑一次 MAST 式的失敗模式稽核。軌跡 → 分類 → 緩解排序。

## 產出交付

生產環境的失敗模式紀律：

- **每季做一次 MAST 稽核。** 不是每年。類別會隨你的系統成長而移動。
- **到處都放斷路器。** 每一次對任何相依服務的對外呼叫。預設在 5-10% 錯誤率開路。
- **黃金資料集。** 小、高品質、人工稽核過。每週對它們做回歸測試。
- **STRATUS 三人組。** 偵測 + 診斷 + 驗證代理監控生產環境。先只從偵測代理開始；症狀變吵時再加診斷。
- **失敗預算。** 依類別替失敗率訂明確的 SLO。超出預算就觸發一次「停止出貨」的對話。

## 練習

1. 跑 `code/main.py`。確認斷路器把重試風暴封頂。改變失敗門檻並觀察那個取捨。
2. 實作一個**慢性失敗的代理指標**：3 個平行代理之間的一致率。當它急遽下降時觸發警示。透過逐步讓代理輸出相關化來模擬一次單一栽培漂移。
3. 讀 Cemri 等人（arXiv:2503.13657）。挑他們 7 套多代理系統中的一套，對映出它前 3 名的失敗類別。這些跟 MAST 所預測的相比如何？
4. 讀團體迷思那篇論文（arXiv:2508.05687）。指認出那五種樣式中，在生產環境最難偵測的是哪一種。提出一項代理指標。
5. 替一套你熟悉的特定多代理系統，設計一組 STRATUS 式的偵測—診斷—驗證三人組。偵測要盯哪些症狀？診斷會建議哪些緩解？驗證怎麼確認它們有效？
