# 并行 / 群智能 / 网络化架构

> 与监督者模式对比：没有中央决策者。智能体读取共享的事件总线，异步领取工作，将结果写回。LangGraph 明确支持"群智能架构"，适用于去中心化、动态的环境。Matrix（arXiv:2511.21686）将控制流和数据流都表示为通过分布式队列传输的序列化消息，以消除编排器瓶颈。其中的权衡很明确：用确定性和可追踪性换取可扩展性。群智能适用于具有许多独立子问题的任务；不适用于需要单一连贯计划的的任务。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`，`queue`）
**前置条件：** 阶段 16 · 05（监督者模式），阶段 16 · 04（原始模型）
**时间：** 约 75 分钟

## 问题

监督者模式可以扩展到几个工作节点。但数百个呢？监督者本身就成了瓶颈：每个关于"谁做什么"的决策都通过一个智能体漏斗传递。一个缓慢的计划步骤就会拖垮整个系统。

群智能架构颠覆了这种设计。工作节点不是由中央规划器调度，而是从共享队列中领取工作。"协调"被内建到事件总线的语义中。没有编排器；系统可以一直扩展，直到队列成为瓶颈。

## 概念

### 形态

```
                ┌──── 共享队列 ────┐
                │                  │
       ┌────────┼────────┐  ◄──────┴───┐
       ▼        ▼        ▼             │
     工作节点  工作节点  工作节点   工作节点
       A        B        C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
             结果池
```

没有编排器。每个工作节点重复执行：拉取任务、处理、写入结果（并可选择性地将后续任务入队）。

### 何时适合使用群智能

- **大量独立任务。** 爬取、转换、分类。任务之间互不依赖。
- **时长不固定的工作。** 如果某些任务耗时 100 毫秒，而另一些耗时 10 秒，群智能会自动平衡负载——快的工作节点会领取下一个任务。监督者则必须预估任务时长。
- **吞吐量优先于确定性。** 你关心的是总完成时间，而不是严格的顺序。

### 何时群智能失效

- **有顺序的工作流。** 如果步骤 3 需要步骤 2 的输出，群智能可能会在步骤 2 完成之前就启动步骤 3。
- **需要全局计划的任务。** 复杂的研究问题需要规划器。一群研究人员产生的是独立的事实，而不是连贯的报告。
- **调试。** 没有中央日志且工作异步进行，复现一个 bug 的成本很高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年的一篇论文，它将群智能推向了自然的结论：控制流和数据流都是分布式队列上的序列化消息。没有中央协调器。容错性来自消息的持久性。可扩展性是消息代理的问题，而不是系统的问题。

贡献：一种编程模型，其中多智能体协调变成了"这个智能体订阅哪个消息主题？"而不是"监督者下一步选择哪个智能体？"这使得系统看起来像一个发布/订阅事件网格。

### LangGraph 的群智能架构

LangGraph 2025 年的文档将"群智能架构"明确描述为多智能体模式之一：智能体是节点，但边构成了一个有向图，包含循环，并且任何节点都可以从池中被激活。工作节点根据条件从可用工作中选择，而不是由监督者分配。

### 故障模式：饥饿与热点

如果所有工作节点都拉取最快的可用任务，长时间运行的任务永远不会被选中，直到它们成为唯一剩下的任务。经典的队列饥饿问题。

缓解措施：
- 带显式老化机制的优先级队列（等待时间越长优先级越高）。
- 工作节点专化：某些工作节点只处理"长"任务。
- 背压：限制进入队列的快速任务数量。

### 基于内容的路由关联

群智能与基于内容的路由（第 22 课）自然结合。不是使用通用队列，而是每种消息类型对应一个队列。专化工作节点只订阅自己类型的队列。这是能够扩展到数千个智能体的消息总线架构的基础。

## 构建

`code/main.py` 实现了一个包含 4 个工作线程从共享 `queue.Queue` 拉取任务的群智能。任务具有不同的时长（有的快，有的慢）。演示对比了：

- **顺序基线：** 一个工作节点串行处理所有任务。
- **固定分配：** 每个任务预先分配给特定工作节点（监督者风格）。
- **群智能：** 工作节点从共享队列拉取任务。

群智能自动平衡负载；固定分配在分配的任务较慢时会使快的工作节点闲置。

运行：

```
python3 code/main.py
```

输出显示每个工作节点的任务计数（群智能分配不均匀但最优）和挂钟时间。

## 使用

`outputs/skill-swarm-fit.md` 评估一个任务应该使用群智能还是监督者。输入项：任务独立性、时长方差、排序需求、可调试性需求。

## 交付

检查清单：

- **带老化机制的优先级队列。** 防止长任务饥饿。
- **工作节点幂等性。** 如果某个工作节点中途崩溃，一个任务可能被多次拉取。工作节点必须是幂等的。
- **持久化队列。** 生产环境使用 Kafka、Redis Streams 或数据库支持的队列。`queue.Queue` 仅在内存中。
- **每个任务的可观测性。** 每个任务都有跟踪 ID；每个工作节点在开始/结束时都记录该 ID。
- **背压。** 如果队列增长速度快于工作节点的处理速度，则需要减慢生产者。

## 练习

1. 运行 `code/main.py`。在可变时长工作负载下，群智能比顺序执行快多少？比固定分配快多少？
2. 添加一个优先级队列变体（使用 `queue.PriorityQueue`）。按任务的"重要性"字段分配优先级。观察低优先级任务在持续负载下是否会出现饥饿。
3. 实现一个热点检测器：当某个工作节点处理的任务量是慢速工作节点的 3 倍以上时记录日志。这表明任务时长分布有什么问题？
4. 阅读 Matrix 论文（arXiv:2511.21686）的摘要和第 3 节。识别 Matrix 所接受的一个具体权衡（可扩展性提升）和所放弃的一个权衡（可追踪性、确定性）。
5. 将群智能演示改为使用包含 `(task_type, payload)` 元组的 `queue.Queue`，工作节点只订阅特定类型。当任务异构时，什么样的路由规则是有意义的？

## 关键词

| 术语 | 表面对话 | 实际含义 |
|------|----------|----------|
| 群智能架构 | "去中心化智能体" | 工作节点从共享队列拉取任务；没有中央编排器。 |
| 事件总线 | "智能体订阅主题" | 按类型或内容将任务路由到工作节点的消息代理。 |
| 饥饿 | "任务永远不运行" | 低优先级任务始终无法被选中，因为更高优先级的工作持续到达。 |
| 热点 | "某个工作节点被淹没" | 负载不均衡，一个工作节点承担了大部分任务。 |
| 背压 | "减慢生产者的速度" | 当队列满时向上游发出信号以停止生产的机制。 |
| 幂等工作节点 | "重复执行也安全" | 一个任务被处理两次产生相同的结果。因为工作节点可能中途崩溃，所以需要幂等性。 |
| 持久化队列 | "崩溃后不丢失数据" | 由磁盘或复制存储支持的队列；工作节点崩溃时任务不会丢失。 |
| Matrix 框架 | "全消息传递群智能" | 数据和控制流都是分布式队列上的序列化消息。 |
