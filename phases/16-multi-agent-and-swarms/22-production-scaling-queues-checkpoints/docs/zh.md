# 生产级扩展——队列、检查点与持久化

> 将多智能体系统扩展到数千个并发运行，需要**持久化执行**。LangGraph 运行时在每个超级步骤后写入一个由 `thread_id` 键定的检查点（默认使用 Postgres）；工作进程崩溃后释放租约，由另一个工作进程接管恢复。智能体可以无限期休眠等待人工输入。**MegaAgent**（arXiv:2408.09955）为每个智能体维护了一个生产者-消费者队列，包含三种状态（Idle / Processing / Response）以及两层协调（组内聊天 + 组间管理聊天）。**Fiber/async** 优于 thread-per-job 模型用于 LLM 流式传输：线程在 99% 的时间里闲置等待令牌，而 fiber 在 I/O 上协作式让出执行权。反面观点：Ashpreet Bedi 的"扩展智能体软件"一文主张使用 **FastAPI + Postgres + 除此之外什么都不加**，直到负载证明确实需要更多——简单的架构往往比预期走得更远。本课程将构建一个持久化检查点日志、一个带状态转换的每智能体工作队列、一个 async-vs-thread 演示，并落地"从简开始"的实用法则。

**类型：** 学习 + 构建
**语言：** Python（stdlib、`asyncio`、`sqlite3`）
**前置条件：** 阶段 16 · 09（并行群体网络）、阶段 16 · 13（共享内存）
**时长：** ~75 分钟

## 问题

一个原型多智能体系统可以在单台笔记本电脑上用内存事件循环配合三个智能体运行。当你要把它推向生产时：

- 智能体有时会运行数小时（长时间研究、人工参与等待）。
- 工作进程崩溃。重启会丢失状态。
- 峰值负载是平均值的 10 倍；你需要水平扩展。
- 用户按智能体运行次数付费；你需要精确一次语义来进行计费。

内存事件循环无法满足以上任何一条。你需要在底层构建一个持久化执行层。截至 2026 年的主流可选方案有：

1. 带检查点的工作流引擎（Temporal、LangGraph 运行时）。
2. 带状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. Actor 模型框架（MegaAgent 的每智能体生产者-消费者模型）。
4. 手写 FastAPI + Postgres（Bedi 的主张）。

本课程将构建每个方案的微型实现。

## 概念

### 持久化执行，该模式

持久化执行引擎在每个"步骤"（在 LangGraph 的术语中称为超级步骤）之后持久保存完整的程序状态。崩溃时：

```
工作进程在步骤中间崩溃
  -> 租约超时
  -> 另一个工作进程接管该 thread_id
  -> 从最后一个检查点恢复
  -> 不产生重复的副作用
```

这需要满足以下条件：

- **可序列化的状态。** 所有智能体状态必须可持久化。持有实时数据库连接的函数闭包无法幸存。
- **确定性恢复。** 给定相同的状态和相同的输入，智能体必须产生相同的动作（或将 LLM 调用委托给外部确定性预言机）。
- **幂等的副作用。** 外部调用（工具调用、支付）必须是幂等的，或者使用去重键。

LangGraph 在每个超级步骤后写入检查点；Temporal 在每个活动后写入；Restate 使用事件溯源日志。三者都实现了相同的模式。

### LangGraph 运行时

每个智能体都有一个 `thread_id`；状态是一个类型化字典；每个超级步骤向检查点表中写入一行。恢复时，运行时从最后一个检查点回放，而不是从头开始。智能体可以 `interrupt()` 等待人工输入；运行时持久化状态并释放工作进程。当输入到达时，任何工作进程都可以恢复执行。

这是 2026 年 4 月的参考生产设计方案。

### MegaAgent 的每智能体队列

arXiv:2408.09955 描述了一个规模实验：在一个集群中运行数千个并发智能体。架构如下：

```
智能体 i:
  状态 ∈ {Idle, Processing, Response}
  入队列   <- 发往智能体 i 的消息
  出队列   -> 回复 + 副作用

协调器:
  组内聊天  （同一组内的智能体）
  组间管理聊天  （高层路由）
```

两层协调使得组内对话密集进行，而组间对话保持稀疏——这种模式用于在数千个智能体规模下保持成本线性增长。

### Async vs thread-per-job

LLM 调用是 I/O 密集型的。等待下一个令牌的线程在 99% 的时间里处于空闲状态。每个线程大约消耗 1MB RAM；在 10,000 个并发调用下，仅栈空间就需要 10GB。

Fiber（Python `asyncio`、Go goroutine、Rust `tokio`）在 I/O 上协作式让出执行权。同样的 10,000 个调用可以轻松容纳在一个进程中。在 LLM 智能体规模下，async 不是一种优化——它就是架构本身。

例外：CPU 密集型的后处理（嵌入、分词器技巧）仍然需要线程或进程。将你的 I/O 层与 CPU 层分开。

### Bedi 的反面观点

"扩展智能体软件"（Ashpreet Bedi，2026）认为大多数团队在测量负载之前就已经过度设计了。务实的默认方案：

- FastAPI + Postgres。
- 每次智能体运行是一行记录；使用乐观并发就地更新状态。
- 通过 `pg_notify` 或简单的 Celery 工作进程处理后台任务。
- 在应用代码中实现重试策略。

对于可控任务上约 100 个以下并发智能体运行的负载，这通常就足够了。当你测量到它确实不够用时再升级。

规则：只有在遇到简单架构无法解决的具体问题时，才采用持久化执行框架。过早采用会在最终无法带来收益的仪式性工作上浪费大量时间。

### 精确一次语义

对于付费的智能体运行，你需要"精确一次有效"（至少一次投递 + 幂等消费者）。关键工程手法：

- **每次运行的去重键。** 将其包含在每个副作用调用中。
- **发件箱模式。** 副作用先写入一个表，然后由单独的处理进程执行。两个步骤都是幂等的。
- **补偿事务。** 当副作用成功但其跟踪写入失败时，调度一个补偿操作。

这些都是数据库工程模式，而非 LLM 特有的。LLM 带来的额外代价仅在于 LLM 调用速度慢；其余都是标准的分布式系统问题。

### 彩虹部署

Anthropic 的多智能体研究系统使用了"彩虹部署"：同时运行多个版本的智能体运行时，这样长时间运行的智能体就不必在每次代码部署时被杀死。在一部分流量上运行新版本的灰度测试；在旧版本的智能体完成任务后将其退役。

这对于长时间运行的有状态系统是标准做法；2026 年的调整在于智能体可能存活数小时，因此部署周期必须适应这一点。

### 经典生产检查清单

- 持久化状态（检查点、快照、或发件箱 + 可回放日志）。
- 幂等的副作用。
- 用于 LLM 调用的异步 I/O 层。
- 带去重的至少一次投递。
- 有状态工作负载的彩虹/灰度部署。
- 可观测性：每智能体追踪、超级步骤审计、重试计数器。

## 构建

`code/main.py` 实现了：

- `CheckpointStore`——基于 SQLite 的检查点日志，使用 thread-id 作为键。每个超级步骤追加一行。
- `run_with_checkpoint(agent, thread_id)`——模拟运行中途崩溃；第二个工作进程从上一个检查点恢复。
- `AgentQueue`——每智能体的 Idle / Processing / Response 状态机，附带一个小型工作队列。
- `demo_async_vs_threads()`——通过 asyncio 和线程分别运行 500 个并发的模拟"LLM 调用"；报告挂钟时间和峰值内存（近似值）。

运行：

```
python3 code/main.py
```

预期输出：检查点恢复在模拟崩溃后成功恢复；async 版本在 < 1 秒内处理 500 个并发调用；线程版本需要数秒，并且每个并发单元消耗的内存高出数个数量级。

## 交付

经典生产加固方案：

- **从简开始（Bedi 法则）。** 使用 FastAPI + Postgres，直到你测量到它确实不够用。
- **在优化之前先做好监控。** 每次运行的延迟直方图、每步骤耗时、重试次数、失败分类。
- **对副作用使用发件箱模式。** 尤其是支付和外部 API 调用。
- **彩虹部署。** 绝不在部署期间杀死正在执行的智能体运行。
- **在遇到特定问题时**采用持久化执行引擎（Temporal / LangGraph / Restate）：需要数小时的人工参与等待、跨区域协调、复杂的重试/补偿策略。
- **I/O 层使用异步。** 仅对 CPU 密集型后处理使用线程。

## 练习

1. 运行 `code/main.py`。确认检查点恢复正常工作；测量 async 与线程的并发性能差异。
2. 实现一个**发件箱**表：每次工具调用先写入发件箱，然后由单独的 goroutine/任务执行。通过运行两次工具调用来验证幂等性。
3. 模拟一个**彩虹部署**：两个并发运行的运行时版本；将新 thread_id 的一半路由到每个版本；确认旧版本上正在执行的线程不会被中断。
4. 阅读 LangGraph 运行时文档（下方链接）。确定该运行时的哪些功能在手写 FastAPI + Postgres 版本中最难复现。这是否是采用的理由，还是可以推迟决定？
5. 阅读 MegaAgent（arXiv:2408.09955）第 3 节。其中明确描述了两层协调（组内聊天 + 组间管理聊天）。画出如何将其映射到具有两个队列家族的消息队列中。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 持久化执行 (Durable execution) | "持久化程序状态" | 引擎在每个超级步骤后写入状态；崩溃恢复是确定性的。 |
| 超级步骤 (Super-step) | "事务边界" | 检查点之间的工作单元。LangGraph 术语。 |
| thread_id | "智能体运行标识符" | 绑定检查点和恢复逻辑的键。 |
| 幂等性 (Idempotency) | "可安全重试" | 重复执行副作用产生与执行一次相同的结果。 |
| 发件箱模式 (Outbox pattern) | "解耦副作用" | 将意图写入一个表；由单独的执行器执行并标记完成。 |
| 至少一次投递 (At-least-once delivery) | "可能存在重复" | 消息队列语义；去重键使消费者达到有效一次的效果。 |
| 彩虹部署 (Rainbow deploy) | "版本重叠" | 在长时间运行的工作负载期间同时运行多个运行时版本。 |
| 异步 fiber (Async fiber) | "协作式让出" | 用户态并发；对于 I/O 密集型负载，比线程成本更低。 |
| 检查点 (Checkpoint) | "状态快照" | 在超级步骤边界序列化的状态；恢复的关键。 |
