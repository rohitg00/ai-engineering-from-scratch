给定两个需要互操作的系统，生成 A2A 集成计划：Agent Card 内容、任务模式、认证、传输模式。

生成以下内容：

1. **Agent Card**。名称、版本、技能、端点、支持的模态（文本、结构化、图像、音频、视频）、protocol_version、认证声明。
2. **每技能任务模式**。输入 JSON schema + 工件 JSON schema。要明确——客户端将进行验证。
3. **认证选择**。Bearer 令牌（OAuth2 或不透明）、mTLS 或签名请求。根据威胁模型（公共互联网、VPC、混合）说明理由。
4. **传输模式**。轮询 vs SSE 流式传输 vs webhook 回调。长时间运行或进度密集型任务使用流式传输；短任务使用轮询。
5. **速率限制**。每客户端和每任务限制。防止滥用。
6. **幂等性**。重复 `POST /tasks` 请求的策略（客户端侧任务键、服务端侧去重）。
7. **故障处理**。超出 `failed` 的任务状态（可重试 vs 致命）、死信策略、错误工件模式。
8. **MCP vs A2A 拆分**。如果远程智能体内部使用 MCP，说明哪些工具被暴露 vs 保持内部。

硬性拒绝：

- 没有声明协议版本的 Agent Card。
- 当用例需要结构时使用自由格式文本的任务模式。
- 公共互联网部署上的 auth=none。

拒绝规则：

- 如果两个智能体在同一进程中运行，拒绝 A2A 并推荐直接的 Python/JS 调用。A2A 是用于跨系统边界的。
- 如果延迟要求低于 100ms 往返时间，拒绝 A2A 并推荐带有共享模式的直接 RPC。
- 如果远程智能体未声明 Agent Card，拒绝集成并推荐先发布一个。

输出：一页集成简报。以 Agent Card JSON 内嵌结尾，以便工程团队可直接放入 `/.well-known/agent.json`。
