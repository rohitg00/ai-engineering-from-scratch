# 层级架构及其失败模式

> 层级架构即主管嵌套：主管管理者管理子主管，子主管管理工作者。CrewAI 的 `Process.hierarchical` 是教科书式的实现：通过 `manager_llm` 动态分派任务并验证输出。LangGraph 的等价实现是 `create_supervisor(create_supervisor(...))`。当任务本身就是真实的组织架构图时，这是一种自然的模式。但它也是最容易陷入管理循环的模式——主管管理者分派工作不当、错误解读下级输出，或无法达成共识。顺序架构通常比它更可靠。

**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置条件：** 第16阶段 · 05（主管模式）
**时长：** 约60分钟

## 问题

一旦掌握了主管模式，自然而然的下一步就是"如果工作者本身也是主管呢？"团队之下有子团队；公司中有部门套部门。层级架构正是这种结构的映射。

问题在于：LLM 管理者与人类管理者不同。人类管理者对其下属所掌握的知识有稳定的先验判断。而 LLM 管理者每次都会根据当前上下文重新对整个组织架构进行推理。上下文稍有偏移，整棵树就会错误分配工作。

## 概念

### 结构

```
                 Manager（主管）
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
     Sub-Mgr A（子主管A）  Sub-Mgr B（子主管B）
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点负责规划、分派和综合。只有叶节点执行实际工作。

### 优势场景

- **清晰的组织映射。** 如果实际任务具有部门性质（"法务审阅文档、财务审阅文档、工程审阅文档，然后汇总上报高管"），层级结构是明确的。
- **局部汇总。** 每个子主管在将团队输出呈报给顶层主管之前先进行汇总。顶层主管看到的是三个子主管的汇总，而不是十五个工作者的原始输出。

### 失败场景

以下是2026年的事后分析反复发现的三种失败模式：

1. **任务分派错误。** 主管读取目标后，凭空想象出一种任务分解方式，并将其分派给错误的子主管。由于子主管会忠实地执行被指派的任务，该错误只有在顶层汇总时才会暴露——距离人类能够发现它的位置已经隔了一层。
2. **输出误读。** 子主管返回"无法验证主张X"。顶层主管将其概括为"主张X未确认"。每个层级都会发生含义漂移。
3. **共识循环。** 两个子主管意见不一；顶层主管要求他们协调；他们重新向下分派；工作者重新执行；子主管返回略有不同的答案；如此循环。CrewAI 的 `Process.hierarchical` 通过步数上限来防止这种情况，但这个上限本身也成了一个超参数。

### 决策性问题

顺序架构（线性流水线）与层级架构：你的任务真的有独立的子团队，还是它只是一个伪装成树状结构的线性流程？如果是后者，使用顺序架构；如果是前者，使用层级架构，但要制定明确的协调规则。

### CrewAI 的实现

`Process.hierarchical` 将 manager LLM 置于专业 crew 之上。管理者负责：

- 接收顶层任务，
- 向 crew 分配子任务，
- 评估 crew 的输出，
- 决定是接受、重新分派还是迭代。

文档：https://docs.crewai.com/en/introduction（在"核心概念"下查找"层级流程"）。

### LangGraph 的实现

LangGraph 使用嵌套的 `create_supervisor` 调用。内部 supervisor 拥有自己的图；外部 supervisor 将内部图视为一个不透明节点。这在调试方面比 CrewAI 更清晰（可以分别逐步调试每个图），但在表达树的动态重构方面则更困难。

参考：https://reference.langchain.com/python/langgraph-supervisor。

## 构建

`code/main.py` 运行一个3层层级结构：

- 顶层主管：将任务拆分为"工程"和"法务"两个分支，
- 工程子主管：拆分为"前端"和"后端"工作者，
- 法务子主管：一个工作者。

演示对比了"顺利路径"（所有人意见一致）与**扰动路径**——顶层主管的分解中将"法务"误标为"财务"，并观察错误的级联效应：子主管忠实地执行财务工作，顶层综合器报告财务结果，原始的法务问题无人回答。

运行：

```
python3 code/main.py
```

输出会展示两条路径，并清晰地对比"被要求做什么"与"实际交付了什么"。

## 使用

`outputs/skill-hierarchy-fitness.md` 评估给定任务应使用层级架构、顺序架构还是扁平主管模式。输入：任务描述、组织架构、协调预算。输出：模式推荐及需要防范的具体失败模式。

## 交付

如果你要交付层级架构：

- **树深度限制为2层。** 三层就已经会将大多数错误隐藏在可观测性之外。
- **明确的协调预算。** 设置顶层主管必须做出决策前的最大轮数。通常为2轮。
- **每次综合都要有溯源。** 每个节点的汇总必须注明由哪些叶节点的输出产生。
- **对分解漂移发出警报。** 记录管理者每一步的分解结果；与用户查询进行对比。如果分解结果不再覆盖查询内容，则触发警报。

## 练习

1. 运行 `code/main.py`，比较顺利路径与扰动路径。经过多少层管理者转手后，顶层输出才会与用户的问题完全偏离？
2. 添加第三层（顶层 → 子层 → 子子层 → 工作者）。测量随着深度增加，扰动路径自我纠正与完全偏离的频率变化。
3. 在每个子主管下实现一个"金丝雀"工作者，它始终被问及原始的用户问题（不做任何修改）。利用金丝雀的回答检测分解漂移。当金丝雀的回答与综合答案不一致时，管理者应如何应对？
4. 阅读 CrewAI 的 `Process.hierarchical` 文档。找出 CrewAI 应用的一个具体防护措施（步数上限、manager_llm 约束），并描述它针对的是哪种失败模式。
5. 比较嵌套的 LangGraph supervisor 与 CrewAI 的层级架构。哪一种更容易检测协调循环？

## 关键术语

| 术语 | 人们说的意思 | 实际含义 |
|------|--------------|----------|
| 层级架构 (Hierarchical) | "组织架构图模式" | 主管之上还有主管；只有叶节点执行实际工作。 |
| 主管 LLM (Manager LLM) | "老板" | 在内部节点上进行分解、分派和验证的 LLM。 |
| 分解漂移 (Decomposition drift) | "老板跑偏了" | 顶层主管的任务拆分不再覆盖原始问题。 |
| 协调循环 (Reconciliation loop) | "无休止的会议" | 子主管意见不一；顶层重新分派；工作者重新执行；循环直至预算耗尽。 |
| 深度2上限 (Depth-2 ceiling) | "不要超过2层深度" | 经验法则：3层及以上会导致可观测性崩溃。 |
| 金丝雀问题 (Canary question) | "每一层的地面真相" | 始终以原始查询（不做修改）询问一个工作者，用于检测漂移。 |
| 溯源链 (Provenance chain) | "谁说了什么" | 从每次综合回溯到产生它的叶节点输出。 |
