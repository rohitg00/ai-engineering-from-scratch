# 階層式架構與它的失敗模式

> 階層式就是 supervisor 的巢狀化。經理代理管子經理，子經理管 worker。CrewAI 的 `Process.hierarchical` 是教科書版本：一個 `manager_llm` 動態委派任務並驗證輸出。LangGraph 的等價物是 `create_supervisor(create_supervisor(...))`。當任務真的就是一張組織圖時，這是自然的模式。它也是最容易塌陷成「管理階層繞圈」的模式 —— 經理代理指派工作指派得很差、誤讀子輸出，或達不成共識。循序式往往勝過它。

**類型：** 學習 + 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 16 · 05（Supervisor 模式）
**時間：** 約 60 分鐘

## 問題

一旦 supervisor 模式想通了，自然的下一步就是「如果那些 worker 自己也是 supervisor 呢？」團隊有子團隊；公司有部門的部門。階層式架構把那件事鏡射過來。

問題在於：LLM 經理跟人類經理不是同一回事。人類經理對「自己的下屬知道什麼」有穩定的先驗。LLM 經理則在每一輪都從它脈絡裡的任何東西，把那個組織重新推理一遍。那份脈絡稍微一漂移，整棵樹就把工作分派錯。

## 概念

### 那個形狀

```
                 Manager
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       Sub-Mgr A         Sub-Mgr B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每個內部節點都負責規劃、委派與綜合。只有葉子在做事。

### 它發光的地方

- **清楚的組織對映。** 若真實任務就是部門式的（「法務審這份文件、財務審這份文件、工程審這份文件，然後替高層做摘要」），那個階層就是明寫的。
- **局部摘要。** 每個子經理在頂層經理看到之前，先把自己團隊的輸出綜合起來。頂層經理看到的是三份子經理摘要，不是十五份 worker 輸出。

### 它崩掉的地方

2026 年的事後檢討一再發現三種失敗模式：

1. **任務指派錯誤。** 經理讀了目標、幻覺出一份分解，然後委派給錯的子經理。因為子經理乖乖地照著拿到的東西做，這個錯誤要到頂層綜合時才浮出來 —— 離人類本來抓得到的那個點，已經隔了一層。
2. **輸出誤讀。** 子經理回傳「無法查證主張 X」。頂層經理摘要成「主張 X 未被確認」。意義在每一層都在漂移。
3. **共識迴圈。** 兩個子經理意見不合；頂層經理要它們調和；它們往下重新委派；worker 重跑；子經理回傳略有不同的答案；繞圈。CrewAI 的 `Process.hierarchical` 用步數限制防這件事，但那個限制本身現在變成一個超參數。

### 那個決定性的問題

循序式（線性管線）對上階層式：你的任務真的有獨立的子團隊，還是那只是一條假裝成樹的線性流程？若是後者，用循序式。若是前者，用階層式，但要替明寫的調和規則編好預算。

### 角色制框架的實作

CrewAI 的 `Process.hierarchical` 在專家 crew 之上接一個經理 LLM。那位經理會：

- 接收頂層任務，
- 把子任務指派給 crew，
- 評估 crew 的輸出，
- 決定要接受、重新委派，還是迭代。

文件：https://docs.crewai.com/en/introduction（在 Core Concepts 底下找「Hierarchical Process」）。

### 圖式框架的實作

LangGraph 用巢狀的 `create_supervisor` 呼叫。內層的 supervisor 有它自己的圖；外層的 supervisor 把內層的圖當成一個不透明節點。這在除錯上比 CrewAI 乾淨（你可以分別逐步走過每張圖），但要表達「動態重塑那棵樹」就比較難。

參考：https://reference.langchain.com/python/langgraph-supervisor。

## 動手實作

`code/main.py` 跑一個 3 層的階層：

- 頂層經理：把任務切成「工程」與「法務」兩條分支，
- 工程子經理：切成「前端」與「後端」兩個 worker，
- 法務子經理：一個 worker。

示範把順利路徑（大家意見一致）對照一條**被擾動的路徑**：頂層經理的分解把「法務」誤標成「財務」，然後看著錯誤連鎖下去 —— 子經理乖乖地做了財務的工作、頂層綜合者回報財務的發現，而原本那個法務問題根本沒被回答。

跑：

```
python3 code/main.py
```

輸出顯示兩條路徑，並清楚並排「被問了什麼」對照「交付了什麼」。

## 框架應用

`outputs/skill-hierarchy-fitness.md` 評估一項給定任務該用階層式、循序式，還是扁平的 supervisor。輸入：任務描述、組織結構、調和預算。輸出：模式建議，附上要防範的具體失敗模式。

## 產出交付

若你要出貨階層式：

- **樹深上限設 2。** 三層就已經把大多數錯誤藏到可觀測性之外了。
- **明寫的調和預算。** 設定頂層經理必須拍板前的最大回合數。通常是 2。
- **每一次綜合都要有出處。** 每個節點的摘要都必須引用是哪些葉子輸出產生了它。
- **對分解漂移發警示。** 逐步記錄經理的分解；拿它跟使用者查詢做 diff。若那份分解不再涵蓋該查詢，就發警示。

## 練習

1. 跑 `code/main.py`，比較順利與被擾動兩條路徑。要經過幾層經理交接，頂層輸出才會完全偏離使用者的問題？
2. 加上第三層（頂層 → 子 → 子子 → worker）。量測隨著深度增加，被擾動的路徑自我修正與完全偏離的比例各是多少。
3. 在每個子經理處實作一個「金絲雀」worker，它永遠被問原封不動的使用者問題。用金絲雀的答案來偵測分解漂移。當金絲雀與綜合出來的答案不一致時，經理該怎麼反應？
4. 讀 CrewAI 的 `Process.hierarchical` 文件。指認出 CrewAI 施加的一項具體護欄（步數限制、manager_llm 限制），並描述它針對的是哪種失敗模式。
5. 把巢狀的 LangGraph supervisor 跟 CrewAI 的階層式做比較。哪一個讓調和迴圈更便宜地被偵測到？

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 階層式 | 「組織圖模式」 | Supervisor 之上還有 supervisor；只有葉子在做事。 |
| 經理 LLM | 「那個老大」 | 在內部節點負責分解、指派與驗證的那個 LLM。 |
| 分解漂移 | 「老大搞錯重點了」 | 頂層經理的切分不再涵蓋原本的問題。 |
| 調和迴圈 | 「開不完的會」 | 子經理意見不合；頂層重新委派；worker 重跑；一路繞到預算耗盡。 |
| 深度 2 上限 | 「不要超過 2 層」 | 經驗性護欄：3 層以上會讓可觀測性塌掉。 |
| 金絲雀問題 | 「每一層的基準真值」 | 一個永遠被問原封不動原始查詢的 worker，用來偵測漂移。 |
| 出處鏈 | 「誰說了什麼」 | 從每次綜合往回追到產生它的那些葉子輸出。 |
