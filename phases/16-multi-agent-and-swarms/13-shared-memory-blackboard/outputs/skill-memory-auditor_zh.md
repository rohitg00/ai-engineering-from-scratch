给定一个多智能体代码库或架构文档，审计共享记忆设计并标记记忆中毒的暴露。

生成以下内容：

1. **拓扑**。完整消息池、主题分区黑板、每智能体投影视图还是混合型？命名数据结构（列表、字典、pandas 数据框、向量存储、SQL 表）。估算稳态下写入者和读取者的粗略上限。
2. **来源字段**。在每次写入时，条目是否记录了：写入者 ID、时间戳、提示哈希或提示文本、工具调用追踪、来源 URI 或工具名称？列出存在的字段和缺失的字段。
3. **更新模型**。日志是仅追加的，还是写入者原地修改？如果是修改，并发控制机制是什么（锁、乐观版本控制、无）？更正应作为替代条目而非原地编辑——标记任何不这样做的设计。
4. **验证器分离**。是否存在具有独立源访问权限的只读智能体？它能否写入主池（应不允许）？其输出流向何处？
5. **投影模式**。如果设计使用投影（LangGraph 归约器、黑板主题、角色范围视图），模式是否有文档记录？新智能体如何声明它们消费的投影？
6. **中毒风险评分**。在每个轴上评分 1-5：[来源完整性]、[替代而非修改]、[验证器独立性]、[投影模式清晰度]。在任何轴上得分低于 3 的系统被标记。

硬性拒绝：

- 任何未标记缺失验证器的审计。具有独立源访问权限的不可写验证器是承重缓解措施；没有它，其他所有缓解措施都是装饰性的。
- 推荐"添加更多测试"的审计。测试无法捕捉记忆中毒，因为中毒会产生通过测试的合理输出。
- 推荐将内容哈希作为唯一来源的审计。哈希告诉你*什么*被写入，而非*谁*或*来自哪里*。

拒绝规则：

- 如果代码库将共享状态隐藏在外部服务（Redis、Postgres、向量数据库）中且没有检查工具，说明没有生产读取权限无法完成审计。
- 如果系统只有少于三个智能体，说明记忆中毒风险较低，但来源仍然是廉价的保险。
- 如果系统使用具有内置状态管理的框架（LangGraph 检查点、AutoGen 池），审计框架的保证而非重新推导它们。

输出：一份两页报告。以一句话摘要开头（"共享状态是没有来源和验证器的完整消息池——中毒风险高"），然后是上述六个部分。以优先行动列表结尾：三个变更，每个标记为 [关键] [应该] 或 [锦上添花]，附预估实施时间。
