# 共享内存与黑板模式

> 2026 年的多智能体系统中并存着两种方式：**消息池**（所有人都能看到所有人的消息，如 AutoGen GroupChat 或 MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如 Context-Aware MCP 或 Matrix 框架）。两者都是多智能体系统中唯一有状态的部分——也就是说，它们也是有趣 bug 的温床。典型的失败模式是**记忆中毒**：一个智能体"幻觉"出一个"事实"，其他智能体将其视为已验证信息，精确度逐渐下降，这种下降比立即崩溃要难调试得多。本课程从标准库构建这两种结构，注入一次中毒攻击，并展示三种在生产中实际有效的缓解措施。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`）
**前置知识：** 阶段 16 · 04（基础模型），阶段 16 · 09（并行群体网络）
**时间：** 约 75 分钟

## 问题

多智能体系统需要一个地方让智能体共享事实。一个直观的选择是"在消息中传递一切"——但这相当于用额外的复制重新发明了共享状态。另一种是"给每个人一个全局日志"——但全局日志会无限制增长且容易中毒。第三种是"为每个智能体投影一个视图"——可扩展但需要大量模式定义。

当其中一个智能体产生幻觉并将幻觉写入共享状态时，每个读取该状态的下游智能体都会将幻觉当作事实接受。等到人类注意到时，推理链已经深入了五步，而根因是第三条写入的消息。调试多智能体精度下降比调试崩溃要困难得多。

这就是记忆中毒。它是 MAST 分类法（Cemri et al., arXiv:2503.13657）中记录第二多的失败家族，这是一个结构性问题：任何没有来源追踪和不可写验证器的共享内存设计最终都会出现这种问题。

## 概念

### 两种主要拓扑结构

**全量消息池。** 每个智能体读取每一条消息。AutoGen GroupChat 和 MetaGPT 使用这种方式。简单、透明、可检查，但超过约 10 个智能体后无法扩展，因为每个智能体的上下文会被其他智能体的工作填满。

```
agent-A ──写入──▶ ┌────────────────┐ ◀──读取── agent-D
                   │ 消息池          │
agent-B ──写入──▶ │                │ ◀──读取── agent-E
                   │ （全局日志）    │
agent-C ──写入──▶ └────────────────┘ ◀──读取── agent-F
```

**带订阅的黑板。** 智能体声明对主题的兴趣；基础设施只路由相关消息。CA-MCP（arXiv:2601.11595）和 Matrix 去中心化框架（arXiv:2511.21686）使用这种方式。可扩展性更强，但需要预先设计模式以使订阅有意义。

```
                   ┌─ 主题: prices ──┐
agent-A ──发布──▶ │                  │ ──▶ agent-D（已订阅）
                   ├─ 主题: orders ──┤
agent-B ──发布──▶ │                  │ ──▶ agent-E（已订阅）
                   ├─ 主题: alerts ──┤
agent-C ──发布──▶ │                  │ ──▶ agent-F（已订阅）
                   └──────────────────┘
```

### 各自适用的场景

- **全量池**在智能体数量少（< 10）、异构、对话时间短时胜出。当每个人都能看到一切时，推理谁说了什么是微不足道的。
- **黑板**在智能体数量多、角色同质但实例众多（群体）、对话长时间运行时胜出。路由节省了代币成本和上下文污染。

生产系统通常混合使用：上层使用小型全量池（规划层），下层使用黑板（工作层）。

### 记忆中毒：一个场景

三个智能体合作完成一项研究任务。智能体 A 是检索智能体。智能体 B 是摘要生成器。智能体 C 是分析师。

1. A 获取一个页面并向共享状态写入一条消息："研究报告了 42% 的准确率提升。"
2. 实际上获取的页面说的是"4.2% 的提升"。A 幻觉了一位小数。
3. B 读取共享状态后写入："报告显示 42% 的大幅准确率提升（来源：A）。"
4. C 读取共享状态后写入："建议采纳——42% 的提升是变革性的。"
5. 最终报告引用了一个从未存在过的 42% 的数字。

没有智能体崩溃。没有测试失败。系统"正常工作"了。幻觉通过共享状态从一个智能体的上下文传播到了每个下游智能体的推理中。

### 为什么这是结构性的

没有共享状态时，智能体 A 的幻觉只停留在 A 的上下文中。下游智能体会重新获取或重新推导，有可能发现错误。有了天真的共享状态，A 的上下文就成了所有人的上下文，幻觉被洗白成了事实。

问题不在于共享状态本身——而在于**没有来源追踪且没有独立验证器**的共享状态。三种缓解措施应对这个问题：

1. **为每次写入标注来源。** 共享状态中的每条记录都记录了谁写的、何时写的、在什么提示下写的，以及（如果适用）智能体引用了什么来源。下游智能体根据来源信息进行批判性阅读。
2. **对写入进行版本管理；采用仅追加模式。** 更正是覆盖旧条目的新条目，而不是原地更新。审计追踪得以保留。
3. **至少保留一个不能写入共享状态的智能体。** 一个只读的验证器智能体采样条目，重新获取来源，并标记不一致之处。因为它不能写入池中，所以不会被池中毒。

### 黑板的前身（Hayes-Roth, 1985）

黑板模式比 LLM 智能体早了四十年。Hayes-Roth（1985，《A Blackboard Architecture for Control》）描述了专业的"知识源"（Knowledge Sources），它们观察全局黑板、贡献部分解决方案并触发其他来源。2026 年的黑板（CA-MCP、Matrix）是相同的模式，只是用 LLM 智能体作为知识源、用 JSON 数据块作为部分解决方案。早期文献已经记录了写竞争、机会性控制和一致性等问题的解决方案，而现代系统正在重新发现这些方案。

### 投影视图 vs 全量视图

纯黑板给每个订阅者相同的投影视图（按主题范围限定）。一种更激进的设计是**按智能体投影**：每个智能体获得一个根据其角色定制的视图。LangGraph 的状态规约器（state reducers）是 2026 年的典型实现——规约函数将全局状态折叠成角色特定的切片。

按智能体投影可扩展性更强，但需要模式定义。没有模式的话，你就要在每个智能体的提示中临时构建投影。

### 写竞争模式

多个智能体同时写入是一个并发问题，而不仅仅是 LLM 问题。三种模式有效：

- **顺序写入器（单一生产者）。** 所有写入通过一个协调智能体串行化。简单，但会成为瓶颈。
- **带版本控制的乐观并发。** 每条记录都有一个版本；写者在版本不匹配时失败并重试。经典的数据库技术。
- **主题分区。** 不同的智能体拥有不同的主题。没有跨主题竞争。需要设计分区边界。

大多数 2026 框架默认使用顺序写入器，因为 LLM 调用足够慢，竞争很少发生，瓶颈并不明显。

### 不可写验证器

最重要的缓解措施是只读验证器。实现规则：

- 验证器与团队共享状态（读取黑板或池）。
- 验证器没有共享状态的写入句柄——只有独立的验证通道。
- 验证器独立获取写入中引用的来源。标记不一致之处。
- 验证器自身的输出路由给人类或独立的决策智能体，决不反馈回池中。

没有这种隔离，验证器的输出会成为池中的新条目，这意味着被中毒的池会毒化验证器，进而毒化它的验证结果。

## 构建

`code/main.py` 使用标准库 Python 实现了两种拓扑结构，外加一个玩具中毒攻击和三种缓解措施。

- `MessagePool` — 线程安全的仅追加日志，支持完整读取。
- `Blackboard` — 按主题键区分的发布/订阅，支持按智能体订阅。
- `ProvenanceEntry` — 每次写入记录（写入者、时间戳、提示哈希值、来源 URI）。
- `PoisoningScenario` — 运行一个三智能体研究任务，其中智能体 A 幻觉了一位小数。输出最终报告。
- `Verifier` — 一个只读智能体，重新获取来源并标记不一致之处。在有验证器的情况下运行相同的场景。

运行：

```
python3 code/main.py
```

预期输出：
- 运行 1（无验证器）：幻觉出的 42% 传播到最终报告。
- 运行 2（有验证器）：验证器标记不一致之处，池被标记为"flagged"，最终报告包含撤回声明。

## 使用

`outputs/skill-memory-auditor.md` 是一个技能，用于审计任何多智能体系统的共享内存设计，检查其来源追踪、版本管理和验证器隔离。在上线前对新多智能体架构运行此技能。

## 交付检查清单

对于任何共享内存设计：

- 在每次写入时记录来源：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 使日志仅追加。更正是引用被取代条目的新条目。
- 部署至少一个具有独立来源访问权限的只读验证器智能体。
- 将验证器输出路由到单独的通道，而不是回到共享池中。
- 记录被取代写入的比例——比例上升是幻觉模式的早期证据。

## 练习

1. 运行 `code/main.py`。确认运行 1 传播了幻觉，运行 2 捕获了它。
2. 添加第二个幻觉：智能体 B 虚构了一个数据集大小。验证器应能捕获两者，而无需针对任何一个进行手工调整。
3. 将全量池切换为带主题分区（`prices`、`summaries`、`analyses`）的黑板。主题分区使哪些中毒场景更难实现，而对哪些场景没有帮助？

5. 阅读 CA-MCP（arXiv:2601.11595）。将其"共享上下文存储"映射到 `code/main.py` 中的 `MessagePool` 或 `Blackboard` 类。CA-MCP 在此基础上添加了哪些原语？

## 关键术语

| 术语 | 人们通常说的 | 实际含义 |
|------|-------------|---------|
| 消息池 | "共享聊天历史" | 每个智能体读取的仅追加日志。完全透明，扩展性差。 |
| 黑板 | "共享工作空间" | 按主题键区分的发布/订阅。智能体订阅相关主题。可扩展性更强。 |
| 来源追踪 | "谁写了什么" | 每次写入的元数据：写入者、时间戳、提示、来源。 |
| 记忆中毒 | "幻觉传播" | 一个智能体的错误进入共享状态，下游智能体将其当作事实接受。 |
| 仅追加 | "无原地更新" | 更正是覆盖旧条目的新条目。保留审计追踪。 |
| 不可写验证器 | "独立审计员" | 只读智能体，重新获取来源并标记不一致之处。 |
| 投影 | "限定范围的视图" | 从全局状态计算出的按智能体视图。LangGraph 规约器是典型例子。 |
| 知识源 | "专业智能体" | Hayes-Roth 1985 年对黑板参与者的术语。 |
