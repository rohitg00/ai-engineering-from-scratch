# 共享記憶與黑板模式

> 2026 年的多代理系統中有兩種做法並存：**訊息池**（每個人都看到每個人的訊息，如 AutoGen GroupChat 或 MetaGPT）與**帶訂閱的黑板**（代理訂閱相關事件，如 Context-Aware MCP 或 Matrix 框架）。兩者都是多代理系統中唯一有狀態的部分 —— 這也意味著兩者都是有趣臭蟲住的地方。那個典範失敗模式是**記憶投毒**：某個代理幻覺出一則「事實」，其他代理把它當成已查證，準確率就以一種比立刻崩潰難除錯得多的方式逐漸衰退。這一課用 stdlib 把兩種結構都建出來、注入一次投毒攻擊，並展示三種在生產環境真的有效的緩解方式。

**類型：** 學習 + 實作
**程式語言：** Python (stdlib, `threading`)
**先修單元：** 階段 16 · 04（原語模型）、階段 16 · 09（平行 Swarm 網路）
**時間：** 約 75 分鐘

## 問題

多代理系統需要一個地方讓代理共享事實。一個直白的選項是「把所有東西都放在訊息裡傳」—— 但那是在多複製一份的前提下重新發明共享狀態。另一個是「給大家一份全域日誌」—— 但全域日誌會無界地長大，而且很容易被投毒。第三個是「替每個代理投影一個視圖」—— 可擴展，但 schema 很重。

當其中一個代理產生幻覺並把那個幻覺寫進共享狀態時，每一個讀到那個狀態的下游代理都會把該幻覺當成事實接受。等人類注意到時，推理鏈已經深達五步，而根因是有史以來寫下的第三則訊息。替多代理的準確率衰退除錯，比替一次崩潰除錯還難。

這就是記憶投毒。它是 MAST 分類法（Cemri 等人，arXiv:2503.13657）中第二常被記錄的失敗家族，而且它是結構性的：任何沒有出處與不可寫查證者的共享記憶設計，遲早都會出現它。

## 概念

### 兩種主要拓撲

**完整訊息池。** 每個代理都讀每則訊息。AutoGen GroupChat 與 MetaGPT 用這種。簡單、透明、可檢視，但超過約 10 個代理就擴展不了，因為每個代理的脈絡都被其他代理的工作填滿。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**帶訂閱的黑板。** 代理宣告自己對哪些主題有興趣；那層基底只路由相關訊息。CA-MCP（arXiv:2601.11595）與 Matrix 去中心化框架（arXiv:2511.21686）用這種。擴展得更遠，但需要前期的 schema 設計，訂閱才有意義。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 各自何時勝出

- **完整池**在代理很少（< 10）、彼此異質、而且對話是短時程時勝出。當大家都看到一切時，推敲誰說了什麼是很簡單的事。
- **黑板**在代理很多、角色同質但實例眾多（swarm）、而且對話是長時間執行時勝出。路由省下詞元成本與脈絡汙染。

生產系統常常混用：上層是一個小小的完整池（規劃層），下層是黑板（worker 層）。

### 記憶投毒，用一個情境說明

三個代理在做一項研究任務。代理 A 是檢索代理。代理 B 是摘要者。代理 C 是分析師。

1. A 抓了一個頁面，並把一則訊息寫進共享狀態：「該研究回報準確率改善 42%。」
2. 抓到的頁面實際上寫的是「改善 4.2%」。A 幻覺出一個小數點。
3. B 讀共享狀態後寫下：「回報有大幅 42% 的準確率增益（來源：A）。」
4. C 讀共享狀態後寫下：「建議採用 —— 42% 的提升是變革性的。」
5. 最終報告引用了一個從來不存在的 42%。

沒有代理崩潰。沒有測試失敗。系統「運作正常」。那個幻覺透過共享狀態，從一個代理的脈絡穿進了每一個下游代理的推理。

### 為什麼這是結構性的

沒有共享狀態，代理 A 的幻覺就留在 A 的脈絡裡。下游代理會重新抓取或重新推導，可能就抓到那個錯誤。有了天真的共享狀態，A 的脈絡就變成大家的脈絡，那個幻覺就被洗成了事實。

問題不在共享狀態本身 —— 而在**沒有出處、也沒有獨立查證者**的共享狀態。有三種緩解處理這件事：

1. **每一次寫入都標註出處。** 共享狀態裡的每一筆條目都記下是誰寫的、何時、在什麼提示詞之下，以及（若適用）該代理引用了什麼來源。下游代理帶著與出處掛鉤的懷疑去讀。
2. **替寫入做版本；把它們當成僅可附加。** 一次更正是一筆取代舊者的新條目，不是就地更新。稽核軌跡被保留下來。
3. **至少留一個不能寫入共享狀態的代理。** 一個唯讀的查證者代理抽樣條目、重新抓取來源、標出不一致。因為它不能寫進池子，它也就不會被池子投毒。

### 黑板的前例（Hayes-Roth，1985）

黑板模式比 LLM 代理早了四十年。Hayes-Roth（1985，〈A Blackboard Architecture for Control〉）描述了一群專家知識源（Knowledge Source），它們觀察一塊全域黑板、貢獻部分解，並觸發其他知識源。2026 年的黑板（CA-MCP、Matrix）是同一套模式，只是把 LLM 代理當成知識源、把 JSON blob 當成部分解。那些舊文獻早就記錄了寫入爭用、機會式控制與一致性的解法，而現代系統正在重新發現它們。

### 投影 vs 完整視圖

純黑板給每個訂閱者同一份投影（依主題劃定範圍）。更激進的設計是**逐代理投影**：每個代理拿到一個依自己角色客製的視圖。LangGraph 的 state reducer 是 2026 年那份典範實作 —— reducer 函數把全域狀態摺疊成一個角色專屬的切片。

逐代理投影擴展得更遠，但需要一份 schema。沒有 schema，你就會在每個代理的提示詞裡臨時重造投影。

### 寫入爭用的模式

多個代理同時寫入是一個併發問題，不只是 LLM 問題。有三種模式管用：

- **循序寫入者（單一生產者）。** 所有寫入都經過一個負責序列化的協調者代理。簡單，但會是瓶頸。
- **帶版本的樂觀併發。** 每筆條目有一個版本；寫入者在版本不符時失敗並重試。經典的資料庫技術。
- **主題分割。** 不同代理擁有不同主題。沒有跨主題爭用。需要設計好的分割邊界。

2026 年多數框架預設用循序寫入者，因為 LLM 呼叫夠慢，爭用很罕見，而那個瓶頸也不痛。

### 那個不可寫的查證者

最承重的緩解就是那個唯讀查證者。實作規則：

- 查證者與團隊共享狀態（讀黑板或訊息池）。
- 查證者對共享狀態沒有寫入把手 —— 只能寫到一條獨立的查證通道。
- 查證者獨立抓取寫入中所引用的來源。標出不一致。
- 查證者自己的輸出被送給人類或一個獨立的決策代理，絕不餵回池子。

沒有這道隔離，查證者的輸出就變成池子裡的新條目，這代表被投毒的池子會毒到查證者，而它又毒到自己的查證結果。

## 動手實作

`code/main.py` 用 stdlib Python 實作兩種拓撲，外加一次玩具版投毒攻擊與那三種緩解。

- `MessagePool` —— 執行緒安全、僅可附加的日誌，可完整讀出。
- `Blackboard` —— 以主題為鍵的發布／訂閱，帶逐代理訂閱。
- `ProvenanceEntry` —— 每次寫入都記錄 (writer, timestamp, prompt_hash, source_uri)。
- `PoisoningScenario` —— 跑一項三代理的研究任務，其中代理 A 幻覺出一個小數點。印出最終報告。
- `Verifier` —— 一個唯讀代理，會重新抓取來源並標出不一致。在有查證者在場的情況下跑同一個情境。

跑：

```
python3 code/main.py
```

預期輸出：
- 第 1 趟（沒有查證者）：那個幻覺出來的 42% 一路傳到最終報告。
- 第 2 趟（有查證者）：查證者標出不一致，池子被標記為「flagged」，最終報告含一則撤回。

## 框架應用

`outputs/skill-memory-auditor.md` 是一項技能，會稽核任何多代理系統共享記憶設計的出處、版本控管與查證者隔離。在新的多代理架構進生產之前拿它跑一次。

## 產出交付

對任何共享記憶設計：

- 每次寫入都記錄出處：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 讓日誌僅可附加。更正是引用被取代者的新條目。
- 部署至少一個帶獨立來源存取的唯讀查證者代理。
- 把查證者的輸出送到一條獨立通道，不要送回共享池。
- 記錄「取代型寫入」占所有寫入的比例 —— 這個比例上升就是幻覺樣式的早期證據。

## 練習

1. 跑 `code/main.py`。確認第 1 趟把幻覺傳播出去，而第 2 趟抓到了它。
2. 加上第二個幻覺：代理 B 發明了一個資料集大小。查證者應該在沒有針對任一者手動調校的情況下，兩個都抓到。
3. 把完整池換成帶主題分割（`prices`、`summaries`、`analyses`）的黑板。主題分割讓哪些投毒情境更難成功，又對哪些沒有幫助？
4. 讀 Hayes-Roth（1985，〈A Blackboard Architecture for Control〉）。指認出論文中兩項本課沒討論、而 2026 年的系統會受益的控制模式。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 訊息池 | 「共享的聊天歷史」 | 每個代理都會讀、僅可附加的日誌。完全透明，擴展性差。 |
| 黑板 | 「共享工作區」 | 以主題為鍵的發布／訂閱。代理訂閱相關主題。擴展得更遠。 |
| 出處 | 「誰寫了什麼」 | 每次寫入上的中繼資料：寫入者、時間戳、提示詞、來源。 |
| 記憶投毒 | 「幻覺在擴散」 | 某個代理的錯誤進了共享狀態，下游代理把它當成事實接受。 |
| 僅可附加 | 「不做就地更新」 | 更正是取代舊者的新條目。保留稽核軌跡。 |
| 不可寫的查證者 | 「獨立稽核者」 | 會重新抓取來源並標出不一致的唯讀代理。 |
| 投影 | 「劃定範圍的視圖」 | 由全域狀態算出的逐代理視圖。LangGraph 的 reducer 是那個典範案例。 |
| 知識源 | 「專家代理」 | Hayes-Roth 1985 年對黑板參與者的稱呼。 |
