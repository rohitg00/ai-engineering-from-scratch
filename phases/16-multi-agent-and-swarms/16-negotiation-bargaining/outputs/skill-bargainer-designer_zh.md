给定一个协商或任务市场场景（双方讨价还价、N 方拍卖、合同网任务分配），设计协议。

生成以下内容：

1. **机制**。双方讨价还价、N 投标人拍卖、合同网广播或多方联盟。命名博弈类型。
2. **报价生成器**。确定性（Zeuthen 风格让步、Rubinstein 均衡、简单线性调度）或 LLM 提示。默认：确定性，除非报价必须是定性结构（提案、角色分配）。
3. **叙述层**。LLM 贡献的内容：人性化框架、说服策略、角色。明确说明 LLM 不*决定*什么。
4. **私有与公共渠道**。推理追踪如何避免进入对手方的上下文。"私人草稿板" + "公共消息"作为两个字段。根据 arXiv:2503.06416，这是不可谈判的。
5. **轮次上限**。双方最多 3-5 轮。无界不可选；它奖励从众并鼓励情绪化报价。
6. **保留价与 BATNA 纪律**。双方必须知道自己的保留价。如果对方探查，LLM 叙述者不得透露。根据此规则验证每条出站消息。
7. **成交率监控**。此协议的基线预期成交率（引用协商基准中的数字：27%-89% 范围，取决于 LLM 角色）。回归的告警阈值。
8. **升级**。低于阈值的轮次、ZOPA 违规或对手方违反规则——路由到调解智能体或人类。

硬性拒绝：

- 任何 LLM 在没有确定性后备的情况下计算数值报价的设计。arXiv:2402.15813 显示这会产生约 27% 的成交率。
- 任何没有单独私人和公共渠道的设计。对手方将读取你的推理。
- 任何有无界轮次的设计。保证导致从众驱动的结果。
- 让单个智能体同时持有买方和卖方状态的设计（角色扮演讨价还价）。私有信息属性是机制本身；合并角色则消除了它。

拒绝规则：

- 如果任务没有数值收益（定性协商、合同条款），OG-Narrator 分解可能不适用。推荐结构化提案 + 模式验证。
- 如果用户无法实现单独的草稿板（单 LLM 调用架构），明确标记泄露风险并推荐双调用架构。
- 如果协商是敌对的且对方可能撒谎，推荐调解智能体加上已记录的报价以供审计。

输出：一页简报。以一句话摘要开头（"双方讨价还价：Zeuthen 报价生成器 + LLM 叙述者，5 轮上限，独立草稿板，成交率低于 85% 时告警"），然后是上述八个部分。以示例消息结尾：对手方看到的 vs 私人草稿板持有的。
