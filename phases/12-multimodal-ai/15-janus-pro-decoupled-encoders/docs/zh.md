# Janus-Pro：用于统一多模态模型的解耦编码器

> 统一多模态模型存在一个不可避免的张力。理解任务需要语义特征——SigLIP 或 DINOv2 输出的向量富含概念级别的信息。生成任务需要易于重建的编码——能够重新组合成清晰像素的 VQ 标记。这两种目标在单个编码器中无法兼容。Janus（DeepSeek，2024 年 10 月）和 Janus-Pro（DeepSeek，2025 年 1 月）认为解决方案是放弃这种尝试：将两个编码器解耦。在任务之间共享 Transformer 主体，但理解任务路由到 SigLIP，生成任务路由到 VQ 分词器。在 7B 规模下，Janus-Pro 在 GenEval 上击败了 DALL-E 3，同时在 MMMU 上与 LLaVA 持平。本节课将探讨为什么两个编码器能在单个编码器失败的地方取得成功。

**类型：** 构建
**语言：** Python（标准库，双编码器路由 + 共享主体信号）
**前置知识：** 第 12 阶段 · 13（Transfusion），第 12 阶段 · 14（Show-o）
**时间：** ~120 分钟

## 学习目标

- 解释为什么单个共享编码器会损害理解或生成质量。
- 描述 Janus-Pro 的路由机制：输入端使用 SigLIP 特征用于理解，输入和输出端使用 VQ 标记用于生成。
- 追溯使 Janus-Pro 超越 Janus 的数据混合规模扩展。
- 比较解耦式（Janus-Pro）、耦合连续式（Transfusion）和耦合离散式（Show-o）架构。

## 问题所在

统一模型在理解和生成任务之间共享 Transformer 主体。之前的尝试（Chameleon、Show-o、Transfusion）都使用一个视觉分词器同时处理两个方向。这个分词器是一种妥协：

- 针对重建（生成）优化：VQ-VAE 能捕获细粒度的像素细节，但产生的标记语义连贯性较弱。
- 针对语义（理解）优化：SigLIP 嵌入将"猫"图像聚集在"猫"标记附近，但无法实现良好的重建。

Show-o 和 Transfusion 为此付出了代价，在其中一个方向上存在明显的质量损失。Janus-Pro 提出：当任务需求不同时，为何要强行使用同一个分词器？

## 核心理念

### 解耦的视觉编码

Janus-Pro 的架构将两个编码器分开：

- **理解路径。** 输入图像 → SigLIP-SO400m → 2 层 MLP → Transformer 主体。
- **生成路径。** 输入图像（如果以现有图像为条件）→ VQ 分词器 → 标记 ID → Transformer 主体。
- **输出生成。** Transformer 预测的图像标记 → VQ 解码器 → 像素。

Transformer 主体是共享的。主体上游和下游的所有部分都是任务特定的。

输入通过提示格式消除歧义：`<understand>` 标签路由到 SigLIP；`<generate>` 标签路由到 VQ。或者路由方式由任务隐式决定。

### 为什么这样有效

理解损失接收 SigLIP 特征，这些特征经过 CLIP 风格的预训练，已经针对语义相似性进行了优化。模型在感知基准上的表现优于 Show-o / Transfusion，因为输入特征更适合该任务。

生成损失接收 VQ 标记，这些标记经过分词器针对重建进行了优化。图像质量优于 Show-o，因为 VQ 编码能够干净地还原为像素。

共享的 Transformer 主体接收两种输入分布（SigLIP 和 VQ），并学会同时处理两者。其主张是：只要有足够的数据和足够的参数，主体就能吸收这种切换。

### 数据规模——Janus 与 Janus-Pro 对比

Janus（原始版，arXiv 2410.13848）引入了解耦思想，但规模较小（1.3B 参数，有限的数据）。Janus-Pro（arXiv 2501.17811）进行了扩展：

- 7B 参数（从 1.3B 扩展）。
- 第一阶段（对齐）使用 9000 万图像-文本对，从 7200 万提升。
- 第二阶段（统一训练）使用 7200 万对，从 2600 万提升。
- 第三阶段新增 20 万图像生成指令样本。

结果：Janus-Pro-7B 在 MMMU 上匹配 LLaVA（60.3 vs ~58），在 GenEval 上击败 DALL-E 3（0.80 vs 0.67）。一个开放模型，在统一频谱的两端都具有竞争力。

### JanusFlow——整流流变体

JanusFlow（arXiv 2411.07975）将 VQ 生成路径替换为整流流（rectified flow）生成路径（连续型）。架构变为 SigLIP-用于理解 + 整流流-用于生成。质量天花板进一步提升。架构仍然是解耦编码器 + 共享主体。

### 共享主体的职责

Transformer 主体处理统一的序列，但面对两种输入分布。其职责是：

- **对于理解：** 消费 SigLIP 特征 + 文本标记 → 自回归生成文本。
- **对于生成：** 消费文本标记 +（可选的图像 VQ 标记）→ 自回归生成图像 VQ 标记。

主体没有按模块划分的模态特定权重。它就是你在 Qwen 或 Llama 中常见的那种文本风格 Transformer，外加两个输入适配器。

有趣的是，这意味着 Janus-Pro 的主体可以从预训练的 LLM 初始化。Janus-Pro 确实从 DeepSeek-MoE-7B 进行了初始化。这个选择很重要：LLM 贡献了从零开始训练的统一模型难以企及的推理能力。

### 与 InternVL-U 的对比

InternVL-U（第 12.10 课）是 2026 年的后续工作。它结合了：

- 原生多模态预训练（InternVL3 骨干网络）。
- 解耦编码器路由（SigLIP 输入，VQ + 扩散头输出）。
- 统一的理解 + 生成 + 编辑能力。

InternVL-U 将 Janus-Pro 的架构选择纳入了更大的框架。解耦编码器的理念现已成为大规模统一模型的默认方案。

### 局限性

解耦编码器增加了架构复杂性。需要训练两个分词器，维护两条输入路径，处理两套故障模式。对于不需要生成能力的产品，Janus-Pro 显得过于复杂——选择 LLaVA 系列的理解模型即可。

对于不需要理解能力的产品，Janus-Pro 显得大材小用——选择 Stable Diffusion 3 / Flux 模型即可。

对于两者都需要的产品，Janus-Pro 现在是参考性的开放架构。

## 使用它

`code/main.py` 模拟了 Janus-Pro 的路由机制：

- 两个模拟编码器：类 SigLIP（产生 256 维语义向量）和类 VQ（产生整数编码）。
- 一个提示路由器，根据任务标签选择编码器。
- 一个共享主体（占位实现），处理由任一编码器产生的标记序列。
- 从第一阶段（对齐）到第三阶段（指令微调）的加权采样调度切换。

打印 3 个示例的路由路径：图像问答、文生图、图像编辑。

本节课产出 `outputs/skill-decoupled-encoder-picker.md`。给定一个需要前沿质量的统一生成 + 理解能力的产品，它将选择 Janus-Pro、JanusFlow 或 InternVL-U，并附带具体的数据规模建议。

## 练习

1. Janus-Pro-7B 在 GenEval 上击败了 DALL-E 3。解释为什么一个 7B 的开放模型能在生成任务上匹敌前沿专有模型，但在理解任务上却不能。

2. 实现一个路由器函数：给定提示文本，分类为 `understand` 或 `generate`。如何处理像"描述一下然后画出来"这样模棱两可的提示？

3. JanusFlow 用整流流取代了 VQ 路径。Transformer 主体现在输出什么？损失函数有什么变化？

4. 提出 Janus-Pro 架构可以通过再增加一个解耦编码器处理的第四种任务。示例：图像分割（DINO 风格）、深度估计（MiDaS 风格）。

5. 阅读 Janus-Pro 第 4.2 节关于数据扩展的内容。与 Janus 相比，哪个数据阶段对 T2I 质量提升贡献最大？

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|------------|----------|
| 解耦编码 | "两个视觉编码器" | 每个方向有单独的分词器或编码器：理解用语义编码器，生成用重建编码器 |
| 共享主体 | "一个 Transformer" | 单个 Transformer 处理任一编码器的输出；没有模态特定权重 |
| SigLIP 用于理解 | "语义特征" | CLIP 家族的视觉塔，提供丰富的概念特征但重建能力差 |
| VQ 用于生成 | "重建编码" | 矢量量化标记，能干净地解码回像素 |
| JanusFlow | "整流流变体" | 使用连续流匹配生成头替代 VQ 的 Janus-Pro 变体 |
| 路由标签 | "任务标签" | 选择输入编码器的提示标记（`<understand>` / `<generate>`） |
