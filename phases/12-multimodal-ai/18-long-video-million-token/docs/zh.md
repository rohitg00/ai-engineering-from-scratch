# 百万 Token 上下文中的长视频理解

> 一段 1 小时、24 FPS 的 4K 视频，经过分块和嵌入后，会产生约 6000 万个 token。一段 2 小时的播客转写文本为 30,000 个 token。一部长篇蓝光电影，即使以激进的池化方式压缩，也有数十万个 token。Google 的 Gemini 1.5（2024 年 3 月）以 1000 万 token 的上下文开启了这一时代，能够在一小时长的视频中可靠地完成"大海捞针"式召回。LWM（Liu 等人，2024 年 2 月）展示了环形注意力（Ring Attention）的扩展路径。LongVILA 和 Video-XL 进一步扩展了摄取能力。VideoAgent 则用智能体检索（Agentic Retrieval）取代了原始上下文。每种方法都在计算量、召回率和工程复杂度之间做出了不同的权衡。本课将对这些方法进行对比解读。

**类型：** 构建
**语言：** Python（标准库，大海捞针模拟器 + 智能体检索路由器）
**前置知识：** 阶段 12 · 17（视频时序 token）
**预计时间：** ~180 分钟

## 学习目标

- 计算长视频在不同 FPS 和池化下的视觉 token 总数。
- 解释三种扩展路径：暴力上下文（Gemini 1.5）、环形注意力（LWM）、Token 压缩（LongVILA / Video-XL）。
- 比较原始上下文视频 VLM 与智能体检索视频 VLM（VideoAgent）在准确率和延迟上的差异。
- 为一段 30 分钟的视频设计一个"大海捞针"测试，并测量在特定分钟处的召回率。

## 问题

Qwen2.5-VL 在 384 原生分辨率下的单帧分块约为 729 个 token。经过 3x3 池化后，每帧 81 个 token。一段 30 分钟的视频以 1 FPS 采样 = 1800 帧 = 145,800 个 token。到 2025 年，开源 VLM 勉强能处理，已经很紧张了。以 2 FPS 采样时，则为 291,600 个 token——只有最大的上下文窗口才能容纳。

一部 2 小时的电影以 1 FPS 采样是 583k 个 token。这超出了大多数 2026 年开源模型的能力；需要使用 Gemini 2.5 Pro 或更激进的池化方法。

出现了三种扩展路径。

## 核心概念

### 路径 1：暴力上下文（Gemini 1.5，Claude Opus）

用硬件硬扛问题。将上下文扩展到数百万 token，在一次前向传播中处理所有内容。

Gemini 1.5 Pro 首发支持 100 万 token；Gemini 1.5 Ultra 扩展到 1000 万；2026 年的 Gemini 2.5 Pro 可以可靠地处理数小时的视频。论文（arXiv:2403.05530）记录了在约 950 万 token 范围内 99.7% 的大海捞针召回率。

工程实现：一种带有内存层次结构的自定义注意力实现（局部 + 全局 + 稀疏），加上 MoE 专家路由以提高长上下文效率。未完全公开细节。非开源。

### 路径 2：环形注意力（LWM，LongVILA）

环形注意力将长序列分布在一个"环"中的多个设备上，每个设备持有一个分块。整个序列的注意力通过以下方式实现：每个设备将其分块发送到环中的下一个设备，计算部分注意力，然后进行聚合。

LWM（Liu 等人，2024 年）用这种方法训练了一个 100 万 token 上下文模型。训练计算量随上下文线性增长，而非二次增长——注意力的二次开销被分摊到了环中的各个设备上。

LongVILA（arXiv:2408.10188）将该模式适配到了 VLM。1400 帧视频，每帧 192 个 token = 268k 上下文，使用环形注意力在 8 路并行下进行训练。

### 路径 3：Token 压缩（Video-XL，LongVA）

比暴力上下文更便宜：在 LLM 看到序列之前进行激进的压缩。

Video-XL（arXiv:2409.14485）使用视觉总结 token：每 N 帧构成一个片段，每个片段产生一个"总结"token，该 token 对这 N 帧进行注意力操作。推理时，LLM 每个片段只看到一个总结 token，从而大幅缩小上下文。

LongVA 通过"长上下文迁移"技术将 LLM 上下文从 200k 扩展到 200 万。在长上下文文本上训练，然后通过共享表示将能力迁移到长上下文视频。

Token 压缩以牺牲特定时间点的召回率为代价换取可扩展性。模型大致知道发生了什么，但有时会错过精确的帧。

### 路径 4：智能体检索（VideoAgent）

不将完整视频送入 LLM。相反，将视频视为数据库，并使用 LLM 对其进行查询。

VideoAgent（arXiv:2403.10517）：

1. LLM 读取问题。
2. LLM 向检索工具请求相关片段（"展示包含猫的片段"）。
3. 工具返回匹配的片段时间戳。
4. LLM 通过 VLM 读取这些片段。
5. LLM 组合答案或提出后续查询。

这是将 LLM 作为智能体的模式应用于长视频。推理成本更低（只编码相关片段），工程难度更大（检索质量成为瓶颈）。

### 大海捞针基准测试

标准的长上下文测试：在视频中随机位置插入一个独特的视觉或文本标记，然后提出一个需要召回该标记的问题。

评估指标：跨越视频长度和标记位置的 Recall@k。

Gemini 2.5 Pro 在长达 90 分钟的视频中召回率 >99%。开源 72B 模型（Qwen2.5-VL-72B、InternVL3-78B）在 30 分钟时召回率约为 85-90%，超过 60 分钟后性能下降。

对于 2 小时以上的视频，VideoAgent 可以匹敌甚至超越原始上下文模型，因为如果检索工具足够好，它可以精准命中目标。

### 如何选择路径

对于 15 分钟的视频，追求前沿精度：开源 72B 加原生上下文通常就够用了。选择 Qwen2.5-VL-72B。

对于 30 分钟到 1 小时的内容：开源选 LongVILA 或 Video-XL；闭源选 Gemini 2.5 Pro。质量要求高时——闭源更优。

对于 2 小时以上的内容：选择 VideoAgent 或类似的检索模式。或者，将内容总结成更小的块，然后输入层次化摘要。

### 2026 年的生产模式

在实践中，生产环境中的长视频流水线是混合式的：

1. 对整个视频进行动态 FPS 采样 + 激进池化（得到一个 100k token 的全局表示）。
2. 将其输入 72B VLM 以获得全局摘要。
3. 如果用户提出细节性问题，以摘要为索引运行智能体检索。

这种方式结合了暴力上下文的全局理解能力和检索的局部细节能力。

4. 环形注意力的内存成本在序列长度上线性增长，在设备数量上也线性增长。解释原因，以及如果跳过环旋转阶段会发生什么问题。

5. 阅读 Gemini 1.5 论文第 5 节关于大海捞针的部分。论文发现了在 100 万 vs 1000 万 token 边界上召回率有哪些变化？

## 关键术语

| 术语 | 通俗理解 | 实际含义 |
|------|---------|---------|
| 暴力上下文（Brute context） | "就是塞更多 token" | 将 LLM 上下文扩展到数百万 token，一次处理所有内容 |
| 环形注意力（Ring attention） | "LWM 风格的并行" | 分布式注意力模式，每个设备持有一个分块并轮转 |
| Token 压缩（Token compression） | "总结 token" | 在送入 LLM 之前通过学习到的压缩器减少每个片段的 token 数 |
| 大海捞针（Needle-in-haystack） | "NIH 测试" | 在随机位置插入唯一标记，测试时让模型召回它 |
| 智能体检索（Agentic retrieval） | "LLM 作为查询规划器" | LLM 向检索工具请求相关片段，通过 VLM 读取它们，组合出答案 |
| VideoAgent | "视频的检索模式" | 经典的智能体检索设计：问题 -> 工具 -> 片段 -> 答案 |
