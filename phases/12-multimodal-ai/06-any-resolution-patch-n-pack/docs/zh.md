# 任意分辨率视觉：Patch-n'-Pack 与 NaFlex

> 真实图像并非 224x224 的正方形。收据是 9:16 的，图表是 16:9 的，医学扫描图像可能是 4096x4096 的，手机截图是 9:19.5 的。2024 年之前的 VLM 做法——将所有图像缩放到固定的正方形——丢弃了使 OCR、文档理解和高分辨率场景解析得以工作的关键信息。NaViT（Google, 2023）证明了你可以将可变分辨率的 patch 通过块对角掩码（block-diagonal masking）打包到单个 transformer batch 中。Qwen2-VL 的 M-RoPE（2024）完全摒弃了绝对位置表。LLaVA-NeXT 的 AnyRes 将高分辨率图像切分为基础图加子图像。SigLIP 2 的 NaFlex 变体（2025）现已成为开源 VLM 的默认编码器，只需单个检查点即可服务于所有宽高比。本课程将端到端地实现 patch-n'-pack。

**类型：** 构建
**语言：** Python（标准库，patch 打包器 + 块对角掩码）
**前置知识：** 阶段 12 · 01（ViT patch），阶段 12 · 05（LLaVA）
**时长：** ~120 分钟

## 学习目标

- 将一批可变分辨率图像的 patch 打包成一个序列，并构建块对角注意力掩码。
- 针对特定任务，在 AnyRes 分块（LLaVA-NeXT）、NaFlex（SigLIP 2）和 M-RoPE（Qwen2-VL）之间做出选择。
- 计算 OCR、图表和摄影场景下无需缩放的 token 预算。
- 说出正方形缩放的三种失败模式：文字挤压、内容裁剪、填充 token 浪费。

## 问题所在

Transformer 期望接收序列。一个 batch 是一组长度相同的序列堆叠。如果你的图像是 224x224，每次得到 196 个 patch token，无需填充，任务完成。在 224 上训练，在 224 上推理，再也不需要考虑分辨率问题。

但现实世界并不配合。文档是竖屏的（8.5x11 英寸，约 2:3）。图表截图是横屏的（16:9）。收据又高又窄（1:3）。医学影像分辨率可达 2048x2048 或更大。手机设备截图是 1170x2532（0.46:1）。

2024 年之前的三种方案及其各自的失败原因：

1. **缩放到固定正方形**（224x224 或 336x336）。挤压会扭曲文字和面部。缩小会破坏图表标签和 OCR 内容。这是 LLaVA-1.5 之前的标准做法。
2. **裁剪到固定宽高比**。你会丢弃大部分图像，而选择裁剪位置本身就是一个视觉问题。
3. **填充到最长边**。解决了变形问题，但在竖屏图像上会浪费 50% 以上的 token 用于填充。所有填充 token 的二次注意力代价巨大。

2024-2025 年的答案：让 transformer 以图像的原始分辨率消化 patch，并找出如何将异构 batch 打包成一个序列而不浪费计算资源。

## 核心概念

### NaViT 与 patch-n'-pack

NaViT（Dehghani 等, 2023）是证明这种方法在大规模下可行的论文。其思想非常直接：

1. 对 batch 中的每张图像，在选定的 patch 大小（例如 14）下计算其原始 patch 网格。
2. 将每张图像的 patch 展平为其自身的变长序列。
3. 将所有图像的 patch 连接成该 batch 的一个长序列。
4. 构建一个块对角注意力掩码，使得图像 A 的 patch 只在图像 A 内部相互关注。
5. 携带每个 patch 的位置信息（2D RoPE 或分数位置嵌入）。

一个包含三张图像（336x336，576 token；224x224，256 token；448x336，768 token）的 batch 会变成一个 1600 token 的序列，带有一个 1600x1600 的块对角掩码。无填充。无计算浪费。Transformer 处理任意宽高比。

NaViT 还引入了训练期间的分数式 patch 丢弃——在 batch 中随机丢弃 50% 的 patch——既起到了正则化作用，又加速了训练。SigLIP 2 继承了这一点。

### AnyRes（LLaVA-NeXT）

LLaVA-NeXT 的 AnyRes 是一种务实的替代方案。给定一张高分辨率图像和一个固定编码器（336 尺寸的 CLIP 或 SigLIP），对图像进行分块：

1. 从预定义的网格布局集合——(1x1)、(1x2)、(2x1)、(1x3)、(3x1)、(2x2) 等——中选择最能匹配图像宽高比的一种。
2. 将整张图像切分为所选网格；每个图块变成 336x336 的裁剪块。
3. 同时生成一张缩略图：将整张图像缩放到 336x336，作为全局上下文 token。
4. 通过冻结的 336 编码器编码每个图块。拼接所有图块 token 和缩略图 token。

对于一张 672x672 的图像，采用 2x2 网格加缩略图：4 × 576 + 576 = 2880 个视觉 token。代价高昂但效果显著——LLM 同时看到了局部细节和全局上下文。

当你的编码器被冻结且只支持单一分辨率时，AnyRes 是首选方案。它会大幅增加大图像的 token 数量（一张 1344x1344 的图像在 4x4 网格下会产生 9216 + 576 ≈ 9800 个 token，几乎填满 8k LLM 上下文）。

### M-RoPE（Qwen2-VL）

Qwen2-VL 引入了多模态旋转位置编码（Multimodal Rotary Position Embedding）。不同于 NaViT 的分数位置或 AnyRes 的分块加缩略图，每个 patch 携带一个 3D 位置（时间维、高度、宽度）。查询/键的旋转操作处理任意的 H、W 和时间长度。

M-RoPE 无需重新训练即可原生支持动态分辨率。推理时输入任意 H×W 的图像，patch 嵌入器产生 H/14 × W/14 个 token，每个 token 获得其 (t=0, r=行, c=列) 位置，RoPE 以正确的频率旋转注意力，完成。Qwen2.5-VL 和 Qwen3-VL 延续了这种方法。InternVL3 的 V2PE 是相同的思路，但每个模态使用可变的编码。

与 AnyRes 不同，M-RoPE 的 token 数为 O(H × W / P²) 的原始分辨率——没有乘性的分块开销。与 NaViT 不同，它仍然期望每次前向传播处理单张图像。跨分辨率的批处理仍然需要在此基础上使用 patch-n'-pack。

### NaFlex（SigLIP 2）

NaFlex 是 SigLIP 2 检查点的原生灵活（native-flex）模式。单个模型在推理时服务于多种序列长度（256、729、1024 token）。在内部，它在训练期间使用 NaViT 风格的 patch-n'-pack 以及每个 patch 的绝对分数位置。其卖点在于：一个检查点，根据任务在推理时选择你的 token 预算。

对于语义任务（分类、检索），使用 256 token。对于 OCR 或图表理解，使用 1024 token。无需重新训练。

### 打包掩码

块对角掩码是大多数实现容易出错的地方。对于一个总长度为 `N_total`、覆盖了图像 `i=0..B-1`（长度分别为 `n_i`）的打包序列，形状为 `(N_total, N_total)` 的掩码 `M` 在两个索引属于同一图像的块内时为 1，否则为 0。可以通过累积长度列表来构建：

```
offsets = [0, n_0, n_0+n_1, ..., N_total]
M[i, j] = 1 当且仅当存在 b 使得 offsets[b] <= i < offsets[b+1] 且 offsets[b] <= j < offsets[b+1]
```

在 PyTorch 中，这可以用 `torch.block_diag` 或显式的 gather 一行实现。FlashAttention 的变长路径（`cu_seqlens`）完全跳过了掩码，直接使用累积长度张量在序列内部进行注意力计算——对于典型 batch 来说，比密集掩码快约 10 倍。

### Token 预算

根据任务选择策略：

- **OCR / 文档**：1024-4096 token。SigLIP 2 NaFlex 使用 1024，或 AnyRes 3x3 加缩略图。
- **图表和 UI**：384-448 原始分辨率下 729-1024 token。Qwen2.5-VL 动态分辨率配合最大像素数上限。
- **自然照片**：256-576 token 就足够了。下游 LLM 能看到足够的信息。在内容密度高的地方投入 token。
- **视频**：空间池化后每帧 64-128 token，2-8 FPS。课程 12.17 会涉及。

2026 年的生产规则：为每个任务设定一个最大像素数上限，在达到该上限之前以原始宽高比编码，打包 batch，跳过填充。Qwen2.5-VL 提供了 `min_pixels` 和 `max_pixels` 作为精确的控制旋钮。

## 使用它

`code/main.py` 实现了一个异构图像 batch 的 patch-n'-pack，使用整数像素坐标。它：

- 接收一个 (H, W) 图像尺寸列表。
- 计算每张图像在 patch 大小为 14 时的 patch 序列长度。
- 将它们打包成一个总长度为 `sum(n_i)` 的序列。
- 构建块对角注意力掩码（为清晰起见使用密集形式）。
- 比较打包代价与正方形缩放和 AnyRes 分块的代价。
- 打印一个混合 batch（收据、图表、截图、照片）的 token 预算表。

运行它。得出的数字就是为什么 2026 年的每个开源 VLM 都使用 patch-n'-pack 的原因。

## 交付它

本课程产出 `outputs/skill-resolution-budget-planner.md`。给定一个混合宽高比的工作负载（OCR、图表、照片、视频帧）和一个总 token 预算，它会选择正确的策略（NaFlex、AnyRes、M-RoPE 或固定正方形），并输出每个请求的配置。当你在为产品评估 VLM 大小时使用这个技能——它可以防止无声的 10 倍 token 膨胀，这种膨胀会摧毁延迟预算。

## 练习

1. 一张收据尺寸为 600x1500（1:2.5）。在 patch 大小为 14 时，原始分辨率下有多少个 token？缩放到 336 的正方形后有多少个？实践中哪种方式会损失更多 OCR 精度？

2. 为一个包含四张图像（长度分别为 256、576、729、1024）的 batch 构建块对角掩码。验证注意力矩阵为 2585x2585，且恰好有 `256² + 576² + 729² + 1024²` 个非零元素。

3. 对于一张 1792x896 的图像（patch 为 14），比较：(a) 缩放到 336 正方形后编码，(b) AnyRes 2x1 加缩略图，(c) 原始分辨率下的 M-RoPE。哪种使用的 token 最少？哪种保留了最多的细节？

4. 实现分数式 patch 丢弃：给定一个打包序列，均匀随机丢弃 50% 的 token，并相应地更新块对角掩码。测量掩码稀疏度的变化。

5. 阅读 Qwen2-VL 论文（arXiv:2409.12191）的第 3.2 节。用两句话描述 `min_pixels` 和 `max_pixels` 控制什么，以及为什么这两个边界都很重要。

## 关键术语

| 术语 | 人们说的 | 实际含义 |
|------|----------|----------|
| Patch-n'-pack | "NaViT 风格的打包" | 将来自不同图像的可变长度 patch 序列连接成一个 batch 维度 |
| 块对角掩码 | "打包掩码" | 注意力掩码，将每张图像的 patch 限制为只关注自身，而不关注包中的相邻图像 |
| AnyRes | "LLaVA-NeXT 分块" | 将高分辨率图像分割为固定大小图块的网格，加上全局缩略图；使用固定编码器编码每个图块 |
| NaFlex | "SigLIP 2 原生灵活" | 单个 SigLIP 2 检查点，推理时无需重新训练即可服务于 256/729/1024 token 预算 |
| M-RoPE | "多模态 RoPE" | 3D 旋转位置编码（时间、行、列），无需位置表即可处理任意 H、W、T |
| cu_seqlens | "FlashAttention 打包" | FlashAttention 变长路径使用的累积长度张量，替代密集的块对角掩码 |
| min_pixels / max_pixels | "分辨率边界" | Qwen2.5-VL 的每请求控制旋钮，用于限制过小或过大输入的 token 数量 |
| 视觉 token 预算 | "每张图像用多少 token" | 每张图像产生的 patch token 的大致数量；决定了 LLM 的提示预算和注意力代价 |
