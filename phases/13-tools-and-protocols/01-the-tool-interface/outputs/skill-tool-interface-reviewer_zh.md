给定一个拟议的工具定义，根据四步循环（描述、决策、执行、观察）对其进行审查，并在工具到达模型前标记出破坏循环的缺陷。

产出：

1. **名称审计。** 名称是否为 `snake_case` 格式，跨版本是否稳定，且无歧义？标记与内置名称冲突、包含时态（"was_", "will_"）或嵌入了参数的名称。
2. **描述审计。** 描述是否是一个完整的使用简介？要求采用两句式结构："当X时使用。不要用于Y。" 标记少于40个字符的描述、营销文案或任何不能指导模型选择的描述。
3. **Schema审计。** Schema 是否为有效的 JSON Schema 2020-12？每个字段是否都有类型？`required` 列表是否显式列出？枚举是否用于封闭值集？标记应当使用枚举但却是开放式字符串字段、缺少类型以及输入对象上未声明 `additionalProperties` 的情况。
4. **执行器审计。** 执行器在给定参数下是否确定性的？它是否以类型化错误（而非逃逸到宿主程序的异常）处理失败？如果它是后果性的（改变状态、花费金钱、接触用户数据），是否已标记并设置了确认屏障？
5. **分类。** 声明工具是纯函数型还是后果型，并说明原因。后果型工具如果没有确认屏障则立即拒绝。

硬拒绝：
- 任何描述只说明工具做什么而不说明何时使用的工具。模型需要"何时"用于第二步。
- 任何包含无类型字段的 schema。验证器无法正常工作。
- 任何同时具备以下三项的工具：接受不可信输入、读取敏感数据、执行后果性操作。违反 Meta 的规则二。
- 任何执行器在遇到错误输入时抛出未处理异常的工具。宿主不应在每个调用周围都需要 try/except。

拒绝规则：
- 如果工具定义缺少 schema，则拒绝。先引导至阶段 13 · 04。
- 如果工具是纯函数型但描述说"谨慎使用"，拒绝并要求解释原因。纯函数型工具应可廉价地重复运行。
- 如果审查者被要求批准一个在没有只读保护的情况下访问生产数据库的工具，拒绝并引导至阶段 13 · 17（网关与策略）。

输出：一页审计报告，列出名称、描述、schema 和执行器方面的发现，附有严重级别（block / warn / nit），以及最终裁决（ship / revise / reject）。对于任何拒绝项，在可行情况下以一行重写建议结尾。
