# 工具接口——为什么智能体需要结构化 I/O

> 语言模型产生 token。程序执行行动。这两者之间的鸿沟就是工具接口：一份契约，让模型请求一个动作，让宿主执行它。2026 年的每个技术栈——OpenAI、Anthropic 和 Gemini 上的函数调用；MCP 的 `tools/call`；A2A 的 task parts——都是同一个四步循环的不同编码。本课程命名了该循环，并展示了运行它的最小机制。

**类型：** 学习
**语言：** Python（标准库，无 LLM）
**前置要求：** 阶段 11（LLM 补全 API）
**时长：** ≈45 分钟

## 学习目标

- 解释为什么一个只能生成文本的 LLM 无法独立地对真实世界执行操作。
- 绘制四步工具调用循环（描述 → 决定 → 执行 → 观察）并说出每一步的拥有者。
- 将工具描述编写为三个部分：名称、JSON Schema 输入和确定性执行器函数。
- 区分纯工具和副作用工具，并说明为什么这种拆分对安全性至关重要。

## 问题

LLM 输出一个关于下一个 token 的概率分布。这就是全部的输出面。如果你问一个聊天模型"班加罗尔现在的天气怎么样"，它可以写出一个看似合理的句子，但它无法调用天气 API。这个句子可能恰好正确，也可能已经过时三天了。

消除这一鸿沟正是工具接口的目的。宿主程序——你的智能体运行时、Claude Desktop、ChatGPT、Cursor 或一个自定义脚本——向模型公布一份可调用工具的列表。模型在决定需要执行某个动作时，会输出一个结构化的载荷，其中包含工具名称及其参数。宿主解析该载荷，实际运行该工具，并将结果反馈给模型。循环持续进行，直到模型判断不再需要调用为止。

这份契约的第一个版本于 2023 年 6 月作为 OpenAI 的 "functions" 参数推出。Anthropic 在 Claude 2.1 中随之推出了 `tool_use` 块。Gemini 在几个月后增加了 `functionDeclarations`。现在每个提供商都暴露了相同的结构：输入一个 JSON-Schema 类型的工具列表，输出一个 JSON 载荷的工具调用。Model Context Protocol（2024 年 11 月）将这份契约泛化，使得一个工具注册表可以为所有模型服务。A2A（2026 年 4 月，v1.0）则将同一原语应用于智能体与智能体之间的委派。

四步循环是所有这一切之下的不变项。阶段 13 中的其余内容都是对其的展开。

## 概念

### 第一步：描述

宿主用三个字段声明每个工具。

- **名称。** 一个稳定、机器可读的标识符。`get_weather`，而不是"天气那个东西"。
- **描述。** 一段自然语言的简短说明。"当用户询问某个城市的当前天气状况时使用。不要用于历史数据。"
- **输入模式。** 一个 JSON Schema 对象（2020-12 草案），描述该工具的参数。

模型接收这个列表。现代提供商使用特定于提供商的模板将这些声明序列化到系统提示中，因此你作为调用方只需处理结构化形式。

### 第二步：决定

根据用户的消息和可用的工具，模型选择三种行为之一。

1. **直接回答**文本。不调用工具。
2. **调用一个或多个工具。** 输出结构化的调用对象。在 `parallel_tool_calls: true` 下（OpenAI 和 Gemini 默认开启，Anthropic 需选择开启），模型可以在一次回复中输出多个调用。
3. **拒绝。** 严格模式的结构化输出可以输出一个类型化的 `refusal` 块，而不是调用。

工具调用载荷有三个稳定的字段：调用 `id`、工具 `name` 和 JSON `arguments` 对象。id 的存在是为了让宿主能够将后续的结果与特定的调用关联起来，这在并行调用无序返回时非常重要。

### 第三步：执行

宿主接收调用，对照已声明的模式验证参数，然后运行执行器。无效的参数意味着模型幻觉生成了一个字段或使用了错误的类型——这是弱模型上非常常见的失败模式。生产环境中的宿主在遇到无效参数时通常会做三件事之一：快速失败并将错误展示给模型，使用受限解析器修复 JSON，或将包含验证错误的提示重新发送给模型重试。

执行器本身是普通的代码。Python、TypeScript、Shell 命令、数据库查询。它产生一个结果，通常是一个字符串，但也可以是任何 JSON 值或结构化内容块（MCP 中的文本、图像或资源引用）。结果必须是可序列化的。

### 第四步：观察

宿主将工具结果追加到对话中（作为带有匹配 `id` 的 `tool` 角色消息），然后重新调用模型。模型现在在上下文中拥有了工具输出，可以生成最终答案或请求更多调用。这一过程持续进行，直到模型停止发出调用或宿主达到迭代次数的安全限制。

### 信任分离

从安全性角度看，工具有两种类型。

- **纯工具。** 只读、确定性、无副作用。`get_weather`、`search_docs`、`get_current_time`。可以安全地进行推测性调用。
- **副作用工具。** 改变状态、花费金钱、接触用户数据。`send_email`、`delete_file`、`execute_trade`。必须设置门控。

Meta 在 2026 年提出的智能体安全"双项规则"指出，单次轮换最多可以组合以下三项中的两项：不可信输入、敏感数据、副作用操作。工具接口正是你执行该规则的地方——通过拒绝调用、要求用户确认或提升作用域。参见阶段 13 · 15 获取完整的安全章节，以及阶段 14 · 09 获取智能体级别的权限策略。

### 循环存在于何处

| 上下文 | 谁描述 | 谁决定 | 谁执行 |
|---------|---------------|-------------|--------------|
| 单轮函数调用（OpenAI/Anthropic/Gemini） | 应用开发者 | LLM | 应用开发者 |
| MCP | MCP 服务器 | 通过 MCP 客户端的 LLM | MCP 服务器 |
| A2A | Agent Card 发布者 | 调用方智能体 | 被调用智能体 |
| Web 浏览器（函数调用智能体） | 浏览器扩展 / WebMCP | LLM | 浏览器运行时 |

处处都是同样的四个步骤。列名变了，但结构没有变。

### 为什么不让模型直接输出 JSON？

"让模型用 JSON 回复"是函数调用出现之前的模式。在前沿模型上它大约有 5% 到 15% 的失败率，在更小的模型上则高得多。失败模式包括缺少花括号、多余的逗号、幻觉字段以及错误的类型。随后你需要一个 JSON 修复过程、一次重试或一个受限解码器。

原生函数调用更好，原因有三。第一，提供商对模型进行端到端训练以生成精确的调用结构，因此在严格模式下有效 JSON 率可达 98% 到 99%。第二，调用载荷位于自己专属的协议槽中，而非自由文本内部——因此工具调用永远不会泄漏到用户可见的回复中。第三，提供商通过受限解码（OpenAI 的 strict 模式、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`）强制执行模式合规性。输出保证能够通过验证。

### 断路器

循环在模型停止发出调用或宿主达到最大轮次计数时终止。生产环境中的宿主将此值设置在 5 到 20 轮之间。超过此范围，你几乎肯定陷入了模型无法退出的循环中。Claude Code 默认为 20 轮；OpenAI Assistants 为 10 轮；Cursor 的智能体模式为 25 轮。

另一种选择——无界循环——每六个月就会以"智能体一夜之间消耗了 400 美元的 API 调用费用"这样的复盘报告出现。切勿在未设置上限的情况下发布。

## 使用它

`code/main.py` 在没有 LLM 的情况下运行四步循环。一个假的"决策器"函数通过对用户消息进行模式匹配来模拟模型；执行器、模式验证器和观察步骤框架都是真实的。运行它以查看带有可打印中间状态的完整请求/响应编排，然后在后续课程中用任何真实提供商替换假的决策器。

需要注意的地方：

- 工具注册表为每个工具维护四个字段：名称、描述、模式和执行器引用。
- 验证器是一个仅使用标准库编写的最小 JSON Schema 子集（类型、必填、枚举、最小值/最大值）。阶段 13 · 04 提供了一个更完整的版本。
- 循环将迭代次数限制为五次。生产环境中的智能体正需要这种断路器。

## 交付

本课程产出 `outputs/skill-tool-interface-reviewer.md`。给定一个草稿工具定义（名称 + 描述 + 模式 + 执行器概要），该技能会对其进行循环适配性审计：名称是否机器稳定、描述是否是一份完整的使用说明、模式是否正确使用了 JSON Schema 2020-12、纯工具与副作用工具的分类是否明确。

## 练习

1. 在 `code/main.py` 中添加第四个名为 `get_stock_price(ticker)` 的工具。将其描述编写为"当用户通过股票代码询问当前股价时使用。不要用于历史价格或市场摘要。"运行测试框架，确认假的决策器会将提及股票代码的查询路由到新工具。

2. 破坏模式验证器。传递一个 `arguments` 对象缺少必填字段的调用，并确认宿主在执行前拒绝了它。然后传递一个包含额外未知字段的调用。决定：宿主应该拒绝还是忽略？用安全性论证证明你的选择。

3. 将测试框架中的每个工具分类为纯工具或副作用工具。为需要它的注册表条目添加 `consequential: true` 标志，并修改循环，使得每当选择了一个副作用工具时打印一条"将向用户确认"的消息。这就是每个生产环境宿主所需的确认门控的雏形。

4. 在纸上绘制四步循环，并为你最喜欢的客户端（Claude Desktop、Cursor、ChatGPT 或自定义技术栈）填写上方的提供商列对照表。与阶段 13 · 06 中 MCP 特定变体进行交叉对比。

5. 从头到尾阅读 OpenAI 的函数调用指南。找出一个存在于请求中但未出现在本课程呈现的四步循环中的字段。解释它增加了什么，以及为什么它是便捷功能而非必需功能。

## 关键术语

| 术语 | 人们通常说的意思 | 实际含义 |
|------|----------------|------------------------|
| 工具（Tool） | "模型可以调用的东西" | 名称 + JSON-Schema-类型输入 + 执行器函数的三元组 |
| 函数调用（Function calling） | "原生工具使用" | 提供商级别的 API 支持，用于输出结构化工具调用而非散文 |
| 工具调用（Tool call） | "模型执行动作的请求" | 由模型输出的包含 `id`、`name`、`arguments` 的 JSON 载荷 |
| 工具结果（Tool result） | "工具返回的内容" | 执行器的输出，包装在带有匹配 id 的 `tool` 角色消息中 |
| 并行工具调用（Parallel tool calls） | "一次调用多个" | 单次模型回复中的多个调用对象，相互独立且可通过 id 排序 |
| 严格模式（Strict mode） | "有保证的 JSON" | 受限解码，强制模型的输出符合声明的模式 |
| 纯工具（Pure tool） | "只读工具" | 无副作用；安全地重复运行 |
| 副作用工具（Consequential tool） | "行动工具" | 改变外部状态；需要门控、审计或用户确认 |
| 四步循环（Four-step loop） | "工具调用周期" | 描述 → 决定 → 执行 → 观察 |
| 宿主（Host） | "智能体运行时" | 持有工具注册表、调用模型并运行执行器的程序 |
