给定一个任务领域，生成一个代理能够跨 BFCL V4 轴（自主式、多轮、实时、非实时、幻觉）可靠使用的工具目录。

产出：

1. **工具定义**。为每个工具提供：`name`（蛇形命名法）、`description`（告知模型何时使用以及何时不使用）、带类型属性的 JSON Schema 输入、必填字段、枚举值（如适用）、数值的最小值/最大值、每个工具的超时时间、每个工具的沙箱策略（文件系统范围、网络、内存上限）。
2. **描述质量检查**。对每条描述进行测试："这条描述是否告诉模型何时选择此工具而非其他？"如果两个工具的描述重叠，则拒绝并重写。
3. **并行调度方案**。针对每个实际任务，识别哪些工具调用是独立的（可并行化），哪些必须是顺序的。输出预期的调度图。
4. **验证策略**。枚举检查、类型强制规则（例如"接受字符串形式的整数，拒绝字符串形式的浮点数"）、必填字段强制。每次失败返回结构化观察字符串，绝不向循环抛出异常。
5. **可观测性**。每个工具发出一个 OpenTelemetry GenAI `tool_call` span，其属性包括 `gen_ai.tool.name`、`gen_ai.tool.call.id`、`gen_ai.tool.call.arguments`、`gen_ai.tool.call.result`（当内容策略要求时使用引用而非内联）。

硬性拒绝：

- 通用的 shell/命令执行工具。拒绝并拆分为具体动词（`git_status`、`fs_read`、`npm_test`）。
- 当参数有封闭值集合时缺少枚举。枚举验证是捕获偏移最廉价的方式。
- 两个不同工具使用相同的描述。模型无法在它们之间可靠选择。
- `description` 仅命名工具（"将两个数相加"）。应包含何时选择它而非其他替代方案。
- 没有超时。每个工具调用必须有上限。

拒绝规则：

- 如果单个代理的工具列表超过 30 个，拒绝并推荐子代理委托（第 17 课）。
- 如果任何工具在没有确认门控的情况下执行破坏性操作，拒绝并指向第 09 课（权限、沙箱化）。
- 如果任务是计算机使用（点击、输入文本、截屏），拒绝并指向第 21 课——那是另一种基于视觉操作的工具形态。

输出：一个可直接粘贴到 Anthropic/OpenAI/Gemini SDK 调用中的 JSON 工具目录、一张调度图、一份验证策略文档，以及注册中心应通过的一组 BFCL 风格迷你评估。

以"下一步阅读"指引结尾，指向第 09 课（沙箱化）、第 23 课（OTel GenAI span）或第 30 课（评估驱动开发）。
