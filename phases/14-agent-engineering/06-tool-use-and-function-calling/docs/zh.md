# 工具使用与函数调用

> Toolformer（Schick 等人，2023）开启了自监督工具标注的先河。伯克利函数调用排行榜 V4（Patil 等人，2025）设定了 2026 年的标杆：40% 智能体任务、30% 多轮对话、10% 实时场景、10% 非实时场景、10% 幻觉检测。单轮调用已基本解决。记忆、动态决策和长序列工具链仍是未解难题。

**类型：** 构建
**语言：** Python（标准库）
**前置要求：** 阶段 14 · 01（智能体循环）、阶段 13 · 01（函数调用深入解析）
**时长：** 约 60 分钟

## 学习目标

- 解释 Toolformer 的自监督训练信号：仅当执行工具调用能降低下一个 token 的损失时，才保留该工具标注。
- 列出 BFCL V4 的五个评测类别及其各自衡量内容。
- 实现一个基于标准库的工具注册中心，包含模式验证、参数类型强制转换和执行沙箱。
- 剖析 2026 年的三个未解难题：长序列工具链、动态决策和记忆。

## 问题

早期的工具使用问的是：模型能否预测出正确的函数调用？现代的工具使用问的是：模型能否在 40 步内串联工具、具备记忆、处理部分可观测性、从工具故障中恢复，并且不幻觉出不存在的工具？

Toolformer 确立了基线：模型可以通过自监督学习掌握何时调用工具。BFCL V4 定义了 2026 年的评估目标。二者之间的差距，正是生产级智能体所处的空间。

## 概念

### Toolformer（Schick 等人，NeurIPS 2023）

核心思想：让模型用自己的预训练语料库标注候选 API 调用。对每个候选调用执行一次。仅当包含工具结果能降低下一个 token 的损失时，才保留该标注。在筛选后的语料库上进行微调。

涵盖的工具：计算器、问答系统、搜索引擎、翻译器、日历。自监督信号纯粹取决于工具是否有助于预测文本——无需人工标注。

规模效应：工具使用在规模增大时涌现。较小的模型会因工具标注而受损；较大的模型则从中受益。这就是为什么 2026 年的前沿模型内置了强大的工具使用能力，而大多数 7B 模型仍需要通过显式的工具使用微调才能可靠运行。

### 伯克利函数调用排行榜 V4（Patil 等人，ICML 2025）

BFCL 是 2026 年事实上的评估标准。V4 的构成如下：

- **智能体任务（40%）**——完整的智能体轨迹：记忆、多轮交互、动态决策。
- **多轮对话（30%）**——包含工具链的交互式对话。
- **实时场景（10%）**——用户提交的真实提示（分布更困难）。
- **非实时场景（10%）**——合成测试用例。
- **幻觉检测（10%）**——检测何时不应调用任何工具。

V3 引入了基于状态的评估：在一系列工具调用后，检查 API 的实际状态（例如"文件是否已创建？"），而不是比对工具调用的 AST。V4 增加了网络搜索、记忆和格式敏感性类别。

2026 年的关键发现：单轮函数调用已接近解决。失败主要集中在记忆（在轮次间传递上下文）、动态决策（根据先前结果选择工具）、长序列链（20 步后出现漂移）和幻觉检测（当没有合适工具时拒绝调用）。

### 工具模式

每个提供商都有各自的模式。细节各不相同，但整体结构一致：

```
name: 字符串
description: 字符串（功能说明及使用时机）
input_schema: JSON Schema（属性、必填字段、类型、枚举值）
```

Anthropic 直接使用 `input_schema`。OpenAI 使用 `function.parameters`。两者都接受 JSON Schema。描述说明至关重要——模型通过阅读描述来选择合适的工具。糟糕的工具描述是"选错工具"类故障的头号根源。

### 参数验证

绝不信任任何工具调用。需验证：

1. **类型强制转换。** 模型可能返回字符串 `"5"` 而模式要求 int。如果转换无歧义则强制转换；否则拒绝。
2. **枚举值验证。** 如果模式规定 `status in {"open", "closed"}` 而模型输出 `"in_progress"`，则返回描述性错误拒绝。
3. **必填字段。** 缺少必填字段时，直接将结构化的错误观察结果返回给模型，而不是崩溃。
4. **格式验证。** 日期、电子邮件、URL——使用具体解析器（而非正则表达式）进行验证。

每一次验证失败都应返回结构化的观察结果，以便模型用正确的格式重试。

### 并行工具调用

现代提供商支持在单次助手回复中并行调用多个工具。流程如下：

1. 模型发出 3 个带有不同 `tool_use_id` 的工具调用。
2. 运行时执行这些调用（若相互独立则并行执行）。
3. 每个结果作为 `tool_result` 块返回，通过 `tool_use_id` 关联。

工程原则：将关联 ID 视为承载关键信息。一旦交换，就会导致工具与结果错误对应。

### 沙箱

工具执行是沙箱的边界。详见第 09 课。简而言之：每个工具都应指定读/写范围、网络访问权限、超时时间和内存上限。泛化的 `run_shell(cmd)` 是危险信号；具体的 `git_status()` 更安全。

## 动手构建

`code/main.py` 实现了一个生产级工具注册中心：

- JSON Schema 子集验证器（仅标准库）。
- 工具注册，包含描述、输入模式、超时时间和执行器。
- 参数类型强制转换和枚举值验证。
- 带关联 ID 的并行工具调度。
- 结构化的错误观察结果。

运行方式：

```
python3 code/main.py
```

运行轨迹展示了一个迷你智能体在一轮中调用三个工具，其中一个故意格式错误的调用被拒绝，并返回了模型可据此操作的描述性错误。

## 使用

每个提供商都有自己的工具模式——Anthropic、OpenAI、Gemini、Bedrock。如果需要支持多个提供商，请使用转换层（OpenAI Agents SDK、Vercel AI SDK、LangChain 工具适配器）。BFCL 是参考基准——如果工具使用是产品的核心功能，在发布前请用 BFCL 对智能体进行测试。

## 练习

1. 添加一个"空操作"工具，让模型可以明确拒绝使用任何其他工具。在类似 BFCL 的幻觉测试上进行评估。
2. 实现将字符串形式的 int 和字符串形式的 float 进行类型强制转换。强制转换在什么情况下开始掩盖真正的 bug？
3. 为每个工具添加超时和断路器（连续 3 次失败后，60 秒内拒绝该工具）。这会如何改变模型的恢复方式？
4. 阅读 BFCL V4 的描述。选择一个类别（例如"多轮对话"），用你的智能体运行 10 个示例提示。报告通过率。
5. 将标准库验证器移植到 Pydantic 或 Zod。Pydantic/Zod 发现了哪些简易验证器遗漏的问题？

## 关键术语

| 术语 | 表面含义 | 实际含义 |
|------|----------|----------|
| 函数调用 | "工具使用" | 带模式验证的结构化输出工具调用 |
| Toolformer | "自监督工具标注" | Schick 2023 — 保留其结果能降低下一个 token 损失的工具调用 |
| BFCL | "伯克利函数调用排行榜" | 2026 基准：40% 智能体任务、30% 多轮对话、10% 实时场景、10% 非实时场景、10% 幻觉检测 |
| 工具模式 | "给模型的函数签名" | 名称、描述、参数的 JSON Schema |
| tool_use_id | "关联 ID" | 将工具调用与其结果关联；对并行调度至关重要 |
| 幻觉检测 | "知道何时不调用" | V4 类别：当没有合适工具时拒绝调用 |
| 参数类型强制转换 | "字符串到整数的修复" | 对可预测的模式不匹配进行窄修复；存在歧义时拒绝 |
