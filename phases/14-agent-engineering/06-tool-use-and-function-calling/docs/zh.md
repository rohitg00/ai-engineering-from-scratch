# 工具使用與函數呼叫

> Toolformer（Schick 等人，2023）開啟了自監督的工具標註。Berkeley Function Calling Leaderboard V4（Patil 等人，2025）訂下 2026 年的門檻：40% 代理式、30% 多輪、10% live、10% non-live、10% 幻覺。單輪已經解決了。記憶、動態決策與長時程的工具鏈則還沒有。

**類型：** 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 14 · 01（代理迴圈）、階段 13 · 01（函數呼叫深潛）
**時間：** 約 60 分鐘

## 學習目標

- 解釋 Toolformer 的自監督訓練訊號：只有當執行工具能降低下一個詞元的損失時，才保留那則工具標註。
- 說出 BFCL V4 的五個評測類別，以及每個各在量什麼。
- 用 stdlib 實作一份工具註冊表，含 schema 驗證、參數強制轉型與執行沙箱。
- 診斷 2026 年的三個未解問題：長時程工具串接、動態決策，以及記憶。

## 問題所在

早期的工具使用問的是：模型能不能預測出一次正確的函數呼叫？現代的工具使用問的是：模型能不能跨 40 步串接工具，帶著記憶、在部分可觀測的情況下、能從工具失敗中復原，而且不會幻覺出根本不存在的工具？

Toolformer 立下了基線：模型可以用自監督學會何時該呼叫工具。BFCL V4 定義了 2026 年的評測目標。兩者之間的落差，就是生產代理所生活的那片空間。

## 核心概念

### Toolformer（Schick 等人，NeurIPS 2023）

構想：讓模型在自己的預訓練語料上標註候選的 API 呼叫。對每個候選，實際去執行它。只有當納入工具結果會降低下一個詞元的損失時，才保留該標註。再拿過濾後的語料去微調。

涵蓋的工具：計算機、問答系統、搜尋引擎、翻譯器、行事曆。自監督訊號純粹關於工具是否有助於預測文字 —— 沒有人工標註。

規模上的結果：工具使用是隨規模浮現的。較小的模型被工具標註拖累；較大的模型則獲益。這就是為什麼 2026 年的前沿模型內建了很強的工具使用能力，而多數 7B 模型得靠明確的工具使用微調才可靠。

### Berkeley Function Calling Leaderboard V4（Patil 等人，ICML 2025）

BFCL 是 2026 年事實上的評測。V4 的組成：

- **代理式（40%）** —— 完整的代理軌跡：記憶、多輪、動態決策。
- **多輪（30%）** —— 帶工具鏈的互動式對話。
- **Live（10%）** —— 使用者提交的真實提示詞（分布更難）。
- **Non-Live（10%）** —— 合成的測試案例。
- **幻覺（10%）** —— 偵測何時不該呼叫任何工具。

V3 引入了基於狀態的評測：在一串工具序列之後，去檢查 API 的實際狀態（例如「檔案建好了嗎？」），而不是去比對工具呼叫的 AST。V4 加上了網頁搜尋、記憶與格式敏感度等類別。

2026 年的關鍵發現：單輪函數呼叫已經接近解決。失敗集中在記憶（跨輪次帶著脈絡）、動態決策（依先前結果挑工具）、長時程串接（超過 20 步之後漂移），以及幻覺偵測（沒有合適工具時要拒絕呼叫）。

### 工具 schema

每家供應商都有一份 schema。細節有差，但共享同一種形狀：

```
name: string
description: string (what it does, when to use it)
input_schema: JSON Schema (properties, required, types, enums)
```

Anthropic 直接用 `input_schema`。OpenAI 用 `function.parameters`。兩者都吃 JSON Schema。描述是承重結構 —— 模型靠讀它們來挑對工具。糟糕的工具描述是「挑錯工具」這類失敗的頭號根因。

### 參數驗證

不要信任任何一次工具呼叫。要驗證：

1. **型別強制轉型。** schema 說是 int，模型卻可能回傳字串 `"5"`。若無歧義就轉；有歧義就拒絕。
2. **列舉驗證。** 若 schema 說 `status in {"open", "closed"}` 而模型吐出 `"in_progress"`，就用一段有描述性的錯誤拒絕它。
3. **必填欄位。** 少了必填欄位 -> 立刻把錯誤觀察回傳給模型，而不是崩潰。
4. **格式驗證。** 日期、電子郵件、URL —— 用實在的解析器驗，不要用正規表達式。

每一次驗證失敗都該回傳一段結構化的觀察，好讓模型能用正確的形狀重試。

### 平行工具呼叫

現代供應商支援在同一個助理輪次裡做平行工具呼叫。迴圈是：

1. 模型吐出 3 次工具呼叫，各帶不同的 `tool_use_id`。
2. 執行環境執行它們（相互獨立的話就平行跑）。
3. 每個結果以 `tool_result` 區塊回去，依 `tool_use_id` 關聯。

工程規則：把關聯 ID 當成承重結構。把它們調換掉，你就會得到「錯的工具配到錯的結果」這種路由。

### 沙箱化

工具執行就是沙箱邊界。細節見第 09 課。簡短版：每項工具都該指明讀寫表面、網路存取、逾時、記憶體上限。泛用的 `run_shell(cmd)` 是紅旗；專用的 `git_status()` 比較安全。

## 動手實作

`code/main.py` 實作一份生產形狀的工具註冊表：

- JSON Schema 子集的驗證器（只用 stdlib）。
- 工具註冊，含描述、輸入 schema、逾時與執行器。
- 參數強制轉型與列舉驗證。
- 帶關聯 ID 的平行工具分派。
- 把錯誤觀察做成結構化字串。

跑它：

```
python3 code/main.py
```

軌跡顯示一個迷你代理在同一輪裡呼叫三項工具，其中一次是刻意做成畸形的呼叫，會被以一段模型可以據以行動的描述性錯誤拒絕。

## 框架應用

每家供應商都有自己的工具 schema —— Anthropic、OpenAI、Gemini、Bedrock。如果你需要多供應商，就用一層轉譯（OpenAI Agents SDK、Vercel AI SDK、LangChain 的 tool adapter）。BFCL 是那個參考基準 —— 如果工具使用是產品的核心，出貨前先拿它跑你的代理。

## 練習

1. 加一項「no-op」工具，讓模型能明確拒絕使用任何其他工具。在一個 BFCL 式的幻覺測試上量它。
2. 替「int 寫成字串」與「float 寫成字串」實作參數強制轉型。轉型從哪裡開始會掩蓋掉真正的臭蟲？
3. 加上逐工具的逾時與斷路器（連續失敗 3 次後，該工具 60 秒內拒絕服務）。這會改變模型復原的方式嗎？
4. 讀 BFCL V4 的說明。挑一個類別（例如「多輪」），拿 10 則範例提示詞跑你的代理。回報通過率。
5. 把那個 stdlib 驗證器移植到 Pydantic 或 Zod。Pydantic／Zod 抓到了哪些這個玩具漏掉的東西？

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 函數呼叫 | 「工具使用」 | 帶已驗證 schema 的結構化輸出式工具調用 |
| Toolformer | 「自監督的工具標註」 | Schick 2023 —— 只保留那些結果能降低下一詞元損失的工具呼叫 |
