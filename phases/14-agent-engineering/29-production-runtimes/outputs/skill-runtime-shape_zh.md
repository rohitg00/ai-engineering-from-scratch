给定一个任务类别（预期持续时间、步骤数、触发类型、延迟预算），选择运行时形态。

决策：

1. < 30s，用户等待 → **请求-响应**。
2. 渐进式用户体验或语音 → **流式**。
3. 数分钟到数小时，用户不等待 → **基于队列**。
4. 响应外部事件 → **事件驱动**。
5. 定期维护 → **定时任务**。
6. 以上任何场景中重启成本较高 → 添加**持久化执行**。

产出：

1. 你的技术栈中的形态框架。
2. 可观测性：OTel GenAI span（第 23 课），后端接入（第 24 课）。
3. 对于队列：DLQ + 重试策略 + 队列深度指标。
4. 对于事件：显式的订阅者注册表 + 重放路径。
5. 对于定时任务：锁文件或分布式锁以防止重叠运行。
6. 对于持久化：检查点后端 + 恢复语义。

硬性拒绝：

- 对 5 分钟任务使用同步 HTTP。用户会挂断；工作者会堆积。
- 基于队列但没有 DLQ。失败的任务会消失。
- 后台工作没有追踪导出。失败不可见，直到用户投诉。
- "没有持久化状态，我们会重试。"长时间任务必须设置检查点。

拒绝规则：

- 如果产品有 SLA + 重放要求，拒绝群组拓扑 + 非持久化运行时。
- 如果任务受合规约束，拒绝没有审计跟踪的事件驱动方案。
- 如果用户想要定时任务 + 无锁，拒绝。重叠的定时任务充其量是重复工作，最坏情况下是数据损坏。

输出：运行时框架 + 可观测性钩子 + 包含 SLA、重试策略、检查点选择的 README。以"下一步阅读"结尾，指向第 23 课（OTel）、第 24 课（可观测性）或第 17 课（Managed Agents 用于托管长时间运行的任务）。
