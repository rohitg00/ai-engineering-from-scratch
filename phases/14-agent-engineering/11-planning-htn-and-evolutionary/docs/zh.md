# 用 HTN 與演化式搜尋做規劃

> 符號式規劃處理那些計畫必須可證明正確的情況。演化式程式碼搜尋處理那些適應度函數是機器可檢核的情況。ChatHTN（2025）與 AlphaEvolve（2025）展示了各自跟 LLM 配對後能解鎖什麼。

**類型：** 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 14 · 02（ReWOO 與 Plan-and-Execute）
**時間：** 約 75 分鐘

## 學習目標

- 解釋階層式任務網路：任務、方法、運算子、前置條件、效果。
- 描述 ChatHTN 的混合迴圈 —— 符號式搜尋配上 LLM 退路分解。
- 解釋 AlphaEvolve 的演化迴圈，以及它為何只有在有程式化評估器時才行得通。
- 用 stdlib 實作一個玩具版 HTN 規劃器，外加一個玩具版演化式搜尋。

## 問題所在

ReWOO（第 02 課）、Plan-and-Execute 與 ReAct 涵蓋了多數的代理規劃。有兩種情況它們涵蓋得不好：

1. **正確性可證明的計畫。** 排程、航線規劃、法遵工作流 —— 計畫必須依構造就是健全的。一份流暢但偶爾幻覺出某個步驟的 LLM 計畫是不可接受的。
2. **有機器可檢核適應度函數的最佳化。** 矩陣乘法、排程啟發式、編譯器 pass —— 目標不是「一份正確的計畫」，而是「最好的那份計畫」。

HTN 規劃與 AlphaEvolve 解的是兩個不同的問題。兩者都把 LLM 當成放大器，不是替代品。

## 核心概念

### 階層式任務網路

一個 HTN 由這些構成：

- **任務** —— 複合的（待分解）與原始的（可直接執行）。
- **方法** —— 把複合任務分解成子任務的做法，帶前置條件。
- **運算子** —— 帶前置條件與效果的原始行動。
- **狀態** —— 一組事實。

規劃：給定一個目標任務與初始狀態，找出一個分解，使其成為一串前置條件依序都被滿足的原始運算子。

HTN 比 LLM 還老，而且到今天仍是「可證明正確的計畫」的參考做法。

### ChatHTN（Gopalakrishnan 等人，2025）

ChatHTN（arXiv:2505.11814）把符號式 HTN 與 LLM 查詢交錯起來：

1. 先試著用既有的方法分解當前的複合任務。
2. 若沒有方法適用，就問 LLM：「在狀態 `s` 下，你會怎麼分解 `task`？」
3. 把 LLM 的回應轉譯成候選子任務。
4. 對照運算子 schema 驗證；拒絕無效的分解。
5. 遞迴。

論文的核心主張：產出的每一份計畫都可證明健全，因為 LLM 的建議只會以候選分解的身分進來，絕不會直接編輯計畫。符號層擁有正確性；LLM 則擴充方法庫。

線上方法學習（OpenReview `gwYEDY9j2x`，2025 年的後續）加了一個學習器，用回歸把 LLM 產出的分解一般化 —— 把 LLM 查詢頻率削掉最多 75%。

### AlphaEvolve（Novikov 等人，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是另一種東西：由 Gemini 2.0 Flash/Pro 集成所編排的演化式程式碼搜尋。

迴圈：

1. 從一支種子程式 + 一個程式化評估器（回傳適應度分數）開始。
2. 一群 LLM 集成提出突變。
3. 讓突變跑過評估器。
4. 留下最好的；再突變。

已發表的斬獲：

- 56 年來第一次在 4x4 複數矩陣乘法上勝過 Strassen（48 次純量乘法）。
- 透過一項 Borg 排程啟發式，替 Google 收回 0.7% 的運算量。
- 在一項前沿工作負載上讓 FlashAttention 加速 32%。

硬性條件：適應度函數必須是機器可檢核的。在散文式答案上做演化式搜尋不會收斂。

### 什麼時候用哪個

| 問題類別 | 用 | 為什麼 |
|---------------|-----|-----|
| 帶硬性限制的排程 | HTN + ChatHTN | 可證明的健全性 |
| 編譯器最佳化 | AlphaEvolve | 機器可檢核的適應度 |
| 多步驟的任務執行 | ReAct / ReWOO | LLM 在迴圈裡，沒有形式保證 |
| 有測試的程式碼改善 | AlphaEvolve | 測試就是評估器 |
| 受政策約束的自動化 | HTN | 前置條件把政策編碼進去 |

### 這套模式在哪裡會出錯

- **沒有運算子的 HTN。** 少了前置條件／效果的 schema，健全性主張就垮了。ChatHTN 那套「LLM 提出分解」需要 schema 去拒絕無效的走法。
- **沒有真評估器的 AlphaEvolve。** 「問 LLM 這段程式碼是不是比較好」不是適應度函數。評估器必須是決定性且快速的。
- **過度工程。** 多數代理任務兩者都不需要。先伸手拿 ReAct 或 ReWOO。

## 動手實作

`code/main.py` 實作了兩個玩具：

- 一個 stdlib 的 HTN 規劃器，含運算子、方法、前置條件、效果，以及一個在沒有方法能匹配複合任務時介入的 `LLMFallback`。那個「LLM」是腳本化的分解器，所以規劃器可以離線跑。
- 一個對算術程式做的 stdlib 演化式搜尋：長出一些運算式，讓其輸出在測試集上最小化 `|f(x) - target|`。評估器是決定性的。

跑它：

```
python3 code/main.py
```

軌跡顯示 HTN 規劃器分解一個複合任務（中途會走一次 LLM 退路），以及那個演化迴圈收斂到目標運算式。

## 框架應用

- **HTN 規劃器** —— `pyhop`、`SHOP3`，或為了領域專屬的政策強制而自己蓋一個。
- **ChatHTN** —— 研究用程式碼；那套模式（符號式 + LLM 退路）可以乾淨地移植到任何 HTN 規劃器上。
- **AlphaEvolve** —— DeepMind 的論文；那套模式（集成 + 評估器）是可重現的。OpenEvolve 與類似的開源分支正在冒出來。
- **代理框架** —— 目前還沒有哪個把 HTN 或 AlphaEvolve 當一等公民出貨。把它蓋成子代理或背景 worker。

## 產出交付

`outputs/skill-hybrid-planner.md` 會產出一份混合規劃器鷹架（HTN 或演化式），並把 LLM 的角色明確劃定範圍。

## 練習

1. 替 HTN 規劃器擴充回溯：當某個運算子的後置條件在執行期失敗時，回捲並試下一個方法。
2. 給 ChatHTN 加一份 LLM 方法快取：當 LLM 在狀態樣式 `P` 下分解任務 `T` 時，把結果存起來。下一次呼叫前先重新檢查方法庫。
3. 把演化式搜尋的評估器換成真正的測試套件。演化出一個能通過 20 個測試案例的排序函數；回報收斂所需的世代數。
4. 讀 AlphaEvolve 關於評估器設計的筆記。替一個你在意的領域設計一個評估器（SQL 查詢最佳化、測試套件最小化、部署 YAML）。
5. 合起來用：用 HTN 把一個複合任務分解成子任務，再對每個子任務的原始運算子做演化式搜尋。它在哪裡發光，又在哪裡過度工程？

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| HTN | 「階層式規劃器」 | 帶運算子、前置條件、效果的任務分解 |
| 方法 | 「分解規則」 | 把複合任務拆成子任務的做法 |
| 運算子 | 「原始行動」 | 帶前置條件與效果的具體步驟 |
| ChatHTN | 「LLM + HTN」 | 沒有方法匹配時，符號式規劃器就去問 LLM |
| AlphaEvolve | 「演化式程式碼搜尋」 | 一群 LLM 集成突變程式碼；決定性評估器負責選擇 |
| 適應度函數 | 「評估器」 | 對輸出給出決定性、機器可檢核的分數 |
| 線上方法學習 | 「被快取的 LLM 分解」 | 把 LLM 的計畫存下並一般化，以削減查詢成本 |
