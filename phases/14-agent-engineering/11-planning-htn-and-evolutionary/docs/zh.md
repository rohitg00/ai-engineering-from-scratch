# 基于 HTN 与进化搜索的规划

> 符号化规划处理方案可被证明正确的场景，进化代码搜索处理适应度函数可被机器检验的场景。ChatHTN（2025）与 AlphaEvolve（2025）展示了各自在与 LLM 结合时能解锁怎样的能力。

**类型：** 动手构建
**语言：** Python（标准库）
**前置要求：** 阶段 14 · 02（ReWOO 与 Plan-and-Execute）
**时长：** ~75 分钟

## 学习目标

- 解释层次化任务网络：任务、方法、算子、前置条件、效果。
- 描述 ChatHTN 的混合循环——符号化搜索与 LLM 兜底分解。
- 解释 AlphaEvolve 的进化循环及其为何仅适用于程序化评估器。
- 使用标准库实现一个玩具级 HTN 规划器和一个玩具级进化搜索。

## 问题

ReWOO（第 02 课）、Plan-and-Execute 和 ReAct 覆盖了大多数智能体规划场景。但有两类情况它们难以胜任：

1. **需确保正确性的方案。** 调度、航线规划、合规工作流——方案必须从构造上就是正确的。一个流畅的 LLM 方案偶尔幻觉出一个步骤是不可接受的。
2. **具备可机器检验适应度函数的优化问题。** 矩阵乘法、调度启发式算法、编译器优化——目标不是"一个正确的方案"，而是"最优的方案"。

HTN 规划与 AlphaEvolve 分别解决了上述两个问题。两者都将 LLM 作为放大器，而非替代品。

## 概念

### 层次化任务网络

HTN 的构成：

- **任务**——复合任务（需分解）和原始任务（可直接执行）。
- **方法**——将复合任务分解为子任务的方式，附带前置条件。
- **算子**——具有前置条件和效果的原始动作。
- **状态**——一组事实的集合。

规划过程：给定一个目标任务和初始状态，寻找一种分解方式，将其拆解为按顺序满足各前置条件的原始算子。

HTN 的历史比 LLM 更悠久，至今仍是可证明正确方案的参考范式。

### ChatHTN（Gopalakrishnan 等，2025）

ChatHTN（arXiv:2505.11814）将符号化 HTN 与 LLM 查询交错执行：

1. 尝试使用已有方法分解当前复合任务。
2. 若无方法适用，则询问 LLM："在状态 `s` 下，你将如何分解任务 `task`？"
3. 将 LLM 的响应翻译为候选子任务。
4. 根据算子模式进行验证；拒绝无效的分解。
5. 递归执行。

该论文的核心主张是：生成的每个方案都是可证明正确的，因为 LLM 的建议仅作为候选分解进入流程，而从不直接编辑方案。符号化层掌握正确性；LLM 负责扩展方法库。

在线方法学习（OpenReview `gwYEDY9j2x`，2025 年后续工作）增加了一个学习器，通过回归泛化 LLM 生成的分解——将 LLM 查询频率最多降低 75%。

### AlphaEvolve（Novikov 等，2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是一种不同范式：由 Gemini 2.0 Flash/Pro 集成体编排的进化代码搜索。

循环流程：

1. 从种子程序 + 程序化评估器（返回适应度分数）开始。
2. LLM 集成体提出变异方案。
3. 将变异方案交由评估器运行。
4. 保留最佳方案；再次变异。

已公布的成果：

- 56 年来首次改进 Strassen 算法在 4x4 复数矩阵乘法上的表现（48 次标量乘法）。
- 通过 Borg 调度启发式算法回收 0.7% 的 Google 算力。
- 在某前沿工作负载上实现 32% 的 FlashAttention 加速。

硬性约束：适应度函数必须可被机器检验。对文本答案进行进化搜索不会收敛。

### 何时使用何种方法

| 问题类别 | 使用 | 原因 |
|---------------|-----|-----|
| 带硬约束的调度 | HTN + ChatHTN | 可证明的正确性 |
| 编译器优化 | AlphaEvolve | 可机器检验的适应度 |
| 多步骤任务执行 | ReAct / ReWOO | LLM 在循环中，无形式化保证 |
| 带测试的代码改进 | AlphaEvolve | 测试即评估器 |
| 基于策略的自动化 | HTN | 前置条件编码策略 |

### 该模式在何处容易出错

- **缺少算子的 HTN。** 如果没有前置条件/效果模式，正确性声称就失去了基础。ChatHTN 的"LLM 建议分解"需要模式来拒绝无效操作。
- **缺少真正评估器的 AlphaEvolve。** "问 LLM 代码是否更好"并非适应度函数。评估器必须是确定性的且快速。
- **过度工程化。** 大多数智能体任务并不需要上述任一方法。应优先考虑 ReAct 或 ReWOO。

## 动手构建

`code/main.py` 实现了两个玩具级示例：

- 一个标准库 HTN 规划器，包含算子、方法、前置条件、效果，以及一个在无方法匹配复合任务时触发的 `LLMFallback`。"LLM"是一个脚本化分解器，以便规划器可离线运行。
- 一个基于标准库的进化搜索，用于算术程序：进化出在测试集上使 `|f(x) - target|` 最小化的表达式。评估器是确定性的。

运行方式：

```
python3 code/main.py
```

输出轨迹展示了 HTN 规划器分解复合任务（过程中包含 LLM 兜底）的过程，以及进化循环收敛到目标表达式的过程。

## 使用方式

- **HTN 规划器**——`pyhop`、`SHOP3`，或自行构建用于特定领域的策略执行。
- **ChatHTN**——研究级代码；其模式（符号化 + LLM 兜底）可干净地移植到任何 HTN 规划器。
- **AlphaEvolve**——DeepMind 论文；其模式（集成体 + 评估器）是可复现的。OpenEvolve 及类似开源分支正在涌现。
- **智能体框架**——目前尚无框架原生提供一流的 HTN 或 AlphaEvolve 支持。可作为子智能体或后台工作进程来构建。

## 交付物

`outputs/skill-hybrid-planner.md` 生成一个混合规划器脚手架（HTN 或进化型），其中 LLM 的角色被明确限定。

## 练习

1. 为 HTN 规划器添加回溯功能：当算子的后置条件在运行时失败时，回滚并尝试下一种方法。
2. 为 ChatHTN 添加 LLM 方法缓存：当 LLM 在状态模式 `P` 下分解任务 `T` 时，存储结果。下次调用时先检查方法库。
3. 将进化搜索的评估器替换为真实测试套件。进化出一个能通过 20 个测试用例的排序函数；报告收敛所需的代数。
4. 阅读 AlphaEvolve 的评估器设计笔记。为你关注的领域（SQL 查询优化、测试套件最小化、部署 YAML）设计一个评估器。
5. 组合使用：使用 HTN 将复合任务分解为子任务，然后对每个子任务的原始算子进行进化搜索。分析该组合在何处表现出色，在何处过度工程化。

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|----------------|------------------------|
| HTN | "层次化规划器" | 基于算子、前置条件、效果的任务分解 |
| 方法 | "分解规则" | 将复合任务拆解为子任务的方式 |
| 算子 | "原始动作" | 具有前置条件和效果的具体步骤 |
| ChatHTN | "LLM + HTN" | 符号化规划器在无方法匹配时询问 LLM |
| AlphaEvolve | "进化代码搜索" | LLM 集成体变异代码；确定性评估器进行选择 |
| 适应度函数 | "评估器" | 确定性的、可机器检验的输出评分 |
| 在线方法学习 | "缓存的 LLM 分解" | 存储并泛化 LLM 方案以降低查询成本 |
