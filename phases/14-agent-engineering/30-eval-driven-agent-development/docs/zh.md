# 評測驅動的代理開發

> Anthropic 的指引：「從簡單的提示詞開始，用完整的評測去最佳化它們，只有在需要時才加上多步驟的代理式系統。」評測不是最後一步。它是驅動階段 14 中其他每一項選擇的外圈迴圈。

**類型：** 學習 + 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 14 全部。
**時間：** 約 60 分鐘

## 學習目標

- 說出那三層評測 —— 靜態基準、自訂離線、線上生產 —— 以及各自的用途。
- 解釋 evaluator-optimizer 的緊迴圈。
- 描述 2026 年的最佳實務：評測跟程式碼放在一起、在 CI 裡跑、替 PR 設閘門。
- 把階段 14 的每一課都連到它所產生的評測案例。

## 問題所在

代理在示範裡都會過。它們在生產環境失敗的方式，是示範預測不了的。基準回答的是「這個模型廣泛來說有能力嗎？」，不是「這個代理有沒有替我的產品出對的修補？」答案是：三層評測、持續執行，並把每一道護欄與每一條學到的規則都對映到一個評測案例。

## 核心概念

### 三層評測

1. **靜態基準** —— 程式碼用 SWE-bench Verified（第 19 課）、瀏覽／桌面用 WebArena/OSWorld（第 20 課）、通才用 GAIA（第 19 課）、工具使用用 BFCL V4（第 06 課）。用在跨模型比較與回歸把關。汙染是真的：SWE-bench+ 發現 32.67% 的解答外洩。永遠要報 Verified／經 + 稽核過的分數。

2. **自訂離線評測** —— 你產品的形狀：
   - LLM-as-judge（Langfuse、Phoenix、Opik —— 第 24 課）。
   - 基於執行（跑那份修補、檢查測試）。
   - 基於軌跡（把行動序列跟黃金軌跡比對；OSWorld-Human 顯示頂尖代理是黃金軌跡的 1.4-2.7 倍）。

3. **線上評測** —— 生產環境：
   - 工作階段重播（Langfuse）。
   - 護欄觸發的警示（第 16、21 課）。
   - 逐步的成本／延遲追蹤（第 23 課的 OTel span）。

### Evaluator-optimizer（Anthropic）

那個緊迴圈：

1. 提議者產出輸出。
2. 評估器評判。
3. 精修直到評估器通過。

這是 Self-Refine（第 05 課）的一般化。任何你在意的代理流程，都可以用 evaluator-optimizer 包起來以求可靠。

### 2026 年的最佳實務

- 評測跟程式碼放在一起。
- 每個 PR 都在 CI 裡跑。
- 用評測分數替合併設閘門（例如「相對 main 的回歸不得超過 5%」）。
- 每一道護欄都對映到一個評測案例。
- 每一條學到的規則（Reflexion、pro-workflow 的 learn-rule）都對映到一個失敗案例。

### 把階段 14 串起來

階段 14 的每一課都產生評測案例：

| 課 | 它產生的評測案例 |
|--------|------------------------|
| 01 代理迴圈 | 預算耗盡、無窮迴圈守衛 |
| 02 ReWOO | 工具失敗時規劃器有正確重規劃 |
| 03 Reflexion | 學到的反思在重試時有被套用 |
| 05 Self-Refine/CRITIC | 裁判讓精修後的輸出通過 |
| 06 工具使用 | 參數強制轉型有效；未知工具被拒 |
| 07-10 記憶 | 檢索的引用與來源相符；過期事實會失效 |
| 12 工作流模式 | 每種模式都產出正確輸出 |
| 13 LangGraph | 續跑能一模一樣地重現狀態 |
| 14 AutoGen 演員 | DLQ 接住崩掉的處理器 |
| 16 OpenAI Agents SDK | 護欄在對的輸入上被絆到 |
| 17 Claude Agent SDK | 子代理的結果回到編排者身上 |
| 19-20 基準 | SWE-bench Verified 分數、WebArena 成功率、OSWorld 效率 |
| 21 Computer Use | 逐步安全抓到被注入的 DOM |
| 23 OTel | Span 發出必要的屬性 |
| 26 失敗模式 | 偵測器替已知失敗貼標 |
| 27 提示詞注入 | PVE 拒絕被投毒的檢索 |
| 28 編排 | Supervisor 路由到對的專家 |
| 29 執行環境形狀 | DLQ 撐得住 N% 的失敗 |

如果你的評測套組對每一項都有案例，那你就把階段 14 涵蓋完了。

### 評測驅動開發在哪裡會失敗

- **沒有基線。** 沒有最後已知良好版本的評測是讀不懂的。要把基線存起來。
- **沒有接地的 LLM 裁判。** 裁判也會幻覺。CRITIC 模式（第 05 課）—— 讓裁判接地在外部工具上。
- **對評測過擬合。** 為評測最佳化會偏離生產環境的實用性。要輪換案例。
- **不穩的評測。** 非決定性的案例造成假警報。釘住種子、對狀態拍快照。

## 動手實作

`code/main.py` 是一個 stdlib 的評測執行框架：

- 帶類別（benchmark、custom、online）的案例註冊表。
- 一個受測的腳本化代理。
- Evaluator-optimizer 迴圈：提議、評判、精修，直到通過或達最大回合數。
- CI 閘門：彙總通過率 + 相對基線的回歸。

跑它：

```
python3 code/main.py
```

輸出：逐案例的通過／失敗、回歸旗標、CI 閘門裁決。

## 框架應用

- 把評測案例寫在跟代理程式碼同一個儲存庫裡。
- 每個 PR 都透過 CI 跑它們。
- 有回歸就讓建置失敗。
- 追蹤通過率隨時間的變化。
- 把每一次生產失敗都綁上一個新案例。

## 產出交付

`outputs/skill-eval-suite.md` 會替一個代理產品蓋出一套三層評測套組，含 CI 閘門與回歸追蹤。

## 練習

1. 挑一次你的生產失敗。寫一個能重現它的評測案例。你的代理現在過得了嗎？
2. 替你的領域做一份三個維度（事實、語氣、範圍）的 LLM 裁判評分準則。替 50 個工作階段評分。
3. 把評測套組接進 CI。回歸 >=5% 就讓建置失敗。
4. 加一個軌跡效率指標：代理走了幾步、相對於黃金軌跡是多少？
5. 把階段 14 的每一課都對映到你套組裡的一個評測案例。有漏的嗎？那就是要補的缺口。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| 靜態基準 | 「現成的評測」 | SWE-bench、GAIA、AgentBench、WebArena、OSWorld |
| 自訂離線評測 | 「領域評測」 | 在你產品形狀上做的 LLM-as-judge／執行／軌跡評測 |
| 線上評測 | 「生產評測」 | 工作階段重播、護欄警示、成本／延遲追蹤 |
| Evaluator-optimizer | 「提議—評判—精修」 | 迭代直到裁判通過 |
| CI 閘門 | 「合併阻擋器」 | 評測回歸就讓建置失敗 |
| 基線 | 「最後已知良好版本」 | 用來偵測回歸的參考分數 |
| 軌跡效率 | 「相對黃金軌跡的步數」 | 代理步數除以人類專家的最少步數 |
