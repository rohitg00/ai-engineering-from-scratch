# 智能体可观测性：Langfuse、Phoenix、Opik

> 2026年，三大开源智能体可观测性平台占据主导地位。Langfuse（MIT 许可）—— 月安装量超600万，提供追踪 + 提示管理 + 评估 + 会话回放。Arize Phoenix（Elastic 2.0 许可）—— 深度智能体特定评估、RAG 相关性、OpenInference 自动插桩。Comet Opik（Apache 2.0 许可）—— 自动化提示优化、护栏、LLM 判官幻觉检测。

**类型：** 学习
**语言：** Python（标准库）
**前置要求：** 阶段14 · 23课（OTel GenAI）
**时长：** 约45分钟

## 学习目标

- 列举三大顶级开源智能体可观测性平台及其许可证。
- 区分各平台最强能力：Langfuse（提示管理 + 会话），Phoenix（RAG + 自动插桩），Opik（优化 + 护栏）。
- 解释为何到2026年89%的组织报告已具备智能体可观测性能力。
- 实现基于标准库的追踪到仪表盘管道，并集成 LLM 判官评估。

## 问题

OTel GenAI（第23课）提供了模式规范。你仍然需要能够接收跨度、运行评估、存储提示版本并发现回归问题的平台。三个竞争者各有所长，专注于生命周期的不同环节。

## 概念解析

### Langfuse（MIT 许可）

- 月 SDK 安装量超600万，GitHub 星标数超1.9万。
- 功能：追踪、带版本控制和沙盒的提示管理、评估（LLM 做判官、用户反馈、自定义）、会话回放。
- 2025年6月：原商业模块（LLM 做判官、标注队列、提示实验、沙盒）在 MIT 许可下开源。
- 最强能力：端到端可观测性，紧密结合提示管理闭环。

### Arize Phoenix（Elastic License 2.0）

- 更深入的智能体特定评估：追踪聚类、异常检测、RAG 检索相关性。
- 原生 OpenInference 自动插桩。
- 可与托管版 Arize AX 配对用于生产环境。
- 没有提示版本管理——定位为漂移/行为回归工具，与更广泛的平台配合使用。
- 最强能力：RAG 相关性、行为漂移、异常检测。

### Comet Opik（Apache 2.0）

- 通过 A/B 实验实现自动化提示优化。
- 护栏（PII 脱敏、主题约束）。
- LLM 判官幻觉检测。
- Comet 自身测量基准：Opik 日志 + 评估耗时23.44秒，Langfuse 327.15秒（约14倍差异）—— 供应商基准数据仅供参考。
- 最强能力：优化循环、自动化实验、护栏强制执行。

### 行业数据

据 Maxim（2026年领域分析）：89%的组织已部署智能体可观测性；质量问题是最主要的生产环境障碍（32%的受访者提及）。

### 如何选择

| 需求 | 选择 |
|------|------|
| 一站式方案，含提示管理 | Langfuse |
| 深度 RAG 评估 + 漂移检测 | Phoenix |
| 自动化优化 + 护栏 | Opik |
| 开放许可，无 ELv2 | Langfuse（MIT）或 Opik（Apache 2.0） |
| Datadog / New Relic 集成 | 任意均可——它们都导出 OTel |

### 此模式的常见误区

- **没有评估策略。** 没有评估的追踪只是昂贵的日志记录。
- **自建 LLM 判官但缺乏 grounding。** CRITIC 模式（第5课）同样适用——判官需要外部工具进行事实核查。
- **提示版本未与追踪关联。** 当生产环境出现回归时，无法二分定位到引发问题的提示版本。

## 动手实现

`code/main.py` 实现了一个基于标准库的追踪收集器 + LLM 判官评估器：

- 接收 GenAI 格式的跨度数据。
- 按会话分组，标记失败的运行（触发护栏、低置信度评估）。
- 一个脚本化的 LLM 判官，按评分标准对智能体响应进行打分。
- 一个仪表盘风格的摘要：失败率、主要失败原因、评估分数分布。

运行方式：

```
python3 code/main.py
```

输出：每个会话的评估分数和失败分类，与 Langfuse/Phoenix/Opik 的展示方式一致。

## 使用方式

- **Langfuse** 自托管或云服务；通过 OTel 或 SDK 接入。
- **Arize Phoenix** 自托管；自动插桩 OpenInference。
- **Comet Opik** 自托管或云服务；自动化优化循环。
- **Datadog LLM 可观测性** 适用于已在运行 Datadog 的混合运维+ML 团队。

## 练习

1. 导出一周的 OTel 追踪数据到 Langfuse 云（免费层）。哪些会话失败了？原因是什么？
2. 为你自己的领域编写一个 LLM 判官评分标准（事实正确性、语气、范围遵从性）。在50条追踪数据上测试。
3. 比较 Langfuse 的提示版本管理与 Phoenix 的追踪聚类。哪种方法能更快告诉你哪里出了问题？
4. 阅读 Opik 的护栏文档。为你的某个智能体运行接入 PII 脱敏护栏。
5. 在自己的语料上对三个平台进行基准测试。忽略供应商发布的数据，自己实测。

## 关键术语

| 术语 | 通常说法 | 实际含义 |
|------|----------|----------|
| 追踪 | "跨度收集器" | 接收 OTel/SDK 跨度；按会话索引 |
| 提示管理 | "提示内容管理系统" | 版本化的提示，与追踪关联 |
| LLM 做判官 | "自动化评估" | 独立的 LLM 按评分标准对智能体输出打分 |
| 会话回放 | "追踪回放" | 逐步回放过去的运行以进行调试 |
| RAG 相关性 | "检索质量" | 检索到的上下文是否匹配查询 |
| 追踪聚类 | "行为分组" | 对相似运行进行聚类以检测漂移 |
| 护栏强制执行 | "日志时的策略" | 对记录内容进行 PII/毒性/范围检查 |
