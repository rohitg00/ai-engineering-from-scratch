# Anthropic 工作流模式：简单优于复杂

> Schluntz 与 Zhang（Anthropic，2024年12月）将**工作流**（预定义路径）与**智能体**（动态工具使用）区分开来。五种工作流模式可覆盖大多数场景。从直接 API 调用开始，仅当步骤无法预判时再引入智能体。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**前置知识：** 第14阶段 · 01（智能体循环）  
**时长：** ~60分钟  

## 学习目标

- 说出 Anthropic 的五种工作流模式的名称：提示链式调用、路由、并行化、编排器-工作者、评估器-优化器。
- 解释智能体与工作流的区别，以及每种模式带来的工程成本。
- 判断何时选择工作流而非智能体（反之亦然）。
- 在标准库中，针对一个模拟 LLM 实现全部五种模式。

## 问题

团队为那些仅需一次函数调用就能解决的问题，却倾向于使用多智能体框架。其代价是真实的：框架增加了层级，掩盖了提示词（prompt），隐藏了控制流，并引入了过早的复杂性。Schluntz 与 Zhang 于 2024 年 12 月发表的文章是业界最受引用的反思之作：从简单开始，只有当复杂性证明了其价值时才引入。

## 概念

### 工作流 vs 智能体

- **工作流（Workflow）。** 通过预定义的代码路径编排 LLM 和工具。工程师拥有图的所有权。
- **智能体（Agent）。** LLM 动态地指导自己的工具，并自主执行步骤。模型拥有图的所有权。

两者各有其适用场景。工作流更便宜、更快且更易于调试。智能体能够解决开放式问题，但其失败模式更难推理。

### 增强型 LLM

所有五种模式的基础：一个 LLM 配备三种能力——搜索（检索）、工具（操作）、记忆（持久化）。任何 API 调用都可以使用这些能力。

### 五种模式

1. **提示链式调用（Prompt chaining）。** 第一次调用的输出是第二次调用的输入。适用于任务具有清晰的线性分解的场景。各步骤之间可设置程序化门控。

2. **路由（Routing）。** 一个分类器 LLM 选择调用哪个下游 LLM 或工具。适用于不同类型的输入需要不同处理方式的情况（如一级支持 vs 退款 vs Bug 修复 vs 销售）。

3. **并行化（Parallelization）。** 并发执行 N 次 LLM 调用，聚合结果。有两种形态：分块（处理不同片段）和投票（相同提示，N 次运行，多数/综合）。

4. **编排器-工作者（Orchestrator-workers）。** 一个编排器 LLM 动态决定运行哪些工作者（也是 LLM），并综合它们的输出。类似于智能体循环，但编排器不会无限循环。

5. **评估器-优化器（Evaluator-optimizer）。** 一个 LLM 提出答案，另一个 LLM 对其进行评估。迭代直到评估通过。这是 Self-Refine（第05课）的泛化形式。

### 工作流优于智能体的场景

- **可预测的任务。** 如果你能列举出所有步骤，那就应该这么做。
- **成本可控的任务。** 工作流的步骤数量有上限；智能体可能失控螺旋。
- **合规性要求高的任务。** 审计人员希望直接读取工作流图，而不是从轨迹中推断。

### 智能体优于工作流的场景

- **开放式研究。** 当下一步取决于上一步的返回结果时。
- **变长任务。** 持续数分钟到数小时，且步骤数量未知的任务。
- **新领域。** 当你还不知道正确的工作流模式时——先探索，后固化。

### 上下文工程的配套学科

"面向 AI 智能体的有效上下文工程"（Anthropic 2025）将该相关学科正式化：20万 token 窗口是一个**预算**，而不是一个**容器**。包含什么、何时压缩、何时让上下文增长——这些问题在该课程第14阶段关于上下文压缩的课程中有详细讨论（重编号前为本课程第14阶段早期第06课）。

## 动手构建

`code/main.py` 使用 `ScriptedLLM` 实现了全部五种工作流模式：

- `prompt_chain(input, steps)` — 顺序执行。
- `route(input, classifier, handlers)` — 分类 + 分发。
- `parallel_vote(prompt, n, aggregator)` — N 次运行，聚合结果。
- `orchestrator_workers(task, workers)` — 编排器选择工作者。
- `evaluator_optimizer(task, proposer, evaluator, max_iter)` — 迭代直到通过。

运行方式：

```
python3 code/main.py
```

每种模式都会打印其运行轨迹。每种模式的代码量约为 10-15 行；而一个框架的成本则以千行计。

## 实际运用

- 大多数任务使用直接 API 调用。
- 仅当模式确实需要持久状态（LangGraph）、Actor 模型并发（AutoGen v0.4）或角色模板化（CrewAI）时才使用框架。
- 当你希望获得类似 Claude Code 的工具框架形态，而又不想重新实现时，可以选择 Claude Agent SDK。

## 交付产物

`outputs/skill-workflow-picker.md` 能够针对给定的任务描述选择正确的工作流模式，包括决策依据，以及当工作流不足以解决问题时转向智能体的重构路径。

## 练习

1. 实现带有置信度阈值的路由。低于阈值 -> 升级给人处理。对于一级支持用例，这个阈值应该设定在哪里？
2. 为 `parallel_vote` 添加超时机制。当某个调用挂起时会发生什么？如何聚合存在缺失投票的结果？
3. 将 `evaluator_optimizer` 改造成一个"强盗"算法：在每次迭代中保留排名前二的输出，以防止后期出现的好结果被后期出现的坏结果覆盖。
4. 将提示链式调用与路由结合起来：一个路由器选择三条链中的一条。衡量 token 成本，并与单一的"大提示词"方案进行比较。
5. 选择你的一个生产功能，绘制工作流图，统计步骤数量。在这种情况下，使用智能体真的会更好吗？

## 关键术语

| 术语 | 通常说法 | 实际含义 |
|------|----------|----------|
| 工作流 | "预定义流程" | 工程师所有的 LLM 和工具调用图 |
| 智能体 | "自主 AI" | 模型所有的图；动态工具导向 |
| 增强型 LLM | "带工具的 LLM" | LLM + 搜索 + 工具 + 记忆；原子单元 |
| 提示链式调用 | "顺序调用" | 第 N 次调用的输出是第 N+1 次调用的输入 |
| 路由 | "分类器分发" | 选择哪条链/哪个模型来处理输入 |
| 并行化 | "扇出" | N 次并发调用；通过分块或投票进行聚合 |
| 编排器-工作者 | "调度智能体" | 编排器 LLM 动态选择专家 LLM |
| 评估器-优化器 | "提议者 + 评判者" | 迭代直到评估通过；Self-Refine 的泛化 |
