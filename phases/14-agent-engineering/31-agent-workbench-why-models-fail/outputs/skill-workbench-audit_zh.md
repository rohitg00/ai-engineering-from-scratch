给定一个仓库路径和将在其中运行的智能体产品，审计七个工作台表面并生成就绪报告。

七个表面：

1. 指令：智能体首先读取的根文件（例如 `AGENTS.md`），简短，指向更深的规则。
2. 状态：持久的、机器可读的文件，记录任务、触及的文件、阻塞项、下一步动作。
3. 范围：每任务的契约，列出允许的文件、禁止的文件、验收标准、回滚计划。
4. 反馈：捕获命令、stdout、stderr、退出码的运行器，并将结果反馈到循环中。
5. 验证：运行测试、lint、类型检查、冒烟测试，并确认验收标准的门控。
6. 审查：由不同角色进行的二次检查，构建者不能标记自己的工作。
7. 交接：总结更改内容、原因、剩余内容以及下一步最佳动作的产物。

产出：

- 每个表面的分数：0 缺失、1 部分、2 健康。将每个分数与你观察到的文件或过程关联。
- 按杠杆排序的三个优先级：哪个缺失的表面如果首先添加会消除最多的失败模式。
- 一个机器可读的 `workbench_audit.json` 报告加上一个人可读的 `workbench_audit.md` 摘要。
- 最弱表面的起点补丁：将分数从 0 提升到 1 的最小文件更改。

硬性拒绝：

- 没有文件路径或过程引用的"健康"分数。没有证据的审计会腐烂。
- 单个合并的"智能体配置"表面。合并表面会在任务失败时隐藏哪个表面出了问题。
- 因为测试慢而跳过验证。如果验证不在工作台上，构建者就自己给自己的作业评分。

拒绝规则：

- 如果仓库根本没有测试命令，拒绝验证分数并将其作为阻塞性问题提出来。
- 如果仓库没有版本控制历史，拒绝交接分数并将其作为阻塞性问题提出来。
- 如果智能体产品以 root 身份或具有无限制文件访问权限运行，拒绝范围分数，直到定义了沙箱或写入列表。

输出结构：

```
workbench-audit/
├── workbench_audit.json
├── workbench_audit.md
├── patches/
│   └── <weakest-surface>.patch
└── README.md
```
