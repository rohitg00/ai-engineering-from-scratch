# ReWOO 与 Plan-and-Execute：解耦式规划

> ReAct 将思考与行动交织在同一个流程中。ReWOO 则将它们分离：先制定一个整体计划，然后执行。在 HotpotQA 上 token 消耗减少 5 倍，准确率提升 4%，并且可以将规划器蒸馏到 7B 模型中。Plan-and-Execute 对其进行了泛化；Plan-and-Act 将其扩展到网页导航场景。

**类型：** 构建  
**语言：** Python（标准库）  
**前置要求：** 阶段 14 · 01（Agent 循环）  
**时长：** ~60 分钟

## 学习目标

- 解释为什么 ReWOO 的规划器（Planner）/ 工作器（Worker）/ 求解器（Solver）分离相比 ReAct 的交织循环能节省 token 并提升鲁棒性。
- 实现一个计划 DAG、一个依赖排序执行器，以及一个组合工作器输出的求解器——全部基于标准库。
- 使用 2026 年 Anthropic 提出的"五种工作流模式"框架，判断何时任务应采用"先规划后执行"模式，何时应采用交织的 ReAct 模式。
- 认识到何时需要 Plan-and-Act 的合成计划数据来完成长 horizon 的网页或移动端任务。

## 问题所在

ReAct 的"思考-行动-观察"交织循环简单且灵活，但每次工具调用都必须携带全部历史上下文——包括之前的每一次思考。Token 用量随深度呈二次方增长。更糟的是：当工具在循环中途失败时，模型必须根据错误观察重新推导整个计划。

ReWOO（Xu 等人，arXiv:2305.18323，2023 年 5 月）注意到了这一问题并做出了一个抉择：先一次性规划完整计划，并行获取证据，最后组合答案。一次 LLM 调用来规划，N 次工具调用来获取证据（可并行），一次 LLM 调用来求解。代价是灵活性降低（计划是静态的），但换来更好的 token 效率和更清晰的失败模式。

## 核心概念

### 三个角色

```
规划器：  用户问题 -> [计划 DAG]
工作器：  [计划 DAG] -> [证据]        （工具调用，可能并行）
求解器：  用户问题, 计划 DAG, 证据 -> 最终答案
```

规划器生成一个 DAG。每个节点指定一个工具、其参数以及它所依赖的早期节点（引用如 `#E1`、`#E2`）。工作器按拓扑顺序执行节点。求解器将所有信息拼接在一起。

### 为什么 token 减少 5 倍

ReAct 的提示长度随步骤数线性增长。到第 10 步时，提示中包含了思考 1 加行动 1 加观察 1 加思考 2 加行动 2 加观察 2，依此类推。每个中间步骤还冗余包含了原始提示。

ReWOO 只需一次规划器提示（较大）、N 次小型工作器提示（每个仅包含工具调用，无链条）以及一次求解器提示。在 HotpotQA 上，该论文测量到约 5 倍更少的 token，同时准确率绝对提升了 4%。

### 为什么更鲁棒

如果工作器 3 在 ReAct 中失败，循环必须在运行过程中推理出错误并在中间恢复。在 ReWOO 中，工作器 3 返回一个错误字符串；求解器在上下文中结合原始计划看到该错误，可以优雅地降级处理。失败定位是以节点为单位的，而不是以步骤为单位的。

### 规划器蒸馏

该论文的第二个成果：由于规划器不接触观察结果，你可以用 175B 教师模型的规划器输出来微调一个 7B 模型。小模型负责规划；推理时无需大模型。这已成为标准做法——许多 2026 年生产环境中的 agent 使用小型规划器和大型执行器，或反之。

### Plan-and-Execute（LangChain，2023）

LangChain 团队在 2023 年 8 月的博文中将 ReWOO 泛化成一个模式名称：Plan-and-Execute。前置规划器生成步骤列表，执行器运行每个步骤，一个可选的重规划器可以在观察结果后进行修订。这比 ReWOO 更接近 ReAct（重规划器将观察结果带回规划过程），但保留了 token 节省的优势。

### Plan-and-Act（Erdogan 等人，arXiv:2503.09572，ICML 2025）

Plan-and-Act 将该模式扩展到长 horizon 的网页和移动端 agent。其关键贡献在于合成计划数据：一个带标签的轨迹生成器产生带有显式计划的训练数据。用于微调规划器模型，使其在 WebArena 类任务中能持续工作 30-50 步以上，而单条 ReAct 轨迹在此类任务中会失去连贯性。

### 何时选择哪种模式

| 模式 | 适用场景 |
|------|----------|
| ReAct | 短任务、未知环境、需要响应式异常处理 |
| ReWOO | 具有已知工具的结构化任务、对 token 敏感、证据可并行获取 |
| Plan-and-Execute | 类似 ReWOO，但需要在部分执行后重新规划 |
| Plan-and-Act | 长 horizon（>30 步）、网页/移动端/计算机使用 |
| 思维树（Tree of Thoughts） | 值得为搜索付出代价（第 04 课） |

Anthropic 在 2024 年 12 月的指导建议是：从最简单的模式开始。如果任务只是单次工具调用加一段总结，不要使用 ReWOO。如果任务是 40 步的研究任务，不要仅使用 ReAct。

## 构建它

`code/main.py` 实现了一个示例 ReWOO：

- `Planner`——一个脚本化策略，根据提示生成计划 DAG。
- `Worker`——通过注册表分派每个节点的工具调用。
- `Solver`——脚本化组合，读取证据并生成最终答案。
- 依赖解析——像 `#E1` 这样的引用会被替换为之前工作器的输出。

该演示回答"法国首都的人口是多少（以百万计）？"使用了两个步骤的计划：（1）查找首都，（2）查找人口，然后求解。

运行它：

```
python3 code/main.py
```

追踪信息首先显示完整计划，然后是工作器结果，最后是求解器组合。比较 token 数量（我们打印了粗略的字符计数）与 ReAct 风格的交织运行——ReWOO 在这种结构化任务上胜出。

## 使用它

LangGraph 将 Plan-and-Execute 作为一个配方提供（`create_react_agent` 用于 ReAct，自定义图用于 plan-execute）。CrewAI 的 Flows 直接编码了该模式：你预先定义任务，Flow DAG 执行它们。Plan-and-Act 的合成数据方法仍主要处于研究阶段；运行时模式（显式计划 DAG）已通过 LangGraph 和 CrewAI Flows 投入生产。

## 交付它

`outputs/skill-rewoo-planner.md` 根据用户请求和工具目录生成一个 ReWOO 计划 DAG。它在将计划交给执行器之前会进行验证（无环、每个引用都已解析、每个工具都存在）。

## 练习

1. 对独立的计划节点并行执行工作器。在一个有 2 个并行组的 6 节点 DAG 上，这能带来什么收益？
2. 添加一个重规划器节点，在任意工作器返回错误时触发。使 ReWOO 变成 Plan-and-Execute 的最小改动是什么？
3. 将 `Planner` 替换为小模型（7B 级别），保留 `Solver` 在前沿模型上。比较端到端质量——这种分离在哪些场景下会失败？
4. 阅读 ReWOO 论文中关于规划器蒸馏的第 4 节。在概念层面重现 175B -> 7B 的结果：你需要什么样的训练数据，以及如何评分计划质量？
5. 将示例代码移植到 Plan-and-Act 的轨迹形式：计划是一个序列而非 DAG。哪些权衡发生了变化？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| ReWOO | "不依赖观察的推理" | 先规划，再并行获取证据，然后求解——规划提示中不包含观察结果 |
| Plan-and-Execute | "LangChain 的规划-执行模式" | ReWOO 加上一个执行后可选的重新规划节点 |
| Plan-and-Act | "规模化规划-执行" | 显式的规划器/执行器分离，配合用于长 horizon 任务的合成计划训练数据 |
| 证据引用 | "#E1, #E2, ..." | 计划节点占位符，在分派时替换为之前工作器的输出 |
| 规划器蒸馏 | "小规划器，大执行器" | 在大模型生成的规划轨迹上微调小模型 |
| Token 效率 | "更少的往返次数" | 论文中在 HotpotQA 上相比 ReAct 减少 5 倍 token |
| DAG 执行器 | "拓扑分派器" | 按依赖顺序运行计划节点；每个层级可并行 |
