# 混合式記憶：向量 + 圖 + KV

> 混合式記憶平行跑三種儲存 —— 向量負責語意相似、KV 負責快速事實查找、圖負責實體關係推理 —— 再由一層評分在檢索時把它們融合起來。這是外部記憶被廣泛採用的生產模式；Mem0（Chhikara 等人，2025）是其中一份參考實作。

**類型：** 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 14 · 07（MemGPT）、階段 14 · 08（Letta 區塊）
**時間：** 約 75 分鐘

## 學習目標

- 解釋為何單一儲存（只有向量、只有圖、只有 KV）不足以支撐代理記憶。
- 說出 Mem0 的三種平行儲存，以及各自最佳化的是什麼。
- 描述 Mem0 的融合評分 —— 相關性、重要性、近期性 —— 以及它為何是加權和，而不是階層。
- 用 stdlib 實作一個玩具版三儲存記憶，`add()` 會寫進三者，`search()` 會把結果融合。

## 問題所在

單一儲存對三類查詢中的某一類一定是錯的：

- **語意相似** —— 「我們上週談代理漂移時講了什麼？」向量勝；KV 與圖都會漏。
- **事實查找** —— 「使用者的電話號碼是多少？」KV 勝；向量太浪費，圖是殺雞用牛刀。
- **關係推理** —— 「哪些客戶共用同一個帳務實體？」圖勝；向量與 KV 答不出來。

生產代理會在同一個工作階段裡同時發出這三種查詢。單一儲存的記憶對其中兩種一定是錯的。Mem0 的貢獻在於把三者接在同一組 `add`／`search` 表面之後，並用一個評分函數把它們融合起來。

## 核心概念

### 三種平行儲存

Mem0（arXiv:2504.19413，2025 年 4 月）在 `add(text, user_id, metadata)` 時：

1. 從文字中抽出候選事實（一個由 LLM 驅動的步驟）。
2. 把每則事實寫進向量儲存（嵌入），供語意搜尋。
3. 把每則事實寫進 KV 儲存，鍵為 (user_id, fact_type, entity)，供 O(1) 查找。
4. 把每則事實以具型別的邊寫進圖儲存（Mem0g），供關係查詢。

在 `search(query, user_id)` 時：

1. 向量儲存依嵌入餘弦回傳 top-k。
2. KV 儲存依從查詢導出的 (user_id, type, entity) 回傳直接命中。
3. 圖儲存回傳從查詢實體可達的子圖。
4. 一層評分把三者融合。

### 融合評分

```
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **相關性** —— 向量餘弦、KV 精確匹配、圖的路徑權重。
- **重要性** —— 在寫入時標記，或學出來（有些事實比較重要：姓名、ID、政策）。
- **近期性** —— 依距上次寫入或讀取的時間做指數衰減。

權重要依產品調。聊天代理把 `w_recency` 調高；法遵代理把 `w_importance` 調高；檢索代理把 `w_relevance` 調高。

### Mem0g 與時間性推理

Mem0g 加了一個衝突偵測器。當一則新事實跟既有的邊矛盾時，那條既有的邊會被標成無效，但不刪除。時間性查詢（「使用者三月時住哪個城市？」）會走「在該時點有效」的子圖。

這就是 Letta 的作廢模式所一般化的那種法遵等級行為。

### 基準數字

Mem0 論文回報（2025）：

- **LoCoMo**（長篇對話記憶）：91.6
- **LongMemEval**（長時程情節記憶）：93.4
- **BEAM 1M**（100 萬詞元的記憶基準）：64.1

各條比較基線（128k 全脈絡 LLM、扁平向量儲存、扁平 KV）都輸 10 分以上。光靠基準數字不足以決定選型 —— 運維形狀才是 —— 但這些數字說明融合設計不是捨入誤差。

### 範圍分類

Mem0 依範圍切分記憶：

- **使用者記憶** —— 跨工作階段持久，鍵在 `user_id`。
- **工作階段記憶** —— 在單一討論串內持久。
- **代理記憶** —— 逐代理實例的狀態。

每一次寫入都要挑一個範圍。檢索可以跨範圍查詢，並給每個範圍不同權重。不假思索地混用範圍，就是「助理把 Bob 的專案告訴了 Alice」這類事故的由來。

### 這套模式在哪裡會出錯

- **嵌入漂移。** 前一百次查詢看起來都對的向量結果，會隨語料長大而退化。要定期把使用次數最高的 N 筆紀錄重新嵌入。
- **KV schema 蔓生。** `(user_id, type, entity)` 看起來很簡單，直到每個團隊都加上自己的 `type`。每季稽核一次那組 type。
- **圖爆炸。** 一個很吵的抽取器每則訊息就加 50 條邊。要限制每次 `add` 呼叫可寫入的圖邊數；低信心的邊就丟掉。

## 動手實作

`code/main.py` 用 stdlib 實作這套三儲存模式：

- `VectorStore` —— 用樸素的詞元重疊相似度充當嵌入。
- `KVStore` —— 以 `(user_id, fact_type, entity)` 為鍵的 dict。
- `GraphStore` —— 具型別的邊（subject, relation, object, valid）。
- `Mem0` —— 頂層門面，含 `add()`、`search()`、融合評分與知範圍的檢索。
- 一份在多使用者、多工作階段對話上的實作軌跡。

跑它：

```
python3 code/main.py
```

輸出顯示三條各自獨立的回想路徑，加上融合後的 top-k。把 `main()` 頂端的評分權重翻一翻，看排序怎麼變。

## 框架應用

- **Mem0（Apache 2.0）** —— 生產就緒。用 Postgres + Qdrant + Neo4j 自架，或用託管雲端。
- **Letta** —— core／recall／archival 三層；向量與圖後端自備。
- **Zep** —— 商業替代方案，帶時間性知識圖與事實抽取。
- **自製** —— 當你需要精確掌控抽取器（法遵）或融合權重（近期性主導的語音代理）時。

## 練習

1. 把玩具版的向量相似度換成真正的嵌入模型（sentence-transformers、Ollama、OpenAI embeddings）。在一段合成的長對話上量 recall@10。經過 1000 次寫入後，排序會漂移嗎？
2. 加一個時間性查詢：`search(query, as_of=timestamp)`。只回傳在該時點或之前有效的紀錄。哪個儲存要動的工最多？
3. 實作一個衝突偵測器：若一則進來的事實跟某條圖邊矛盾，就把舊邊作廢並把兩者都記錄下來。用「使用者住柏林」-> 「使用者住里斯本」來測。
4. 把融合評分器擴充成含一個 `user_feedback` 維度（對檢索到的紀錄按讚）。你要怎麼防止被操弄（代理只回傳它自己已經喜歡的紀錄）？
5. 讀 Mem0 文件（`docs.mem0.ai`）。把這個玩具移植成 `mem0` 的客戶端呼叫。在同樣 20 條測試查詢上比較檢索品質。
