# Reflexion: 语言强化学习

> 基于梯度的强化学习需要数千次试验和 GPU 集群才能修复一个失败模式。Reflexion（Shinn 等人，NeurIPS 2023）用自然语言来完成这一任务：每次试验失败后，智能体撰写一条反思，将其存储在情景记忆中，并在下一次试验时将该记忆作为上下文条件。这是 Letta 的睡眠时间计算（sleep-time compute）、Claude Code 的 CLAUDE.md 学习记录以及 pro-workflow 的 learn-rule 背后的模式。

**类型：** 构建
**语言：** Python（标准库）
**前置知识：** 阶段 14 · 01（智能体循环），阶段 14 · 02（ReWOO）
**时长：** 约 60 分钟

## 学习目标

- 说出 Reflexion 的三个组成部分（Actor、Evaluator、Self-Reflector）以及情景记忆的作用。
- 用标准库实现一个包含二元评估器、反思缓冲区和全新重试的 Reflexion 循环。
- 为给定任务在标量反馈、启发式反馈和自我评估反馈之间做出选择。
- 解释为什么语言强化能够捕捉到基于梯度的强化学习需要数千次试验才能修复的错误。

## 问题

智能体在执行任务时失败。在标准强化学习中，你需要再运行数千次试验、计算梯度、更新权重。这既昂贵又缓慢，而且大多数生产环境中的智能体不会为每一次失败都分配训练预算。

Reflexion（Shinn 等人，arXiv:2303.11366）提出了一个不同的问题：如果智能体只是思考自己失败的原因，然后带着这个思考重新尝试呢？没有权重更新，没有梯度。只有自然语言在试验之间存储。

结果：在 ALFWorld 上，它击败了 ReAct 和其他未经微调的基线模型。在 HotpotQA 上，它相比 ReAct 有所改进。在代码生成（HumanEval/MBPP）上，它创下了当时的最高水平。全程没有使用一个梯度步骤。

## 概念

### 三个组成部分

```
Actor          : 生成一条轨迹（ReAct 风格循环）
Evaluator      : 对轨迹评分——二元、启发式或自我评估
Self-Reflector : 针对失败撰写一条自然语言反思
```

再加上一个数据结构：

```
情景记忆: 先前反思的列表，附加到下一次试验的提示词前面
```

一次试验运行 Actor。Evaluator 对其评分。如果评分较低，Self-Reflector 生成一条反思（"我选错了工具，因为我误以为问题是在问 X，而实际上它是在问 Y"）。反思进入情景记忆。下一次试验从头开始，但会看到这条反思。

### 三种评估器类型

1. **标量型**——一个外部的二元信号。ALFWorld 成功或失败。HumanEval 测试通过或不通过。最简单，信号最强。
2. **启发式型**——预定义的失败特征。"如果智能体连续两次产生相同动作，标记为卡住。""如果轨迹超过 50 步，标记为低效。"
3. **自我评估型**——LLM 对自己的轨迹进行评分。当没有真实答案可用时使用。信号较弱；与基于工具的验证配合良好（第 05 课——CRITIC）。

2026 年的默认方案是混合使用：有真实答案时用标量型，没有时用自我评估型，启发式型作为安全护栏。

### 为什么这具有普适性

Reflexion 与其说是一个新算法，不如说是一个已命名的模式。几乎每个生产环境中的"自愈"智能体都运行某种变体：

- Letta 的睡眠时间计算（第 08 课）：一个独立的智能体对过去的对话进行反思并写入记忆块。
- Claude Code 的 `CLAUDE.md` / "保存记忆"模式：将反思捕获为学习记录，附加到未来的会话中。
- pro-workflow 的 `/learn-rule` 命令：将修正捕获为显式规则。
- LangGraph 的反思节点：一个对输出进行评分并路由到精炼步骤的节点。

所有这些都源自同一个洞见：自然语言是一种足够丰富的媒介，可以在两次运行之间承载"我从失败中学到了什么"。

### 何时有效，何时无效

Reflexion 在以下情况下有效：

- 存在明确的失败信号（测试失败、工具错误、答案错误）。
- 任务类别是可重复的（同一类型的问题可以再次被提出）。
- 反思有足够的空间在轨迹上做出改进（足够的行动预算）。

Reflexion 在以下情况下没有帮助：

- 智能体已经在第一次尝试时成功了。
- 失败是外部原因（网络中断、工具故障）——反思"网络中断了"对未来运行没有帮助。
- 反思变成了迷信——存储关于一次性不稳定运行的叙述。

2026 年的陷阱：记忆腐化（memory rot）。反思不断累积；有些已经过时或错误；随着情景缓冲区的增长，重新运行变得越来越慢。缓解措施：定期压缩（第 06 课）、为反思设置 TTL，或者使用一个独立的睡眠时间清理智能体（Letta）。

## 构建它

`code/main.py` 在一个玩具谜题上实现了 Reflexion：生成一个包含 3 个元素且总和等于目标的列表。Actor 发出候选列表；Evaluator 检查总和；Self-Reflector 写一行关于问题出在哪里的反思。反思进入情景记忆，供下一次试验使用。

组件：

- `Actor`——一个脚本化的策略，在看到反思时会改进。
- `Evaluator.binary()`——对目标总和进行通过/失败判断。
- `SelfReflector`——生成一行对失败的诊断。
- `EpisodicMemory`——一个带有 TTL 语义的有界列表。

运行它：

```
python3 code/main.py
```

追踪信息显示三次试验。试验 1 失败，存储了一条反思；试验 2 看到了反思并有所改进，但仍然失败；试验 3 成功。与基线运行（无反思）对比——基线会一直停留在试验 1 的答案上。

## 使用它

LangGraph 将反思作为一个节点模式提供。Claude Code 的 `/memory` 命令和 pro-workflow 的 `/learn-rule` 将情景缓冲区外部化为一个 Markdown 文件。Letta 的睡眠时间计算在空闲时运行 Self-Reflector，使主智能体保持低延迟。OpenAI Agents SDK 不直接提供 Reflexion；你需要通过自定义 Guardrail（按分数拒绝轨迹）和跨运行持久化的 `Session` 记忆来构建它。

## 交付它

`outputs/skill-reflexion-buffer.md` 创建并维护一个带有反思捕获、TTL 和去重功能的情景缓冲区。给定一个任务类别和一个失败，它会生成一条确实对下一次试验有帮助的反思（而不是一句泛泛的"再仔细一点"）。

## 练习

1. 从二元评估器切换到返回距离度量（离目标有多远）的标量评估器。收敛速度会加快吗？
2. 为反思添加 10 次试验的 TTL。超过这个点之后，旧的反思是有害还是有益？
3. 实现启发式评估器：如果相同动作重复出现，将试验标记为卡住。这与 Self-Reflector 如何交互？
4. 用一个对抗性的 Actor（忽略反思）运行 Reflexion。最少需要什么样的反思提示工程才能迫使 Actor 注意到反思？
5. 阅读 Reflexion 论文第 4 节关于 ALFWorld 的部分。从概念上重现 130% 的成功率提升：与普通 ReAct 相比，关键的差异是什么？

## 关键术语

| 术语 | 人们通常说的 | 实际含义 |
|------|------------|---------|
| Reflexion | "自我修正" | Shinn 等人 2023——Actor、Evaluator、Self-Reflector 加情景记忆 |
| 语言强化 | "无梯度学习" | 自然语言反思，附加到下一次试验的提示词前面 |
| 情景记忆 | "每个任务的反思" | 针对一个任务类别的有界先前反思缓冲区 |
| 标量评估器 | "二元成功信号" | 基于真实答案的通过/失败或数值评分 |
| 启发式评估器 | "基于模式的检测器" | 预定义的失败特征（如卡死循环、步数过多） |
| 自我评估器 | "LLM 对自己的轨迹进行评判" | 在没有真实答案时使用的低信号备选方案——与基于工具的验证配合使用 |
| 记忆腐化 | "过时的反思" | 情景缓冲区充满了过时条目；通过压缩/TTL 修复 |
| 睡眠时间反思 | "异步自我反思" | 在主路径之外运行 Self-Reflector，使主智能体保持快速响应 |
