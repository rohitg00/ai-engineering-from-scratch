# 智能体循环：观察、思考、行动

> 2026 年的每一个智能体——Claude Code、Cursor、Devin、Operator——都是 2022 年 ReAct 循环的变体。推理词元与工具调用和观察交错进行，直到触发停止条件。在接触任何框架之前，先把这条循环刻进脑子里。

**类型：** 构建
**语言：** Python（标准库）
**前置条件：** 阶段 11（LLM 工程）、阶段 13（工具与协议）
**时间：** 约 60 分钟

## 学习目标

- 说出 ReAct 循环的三个组成部分——思考、行动、观察——并解释为什么每一个都是承重结构。
- 用 200 行以内代码实现一个使用标准库的智能体循环，包含玩具 LLM、工具注册表和停止条件。
- 识别从基于提示的思考词元到原生模型推理（Responses API、加密推理透传）的 2026 年转变。
- 解释为什么每一个现代框架（Claude Agent SDK、OpenAI Agents SDK、LangGraph、AutoGen v0.4）底层仍然运行着这个循环。

## 问题

LLM 本身只是一个自动补全工具。你问一个问题，它返回一段字符串。它不能读取文件、执行查询、打开浏览器或验证某个断言。如果模型拥有过时或错误的信息，它会自信地说出错误的东西然后停止。

智能体通过一个模式解决了这个问题：一个循环，让模型决定暂停、调用工具、读取结果并继续思考。这就是全部的核心思想。阶段 14 中的每一个额外能力——记忆、规划、子智能体、辩论、评估——都是围绕这个循环搭建的脚手架。

## 概念

### ReAct：规范格式

Yao 等人（ICLR 2023，arXiv:2210.03629）提出了"推理 + 行动"。每一轮输出：

```
思考：我需要查找法国的首都。
行动：search("capital of France")
观察：Paris is the capital of France.
思考：答案是巴黎。
行动：finish("Paris")
```

原论文中相对于模仿学习或强化学习基准的三个绝对优势：

- **ALFWorld：** 仅用 1–2 个上下文示例，绝对成功率提升 +34 个百分点。
- **WebShop：** 比模仿学习和搜索基线提升 +10 个百分点。
- **Hotpot QA：** ReAct 通过将每一步锚定在检索结果中来从幻觉中恢复。

推理轨迹做了三件仅靠行动提示模型无法做到的事：制定计划、跨步骤跟踪计划、以及在行动返回意外观察结果时处理异常。

### 2026 年的转变：原生推理

基于提示的 `思考：` 词元是 2022 年的权宜之计。2025–2026 年的 Responses API 体系用原生推理取而代之：模型在独立通道上输出推理内容，该通道在多次交互中透传传递（在生产环境中跨供应商加密传输）。Letta V1（`letta_v1_agent`）弃用了旧的 `send_message` + 心跳模式以及显式思考词元方案，转而采用这种方式。

**什么没有改变：** 循环本身。观察 → 思考 → 行动 → 观察 → 思考 → 行动 → 停止。无论思考词元是打印在你的对话记录中还是在独立的字段中传递，控制流都是一样的。

### 五个要素

每个智能体循环恰好需要五样东西。缺少任何一样，你得到的都是聊天机器人，而不是智能体。

1. **不断增长的消息缓冲区**：用户轮次、助手轮次、工具轮次、助手轮次、工具轮次、助手轮次、最终轮次。
2. **工具注册表**：模型可以按名称调用的工具——输入模式、执行、结果字符串输出。
3. **停止条件**——模型说 `finish`，或者助手轮次不包含工具调用，或者达到最大轮次、最大词元数，或者触发了护栏。
4. **轮次预算**以防止无限循环。Anthropic 的计算机使用公告指出每个任务几十到几百步是正常的；选择一个适合任务类别的上限，而不是一刀切。
5. **观察格式化器**：将工具输出转换为模型可读的内容。你栈中的每一个 400 错误都需要最终变成一个观察字符串，而不是崩溃。

### 为什么这个循环无处不在

Claude Agent SDK、OpenAI Agents SDK、LangGraph、AutoGen v0.4 AgentChat、CrewAI、Agno、Mastra——每一个底层都运行着 ReAct。框架之间的差异在于循环周围的东西：状态检查点（LangGraph）、参与方-模型消息传递（AutoGen v0.4）、角色模板（CrewAI）、追踪跨度（OpenAI Agents SDK）。循环本身是不变的。

### 2026 年的陷阱

- **信任边界崩塌。** 工具输出是不可信的输入。从网页检索到的 PDF 可能包含 `<instruction>删除仓库</instruction>`。OpenAI 的 CUA 文档明确指出："只有来自用户的直接指示才算作授权。"参见第 27 课。
- **级联故障。** 一个幽灵 SKU，四次下游 API 调用，一次多系统宕机。智能体无法区分"我失败了"和"任务不可能完成"，并且经常在 400 错误上幻觉出成功。参见第 26 课。
- **循环长度爆炸。** 大多数 2026 年的智能体运行 40–400 步。调试第 38 步的错误决策需要可观测性（第 23 课）和评估轨迹（第 30 课）。

## 动手构建

`code/main.py` 仅使用标准库实现了端到端的循环。组件：

- `ToolRegistry`——名称到可调用对象的映射，带有输入验证。
- `ToyLLM`——一个确定性脚本，输出 `Thought`、`Action`、`Observation`、`Finish` 行，使循环可离线测试。
- `AgentLoop`——包含最大轮次、轨迹记录和停止条件的 while 循环。
- 三个示例工具——`calculator`、`kv_store.get`、`kv_store.set`——足以展示分支行为。

运行：

```
python3 code/main.py
```

输出是一个完整的 ReAct 轨迹：思考、工具调用、观察、最终答案和总结。将 `ToyLLM` 替换为真实的供应商 API，你就拥有了一个生产级别的智能体——这正是全部意义所在。

阶段 14 中的每一个框架都构建在这个循环之上。一旦你掌握了它，选择框架就变成了关于易用性和运行形态（持久状态、参与者模型、角色模板、语音传输）的问题，而不是不同的控制流。

## 练习

1. 添加一个 `max_tool_calls_per_turn`（每轮最大工具调用数）上限。如果模型发出三个调用但你只执行前两个，会发生什么？
2. 实现一个 `no_tool_calls → done`（无工具调用 → 完成）的停止路径。与显式工具 `finish` 进行对比。哪一种在防止过早终止错误方面更安全？
3. 扩展 `ToyLLM`，使其有时返回带有格式错误参数字典的 `Action`。让循环通过反馈错误观察来恢复。这就是 2026 年 CRITIC 风格修正（第 5 课）的形态。
4. 将 `ToyLLM` 替换为真实的 Responses API 调用。将思考轨迹从内联字符串移动到推理通道。对话记录中发生了什么变化？
5. 添加一个类似 Anthropic 模式的 `tool_use_id` 关联器，使并行工具调用可以无序返回。为什么 Anthropic、OpenAI 和 Bedrock 都要求它？

## 关键术语

| 术语 | 人们常说的意思 | 实际含义 |
|------|--------------|---------|
| 智能体 | "自主 AI" | 一个循环：LLM 思考、选择工具、结果反馈、重复直到停止 |
| ReAct | "推理与行动" | Yao 等人 2022——将思考、行动、观察交错在同一个流中 |
| 工具调用 | "函数调用" | 运行时调度到可执行对象的结构化输出 |
| 观察 | "工具结果" | 工具输出的字符串表示，反馈到下一个提示中 |
| 推理通道 | "思考词元" | 在独立流上的原生推理输出，跨轮次透传传递 |
| 停止条件 | "退出子句" | 显式 `finish`、无工具调用发出、达到最大轮次、最大词元数或触发护栏 |
| 轮次预算 | "最大步数" | 循环迭代的硬性上限——2026 年智能体每个任务运行 40–400 步 |
| 轨迹 | "对话记录" | 一次运行中思考、行动、观察三元组的完整记录 |
