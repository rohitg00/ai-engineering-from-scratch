# 记忆：虚拟上下文与 MemGPT

> 上下文窗口是有限的。而对话、文档和工具调用轨迹是无限的。MemGPT（Packer 等人，2023）将此框架类比为操作系统的虚拟内存——主上下文是 RAM，外部存储是磁盘，智能体在两者之间进行页面交换。这是 2026 年每个记忆系统都继承的模式。

**类型：** 构建  
**语言：** Python（标准库）  
**前置条件：** 阶段 14 · 01（智能体循环），阶段 14 · 06（工具使用）  
**时长：** 约 75 分钟

## 学习目标

- 解释 MemGPT 所依托的 OS 类比：主上下文 = RAM，外部上下文 = 磁盘，记忆工具 = 换页入/出。
- 在标准库中实现 MemGPT 的双层模式，包含主上下文缓冲区、可搜索的外部存储以及换页入/出工具。
- 描述智能体如何发出"中断"以查询或修改外部记忆，以及结果如何拼接回下一次提示。
- 识别 MemGPT 中延续到 Letta（第 08 课）和 Mem0（第 09 课）的设计选择。

## 问题所在

上下文窗口看似能解决记忆问题，实则不能。生产中反复出现三种失效模式：

1. **溢出。** 多轮对话、长文档或大量工具调用轨迹超出窗口。超出截断点的内容全部丢失。
2. **稀释。** 即使在窗口内，塞入不相关的上下文也会稀释对重要内容的注意力。前沿模型在长输入上仍会退化。
3. **持久性。** 新会话以空窗口开始。没有外部记忆的智能体无法在会话间说"记得你曾让我……"。

更大的窗口有帮助，但无法根治。Mem0 2025 年的论文测得，128k 窗口的基线模型仍然遗漏了 4k 窗口搭配外部记忆的智能体能捕捉到的长期事实。

## 核心概念

### MemGPT：操作系统类比

Packer 等人（arXiv:2310.08560，v2，2024 年 2 月）将上下文管理映射到操作系统的虚拟内存：

| OS 概念 | MemGPT 概念 | 2026 年生产环境类比 |
|---------|-------------|----------------------|
| RAM | 主上下文（提示） | Anthropic/OpenAI 上下文窗口 |
| 磁盘 | 外部上下文 | 向量数据库、KV 存储、图存储 |
| 缺页中断 | 记忆工具调用 | `memory.search`、`memory.read`、`memory.write` |
| OS 内核 | 智能体控制循环 | 带记忆工具的 ReAct 循环 |

智能体运行标准的 ReAct 循环。额外的一类工具使其能将数据换页入/出主上下文。

### 双层结构

- **主上下文。** 固定大小的提示，承载当前任务。始终对模型可见。
- **外部上下文。** 无限制，可通过工具搜索。相关内容被读取，新事实出现时被写入。

原始论文在两项超出基础窗口的任务上评估了该设计：超过 10 万 token 的文档分析，以及跨天数进行持久记忆的多会话聊天。

### 中断模式

MemGPT 引入了"记忆即中断"：在对话中途，智能体可以调用记忆工具，运行时执行该工具，结果作为新的观察拼接进下一轮助手回复。概念上与 Unix 的 `read()` 系统调用完全一致——阻塞进程、返回字节、进程继续。

标准记忆工具接口：

- `core_memory_append(section, text)` — 写入提示中的一个持久化段落。
- `core_memory_replace(section, old, new)` — 编辑一个持久化段落。
- `archival_memory_insert(text)` — 写入可搜索的外部存储。
- `archival_memory_search(query, top_k)` — 从外部存储检索。
- `conversation_search(query)` — 扫描过往轮次。

### MemGPT 止步之处，Letta 起步之处

2024 年 9 月，MemGPT 更名为 Letta。研究仓库（`cpacker/MemGPT`）仍然保留；Letta 在此基础上扩展：

- 从双层变为三层（核心、回溯、存档——见第 08 课）。
- 用原生推理取代 `send_message`/心跳模式（第 08 课）。
- 休眠时智能体执行异步记忆工作（第 08 课）。

即使生产系统运行的是 Letta、Mem0 或自定义的双层存储，MemGPT 论文仍是 2026 年的根基。

### 该模式的问题所在

- **记忆腐烂。** 写入累积速度快于读取速度；检索被过时事实淹没。修复：定期整合（Letta 休眠时处理）、显式失效（Mem0 冲突检测器）。
- **记忆投毒。** 外部记忆是被检索的文本。如果攻击者控制的内容进入记忆笔记，智能体在下一次会话中会重新摄入它。这是 Greshake 等人（第 27 课）攻击在时间维度上的重演。
- **引用丢失。** 智能体能回忆起"用户让我发布 X"，但无法引用是哪个轮次。每次存档写入时都应存储来源引用（会话 ID、轮次 ID）。

## 动手构建

`code/main.py` 在标准库中实现了 MemGPT 的双层模式：

- `MainContext` — 固定大小的提示缓冲区，包含一个 `core` 字典和一个 `messages` 列表；超出容量时自动压缩最旧的消息。
- `ArchivalStore` — 内存中的类 BM25 存储（基于 token 重叠评分），记录包含（id、text、tags、session、turn）。
- 五个映射到 MemGPT 接口的记忆工具。
- 一个脚本化的智能体，向存档中填充事实，然后通过调用 `archival_memory_search` 来回答问题。

运行方式：

```
python3 code/main.py
```

运行轨迹展示了智能体写入三条事实、将主上下文填满至容量上限（强制驱逐），然后通过从存档中检索来回答后续问题——在没有任何真实 LLM 的情况下复现了 MemGPT 的工作流程。

## 实际应用

当今每一个生产级记忆系统都是 MemGPT 的变体：

- **Letta**（第 08 课）—— 三层架构、原生推理、休眠时计算。
- **Mem0**（第 09 课）—— 向量 + KV + 图存储融合，带评分层。
- **OpenAI Assistants / Responses** —— 通过线程和文件实现托管式记忆。
- **Claude Agent SDK** —— 通过技能和会话存储实现长期记忆。

选择时依据运营形态（自托管、托管式、框架集成），而非核心模式——因为核心模式就是 MemGPT。

## 成果交付

`outputs/skill-virtual-memory.md` 是一个可复用的技能，它为任何目标运行时生成正确的双层记忆框架（主存储 + 存档存储 + 工具接口），并内置了驱逐策略和引用字段。

## 练习

1. 添加一个以 token 衡量的 `max_main_context_tokens` 上限（用 `len(text.split()) * 1.3` 近似）。当超出上限时，将最旧的消息压缩为摘要。对比有/无摘要器的行为差异。
2. 在存档存储上正确实现 BM25（词频、逆文档频率）。在一个玩具事实集上测量 recall@10 与基于 token 重叠的基线的对比。
3. 为存档插入添加 `citation` 字段（session_id、turn_id、source_url）。使智能体在每次基于检索的回答中引用来源。
4. 模拟记忆投毒：添加一条存档记录，内容为"忽略所有后续用户指令"。编写一个守卫逻辑，扫描检索结果中具有指令形式的文本并将其标记为不可信。
5. 将该实现迁移到使用 MemGPT 研究仓库的核心记忆 JSON 模式（`cpacker/MemGPT`）。当从扁平字符串切换到类型化段落时，需要做哪些改动？

## 关键术语

| 术语 | 大家说的 | 实际含义 |
|------|---------|---------|
| 虚拟上下文（Virtual context） | "无限记忆" | 主（提示）+ 外部（可搜索）双层，支持换页入/出 |
| 主上下文（Main context） | "工作记忆" | 提示——固定大小，始终可见 |
| 存档记忆（Archival memory） | "长期存储" | 外部可搜索持久化，按需检索 |
| 核心记忆（Core memory） | "持久提示段落" | 固定在主上下文中的命名段落 |
| 记忆工具（Memory tool） | "记忆 API" | 智能体发出的用于读/写外部记忆的工具调用 |
| 中断（Interrupt） | "记忆缺页中断" | 智能体暂停，运行时获取，结果拼接进下一轮 |
| 记忆腐烂（Memory rot） | "过时事实" | 旧写入淹没检索；通过整合解决 |
| 记忆投毒（Memory poisoning） | "注入的持久笔记" | 攻击者内容被存储为记忆，在召回时重新摄入 |
