# 失敗模式：代理為什麼會壞掉

> MASFT（柏克萊，2025）把 14 種多代理失敗模式編成 3 個類別。Microsoft 的失敗模式分類法記錄了既有的 AI 失敗如何在代理式情境中被放大。業界的田野資料則收斂到五種反覆出現的模式：幻覺行動、範圍蔓延、連鎖錯誤、脈絡遺失、工具誤用。

**類型：** 學習 + 實作
**程式語言：** Python (stdlib)
**先修單元：** 階段 14 · 05（Self-Refine 與 CRITIC）、階段 14 · 24（可觀測性）
**時間：** 約 60 分鐘

## 學習目標

- 說出 MASFT 的三個失敗類別，以及每個類別至少四種具體模式。
- 解釋代理式的失敗為何會放大既有的 AI 失敗模式（偏誤、幻覺）。
- 描述那五種業界反覆出現的模式與它們的緩解方式。
- 用 stdlib 實作一個偵測器，替代理軌跡貼上失敗模式標籤。

## 問題所在

團隊出貨的代理在 90% 的軌跡上都運作良好。那 10% 的失敗並不是隨機雜訊 —— 它們落在少數幾個反覆出現的類別裡。一旦你叫得出它們的名字，你就能監控它們、修好它們。

## 核心概念

### MASFT（柏克萊，arXiv:2503.13657）

多代理系統失敗分類法。14 種失敗模式，聚成 3 個類別。標註者間的 Cohen's Kappa 為 0.88 —— 這些類別是可靠可分辨的。

核心主張：這些失敗是多代理系統根本的設計缺陷，不是那種換更好的基礎模型就修得掉的 LLM 侷限。

### Microsoft 的〈Taxonomy of Failure Mode in Agentic AI Systems〉

- 既有的 AI 失敗（偏誤、幻覺、資料外洩）在代理式情境中會被放大。
- 新的失敗從自主性中浮現：規模化的非預期行動、工具誤用、任務漂移。
- 這份白皮書就是代理式產品的風險登記簿。

### 〈Characterizing Faults in Agentic AI〉（arXiv:2603.06847）

- 失敗源自編排、內部狀態演變，以及與環境的互動。
- 不只是「爛程式碼」或「爛模型輸出」。

### LLM 代理幻覺綜述（arXiv:2509.18970）

兩種主要表現：

1. **指示遵循偏離** —— 代理不照系統提示詞走。
2. **長距脈絡誤用** —— 代理忘記或錯用了較早輪次的脈絡。

子意圖錯誤：遺漏（漏掉一步）、冗餘（重複一步）、失序（步驟順序亂掉）。

### 那五種業界反覆出現的模式

Arize、Galileo、NimbleBrain 在 2024-2026 年的田野分析收斂到：

1. **幻覺行動。** 代理調用了不存在的工具，或捏造參數。
2. **範圍蔓延。** 代理把任務擴張到使用者要求之外（開了多餘的 PR、寄了多餘的信）。
3. **連鎖錯誤。** 一次錯誤呼叫觸發下游效應。一個幽靈 SKU 的幻覺觸發四次 API 呼叫 —— 變成一次多系統事故。
4. **脈絡遺失。** 長時程任務忘掉了早期輪次的限制。
5. **工具誤用。** 用錯的參數呼叫對的工具，或根本呼叫錯工具。

連鎖是最要命的。代理分不出「我失敗了」與「這任務不可能」，而且常常在 400 錯誤上幻覺出一則成功訊息來把迴圈收掉。

### 緩解：每一步都設閘門

在推理鏈的每一步都設自動化查證閘門，對照環境狀態檢查事實接地。具體來說：

- 逐步的安全分類器（第 21 課）。
- 工具呼叫的參數驗證（第 06 課）。
- 把檢索到的內容跟已知事實交叉比對（第 05 課，CRITIC）。
- 靠重新探測狀態來偵測成功幻覺（那個檔案真的建好了嗎？）。

### 失敗監控在哪裡會出錯

- **只替崩潰打標。** 多數代理失敗產出的是看起來很有效的輸出。需要內容層級的檢查。
- **沒有基線。** 漂移偵測需要一個最後已知良好的版本；沒有它，你說不出「這件事正在變糟」。
- **警示過多。** 每次失敗都發一次呼叫。要分群並做速率限制。

## 動手實作

`code/main.py` 用 stdlib 實作一個失敗模式標記器：

- 一份涵蓋那五種模式的合成軌跡資料集。
- 逐模式的偵測函數（在工具呼叫、輸出、重複行動上的特徵樣式）。
- 一個標記器，替每條軌跡貼標並回報模式分布。

跑它：

```
python3 code/main.py
```

輸出：逐軌跡的標籤 + 彙總分布，以很便宜的方式重現 Phoenix 的軌跡分群會浮出來的東西。

## 框架應用

- **Phoenix** 給生產環境的漂移分群（第 24 課）。
- **Langfuse** 給工作階段重播 + 標註。
- **自製** 給那些你的可觀測性平台偵測不到的領域專屬特徵。

## 產出交付

`outputs/skill-failure-detector.md` 會產出量身訂做給你領域的失敗模式偵測器，並接上一個軌跡儲存。

## 練習

1. 加一個「成功幻覺」偵測器：代理回傳成功，但目標狀態根本沒變。
2. 從你做過的產品裡挑 100 條真實軌跡貼標。哪種模式佔多數？修好它的成本是多少？
3. 實作一個「連鎖半徑」指標：給定第 N 步的一次失敗，它影響了多少下游步驟？
4. 讀 MASFT 的 14 種失敗模式。挑三種適用於你產品的。替它們寫偵測器。
5. 把其中一個偵測器接進 CI 工作：若有 >=5% 的軌跡被貼上某個模式，就讓建置失敗。

## 關鍵術語

| 術語 | 大家怎麼說 | 實際是什麼意思 |
|------|----------------|------------------------|
| MASFT | 「多代理失敗分類法」 | 柏克萊那份 14 模式的分類 |
| 連鎖錯誤 | 「漣漪式失敗」 | 一個早期的錯誤傳播過 N 個步驟 |
| 脈絡遺失 | 「忘了那條限制」 | 長時程的輪次把早期輪次的事實掉了 |
| 工具誤用 | 「錯的工具／錯的參數」 | 有效的呼叫，錯誤的調用 |
| 成功幻覺 | 「假裝完成」 | 代理在 400 上宣稱成功；狀態根本沒變 |
| 範圍蔓延 | 「越權」 | 代理做了比被要求的更多的事 |
| 指示遵循偏離 | 「不服從」 | 無視系統提示詞或使用者的限制 |
| 子意圖錯誤 | 「計畫層的臭蟲」 | 計畫執行中的遺漏、冗餘、失序 |
