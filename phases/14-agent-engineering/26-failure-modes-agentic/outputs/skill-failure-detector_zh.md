给定一个产品领域和一个追踪存储，生成代理失败模式的检测器。

产出：

1. 每个模式一个检测器：`hallucinated_action`、`scope_creep`、`cascading_errors`、`context_loss`、`tool_misuse`、`success_hallucination`。
2. 领域特定的检测器（例如，对于开发工具："创建了 PR 但未关联 issue"；对于营销工具："未经确认向超过 5 个收件人发送邮件"）。
3. 标记器，将所有检测器应用于每个追踪并输出分布。
4. 基于阈值的告警：如果今天 >=5% 的追踪标记了某个模式，则发送页面或创建工单。
5. 样本保留：对每个被标记的追踪，保留输入 + 输出 + 状态快照供操作者审查。

硬性拒绝：

- 在生产环境中每个追踪需要 LLM 调用的检测器。使用基于模式的检测器；将 LLM 判断器保留用于采样审查。
- 仅在崩溃时标记。大多数失败产生看似有效的输出。需要基于内容 + 状态的特征检查。
- 存储被标记的追踪而不进行个人身份信息脱敏。失败样本携带最糟糕的内容；存储前必须擦除。

拒绝规则：

- 如果用户想要"所有追踪永久存储"，因成本 + 合规原因拒绝。按标签 + 速率采样。
- 如果产品没有"已知良好"的基线，拒绝漂移告警。漂移需要一个参照。
- 如果检测器没有版本管理，拒绝。检测器回归会在无声中破坏你的信号。

输出：`detectors.py`、`tagger.py`、`alerts.py`、`retention.py`、`README.md`，解释阈值、保留策略、告警路由。以"下一步阅读"结尾，指向第 24 课（可观测性后端）或第 27 课（提示注入）以了解对抗性失败模式。
